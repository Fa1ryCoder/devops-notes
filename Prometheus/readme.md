Начнем с определения Prometheus. Что такое Prometheus?
"Prometheus" — это система мониторинга, которая собирает и хранит метрики как временные ряды, используя уникальную многомерную модель данных с labels (тегами). Она работает по pull-модели (сама опрашивает targets по http с помощью config где указаны nodes), предоставляет мощный декларативный язык запросов PromQL для агрегации и анализа, имеет встроенный механизм алертинга и активно используется в cloud-native стеках (Kubernetes)
Все равно остаются вопросы по определению. Метрика, временной ряд и т.д. Что же все это такое?

"Метрика (metrics)" - это измерение какого либо параметра системы во времени. Проще: это число которое, Prometheus регулярно запысывает. Например:
    Загрузка CPU = 72%
    Свободная память = 1.3 GB
    Количество HTTP-запросов = 152
    температура сервера = 45°C
Важно отметить что Prometheus оперирует сырыми числами(row data) и не хранит информацию о единицах измерения. Чтобы превратить его в осмысленную метрику (например, в процент загрузки или скорость запросов в секунду), данные необходимо обработать с помощью PromQL(Это уже задача специалиста кто создает запросы). Изначально данные будут выглядить вот так: 0.72 (ratio), 1395864371 (bytes), 1003152, 45000.
В Prometheus метрика выглядит примерно так:
    node_cpu_seconds_total{cpu="0",mode="idle"} 12345.6
Здесь:
    - node_cpu_seconds_total = имя метрики
    - {cpu="0",mode="idle"} = метки (labels)
    - 12345.6 = значение

"Временной ряд (time series)" - это история значения метрики во времени. То есть Prometheus не просто хранит одно число. Он хранит: 
    время --> значение. 
Например:
    12:00 --> CPU = 40%
    12:01 --> CPU = 55%
    12:02 --> CPU = 72%
    12:03 --> CPU = 38%
Это и есть временной ряд. Временный ряды хранятся локально на диске, можно опционально интегрировать с удалёнными системами хранения. Он собирает данные(метрики во времени), примерно, ~2 часа и потом запечатывает в блок. Пример блока:
    /01KGPQB344WPSFXVM8F0A1XJCR
Важно: Мы не собираем данные когда пишем, например, метрику: node_cpu_seconds_total{mode="idle"}[5m]. Мы запрашиваем собранные данные с помощью PromQL. PromQL это язык запросов, а не сбора! 
Процесс перемещения метрик я разбил на 2 этапа. Этап №1: 
Каждые 15 секунд (по настройке из конфига) Prometheus дергает http://node-exporter:9100/metrics и получает метрики с ноды с дефолтными тегами. Идет добавление лейблов которые мы указываем в /etc/prometheus/prometheus.yml и записывается в WAL. 
WAL (Write Ahead Log, wal) - это черновик страховка. Простой бинарный файл на диске куда Prometheus изначально записывает метрики. Цель простая: если сервер умрет, то при включении Prometheus восстановит те частичные данные которые он успел записать в WAL.
HEAD(chunks_head) - это структура данных которая лежит в оперативке(RAM). Зачем же она нужна? А все очень просто. Когда мы, например, в графане открываем график за последние 5 минут, то Prometheus сначала лезет именно в chunks_head, а не в архивы данных. Т.к. запросы к RAM обрабатываются практически мгновенно. RAM работает в тысячи раз быстрее диска. Но память штука дорогая и не резиновая. Поэтому данные в chunks_head не могут жить вечно. После того как прошло 2 часа, HEAD заполнился. Прометей берет всё, что накопилось в HEAD, упаковывает и сжимает в 10 раз и превращает в блок(та самая директория из примера про блок). После того как блок сохранен, старый WAL уже не нужен и он удаляется.
lock - этот файл гарантирует что только один экземпляр Prometheus работает с данными в один момент времени, предотвращая конфликты записи другим Prometheus. Когда Prometheus стартует создается файл lock и если другой экземпляр начнет писать туда же то получится ошибка:
    database is locked
Другими словами файл-блокировщик который не дает записывать данные в TSDB

Небольшое резюме по этому процессу:
1. При старте Prometheus создается lock + восстановление HEAD из WAL
2. Пришла метрика
3. Добавили лейблы и записали в WAL (защита от потери данных)
4. Тут же добавили в HEAD в оперативку (теперь мы можем отрисовать это на графике)
5. Прошло 2 часа, HEAD заполнился
6. Освобождение HEAD путем упаковывания, сжимания и перемещения в блоки
7. Когда блок сохранен, удаляются старые сегменты WAL

"Теги (labels)" - это пары ключ="значение", которые прикрепляются к метрике для добавления контекста. Метрики нужны для:
    Дифференциация: Позволяют отличить метрику одного сервера от другого (instance="web-01" vs instance="web-02").
    Агрегация: Позволяют посчитать общую сумму запросов по всему региону или конкретному приложению, используя фильтры в PromQL
    Динамичность: Тебе не нужно создавать метрику http_requests_total_server1, ты создаешь одну метрику http_requests_total и разделяешь данные метками.

Возьмем пример:
    http_requests_total{instance="web-01", method="GET"}
        - 1-ый ключ instance = значению "web-01", 
        - 2-ой ключ method = значению "GET". 
При конфигурировании мы можем и будем вынуждены задавать свои собственные теги и значения каждой ноде для гибкостки наших запросов. Задаются они в конфиг файле самого Prometheus в формате .yml(дефолтный путь /etc/prometheus/prometheus.yml).
