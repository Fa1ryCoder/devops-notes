В теме `2.5` мы узнали что `git add` переводит файл в состояние `staged`. Но зачем вообще нужен этот промежуточный шаг — почему нельзя закоммитить изменения напрямую, без индекса?

---

## 1. Двухступенчатая система сохранения

В Git реализована двухступенчатая система сохранения изменений:

```
Рабочая директория  →  git add  →  Индекс  →  git commit  →  Репозиторий
```

Это отличает Git от более простых систем где изменения сохраняются напрямую без промежуточного шага. Даже `git commit -a` не пропускает этот шаг — просто выполняет `git add` автоматически перед коммитом. Индекс даёт разработчику **полный контроль** над тем какая именно версия кода попадёт в репозиторий.

---

## 2. Атомарность коммитов

Мы уже разбирали в `2.6`, что такое атомарный коммит. Вопрос в другом: как его получить, если работа над задачами в рабочей директории идёт вперемешку?

**Проблема:** в процессе работы в одной рабочей директории часто накапливаются изменения относящиеся к разным задачам. Например одновременно велась работа над авторизацией и системой оплаты:

```
Рабочая директория:
  auth.py      ← изменения по авторизации
  payment.py   ← изменения по оплате
  utils.py     ← изменения по авторизации
```

Если сохранить всё одним коммитом — такой набор изменений будет сложно понять. В будущем будет трудно отменить изменения только по одной задаче не затронув остальные. Это нарушает принцип атомарности.

**Решение:** индекс позволяет выбрать только те изменения которые относятся к конкретной задаче. Если часть функционала готова а часть ещё в работе — коммитим готовое и оставляем незаконченное ждать в рабочей директории:

```bash
# Добавляем только файлы по авторизации — payment.py ещё не готов
git add auth.py utils.py
git commit -m "feat: добавить авторизацию через OAuth"

# Продолжаем работу над payment.py...
# Когда будет готов — добавим отдельным коммитом
git add payment.py
git commit -m "feat: добавить интеграцию с платёжной системой"
```

## 3. Частичное индексирование — git add -p

Git позволяет проявлять гибкость даже на уровне одного файла. Если в одном файле есть и готовые и незаконченные изменения — их можно разделить с помощью флага `-p` (`--patch`):

```bash
git add -p auth.py
```

Git разбивает изменения в файле на фрагменты (hunks) и для каждого предлагает выбрать действие. Основные варианты — `y` добавить фрагмент в индекс, `n` не добавлять. Полный список доступных действий можно посмотреть нажав `?`:

```
@@ -1,1 +1,4 @@   ← старая версия: 1 строка, новая: 4 строки
 def login():
+    validate_token()   ← готово
+    check_permissions() ← готово
+    send_analytics()   ← ещё не готово

Stage this hunk [y,n,q,a,d,?]?
```

**Результат:** в индексе окажется версия файла только с выбранными изменениями — именно она попадёт в коммит. В рабочей директории файл останется со всеми изменениями включая неиндексированные.

```bash
git status
# Changes to be committed:
#   modified: auth.py   ← версия с validate_token и check_permissions
#
# Changes not staged for commit:
#   modified: auth.py   ← тот же файл, но с send_analytics (не попадёт в коммит)
```

> Именно поэтому один и тот же файл может одновременно быть в двух секциях `git status` — мы разбирали это в теме `2.5`.

## Итог

Индекс необходим для того чтобы коммиты были точными, понятными и атомарными. Этот контроль работает на любом масштабе — от целого файла до одной строки внутри него.
