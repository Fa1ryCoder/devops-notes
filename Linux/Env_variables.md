## 1. Что такое переменные окружения

### Определение

**Переменная окружения (environment variable)** — это пара `КЛЮЧ=значение`, которую ядро Linux хранит для каждого процесса отдельно. Это не глобальное хранилище системы — это часть **контекста конкретного процесса**, такая же как открытые fd или рабочая директория.

Когда вы запускаете программу — она получает не только код на выполнение, но и **окружение**: набор переменных от которых зависит её поведение. Программа читает их через стандартный API и настраивает себя без изменения кода.

### Зачем это нужно

Представьте: у вас есть приложение которое работает на трёх стендах — dev, staging, production. На каждом стенде разный адрес базы данных, разные пароли, разный уровень логирования. Без переменных окружения пришлось бы:
- Держать три разных конфига в репозитории (и случайно закоммитить пароль)
- Менять код при каждом деплое
- Хранить секреты в git

С переменными окружения — один и тот же образ приложения, разное поведение на каждом стенде:

> **💡 Что такое «стенд» технически?**
>
> «Стенд» (или «окружение», англ. *environment*) — это отдельный сервер, виртуальная машина или контейнер, на котором запущено приложение. Dev-стенд — это одна машина (или VM/контейнер), staging — другая, production — третья. У каждой машины своя операционная система со своим набором переменных окружения.
>
> Проверить переменные окружения **текущего процесса** (т.е. вашей оболочки bash или любого запущенного вами процесса) можно командой:
> ```bash
> env
> ```
> Она выводит именно те переменные, которые видит **текущий процесс** — не какое-то глобальное хранилище системы, а контекст вашего конкретного процесса.
>
> **Техническая формулировка:** при запуске любой программы ядро Linux передаёт ей через системный вызов `execve()` массив строк `envp[]` — набор пар `КЛЮЧ=значение`. Это происходит один раз, **в момент старта процесса**. Приложение читает их через стандартный API своего языка (`os.environ` в Python, `System.getenv()` в Java, `process.env` в Node.js и т.д.). На каждом стенде переменные окружения конфигурируются отдельно — через `EnvironmentFile=` в unit-файлах systemd, через `.env` файлы, через `docker-compose.yml`, через Kubernetes ConfigMap/Secret. Один и тот же бинарник или Docker-образ читает разные значения на разных стендах — без изменения кода.

```
┌─────────────────────────────────────────────────────────────┐
│                    ОДИН И ТОТ ЖЕ КОД                        │
│                app/main.py, app/server.go                    │
└──────────────────────┬──────────────────────────────────────┘
                       │ читает из окружения
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   DEV стенд      STAGING стенд   PROD стенд
   DB=localhost   DB=staging-db   DB=prod-db
   LOG=debug      LOG=info        LOG=warn
   PORT=8000      PORT=8000       PORT=8000
```

### Как программа читает переменные

Программа обращается к окружению через стандартный API своего языка. Два примера:

```bash
# Bash
echo $PATH
echo ${DB_HOST:-localhost}   # если DB_HOST не задана — подставить 'localhost'
echo ${SECRET_KEY:?Переменная SECRET_KEY обязательна}  # упасть с ошибкой если нет
```

```python
# Python
import os

db_host = os.environ.get('DB_HOST', 'localhost')  # с дефолтом если переменная не задана
secret   = os.environ['SECRET_KEY']               # без дефолта — бросит KeyError если нет
port     = int(os.environ.get('PORT', '8080'))     # преобразование типа: env всегда строка
```

> ⚠️ Переменные окружения — это **всегда строки**. Если приложение ждёт число или булево — нужно явное преобразование. `PORT=8080` в окружении это строка `"8080"`, а не число `8080`.

## 2. Наследование окружения

### Как окружение передаётся процессам — fork, exec, execve

Чтобы ответить на вопрос «как переменные окружения попадают в процесс», нужно понять три понятия и как они работают вместе: `fork()` и `execve()` — это системные вызовы ядра, `exec()` — библиотечный слой над ними.

---

**`fork()` — клонировать себя**

`fork()` — системный вызов который просит ядро создать **точную копию текущего процесса**. Копируется всё: код, стек, куча, открытые fd, и — что важно для нас — **полная копия окружения**. После `fork()` в системе два одинаковых процесса. Родитель получает PID дочернего, дочерний получает 0. Оба продолжают выполнение с одной и той же точки.

```
bash PID=100 (родитель)
  окружение: PATH=..., MY_VAR=hello
        │
        │ 1. fork() ─────────────────────────────────┐
        │                                            │
        ▼                                            ▼
bash PID=100 (продолжает работу)     bash PID=101 (копия, дочерний)
  MY_VAR=hello                         MY_VAR=hello  ← унаследовал
```

Проблема: после `fork()` дочерний процесс — это тот же bash, только с другим PID. Нам нужно не это, нам нужно запустить другую программу. Здесь вступает `exec`.

---

**Семейство-функций `exec()` — библиотечный слой между вами и ядром**

Прежде чем говорить про `execve()`, важно понять разницу между двумя уровнями:

```
bash PID=100 (родитель)
  окружение: PATH=..., MY_VAR=hello
        │
        │ 1. fork() ─────────────────────────────────┐
        │                                            │
        ▼                                            ▼
bash PID=100 (продолжает работу)     bash PID=101 (копия, дочерний)
  MY_VAR=hello                         MY_VAR=hello  ← унаследовал
        │                                    │
        │ ждёт завершения                    │ 2. exec() ← библиотека glibc
        │ дочернего                          │    принимает аргументы, форматирует,
        │                                    │    передаёт в ядро → execve()
```

`exec()` **никогда не вызывается ядром напрямую** — это не системный вызов. Это набор функций стандартной библиотеки (glibc), которые живут в пользовательском пространстве. Их задача — принять аргументы в удобном для программиста виде, привести их к нужному формату, и передать управление настоящему системному вызову `execve()`.

Аналогия: вы звоните в банк и говорите «переведи деньги Ивану». Оператор (это `exec()`) выслушивает вас, заполняет форму платёжного поручения с нужными полями, и отправляет её в процессинговый центр. Процессинговый центр (это `execve()`) — уже реально списывает деньги. Вы никогда не разговариваете с процессинговым центром напрямую.

Для DevOps достаточно знать одно: все функции семейства exec() — это обёртки с разными удобными сигнатурами, которые в итоге все вызывают `execve()`. Какую бы из них ни использовал разработчик в коде — в ядро всегда уходит `execve()`.

---

**`execve()` — системный вызов, который реально заменяет процесс**

`execve()` — это уже настоящий системный вызов ядра. Именно он **заменяет текущий процесс** другой программой.

Чтобы понять что происходит внутри, нужно знать три понятия. Ниже — краткие определения, полное объяснение с примерами и схемами в отдельном документе [`linux_memory_model.md`](linux_memory_model.md).

> **Виртуальное адресное пространство** — каждый процесс видит свою изолированную память. Ядро через аппаратный блок MMU маппит виртуальные адреса процесса на реальные физические страницы RAM. Это обеспечивает изоляцию процессов, защиту памяти и возможность многозадачности.
>
> **Стек (stack)** — регион памяти для вызовов функций. Хранит стековые кадры с локальными переменными, аргументами и адресом возврата. Управляется процессором автоматически через регистр `SP`.
>
> **Куча (heap)** — регион памяти для долгоживущих данных, которые должны существовать дольше одной функции. Управляется аллокатором памяти через явные вызовы `malloc`/`free` или сборщик мусора.
>
> ---
>
> **«Сбросить стек и кучу»** в контексте `execve()` означает следующее: старая программа (например bash) накопила в стеке дерево вызовов функций, а в куче — динамические данные. При `execve()` ядро уничтожает всё это: стек обнуляется (новая программа стартует с чистого начального кадра), куча пустая (никаких старых данных). Физическая RAM при этом не «стирается» побайтово — ядро просто перемаппирует эти страницы и отдаёт процессу заново как «чистые» с точки зрения новой программы.

Итак, `execve()` — системный вызов который **заменяет текущий процесс** другой программой: ядро загружает новый исполняемый файл (ELF) в адресное пространство процесса, уничтожает старый стек и кучу, и начинает выполнение с точки входа (`main()`) новой программы. PID при этом **не меняется** — это тот же процесс, но с совершенно другим кодом внутри.

`execve()` принимает три аргумента:
```
execve(путь_к_программе, аргументы[], окружение[])
         ↑                   ↑              ↑
  /usr/sbin/nginx     ["-c", конфиг]   [VAR=val, ...]
```

Третий аргумент — это и есть массив переменных окружения. Именно здесь окружение **передаётся новой программе**.

---

**Как fork + execve работают вместе**

Запуск любой программы из оболочки — это всегда цепочка `fork()` → `exec()` → `execve()`:

```
bash PID=100                          (родитель)
  окружение: PATH=..., MY_VAR=hello
        │
        │ 1. fork() ─────────────────────────────────┐
        │                                            │
        ▼                                            ▼
bash PID=100 (продолжает работу)     bash PID=101 (копия, дочерний)
  MY_VAR=hello                         MY_VAR=hello  ← унаследовал
        │                                    │
        │ ждёт завершения                    │ 2. exec() ← семейство-функций glibc
        │ дочернего                          │    форматирует аргументы,
        │                                    │    готовит вызов для ядра
        │                                    │
        │                                    │ 3. execve("/usr/sbin/nginx",
        │                                    │          args,
        │                                    │          environ)  ← передаёт окружение
        │                                    │
        │                                    ▼
        │                             nginx PID=101  (тот же PID!)
        │                               MY_VAR=hello  ← получил через execve
        │                               PATH=...
        │                               (bash-кода больше нет)
        │
        │ 4. wait() — забирает код завершения nginx
        ▼
bash продолжает работу, выводит prompt (user@host:~$)
```

**Ключевые моменты:**

- `fork()` копирует окружение родителя в дочерний процесс
- `exec()` — семейство-функций библиотеки glibc, форматирует аргументы и передаёт вызов в ядро
- `execve()` — реальный системный вызов ядра, передаёт окружение новой программе как третий аргумент
- Новая программа получает окружение **в момент запуска** — это снимок, не живая ссылка
- После запуска изменение переменной в одном процессе **не влияет** на другой — у каждого своя копия

> **💡 Почему bash клонирует себя перед запуском nginx? Зачем нужен fork?**
>
> Это самый частый вопрос, и интуитивно он действительно непонятен: ведь никакого нового терминала не открывается. Разберём по шагам.
>
> **Что было бы без fork — если бы bash сам вызвал execve() напрямую:**
>
> ```
> bash PID=100
>   └─ exec() → execve("/usr/sbin/nginx") ← bash ЗАМЕНЯЕТ СЕБЯ на nginx
>                                            bash больше не существует
>                                            nginx работает с PID=100
>                                            nginx завершился → процесс PID=100 умер
>                                            терминальная сессия закончилась
>                                            вернуться в bash некуда — его нет
> ```
>
> Это катастрофа: запустил `nginx` — потерял терминал навсегда.
>
> **Что происходит на самом деле с fork:**
>
> ```
> bash PID=100 (родитель)
>   │
>   ├─ 1. fork() → создаёт копию себя
>   │              ↓
>   │         bash PID=101 (дочерний — точная копия)
>   │              │
>   │              ├─ 2. exec() ← семейство-функций glibc
>   │              │    форматирует аргументы, передаёт в ядро
>   │              │
>   │              └─ 3. execve("/usr/sbin/nginx")
>   │                      PID=101 теперь — это nginx
>   │                      bash-кода в PID=101 больше нет
>   │                      nginx работает...
>   │                      nginx завершился → PID=101 умер
>   │
>   └─ 4. wait(PID=101) — bash ждёт завершения дочернего
>              ↓
>         bash выводит prompt (user@host:~$) — готов к следующей команде
> ```
>
> **Почему не появляется новый терминал?**
>
> Потому что bash создаёт дочерний процесс, а **не новый терминал**. Дочерний процесс (PID=101) наследует те же открытые файловые дескрипторы что и родитель: stdin, stdout, stderr — они указывают на тот же терминал. Поэтому вывод nginx идёт в ваш текущий терминал. Сам терминал — это отдельный процесс (например `gnome-terminal` или `sshd`) который существует независимо.
>
> Визуально в терминале ничего не происходит: bash просто ждёт (вызов `wait()`). Вы видите вывод nginx, потому что дочерний процесс пишет в тот же stdout. Когда nginx завершается — bash просыпается и выводит **prompt** — это приглашение командной строки, строчка вида `user@hostname:~$` или просто `$`, которую bash показывает когда готов принять следующую команду. Пока nginx работает — prompt не появляется, bash молча ждёт.
>
> **Дочерний bash (PID=101) — не второй терминал.** Это технический промежуточный шаг, который существует буквально миллисекунды: `fork()` создал копию, `exec()` подготовил вызов, `execve()` тут же заменил процесс на nginx. «Копии bash» вы никогда не видите — она мгновенно становится нужной вам программой.

**Почему systemd работает иначе — полное объяснение**

> **💡 Лекция: Откуда берётся окружение процесса — дерево запуска**
>
> Чтобы понять почему nginx запущенный через systemd «ничего не знает о bash», нужно посмотреть на **дерево процессов** и понять откуда каждый процесс берёт своё окружение.
>
> **Ключевой принцип:** окружение процесса — это всегда то, что ему передал **его родитель** через `fork()` + `execve()`. Нет другого способа получить окружение кроме как унаследовать от родителя или получить явно через `execve()`. Поэтому, чтобы понять окружение процесса, нужно проследить всю цепочку от ядра до него.
>
> ---
>
> **Сценарий 1: вы запускаете nginx вручную из терминала**
>
> ```
> ядро Linux
>   └─► systemd (PID=1) ← стартует при загрузке системы, минимальное окружение
>         └─► sshd или gnome-terminal ← ваш способ входа
>               └─► bash PID=100 ← ваша оболочка
>                     │
>                     │  При запуске bash читает:
>                     │    /etc/profile → /etc/profile.d/*.sh (login shell)
>                     │    ~/.bashrc (интерактивный shell)
>                     │  В bash окружение: PATH=расширенный, все ваши export-ы,
>                     │  переменные из ~/.bashrc и т.д.
>                     │
>                     ├─► fork() → bash PID=101 (копия с полным bash-окружением)
>                     │               │
>                     │               ├─► exec() ← семейство-функций glibc
>                     │               │    форматирует аргументы, передаёт в ядро
>                     │               │
>                     │               └─► execve("/usr/sbin/nginx")
>                     │                       nginx PID=101
>                     │                       окружение: всё что было у bash PID=100
>                     │                       → PATH из ~/.bashrc ✓
>                     │                       → ваши export-ы ✓
>                     │                       → HOME, USER ✓
>                     └─► wait() → ждёт завершения nginx
> ```
>
> nginx получил богатое окружение **потому что его родитель — bash**, который до этого прочитал `~/.bashrc`, `/etc/profile` и накопил все ваши переменные.
>
> ---
>
> **Сценарий 2: systemd запускает nginx как сервис**
>
> ```
> ядро Linux
>   └─► systemd (PID=1) ← стартует при загрузке системы
>         │
>         │  Окружение systemd: минимальное.
>         │  ~/.bashrc для systemd НИКОГДА не читался — systemd не bash и
>         │  не является интерактивной оболочкой пользователя.
>         │  /etc/profile тоже не читался — это для login shell.
>         │  У systemd нет «терминальной сессии».
>         │
>         ├─► fork() → дочерний процесс systemd
>         │               │
>         │               ├─► exec() ← семейство-функций glibc
>         │               │    форматирует аргументы, передаёт в ядро
>         │               │
>         │               └─► execve("/usr/sbin/nginx", args, [окружение из unit файла])
>         │                       nginx PID=???
>         │                       окружение: ТОЛЬКО то что в Environment= и EnvironmentFile=
>         │                       → ~/.bashrc? НЕТ — в цепочке не было bash
>         │                       → /etc/profile? НЕТ — не было login shell
>         │                       → ваши export-ы из терминала? НЕТ
>         │                       → только явно заданные в unit файле ✓
>         └─► продолжает управлять другими сервисами
> ```
>
> nginx получил минимальное окружение **потому что его родитель — systemd**, который никогда не проходил через bash-сессию пользователя. В цепочке `ядро → systemd → nginx` bash вообще не участвует.
>
> ---
>
> **Почему «ничего от bash» и «ничего от ~/.bashrc» — это одно и то же**
>
> Это не два разных источника — это одно явление. `~/.bashrc` — это скрипт, который **bash выполняет при старте** и устанавливает переменные в **своё** окружение. Когда потом bash запускает ваше приложение, оно наследует эти переменные. Но если bash вообще нет в цепочке (как в случае с systemd), то и переменных из `~/.bashrc` тоже нет — просто потому что тот процесс, который их читал, не является предком nginx в этой цепочке.
>
> ```
> Аналогия: вы получаете наследство только от своих предков.
> Если Иван (bash) накопил богатство (~/.bashrc переменные),
> а вы (nginx) — его ребёнок, вы получаете наследство.
>
> Если вас (nginx) породил Пётр (systemd), который никак не связан с Иваном,
> то богатство Ивана к вам не попадёт — вы не его потомок.
> ```
>
> ---
>
> **Практический вывод для DevOps:**
>
> Если сервис через systemd не видит нужную переменную — она должна быть явно указана в unit файле. Нет никакого автоматического «подтягивания» переменных пользователя в сервис. Это правильное поведение: сервисы должны быть воспроизводимыми и не зависеть от состояния интерактивной сессии конкретного инженера на сервере.

---

**Важнейшее следствие:** изменение переменной в дочернем процессе **не влияет** на родителя и других детей. Каждый процесс имеет свою копию окружения.

```bash
# демонстрация: родитель (текущий bash) запускает два независимых
# дочерних процесса. Каждый получил свою копию окружения при fork().
# Они ничего не знают друг о друге и не влияют друг на друга.
export TEST=parent

# дочерний процесс №1 — просто читает унаследованную переменную
bash -c 'echo "дочерний №1 видит: $TEST"'
# дочерний №1 видит: parent   ← унаследовал копию от родителя

# дочерний процесс №2 — меняет переменную в своей копии
bash -c 'export TEST=child; echo "дочерний №2 изменил: $TEST"'
# дочерний №2 изменил: child  ← изменил только свою копию

# родитель проверяет свою переменную после того как оба дочерних завершились
echo "родитель видит: $TEST"
# родитель видит: parent       ← не изменился, его копию никто не трогал
```

### Где реально хранится окружение процесса

Окружение процесса — это часть его адресного пространства памяти. Посмотреть можно напрямую через `/proc`:

```bash
# окружение запущенного процесса (переменные разделены нулевым байтом \0)
cat /proc/$(pgrep -o nginx)/environ | tr '\0' '\n'

# пример вывода:
# PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin
# HOME=/var/lib/nginx
# USER=nginx
# NGINX_VERSION=1.24.0

# посмотреть конкретную переменную процесса
cat /proc/$(pgrep -o nginx)/environ | tr '\0' '\n' | grep PATH
```

## 3. export — в чём разница

Это один из самых частых источников путаницы.

### Переменная оболочки vs переменная окружения

В bash есть два типа переменных:

**Переменная оболочки (shell variable)** — живёт только внутри текущего bash процесса. Дочерние процессы её **не видят**:

```bash
MY_VAR=hello          # просто переменная оболочки
bash -c 'echo $MY_VAR'
#                     ← пусто! дочерний bash не получил переменную
```

**Переменная окружения (environment variable)** — попадает в окружение процесса и **передаётся дочерним**:

```bash
export MY_VAR=hello   # теперь это переменная окружения
bash -c 'echo $MY_VAR'
# hello               ← дочерний bash получил переменную
```

```
Без export:                    С export:
──────────────────────         ──────────────────────────────
bash                           bash
 │ MY_VAR=hello                 │ MY_VAR=hello (экспортирована)
 │                              │
 ├── python app.py              ├── python app.py
 │    окружение:                │    окружение:
 │    PATH, HOME, ...           │    PATH, HOME, MY_VAR=hello ✓
 │    MY_VAR — нет ✗            │
 │                              │
```

### Как проверить что экспортировано

```bash
# показать только экспортированные переменные
export -p
# declare -x HOME="/home/user"
# declare -x MY_VAR="hello"
# declare -x PATH="/usr/bin:/bin"

# показать все переменные включая неэкспортированные
set | head -20

# только окружение (то что видят дочерние процессы)
env
```

### Однострочный export для запуска команды

Можно передать переменные только для одного запуска — не загрязняя текущее окружение:

```bash
# переменная существует только для этой команды
DB_HOST=localhost python app.py

# несколько переменных
DEBUG=true PORT=8080 python app.py

# проверить что в текущей сессии ничего не изменилось
echo $DB_HOST   # пусто
```

## 4. Где хранятся переменные — уровни

Переменные окружения можно задать на разных уровнях. Важно понимать **кто что видит** и **когда применяется**:

```
┌─────────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ 1: Ядро / Система                                      │
│  /etc/environment — применяется для ВСЕХ пользователей          │
│  Читается PAM при логине                                        │
├─────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 2: Профиль системы                                     │
│  /etc/profile и /etc/profile.d/*.sh                             │
│  Выполняется при логине (login shell)                           │
├─────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 3: Профиль пользователя                                │
│  ~/.profile, ~/.bash_profile — логин шелл                       │
│  ~/.bashrc — интерактивный не-логин шелл                        │
├─────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 4: Сессия / Процесс                                    │
│  export VAR=value в терминале — только текущая сессия           │
│  VAR=value cmd — только для одной команды                       │
└─────────────────────────────────────────────────────────────────┘
```

> **PAM (Pluggable Authentication Modules)** — это подсистема Linux которая управляет аутентификацией и настройкой сессии при логине. Когда вы входите по SSH или открываете терминал — PAM запускает цепочку модулей: проверяет пароль, применяет ограничения (`limits.conf`), читает `/etc/environment` и устанавливает переменные окружения. systemd и cron не используют PAM — они запускают процессы напрямую, минуя всю эту цепочку. Именно поэтому настройки из `limits.conf` и `/etc/environment` не действуют на сервисы systemd.

### /etc/environment — глобальные переменные для всех

Самый простой файл — просто пары `КЛЮЧ=значение`, без bash синтаксиса, без `export`:

```bash
cat /etc/environment
# PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
# LANG=en_US.UTF-8
# TZ=Europe/Moscow
```

> ⚠️ В `/etc/environment` нельзя писать `export`, нельзя использовать `$VAR` для ссылки на другие переменные — только голые `КЛЮЧ=значение`. Это не bash скрипт, это конфиг для PAM.

```bash
# применить изменения в текущей сессии
source /etc/environment

# но правильнее — перелогиниться, или применять через PAM
# (PAM применяет этот файл автоматически при логине)
```

### /etc/profile и /etc/profile.d/ — скрипты системного профиля

`/etc/profile` — это главный системный скрипт, который bash выполняет при **login shell** (SSH-логин, `su -`, `sudo -i`). Он задаёт базовые системные переменные и в конце сам подключает все файлы из `/etc/profile.d/`.

`/etc/profile.d/` — директория для отдельных скриптов по назначению. Вместо того чтобы писать всё в один большой `/etc/profile`, принято класть сюда отдельные файлы: `java.sh`, `golang.sh`, `myapp.sh` и т.д. Каждый файл `.sh` в этой директории выполняется при логине автоматически через `/etc/profile`:

```bash
ls /etc/profile.d/
# bash_completion.sh  java.sh  golang.sh  ...

# создать системную переменную для всех
cat > /etc/profile.d/myapp.sh << 'EOF'
export JAVA_HOME=/usr/lib/jvm/java-17
export GOPATH=/usr/local/go
EOF
chmod +x /etc/profile.d/myapp.sh
```

### ~/.bashrc, ~/.profile, ~/.bash_profile — когда что работает

Три файла пользовательского профиля, которые часто путают:

- **`~/.profile`** — выполняется при **login shell** (SSH-логин, `su -`). Здесь задают переменные окружения которые должны быть доступны во всех сессиях пользователя. Читается один раз при входе.
- **`~/.bash_profile`** — то же самое что `~/.profile`, но специфично для bash. Если существует `~/.bash_profile` — bash читает его вместо `~/.profile`. Многие дистрибутивы используют один или другой, не оба.
- **`~/.bashrc`** — выполняется при каждом запуске **интерактивного не-login** bash (открыли новую вкладку терминала, запустили `bash`). Здесь обычно хранят алиасы, настройки, переменные для ежедневной работы в терминале. При SSH-логине напрямую **не** читается — только если `~/.profile` или `~/.bash_profile` явно вызывает `source ~/.bashrc` (что часто и делается).

Это важно понимать для диагностики «почему переменная не видна»:

```
Тип сессии              Что выполняется
──────────────────────────────────────────────────────
SSH логин               /etc/profile → ~/.profile → ~/.bash_profile
Открыл терминал GUI     ~/.bashrc
sudo -i                 /etc/profile → ~/.profile (root)
sudo -u user cmd        Переменные НЕ наследуются (новое окружение)
su - user               /etc/profile → ~/.profile (нового пользователя)
su user (без -)         ~/.bashrc текущего пользователя
cron                    Минимальное окружение! Только базовые переменные
systemd сервис          Только то что задано в unit файле
```

> ⚠️ **Частая проблема:** добавили переменную в `~/.bashrc`, но скрипт запущенный через cron её не видит. Потому что cron запускает скрипты с минимальным окружением без `~/.bashrc`. Варианты решений и советы по дебагу разбираются в разделе [«Вопросы на собесе»](#11-вопросы-на-собесе).

```bash
# ~/.bashrc — для интерактивных сессий терминала
export EDITOR=vim
export NVM_DIR="$HOME/.nvm"
alias ll='ls -la'

# применить в текущей сессии без перезапуска терминала
source ~/.bashrc
# или короче
. ~/.bashrc
```

### Порядок применения и приоритеты

```bash
# посмотреть текущее окружение — всё что видит процесс
env | sort

# найти откуда пришла конкретная переменная
# способ 1: grep по всем конфигам
grep -r "MY_VAR" /etc/environment /etc/profile /etc/profile.d/ ~/.bashrc ~/.profile 2>/dev/null

# способ 2: включить трассировку bash
bash -x -l -c 'echo $MY_VAR' 2>&1 | head -50
```

## 5. Специальные переменные Linux

Наиболее часто используемые системные переменные:

| Переменная | Значение | Пример |
|-----------|---------|--------|
| `PATH` | Список директорий для поиска исполняемых файлов | `/usr/bin:/usr/local/bin:/bin` |
| `HOME` | Домашняя директория текущего пользователя | `/home/user` |
| `USER` | Имя текущего пользователя | `nginx` |
| `PWD` | Текущая рабочая директория | `/var/www/html` |
| `LANG` | Локаль системы | `en_US.UTF-8` |
| `TZ` | Часовой пояс | `Europe/Moscow` |
| `HOSTNAME` | Имя хоста | `prod-web-01` |

### PATH — как работает и как расширить

`PATH` — самая важная переменная. Когда вы вводите `nginx`, bash ищет исполняемый файл `nginx` последовательно в каждой директории из PATH:

```bash
echo $PATH
# /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

# как bash ищет команду
which nginx
# /usr/sbin/nginx

# добавить директорию в PATH (в конец — меньший приоритет)
export PATH="$PATH:/opt/myapp/bin"

# добавить в начало — больший приоритет (перекрывает системные утилиты)
export PATH="/opt/myapp/bin:$PATH"

# постоянно — в ~/.bashrc
echo 'export PATH="$PATH:/opt/myapp/bin"' >> ~/.bashrc
source ~/.bashrc
```

> ⚠️ Никогда не добавляйте `.` (текущую директорию) в PATH — это уязвимость. Злоумышленник может подложить файл `ls` в текущую директорию.

### Код возврата $?

`$?` — специальная переменная bash, содержащая код завершения последней выполненной команды. `0` означает успех, любое ненулевое значение — ошибку. Подробнее эта тема относится к bash scripting.

```bash
ls /tmp
echo $?   # 0 — команда выполнилась успешно

ls /nonexistent
echo $?   # 2 — ошибка (No such file or directory)
```

## 6. Переменные окружения в systemd

Это критически важная тема для DevOps. Сервисы запускаются через systemd и **не наследуют** ни `~/.bashrc`, ни `/etc/profile`. Они получают только то что явно задано в unit файле.

### Четыре способа передать переменные в сервис

**Способ 1: `Environment=` прямо в unit файле**

Для простых, несекретных значений:

```ini
[Service]
Environment=NODE_ENV=production
Environment=PORT=8080
Environment=LOG_LEVEL=info
# можно несколько переменных в одной строке
Environment="DB_HOST=localhost" "DB_PORT=5432"
```

**Способ 2: `EnvironmentFile=` — переменные из файла**

Для большого количества переменных или когда хочется разделить конфиг от unit файла:

```bash
# /etc/myapp/env
NODE_ENV=production
PORT=8080
DB_HOST=localhost
DB_PORT=5432
DB_NAME=myapp
LOG_LEVEL=info
```

```ini
[Service]
EnvironmentFile=/etc/myapp/env
# или несколько файлов
EnvironmentFile=/etc/myapp/env
EnvironmentFile=-/etc/myapp/env.local  # - означает "не падать если файл не существует"
```

**Способ 3: override.conf для изменения без правки основного файла**

```bash
systemctl edit myapp
# добавляем:
# [Service]
# Environment=DEBUG=true
```

**Способ 4: `PassEnvironment=` — передать переменную из окружения самого systemd**

Это редкий способ. Суть: у systemd (PID=1) есть своё собственное минимальное окружение. Если в него добавить переменную через `systemctl set-environment`, то `PassEnvironment=` позволяет передать её конкретному сервису.

```bash
# шаг 1: добавить переменную в глобальное окружение systemd
systemctl set-environment DEPLOY_ENV=production

# шаг 2: в unit файле указать какие переменные передать сервису
```

```ini
[Service]
PassEnvironment=DEPLOY_ENV
```

```bash
# проверить что сейчас есть в окружении systemd
systemctl show-environment

# убрать переменную из окружения systemd
systemctl unset-environment DEPLOY_ENV
```

> ⚠️ `PassEnvironment=` передаёт переменную из окружения systemd, а не из вашего терминала. Если вы просто сделали `export MY_VAR=hello` в терминале — это не попадёт в `PassEnvironment=`. Нужно явно добавить через `systemctl set-environment`. На практике этот способ почти не используется — удобнее `Environment=` или `EnvironmentFile=`.

### Как проверить что переменные применились

```bash
# посмотреть переменные которые видит сервис
systemctl show myapp | grep Environment

# самый надёжный способ — смотреть /proc запущенного процесса
cat /proc/$(pgrep -o myapp)/environ | tr '\0' '\n'

# проверить через systemd-run (запустить команду с окружением сервиса)
systemd-run --uid=myapp --same-dir env | sort
```

### Важные особенности EnvironmentFile

```ini
# файл НЕ является bash скриптом — нельзя писать:
# export VAR=value       ← не работает
# VAR=$(command)         ← не работает
# source другой_файл     ← не работает

# можно только:
VAR=value
VAR="значение с пробелами"
# комментарии через #
```

```bash
# права на файл с переменными — только root должен читать
# если там секреты
chown root:root /etc/myapp/env
chmod 600 /etc/myapp/env
# или чтобы пользователь сервиса тоже мог читать
chown root:myapp /etc/myapp/env
chmod 640 /etc/myapp/env
```

### Порядок применения в systemd

```
Окружение systemd сервиса формируется так:

1. Базовое окружение systemd (минимальный PATH, очень мало переменных)
2. Environment= из unit файла
3. EnvironmentFile= из unit файла
4. PassEnvironment= — переменные переданные из глобального окружения systemd

Позднее значение ПЕРЕЗАПИСЫВАЕТ более раннее.
```

```bash
# посмотреть базовое окружение systemd
systemctl show-environment

# добавить переменную в глобальное окружение systemd
systemctl set-environment MY_VAR=hello

# убрать
systemctl unset-environment MY_VAR

# сбросить всё к дефолту
systemctl import-environment
```

### systemd запускает процессы не через shell

Это один из самых важных нюансов который объясняет сразу несколько «почему не работает».

Когда вы запускаете команду в терминале — bash сначала обрабатывает строку: раскрывает переменные (`$VAR`), glob-паттерны (`*.log`), подстановки (`$(command)`). Только потом передаёт результат ядру.

systemd делает иначе. Он передаёт команду из `ExecStart=` **напрямую ядру** через `execve()`, минуя bash полностью. Никакой оболочки между — ядро запускает процесс как есть.

```
Терминал:                          systemd:
─────────────────────────          ─────────────────────────────
вы пишете команду                  читает ExecStart= из unit файла
       ↓                                     ↓
    bash                             НЕТ bash
  раскрывает $VAR                    нет раскрытия переменных
  раскрывает *.log                   нет glob
  выполняет $(cmd)                   нет подстановок команд
  читает ~/.bashrc                   нет ~/.bashrc
       ↓                                     ↓
  exec() → execve(программа)    exec() → execve(программа напрямую)
```

**Что из этого следует на практике:**

```ini
# ❌ $VAR не раскроется — systemd передаст строку "$HOME/app" буквально
ExecStart=$HOME/app/server

# ✅ полный путь
ExecStart=/home/myuser/app/server

# ❌ glob не работает
ExecStart=/usr/bin/python /opt/app/*.py

# ✅ явный файл
ExecStart=/usr/bin/python /opt/app/main.py

# ❌ подстановка команды не работает
ExecStart=/opt/app/server --version=$(cat /etc/app/version)

# ✅ использовать ExecStartPre для подготовки, или читать файл в самом приложении
ExecStart=/opt/app/server

# ❌ source не работает — это bash встроенная команда
ExecStartPre=source /etc/myapp/env

# ✅ для загрузки переменных — EnvironmentFile=
EnvironmentFile=/etc/myapp/env
ExecStart=/opt/app/server
```

**Ещё следствие:** если вам всё же нужен bash для сложной логики в ExecStart — явно вызывайте его:

```ini
# явный вызов bash — тогда всё работает как в терминале
ExecStart=/bin/bash -c 'source /etc/myapp/env && exec /opt/app/server'
ExecStartPre=/bin/bash -c 'echo "Starting on $(hostname)" >> /var/log/myapp/start.log'
```

> ⚠️ Но злоупотреблять этим не стоит: скрипты в ExecStart усложняют диагностику. Лучше вынести логику в отдельный скрипт-обёртку и вызывать его.

## 7. Ограничения размера окружения

Это реальный production кейс который встречается чаще чем кажется — особенно в CI/CD системах, сборочных серверах и микросервисах с большим количеством переменных.

### Откуда берётся лимит

Ядро Linux выделяет окружение процесса в его стеке при запуске. Размер этого пространства ограничен константой `ARG_MAX` — максимальный суммарный размер аргументов командной строки **плюс** переменных окружения при вызове `execve()`.

```bash
# узнать лимит на текущей системе
getconf ARG_MAX
# 2097152  ← 2MB (типичное значение)

# посмотреть через /proc
cat /proc/$(pgrep -o bash)/limits | grep "Max arg"
# Max arg length  2097152  2097152  bytes

# размер текущего окружения
env | wc -c
# 3842   ← 3.8KB — обычно мало
```

### Как это ломается

```
Суммарный размер = длина всех имён переменных
                 + длина всех значений
                 + нулевые байты-разделители
                 + аргументы командной строки

Если сумма > ARG_MAX → execve() вернёт ENOMEM или E2BIG
```

Типичная ошибка в логах:

```
bash: /opt/deploy/run.sh: Argument list too long
execve failed: Argument list too long
```

### Когда это происходит

**CI/CD с накопленными переменными** — Jenkins, GitLab CI, GitHub Actions передают десятки переменных о сборке. Плюс переменные инфраструктуры. Плюс секреты. Легко набирается 100+ переменных.

**Приложение с base64 секретами** — сертификаты, ключи, JSON-конфиги закодированные в base64 и переданные как переменная окружения:

```bash
# ПЛОХО: 4KB сертификат в переменной
export TLS_CERT=$(base64 -w0 /etc/ssl/certs/myapp.crt)
# TLS_CERT теперь занимает ~5KB в окружении
```

**Большой EnvironmentFile в systemd** — если в файле сотни переменных или переменные с длинными значениями.

### Диагностика

```bash
# размер текущего окружения в байтах
env | wc -c

# найти самые большие переменные
env | awk -F= '{print length($0), $1}' | sort -rn | head -10

# размер окружения конкретного процесса
wc -c < /proc/<PID>/environ

# проверить лимит системы
getconf ARG_MAX

# проверить сколько переменных всего
env | wc -l
```

### Практические решения

**Решение 1: вынести большие значения в файлы**

```bash
# ❌ сертификат в переменной — занимает место в окружении
export TLS_CERT="LS0tLS1CRUdJTi..."

# ✅ путь к файлу в переменной — сам файл не в окружении
export TLS_CERT_PATH=/etc/ssl/certs/myapp.crt
# приложение читает файл само
```

**Решение 2: разделить на несколько EnvironmentFile**

```ini
# вместо одного большого файла — несколько маленьких по назначению
[Service]
EnvironmentFile=/etc/myapp/app.env      # настройки приложения
EnvironmentFile=/etc/myapp/db.env       # настройки БД
EnvironmentFile=-/etc/myapp/secrets.env # секреты (опциональный)
```

**Решение 3: убрать лишние переменные из окружения**

```bash
# посмотреть что реально используется приложением
grep -r "os.environ\|getenv\|process.env" /opt/myapp/src/ | grep -oP "'[A-Z_]+'" | sort -u

# запустить с минимальным окружением — только нужные переменные
env -i HOME=/home/myapp PATH=/usr/bin:/bin DB_HOST=localhost /opt/myapp/server
```

**Решение 4: увеличить лимит (временная мера)**

```bash
# лимит задаётся при сборке ядра и через параметры запуска
# на большинстве систем его нельзя изменить без пересборки ядра

# но можно уменьшить размер окружения другими способами:
# убрать ненужные переменные
unset LARGE_VAR_NOT_NEEDED
```

### Проверить заранее перед деплоем

```bash
# скрипт для проверки размера окружения перед запуском
ENV_SIZE=$(env | wc -c)
ARG_MAX=$(getconf ARG_MAX)
THRESHOLD=$((ARG_MAX * 80 / 100))   # 80% от лимита — порог предупреждения

if [ $ENV_SIZE -gt $THRESHOLD ]; then
    echo "WARNING: окружение занимает ${ENV_SIZE} байт (лимит ${ARG_MAX})"
    echo "Топ-5 самых больших переменных:"
    env | awk -F= '{print length($0), $1}' | sort -rn | head -5
fi
```

## 8. Секреты

### Что нельзя делать

**Нельзя хранить секреты в репозитории** — даже если потом удалить, в git истории останется:

```bash
# ❌ — пароль в коде
DB_PASSWORD = "supersecret123"

# ❌ — пароль в Dockerfile
ENV DB_PASSWORD=supersecret123

# ❌ — пароль в docker-compose.yml который закоммичен в git
environment:
  DB_PASSWORD: supersecret123

# ❌ — пароль в переменной которую видно в ps aux
CMD ["python", "app.py", "--password=supersecret"]
# ps aux покажет весь аргумент!
```

**Нельзя передавать секреты через `docker history`:**

```bash
docker history myimage
# видны все ENV слои с паролями если они были заданы через ENV в Dockerfile
```

### Как правильно

**Вариант 1: EnvironmentFile с правильными правами**

```bash
# файл только для root
cat /etc/myapp/secrets.env
# DB_PASSWORD=supersecret
# API_TOKEN=abc123

chown root:myapp /etc/myapp/secrets.env
chmod 640 /etc/myapp/secrets.env
```

```ini
[Service]
EnvironmentFile=/etc/myapp/secrets.env
```

**Вариант 2: .env файл в .gitignore**

```bash
# .gitignore
.env
.env.local
*.env
secrets/

# .env.example — пример с пустыми значениями, коммитится в git
DB_PASSWORD=
API_TOKEN=
SECRET_KEY=
```

**Вариант 3: Docker secrets (для Swarm)**

```bash
# создать секрет
echo "supersecret" | docker secret create db_password -

# использовать в сервисе
docker service create \
  --secret db_password \
  myapp
# секрет монтируется в /run/secrets/db_password внутри контейнера
```

**Вариант 4: Vault (HashiCorp) — для серьёзного продакшена**

```bash
# приложение само запрашивает секрет у Vault при старте
# Vault отдаёт секрет только авторизованным приложениям
# секреты ротируются автоматически
# полный аудит кто когда получал секрет
```

### Проверить что секреты не утекли

```bash
# проверить что переменная не видна в аргументах процесса
cat /proc/$(pgrep -o myapp)/cmdline | tr '\0' ' '
# /usr/bin/python app.py   ← хорошо, пароля нет

# проверить что docker history не показывает секреты
docker history myimage --no-trunc | grep -i password

# найти все .env файлы которые могли случайно уйти в git
git log --all --full-history -- "**/.env" "**/*.env"
```

## 10. Реальные кейсы с дебагом

### Кейс 1: «Сервис запускается вручную, но падает через systemd»

**Симптом:** `python app.py` работает, `systemctl start myapp` падает с ошибкой `DB_HOST not set`.

**Мышление:** systemd не наследует окружение терминала. Смотрим что видит процесс.

```bash
# Шаг 1: проверяем окружение запущенного вручную процесса
env | grep DB
# DB_HOST=localhost
# DB_PASSWORD=secret

# Шаг 2: смотрим что видит сервис через systemd
systemctl show myapp | grep Environment
# ← пусто! переменные не заданы в unit файле

# Шаг 3: смотрим как запускается (ошибка в логах)
journalctl -u myapp -b 0 -n 20
# KeyError: 'DB_HOST'  ← подтверждение

# Шаг 4: создаём EnvironmentFile
cat > /etc/myapp/env << 'EOF'
DB_HOST=localhost
DB_PASSWORD=secret
EOF
chmod 640 /etc/myapp/env

# Шаг 5: добавляем в unit файл
systemctl edit myapp
# [Service]
# EnvironmentFile=/etc/myapp/env

systemctl daemon-reload && systemctl restart myapp

# Шаг 6: проверяем что переменные применились
cat /proc/$(pgrep -o myapp)/environ | tr '\0' '\n' | grep DB
# DB_HOST=localhost
# DB_PASSWORD=secret  ← есть
```

### Кейс 2: «Команда не найдена после добавления в PATH»

**Симптом:** добавили `/opt/myapp/bin` в PATH в `~/.bashrc`, но `myapp` всё равно `command not found`.

```bash
# Шаг 1: проверяем текущий PATH
echo $PATH
# /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin
# /opt/myapp/bin отсутствует!

# Шаг 2: проверяем что написали в .bashrc
grep PATH ~/.bashrc
# export PATH="$PATH:/opt/myapp/bin"  ← написано правильно

# Шаг 3: применяем изменения (забыли сделать source!)
source ~/.bashrc

# Шаг 4: проверяем
echo $PATH
# /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/opt/myapp/bin ✓

which myapp
# /opt/myapp/bin/myapp ✓
```

**Если source не помогает — смотрим в каком файле реально задаётся PATH:**

```bash
# трассировка откуда берётся PATH при логине
bash --login -x -c 'echo $PATH' 2>&1 | grep PATH | head -20

# проверить все файлы профиля
grep -r "PATH" /etc/environment /etc/profile /etc/profile.d/ ~/.bashrc ~/.profile 2>/dev/null
```

### Кейс 3: «Разные значения переменной в разных сессиях»

**Симптом:** в одном терминале `echo $MY_VAR` даёт `production`, в другом — пусто.

```bash
# Шаг 1: понимаем откуда берётся значение в первом терминале
# Возможные причины:
# - переменная задана только в текущей сессии (export в терминале)
# - один терминал — login shell (читает ~/.profile), другой — нет

# Шаг 2: проверяем тип сессии

# -bash  ← login shell (тире в начале)
# bash   ← обычный интерактивный shell

# Шаг 3: смотрим что задано временно в сессии
export -p | grep MY_VAR

# Шаг 4: ищем где переменная задаётся постоянно
grep -r "MY_VAR" ~/.bashrc ~/.profile ~/.bash_profile /etc/environment /etc/profile.d/ 2>/dev/null

# Шаг 5: если нигде — переменная была задана вручную в этой сессии и пропадёт

echo 'export MY_VAR=production' >> ~/.bashrc

### Кейс 4: «Переменная задана, но приложение берёт старое значение»

**Симптом:** изменили `DB_HOST` в `/etc/myapp/env`, перезапустили — приложение всё равно коннектится к старому хосту.

# Шаг 3: перезапускаем правильно
systemctl daemon-reload
systemctl restart myapp

# Шаг 4: проверяем
cat /proc/$(pgrep -o myapp)/environ | tr '\0' '\n' | grep DB_HOST
# DB_HOST=new-host.internal ← теперь правильно
```

### Кейс 5: «Cron скрипт не работает хотя вручную работает»

**Симптом:** скрипт деплоя работает вручную, но падает в cron.

```bash
# Типичная ошибка в cron:
# /opt/myapp/deploy.sh: line 5: python3: command not found

# Причина: у cron минимальный PATH
# PATH=/usr/bin:/bin  ← только базовые директории

# Шаг 1: посмотреть что видит cron
# Добавить в crontab временную задачу:
* * * * * env > /tmp/cron_env.txt
# через минуту смотрим:
cat /tmp/cron_env.txt
# PATH=/usr/bin:/bin
# HOME=/root
# LOGNAME=root
# Нет ~/.bashrc, нет кастомных переменных!

# Шаг 2: решение — явно задать PATH в crontab
crontab -e
# PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/opt/myapp/bin
# 0 2 * * * /opt/myapp/deploy.sh

# или задать PATH в самом скрипте
cat deploy.sh
# #!/bin/bash
# export PATH="/usr/local/bin:/usr/bin:/bin:$PATH"
# source /etc/myapp/env  ← явно загружаем переменные
```

## 11. Вопросы на собесе

### Базовый уровень

**В: Чем `export VAR=value` отличается от `VAR=value`?**
> О: `VAR=value` создаёт переменную оболочки — она видна только внутри текущего bash процесса, дочерние процессы её не получат. `export VAR=value` добавляет переменную в окружение процесса — она передаётся всем дочерним процессам при `fork()`. Проверить: `export -p` покажет только экспортированные переменные.

**В: Где хранится переменная окружения запущенного процесса?**
> О: В адресном пространстве самого процесса. Прочитать можно через `/proc/<PID>/environ` — переменные разделены нулевым байтом. Важно: это снимок в момент запуска, изменение файла конфигурации не меняет переменные живого процесса.

**В: Почему `limits.conf` не работает для systemd, а `~/.bashrc` не работает для cron?**
> О: Оба механизма работают через PAM или login shell — они применяются только при интерактивном логине. systemd запускает сервисы напрямую без PAM. cron запускает задачи с минимальным окружением. Для systemd нужен `EnvironmentFile=` в unit файле, для cron — явный `export PATH=` в crontab или в скрипте.

**В: Добавили переменную в `~/.bashrc`, но cron-скрипт её не видит. Как исправить и как дебажить?**

> **Почему это происходит:** cron запускает задачи напрямую без bash-сессии пользователя. `~/.bashrc` не читается, окружение минимальное — только `HOME`, `LOGNAME`, `SHELL` и урезанный `PATH`.
>
> **Варианты решений:**
>
> **1. Установить переменную прямо в crontab — лучшая практика**
> ```
> # задаётся один раз в начале crontab, действует на все задачи
> MY_VAR=hello
> PATH=/usr/local/bin:/usr/bin:/bin
>
> * * * * * /opt/scripts/deploy.sh
> ```
> Это явно и предсказуемо — окружение видно прямо в crontab без поиска по файлам.
>
> **2. Задать переменную внутри самого скрипта**
> ```bash
> #!/bin/bash
> export MY_VAR=hello
> export PATH=/usr/local/bin:/usr/bin:/bin
> # остальной код...
> ```
> Подходит если скрипт запускается и вручную и через cron — он сам несёт своё окружение.
>
> **3. Явно загрузить нужный файл в начале скрипта**
> ```bash
> #!/bin/bash
> source /etc/myapp/env.sh   # отдельный файл с переменными
> # или
> set -a; source /etc/myapp/.env; set +a
> ```
> Хуже чем вариант 1 — зависимость от внешнего файла, надо следить за его путём.
>
> **4. `source ~/.bashrc` в начале скрипта — антипаттерн**
> ```bash
> source ~/.bashrc  # ❌ не делайте так
> ```
> `.bashrc` предназначен для интерактивных сессий — он может содержать команды которые ломаются без терминала (`bind`, `stty`, интерактивные алиасы). Это хрупко.
>
> ---
>
> **Как дебажить:**
>
> **Шаг 1 — посмотреть что вообще видит cron.** Добавить временную задачу которая сбросит окружение в файл:
> ```
> * * * * * env > /tmp/cron_env.txt 2>&1
> ```
> Через минуту:
> ```bash
> cat /tmp/cron_env.txt
> # увидите минимальный PATH, отсутствие MY_VAR и т.д.
> ```
>
> **Шаг 2 — воспроизвести окружение cron локально,** не ждя следующего запуска:
> ```bash
> # запустить скрипт с тем же минимальным окружением что у cron
> env -i HOME=/home/user SHELL=/bin/bash LOGNAME=user \
>     PATH=/usr/bin:/bin /bin/bash /opt/scripts/deploy.sh
> ```
> Если скрипт упадёт здесь — нашли проблему, не нужно ждать cron.
>
> **Шаг 3 — проверить логи cron** если скрипт молча не выполняется:
> ```bash
> grep CRON /var/log/syslog | tail -20
> # или
> journalctl -u cron --since "1 hour ago"
> ```

### Middle уровень

**В: Изменили EnvironmentFile сервиса, сделали `systemctl restart`. Переменная всё равно старая. Почему?**
> О: После изменения unit файла или EnvironmentFile нужно сначала `systemctl daemon-reload` — это заставляет systemd перечитать конфигурацию с диска. Затем `systemctl restart`. Без daemon-reload systemd использует кэшированный unit файл. Проверить реальные переменные: `cat /proc/<PID>/environ | tr '\0' '\n'`.

**В: Почему в `ExecStart=` нельзя использовать `$HOME` или `$(hostname)`?**
> О: systemd запускает процессы напрямую через `execve()`, минуя bash. Никакой оболочки нет — нет раскрытия `$VAR`, нет подстановок `$(cmd)`, нет glob. Строка из `ExecStart=` передаётся ядру буквально. Если нужен bash — явно вызывать: `ExecStart=/bin/bash -c '...'`. Для переменных — использовать `Environment=` или `EnvironmentFile=`.

**В: У вас два сервиса запущены от одного пользователя `www-data`. Как дать им разные переменные окружения?**
> О: Переменные окружения задаются на уровне процесса/сервиса, не пользователя. Каждый unit файл имеет свой `Environment=` или `EnvironmentFile=`. Оба сервиса могут быть от `www-data` но иметь совершенно разные переменные — они изолированы на уровне процессов.

**В: Как переменные окружения передаются от родителя к дочернему процессу?**
> О: Через два системных вызова. `fork()` создаёт точную копию процесса включая полную копию окружения — теперь два процесса с одинаковым окружением. `execve()` заменяет код дочернего процесса новой программой и принимает окружение третьим аргументом — именно так новая программа его получает. После этого у каждого процесса своя независимая копия: изменение переменной в дочернем не влияет на родителя. systemd не использует bash как посредника — он сам вызывает `execve()` напрямую, передавая только то окружение которое задано в `Environment=` и `EnvironmentFile=`. Поэтому `~/.bashrc` на сервисы не влияет.

**В: Сервис упал с ошибкой «Argument list too long». Как диагностировать и исправить?**
> О: Суммарный размер переменных окружения превысил `ARG_MAX` (обычно 2MB). Диагностика: `env | wc -c` — размер окружения, `env | awk -F= '{print length($0), $1}' | sort -rn | head -10` — самые большие переменные. Решение: вынести большие значения (сертификаты, ключи) из переменных в файлы и передавать путь к файлу, разбить `EnvironmentFile=` на несколько маленьких, убрать неиспользуемые переменные.

## 12. Шпаргалка

### Основные команды

```bash
env                          # показать всё окружение текущего процесса
env | sort                   # то же, отсортированно
export -p                    # только экспортированные переменные
echo $VAR                    # значение переменной
printenv VAR                 # то же, но безопаснее (не ломается на пустых)

export VAR=value             # создать/обновить переменную окружения
unset VAR                    # удалить переменную
VAR=value command            # задать только для одной команды

source ~/.bashrc             # применить изменения bashrc в текущей сессии
. ~/.bashrc                  # то же, короче
```

### Диагностика

```bash
# окружение запущенного процесса
cat /proc/<PID>/environ | tr '\0' '\n'
cat /proc/<PID>/environ | tr '\0' '\n' | grep VAR

# откуда берётся переменная
grep -r "VAR_NAME" /etc/environment /etc/profile /etc/profile.d/ \
    ~/.bashrc ~/.profile 2>/dev/null

# что видит systemd сервис
systemctl show <svc> | grep -i environment
cat /proc/$(pgrep -o <svc>)/environ | tr '\0' '\n'

# базовое окружение systemd
systemctl show-environment
```

### Где хранить для каждого случая

| Где хранить | Для кого работает | Когда применяется |
|------------|------------------|-------------------|
| `/etc/environment` | Все пользователи | При логине (PAM) |
| `/etc/profile.d/*.sh` | Все пользователи | Login shell |
| `~/.bashrc` | Текущий пользователь | Интерактивный терминал |
| `~/.profile` | Текущий пользователь | Login shell |
| `EnvironmentFile=` в unit | systemd сервис | При старте сервиса |
| `Environment=` в unit | systemd сервис | При старте сервиса |
| Crontab `VAR=val` | Cron задачи | При выполнении задачи |

### Размер окружения

```bash
getconf ARG_MAX                                          # лимит системы (обычно 2MB)
env | wc -c                                              # размер текущего окружения
env | awk -F= '{print length($0), $1}' | sort -rn | head -10  # топ по размеру
wc -c < /proc/<PID>/environ                             # размер окружения процесса
```

### Права на файлы с секретами

```bash
# только root читает
chown root:root /etc/myapp/secrets.env
chmod 600 /etc/myapp/secrets.env

# root + группа сервиса читают
chown root:myapp /etc/myapp/secrets.env
chmod 640 /etc/myapp/secrets.env
```
