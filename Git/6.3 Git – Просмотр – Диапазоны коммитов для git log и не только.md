# 6.3 Git – Просмотр – Диапазоны коммитов для git log и не только

`git log` — не только команда «покажи историю». Она понимает диапазоны и наборы коммитов: несколько ссылок сразу, исключение одной ветки из другой, разность между двумя ветками. Дальше — на одном сквозном примере: ветка `master` и отделившаяся от неё `feature`, которые с этого момента развиваются независимо.

## Базовое поведение git log

По умолчанию `git log` выводит коммиты, достижимые из текущего HEAD — историю активной ветки. Управлять этим можно несколькими способами:

1. **Указать конкретную ссылку.** `git log feature` покажет историю, достижимую из `feature`, стоя при этом на `master` — переключаться веткой не нужно, команда только читает граф коммитов, не трогая рабочую директорию. Вместо имени ветки подойдёт тег или хеш коммита.

2. **Указать несколько ссылок.** `git log master feature` выведет коммиты, достижимые хотя бы из одной из них, — это объединение, а не пересечение. Общая часть истории попадёт в вывод один раз, а порядок коммитов — не «сначала одна ветка, потом другая», а по дате, вперемешку.

3. **`--graph`.** Рисует ASCII-граф веток прямо в терминале: `*` — коммит, `|` — линия ветки, `/` и `\` — точки расхождения и слияния. На практике почти всегда идёт в связке с `--oneline` — без него граф расползается на десятки строк из-за многострочных сообщений коммитов.

4. **`--all`.** Показывает коммиты, достижимые от всех существующих ссылок — всех веток и тегов, а не только текущей.

5. **`--decorate`.** Подписывает у коммита имена ссылок, которые на него указывают, — ветки, HEAD, теги. Без флага в выводе только хеш и сообщение, непонятно, где физически находятся ветки. `HEAD -> master` значит: HEAD сейчас на `master`, а `master` указывает на этот коммит.

`git log --oneline --all --graph --decorate` — быстрый способ увидеть состояние всего репозитория целиком: какие ветки где стоят, не переключаясь между ними:

```
$ git log --oneline --all --graph --decorate
* 0865309 (feature) C3: feature change 3
* 58fc4d0 C2: feature change 2
* d26e9f9 C1: feature change 1
| * c456e33 (HEAD -> master) D2: master change 2
| * 2e729d6 D1: master change 1
|/
* 587d152 B: common base
* 5606096 A: init
```

Несмотря на графические клиенты вроде gitk или встроенных средств IDE, `git log` остаётся основным инструментом — благодаря гибкости и количеству флагов для поиска: по автору, по сообщению коммита, по изменениям в содержимом файлов.

## Две точки: диапазон между ветками

Частая задача — посмотреть, что появилось в `feature` с момента, когда она отделилась от `master`, и ещё не попало в `master`.

Синтаксис с `^` исключает всё, что достижимо из указанной ссылки: `git log feature ^master` покажет коммиты, которые есть в `feature`, но недостижимы из `master`. Запись через две точки, `git log master..feature`, полностью эквивалентна — тот же самый диапазон, только более читаемый и распространённый синтаксис.

```
$ git log --oneline master..feature
0865309 C3: feature change 3
58fc4d0 C2: feature change 2
d26e9f9 C1: feature change 1
```

Порядок операндов важен. Поменяв стороны местами — `feature..master` — получим обратное: что есть в `master`, но нет в `feature`, в примере выше `D1` и `D2`.

Если одна из сторон диапазона — HEAD, её можно опустить с любой стороны. Стоя на `master`, `git log ..feature` равносильно `git log master..feature`, а `git log feature..` — `git log feature..master`. Именно так на практике чаще всего проверяют, не отстала ли текущая ветка от удалённой: `git log ..origin/master` покажет коммиты в `origin/master`, которых ещё нет локально.

## Три точки: симметрическая разность

Три точки решают другую задачу — сравнить две ветки напрямую, без общей истории. `git log master...feature` покажет коммиты, которые есть либо в `master`, либо в `feature`, но не в обеих сразу:

```
$ git log --oneline master...feature
c456e33 D2: master change 2
0865309 C3: feature change 3
2e729d6 D1: master change 1
58fc4d0 C2: feature change 2
d26e9f9 C1: feature change 1
```

В отличие от простого перечисления двух ссылок (`git log master feature` из раздела выше), где в вывод попадает и общая история, три точки её отсекают — остаются только `D1`, `D2`, `C1`, `C2`, `C3`, а общие `A` и `B` пропадают.

Два флага делают эту разность читаемой:

1. **`--boundary`.** Добавляет в вывод «пограничный» коммит — точку, в которой ветки разошлись. В `--graph` он рисуется кружком (`o`) вместо звёздочки (`*`), которой помечены обычные коммиты.

2. **`--left-right`.** Помечает каждый коммит символом `<` или `>` — в зависимости от того, с какой стороны он пришёл, из первой ссылки или из второй.

Вместе с `--graph` это даёт наглядное представление о расхождении одной командой:

```
$ git log --oneline --graph --left-right --boundary master...feature
< c456e33 D2: master change 2
< 2e729d6 D1: master change 1
| > 0865309 C3: feature change 3
| > 58fc4d0 C2: feature change 2
| > d26e9f9 C1: feature change 1
|/
o 587d152 B: common base
```

## git diff: другой смысл тех же точек

Тот же синтаксис `..` и `...` в `git diff` работает совершенно иначе, чем в `git log` — подробный разбор в теме 6.1, здесь только контраст, чтобы не спутать одно с другим на собеседовании.

| Синтаксис | В `git log` | В `git diff` |
|---|---|---|
| `A..B` | коммиты, достижимые из B, но не из A | то же, что `git diff A B` — прямое сравнение состояний A и B |
| `A...B` | симметрическая разность: уникальные коммиты обеих сторон | сравнение merge-base(A, B) с B — что изменилось в B с момента расхождения, изменения в A игнорируются |

В `git log` точки задают операции над множеством коммитов, и результат — список коммитов. В `git diff` они задают, какие два состояния сравнить построчно, и результат — один diff. Прямой аналогии между смыслом точек в этих двух командах нет и искать её не стоит: в diff они устроены иначе по историческим причинам.

## Не только git log

Диапазоны через `^`, `..` и `...` — не особенность `log`, а часть общего синтаксиса задания коммитов в Git. Его понимают `git diff`, `git show`, `git rebase`, `git cherry-pick` и другие команды, принимающие коммит или диапазон коммитов на вход, — с оговоркой, что смысл точек может отличаться, как в случае с `git diff` выше.

Полное описание синтаксиса — во встроенной документации: `git help revisions` (или `man gitrevisions`).
