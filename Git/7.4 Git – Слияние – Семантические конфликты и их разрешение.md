# 7.4 Git – Слияние – Семантические конфликты и их разрешение

## Что такое семантический конфликт

При слиянии двух веток Git сравнивает каждую из них не друг с другом напрямую, а с общим предком — коммитом, от которого обе ветки когда-то разошлись. Такое сравнение называется трёхсторонним слиянием: в нём участвуют три коммита — общий предок и обе ветки, — и по разнице с предком Git определяет, что изменила каждая ветка. Если изменения в разных ветках относятся к разным строкам файла, Git объединяет их автоматически, без запроса подтверждения.

Эта проверка чисто текстовая: Git смотрит, пересекаются ли изменённые строки, но не анализирует, как эти строки взаимодействуют по смыслу. Из-за этого возможна ситуация, когда две ветки меняют разные места файла, слияние проходит без единого конфликта, а получившийся код всё равно не работает. Такую ситуацию называют семантическим конфликтом — в отличие от обычного (технического) конфликта, здесь Git не видит проблему в принципе и не сообщает о ней ни в процессе слияния, ни в `git status`.

Типичный сценарий: в одной ветке меняется сигнатура функции — её объявление с именем и набором параметров. В неё добавляется обязательный аргумент, и все существующие вызовы этой функции в той же ветке обновляются под новую сигнатуру. Параллельно в другой ветке разработчик, не зная об этом изменении, добавляет новый вызов той же функции — в старом формате, без аргумента.

Ниже — состояние файла `deploy.py` в двух ветках, разошедшихся от общего предка.

Ветка `master` (сигнатура функции изменена, единственный существующий вызов обновлён):

```python
def deploy(environment):
    print(f"Deploying to {environment}")

def notify():
    print("Sending notification")

def run_pipeline():
    deploy("production")
    notify()

run_pipeline()
```

Ветка `ui` (добавлена новая функция, которая вызывает `deploy()` в старом формате):

```python
def deploy():
    print("Deploying")

def notify():
    print("Sending notification")

def run_pipeline():
    deploy()
    notify()

def run_pipeline_staging():
    deploy()

run_pipeline()
run_pipeline_staging()
```

Изменения `master` — это определение функции и вызов внутри `run_pipeline()`. Изменения `ui` — это только добавленные в конец файла функция `run_pipeline_staging()` и её вызов. Эти строки не пересекаются, поэтому слияние проходит чисто:

```
$ git merge ui
Auto-merging deploy.py
Merge made by the 'ort' strategy.
 deploy.py | 4 ++++
 1 file changed, 4 insertions(+)
```

Git не сообщил ни об одном конфликте. Но в результирующем файле функция `run_pipeline_staging()` по-прежнему вызывает `deploy()` без аргумента, а функция теперь требует его обязательно:

```python
def run_pipeline_staging():
    deploy()
```

При запуске скрипта это приводит к ошибке уже во время выполнения, а не во время слияния:

```
$ python3 deploy.py
Deploying to production
Sending notification
Traceback (most recent call last):
  File "deploy.py", line 15, in <module>
    run_pipeline_staging()
  File "deploy.py", line 12, in run_pipeline_staging
    deploy()
TypeError: deploy() missing 1 required positional argument: 'environment'
```

Коммит слияния при этом уже зафиксирован в истории репозитория:

```
$ git log --oneline -1
04cc39a Merge branch 'ui'
```

## Почему нельзя просто исправить новым коммитом

Технически ничего не мешает оставить коммит слияния как есть и исправить `run_pipeline_staging()` отдельным следующим коммитом. Но коммит фиксирует снимок файлов на момент своего создания, и этот снимок неизменен — более поздний коммит не переписывает то, что записано в более раннем. Коммит `04cc39a` из примера выше навсегда останется коммитом с ошибочным кодом, даже после того как в ветке появится исправление:

```
$ git show 04cc39a:deploy.py | tail -5
def run_pipeline_staging():
    deploy()

run_pipeline()
run_pipeline_staging()
```

Если кто-то позже обратится именно к этому коммиту — например, для сборки конкретной версии или анализа истории — он получит код с ошибкой.

Поэтому слияние с семантическим конфликтом считается незавершённым, пока ошибка не исправлена внутри самого коммита слияния, а не отдельным коммитом после него.

## Как исправить семантический конфликт

Если коммит слияния уже создан и проблема обнаружена постфактум, первым делом нужно вернуться в состояние до слияния:

```
$ git reset --hard HEAD~1
HEAD is now at 393b077 Добавить обязательный аргумент environment в deploy()
```

`HEAD~1` — это первый родитель коммита слияния, то есть коммит, на котором ветка `master` находилась до объединения с `ui`.

Дальше слияние повторяют с флагом `--no-commit`: он выполняет слияние, но останавливается перед созданием коммита.

Если бы слияние могло пройти fast-forward'ом — то есть `master` был бы прямым предком `ui` без собственных новых коммитов, — `--no-commit` не сработал бы как ожидается: при fast-forward Git сразу перемещает указатель ветки и обновляет рабочую директорию, не создавая коммит слияния вовсе, и флагу тут нечего останавливать. В этом примере ветки уже разошлись, fast-forward невозможен, и `--no-commit` останавливает слияние перед коммитом, как и задумано:

```
$ git merge --no-commit ui
Auto-merging deploy.py
Automatic merge went well; stopped before committing as requested
```

`git status` в этот момент показывает, что слияние ещё не завершено, хотя технических конфликтов нет:

```
$ git status
On branch master
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
	modified:   deploy.py
```

Файл `deploy.py` в рабочей директории уже содержит результат слияния — то есть ту самую ошибку. Её нужно исправить вручную:

```python
def run_pipeline_staging():
    deploy("staging")
```

После исправления файл добавляется в индекс, и слияние завершается коммитом. Пока идёт слияние, `git commit` без дополнительных флагов открывает редактор с уже подготовленным сообщением (`Merge branch 'ui'`), чтобы его можно было изменить перед сохранением. Флаг `--no-edit` пропускает этот шаг и сразу принимает сообщение как есть, не открывая редактор:

```
$ git add deploy.py
$ git commit --no-edit
[master 193b2a4] Merge branch 'ui'
```

Вместо `git commit --no-edit` можно выполнить `git merge --continue` — команда делает то же самое: проверяет, что слияние ещё не завершено, и создаёт коммит с тем же сообщением, тоже не открывая редактор.

В истории при этом остаётся один коммит слияния, а не коммит слияния плюс отдельный исправляющий коммит:

```
$ git log --graph --decorate --oneline master ui
*   193b2a4 (HEAD -> master) Merge branch 'ui'
|\
| * 19c03d2 (ui) Добавить run_pipeline_staging() с повторным вызовом deploy()
* | 393b077 Добавить обязательный аргумент environment в deploy()
|/
* d11b37a Начальная версия deploy.py
```

Запуск скрипта теперь проходит без ошибок:

```
$ python3 deploy.py
Deploying to production
Sending notification
Deploying to staging
```

Всё описанное выше — это исправление уже случившейся ситуации: `git merge ui` был выполнен как обычно, конфликтов не было, Git сразу создал коммит слияния, и только потом обнаружилась ошибка. Если же есть основания заранее ожидать семантический конфликт — например, известно, что менялась сигнатура часто используемой функции, — можно не рисковать и с самого начала, вместо обычного `git merge ui`, выполнить `git merge --no-commit ui`. Тогда автоматического коммита не будет вовсе, результат можно проверить, пока он ещё только в индексе, и шаг с `reset --hard` не понадобится.

## Как Git отслеживает состояние слияния

Пока слияние не завершено коммитом — будь то из-за технического конфликта или из-за `--no-commit` — Git хранит информацию об этом в файле `.git/MERGE_HEAD`. В нём записан SHA-1 коммита, который вливается в текущую ветку:

```
$ cat .git/MERGE_HEAD
19c03d2c10fd8fecb0c1fea2dacb000c83a7e429
$ git rev-parse ui
19c03d2c10fd8fecb0c1fea2dacb000c83a7e429
```

Именно наличие этого файла говорит Git, что сейчас идёт слияние, а не обычная фиксация изменений. Когда выполняется `git commit`, Git проверяет, существует ли `MERGE_HEAD`. Если файл есть, создаётся коммит с двумя родителями — текущим `HEAD` и коммитом из `MERGE_HEAD`, то есть коммит слияния. После создания коммита файл `MERGE_HEAD` удаляется.

Сообщение по умолчанию для коммита слияния ("Merge branch 'ui'") Git заранее записывает в файл `.git/MERGE_MSG` — оно и подставляется, когда используется `--no-edit` или `git merge --continue`.
