# 3. Ad-hoc команды и модули Ansible

## Что такое ad-hoc команды

Ad-hoc (от латинского "для этого случая") — это запуск одного конкретного действия прямо из командной строки, без написания плейбука. Способ сказать Ansible: "зайди на эти машины и сделай вот это прямо сейчас".

Структура команды всегда одна и та же:

```bash
ansible <группа> -m <модуль> -a "<аргументы>" -i <inventory>
```

- `<группа>` — кто выполняет (группа из inventory или конкретный хост)
- `-m` — какой модуль использовать
- `-a` — аргументы модуля (что именно сделать)
- `-i` — путь к inventory (если не прописан в `ansible.cfg`)

**Про флаг `-a`:** расшифровывается как "module arguments". Это "дверь" для передачи данных внутрь модуля — но что именно передавать, зависит от самого модуля. Например, модуль `command` ожидает команду для выполнения (`"df -h"`, `"uptime"`), при этом `-h` — это уже аргумент самой утилиты `df`, а не Ansible, просто он едет внутри строки. Модуль `apt` ожидает параметры в формате ключ=значение (`"name=nginx state=present"`) — никакой команды тут нет. Модуль `copy` ожидает пути (`"src=/файл dest=/куда"`). А модуль `ping` вообще не требует `-a` и работает без него.

То есть без `-a` упадут только те модули, которым обязательно нужны параметры для работы — например `command` (непонятно что выполнять). Остальные могут работать и без него.

Ты уже использовал ad-hoc — `ansible cashregisters -m ping` это и есть ad-hoc команда с модулем `ping` без аргументов.

---

## Зачем это нужно, если есть плейбуки

Ad-hoc удобен для:
- **Быстрой диагностики** — проверить дисковое пространство на всех кассах одной командой.
- **Разовых действий** — перезапустить сервис, не писать ради этого плейбук.
- **Тестирования модулей** — прежде чем писать плейбук, проверить что модуль делает именно то, что нужно.

---

## Основные модули

Модулей в Ansible сотни, но на практике 80% задач закрывают около десятка:

| Модуль | Что делает |
|---|---|
| `ping` | Проверка связи |
| `command` | Выполнить команду на хосте |
| `shell` | Выполнить команду через `/bin/sh` (поддерживает пайпы, переменные окружения) |
| `apt` | Управление пакетами (установка, удаление, обновление) |
| `copy` | Скопировать файл с control node на хост |
| `fetch` | Скопировать файл с хоста на control node |
| `file` | Создать/удалить файл или директорию, поменять права |
| `service` / `systemd` | Запустить/остановить/перезапустить сервис |
| `template` | Скопировать файл с подстановкой переменных (Jinja2) |
| `user` | Создать/удалить пользователя |

## Модуль `command` — выполнить команду на хосте

Самый базовый модуль. Он просто берёт указанную утилиту и запускает её на удалённой машине напрямую, без привлечения командной оболочки (шелла).

```bash
# Проверить свободное место на дисках всех касс
ansible cashregisters -m command -a "df -h" -i inventory/hosts.yml

# Посмотреть аптайм кассовых серверов
ansible cashregisters -m command -a "uptime" -i inventory/hosts.yml
```

**📋 Разбор ответа Ansible**

Когда команда выполнится, вы увидите подобный ответ в терминале:

```
rmk-161 | CHANGED | rc=0 >>
 21:03:38 up 13 days,  4:33,  6 users,  load average: 0.01, 0.10, 0.21
```

Первая строка — это стандартный сервисный заголовок Ansible. Он всегда строится по жёсткой схеме:

```
<имя_хоста> | <статус> | rc=<код> >>
```

- `rmk-161` — локальное имя-маска (алиас) кассы из файла inventory.
- `CHANGED` — статус (результат) выполнения.
- `rc=0` — Return Code (код возврата). `0` всегда означает, что Linux-команда завершилась успешно. Любое другое число — признак ошибки.
- `>>` — разделитель, указывающий, что ниже идёт чистый текст, который вернула сама команда.

**Важно:** у специализированных модулей (вроде `apt` или `file`) вывод после заголовка будет идти не обычным текстом, а в формате JSON, но сам заголовок останется точно таким же:

```
cash-001 | CHANGED => { "changed": true, ... }
```

**🎨 Четыре глобальных статуса Ansible**

В зависимости от исхода операции, имя хоста и статус подкрашиваются в терминале разными цветами:

- `SUCCESS` (зелёный) — задача выполнилась успешно, но система уже была в нужном состоянии, поэтому никаких изменений не произошло (например: вы запускали старт сервиса, а он и так уже работал).
- `CHANGED` (жёлтый) — сценарий отработал успешно, и состояние системы изменилось.
- `FAILED` (красный) — произошла ошибка внутри самого сервера (например, вы опечатались в команде). Код возврата `rc` при этом будет отличным от нуля.
- `UNREACHABLE` (красный) — Ansible вообще не смог достучаться до кассы (упала сеть, выключено питание или заблокирован SSH).

**🛠️ Подвох статуса `CHANGED` у модулей `command` и `shell`**

Вы заметите, что обычные команды (`df -h`, `uptime`) всегда возвращают жёлтый статус `CHANGED`. Почему так?

**Как ведут себя «умные» модули (`apt`, `file`, `template`):** они написаны на Python. Перед работой они заглядывают в систему, сравнивают её текущее состояние с тем, что вы просите, и если пакет уже стоит или папка создана — спокойно возвращают зелёный `SUCCESS`.

**Как ведут себя `command` и `shell`:** они «слепые». Ansible видит только факт запуска бинарника и код `rc=0`. Он физически не знает, поменяла ли утилита что-то на диске или нет. Поэтому Ansible действует из соображений паранойи: «Я что-то успешно запустил на хосте, а значит состояние системы потенциально изменилось» — и на всякий случай красит ответ в жёлтый `CHANGED`.

**⚠️ Ограничение модуля `command`**

Поскольку модуль запускает утилиты напрямую, минуя командную оболочку (шелл), он категорически не поддерживает:

- Пайпы и конвейеры (символ `|`) — нельзя отфильтровать вывод через `grep`.
- Перенаправления потоков в файлы (символы `>`, `>>`).
- Чтение системных переменных окружения (например, `$PATH` или `$USER`).

Если нужен этот функционал, вместо `command` используется модуль `shell`, который разберём далее.

## Модуль `shell` — команда через `/bin/sh`

Работает так же как `command`, но выполняет команду через полноценный шелл. Поддерживает пайпы, перенаправления, переменные окружения.

```bash
# Пайп — найти все запущенные Java-процессы на кассах
ansible cashregisters -m shell -a "ps aux | grep java | grep -v grep" -i inventory/hosts.yml

# Проверить последние строки лога
ansible cashregisters -m shell -a "tail -n 20 /linuxcash/logs/cashserver.log" -i inventory/hosts.yml

# Перенаправление > — сохранить список процессов в файл на кассе
ansible cashregisters -m shell -a "ps aux > /tmp/processes.txt" -i inventory/hosts.yml

# Перенаправление >> — дописать в конец файла (не перезаписывая)
ansible cashregisters -m shell -a "date >> /tmp/audit.log" -i inventory/hosts.yml

# Переменная окружения — узнать под каким пользователем реально выполняется команда
ansible cashregisters -m shell -a 'echo $USER' -i inventory/hosts.yml
```

**Про кавычки в `-a`:** если обернуть аргумент в двойные кавычки (`"echo $USER"`), локальный шелл на управляющем сервере подставит значение `$USER` ещё до отправки команды на кассы — на кассах выполнится уже `echo fa1ry` вместо `echo $USER`. Чтобы переменную читал именно шелл внутри кассы, используются одинарные кавычки (`'echo $USER'`) — они запрещают локальному шеллу раскрывать переменные.

## Модуль `apt` — управление пакетами (для Ubuntu/Debian)

Используется для установки, обновления или удаления программ. Аргументы передаются строго в формате ключ=значение.

| Параметр | Что делает |
|---|---|
| `name` | Имя пакета |
| `state` | `present` — установить, `absent` — удалить, `latest` — обновить до последней версии |
| `update_cache` | `yes` — выполнить `apt update` перед установкой |
| `upgrade` | `yes` — обновить все пакеты (аналог `apt upgrade`) |
| `autoremove` | `yes` — удалить ненужные зависимости (аналог `apt autoremove`) |
| `install_recommends` | `no` — не ставить рекомендуемые пакеты (уменьшает размер установки) |
| `deb` | Путь к локальному `.deb` файлу — установка напрямую без репозитория |

```bash
# Установить утилиту curl на все кассы
ansible cashregisters -m apt -a "name=curl state=present" -i inventory/hosts.yml

# Удалить ненужный пакет (например, nmap)
ansible cashregisters -m apt -a "name=nmap state=absent" -i inventory/hosts.yml

# Обновить кэш репозиториев (аналог команды apt update)
ansible cashregisters -m apt -a "update_cache=yes" -i inventory/hosts.yml
```

Обрати внимание на параметры `state=present` (установить, если нет) и `state=absent` (удалить, если есть). Это чистый пример декларативного подхода Ansible.

## Модули `copy` и `fetch` — работа с файлами по сети

`copy` — отправляет файл с управляющего сервера на кассы. `fetch` — наоборот, забирает файл с удалённой кассы на управляющий сервер.

```bash
# Залить обновлённый конфиг на все кассы
ansible cashregisters -m copy -a "src=/tmp/cashserver.conf dest=/linuxcash/config/cashserver.conf" -i inventory/hosts.yml

# Стянуть лог с одной конкретной проблемной кассы для анализа
ansible rmk-161 -m fetch -a "src=/linuxcash/logs/cashserver.log dest=/tmp/logs/" -i inventory/hosts.yml
```

При использовании `fetch` Ansible не просто кладёт файл в `dest` — он воспроизводит внутри неё полную структуру: имя хоста и полный путь к файлу на удалённой машине. То есть файл из примера выше ляжет не в `/tmp/logs/cashserver.log`, а в:

```
/tmp/logs/rmk-161/linuxcash/logs/cashserver.log
```

Это сделано специально — если забирать одноимённые файлы с нескольких касс сразу, они не перезапишут друг друга, каждый окажется в своей подпапке с именем хоста.

⚠️ **Ограничение `fetch`:** работает только с одиночными файлами, директории не поддерживаются. Для скачивания целой директории есть два способа: универсальный — через `shell` запаковать директорию в архив `tar` на кассе, потом забрать архив через `fetch`; или через модуль `synchronize` (обёртка над `rsync`) — удобнее, но требует наличия `rsync` на обеих машинах.

## Модуль `file` — управление правами, папками и ссылками

Нужен для создания каталогов, удаления старых файлов и выставления прав (`chmod` / `chown`).

```bash
# Создать папку под новые логи и выставить владельца и права
ansible cashregisters -m file -a "path=/linuxcash/logs/new_service state=directory owner=artix group=artix mode=0755" -i inventory/hosts.yml

# Удалить временный файл с касс
ansible cashregisters -m file -a "path=/tmp/old_dump.sql state=absent" -i inventory/hosts.yml
```

## Модуль `systemd` — управление службами

Позволяет запускать, останавливать, перезапускать сервисы на кассах, а также управлять их автозагрузкой.

```bash
# Массово перезапустить кассовую службу
ansible cashregisters -m systemd -a "name=cashserver state=restarted" -i inventory/hosts.yml

# Остановить службу nginx и убрать её из автозагрузки
ansible cashregisters -m systemd -a "name=nginx state=stopped enabled=no" -i inventory/hosts.yml
```

## Модуль `user` — управление пользователями

Создаёт, изменяет или удаляет системных пользователей на удалённых машинах.

```bash
# Создать пользователя ansible на всех кассах
ansible cashregisters -m user -a "name=ansible shell=/bin/bash state=present" -i inventory/hosts.yml

# Удалить пользователя с касс
ansible cashregisters -m user -a "name=olduser state=absent remove=yes" -i inventory/hosts.yml
```

Параметр `remove=yes` при `state=absent` дополнительно удаляет домашнюю директорию пользователя.

## 🛠️ Полезные фишки ad-hoc команд

**Группа `all`:** если нужно выполнить команду по всем хостам из инвентаря, вместо имени конкретной группы пишется `all`:

```bash
ansible all -m ping -i inventory/hosts.yml
```

**Режим проверки (`--check`):** флаг `-C` заставляет Ansible симулировать выполнение — зайдёт на кассы, покажет что изменилось бы, но физически на диск ничего не запишет. Идеально для безопасного аудита перед реальным запуском:

```bash
ansible cashregisters -m apt -a "name=curl state=present" -C -i inventory/hosts.yml
```

**Запуск с повышением прав (`-b`):** если модулю нужны root-права (например, для установки пакетов), добавляется флаг `-b` (become):

```bash
ansible cashregisters -m apt -a "name=htop state=present" -b -i inventory/hosts.yml
```
