# 10. Handlers и notify — паттерн «изменение → перезапуск сервиса»

## Зачем нужны handlers

Типовая ситуация: плейбук раскладывает конфиг сервиса. Сервис читает конфиг только при старте, поэтому после изменения файла его нужно перезапустить. Без handlers эта задача решается двумя способами, и оба плохие.

✗ **Вариант 1: безусловный перезапуск в конце плейбука.**

```yaml
- name: Deploy nginx config
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf

- name: Restart nginx
  ansible.builtin.service:
    name: nginx
    state: restarted
```

Перезапуск выполняется при каждом прогоне — даже когда конфиг не менялся. Сервис получает лишний рестарт (и короткий простой) на ровном месте, а вывод плейбука на «чистом» прогоне всегда показывает `changed`, хотя по факту ничего не изменилось.

✗ **Вариант 2: `register` + `when`.** Вот он в полном виде — три таски трогают конфигурацию сервиса, четвёртая перезапускает:

```yaml
- name: Deploy nginx config
  ansible.builtin.template: ...
  register: nginx_config

- name: Deploy TLS certificate
  ansible.builtin.copy: ...
  register: nginx_cert

- name: Deploy unit file
  ansible.builtin.template: ...
  register: nginx_unit

- name: Restart nginx
  ansible.builtin.service:
    name: nginx
    state: restarted
  when: nginx_config.changed or nginx_cert.changed or nginx_unit.changed
```

Это работает правильно: перезапуск случится только при реальном изменении. Проблемы начинаются при сопровождении — они разобраны ниже, после второго примера.

✓ **Handlers.** То же самое через `notify`:

```yaml
  tasks:
    - name: Deploy nginx config
      ansible.builtin.template: ...
      notify: Restart nginx

    - name: Deploy TLS certificate
      ansible.builtin.copy: ...
      notify: Restart nginx

    - name: Deploy unit file
      ansible.builtin.template: ...
      notify: Restart nginx

  handlers:
    - name: Restart nginx
      ansible.builtin.service:
        name: nginx
        state: restarted
```

Разница между вариантами — в трёх вещах:

**1. Связь объявлена на самой таске, а не в чужом условии.** В варианте 2 таска про сертификат сама по себе ничего не знает о рестарте — связь спрятана внизу, в `when` рестарта. В варианте с notify связь написана прямо на таске: «после меня уведоми "Restart nginx"». Читаешь таску — сразу видишь её последствия. Поэтому список «кто влияет на сервис» не нужно вести вручную и следить за его полнотой — он собирается сам из уведомлений на тасках.

**2. Добавление таски — одна строка, а не две правки.** Появилась четвёртая таска, влияющая на nginx. В варианте 2 нужно: добавить ей `register: nginx_something` **и** не забыть дописать `or nginx_something.changed` в условие рестарта, которое находится в другом месте файла. Забыл второй шаг — плейбук отрабатывает зелёным, а сервис работает на старом конфиге, и никто этого не видит. С notify четвёртая таска просто пишет себе `notify: Restart nginx` — условие рестарта править не нужно, его вообще нет.

**3. Служебные переменные исчезают.** `nginx_config`, `nginx_cert`, `nginx_unit` в варианте 2 существуют с единственной целью — донести факт `changed` до условия. Это три имени, которые нужно придумать, не перепутать и не опечатать в `when`. С notify учёт «было ли изменение» ведёт сам Ansible, переменные не нужны.

## Базовый синтаксис

Handler — это обычная таска, но живёт она в секции `handlers` (на том же уровне, что и `tasks`) и запускается не по порядку, а по уведомлению:

```yaml
- name: Configure nginx
  hosts: webservers
  become: true

  tasks:
    - name: Deploy nginx config          # обычная таска
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: Restart nginx              # имя handler-а, который нужно уведомить

  handlers:
    - name: Restart nginx                # это имя должно точно совпадать с notify
      ansible.builtin.service:
        name: nginx
        state: restarted
```

Связь между таской и handler-ом — **точное совпадение строки** в `notify` с `name` handler-а. Никакой магии по смыслу: `Restart nginx` и `restart nginx` — разные строки.

Ключевое правило: **notify срабатывает только если таска завершилась со статусом `changed`**. Как это выглядит на двух прогонах подряд:

Первый прогон — конфиг на хосте отличается от шаблона:

```
TASK [Deploy nginx config] *****************
changed: [web-01]

RUNNING HANDLER [Restart nginx] ************
changed: [web-01]
```

Второй прогон — конфиг уже на месте:

```
TASK [Deploy nginx config] *****************
ok: [web-01]
```

Таска отработала со статусом `ok` — уведомления не было, handler не запускался, сервис не трогали. Это и есть паттерн из названия темы: перезапуск привязан не к факту прогона плейбука, а к факту изменения.

Шаблоны и то, почему `ansible.builtin.template` корректно определяет «изменилось / не изменилось», разобраны в теме 7 — здесь это просто самый частый источник notify.

### `state: restarted` или `state: reloaded`

Для сервисов, которые умеют перечитывать конфиг без остановки (nginx, sshd), вместо полного перезапуска можно использовать мягкую перезагрузку:

```yaml
  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded
```

`restarted` останавливает и запускает процесс — активные соединения обрываются. `reloaded` отправляет сигнал перечитать конфиг — соединения живут. Что выбрать, зависит от сервиса: не все умеют reload, а некоторые изменения (например, смена портов у sshd) требуют полного рестарта. Механика handlers от этого выбора не меняется.

## Три правила выполнения

Здесь сосредоточены все сюрпризы handlers. Правила короткие, но именно на них ловятся ошибки.

### Правило 1: handler выполняется в конце плея, а не сразу после notify

```yaml
  tasks:
    - name: Deploy nginx config
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: Restart nginx

    - name: Deploy SSH banner
      ansible.builtin.template:
        src: banner.j2
        dest: /etc/ssh/banner

  handlers:
    - name: Restart nginx
      ansible.builtin.service:
        name: nginx
        state: restarted
```

Порядок выполнения: «Deploy nginx config» → «Deploy SSH banner» → и только потом «Restart nginx». Уведомление не запускает handler немедленно — оно ставит отметку «в конце плея выполнить». Это сделано намеренно: все таски, влияющие на сервис, успевают отработать, и сервис перезапускается один раз с уже полным набором изменений, а не после каждой правки по отдельности.

Важное уточнение: **в конце плея, а не плейбука**. Если в плейбуке два плея, handlers первого плея выполняются до старта второго. Уведомить из первого плея handler второго нельзя — секция `handlers` принадлежит своему плею.

### Правило 2: handler выполняется один раз, сколько бы уведомлений ни пришло

Пример уже был во введении: три таски (конфиг, сертификат, юнит-файл), и каждая уведомляет «Restart nginx». Вот как выглядит прогон, в котором все три отработали со статусом `changed`:

```
TASK [Deploy nginx config] *****************
changed: [web-01]

TASK [Deploy TLS certificate] **************
changed: [web-01]

TASK [Deploy unit file] ********************
changed: [web-01]

RUNNING HANDLER [Restart nginx] ************
changed: [web-01]
```

Три уведомления — один запуск. Повторные уведомления уже уведомлённого handler-а ничего не меняют. Это вторая половина смысла паттерна: сколько бы тасков ни трогали сервис, простой от перезапуска — один.

### Правило 3: порядок выполнения — порядок объявления в `handlers`, а не порядок notify

```yaml
  tasks:
    - name: Deploy application unit file
      ansible.builtin.template:
        src: myapp.service.j2
        dest: /etc/systemd/system/myapp.service
      notify:
        - Restart myapp          # уведомили первым...
        - Reload systemd         # ...уведомили вторым

  handlers:
    - name: Reload systemd       # ...но выполнится первым — объявлен раньше
      ansible.builtin.systemd_service:
        daemon_reload: true

    - name: Restart myapp        # выполнится вторым
      ansible.builtin.service:
        name: myapp
        state: restarted
```

Порядок строк в `notify` ни на что не влияет — handlers выполняются в том порядке, в котором записаны в секции `handlers`. Поэтому зависимости между handlers выражаются порядком объявления: здесь `daemon_reload` обязан пройти до рестарта (иначе systemd перезапустит сервис по старому юнит-файлу), значит «Reload systemd» стоит в секции первым.

## `notify` со списком

Пример выше уже использовал эту форму: одна таска может уведомить несколько handlers — `notify` принимает и строку, и список строк:

```yaml
      notify:
        - Reload systemd
        - Restart myapp
```

Каждый handler из списка получает свою отметку «выполнить в конце плея». Правила 1–3 работают для каждого независимо.

## `listen` — подписка на тему

До сих пор таска вызывала handler напрямую по имени: `notify: Restart nginx`. Но когда одно изменение должно запускать несколько handlers, список имён в каждом `notify` становится неудобным: добавился третий handler — правь все таски, где перечислены первые два.

`listen` решает это через **тему**: таска отправляет уведомление в тему, а handlers на неё **подписываются**:

```yaml
  tasks:
    - name: Deploy application unit file
      ansible.builtin.template:
        src: myapp.service.j2
        dest: /etc/systemd/system/myapp.service
      notify: Redeploy myapp         # уведомляем тему «Redeploy myapp»

    - name: Deploy application config
      ansible.builtin.template:
        src: myapp.conf.j2
        dest: /etc/myapp/myapp.conf
      notify: Redeploy myapp         # уведомляем ту же тему

  handlers:
    - name: Reload systemd
      ansible.builtin.systemd_service:
        daemon_reload: true
      listen: Redeploy myapp         # подписан на тему

    - name: Restart myapp
      ansible.builtin.service:
        name: myapp
        state: restarted
      listen: Redeploy myapp         # тоже подписан на тему
```

Как Ansible понимает, что в `notify` — имя или тема? Никак, ему это и не нужно: он просто ищет handler, у которого строка из `notify` встречается в `name` **или** в `listen`. С обычным `notify: Restart nginx` из раздела «Базовый синтаксис» совпадение находится в `name`; здесь — в `listen`:

```yaml
      notify: Redeploy myapp

  handlers:
    - name: Reload systemd       # name не совпал...
      ansible.builtin.systemd_service: ...
      listen: Redeploy myapp     # ← ...но совпало здесь, в listen
```

Проверка одна и та же: взять строку из `notify`, пройти по handlers, сравнить с `name` и с `listen` каждого. Совпадение есть совпадение, где бы оно ни нашлось. Практическое следствие: в одном notify-списке можно вперемешку указывать имена и темы —

```yaml
      notify:
        - Restart nginx          # имя конкретного handler-а
        - Redeploy myapp         # тема, на которую подписаны двое
```

— и это сработает, потому что механизм поиска один, а не отдельный «режим имён» и «режим тем».

Свойства и нюансы:

**Легко расширять.** Появился новый handler для этого же случая — он просто прописывает себе `listen: Redeploy myapp`. Исходные таски править не нужно.

**Тема — это просто метка.** «Redeploy myapp» — не таска и не handler: в выводе прогона этой строки нет, ничего с таким именем не выполняется. Выполняются только сами handlers, под своими `name`.

**Условие запуска не меняется.** Уведомление по-прежнему срабатывает только при статусе `changed` — базовое правило notify действует и для тем.

**Всё или ничего.** Достаточно одного уведомления от любой таски, чтобы в конце плея выполнились **все** подписанные на тему handlers. Выборочно запустить часть подписчиков нельзя.

**Порядок сохраняется.** Подписанные handlers выполняются в порядке объявления в секции `handlers` (правило 3).

Три случая для примера выше:

| «Deploy application unit file» | «Deploy application config» | Что выполнится в конце плея |
|---|---|---|
| `ok` | `ok` | ничего |
| `changed` | `ok` | «Reload systemd», затем «Restart myapp» |
| `changed` | `changed` | «Reload systemd», затем «Restart myapp» (по одному разу — правило 2) |

**Когда `listen` не подходит:** нужна разная реакция на разные таски — например, изменение юнит-файла требует daemon-reload и рестарта, а изменение конфига — только рестарта. Тема так не умеет («всё или ничего»), это случай обычного `notify` по именам handlers, у каждой таски свой список.

## `meta: flush_handlers` — запустить накопленное сейчас

Иногда ждать конца плея нельзя: следующим таскам нужен сервис, уже работающий на новом конфиге. Для этого есть специальная таска, которая принудительно выполняет все накопленные к этому моменту уведомления:

```yaml
  tasks:
    - name: Deploy nginx config
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: Restart nginx

    - name: Run pending handlers now
      ansible.builtin.meta: flush_handlers

    - name: Wait for nginx to accept connections    # к этому моменту nginx уже перезапущен
      ansible.builtin.wait_for:
        port: 80
        timeout: 30
```

`ansible.builtin.meta` — служебный модуль, он управляет самим выполнением плея, а не состоянием хоста. `flush_handlers` запускает **все** уведомлённые на данный момент handlers; выбрать какой-то один нельзя. Если уведомлений не было, точка flush просто ничего не делает. После flush накопление начинается заново: таски ниже могут снова уведомлять те же handlers, и в конце плея те выполнятся ещё раз.

Ограничение: `flush_handlers` не поддерживает `when` — эта таска выполняется всегда, условие на неё повесить нельзя.

## Подводные камни

### Плей упал — handlers не выполнились

Самая опасная ловушка handlers, потому что ломается она молча.

Сценарий:

1. «Deploy nginx config» отработала со статусом `changed`, уведомила «Restart nginx». Конфиг на хосте уже новый.
2. Следующая таска упала — плей на этом хосте остановился.
3. Handlers выполняются в конце плея, а конец не наступил — **«Restart nginx» не выполнился**. nginx работает на старом конфиге, при этом файл на диске новый.
4. Ошибку починили, запустили плейбук снова. «Deploy nginx config» видит, что файл уже совпадает с шаблоном → статус `ok` → **уведомления нет**. Handler снова не выполнился.

Итог: оба прогона завершились, файл правильный, а сервис так и не перечитал конфиг — и ни один вывод плейбука на это не указывает. Рассинхронизация «файл новый, процесс старый» живёт до первого ручного рестарта.

Лечение — заставить Ansible выполнять уже уведомлённые handlers даже при падении плея. Разово, флагом:

```bash
ansible-playbook site.yml --force-handlers
```

Или постоянно, в `ansible.cfg`:

```ini
[defaults]
force_handlers = True
```

С этой настройкой шаг 2 сценария меняется: плей на хосте падает, но уведомлённые к этому моменту handlers всё равно выполняются, и рассинхронизации не возникает.

### Опечатка в `notify` всплывает не сразу

```yaml
      notify: Restart ngin          # опечатка: handler называется «Restart nginx»
```

Эта ошибка **не** ловится ни при разборе плейбука, ни через `--syntax-check`. Она всплывает только в момент, когда таска реально завершилась со статусом `changed` и попыталась уведомить несуществующий handler — тогда Ansible падает с ошибкой, что handler не найден.

Коварство в сроках обнаружения: на тестовом прогоне, где конфиг уже на месте, таска даёт `ok`, уведомления не происходит — ошибки нет. А на боевом прогоне, где конфиг изменился, плейбук падает посреди плея. Проверить связку `notify` ↔ `name` глазами стоит сразу при написании, не полагаясь на пробный запуск.

### `when` на handler-е — дополнительный фильтр поверх notify

Handler — обычная таска, `when` на нём работает как везде (тема 8). Но условий для запуска становится два, и выполняются они последовательно: сначала какая-то таска с `notify: Restart nginx` должна завершиться со статусом `changed` (без этого handler вообще не рассматривается, до его `when` дело не доходит), затем — в момент выполнения в конце плея — проверяется его `when`:

```yaml
  tasks:
    - name: Deploy nginx config
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: Restart nginx              # условие 1: эта таска дала changed

  handlers:
    - name: Restart nginx
      ansible.builtin.service:
        name: nginx
        state: restarted
      when: allow_restart | default(true)    # условие 2: проверяется в конце плея
```

Если `when` дал `false`, уведомлённый handler пропускается. Чем это опасно, видно на сценарии «днём катим конфиги с запрещёнными рестартами, ночью прогоняем плейбук ещё раз с разрешёнными» — кажется, что так можно, но нет.

**Днём** — прогон с `allow_restart=false`:

1. Таска раскладывает новый конфиг — **файл на хосте уже изменён**. Статус `changed`, notify отправлен.
2. В конце плея Ansible доходит до handler-а, но его `when` даёт `false` — рестарт запрещён переменной.
3. Результат: `skipping` — конфиг новый, а перезапуска не было. Сигнал notify при этом отброшен **насовсем**: Ansible не откладывает его на следующий прогон, а просто забывает.

```
TASK [Deploy nginx config] *****************
changed: [web-01]

RUNNING HANDLER [Restart nginx] ************
skipping: [web-01]
```

**Ночью** — прогон с `allow_restart=true`:

1. Таска сравнивает файл на хосте с шаблоном: одинаковые → `ok`, не `changed`.
2. Нет `changed` — notify не отправляется.
3. В конце плея Ansible к handler-у даже не подходит, его `when` уже неважен. nginx так и работает на старом конфиге — та же рассинхронизация «файл новый, процесс старый», что и в первой ловушке, только созданная сознательно.

Суть: `when` на handler-е превращает уведомление в одноразовый пропуск. Не выполнилось условие в момент прогона — событие утеряно; следующий прогон не вспомнит, что конфиг менялся в прошлый раз. Поэтому `when` здесь годится как стоп-кран «не трогать сервис сейчас», но строить на нём логику «перезапусти потом» нельзя.
