# 7.2 Git – Слияние – Коммит слияния, дальнейшие слияния

## 1. Коммит слияния и его родители

Коммит слияния (merge commit) — это коммит, который создаёт `git merge` при «истинном» слиянии. От обычного коммита он отличается одним: у него два родителя вместо одного.

Родители — это конкретные коммиты, и у каждого своя роль:

- **первый родитель** — вершина ветки, на которой мы стояли, когда запускали `git merge` (та ветка, В КОТОРУЮ сливали);
- **второй родитель** — вершина ветки, которую сливали.

Порядок фиксированный и зависит только от того, где мы стояли в момент слияния. Стояли на master, влили feature — первый родитель из master, второй из feature.

Существует и слияние трёх и более веток одной командой (`git merge branch1 branch2`) — оно называется octopus merge, и родителей у такого коммита будет три и больше. На практике это редкость, дальше везде разбирается обычный случай с двумя.

## 2. Как посмотреть коммит слияния

Возьмём конкретный пример. Есть файл `file.txt` из трёх строк. В master независимо поменяли первую строку, в feature — третью, и вдобавок добавили в feature новый файл `feature.txt`. Слили feature в master — получился merge-коммит. Дальше везде в этом разделе смотрим именно на него.

В графе истории он — точка, где сходятся две линии:

```
$ git log --graph --oneline --all --decorate
*   15c58df (HEAD -> master) Merge branch 'feature'
|\  
| * 5b9be64 (feature) Add feature.txt
| * 87ffdda Change line3 in feature
* | 79bdb5b Change line1 in master
|/  
* c1837bd Initial commit
```

Подробности — через `git show`:

```
$ git show 15c58df
commit 15c58df85de46da6de8ca4a540d4ef250fb8159f
Merge: 79bdb5b 5b9be64
Author: Test User <test@example.com>
Date:   Wed Aug 12 11:45:32 2026 +0000

    Merge branch 'feature'

diff --cc file.txt
index 45c8e9c,b11132f..ba6c03d
--- a/file.txt
+++ b/file.txt
@@@ -1,3 -1,3 +1,3 @@@
 -line1
 +line1-master
  line2
- line3
+ line3-feature
```

Строка `Merge: 79bdb5b 5b9be64` показывает обоих родителей: первый (`79bdb5b` — из master), второй (`5b9be64` — из feature). У обычного коммита этой строки нет.

`diff --cc file.txt` — заголовок diff'а для `file.txt`, но не такой, как у обычного коммита (там было бы `diff --git a/file.txt b/file.txt`). `--cc` значит, что это комбинированный diff: Git сравнил результат сразу с обоими родителями и показывает только те строки, где родители разошлись между собой. Строки `--- a/file.txt` и `+++ b/file.txt` под ним — стандартная часть любого diff'а, не специфика merge-коммитов: `a/` — версия «было», `b/` — версия «стало». Дальше — сами изменения: `line1` и `line3` — старые значения, их заменили; `line1-master` и `line3-feature` — то, что стало после слияния. `line2` никто не менял, поэтому она показана как есть.

Из-за компактности комбинированного diff'а всё, что пришло с одной стороны без пересечений, в нём не показывается. Поэтому `git show` на merge-коммите часто выглядит почти пустым — например, `feature.txt` из графа выше в diff вообще не попал, хотя реально добавился в результате слияния.

Если нужно увидеть полные изменения, есть флаг `-m` — он выводит обычный `diff --git` отдельно относительно каждого родителя. В части относительно первого родителя (master) `feature.txt` виден целиком:

```
$ git show -m 15c58df
diff --git a/feature.txt b/feature.txt
new file mode 100644
--- /dev/null
+++ b/feature.txt
@@ -0,0 +1 @@
+feature only content
```

В части относительно второго родителя (feature) этого файла нет — там он существовал и до слияния, поэтому изменений по нему нет.

## 3. Навигация по родителям: `^` и `~`

Оба символа двигают ссылку на коммит (`HEAD`, ветку, хеш) назад по истории. Если написаны подряд, читаются слева направо — каждый следующий применяется не к `HEAD`, а к тому коммиту, где оказались после предыдущего.

`^N` — разовый прыжок к конкретному родителю: `^1` (или просто `^`) — к первому, `^2` — ко второму. `^2` работает только на merge-коммите, у обычного коммита второго родителя нет.

`~N` — N шагов подряд по первым родителям. Это то, что нужно для движения вглубь по **первому** родителю — писать `^1` перед `~N` не нужно, `~N` от `HEAD` уже и есть весь путь:

```
$ git log -1 --oneline HEAD~1
79bdb5b Change line1 in master
$ git log -1 --oneline HEAD~2
c1837bd Initial commit
```

Для движения вглубь по **второму** родителю так просто не получится — `~N` сам по себе всегда идёт по первым родителям и никогда не заходит во второго. Поэтому сначала разовый прыжок `^2`, чтобы попасть в саму feature, а дальше от этой точки — снова `~N`, потому что дальше это уже обычная линейная история:

```
$ git log -1 --oneline HEAD^2
5b9be64 Add feature.txt
$ git log -1 --oneline HEAD^2~1
87ffdda Change line3 in feature
$ git log -1 --oneline HEAD^2~2
c1837bd Initial commit
```

## 4. Что Git умеет благодаря двум родителям

Второй родитель — не просто справочная информация. По нему Git понимает, что именно уже влито, и это меняет поведение нескольких команд.

**Повторное слияние ничего не делает.** Вершина feature уже достижима из HEAD через второго родителя, значит вливать нечего:

```
$ git merge feature
Already up to date.
```

**Видно, какие ветки уже слиты.** `git branch --merged` показывает ветки, все коммиты которых уже есть в текущей ветке; `--no-merged` — наоборот, ветки с ещё не влитыми коммитами:

```
$ git branch --merged
  feature
* master

$ git branch --no-merged
  experimental
```

Практический смысл: `--merged` — список веток, которые можно безопасно удалять; `--no-merged` — список работы, которая ещё не попала в основную ветку. Без аргумента сравнение идёт с текущей веткой; можно указать другую явно: `git branch --merged master`. Показывает всё, что подходит под условие, — веток может быть сколько угодно, ограничения нет. По умолчанию это только локальные ветки; чтобы учесть и remote-tracking (`origin/...`), нужен флаг `-a` (локальные + remote) или `-r` (только remote).

**Следующее слияние тех же веток проще.** Добавим в feature ещё один коммит:

```
$ git switch feature
$ echo "v2" >> feature.txt && git commit -am "Update feature.txt v2"
```

Перед слиянием Git ищет общего предка master и feature — командой `git merge-base` (base из темы 7.1). Несмотря на новый коммит в feature, это по-прежнему `5b9be64` — та же вершина feature, что была на момент ПРОШЛОГО слияния и стала его вторым родителем:

```
$ git merge-base master feature
5b9be64bc9981a441bff05dae834ec3270ae2086
```

То есть Git уже знает: всё, что было в feature до `5b9be64` включительно, уже влито в master через прошлый merge-коммит. Пересматривать это заново незачем — в дело идёт только то, что после этой точки, то есть один новый коммит. Сливаем:

```
$ git switch master
$ git merge --no-edit feature
$ git log --graph --oneline --all --decorate
```

```
*   bff52d1 (HEAD -> master) Merge branch 'feature'
|\  
| * cb3ee21 (feature) Update feature.txt v2   <- только этот коммит Git обрабатывал заново
* | 15c58df Merge branch 'feature'
|\| 
| * 5b9be64 Add feature.txt                   <- дальше этой точки Git не заходит
| * 87ffdda Change line3 in feature
* | 79bdb5b Change line1 in master
|/  
* c1837bd Initial commit
```

## 5. Сообщение merge-коммита

По умолчанию `git merge feature` открывает редактор с заготовкой `Merge branch 'feature'` — её можно принять или дописать. Три способа управлять этим:

`--no-edit` — принять заготовку без открытия редактора:

```
$ git merge --no-edit feature
$ git log -1
    Merge branch 'feature'
```

Тело сообщения пустое. Быстро, но по такому сообщению не видно, что именно принесла ветка.

`--log` — добавить в тело сообщения список заголовков влитых коммитов (это называется shortlog):

```
$ git merge --no-edit --log feature
$ git log -1
    Merge branch 'feature'
    
    * feature:
      Add feature.txt
      Change line3 in feature
```

Теперь прямо из истории master видно содержимое слияния, не заходя в саму feature.

`-m "текст"` — задать сообщение полностью своё, редактор не открывается:

```
$ git merge -m "Merge feature into master" feature
$ git log -1
    Merge feature into master
```

Не путать с `git show -m` из раздела 2 — это разные флаги: у `merge` он задаёт сообщение, у `show` включает diff по каждому родителю.

## 6. Чистая история основной ветки: `--first-parent`

В рабочем проекте история быстро наполняется мелкими коммитами из влитых feature-веток, и обычный `git log` превращается в шум. Флаг `--first-parent` убирает его: при проходе по merge-коммитам Git идёт только по первым родителям и ни разу не сворачивает во вторых — то есть не заходит в саму feature, держится строго линии master.

Граф этой истории уже был в разделе 4 — там видно, что от master в сторону отходят три коммита feature (`cb3ee21`, `5b9be64`, `87ffdda`) через два ответвления. С `--first-parent` их не будет:

```
$ git log --first-parent --graph --oneline master
* bff52d1 Merge branch 'feature'
* 15c58df Merge branch 'feature'
* 79bdb5b Change line1 in master
* c1837bd Initial commit
```

Прямая линия без единого ответвления — ответвлений в выводе просто нет, показывать нечего. Остались коммиты самого master (`79bdb5b`, `c1837bd`) и точки слияния (`bff52d1`, `15c58df`), по одной на каждое слияние feature в master.

Чтобы это работало, важно направление слияния: переключаться на master и вливать в него feature (`git switch master`, затем `git merge feature`). Тогда первым родителем каждого merge-коммита будет линия master, и `--first-parent` пойдёт ровно по ней. Если сливать наоборот — стоя на feature влить в неё master — первым родителем окажется линия feature, и её коммиты попадут в «чистую» историю master как обычные.
