Во введении разобрали, что ветка — это указатель на коммит, а переключение между ветками меняет содержимое рабочей директории. Команды при этом были только названы, без подробностей: что именно происходит на диске, когда набираешь `git branch` или `git switch`. Здесь — как раз про это: что появляется внутри `.git`, какие у команд есть варианты и где на практике можно споткнуться.

## 1. Создание ветки

После `git branch feature` в директории `.git/refs/heads/` появляется новый файл с именем `feature`. Внутри — ровно одна строка: хеш коммита, который был текущим в момент создания (здесь и далее в примерах он сокращён для читаемости — в реальности все 40 символов), и больше ничего — ни списка изменений, ни истории, ни ссылки на исходную ветку.

```
$ git branch feature
$ cat .git/refs/heads/feature
a1b2c3d4e5f6...
```

Поэтому создание ветки происходит мгновенно и не зависит от размера репозитория — хоть там один файл, хоть миллион. Как уже говорили, сам `git branch` при этом никуда не переключает — HEAD как указывал на прежнюю ветку, так и продолжает.

На `.git/refs/heads/` напрямую полагаться не стоит: со временем, когда веток становится много, Git может упаковать их в файл `.git/packed-refs` ради оптимизации, и часть веток физически окажется уже там. Надёжный способ увидеть список — сама команда `git branch`: текущая ветка в выводе отмечена звёздочкой. Если веток много и по именам не вспомнить, что где, полезнее `git branch -v` — покажет ещё и сокращённый хеш с текстом последнего коммита для каждой.

Ветку необязательно заводить именно от текущего коммита. Второй аргумент `git branch` — стартовая точка: имя другой ветки, тег или хеш конкретного коммита, причём необязательно полный — Git понимает хеш от 4 символов, если этого достаточно, чтобы однозначно его определить. Например, `git branch feature a1b2c3d` создаст `feature`, указывающую на коммит `a1b2c3d`, а не на HEAD. Пригодится, если нужна ветка не от текущего места, а от точки в истории на несколько коммитов назад — без предварительного переключения туда. И если потом на неё переключиться, рабочая директория станет такой, какой была на `a1b2c3d`: `switch` ориентируется на то, куда указывает ветка, а не на историю её создания.

## 2. Переключение между ветками

Файлы веток в `refs/heads/` при переключении не трогаются — меняется другой файл, `.git/HEAD`:

```
$ cat .git/HEAD
ref: refs/heads/master

$ git switch feature
$ cat .git/HEAD
ref: refs/heads/feature
```

Сразу вслед за перезаписью `.git/HEAD` Git приводит рабочую директорию к состоянию последнего коммита `feature` — то самое обновление файлов, которое уже обсуждали. Это единая операция: промежуточного «наполовину переключился» состояния не бывает.

Практический вопрос, который рано или поздно возникает: что будет с незакоммиченными изменениями в рабочей директории? Git не блокирует переключение при любых незакоммиченных правках подряд — если файл, который менялся, одинаков в обеих ветках, изменения просто переедут вместе с переключением. Блокировка сработает, только если переключение реально потребовало бы перезаписать файл, в который что-то внесено, но не сохранено: тогда Git остановится с ошибкой и попросит сначала закоммитить изменения или избавиться от них. Без такой проверки одно неосторожное переключение стирало бы несохранённую работу без предупреждения.

## 3. Создание и переключение одной командой

Связка «создать ветку → сразу в неё перейти» (`git branch feature` + `git switch feature`) настолько частая, что для неё есть отдельный флаг — `git switch -c feature`.

Вся эта механика на уровне файлов — и есть техническая сторона той изоляции, о которой говорилось во введении: ветки не мешают друг другу именно потому, что каждая из этих команд трогает только один файл-указатель и содержимое рабочей директории, не задевая остальные ветки вообще.
