# 2. Подключение Ansible к управляемым хостам: создание inventory (инвентаря)

Документ 1 описывал установку Ansible на управляющий сервер. Сейчас Ansible установлен, но ему ещё не сказано, **с какими нодами работать и как к ним подключаться**.

За это отвечает файл **inventory** (инвентарь) — список всех управляемых нод (серверов), с которыми может работать Ansible. Без него у Ansible нет ни одного адреса для подключения: команды вида `ansible all -m ping` или запуск playbook просто не будут знать, к кому стучаться.

В inventory прописывается:
- **Какие хосты существуют** (IP-адреса, имена хостов или целые диапазоны вида `web-[001:050]`);
- **Как их группировать** (например, в группы `webservers` и `dbservers`, по площадкам, окружениям или ролям);
- **Иерархия групп** (группы могут входить в другие группы, позволяя управлять всем парком или отдельным сегментом одной командой);
- **Параметры подключения** — пользователи (`ansible_user`), нестандартные порты SSH (`ansible_port`), пароли или пути к SSH-ключам;
- **Переменные хостов** — путь к интерпретатору Python и любые специфические настройки, отличающиеся от машины к машине.

Один файл, который описывает всё, на что распространяется автоматизация.

---

## Шаг 1. Настройка окружения через ansible.cfg

### 1.1. Что такое ansible.cfg?

Это главный конфигурационный файл Ansible для всего проекта. Без него Ansible использует встроенные значения по умолчанию — они рабочие, но не оптимальные для продакшена. `ansible.cfg` позволяет один раз прописать настройки для всего парка хостов и больше не таскать их флагами в каждой консольной команде.

### 1.2. Почему с ним лучше

Без `ansible.cfg`:
```bash
# Каждый раз нужно указывать -i, иначе Ansible не знает, где инвентарь
ansible webservers -m ping -i inventory/hosts.yml

# Каждый раз нужно указывать -b для sudo и пользователя
ansible webservers -m apt -a "name=curl state=present" -b -i inventory/hosts.yml
```

С `ansible.cfg`:
```bash
# Ansible сам знает, где инвентарь, под кем идти и что нужен sudo
ansible webservers -m ping
ansible webservers -m apt -a "name=curl state=present"
```

### 1.3. Основные параметры конфигурации

| Параметр | Секция | Что делает | Дефолт |
|---|---|---|---|
| `inventory` | `[defaults]` | Путь к файлу хостов по умолчанию. Избавляет от флага `-i`. | нет |
| `remote_user` | `[defaults]` | Под каким пользователем SSH подключаться к хостам. | текущий юзер |
| `host_key_checking` | `[defaults]` | Проверять SSH host key при первом подключении. Выключаем (`False`), чтобы автоматизация не спотыкалась на новых хостах. | `True` |
| `forks` | `[defaults]` | Сколько хостов обрабатывать параллельно. Для большого парка хостов стоит выставлять 20 и более. | `5` |
| `retry_files_enabled` | `[defaults]` | Создавать ли `.retry` файлы в корне проекта, если плейбук на хосте упал. Выключаем (`False`), чтобы не плодить мусор. | `True` |
| `stdout_callback` | `[defaults]` | Формат вывода логов в консоль. Значение `yaml` превращает нечитаемую JSON-кашу в аккуратное дерево. | `default` |
| `become` | `[privilege_escalation]` | Автоматически повышать права до root (аналог флага `-b`). | `False` |
| `become_method` | `[privilege_escalation]` | Каким способом повышать права на целевой системе. | `sudo` |
| `pipelining` | `[ssh_connection]` | Ускорение SSH. Гонит несколько тасок через один коннект, минимизируя сетевые задержки. | `False` |

### 1.4. Готовый шаблон для копирования в проект

Создайте файл `ansible.cfg` в корневой директории проекта (`~/ansible-project/`) и вставьте в него следующие настройки:

```ini
[defaults]
inventory = ./inventory/hosts.yml
host_key_checking = False
forks = 20
# Наведение порядка в логах и корне проекта
retry_files_enabled = False
stdout_callback = yaml
bin_ansible_callbacks = True

[privilege_escalation]
become = True
become_method = sudo
become_user = root

[ssh_connection]
pipelining = True
```

⚠️ **Важно для Linux:** если директория вашего проекта доступна на запись другим пользователям (например, имеет права `777` или лежит в `/tmp`), Ansible из соображений безопасности проигнорирует локальный `ansible.cfg`. Держите проект в домашней директории с корректными правами.

## Шаг 2. Структура проекта и зарезервированные имена

```bash
mkdir -p ~/ansible-project/{inventory,group_vars,host_vars}
cd ~/ansible-project
```

Для логического разделения конфигураций проект раскладывается по трём ключевым директориям: `inventory/`, `group_vars/` и `host_vars/`.

**`group_vars/` и `host_vars/` — зарезервированные имена.** Ansible ищет их автоматически по структуре каталогов (рядом с инвентарём или в корне проекта):

- `group_vars/<имя_группы>.yml` — переменные для группы хостов;
- `host_vars/<имя_хоста>.yml` — переменные конкретного хоста (перекрывают групповые).

Нюанс: переименовать эти папки нельзя — путь к ним не переопределяется ни настройками, ни флагами. Если назвать их иначе (например, `group-variables`), Ansible их молча проигнорирует.

**`inventory/` — конвенция, а не зарезервированное имя.** Сам по себе Ansible не ищет эту папку (его дефолт — `/etc/ansible/hosts`). Она подхватывается только потому, что путь к ней явно прописан в `ansible.cfg`: `inventory = ./inventory/hosts.yml`. Папку можно назвать как угодно, поправив путь в конфиге, но отходить от стандартного имени `inventory` не принято.

## Шаг 3. Создание Inventory (списка хостов)

У инвентаря два возможных формата — YAML и более старый INI. INI компактнее для простого плоского списка (строка вида `web-01 ansible_host=10.0.1.11`), но при вложенных группах и большом наборе переменных быстро становится нечитаемым. Везде в этом курсе используется YAML — с ним и работаем ниже.

Создайте файл `inventory/hosts.yml` и вставьте туда структуру ниже.

```yaml
# inventory/hosts.yml
all:
  children:
    webservers:           # Имя группы (например, веб-серверы под nginx)
      hosts:
        web-01:           # Удобное имя (алиас) хоста
          ansible_host: 10.0.1.11  # Реальный IP-адрес сервера
        web-02:
          ansible_host: 10.0.1.12
        web-03:
          ansible_host: 10.0.1.13
      vars:
        ansible_user: root         # Под каким пользователем подключаться
        ansible_connection: ssh    # Протокол подключения
```

⚠️ **Важно:** Файл написан в формате YAML. Здесь критически важны отступы (пробелы). Не используйте клавишу Tab, только пробелы! Замените IP-адреса и имена на реальные данные ваших хостов.

**3.1. Разбор ключевых параметров:**

- `webservers` — имя группы хостов. Группировка позволяет применять настройки или плейбуки сразу к десяткам хостов одной командой, а не перечислять их вручную.
- `web-01` / `web-02` — это локальные имена-маски в Ansible. В консоли вы будете видеть именно их, а не безликие IP-адреса.
- Блок `vars` — переменные группы. Всё, что написано здесь (например, пользователь `root`), автоматически применится ко всем хостам этой группы. Это избавляет от дублирования кода.

**3.2. Про `all` и `children`:** это не произвольные слова, а обязательный скелет YAML-инвентаря. `all` — встроенная зарезервированная группа Ansible, которая автоматически включает в себя **все** хосты из инвентаря, сколько бы их ни было. Она существует всегда, даже если не прописана явно. `children:` говорит Ansible: «внутри `all` находятся дочерние группы». Без этого ключевого слова Ansible не поймёт, что `webservers` — это группа, а не хост с таким именем.

Если запустить плейбук на `all` — он обновит вообще всё разом. Но здесь есть важный профессиональный нюанс. Представь, что со временем в инвентарь добавятся хосты другого назначения — тестовые стенды, jump-серверы или сервер мониторинга. Группа `all` зацепит и их тоже. При попытке обновить «все веб-серверы» через `all` можно случайно затронуть и сервер мониторинга.

Поэтому на практике создают явную (кастомную) родительскую группу внутри `all`:

```yaml
all:
  children:
    # Создаём свою родительскую группу для ВСЕХ веб-серверов
    all_webservers:
      children:
        dc1_webservers:
          hosts:
            dc1-web-01:
              ansible_host: 10.0.1.11
        dc2_webservers:
          hosts:
            dc2-web-01:
              ansible_host: 192.168.20.10
```

Что это даёт:

1. Только первый дата-центр: `ansible dc1_webservers -m ping`
2. Только второй дата-центр: `ansible dc2_webservers -m ping`
3. Все веб-серверы вместе (но без лишних серверов): `ansible all_webservers -m ping`

Ещё один нюанс группировки: хост может входить сразу в несколько групп одновременно — например, и в `webservers`, и в отдельную группу `production`. Ansible объединяет переменные из всех групп, в которые входит хост. Если одна и та же переменная задана в двух группах по-разному, Ansible разрешает конфликт по своим правилам приоритета (глубина вложенности, затем алфавитный порядок имён групп) — но держать этот порядок в голове на практике не стоит. Конфликт значений между группами обычно сигнализирует, что структуру стоит пересмотреть; частный случай лучше явно вынести в `host_vars` нужного хоста, а не полагаться на то, как Ansible разрешит спор между группами.

**3.3. Как проверить, что файл составлен без ошибок?**

Выполните команду проверки синтаксиса:

```bash
ansible-inventory -i inventory/hosts.yml --list -y
```

Флаг `-i` здесь и во всех командах ниже указан явно — для наглядности и на случай, если `ansible.cfg` из Шага 1 ещё не создан.

Ожидаемый результат: если Ansible выведет в терминал аккуратное дерево с вашими хостами — файл составлен верно.

**3.4. Дополнительные параметры подключения**

Кроме пользователя и типа подключения, у хоста можно задать нестандартный SSH-порт и ключ вместо пароля:

```yaml
web-04:
  ansible_host: 10.0.1.14
  ansible_port: 2222                           # нестандартный SSH-порт (по умолчанию 22)
  ansible_ssh_private_key_file: ~/.ssh/id_web   # подключение по ключу вместо пароля
```

Оба параметра действуют только на этот хост — остальные подключаются как раньше. Если задан ключ, пароль для этого хоста уже не нужен.

Если хостов с одинаковыми настройками много, их можно не перечислять по одному, а задать диапазоном:

```yaml
hosts:
  web-[01:03]:
    ansible_host: 10.0.1.[11:13]
```

Это разворачивается в те же три хоста из примера выше — `web-01`, `web-02`, `web-03` с адресами `10.0.1.11`–`10.0.1.13` — просто более компактной записью. Удобно для десятков однотипных хостов; если у каждого что-то своё, как в примере с `ansible_port` выше, проще явный список.

На этом этапе пароль root для подключения ещё нигде не указан, поэтому реальный `ping` с ответом `pong` пока не выполнить — это будет следующим шагом.

## Шаг 4. Управление паролями

В Ansible пароли не принято мешать со списком IP-адресов. Для этого используются специальные папки: `group_vars` (для настроек всей группы) и `host_vars` (для точечных исключений).

**4.1. Задаём общий пароль для всех хостов группы**

В `group_vars` можно хранить любые переменные, которые нужны для группы хостов — не только пароль. Например, нестандартный SSH-порт, путь к интерпретатору Python, версия ПО, которую нужно установить, или любые кастомные параметры, которые используются в плейбуках. Всё, что прописано в этом файле, автоматически становится доступным для каждого хоста из группы.

В нашем случае пока кладём туда пароль. Создайте файл конфигурации для группы. Имя файла должно строго совпадать с именем группы из инвентаря:

```yaml
# group_vars/webservers.yml
ansible_password: "общий_пароль_root"
```

**4.2. Если у конкретного хоста пароль отличается (исключение)**

Если на каком-то хосте пароль сменили, не нужно портить общий групповой файл — создайте в `host_vars/` файл с именем этого хоста:

```yaml
# host_vars/web-02.yml
ansible_password: "другой_пароль_именно_для_этого_хоста"
```

**Приоритет:** переменные из `host_vars` (конкретный хост) всегда приоритетнее, чем из `group_vars` (группа). Для `web-02` Ansible возьмёт уникальный пароль, а для остальных хостов группы продолжит использовать общий.

## Шаг 5. Первая проверка связи (генеральный тест)

Теперь проверим, как Ansible видит хосты и правильно ли подхватились пароли. Выполняем команду:

```bash
ansible webservers -m ping -i inventory/hosts.yml
```

**Что происходит:** Ansible не просто «пингует» сеть. Он реально заходит на каждый хост по SSH под пользователем `root`, подставляет нужный пароль, закидывает туда микро-скрипт на Python, выполняет его и возвращает отчёт.

Ожидаемый результат (успех):

```
web-01 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}
```

Если вы увидели `"ping": "pong"` зелёным цветом — ваш управляющий сервер полностью готов к работе, связь с хостами установлена.

**Про `[WARNING]` в выводе:**

Помимо `SUCCESS` вы можете увидеть в терминале жёлтое предупреждение вида:

```
[WARNING]: Platform linux on host web-01 is using the discovered Python interpreter at /usr/bin/python3.10, but future installation of another Python interpreter could change the meaning of that path.
```

Это **не ошибка**, можно игнорировать. Ansible сообщает, что сам автоматически нашёл интерпретатор Python на хосте (например, `/usr/bin/python3.10`), и предупреждает: если в будущем на хосте появится ещё один Python (например, после обновления системы или установки нового ПО), путь может стать неоднозначным.

Чтобы убрать это предупреждение и не зависеть от автоопределения, можно явно закрепить путь к интерпретатору в `inventory/hosts.yml`, в блоке `vars` для группы:

```yaml
vars:
  ansible_user: root
  ansible_connection: ssh
  ansible_python_interpreter: /usr/bin/python3.10
```

Делать это прямо сейчас не обязательно — Ansible продолжит нормально работать и с автоопределением. Но если warning будет мешать читать логи, достаточно один раз прописать этот путь, и он исчезнет.

## 🛠️ Траблшутинг первого запуска

Ошибки проявляются при первом реальном запуске — пинге из Шага 5, — но их причины могут сидеть в любом из предыдущих шагов: от настройки `ansible.cfg` до файлов паролей и структуры инвентаря. Если вы видите красные ошибки или предупреждения, найдите свою строку ниже и выполните решение:

**1. Ошибка: `Permission denied (publickey,password)`**

Симптом: автоматика падает, но если заходить на этот же хост вручную через обычный `ssh root@IP`, то пароль подходит и пускает без проблем.

- Причина: Ansible вообще «не увидел» ваш пароль. Скорее всего, имя файла в папке `group_vars/` написано с ошибкой или опечаткой, и настройки не привязались к группе.
- Как исправить: проверьте имя файла буква в букву. Если в инвентаре группа называется `webservers`, то файл обязан называться `group_vars/webservers.yml`.
- Как точно проверить за секунду: выполните команду диагностики:

```bash
ansible-inventory -i inventory/hosts.yml --host web-01
```

(вместо `web-01` подставьте имя проблемного хоста). Если в выведенном списке нет строки `ansible_password` — значит, файл с паролем не подхватился.

**2. Ошибка: `Permission denied (password)`**

- Причина: пароль подхватился, но он физически не подходит к хосту.
- Как исправить:
  - Если упали все хосты — опечатка в общем файле `group_vars/webservers.yml`.
  - Если упал один конкретный хост — проверьте его личный файл в `host_vars/`.

**3. Ошибка: `UNREACHABLE` / `No route to host` (или `Connection timed out`)**

- Причина: сетевая недоступность.
- Как исправить: проверьте, правильный ли IP-адрес указан в файле `inventory/hosts.yml`. Попробуйте «дотянуться» до хоста обычной командой `ping 10.0.1.x` прямо с сервера.

**4. Ошибка: `Host key verification failed`**

- Причина: защита безопасности SSH. Сервер видит этот хост впервые в жизни и боится к нему подключаться без вашего личного разрешения.
- Как исправить: чтобы Ansible не спотыкался и не требовал вручную прожимать «Are you sure you want to continue connecting (yes/no)?» для каждого нового хоста, отключите эту проверку.

Проверьте, что в `ansible.cfg` из Шага 1 присутствует строка:

```ini
[defaults]
host_key_checking = False
```

Если файла ещё нет — создайте его с этим содержимым. Когда настройка на месте, Ansible игнорирует предупреждения о новых ключах и сразу переходит к делу. Обратите внимание: Ansible читает `ansible.cfg` из текущей директории, поэтому команды нужно запускать из корня проекта.

**5. Предупреждение: `Skipping key (...) in group (vars) as it is not a mapping` — фантомная группа `vars`**

Симптом: при каждом запуске Ansible выводит предупреждение:

```
[WARNING]: Skipping key (ansible_user) in group (vars) as it is not a mapping, it is a <class 'ansible.parsing.yaml.objects.AnsibleUnicode'>
```

Причина: ключ `vars:` ошибочно помещён на уровень объявления групп (внутри `children:`). Ansible воспринимает `vars` не как секцию переменных, а как имя фантомной группы хостов, а её содержимое — как хосты. В итоге переменные молча не применяются.

Как исправить: поднять `vars` на уровень группы, к которой переменные относятся:

```yaml
# ❌ ОШИБКА: vars на уровне дочерних групп
all:
  children:
    webservers:
    vars:                       # Ansible считает, что "vars" — это группа
      ansible_user: root

# ✅ ИСПРАВЛЕНИЕ: vars на одном уровне с children (переменные для all)
all:
  vars:
    ansible_user: root
  children:
    webservers:
```

Диагностика: быстро отловить фантомную группу `@vars` и проверить, подтянулись ли переменные к хостам:

```bash
ansible-inventory -i inventory/hosts.yml --graph   # покажет фантомную группу @vars в дереве
ansible-inventory -i inventory/hosts.yml --list    # итоговый разбор с переменными
```

## 🌐 Сноска «На будущее»: динамический инвентарь (Dynamic Inventory)

Весь этот документ учит **статическому** инвентарю: список хостов и адресов вы ведёте вручную, в YAML-файле. Для стабильного, редко меняющегося парка серверов этого достаточно, и это самый простой способ начать.

Но в динамических инфраструктурах (AWS, GCP, OpenStack, Yandex Cloud, Kubernetes, VMware) IP-адреса и количество экземпляров постоянно меняются — сервер может пересоздаться с новым адресом, автоскейлинг добавит или уберёт ноды прямо во время работы. Ручное ведение статического YAML-инвентаря для такой инфраструктуры не применяется: вы физически не успеете редактировать файл вслед за изменениями облака.

Для этого случая используются **Inventory Plugins** (актуальный способ — Ansible сам опрашивает облако или кластер и на лету строит список хостов по заданным правилам) или **legacy dynamic inventory scripts** (устаревший способ: скрипт вместо статического файла, тоже строит список на лету, но без плагинной инфраструктуры). Тема разбирается отдельно, в одной из тем продвинутого блока курса — там, где инвентарь рассматривается на более глубоком уровне.

## 🔐 Сноска «На будущее»: безопасность и шифрование (Ansible Vault)

Сейчас пароли хранятся в файлах открытым текстом. Для изолированного сервера автоматизации внутри закрытого контура компании — это допустимый компромисс ради простоты.

Однако, если этот проект в будущем поедет в Git или к нему получат доступ сторонние люди, пароли необходимо зашифровать утилитой `ansible-vault`:

**Зашифровать файл:**

```bash
ansible-vault encrypt group_vars/webservers.yml
```

Утилита попросит придумать секретный мастер-пароль. Файл станет нечитаемым на диске.

**Запуск команд с зашифрованными паролями:** к любой команде запуска нужно будет просто добавлять флаг расшифровки:

```bash
ansible webservers -m ping -i inventory/hosts.yml --ask-vault-pass
```

**Редактировать зашифрованный файл:**

```bash
ansible-vault edit group_vars/webservers.yml
```

**Посмотреть содержимое без редактирования:**

```bash
ansible-vault view group_vars/webservers.yml
```
