# 8. Условия (`when`) — логика ветвления в тасках

## Зачем нужен `when`

Плейбук выполняется линейно: таск за таском, сверху вниз. Но реальная инфраструктура неоднородна: где-то другая версия дистрибутива, где-то переменная не задана, где-то предыдущий шаг завершился ошибкой. `when` позволяет решать на уровне отдельного таска — выполнять его на этом хосте или пропустить.

Почему ветвление делается именно на уровне таска, а не внутри самого shell-скрипта? Разница видна на примере. Без `when` пришлось бы прятать логику внутрь команды:

```yaml
- name: Установить nginx, если Debian
  ansible.builtin.command: |
    if grep -q Debian /etc/os-release; then apt install -y nginx; fi
```

Так можно, но Ansible в этом случае видит только «команда выполнилась» — сработал ли внутренний `if`, установился ли nginx на самом деле, ему неизвестно. `when` устроен наоборот: решение — выполнять таск или нет — принимается на уровне самого таска, а не спрятано в shell-скрипте внутри команды:

```yaml
- name: Установить nginx
  ansible.builtin.apt:
    name: nginx
    state: present
  when: ansible_facts['os_family'] == "Debian"
```

Три причины, почему второй вариант правильный:

- **Идемпотентность и отчётность.** Ansible показывает статус каждого таска: `ok`, `changed`, `skipped`. В первом варианте Ansible видит только «команда выполнилась» — сработал ли `if` внутри, понять по выводу плейбука невозможно.
- **Читаемость.** Условие в `when` видно сразу в YAML, не нужно вчитываться в shell-скрипт, чтобы понять логику.
- **Модули вместо shell-скриптов.** Второй пример использует модуль `apt`, а не `command` — большинство тасков в плейбуках так и устроены (`apt`, `template`, `service`). Внутри модуля спрятать shell-логику невозможно в принципе, `when` — единственный способ ветвления.

`when` — это выражение, которое Ansible вычисляет **перед** выполнением таска на каждом хосте. Результат приводится к булеву значению — логическому типу, у которого всего два варианта: `true` (истина) и `false` (ложь). Дальше решение: `true` — таск выполняется, `false` — таск получает статус `skipped` и пропускается на этом хосте, а плейбук продолжает работу дальше.

В большинстве условий о «приведении» думать не нужно: сравнения (`env == "production"`) и тесты (`my_var is defined`) по своей природе возвращают ровно `true` или `false` — результат уже булев. Приведение включается в особом случае — когда в `when` стоит голое значение:

```yaml
when: my_var
```

Здесь после вычисления получается не true/false, а содержимое переменной, и Ansible доводит его до булева по правилам Jinja2 — движка, которым вычисляются все выражения в `when`:

- **истина**: непустая строка, ненулевое число, непустой список или словарь;
- **ложь**: пустая строка `""`, ноль `0`, пустой список `[]`, пустой словарь `{}`, `null`.

Обрати внимание: значению не нужно быть буквальным `true`, чтобы условие сработало — при `my_var: "hello"` таск выполнится, потому что строка непустая. Проверяется «наполненность» значения, а не его равенство `true`. Есть и третье состояние: если переменной **вообще нет**, она не ложна — таск падает с ошибкой `is undefined` (защита от опечаток в именах). Проверка, существует ли переменная — это тест `is defined`, он разобран ниже. Ловушка со строкой `"false"` (она непустая и потому истинна) — в конце документа.

## Синтаксис и главная особенность

`when` пишется на уровне таска, рядом с модулем:

```yaml
- name: Установить nginx
  ansible.builtin.apt:
    name: nginx
    state: present
  when: env == "production"
```

**Главная особенность:** `when` принимает «сырое» Jinja2-выражение — **без** `{{ }}`.

```yaml
# ПРАВИЛЬНО
when: my_var == "production"

# НЕПРАВИЛЬНО — вызовет предупреждение или ошибку
when: "{{ my_var == 'production' }}"
```

Почему так? Всё содержимое `when` и так интерпретируется как Jinja2-выражение — Ansible неявно оборачивает его целиком. Если добавить `{{ }}`, получается шаблон внутри шаблона: Ansible сначала отрендерит внутреннее выражение в строку, а потом попытается вычислить строку как условие. Это источник трудноуловимых багов, поэтому Ansible выдаёт предупреждение `conditional statements should not include jinja2 templating delimiters`.

Это главное отличие от остальных мест в плейбуке: в параметрах модулей `{{ }}` обязательны, в `when` — запрещены. То же правило действует для `failed_when`, `changed_when`, `until` — во всех них тоже пишется голое Jinja2-выражение, без `{{ }}`.

## Условия на факты

Классическое применение — привязка к операционной системе. Полезные ключи фактов:

- `ansible_facts['os_family']` — семейство: `Debian` (сюда входят и Debian, и Ubuntu), `RedHat`, и т.д.;
- `ansible_facts['distribution']` — конкретный дистрибутив: `Ubuntu`, `Debian`;
- `ansible_facts['distribution_version']` — версия: `22.04`, `24.04`, `12`.

```yaml
- name: Установить nginx (только на Debian-семействе)
  ansible.builtin.apt:
    name: nginx
    state: present
  when: ansible_facts['os_family'] == "Debian"
```

На хостах с другим семейством ОС таск будет `skipped` — плейбук не упадёт с ошибкой «apt не найден».

Более практичный сценарий — разное поведение для разных версий Ubuntu, например при миграции парка машин:

```yaml
- name: Конфиг sshd для Ubuntu 24.04 и новее
  ansible.builtin.template:
    src: sshd_config_new.j2
    dest: /etc/ssh/sshd_config
    validate: /usr/sbin/sshd -t -f %s
  when: ansible_facts['distribution_version'] is version('24.04', '>=')

- name: Конфиг sshd для старых версий
  ansible.builtin.template:
    src: sshd_config_legacy.j2
    dest: /etc/ssh/sshd_config
    validate: /usr/sbin/sshd -t -f %s
  when: ansible_facts['distribution_version'] is version('24.04', '<')
```

Важно: версии сравниваются через тест `is version(...)`, а **не** через `>=` напрямую. Причина: `distribution_version` — это строка, и строковое сравнение `"9.04" > "24.04"` даст `true` (посимвольно `9` больше `2`). Тест `is version` разбирает версию на компоненты и сравнивает их как числа.

## Тесты Jinja2

**Тесты** — конструкция Jinja2: они возвращают `true`/`false` и применяются через ключевое слово `is`. Именно тесты — основной инструмент внутри `when`.

Тесты, покрывающие ~95% реальной работы:

### `is defined` / `is not defined`

Самый частый тест — проверка, что переменная вообще существует или не существует:

```yaml
- name: Развернуть кастомный motd
  ansible.builtin.template:
    src: motd.j2
    dest: /etc/motd
  when: custom_motd_text is defined
```

Если переменной нет — таск просто пропускается, вместо падения с ошибкой `'custom_motd_text' is undefined`.

### `is none`

Между «переменной нет» и «переменная заполнена» есть промежуточное состояние: ключ существует, но значение — null («ничего»). В YAML оно возникает двумя способами:

```yaml
nginx_conf_override:        # ключ есть, после двоеточия пусто — это null
nginx_conf_override: null   # то же самое, записанное явно
```

Типовой источник — заготовка в инвентаре или group_vars: ключ вписали заранее, значение заполнят потом. Важно: это **не** пустая строка `""` — null означает «значения нет вовсе».

Коварство в том, что `is defined` такую переменную **пропускает**: он проверяет только существование ключа, а ключ есть. Но операции над значением ломаются — всё, что ожидает строку или число, падает: `nginx_conf_override.split('.')` → ошибка `'NoneType' has no attribute`, `is version(...)` → ошибка разбора. Проверка на существование пройдена, а выражение всё равно взорвалось.

Защита — двойная проверка: «ключ существует И в нём реально что-то лежит»:

```yaml
when: nginx_conf_override is defined and nginx_conf_override is not none
```

### `is version(...)`

Сравнение версий. Тест ставится после переменной, которую сравниваем: `is version(value, operator)`, где `value` — эталон для сравнения, а `operator` — оператор. Операторов шесть: `'=='`, `'!='`, `'<'`, `'<='`, `'>'`, `'>='`.

Тест работает с **любой** переменной, содержащей строку версии — из `set_fact`, `register`, inventory:

```yaml
when: app_version is version('2.4.0', '>=')
```

Первый аргумент (`value`) — обычный аргумент теста, туда можно передать и переменную:

```yaml
when: nginx_version is version(min_nginx_version, '>=')
```

Типовая ошибка: `version('min_nginx_version', '>=')` — имя переменной в кавычках. Кавычки превращают имя в обычный текст: Jinja2 не пойдёт искать переменную, а возьмёт сами буквы `min_nginx_version` как строку — и сравнивать версию будет с этим текстом, а не со значением переменной. Внутри `when` уже действует контекст Jinja2 — имена переменных пишутся без кавычек и без `{{ }}`.

## Комбинирование условий

### Операторы сравнения

Кирпичик, из которого строится одиночное условие — сравнение двух значений. Операторов шесть, они стандартные:

| Оператор | Значение |
|---|---|
| `==` | равно |
| `!=` | не равно |
| `>` / `<` | больше / меньше |
| `>=` / `<=` | больше или равно / меньше или равно |

```yaml
when: env == "production"        # строки — в кавычках
when: nginx_conf_check.rc != 0   # числа — без кавычек
when: ansible_facts['processor_vcpus'] >= 2
```

Форма `not env == "production"` эквивалентна `env != "production"`, но принято писать `!=`. Родственная идиома: булевы переменные не сравнивают с `true`/`false` — вместо `enable_nginx == true` и `enable_nginx == false` пишут просто `enable_nginx` и `not enable_nginx`.

### `and`, `or`, `not`, скобки

Внутри `when` работает обычная логика Jinja2:

```yaml
when: ansible_facts['os_family'] == "Debian" and enable_nginx | bool
```

(`| bool` в примерах приводит переменную-флаг к булеву значению. Фильтр действует только на ближайшее значение слева от `|` — здесь на `enable_nginx`, а не на всё условие целиком. Почему это важно именно для нескольких флагов сразу — разобрано в ловушках в конце документа.)

```yaml
when: (env == "staging" or env == "dev") and not skip_deploy | bool
```

Скобки обязательны, когда смешиваются `and` и `or` — иначе легко получить не ту группировку, которую имел в виду.

Отдельно про `not` — три момента:

**Приоритет с фильтром.** Фильтр связывает крепче, чем `not`, поэтому `not skip_deploy | bool` читается как `not (skip_deploy | bool)`: сначала флаг приводится к булеву, потом результат инвертируется. Для флагов это ровно нужный порядок — инвертируется уже приведённое значение, а не сырая строка.

**Идиоматические формы отрицания.** У тестов и у оператора `in` отрицание встроено прямо в синтаксис, и принято использовать именно его:

```yaml
when: my_var is not defined               # а не: not (my_var is defined)
when: "'webservers' not in group_names"   # а не: not ('webservers' in group_names)
```

Обе записи в каждой паре работают одинаково, но встроенные формы читаются как обычное предложение — это стандарт в плейбуках. Внешний `not` остаётся для случаев, где встроенной формы нет: `not skip_deploy | bool`, `not (enable_nginx and enable_ssl)` — здесь `not` инвертирует результат всего выражения в скобках целиком.

**`not` на голом значении.** Как разобрано в начале документа:

- `when: my_var` выполняет таск, когда значение непустое;
- `when: not my_var` — сначала `my_var` сама по себе приводится к булеву: `""`, `0`, `[]`, `null` дают `false`. Дальше `not false` = `true` — поэтому именно при пустом значении таск и выполняется;
- если переменной вообще нет, `not` не поможет — упадёт с той же ошибкой `is undefined`.

### Список условий = `and`

YAML-список внутри `when` эквивалентен объединению через `and`:

```yaml
- name: Развернуть конфиг nginx
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
  when:
    - ansible_facts['os_family'] == "Debian"
    - nginx_config_version is defined
    - enable_nginx | bool
```

Это читается лучше, чем длинная строка с `and`, поэтому для трёх и более условий предпочтителен список. Для `or` такой формы нет — только явный оператор в выражении.

Важный концептуальный момент: **условия в списке независимы друг от друга**. Каждое вычисляется с нуля, из исходных переменных, ничего не зная о соседних строках. Никакого «результата первого условия», который передаётся во второе, не существует. Интуиция из обычного программирования — «сначала вычислили и запомнили, потом использовали» — здесь не работает.

Пример: задача — выполнить таск, только если версия относится к ветке `2.x` и при этом не ниже `2.4.0`:

```yaml
  when:
    - app_version.split('.') | first == '2'      # режет строку и сравнивает
    - app_version is version('2.4.0', '>=')      # берёт ту же исходную строку заново
```

Эта задача решается **сочетанием** двух независимых проверок, а не передачей результата от одной к другой: если первое условие ложно, до второго дело не дойдёт (short-circuit, подробнее в ловушках).

Если промежуточный результат нужен в нескольких задачах, его можно явно сохранить через `set_fact` (`app_branch: "{{ app_version.split('.') | first }}"`) и дальше писать `app_branch == '2'`. Выбор между инлайн-выражением и переменной — вопрос читаемости: при одном-двух использованиях выражение терпимо на месте, при многих — пора в переменную.

### Оператор `in` — проверка вхождения

Проверяет, есть ли значение в списке. Две частые формы.

Вхождение хоста в группу inventory (через магическую переменную `group_names` — список групп текущего хоста):

```yaml
- name: Таск только для веб-серверов
  ansible.builtin.service:
    name: nginx
    state: started
  when: "'webservers' in group_names"
```

Обрати внимание на кавычки: строковый литерал `'webservers'` стоит в начале выражения, и без внешних кавычек YAML-парсер сломается на одиночной кавычке. Поэтому всё выражение обёрнуто в двойные кавычки — это требование YAML, а не Jinja2.

Вторая форма — проверка вхождения значения переменной в список констант, компактная замена цепочки `or`:

```yaml
# Вместо: distribution == "Ubuntu" or distribution == "Debian"
when: ansible_facts['distribution'] in ['Ubuntu', 'Debian']
```

### Ветвление значения: `ternary` и inline-if

`when` решает, выполнять ли таск. Но иногда ветвиться должен не таск, а **значение** внутри выражения. Для этого есть две конструкции.

Первая — фильтр `ternary`:

```yaml
- name: Установить пакет с учётом окружения
  ansible.builtin.apt:
    name: nginx
    state: "{{ (env == 'production') | ternary('present', 'latest') }}"
```

Читается как тернарный оператор: условие истинно → первое значение, ложно → второе. Заметь: здесь `{{ }}` нужны — это параметр модуля, а не `when`.

Вторая — нативный inline-if самого Jinja2, форма `значение if условие else значение`:

```yaml
    state: "{{ 'present' if env == 'production' else 'latest' }}"
```

Обе записи эквивалентны, выбор — дело вкуса. Преимущество inline-if проявляется, когда веток больше двух — их можно выстроить цепочкой:

```yaml
    nginx_workers: "{{ 8 if tier == 'high' else 4 if tier == 'medium' else 2 }}"
```

Главное — понять, к чему цепляется `else`: он держит не следующее значение, а **весь остаток цепочки**. Со скобками (их можно и написать — работает так же) структура видна:

```yaml
    nginx_workers: "{{ 8 if tier == 'high' else (4 if tier == 'medium' else 2) }}"
```

Поэтому читается цепочка шагами, слева направо:

1. `tier == 'high'`? Да → результат `8`, дальше не смотрим. Нет → идём дальше;
2. `tier == 'medium'`? Да → результат `4`, стоп. Нет → идём дальше;
3. условий больше нет → остаётся `2`.

Финальный `else` обязателен: без него при всех ложных условиях выражение упадёт.

Ловушка цепочек: в ветку легко вписать не ту переменную — чаще всего при копировании соседней ветки. Цепочка остаётся синтаксически корректной и молча выдаёт неправильный результат:

```yaml
    backup_target: "{{ primary_host if primary_host is defined else secondary_host if primary_host is defined else 'localhost' }}"
    #                                                                                ↑ должно быть secondary_host
```

Глазами по такому коду проскакиваешь. Ловится проговариванием всей цепочки вслух, шаг за шагом, по приёму самопроверки из конца документа: «взять primary_host, если primary_host существует; иначе взять secondary_host, если... primary_host существует?!» — на третьем шаге фраза перестаёт складываться, несостыковка слышна сразу. Условие второй ветки обязано говорить о том значении, которое ветка возвращает.

## `when` + `register` — реакция на результат предыдущего таска

Связка `register` и `when` — основа сценариев вида «сделай Б, только если А получилось / не получилось / что-то вернуло».

```yaml
- name: Проверить, существует ли конфиг nginx
  ansible.builtin.command: test -f /etc/nginx/nginx.conf
  register: nginx_conf_check
  failed_when: false    # не роняем плейбук, если файла нет — нам нужен только код возврата

- name: Развернуть конфиг, если его нет
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
  when: nginx_conf_check.rc != 0
```

(Строка `failed_when: false` здесь используется утилитарно — «никогда не считать таск проваленным».)

Какие поля окажутся в зарегистрированной переменной — зависит от модуля таска. В примере выше первый таск — `ansible.builtin.command`, поэтому в `nginx_conf_check` есть поля запуска команды, и два из них постоянно используются в условиях:

- `.rc` — код возврата. Именно он проверяется в примере: `nginx_conf_check.rc != 0`;
- `.stdout` — текстовый вывод команды. Например, если зарегистрировать вывод `systemctl is-active nginx` в переменную `service_status`, дальше можно проверить: `when: "'active' in service_status.stdout"`.

У других модулей набор полей другой: у `template` не будет ни `rc`, ни `stdout`. Посмотреть, что реально вернул таск, проще всего через `ansible.builtin.debug`, выведя всю зарегистрированную переменную целиком:

```yaml
- name: Показать содержимое зарегистрированной переменной
  ansible.builtin.debug:
    var: nginx_conf_check
```

Есть и второй способ — не лезть в конкретные поля, а проверить итог таска целиком через статусные тесты. Они работают с результатом любого модуля и читаются обычно лучше:

```yaml
- name: Перезапустить nginx, если конфиг обновился
  ansible.builtin.service:
    name: nginx
    state: restarted
  when: nginx_template_result is changed
```

Четыре статусных теста:

- `is succeeded` — таск выполнился без ошибки;
- `is failed` — таск провалился. Работает только в паре с `ignore_errors: true` на первом таске: по умолчанию провал останавливает выполнение на хосте, и до проверки дело не дойдёт; `ignore_errors` записывает провал, но позволяет плейбуку идти дальше. (А вот после `failed_when: false` этот тест всегда ложен — такой таск не считается проваленным вовсе, его результат проверяют по полям вроде `rc`, как в примере выше);
- `is changed` — таск что-то изменил;
- `is skipped` — таск был пропущен (его собственный `when` оказался ложным).

Важный нюанс с `is skipped`: если первый таск был пропущен, его зарегистрированная переменная всё равно существует, но внутри неё нет `rc`, `stdout` и прочих полей результата — только служебные. Поэтому обращение к `nginx_conf_check.rc` после пропущенного таска упадёт с ошибкой. Защита:

```yaml
when: nginx_conf_check is not skipped and nginx_conf_check.rc != 0
```

## Частые ловушки

### Ловушка 1: строка `"false"` истинна

Переменные из inventory-файлов в INI-формате, из `--extra-vars` в форме `key=value` и из окружения приходят **строками**. Строка `"false"` — непустая, а значит в логике Jinja2 она истинна:

```yaml
# inventory: enable_debug=false
when: enable_debug          # ← ВСЕГДА true: непустая строка "false"
when: enable_debug | bool   # ← правильно: строка приводится к булеву значению
```

Правило: любая переменная, которая по смыслу флаг (да/нет), в условиях всегда пропускается через `| bool`. Это дёшево и защищает от источника переменной: придёт она строкой или настоящим булевым — результат одинаковый.

### Ловушка 2: `| bool` нужен у каждого флага, а не у всего условия

Если флагов несколько, `| bool` нельзя повесить один раз на всё выражение в скобках:

```yaml
# НЕПРАВИЛЬНО
when: (enable_nginx and enable_ssl) | bool
```

Проблема в том, как `and` работает со строками. Он не вчитывается в смысл слов — для него действует одно правило: «если слева не пустота — отдаю то, что написано справа». Пусть обе переменные приходят строками, как обычно из инвентаря. Два сценария.

**Сценарий 1: `enable_nginx: "true"`, `enable_ssl: "false"`.**

1. Считается то, что в скобках: `"true" and "false"`.
2. `and` смотрит на первое значение — `"true"`. Пустая строка? Нет, там 4 буквы. Раз не пустая — `and` отдаёт второе значение как есть.
3. Из скобок выходит текст `"false"`.
4. Внешний `| bool` берёт это слово и честно превращает в `False`.

Итог — `False`. Результат случайно правильный, но по неверной причине: `enable_nginx` вообще не проверялся по смыслу.

**Сценарий 2: `enable_nginx: "false"`, `enable_ssl: "true"`.**

1. Считается то, что в скобках: `"false" and "true"`.
2. `and` смотрит на первое значение — `"false"`. Пустая строка? Нет, там 5 букв — `and` не понимает, что это слово означает ложь, ему видно только «пусто / не пусто». Раз не пустая — снова отдаёт второе значение.
3. Из скобок выходит текст `"true"`.
4. Внешний `| bool` превращает его в `True`.

Итог — `True`, хотя `enable_nginx` был `"false"`. Переменная `enable_nginx` ни на что не повлияла: `and` использовал её только затем, чтобы решить «пустая или нет», а в результат так и не попала.

Правило: пока в первой переменной есть хоть какие-то символы, `and` просто отдаёт вторую переменную целиком, а внешний `| bool` оценивает только её. Поэтому `| bool` нужно ставить на **каждую** переменную до того, как они встретятся с `and` — тогда `and` сравнивает уже настоящие `True`/`False`, а не длину текста.

Правильно — `| bool` у **каждого** флага, до того, как в дело вступит `and`:

```yaml
when: enable_nginx | bool and enable_ssl | bool
```

Здесь оба флага уже приведены к `True`/`False` к моменту, когда `and` начинает работать, поэтому `and` сравнивает готовые булевы значения и честно даёт `False and True` → `False`. Правило: `| bool` ставится у каждой строковой переменной до того, как она попадёт в `and`/`or`, а не оборачивает результат снаружи.

### Ловушка 3: undefined-переменная внутри сложного выражения

Если переменная не определена, то `when: my_var == "x"` падает с ошибкой. Jinja2 вычисляет `and` слева направо и останавливается на первом ложном операнде (short-circuit), поэтому проверка существования **должна идти первой**:

```yaml
# ПРАВИЛЬНО: если my_var не определена, до сравнения дело не дойдёт
when: my_var is defined and my_var == "x"

# НЕПРАВИЛЬНО: сравнение вычисляется первым и падает
when: my_var == "x" and my_var is defined
```

Тот же принцип для вложенных структур: сначала проверяем, что внешний уровень существует, потом лезем внутрь. Частый жизненный случай — результат модуля `stat`, зарегистрированный на таске, который мог быть пропущен:

```yaml
when: conf_stat.stat is defined and conf_stat.stat.exists
```

Перестановка операндов местами уронит выражение на хостах, где `stat`-таск был пропущен: обращение к `conf_stat.stat.exists` вычислится первым и упадёт на несуществующем `stat`.

Обрати внимание и на то, что проверяется именно `conf_stat.stat is defined`, а не `conf_stat is defined`: сама переменная `conf_stat` существует всегда, даже у пропущенного таска — `register` создаёт её в любом случае, просто со служебным содержимым вида `{"skipped": true}`. Проверка `conf_stat is defined` была бы истинна и в этом случае, то есть ни от чего не защищала бы; спасает только проверка вложенного поля, которое кладёт туда сам модуль.

### Ловушка 4: `is defined` относится только к одному операнду

Родственная и очень коварная грабля. Кажется, что это условие проверяет существование всех трёх переменных:

```yaml
# НЕПРАВИЛЬНО — is defined относится ТОЛЬКО к nginx_version
when: nginx_user and nginx_conf_path and nginx_version is defined
```

На деле тест `is defined` цепляется только к последнему операнду — `nginx_version`. А `nginx_user` и `nginx_conf_path` проверяются как «голые» значения: Jinja2 пытается их вычислить, чтобы понять, истинны они или ложны. Если хотя бы одна из них не определена, выражение падает с ошибкой `'nginx_user' is undefined` — то есть проверка на существование сама спотыкается о несуществование, ровно то, от чего должна была защищать.

Правильно — `is defined` у **каждой** переменной, и для читаемости лучше сразу списком:

```yaml
when:
  - nginx_user is defined
  - nginx_conf_path is defined
  - nginx_version is defined
```

Одной строкой через `and` работает так же, но читается тяжело.

Мнемоника: `a and b is defined` ≠ `a is defined and b is defined`. Тест в Jinja2 — унарная операция над одним значением, «распределить» его на всю цепочку `and` нельзя.

### Ловушка 5: условие ссылается на результат собственной задачи

Задача, которая **никогда не выполнится**:

```yaml
- name: Определить версию nginx
  ansible.builtin.set_fact:
    nginx_version: "{{ ansible_facts.packages['nginx'][0].version }}"
  when: nginx_version is defined        # ← ОШИБКА
```

Механика по шагам:

1. Ansible доходит до задачи и **сначала** вычисляет `when`.
2. `nginx_version` ещё не существует — её создаёт эта же задача, которая ещё не выполнилась.
3. `is defined` → `false`.
4. Задача пропускается → переменная так и не создана.

Правильное условие проверяет не переменную, а **причину** — то, что существует независимо от этой задачи:

```yaml
- name: Определить версию nginx
  ansible.builtin.set_fact:
    nginx_version: "{{ ansible_facts.packages['nginx'][0].version }}"
  when: "'nginx' in ansible_facts.packages"
```

(`ansible_facts.packages` появляется после сбора фактов о пакетах модулем `ansible.builtin.package_facts` — обычный gathering facts этот словарь не заполняет.)

**Мнемоника: `is defined` смотрит назад во времени.** Он уместен, когда переменная *могла* быть создана ранее — предыдущей задачей, в инвентаре, через extra vars — а могла и не быть:

```yaml
# Правильно: set_fact выше по плейбуку либо создал переменную, либо нет
- name: Пропустить хост без nginx
  ansible.builtin.meta: end_host
  when: nginx_version is not defined
```

> `meta: end_host` — тихое выбытие хоста из выполнения без ошибки, в отличие от модуля `fail`, который останавливает плейбук с ошибкой.

Здесь условие смотрит на уже отработавший код.

### Ловушка 6: сравнение с числом, когда пришла строка

Родственная ловушка: `--extra-vars "workers=4"` передаст строку `"4"`. Сравнение `workers > 2` в новых версиях Ansible упадёт с ошибкой сравнения строки с числом. Решение — фильтр `| int`:

```yaml
when: workers | int > 2
```

### Ловушка 7: `when` не шаблонизируется дважды

Если в переменной лежит строка с `{{ }}`, внутри `when` она **не** будет развёрнута ещё раз — это защита от инъекций. Ловушкой это становится, когда пытаются хранить «условия в переменных»: так делать не нужно, условия пишутся явно в таске.

### Приём самопроверки: проговори условие словами

Ошибка в операторе сравнения — самая живучая: плейбук синтаксически корректен, запускается, но делает противоположное задуманному.

Приём: перед написанием `when` проговори условие фразой «задача выполнится, если …» — и оператор должен дословно совпасть с этой фразой.

```yaml
# Задумано: пропустить хост, если версия НИЖЕ минимальной
- name: Пропустить хост — версия nginx ниже минимальной
  ansible.builtin.meta: end_host
  when: nginx_version is version(min_nginx_version, '<')
  #                                                  ↑
  #                             «ниже» — значит '<', дословно
```

С оператором `'>='` эта задача выбивала бы все **годные** хосты, а старые пропускала дальше — молча, без единой ошибки.

Вторая опора — `name` задачи и текст условия должны говорить одно и то же. Если в `name` написано «ниже минимальной», а в условии стоит `'>='` — один из них врёт, и это видно при перечитывании.
