## 1. Структура команд Git

Все команды Git строятся по одному принципу:

```
git <команда> <флаги> <аргументы>
```

Примеры:

```bash
git add file.txt          # команда: add, аргумент: file.txt
git commit -m "message"   # команда: commit, флаг: -m, аргумент: "message"
git config --global ...   # команда: config, флаг: --global
```

## 2. Уровни конфигурации

Git использует трёхуровневую систему настроек: `local`, `global`, `system`. Уровни отличаются приоритетом и файлом, куда пишется настройка:

| Приоритет | Уровень  | Файл             | Область действия                                                |
|-----------|----------|------------------|-------------------------------------------------------------------|
| 1         | `local`  | `.git/config`    | Только этот репозиторий. Настройки не влияют на другие проекты  |
| 2         | `global` | `~/.gitconfig`   | Все репозитории твоего пользователя на этой машине               |
| 3         | `system` | `/etc/gitconfig` | Все репозитории всех пользователей на этой машине                |

Git ищет настройку сверху вниз: нашёл в `local` — дальше не смотрит. Не нашёл — идёт в `global`. Не нашёл и там — идёт в `system`. Поэтому `local` может переопределить `global`, а `global` — `system`, но не наоборот.

### Зачем нужны уровни

Представь у тебя 20 репозиториев на машине и во всех нужен одинаковый `user.name` и `user.email`.

**Без global** — нужно зайти в каждый из 20 репозиториев и прописать `local` вручную. 20 раз.

**С global** — прописал один раз в `~/.gitconfig` и всё. Git автоматически берёт эти настройки во всех репозиториях где нет `local`.

> **system** — используется администраторами для настройки Git на серверах для всех пользователей сразу. В повседневной работе этот уровень не нужен — используй `global`. В DevOps актуален для CI/CD серверов (Jenkins, GitLab Runner):
>
> ```bash
> # Корпоративный прокси — весь трафик Git через корпоративный сервер
> sudo git config --system http.proxy http://proxy.company.com:8080
>
> # Проверка SSL сертификатов — безопасность для всех пользователей
> sudo git config --system http.sslVerify true
>
> # Общий шаблон коммитов — все пользователи используют один шаблон
> sudo git config --system commit.template /etc/git/commit-template.txt
>
> # Защита основной ветки на CI/CD сервере
> sudo git config --system receive.denyNonFastForwards true
> ```

## 3. Основные настройки

### Обязательные — без них Git откажется делать коммиты

```bash
git config --global user.name "Иван Иванов"
git config --global user.email "ivan@example.com"
```

Git сохраняет имя и email при каждом коммите — без них `git commit` выдаст ошибку.

### Желательные — без них работать можно, но неудобно

```bash
# Редактор по умолчанию
# Git открывает редактор когда нужно что-то написать — например сообщение коммита
# Если не настроить — откроется vi по умолчанию, из которого многие не знают как выйти
git config --global core.editor "vim"
# Альтернативы: nano, code --wait (VS Code)

# Ветка по умолчанию при git init
# Исторически Git создавал ветку 'master', но в 2020 году GitHub и вся индустрия
# перешли на 'main' как стандарт. Технически разницы нет — это просто название ветки.
# Если не настроить — будет 'master', что создаёт путаницу при работе с GitHub
git config --global init.defaultBranch main
```

### Просмотр настроек

```bash
git config --list                  # все настройки из всех уровней
git config --global --list         # только глобальные
git config --local --list          # только локальные

# Значение конкретного параметра
git config user.email
```

### Удаление настроек

```bash
git config --unset user.name        # удалить конкретный параметр
git config --remove-section user    # удалить всю секцию
```

## 4. Кастомизация терминала

Кастомизация терминала — это отображение текущей ветки Git прямо в командной строке. Без неё ты не видишь в какой ветке находишься пока не напишешь `git branch` или `git status`.

**Без кастомизации:**
```
fa1ry@fa1ry:~/Tools/devops-notes$
```

**С кастомизацией:**
```
fa1ry@fa1ry:~/Tools/devops-notes (main)$
```

**Преимущества:**
- Всегда видишь в какой ветке работаешь — не закоммитишь случайно в не ту ветку
- Видишь есть ли незакоммиченные изменения (некоторые скрипты показывают `*`)
- Экономит время — не нужно постоянно писать `git status`
- Встроенные алиасы — большинство скриптов идут с готовым набором сокращений для Git команд, не нужно настраивать вручную (это shell-алиасы, работают только в этой оболочке — не путать с алиасами самого Git, которые работают в любом шелле и в скриптах)

**Скрипты по оболочкам:**

| Оболочка   | ОС              | Скрипт      |
|------------|-----------------|-------------|
| Zsh        | Linux / macOS   | oh-my-zsh   |
| Bash       | Linux           | git-prompt  |
| PowerShell | Windows         | posh-git    |
| Fish       | Linux / macOS   | fisher      |

## 5. Алиасы

Алиасы — сокращения для длинных команд. Экономят время при ежедневной работе.

Здесь и далее — алиасы самого Git: хранятся в конфиге, не зависят от оболочки.

### Простые алиасы

```bash
git config --global alias.sw switch      # git sw вместо git switch
git config --global alias.br branch      # git br вместо git branch
git config --global alias.st status      # git st вместо git status
git config --global alias.lg "log --oneline --graph --all --decorate"
```

Теперь вместо `git switch main` можно писать `git sw main`.

### Сложные алиасы

Если алиас начинается с `!` — Git выполняет его как команду оболочки, а не как Git-команду. Это позволяет запускать цепочки команд:

```bash
# Удалить все ветки которые уже слиты в main
git config --global alias.cleanup \
  "!git branch --merged | grep -v 'main\|master' | xargs git branch -d"

# Использование
git cleanup
```

### Где хранятся алиасы

Алиасы записываются в `~/.gitconfig`:

```ini
[alias]
    sw = switch
    br = branch
    st = status
    lg = log --oneline --graph --all --decorate
```
