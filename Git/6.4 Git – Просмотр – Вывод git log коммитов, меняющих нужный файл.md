# 6.4 Git – Просмотр – Вывод git log коммитов, меняющих нужный файл

## 1. Фильтрация истории по конкретному файлу

Если передать путь к файлу аргументом, `git log` сравнивает содержимое этого пути в каждом коммите с родительским и показывает только те коммиты, где есть расхождение — остальная история отфильтровывается:

```bash
$ git log --oneline -- app.py
f0d56af update app.py
b2c6b3c initial commit
```

Коммит `update README only`, который менял только `README.md`, в списке не появился — `app.py` в нём не менялся.

Флаг `-p` добавляет к каждому коммиту diff:

```bash
git log -p -- app.py
```

Если коммит менял несколько файлов, diff всё равно покажет изменения только по указанному пути — остальные файлы из вывода исключаются, даже если реально менялись в этом же коммите.

Отдельная особенность — как фильтрация по пути обходится со слияниями. Если слияние не принесло в файл ничего своего — например, файл менялся только на одной из веток, и версия просто взята с неё целиком, без разрешения конфликта — сам коммит слияния в списке не показывается. Git считает его неинтересным для истории этого файла и сразу показывает коммит на той ветке, где изменение реально произошло:

```bash
$ git log --oneline -- file.txt
2e122ab feature changes file.txt
565c29c base commit

$ git log --oneline --full-history -- file.txt
81a5af5 merge feature into master
2e122ab feature changes file.txt
565c29c base commit
```

`--full-history` отключает это упрощение и показывает все коммиты, включая такие слияния.

## 2. Отслеживание переименованных файлов

После переименования (`git mv` или `mv` + `git add`) обычный `git log` с новым именем видит историю только с момента переименования — до этой точки файл в репозитории числился под другим именем, и Git его не находит:

```bash
$ git log --oneline -- application.py
803594e update application.py after rename
2605344 rename app.py to application.py
```

Флаг `--follow` заставляет Git при упоре в коммит переименования подставить старое имя файла и продолжить поиск по нему дальше в прошлое:

```bash
$ git log --oneline --follow -- application.py
803594e update application.py after rename
2605344 rename app.py to application.py
f87d00e touch both app.py and extra.txt
f0d56af update app.py
b2c6b3c initial commit
```

В связке с `-p` в коммите переименования будет виден сам факт переименования:

```bash
$ git log -p --follow -- application.py
...
commit 2605344ad50eb2b35e8df4aa0c347a1acd0484e3
Author: Test <a@a.com>
Date:   Mon Aug 10 10:06:04 2026 +0000

    rename app.py to application.py

diff --git a/app.py b/application.py
similarity index 100%
rename from app.py
rename to application.py
...
```

`--follow` работает только с одним файлом: если передать несколько путей или директорию, Git завершится ошибкой `fatal: --follow requires exactly one pathspec`.

## 3. Использование диапазонов и веток

Фильтр по пути свободно комбинируется с диапазонами коммитов — `A..B` и остальным синтаксисом из темы 6.3. Например, чтобы увидеть изменения `index.html` только на `master`, которых нет на `feature`:

```bash
$ git log --oneline feature..master -- index.html
287ea05 master: change index.html #2
e13f065 master: change index.html #1
```

Без фильтра по пути тот же диапазон показал бы ещё и коммит с `README.md` — путь просто сужает список коммитов диапазона до тех, что реально меняли указанный файл.

## 4. Разрешение конфликтов имён: синтаксис `--`

Если имя файла совпадает с именем ветки, тега или началом хеша коммита, Git не может сам решить, что имелось в виду, и завершается ошибкой:

```bash
$ git log style
fatal: ambiguous argument 'style': both revision and filename
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'
```

Две черты `--` разделяют аргументы: всё до них Git разбирает как ссылки (ветки, теги, диапазоны), всё после — как пути к файлам:

```bash
$ git log -- style
8e92752 add file named style
```

Если имя файла нигде не пересекается с именами веток и тегов, `--` можно опустить — Git и так поймёт аргумент как путь. Но использовать его по умолчанию — хорошая практика: пример останется рабочим, даже если позже появится ветка или тег с тем же именем.

## 5. Директории и несколько путей

Вместо одного файла `git log` принимает директорию — в историю попадут коммиты, менявшие любой файл внутри неё:

```bash
$ git log --oneline -- src/
199d478 change src/b.py
5626ba7 change src/a.py
867febb initial: src/a.py, src/b.py, README.md
```

Можно передать и несколько путей сразу — файлов, директорий или их смеси. Условие — «или»: в список попадёт коммит, менявший хотя бы один из путей, необязательно все сразу:

```bash
$ git log --oneline -- src/a.py README.md
5798902 change README.md only
5626ba7 change src/a.py
867febb initial: src/a.py, src/b.py, README.md
```

Коммит, менявший только `src/b.py`, в этот список не попал — он не затрагивал ни `src/a.py`, ни `README.md`.
