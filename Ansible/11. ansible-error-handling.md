# 11. Обработка ошибок — `failed_when`, `changed_when`, `ignore_errors`, `block/rescue/always`

## Как Ansible понимает «ошибку» по умолчанию

Прежде чем ошибками управлять, нужно понимать, откуда Ansible вообще берёт статус `failed`.

Для обычных модулей (`ansible.builtin.copy`, `ansible.builtin.service`, `ansible.builtin.apt` и т.д.) решение принимает сам модуль: он знает, что считается ошибкой в его предметной области. Не удалось скопировать файл — `failed`, пакет не нашёлся в репозитории — `failed`. Здесь вмешиваться обычно не нужно.

Для `ansible.builtin.command` и `ansible.builtin.shell` правило одно и очень тупое: **ненулевой exit code = ошибка**. Модуль не понимает смысла команды, он видит только код возврата. Именно здесь чаще всего и возникает потребность в ручном управлении: масса нормальных команд возвращает ненулевой код в штатных ситуациях. Например: `grep` возвращает 1, если строка не найдена — это не сбой поиска, а честный ответ «нет совпадений»; `systemctl is-active` возвращает 3, если сервис не запущен, — тоже вполне рабочий статус, а не ошибка проверки; `diff` возвращает 1, если файлы отличаются, — что нередко и есть цель сравнения.

Что происходит при падении таски:

- хост, на котором таска упала, **выбывает из плея** — все последующие таски на нём пропускаются;
- остальные хосты продолжают выполняться как ни в чём не бывало;
- в итоговой статистике (`PLAY RECAP`) у хоста появляется `failed=1`.

Результат любой таски, включая упавшую, можно сохранить через `register` — структура переменной и универсальные поля `changed`/`failed` разобраны в теме 5. Вся эта тема, по сути, о том, как этими полями управлять.

## 1. `ignore_errors` — самый грубый инструмент

### 1.1 Зачем существует

Иногда падение таски не должно останавливать плей: таска необязательная, её результат ни на что дальше не влияет. `ignore_errors: yes` делает ровно это — таска падает, но хост остаётся в плее.

Имя ключа читается буквально — это удобная мнемоника: `ignore_errors` = «игнорировать ошибки». Но это не условие, а простой флаг «да/нет», и игнорирует он не сам факт ошибки, а её **последствия для плея**: ошибка никуда не девается, просто хосту разрешают жить дальше.

```yaml
- name: "Собрать диагностику (необязательно)"
  ansible.builtin.command: /opt/diag/collect.sh
  register: diag_result
  ignore_errors: yes
```

### 1.2 Что важно понимать

`ignore_errors` **не отменяет ошибку — он игнорирует её последствия**. Отсюда три эффекта:

- в выводе прогона таска остаётся красной, с пометкой `...ignoring` — при регулярных прогонах это шум, в котором легко проглядеть настоящую проблему;
- в `register`-переменной поле `failed` остаётся `true` — если дальше кто-то проверяет `diag_result.failed`, он увидит ошибку;
- статистика `PLAY RECAP` покажет `ignored=1`.

### 1.3 Когда это костыль

Типичное злоупотребление — глушить `ignore_errors` команды, которые возвращают ненулевой код в нормальной ситуации:

```yaml
# ✗ Плохо: ошибки маскируются, любое реальное падение grep тоже будет проигнорировано
- name: "Проверить наличие строки в конфиге"
  ansible.builtin.command: grep -q "worker_processes" /etc/nginx/nginx.conf
  register: grep_result
  ignore_errors: yes
```

Проблема: `ignore_errors` глушит **все** ошибки без разбора. Если файла не существует (`grep` вернёт 2) или прав нет — это тоже пройдёт молча. Правильный инструмент здесь — `failed_when`, о нём дальше.

Рабочее правило: `ignore_errors` — для тасков, чей результат действительно неважен. Если ты пытаешься отличить «нормальный ненулевой код» от «настоящей ошибки» — это работа `failed_when`.

```yaml
# ✓ Легитимно: уведомление необязательно, его провал не должен ронять обновление
- name: "Отправить событие об обновлении конфигурации в мониторинг"
  ansible.builtin.uri:
    url: http://monitoring.example.com/api/events
    method: POST
    body_format: json
    body:
      host: "{{ inventory_hostname }}"
      event: "config update finished"
  ignore_errors: yes
```

Мониторинг может быть недоступен — обновление это не отменяет, но **увидеть** красную пометку `...ignoring` в выводе полезно: это сигнал «уведомление не дошло, разберись». `ignore_errors` честно показывает проблему, не останавливая прогон, — ровно та ситуация, для которой он и существует. С `failed_when: false` эта же таска прошла бы зелёной, и недоступный мониторинг никто бы не заметил.

## 2. `failed_when` — переопределяем понятие ошибки

### 2.1 Зачем существует

`failed_when` заменяет встроенное правило «ненулевой код = ошибка» на твоё собственное условие. Именно **заменяет**, а не дополняет: как только у таски есть `failed_when`, статус определяется только им. Синтаксис условия — тот же, что у `when` (тема 8): выражение Jinja2 без `{{ }}`.

Имя ключа читается буквально, и это удобная мнемоника: `failed_when` = «считается упавшей, когда …». Работает это так:

- условие истинно → таска получает статус `failed`: красный вывод, хост выбывает из плея — всё как при обычном падении;
- условие ложно → таска успешна: обычный `ok`/`changed` в выводе, плей продолжается.

Мнемоника из темы 8 «прочитай условие вслух» работает и здесь — она помогает не перепутать направление: `failed_when: false` читается как «не считается упавшей никогда».

### 2.2 Базовый паттерн: `grep` и коды возврата

У `grep` три штатных кода: `0` — найдено, `1` — не найдено, `2` и выше — реальная ошибка (нет файла, нет прав). «Не найдено» — это не ошибка, это ответ:

```yaml
- name: "Проверить наличие строки в конфиге"
  ansible.builtin.command: grep -q "worker_processes" /etc/nginx/nginx.conf
  register: grep_result
  failed_when: grep_result.rc > 1
```

Теперь коды `0` и `1` — успех (дальше можно ветвиться по `grep_result.rc == 0`), а код `2` — честное падение с нормальной диагностикой.

### 2.3 Таска смотрит сама на себя

Обрати внимание на важную деталь: `failed_when` читает `grep_result` — переменную, которую **эта же таска** только что создала. Дело в моменте вычисления:

1. таска выполняется — результат летит в `register`;
2. `failed_when` и `changed_when` вычисляются **после**, по свежему результату этой же таски.

Именно поэтому это легально — в отличие от `when` из темы 8, который вычисляется **до** выполнения таски и поэтому видит только переменные из предыдущих тасков, а не свои собственные. Это единственное место (вместе с `changed_when` и `until`), где таска смотрит на собственный результат.

### 2.4 `failed_when: false` — чистая альтернатива `ignore_errors`

Разберём на конкретном сценарии: nginx на хосте сейчас остановлен, и плейбук доходит до проверки его статуса.

**Без `failed_when` — как повела бы себя обычная таска:**

```yaml
- name: "Проверить, отвечает ли сервис"
  ansible.builtin.command: systemctl is-active nginx
  register: nginx_active
```

1. Ansible выполняет `systemctl is-active nginx`.
2. Команда возвращает код 3 — nginx неактивен, это её штатный ответ на такой статус, а не сбой самой проверки.
3. `ansible.builtin.command` по умолчанию не разбирается в смысле кода — видит ненулевой код и считает таску упавшей.
4. Хост выбывает из плея: все таски **после** этой на данном хосте пропускаются, даже если среди них — таска, которая должна была бы nginx перезапустить.
5. В `PLAY RECAP` у хоста `failed=1`.

Получается абсурд: таска, чья единственная задача — узнать статус, сама прерывает прогон при любом статусе, кроме «активен». Проверка не может одновременно быть проверкой и приговором.

**С `failed_when: false`:**

```yaml
- name: "Проверить, отвечает ли сервис"
  ansible.builtin.command: systemctl is-active nginx
  register: nginx_active
  failed_when: false
```

Код возврата тот же — 3, на сервере ничего не поменялось. Но `failed_when: false` перекрывает стандартное правило: неважно, что вернула команда, эта таска не падает никогда. Вывод зелёный, хост остаётся в плее, а `nginx_active.rc` при этом честно хранит те же 3 — данные не потерялись, потерялся только вердикт «упала/не упала».

Ценность появляется на следующем шаге — когда есть таска, которая реагирует на результат:

```yaml
- name: "Перезапустить nginx, если он не активен"
  ansible.builtin.service:
    name: nginx
    state: restarted
  when: nginx_active.rc != 0
```

Без `failed_when: false` до этой таски дело бы не дошло — плейбук остановился бы строчкой раньше. С ним — доходит и чинит проблему сам. `failed_when: false` не меняет то, что происходит на сервере в момент проверки; он меняет то, как Ansible реагирует на результат: стоять на месте или дать шанс среагировать следующей таской.

Отличие от `ignore_errors`: таска считается **успешной**, а не «упавшей, но проигнорированной». Вывод прогона зелёный, `nginx_active.failed` равен `false`, в статистике нет `ignored`. Для проверочных команд, где ненулевой код — штатный ответ, это правильный вариант.

Разница коротко:

- `ignore_errors: yes` — «ошибка была, но едем дальше» (красный вывод, `failed: true`);
- `failed_when: false` — «это вообще не ошибка» (зелёный вывод, `failed: false`).

### 2.5 Составные условия

Условие может быть любой сложности. Возьмём скрипт миграции схемы БД — `/opt/app/migrate.sh`. У него три возможных исхода:

- миграция была нужна и прошла успешно (`rc = 0`);
- миграция уже была применена раньше, и скрипт не может накатить её повторно, но честно объясняет причину в stderr, например «already applied»;
- реальная поломка — синтаксическая ошибка в файле миграции, обрыв соединения с БД и подобное.

**Без `failed_when`:** `command` смотрит только на код возврата, а второй и третий исход с его точки зрения неотличимы — оба дают ненулевой код, оба помечаются `failed`. Хост выбывает из плея одинаково что при настоящей поломке, что при безобидном повторном прогоне. Проблема та же, что и с `systemctl` выше, только здесь хуже: там штатные исходы хотя бы расходились по разным кодам, а тут «применено» и «сломалось» делят один и тот же диапазон кодов и различаются только текстом в stderr.

```yaml
- name: "Прогнать миграцию схемы"
  ansible.builtin.command: /opt/app/migrate.sh
  register: migrate_result
  failed_when: migrate_result.rc != 0 and 'already applied' not in migrate_result.stderr
```

**С этим условием** — трассируем по всем трём исходам:

- миграция прошла успешно: `rc != 0` уже `false`, и по лени `and` вторая часть даже не вычисляется — таска зелёная;
- миграция уже применена: `rc != 0` — `true`, но фраза «already applied» в stderr есть, значит `not in` даёт `false`, всё условие `false` — таска снова зелёная;
- реальная поломка: `rc != 0` — `true`, фразы в stderr нет, `not in` даёт `true`, условие целиком `true` — и только здесь таска красная, заслуженно.

Прочитанное вслух — «таска считается упавшей, когда код ненулевой и в выводе нет фразы об уже применённой миграции» — совпадает с задуманным поведением: мнемоника из темы 8 подтверждает, что оператор не перепутан.

Ленивость `and` здесь работает не так, как в теме 8, где она защищала от падения на неопределённой переменной. Такого риска тут нет: `migrate_result.stderr` гарантированно существует после `register`, даже если это пустая строка. В этом примере лень — просто про эффективность и порядок чтения: если код и так 0, лезть в текст stderr незачем, ответ уже ясен.

`failed_when` принимает и список условий — они объединяются через `and`, как у `when`:

```yaml
  failed_when:
    - migrate_result.rc != 0
    - "'already applied' not in migrate_result.stderr"
```

## 3. `changed_when` — управляем статусом `changed`

### 3.1 Зачем существует

Механизм тот же, что у `failed_when`, но управляет он статусом `changed`. Проблема, которую он решает: `ansible.builtin.command` и `ansible.builtin.shell` **всегда** возвращают `changed` — модуль не знает, изменила команда что-то или нет, и на всякий случай говорит «изменила».

По той же мнемонике, что и у `failed_when`: `changed_when` читается буквально как «считается изменившей, когда …» — условие истинно, таска `changed`; условие ложно, таска `ok`.

Это ломает две вещи:

- **читаемость прогона** — идемпотентный плейбук на неизменённой системе должен показывать сплошные `ok`; жёлтые `changed` от проверочных команд превращают вывод в шум, по которому нельзя понять, было ли реальное изменение;
- **handlers** — из темы 10: handler запускается по статусу `changed` уведомившей таски. Ложный `changed` → ложный `notify` → сервис перезапускается на каждом прогоне без причины.

### 3.2 `changed_when: false` для проверочных команд

По той же мнемонике: `changed_when: false` — «никогда не считать изменившей», что бы команда ни сделала на самом деле.

**Без `changed_when`:**

```yaml
- name: "Получить версию nginx"
  ansible.builtin.command: nginx -v
  register: nginx_version
```

1. Ansible выполняет `nginx -v`.
2. Команда успешно отработала, `rc = 0`.
3. `ansible.builtin.command` по умолчанию помечает любое своё успешное выполнение как `changed` — он не различает «прочитал» и «изменил».
4. В выводе таска жёлтая: `changed`. Второй прогон плейбука на той же системе даст ровно тот же жёлтый цвет — идемпотентность на глаз не проверить, сплошной шум.

**С `changed_when: false`:**

```yaml
- name: "Получить версию nginx"
  ansible.builtin.command: nginx -v
  register: nginx_version
  changed_when: false
```

Команда выполняется точно так же, `nginx_version.stdout` так же содержит версию. Но статус теперь `ok` — зелёный, честный. И это не только про цвет: если бы к такой таске был привязан `notify`, без `changed_when: false` handler запускался бы на каждом прогоне без единой причины — сама по себе таска ничего не меняла, а Ansible всё равно докладывал бы об изменении.

Это настолько устойчивый паттерн, что стоит принять за правило: **`command`/`shell` с чисто проверочной командой всегда несёт `changed_when: false`**.

### 3.3 Условие по выводу для изменяющих команд

Более практичный случай — команда, которая действительно меняет состояние, но по-разному ведёт себя в зависимости от того, нужно ли ей вообще что-то делать. Возьмём обновление Python-пакета.

**Без `changed_when`:**

```yaml
- name: "Обновить пакет requests"
  ansible.builtin.command: pip install --upgrade requests
  register: pip_result
  notify: "Перезапустить приложение"
```

1. Команда выполняется всегда — и когда есть новая версия, и когда пакет уже самый свежий.
2. В обоих случаях `pip` завершается с `rc = 0` — это успех независимо от того, обновил он что-то или нет.
3. `ansible.builtin.command` смотрит только на код возврата, значит обе ситуации помечаются одинаково: `changed`.
4. `notify` срабатывает при любом исходе → handler перезапускает приложение на каждом прогоне, даже если версия библиотеки не менялась ни разу.

**С условием по выводу:**

```yaml
- name: "Обновить пакет requests"
  ansible.builtin.command: pip install --upgrade requests
  register: pip_result
  changed_when: "'Successfully installed' in pip_result.stdout"
  notify: "Перезапустить приложение"
```

`pip` пишет в stdout строку `Successfully installed ...` только тогда, когда реально что-то поставил или обновил; если пакет уже самой свежей версии, вывод содержит `Requirement already satisfied`, и этой строки там нет. Условие проверяет именно это:

- пакет обновился → строка есть → `changed_when` истинно → таска `changed` → `notify` срабатывает по делу, handler перезапускает приложение с новой версией библиотеки;
- пакет уже свежий → строки нет → `changed_when` ложно → таска `ok` → `notify` не срабатывает, приложение не перезапускается зря.

Без условия по выводу второй случай тоже дал бы `changed`, `notify` бы сработал, и приложение перезапускалось бы на каждом прогоне вообще без повода.

### 3.4 Связь с ручной идемпотентностью через `when`

Мы уже делали идемпотентность для `command` вручную в теме 8: проверочная таска с `register`, потом `when` на изменяющей. Разница с `changed_when` сводится к одному вопросу — **когда мы узнаём, нужно ли выполнять команду?**

**`register` + `when` — работа наперёд.** Сначала лёгкая проверка (например, `stat` или `grep`), потом взгляд на её результат: если всё уже сделано, тяжёлая команда вообще не запускается.

**`changed_when` — работа постфактум.** Команда выполняется всегда. Ansible смотрит на её вывод (`stdout`/`rc`) уже после запуска и по нему решает, писать `changed` или `ok`.

Часто они работают в паре: проверочная таска несёт `changed_when: false`, изменяющая — `when` по её результату.

## 4. `block / rescue / always` — структурная обработка

### 4.1 От группировки к обработке

`block` без `rescue` и `always` — просто группировка тасков под общим `when` (тема 8). Полная форма — когда есть все три секции — превращает его в аналог `try / catch / finally` из языков программирования (Python, Java, JS и почти всех остальных), это не специфика Ansible:

```yaml
- name: "Обновить конфигурацию nginx"
  block:
    - name: "Разложить новый конфиг"
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        backup: yes
      register: nginx_config

    - name: "Проверить конфиг"
      ansible.builtin.command: nginx -t
      changed_when: false

  rescue:
    - name: "Вернуть предыдущий конфиг"
      ansible.builtin.copy:
        src: "{{ nginx_config.backup_file }}"
        dest: /etc/nginx/nginx.conf
        remote_src: yes
      when: nginx_config.backup_file is defined

    - name: "Сообщить о причине"
      ansible.builtin.debug:
        msg: "Упала таска «{{ ansible_failed_task.name }}»: {{ ansible_failed_result.msg | default('см. вывод выше') }}"

  always:
    - name: "Убрать временные файлы деплоя"
      ansible.builtin.file:
        path: /tmp/nginx-deploy
        state: absent
```

- **`block`** — основной сценарий. Падение **любой** таски внутри прерывает блок: оставшиеся таски блока пропускаются, управление уходит в `rescue`.
- **`rescue`** — выполняется **только при падении** в `block`. Если блок прошёл чисто, `rescue` целиком пропускается. Внутри доступны две магические переменные — существуют только здесь, только при реальном падении: `ansible_failed_task` (упавшая таска, полезно `ansible_failed_task.name`) и `ansible_failed_result` (её результат — то, что попало бы в `register`).
- **`always`** — выполняется **в любом случае**: блок прошёл чисто, блок упал и `rescue` отработал, и даже если упал сам `rescue`. Место для очистки, снятия блокировок, финальных уведомлений.

Общая форма, ради которой блок обычно и пишут: **попытка → откат или уведомление → гарантированная очистка**. Пример выше — ровно она: пробуем новый конфиг, при провале возвращаем резервную копию, мусор убираем в любом случае.

### 4.2 Подводный камень: `rescue` гасит ошибку

Если `rescue` отработал без падений, хост считается **живым**: плей для него продолжается, `failed` в `PLAY RECAP` не появляется — вместо него счётчик `rescued`:

```
PLAY RECAP *********************************************************
web-01  : ok=6  changed=2  unreachable=0  failed=0  skipped=0  rescued=1  ignored=0
```

Это и есть смысл механизма, но у него есть обратная сторона: ошибка обработана — значит, ошибки не было. Если после отработки `rescue` хост всё равно остался в нерабочем состоянии (`rescue` не обязан что-то чинить или откатывать — он может, например, просто уведомить) и продолжать плей на нём бессмысленно, об этом нужно позаботиться явно — например, завершить `rescue` таской `ansible.builtin.fail` (тогда хост честно упадёт, а `always` всё равно выполнится) или `meta: end_host`.

Ещё две границы применимости:

- `rescue` ловит **ошибки тасков**, но не недоступность хоста (`unreachable`) и не синтаксические ошибки плейбука — в обоих случаях не срабатывает даже `always`: хост просто выбывает из плея, как при обычном падении без `block`, и в `PLAY RECAP` это отдельный счётчик `unreachable=1`;
- если внутри блока упавшая таска успела сделать `notify`, а плей в итоге дошёл до конца — сработают обычные правила handlers из темы 10, включая `--force-handlers` для случая, когда плей всё-таки упал.

## 5. `until / retries / delay` — повтор до успеха

### 5.1 Зачем существует

Перевод трёх ключей: `until` — «до тех пор, пока (не)», `retries` — «повторные попытки», `delay` — «задержка, пауза».

В теме 9 мы разграничили: `loop` — повтор таски по списку данных, `until` — повтор **одной и той же** таски до выполнения условия. Типовая задача — ожидание готовности: сервис перезапущен, но начинает отвечать не мгновенно.

```yaml
- name: "Дождаться, пока nginx начнёт отвечать"
  ansible.builtin.uri:
    url: http://127.0.0.1/health
    status_code: 200
  register: health_result
  until: health_result.status == 200
  retries: 10
  delay: 3
```

- таска выполняется, результат попадает в `register`;
- вычисляется условие `until` — по собственному результату таски, как `failed_when`;
- условие истинно → успех, едем дальше; ложно → пауза `delay` секунд и новая попытка;
- попытки исчерпаны, а условие так и не выполнилось → таска **падает** как обычная упавшая таска (дальше применимо всё из этой темы — хоть `rescue`, хоть `ignore_errors`).

Значения по умолчанию: `retries: 3`, `delay: 5`. В выводе неудачные попытки видны как `FAILED - RETRYING`, а в `register`-переменной появляется поле `attempts` — сколько попыток понадобилось.

Важная деталь: промежуточные «неудачи» попыток — это не ошибки таски, а всего лишь ложное условие `until`. Если сама команда при этом падает (например, `ansible.builtin.uri` не может подключиться), падение каждой попытки тоже не фатально — фатальна только последняя.

### 5.2 `until` — про «ещё не готово», а не про «сломалось»

Разграничение, которое помогает выбрать инструмент: `until` уместен, когда неуспех **временный по природе** — сервис поднимается, кластер синхронизируется, файл появляется. Если таска падает из-за реальной проблемы (нет пакета, неверный конфиг), повтор ничего не изменит — три одинаковые ошибки вместо одной только затянут прогон. Маскировать повторами постоянную ошибку — антипаттерн.

## 6. `any_errors_fatal` и `max_fail_percentage` — уровень плея

По умолчанию падение хоста — его личная проблема: остальные продолжают. Иногда это неправильно — например, при согласованном обновлении, где половинчатый результат хуже отсутствия результата.

**`any_errors_fatal: true`** на уровне плея останавливает **весь плей для всех хостов**, как только упал хотя бы один:

```yaml
- name: "Согласованное обновление конфигурации"
  hosts: webservers
  any_errors_fatal: true
  tasks:
    ...
```

**`max_fail_percentage`** — мягкий вариант: плей останавливается, когда доля упавших хостов **превышает** порог (именно превышает: при `max_fail_percentage: 30` и десяти хостах прогон переживёт три упавших и остановится на четвёртом).

Обе настройки — про раскатку по большому парку и тесно связаны с параметром `serial` (выполнение партиями). Стратегии выполнения — отдельная тема; здесь достаточно знать, что такие рычаги существуют.
