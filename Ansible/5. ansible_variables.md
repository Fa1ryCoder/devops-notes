## Введение — два разных мира переменных

Переменные — это способ сделать плейбук гибким. Без них пришлось бы писать отдельный плейбук для каждого хоста или каждой среды: один для тестовых серверов, другой для продакшена, третий для другого региона. Переменные позволяют писать один плейбук, который ведёт себя по-разному в зависимости от того, на каком хосте и в каком контексте он запускается.

**Без переменных** — для каждого сервера отдельный плейбук с зашитыми значениями:

```yaml
# playbook_shop42.yml
- name: Настроить веб-сервер в Москве
  hosts: web-msk-01
  tasks:
    - name: Записать конфиг
      ansible.builtin.copy:
        content: |
          server_id=42
          server=192.168.42.1
          region=moscow
        dest: /etc/app/config.ini

# playbook_shop77.yml — ещё один такой же файл, но с другими цифрами
# playbook_shop105.yml — и ещё один...
```

**С переменными** — один плейбук на все серверы, значения лежат в `host_vars` каждого хоста:

```yaml
- name: Настроить все веб-серверы
  hosts: web_servers
  tasks:
    - name: Записать конфиг
      ansible.builtin.copy:
        content: |
          server_id={{ server_id }}
          server={{ server_ip }}
          region={{ region }}
        dest: /etc/app/config.ini
```

Сотня серверов — один плейбук. Добавился новый сервер — добавляешь только `host_vars`, код не трогаешь.

Прежде чем разбирать конкретные механизмы, важно понять одно принципиальное разделение, которое в Ansible легко упустить в начале.

Все переменные в Ansible делятся на две категории по смыслу:

**Переменные инвентаря** отвечают на вопрос «что я знаю об этих хостах». Это данные об инфраструктуре — адреса, учётные данные, тип оборудования, идентификаторы. В примере выше это `server_id`, `server_ip` и `region` — они принадлежат конкретному хосту и лежат в её `host_vars`. Они существуют независимо от того, какой плейбук запускается, и описывают саму среду, а не действия над ней.

**Переменные плейбука** отвечают на вопрос «с какими параметрами выполнять эту задачу». Это данные об автоматизации — имена пакетов, пути к файлам, версии, флаги поведения. Например, `package_name: nginx` или `config_path: /etc/nginx/nginx.conf` — эти значения одинаковы для всех хостов и относятся к тому, *что делает* плейбук, а не к тому, *где он работает*. Задаются в секции `vars` внутри плейбука или в отдельном файле, подключаемом через `vars_files`:

```yaml
- name: Установка nginx
  hosts: web_servers
  vars:
    package_name: nginx
    config_path: /etc/nginx/nginx.conf
```

Они принадлежат конкретному плейбуку и описывают логику работы, а не инфраструктуру.

Если одна и та же переменная определена в нескольких местах — Ansible не выдаст ошибку, а молча выберет значение по приоритету.

### Кавычки и автоопределение типов

YAML без кавычек **угадывает тип** значения. Обычно угадывает верно, но на «числоподобных» строках ошибается молча:

```yaml
version_a: 5.304.10   # две точки — числом не парсится, останется строкой
version_b: 5.3        # float 5.3
version_c: 1.60       # float 1.6 — хвостовой ноль ИСЧЕЗ
port: 8080            # int — здесь угадал правильно
```

Разбор коварного случая: в файле написана версия `1.60`, YAML прочитал float `1.6` — и плейбук будет искать пакет версии `1.6`, которого не существует. Ошибки не будет — будет тихое искажение данных на этапе парсинга, ещё до того, как Ansible вообще начал работать.

Классика жанра — «norway problem»: в старых версиях YAML `no` (двухбуквенный код Норвегии) без кавычек превращался в `false`. Механизм тот же: парсер угадал тип, данные исказились.

Кавычки отключают угадывание: `"1.60"` — это строка `1.60`, как написано.

**Правило:** версии, номера телефонов, почтовые индексы, MAC-адреса — всё, что *выглядит* как число, но *по смыслу* строка — всегда в кавычках. Смысл правила — не думать каждый раз, переживёт ли конкретная строка парсинг, а снять вопрос механически.

## 1. Переменные инвентаря

### 1.1 `host_vars/<hostname>.yml` — переменные конкретного хоста

Используются для данных, специфичных для одной машины: адрес подключения, тип оборудования, идентификатор сервера.

```yaml
# host_vars/web-01.yml
ansible_host: 192.168.1.101
server_role: frontend
server_id: 42
```

### 1.2 `group_vars/<groupname>.yml` — переменные группы хостов

Используются для данных, общих для всех машин в группе: параметры подключения, версия ПО, адрес сервера.

```yaml
# group_vars/web_servers.yml
ansible_user: admin
ansible_ssh_pass: secret
app_version: "2.3.1"
```

### 1.3 Переменные прямо в файле инвентаря

Можно указывать переменные непосредственно внутри `inventory.yml` через ключ `vars` на уровне группы или хоста:

```yaml
# inventory/hosts.yml
all:
  children:
    web_servers:
      hosts:
        web-01:
          ansible_host: 192.168.1.101
          server_role: frontend
        web-02:
          ansible_host: 192.168.1.102
          server_role: backend
      vars:
        ansible_user: admin
        ansible_ssh_pass: secret
```

Этот способ удобен для небольших проектов, когда хостов мало и переменных немного. При росте проекта переменные обычно выносят в отдельные `host_vars/` и `group_vars/` — так проще ориентироваться.

## 2. Переменные плейбука — `vars` и `vars_files`

### 2.1 `vars` — переменные прямо в play

Объявляются внутри play в секции `vars`. Доступны всем tasks этого play.

```yaml
- name: Установка nginx
  hosts: web_servers
  vars:
    package_name: nginx
    config_path: /etc/nginx/nginx.conf
    required_version: "3.1.0"

  tasks:
    - name: Установить пакет
      ansible.builtin.apt:
        name: "{{ package_name }}"
        state: present
```

**Ограничение:** переменные из `vars` видны только внутри своего play. Если в плейбуке несколько play — переменные не передаются между ними.

---

### 2.2 `vars_files` — переменные из отдельного файла

Вместо того чтобы писать все переменные прямо в плейбук, их можно вынести в отдельный YAML-файл и подключить через `vars_files`.

Файл кладут в директорию `vars/` — это общепринятое соглашение, а не требование Ansible. Название может быть любым: Ansible просто читает файл по указанному пути.

```yaml
# vars/nginx.yml
package_name: nginx
config_path: /etc/nginx/nginx.conf
required_version: "3.1.0"
cert_dir: /etc/nginx/ssl
service_name: nginx
```

**Подключение в плейбуке:**

```yaml
- name: Установка nginx
  hosts: web_servers
  vars_files:
    - vars/nginx.yml

  tasks:
    - name: Установить пакет
      ansible.builtin.apt:
        name: "{{ package_name }}"
        state: present
```

Можно подключить несколько файлов сразу — они загружаются по порядку:

```yaml
  vars_files:
    - vars/common.yml
    - vars/nginx.yml
```

**Путь к файлу** указывается относительно директории, где лежит плейбук.

По приоритету `vars` и `vars_files` равнозначны — оба относятся к уровню «переменные play».

## 3. Факты хоста — `ansible_facts`

### Что такое факты

При запуске плейбука Ansible автоматически выполняет task под названием `Gathering Facts` — если ты видел эту строку в выводе, это оно. В этот момент Ansible подключается к каждому хосту через модуль `ansible.builtin.setup` и собирает информацию о нём: операционная система, сетевые интерфейсы, объём памяти, процессор, дисковые разделы и многое другое. Модуль встроен в Ansible — на целевом хосте ничего дополнительно устанавливать не нужно.

Все собранные данные складываются в зарезервированный словарь `ansible_facts` — это специальная переменная, которую Ansible создаёт и заполняет автоматически. Одновременно для каждого факта создаётся отдельная переменная с префиксом `ansible_`. Это два способа добраться до одних и тех же данных — `ansible_facts['distribution']` и `ansible_distribution` вернут одно и то же значение. Подробно разобрано в разделе «Использование в плейбуке» ниже.

### Как посмотреть факты хоста вручную

```bash
ansible web-01 -m ansible.builtin.setup
```

Вывод будет большим — несколько сотен строк JSON. Чтобы отфильтровать нужное:

```bash
# Только список сетевых интерфейсов
ansible web-01 -m ansible.builtin.setup -a "filter=ansible_interfaces"

# Только информация об ОС
ansible web-01 -m ansible.builtin.setup -a "filter=ansible_distribution*"

# Факты конкретного интерфейса
ansible web-01 -m ansible.builtin.setup -a "filter=ansible_lo"
```

> **Важно:** фильтр работает только по имени верхнего факта — вложенные ключи он не понимает. `filter=ansible_lo.ipv4` ничего не вернёт. Фильтр нужен только чтобы сократить вывод при ручном просмотре — выбирать конкретное поле нужно уже внутри плейбука.

### Обращение к вложенным данным

Факты представляют собой сложную структуру (словари внутри словарей, списки внутри словарей).

- Доступ к элементам словаря осуществляется через точку `.` или ключ `['...']`.
- Доступ к элементам списка — через индекс `[0]`.

Разберём на реальном факте `ansible_lo` — в нём есть и словари, и список:

```json
"ansible_lo": {
    "ipv4": {
        "address": "127.0.0.1",
        "netmask": "255.0.0.0"
    },
    "ipv6": [
        {
            "address": "::1",
            "prefix": "128"
        }
    ]
}
```

Правило чтения структуры: видишь `{` — это словарь, обращайся по имени ключа; видишь `[` — это список, обращайся по номеру.

Прогрессия обращений — от простого к сложному:

```yaml
# Шаг 1: словарь через точку
ansible_lo.ipv4.address              # "127.0.0.1"

# Шаг 2: то же самое через квадратные скобки
ansible_lo['ipv4']['address']        # "127.0.0.1"

# Шаг 3: усложняем — ipv6 это список, добавляется индекс
ansible_lo.ipv6[0]                   # весь первый элемент списка

# Шаг 4: после индекса продолжаем цепочку к полю словаря
ansible_lo.ipv6[0].address           # "::1"
```

Пример в плейбуке:

```yaml
- name: Показать IPv6-адрес интерфейса lo
  ansible.builtin.debug:
    msg: "{{ ansible_lo.ipv6[0].address }}"
```

### Использование в плейбуке

К фактам можно обращаться двумя способами.

Короткая форма — это прямое обращение к факту по его имени с префиксом `ansible_` (например, `ansible_architecture`). Ansible автоматически создаёт такие имена-ярлыки для всех данных, которые лежат внутри основного словаря `ansible_facts`:

```yaml
when: ansible_distribution == "Ubuntu"
```

Полная форма — через `ansible_facts['имя_факта']`. Это современный стиль, защищает от конфликта имён с пользовательскими переменными:

```yaml
when: ansible_facts['distribution'] == "Ubuntu"
```

Обе формы работают. В примерах ниже используется полная форма.

Условная установка пакета в зависимости от ОС:

```yaml
- name: Установить пакет только на Ubuntu
  ansible.builtin.apt:
    name: nginx
    state: present
  when: ansible_facts['distribution'] == "Ubuntu"
```

Выбор конфигурации в зависимости от архитектуры:

```yaml
- name: Скопировать бинарник под нужную архитектуру
  ansible.builtin.copy:
    src: "files/app-{{ ansible_facts['architecture'] }}"
    dest: /usr/local/bin/app
```

### Факты об установленных пакетах — `package_facts`

Частая задача: сделать что-то в зависимости от того, какой пакет и какой версии установлен на хосте. Для этого не нужен `shell` с `dpkg -l` и парсингом вывода — есть специальный модуль:

```yaml
- name: Получение списка установленных пакетов
  ansible.builtin.package_facts:
    manager: apt
```

**Ключевой принцип: модули `*_facts` пишут результат не в `register`, а напрямую в `ansible_facts`.** Это отдельный класс модулей-сборщиков (`package_facts`, `service_facts` и другие). Их результат появляется как факты хоста и доступен во всех последующих задачах — `register` не требуется.

Если всё же написать `register: packages` — ничего не сломается, но в переменную попадёт только служебная обёртка (базовые поля `changed`, `failed` — они, как мы помним, универсальны для любого модуля). Полезные данные всё равно окажутся в `ansible_facts.packages`.

**Структура `ansible_facts.packages`** — словарь: ключ — имя пакета, значение — **список** словарей с информацией о нём:

```json
"packages": {
    "nginx": [
        {
            "name": "nginx",
            "version": "1.24.0-2",
            "arch": "amd64",
            "source": "apt"
        }
    ],
    "openssh-server": [
        {
            "name": "openssh-server",
            "version": "1:9.6p1-3",
            "arch": "amd64",
            "source": "apt"
        }
    ]
}
```

Доступ к версии — по ключу, потом первый элемент списка, потом поле:

```yaml
- name: Показать версию nginx
  ansible.builtin.debug:
    msg: "{{ ansible_facts.packages['nginx'][0].version }}"
```

**Почему список и откуда `[0]`:** один пакет может быть установлен в нескольких экземплярах — например, в разных архитектурах (i386 + amd64). В типовом случае элемент один, и `[0]` берёт его.

**Проверка наличия пакета** — оператор `in` по ключам словаря:

```yaml
when: "'nginx' in ansible_facts.packages"
```

Обращение к `ansible_facts.packages['nginx']` на хосте, где пакета нет — ошибка undefined. Поэтому проверка наличия всегда идёт *до* обращения (подробнее о защите от несуществующих переменных — тема 8).

### Отключение сбора фактов

Если факты не нужны — сбор можно отключить. Это ускоряет выполнение плейбука, особенно на большом числе хостов:

```yaml
- name: Быстрое обновление конфига
  hosts: all
  gather_facts: false

  tasks:
    - name: Скопировать конфиг
      ansible.builtin.copy:
        src: nginx.conf
        dest: /etc/nginx/nginx.conf
```

## 4. Переменные, создаваемые во время выполнения — `register` и `set_fact`

Переменные инвентаря и плейбука задаются до запуска — они статичны. Но часто нужно принять решение прямо во время выполнения, опираясь на то, что происходит на хосте.

Например: перед установкой пакета нужно проверить, какая версия уже стоит, и установить новую только если текущая устарела. Или: роль сервера заранее неизвестна, и путь к конфигу нужно собрать на лету из того, что вернула команда. Статическими переменными это не решить — нужны механизмы, которые работают в момент выполнения.

`register` и `set_fact` — это именно такие механизмы. Оба создают переменные в процессе прогона плейбука, но делают это по-разному и для разных целей.

### 4.1 `register` — сохранение результата task

Каждая task в Ansible возвращает объект с результатом своей работы: статус выполнения, вывод команды, изменённые данные. По умолчанию этот результат нигде не сохраняется. `register` позволяет поместить его в переменную.

```yaml
- name: Проверить версию установленного пакета
  ansible.builtin.command: dpkg -l nginx
  register: dpkg_result

- name: Показать результат
  ansible.builtin.debug:
    var: dpkg_result
```

Переменная `dpkg_result` — это словарь (dict):

```
dpkg_result:
  rc: 0                    # код возврата (0 = успех)
  stdout: "..."            # стандартный вывод
  stderr: "..."            # вывод ошибок
  stdout_lines: [...]      # stdout построчно, в виде списка
  changed: true/false      # был ли изменён хост
  failed: true/false       # завершилась ли task с ошибкой
```

**Типичные применения:**

Проверить, что вернула команда, и использовать это в условии:

```yaml
- name: Получить содержимое app.conf
  ansible.builtin.command: cat /etc/app.conf
  register: app_conf_content
  ignore_errors: true

- name: Установить пакет только если app.conf содержит нужную строку
  ansible.builtin.apt:
    name: nginx-extras
    state: present
  when: "'mode=prod' in app_conf_content.stdout"
```

Проверить статус сервиса и в зависимости от него принять решение:

```yaml
- name: Проверить статус сервиса
  ansible.builtin.systemd:
    name: nginx
  register: service_status

- name: Перезапустить только если сервис уже запущен
  ansible.builtin.systemd:
    name: nginx
    state: restarted
  when: service_status.status.ActiveState == "active"
```

Каждый `register` создаёт отдельную переменную с данными того таска, к которому он привязан.

Базовые поля, которые присутствуют в ответе абсолютно любого модуля — это `changed` и `failed`. Если модуль выполняет команды в консоли (например, `command` или `shell`), он также всегда возвращает `rc` (код возврата), `stdout` (стандартный вывод) и `stderr` (вывод ошибок).

Узкоспециализированные модули добавляют свои уникальные поля. Например, модули управления сервисами возвращают словарь со статусом службы, а модули работы с файлами — хэш-суммы и пути. Что именно возвращает конкретный модуль — всегда можно посмотреть в официальной документации в разделе **Return Values**.

**Важно:** переменная, созданная через `register`, существует только в рамках текущего play. Между play она не передаётся (в отличие от `set_fact`).

### 4.2 `set_fact` — создание переменной во время выполнения

`set_fact` — это отдельный модуль, который создаёт переменную с произвольным значением в момент выполнения. В отличие от `register`, ты сам определяешь, что в ней будет.

```yaml
- name: Вычислить путь к конфигу на основе роли сервера
  ansible.builtin.set_fact:
    config_path: "/etc/nginx/{{ server_role }}/nginx.conf"
```

После этой task переменная `config_path` доступна во всех последующих tasks.

**Ключевое отличие от `vars` и `vars_files`:** переменные из `vars` задаются до запуска плейбука и не могут зависеть от того, что происходит на хосте. `set_fact` выполняется в момент прогона и может использовать любые данные, которые уже получены — факты хоста, результаты команд через `register`, другие переменные.

**Типичные применения:**

Вычислить значение на основе факта хоста (`ansible_distribution` — это факт, собранный на этапе `Gathering Facts`):

```yaml
- name: Определить директорию для логов
  ansible.builtin.set_fact:
    log_dir: "{{ '/var/log/nginx' if ansible_distribution == 'Ubuntu' else '/opt/log/nginx' }}"
```

Упростить сложную структуру из `register`:

```yaml
- name: Получить версию пакета
  ansible.builtin.shell: dpkg -l | grep nginx | awk '{print $3}'
  register: pkg_version_raw

- name: Сохранить только строку с версией
  ansible.builtin.set_fact:
    nginx_version: "{{ pkg_version_raw.stdout }}"

# Теперь можно использовать nginx_version вместо pkg_version_raw.stdout везде
```

**`set_fact` сохраняется между play** (в отличие от `register`). Это делает его удобным инструментом для передачи данных от одного play к другому в рамках одного плейбука.

---

### 4.3 Сравнение `register` и `set_fact`

Главное отличие в том, откуда берутся данные.

`register` автоматически сохраняет весь системный отчёт о выполнении конкретной task — статус, ошибки, вывод из консоли. Ты не выбираешь что туда запишется, Ansible просто «фотографирует» результат работы модуля:

```yaml
- name: Проверить статус сервиса
  ansible.builtin.systemd:
    name: nginx
  register: service_result  # сюда запишется ВЕСЬ отчёт системы
```

Внутри `service_result` окажется большой словарь со служебными полями — ты не управляешь этой структурой, просто забираешь из неё нужное. Практически это используется так: сохранил результат в переменную, потом в следующей task обратился к конкретному полю и принял решение на основе него — запустить сервис, пропустить установку, вывести сообщение об ошибке:

```yaml
- name: Перезапустить только если сервис уже запущен
  ansible.builtin.systemd:
    name: nginx
    state: restarted
  when: service_result.status.ActiveState == "active"
```

`set_fact` — это личный блокнот. Ты вручную создаёшь чистую переменную и пишешь туда только то, что сам хочешь — текст, число или конкретный кусочек из другого словаря:

```yaml
- name: Создать свою чистую переменную
  ansible.builtin.set_fact:
    service_status: "active"  # ты сам придумал имя и сам написал значение
```

На практике они часто работают вместе: сначала `register` получает сырой отчёт, потом `set_fact` вытаскивает из него нужное поле и кладёт в читаемую переменную:

```yaml
- name: Получить версию установленного пакета
  ansible.builtin.command: dpkg -l nginx
  register: pkg_version_raw

# pkg_version_raw.stdout = "2.3.1" — но это поле внутри большого словаря
# Вытаскиваем только нужную строку в чистую переменную:

- name: Сохранить версию в удобную переменную
  ansible.builtin.set_fact:
    pkg_version: "{{ pkg_version_raw.stdout }}"

# Теперь везде используем pkg_version вместо pkg_version_raw.stdout
- name: Показать версию
  ansible.builtin.debug:
    msg: "Установлена версия {{ pkg_version }}"
```

## 5. Магические переменные — `hostvars`, `groups`, `group_names`, `inventory_hostname`

Обычные переменные ты объявляешь сам — в инвентаре, плейбуке или через `set_fact`. Магические переменные — это зарезервированные имена, которые **Ansible заполняет автоматически на основе инвентаря и собранных фактов**. Тебе не нужно их объявлять — достаточно просто использовать. Они дают доступ к информации о всей инфраструктуре: в каких группах состоит хост, какие хосты есть в инвентаре, какие у них переменные и факты.

### 5.1 `hostvars` — доступ к данным соседних хостов

Обычно Ansible в момент выполнения таски «изолирован» и видит переменные только того хоста, на котором таска выполняется в данный момент. `hostvars` — это глобальный словарь, который ломает эту изоляцию: в начале плейбука модуль `setup` автоматически собирает факты со всех активных хостов и складывает их в этот общий архив. В результате из любой таски можно легко «подглядеть» переменные или факты любого соседа по инвентарю через конструкцию `hostvars['имя_хоста']`.

#### Синтаксис

Обратиться к хосту можно двумя способами. Способ с квадратными скобками безопаснее, если в имени хоста есть дефисы:

```yaml
# Вариант 1: через квадратные скобки (рекомендуется)
{{ hostvars['host-01']['ansible_default_ipv4']['address'] }}

# Вариант 2: через точку
{{ hostvars['host-01'].ansible_default_ipv4.address }}
```

#### Полный разбор: зачем это нужно и почему без hostvars не обойтись

**Задача:** на сервере мониторинга `mon-01` создать конфиг, в котором перечислены IP-адреса серверов `web-01` и `web-02`.

**Инвентарь:**

```yaml
all:
  children:
    web_servers:
      hosts:
        web-01:
        web-02:
    monitoring:
      hosts:
        mon-01:
```

IP-адресов веб-серверов в инвентаре нет — они получаются по DHCP, известны только имена. Подключается Ansible по этим именам: `web-01` должно резолвиться в IP на уровне DNS или `/etc/hosts` управляющей машины. DNS знает как *подключиться*, но плейбуку для конфига нужен фактический IP интерфейса — его и достаёт `setup` в факты.

**Плейбук из двух play:**

```yaml
# Play 1: цель — только собрать факты с веб-серверов.
# Tasks не нужны, gather_facts отработает сам.
- name: Собрать факты со всех веб-серверов
  hosts: web_servers
  gather_facts: true

# Play 2: работаем ТОЛЬКО на сервере мониторинга
- name: Настроить мониторинг
  hosts: monitoring
  tasks:
    - name: Сгенерировать конфиг
      ansible.builtin.template:
        src: prometheus.yml.j2
        dest: /etc/prometheus/prometheus.yml
```

**Шаблон `prometheus.yml.j2`:**

```jinja2
targets:
{% for host in groups['web_servers'] %}
  - {{ hostvars[host].ansible_default_ipv4.address }}:9100
{% endfor %}
```

**Результат на `mon-01`:**

```
targets:
  - 192.168.1.101:9100
  - 192.168.1.102:9100
```

**Что происходит пошагово:**

**Шаг 1. Запускается play 1** (`hosts: web_servers`). Ansible подключается к `web-01` и `web-02`, модуль `setup` собирает их факты. Теперь Ansible знает: у `web-01` адрес `192.168.1.101`, у `web-02` — `192.168.1.102`. Эти данные лежат в памяти Ansible — в `hostvars['web-01']` и `hostvars['web-02']`.

**Шаг 2. Запускается play 2** (`hosts: monitoring`). Ansible подключается к `mon-01`. С этого момента всё происходит **только на mon-01** — веб-серверы больше не трогаются.

**Шаг 3. Выполняется task с template.** Шаблон рендерится в контексте хоста `mon-01`. Что доступно в этом контексте:

- `ansible_default_ipv4.address` → IP самого `mon-01`. Не то, что нужно.
- Переменные инвентаря `mon-01` → там нет чужих IP.
- **`hostvars`** → а вот тут лежит всё, что собрано на шаге 1.

**Шаг 4.** Шаблон делает `hostvars[host].ansible_default_ipv4.address` для каждого хоста из группы → получает `192.168.1.101` и `192.168.1.102`. Конфиг записан.

**Почему без `hostvars` нельзя.** На шаге 3 ты стоишь на `mon-01`. Все обычные пути ведут к данным самого `mon-01`. Данные `web-01` физически есть в памяти Ansible (собраны на шаге 1), но единственная дверь к ним из чужого контекста — словарь `hostvars`. Других механизмов «дай мне факт другого хоста» в Ansible не существует.

**Альтернатива без `hostvars`** — прописать IP веб-серверов руками: в переменных, в шаблоне, где угодно. Работает, пока IP не поменялся и пока серверов три, а не тридцать.

#### Важный момент

`hostvars` содержит факты (IP, ОС, диски) только тех хостов, до которых Ansible уже дотянулся в текущем плейбуке и выполнил для них `gather_facts`. Если хост просто числится в инвентаре, но в play не участвует — из `hostvars` можно достать только его переменные инвентаря, но не технические факты.

#### Отличие от `ansible_facts`

| | `ansible_facts` | `hostvars` |
|---|---|---|
| Что внутри | Технические данные только текущего хоста (ОС, IP, память) | Переменные и факты любого хоста из инвентаря |
| Откуда берётся | Собирается автоматически при `gather_facts` | Формируется из файлов инвентаря и собранных фактов |
| Когда применять | Условия по ОС, архитектуре, железу | Генерация общих конфигов, передача IP-адресов между хостами |

---

### 5.2 `groups` — списки хостов по группам

`groups` — это встроенная карта всего инвентаря. Словарь, где ключ — имя группы, значение — список хостов, которые в неё входят.

`groups['all']` — особенная встроенная группа, в ней автоматически лежат все хосты из инвентаря. Но обращаться можно к любой группе:

```yaml
groups['web_servers']   # только веб-серверы
groups['db_servers']       # только серверы БД
groups['all']              # вообще все хосты
```

**Зачем это нужно**

Главная цель `groups` — автоматизировать связи между серверами. Она идеальна для генерации общих конфигов (Nginx, Prometheus, Firewall, бэкапы, сбор логов), где один сервер должен знать адреса целой пачки других хостов.

Вместо того чтобы вручную копировать 150 строк с IP-адресами в конфиг мониторинга — берёшь готовый список из `groups` и запускаешь по нему цикл.

**Как это работает в связке с `hostvars`**

Сама по себе `groups` содержит только текстовые имена хостов. Чтобы превратить эти имена в реальные данные (например, IP-адреса), `groups` используют в связке с `hostvars` — перебираешь имена из группы циклом, а затем залезаешь в факты каждого хоста:

```jinja2
{# Динамически собираем конфиг мониторинга для всех хостов из группы web_servers #}
{% for node in groups['web_servers'] %}
Target_Name: {{ node }} -> Target_IP: {{ hostvars[node].ansible_default_ipv4.address }}
{% endfor %}
```

**В чём профит:**

- **Принцип единой точки правды.** Хост вносится один раз в инвентарь. Без этого пришлось бы прописывать те же 150 хостов в 5–10 разных местах: мониторинг, сборщик логов, правила Firewall, бэкапы. Со связкой `groups` + `hostvars` Ansible сам разнесёт их по всем нужным конфигам.
- **Масштабируемость.** Если завтра в группу `web_servers` добавится ещё 100 хостов — шаблон сам автоматически развернёт их во всех целевых конфигах.

---

### 5.3 `group_names` — списки групп текущего хоста

`group_names` — это простой список строк, в котором лежат имена всех групп, в которые входит текущий хост в данный момент.

Разница с `groups` простая. `groups` — это про **весь инвентарь**: «какие хосты входят в группу X», взгляд снаружи на структуру. `group_names` — это взгляд **изнутри хоста**: «в каких группах состою я сам». Task выполняется на хосте, и хост как бы спрашивает про себя.

Конкретика. Инвентарь:

```yaml
all:
  children:
    web_servers:
      hosts:
        web-01:
        web-02:
    testing:
      hosts:
        web-02:      # web-02 состоит в ДВУХ группах
```

Когда task выполняется на `web-01`, `group_names` = `['web_servers']`.
Когда на `web-02` — `group_names` = `['web_servers', 'testing']`.

Практика — один плейбук на всех, но одна task только для тестовых:

```yaml
- name: Включить отладочные логи
  ansible.builtin.command: /opt/enable_debug.sh
  when: "'testing' in group_names"
```

Плейбук прогоняется по всем хостам группы `web_servers`. На `web-01` условие ложно — task пропущена. На `web-02` истинно — выполнена. Без `group_names` пришлось бы писать два плейбука или вести отдельную переменную «это тестовый хост» в `host_vars` каждого хоста.

**В чём профит:**

- **Чистый код.** Вся логика настройки (и тестовых, и боевых серверов) управляется в одном месте.
- **Гибкость.** Один и тот же хост может одновременно находиться в группах `web_servers`, `moscow_region` и `testing`. С помощью `group_names` можно точечно включать нужные настройки для каждой локации или окружения.

---

### 5.4 `inventory_hostname` — имя текущего хоста из инвентаря

`inventory_hostname` — это строка с именем хоста именно так, как оно записано в инвентаре. Не DNS-имя, не результат команды `hostname` на сервере — а буквально то, что написано в `hosts.yml`.

Когда в task нужно сослаться на имя текущего хоста — для генерации уникальных путей, имён файлов, логов или конфигов:

```yaml
- name: Создать лог-файл с именем хоста
  ansible.builtin.file:
    path: "/var/log/ansible/{{ inventory_hostname }}.log"
    state: touch
```

Если в инвентаре хост называется `web-01`, на сервере появится файл:

```
/var/log/ansible/web-01.log
```

`inventory_hostname` — имя из инвентаря. `ansible_hostname` — факт. Они могут не совпадать.

## 6. Приоритет переменных

Когда одна и та же переменная объявлена в разных местах, Ansible не паникует, а выбирает победителя по строгой иерархии. Из 22 официальных уровней приоритета на практике важны всего 4 логические группы — от самой слабой к самой сильной.

**Группа 1 — Умолчания** (самый слабый уровень)

Сюда складывают то, что должно работать «по дефолту», если никто не попросил иначе.

- `defaults/main.yml` внутри роли — абсолютный аутсайдер, перебивается вообще чем угодно
- `group_vars/all` — глобальные настройки для всего инвентаря сразу

**Группа 2 — Контекст инфраструктуры** (инвентарь)

Переменные привязаны к конкретному железу или локации.

- `group_vars/<имя_группы>` — настройки для конкретной группы хостов
- `host_vars/<имя_хоста>` — персональные настройки конкретного сервера, всегда перекрывают настройки группы

**Группа 3 — Логика автоматизации** (код и рантайм)

То, что написано внутри самого плейбука или вычисляется прямо во время его работы. Код всегда важнее настроек инвентаря.

- `vars` и `vars_files` в плейбуке
- `vars/main.yml` внутри роли — жёстко зашитые переменные роли, которые изменять не предполагается
- `set_fact` / `register` — динамические переменные, созданные прямо в процессе выполнения тасок, перебивают любую статику из файлов

**Группа 4 — Ядерный удар** (абсолютный финал)

Флаг `-e` при запуске команды. Не может быть перебит ничем в коде. Вообще ничем.

```bash
# Переопределить абсолютно всё «на лету» прямо из консоли:
ansible-playbook setup.yml -e "app_version=3.2.0"
```

### Золотые правила приоритетов

**Хост бьёт группу** (`host_vars` > `group_vars`)

Если в `group_vars/web_servers.yml` написано `app_version: "2.3.1"`, а в `host_vars/web-01.yml` написано `app_version: "2.2.0"` — для `web-01` победит `2.2.0`.

**Плейбук бьёт инвентарь** (`vars` в play > `host_vars`)

Переменные плейбука важнее, чем данные инвентаря. Это позволяет коду диктовать свои условия, игнорируя то, что зашито в файлах хостов.

**Динамика бьёт статику** (`set_fact` > `vars`)

Если переменная вычислена на лету через `set_fact`, она мгновенно стирает старое значение, заданное статически в плейбуке. Это мощно, но коварно: если дебаг показывает странное значение — ищи скрытый `set_fact` в тасках.

### Типичная ошибка: «Я же поменял в group_vars, почему не работает?»

Самый частый случай: переменная изменена в `group_vars`, а Ansible упорно применяет старое значение.

Причина: переменная перехвачена выше по цепочке приоритетов — скорее всего, она забыта в `host_vars` конкретного сервера или жёстко прописана в `vars` самого плейбука.

Как найти виновника — вывести значение переменной во время выполнения:

```yaml
- name: Проверить текущее значение переменной
  ansible.builtin.debug:
    var: app_version
```

Или посмотреть финальный склеенный результат для конкретного хоста ещё до запуска плейбука:

```bash
ansible-inventory --host web-01 --yaml
```

Эта команда покажет финальный список переменных, который долетает до хоста из инвентаря.
