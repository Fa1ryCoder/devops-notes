# 3.5 Git – Ветки – Перенос веток «вручную»

## 1. Сценарий проблемы

Вы работаете в ветке `master` и по ошибке сделали в ней два коммита с исправлением багов — они должны были попасть в отдельную ветку `fix`.

```bash
$ git log --oneline
bb41668 Fix session timeout
34012f0 Fix null check on login
0522437 Add login endpoint
96ad338 Add user registration
```

Два нижних коммита — стабильное состояние `master`, каким оно должно оставаться. Два верхних — исправления багов, которым место в `fix`. В самом логе это не видно: `git log --oneline` без дополнительных флагов не подписывает коммиты именами веток, а `fix` на этот момент ещё не существует. Проверить, куда именно указывает ветка, можно командой `git branch -v`.

Эти изменения уже зафиксированы в истории, и переключением ветки их не перенести: коммит принадлежит той ветке, в которой был сделан, и продолжает ей принадлежать, пока указатель ветки не передвинут явно.

Задача — передвинуть сами указатели: `master` должен вернуться на коммит `0522437`, а `fix` — указывать на `bb41668`, сохранив обе правки.

## 2. Способ 1: `git branch -f`

**Сохранение текущей работы.** Прежде чем трогать `master`, нужно сохранить уже сделанные коммиты — создать ветку `fix` на том же коммите, где сейчас стоит `master`. Создание ветки — это запись нового файла-ссылки с текущим хешем: она не двигает `HEAD` и не переключает никуда. Дальше, не уходя с `master`, попробуем сразу вернуть её на `0522437` — может показаться, что раз работа уже сохранена в `fix`, ничего не мешает:

```bash
$ git branch fix
$ git branch -v
  fix    bb41668 Fix session timeout
* master bb41668 Fix session timeout
$ git branch -f master 0522437
fatal: cannot force update the branch 'master' used by worktree at '/home/user/project'
```

**Ограничение при переносе текущей ветки.** Звёздочка в выводе `git branch -v` выше стоит у `master` — это та ветка, на которой мы всё ещё стоим, и именно её мы только что пытались принудительно подвинуть. `git branch -f` перезаписывает только хеш в файле самой ветки в `.git/refs/heads/` — рабочую директорию и индекс она вообще не трогает. Если бы Git разрешил эту операцию прямо на `master`, ссылка `master` сдвинулась бы на `0522437`, а файлы в рабочей директории и индекс так и остались бы в состоянии `bb41668`. Файл `HEAD` при этом не меняется — он как был `ref: refs/heads/master`, так и остаётся, — но коммит, на который он в итоге указывает через эту ссылку, поменялся бы автоматически вслед за `master`. Расхождение — между этим итоговым коммитом (`0522437`) и тем, что реально лежит на диске (`bb41668`). Чтобы не допустить такого расхождения, Git запрещает принудительно двигать ветку, на которой вы сейчас стоите.

**Перенос после переключения.** Решение — уйти с `master` перед переносом. Поскольку `fix` сейчас указывает на тот же коммит, переключение не меняет ни одного файла:

```bash
$ git switch fix
Switched to branch 'fix'
$ git branch -f master 0522437
$ git branch -v
* fix    bb41668 Fix session timeout
  master 0522437 Add login endpoint
```

`fix` сохранила обе правки, `master` вернулась к стабильному состоянию.

## 3. Способ 2: `git switch -C`

Флаг `-C` (`--force-create`) у `git switch` объединяет создание или сброс ветки с переключением на неё в одной команде. Если ветки с указанным именем ещё нет — `-C` ведёт себя как обычный `-c`, создавая её на нужном коммите. Если ветка уже существует — `-C` переставляет её на этот коммит и переключается на неё, независимо от того, куда она указывала раньше.

Ключевое отличие от `git branch -f`: `-C` может переставить ветку, на которой вы сейчас стоите. Дело в том, что `switch` — команда, которая отвечает не только за сам указатель, но и за синхронное обновление рабочей директории и индекса под новый коммит. Расхождение, из-за которого `git branch -f` отказывала в первом способе, здесь просто не возникает — всё обновляется одним действием.

На том же примере: `fix` создаётся точно так же, а `master` переносится назад одной командой, без ухода с неё:

```bash
$ git branch fix
$ git switch -C master 0522437
Reset branch 'master'
$ cat auth.py
def register_user(): pass
def login(): pass
$ git branch -v
  fix    bb41668 Fix session timeout
* master 0522437 Add login endpoint
```

Обратите внимание на сообщение — `Reset branch`, а не `Switched to a new branch`: Git отдельно отмечает, что ветка уже существовала и была переставлена, а не создана заново. `auth.py` при этом откатился к состоянию `0522437` по-настоящему, на уровне файла, а не только на уровне ссылки — рабочая директория обновилась так же, как при обычном переключении.

Результат идентичен способу 1, но команд на одну меньше, и не приходится временно уходить на `fix`.

## 4. Ветки как ссылки на коммит

Технически ветка — это файл в `.git/refs/heads/`, хранящий ровно один идентификатор коммита и ничего больше.

Из этого следует, что Git принимает имя ветки везде, где ожидается коммит — включая запись вроде `fix~2`, где `fix` — обычное имя ветки, а `~2` дописано к нему и значит «на 2 коммита раньше». Сначала имя превращается в хеш, а дальше команда работает уже с ним — откуда этот хеш взялся, ей неважно.

```bash
$ git branch -f master fix~2
```

Эта команда переставит `master` ровно на тот же коммит `0522437`, что и прямое указание хеша.

Тот же механизм применим не только к исправлению коммитов не в той ветке — он пригодится в любой ситуации, где ветку нужно принудительно поставить на конкретный коммит. Например, `git switch -C main origin/main` жёстко подтягивает локальную `main` к состоянию на сервере, отбрасывая локальные коммиты, — тем же способом, каким выше был переставлен `master`.

## 5. Диагностика: что где лежит

`git branch -v`, который уже встречался в примерах выше, быстро показывает, на каком коммите стоит каждая ветка, но не показывает, как ветки соотносятся друг с другом по истории.

**`git log --oneline --graph --decorate --all` — вся история сразу, с подписанными ветками.** `--decorate` показывает прямо в логе, какие ветки и `HEAD` сейчас указывают на каждый коммит — то, чего не хватает обычному `git log --oneline`. `--all` подключает все ветки, а не только текущую. На результате способа 2 это выглядит так:

```bash
$ git log --oneline --graph --decorate --all
* bb41668 (fix) Fix session timeout
* 34012f0 Fix null check on login
* 0522437 (HEAD -> master) Add login endpoint
* 96ad338 Add user registration
```

Линия одна: `fix` просто на два коммита дальше `master` по той же истории. Оба фикса — это то, что есть в `fix`, но чего уже нет в `master`. Без `HEAD` в этом выводе видно, где какая ветка стоит, но не видно, где физически находитесь вы сами, — `HEAD` в примере выше отмечает именно это: не просто карту веток, а вашу точку на ней.

**`git branch --contains <коммит>` — обратный вопрос: какой ветке принадлежит конкретный коммит.** Принимает хеш или относительную ссылку:

```bash
$ git branch --contains 0522437
  fix
* master
$ git branch --contains bb41668
  fix
```

`0522437` — общий коммит: до него `master` и `fix` шли одним путём, поэтому в списке обе ветки. `bb41668` существует только в истории `fix` — `master` до него уже не дотягивается.

**Общий порядок действий**, если обнаружили, что накосячили не в той ветке:

1. `git log --oneline --graph --decorate --all` или `git branch -v` — понять, что где лежит сейчас.
2. Найти хеш нужного коммита-цели: явно или относительной ссылкой (`fix~2`, `HEAD~1`).
3. Сохранить то, что нельзя терять, — новой веткой.
4. Переставить нужную ветку на нужный коммит: `git branch -f`, если вы не на ней, `git switch -C`, если на ней.
5. Снова `git branch -v` — убедиться, что легло, как задумано.
