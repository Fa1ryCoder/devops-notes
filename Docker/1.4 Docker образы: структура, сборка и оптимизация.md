# 1.4 Образы: из чего состоят, как собираются и оптимизируются

В 1.2 и 1.3 разобрали, что происходит с уже существующим образом: как он запускается в контейнер через dockerd, containerd и runc, и как устроен его жизненный цикл. Здесь — что происходит раньше: из чего образ состоит и как он собирается.

## Контекст сборки

Docker остаётся клиент-серверной системой и на этапе сборки: `docker build` не читает Dockerfile локально и не выполняет инструкции силами CLI. CLI упаковывает указанную директорию (контекст сборки) в tar-архив и отправляет его демону — тому самому dockerd, который может работать на другой машине, в VM Docker Desktop или на удалённом buildx-билдере. Именно демон, точнее BuildKit внутри него, читает Dockerfile и выполняет инструкции.

Отсюда прямое следствие: скопировать в образ можно только то, что физически лежит внутри контекста. `COPY ../shared/lib.so .` не сработает, даже если файл существует на диске: путь выше контекста демону просто не передаётся.

Второе следствие — цена лишних файлов в контексте. Каждый `docker build` заново упаковывает и передаёт весь контекст целиком. Если в директории лежат `.git`, `node_modules`, старые бинарники или логи, они уходят демону при каждой сборке, даже если ни одна инструкция их не использует. Для этого существует `.dockerignore`, синтаксис тот же, что у `.gitignore`, применяется CLI ещё до формирования архива:

```
.git
node_modules
**/__pycache__
*.log
.env
```

Файлы с секретами вроде `.env` стоит держать в `.dockerignore` не на всякий случай, а обязательно: случайный `COPY . .` утащит их прямо в слой образа, откуда их потом непросто убрать (см. раздел про кэш ниже).

## Слои и метаданные образа

`RUN`, `COPY` и `ADD` создают слой всегда — в этом их смысл, каждая пишет diff (upperdir) поверх предыдущего слоя. `ENV`, `LABEL`, `EXPOSE`, `USER` и `ARG` слоя не создают: они не трогают файловую систему, а меняют метаданные образа — переменные окружения по умолчанию, метки, пользователя, открытые порты.

`WORKDIR` одновременно влияет на конфигурацию образа и, при необходимости, на его файловую систему. Установка `/app` как рабочей директории записывается в метаданные образа. Если `/app` ещё не существует в текущем состоянии файловой системы, Docker создаёт этот каталог, что уже является изменением файловой системы. Если каталог уже существует, например был создан предыдущим `RUN mkdir /app` или присутствует в базовом образе, создавать его повторно не требуется.

При этом не следует считать, что каждый `WORKDIR` автоматически создаёт отдельный слой файловой системы. Важнее разделять два понятия: `WORKDIR` задаёт метаданные (`WorkingDir`), а создание отсутствующей директории является изменением файловой системы, которое должно попасть в итоговую файловую систему образа.

Практический вывод: сколько угодно `ENV`/`LABEL` не раздувают образ, а вот каждый `RUN`/`COPY`/`ADD` — да, даже если следующий слой что-то удаляет. `WORKDIR` в этом смысле пограничный случай. Проверить вклад каждой инструкции в размер можно прямо на своей системе командой `docker history <образ>`.

### ARG vs ENV

`ARG` и `ENV` — переменные для разных этапов жизни образа.

`ARG` — переменная сборки: существует только во время `docker build`, параметризует сам процесс сборки:

```dockerfile
ARG NODE_VERSION=20
FROM node:${NODE_VERSION}-slim
```

Новое значение передаётся флагом: `docker build --build-arg NODE_VERSION=22 .`. Сама по себе переменной окружения работающего контейнера `ARG` не становится.

`ENV` — переменная окружения образа и контейнера: значение сохраняется в конфиге образа и передаётся процессам контейнера:

```dockerfile
ENV APP_ENV=production
```

Значение можно переопределить и без пересборки, флагом `-e`: `docker run -e APP_ENV=staging image`.

Если значение нужно и на сборке, и внутри работающего контейнера, `ARG` явно передаётся в `ENV`:

```dockerfile
ARG APP_VERSION=1.0.0
ENV APP_VERSION=${APP_VERSION}
```

Тогда `docker build --build-arg APP_VERSION=2.0.0 .` даст образ, где `APP_VERSION=2.0.0` войдёт и в конфиг, и в окружение контейнера при запуске.

Несколько нюансов стоит держать в голове:

- **Переопределение.** `ARG` можно поменять только на этапе сборки, флагом `--build-arg`; готовый образ уже не тронуть. `ENV` можно переопределить и при сборке, и при запуске контейнера — флагом `-e` у `docker run`, без пересборки образа вообще.
- **Запекание в слои.** `-e` меняет то, что процесс видит через переменные окружения в момент запуска, но не то, что уже записано на диск во время сборки:

```dockerfile
ENV APP_ENV=production
RUN echo "Собрано для: $APP_ENV" > /build_info.txt
```
```bash
docker run -e APP_ENV=staging myapp env
# APP_ENV=staging — переменная окружения переопределилась

docker run -e APP_ENV=staging myapp cat /build_info.txt
# Собрано для: production — файл написан один раз при сборке
```

`/build_info.txt` содержит то значение, которое `RUN` записал во время сборки, и не пересчитывается заново при каждом запуске контейнера — в отличие от переменной окружения, которую Docker подставляет процессу заново при каждом старте. Переопределение через `-e` до содержимого файла просто не доходит.
- **Глобальный `ARG` перед `FROM`.** Объявленный до первого `FROM`, он живёт в отдельной, глобальной области видимости — доступен только для подстановки в саму строку `FROM`. Чтобы использовать то же значение внутри стадии сборки, его нужно объявить повторно уже после `FROM`:

```dockerfile
ARG NODE_VERSION=20
FROM node:${NODE_VERSION}-slim AS base
ARG NODE_VERSION
RUN echo "Собираем на Node ${NODE_VERSION}"
```

- **Сброс кэша.** Если `ARG` используется внутри инструкции, изменение его значения между сборками для кэша равносильно изменению текста самой этой инструкции:

```dockerfile
ARG APP_VERSION=1.0
RUN echo "Building ${APP_VERSION}"
```

Собрали образ с `APP_VERSION=1.0`, потом пересобрали с `docker build --build-arg APP_VERSION=2.0 .` — этот `RUN` выполнится заново, а не возьмётся из кэша, хотя сам Dockerfile не поменялся ни на строчку.

## Кэш сборки и порядок инструкций

BuildKit идёт по инструкциям сверху вниз и каждую проверяет на кэш не саму по себе, а вместе с тем, что было до неё: слой предыдущей инструкции плюс содержимое текущей — текст для `RUN`/`ENV`, хеш файлов для `COPY`/`ADD`.

Если оба совпадают с прошлой сборкой, инструкция берётся из кэша без выполнения. Если нет — выполняется заново, и это меняет входные данные для всех инструкций после неё: раз слой перед следующей инструкцией теперь другой, её кэш тоже не подходит, даже если сама она не поменялась ни на символ. Так пересборка одной инструкции тянет за собой все, что идут дальше.

Отсюда золотое правило: инструкции идут от реже меняющегося к чаще меняющемуся. Сначала системные зависимости, потом зависимости приложения по отдельно скопированному `package.json` или `requirements.txt`, и только в конце — исходный код:

```dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
```

Если поменять местами — сначала `COPY . .`, потом `pip install` — любое изменение в коде, даже комментарий, инвалидирует слой `COPY`, а вслед за ним и `pip install`. Зависимости будут переустанавливаться на каждой сборке, хотя `requirements.txt` не менялся.

Второй практический момент — объединение команд в одном `RUN`:

```dockerfile
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl ca-certificates && \
    rm -rf /var/lib/apt/lists/*
```

Если `apt-get update` вынести в отдельный `RUN`, он закэшируется как отдельный слой. Через месяц, когда потребуется добавить пакет в соседний `RUN apt-get install`, Docker переиспользует старый закэшированный `update`. Индекс пакетов при этом окажется устаревшим относительно текущего состояния репозитория, и установка может упасть с "unable to locate package" или подтянуть более старую версию, чем ожидалось.

Очистка (`rm -rf /var/lib/apt/lists/*`) обязана быть в том же `RUN`, что и установка, по той же причине, по которой слои вообще существуют: OverlayFS не умеет стирать данные из уже собранного слоя, только скрывать их whiteout-файлом в слое поверх. Байты apt-кэша при этом физически остаются в предыдущем слое, продолжают увеличивать размер образа и передаются при каждом `docker pull`.

## ENTRYPOINT, CMD и PID 1

`RUN` выполняется во время сборки и меняет сам образ: устанавливает пакеты, копирует файлы, каждая команда фиксируется в новом слое. `ENTRYPOINT` и `CMD` относятся уже к запуску контейнера — они не создают слоёв и не трогают файловую систему образа, а определяют, что выполнится при старте.

`ENTRYPOINT` определяет саму программу, которую запускает контейнер, `CMD` — её аргументы по умолчанию. При запуске оба складываются вместе:

```dockerfile
ENTRYPOINT ["python3", "app.py"]
CMD ["--port", "8080"]
```

`docker run myapp` выполнит `python3 app.py --port 8080`. Аргументы после имени образа заменяют только `CMD`, а не саму программу: `docker run myapp --port 9000` даст `python3 app.py --port 9000`.

Без `ENTRYPOINT`, если задан только `CMD`, всё иначе — его можно заменить целиком: при `CMD ["python3", "app.py"]` команда `docker run myapp bash` запустит просто `bash`, а не `python3 app.py bash`.

`ENTRYPOINT` называют фиксированным именно потому, что обычные аргументы `docker run` его не трогают. Заменить саму программу можно только отдельным флагом: `docker run --entrypoint bash myapp` — частый приём, чтобы зайти внутрь образа и посмотреть, что в нём есть, если обычный `ENTRYPOINT` не даёт получить shell.

Коротко напомню то, что уже разбирали в 1.3: как записана сама инструкция `ENTRYPOINT`/`CMD` — массивом, `["python3", "app.py"]` (exec-форма), или обычной строкой, `python3 app.py` (shell-форма) — решает, кто станет PID 1 — само приложение или обёртка `/bin/sh -c`, и от этого зависит, дойдёт ли SIGTERM от `docker stop` до приложения напрямую. **Но и exec-форма не гарантия**: ядро игнорирует необработанный SIGTERM для PID 1, если приложение не завело свой обработчик. `docker run --init` (tini) закрывает обе проблемы разом, включая сбор зомби-процессов.

Проверить, что реально является PID 1 внутри контейнера, можно без теории: `docker top <контейнер>`.

### Паттерн entrypoint.sh

Частый случай — нужна подготовка перед запуском самого приложения: проверить переменные окружения, подставить конфиг из шаблона, подождать доступности базы данных:

```bash
#!/bin/sh
set -e

until pg_isready -h "$DB_HOST" -p "$DB_PORT" > /dev/null 2>&1; do
  sleep 1
done

exec "$@"
```

```dockerfile
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
CMD ["python3", "app.py"]
```

Ключевая деталь — `exec "$@"` в конце скрипта: это встроенная команда самого shell, которая заменяет текущий процесс новым, сохраняя тот же PID, а не порождает потомка. До этой строки PID 1 — это shell, исполняющий entrypoint.sh. После неё PID 1 — уже само приложение, потому что shell как процесс перестал существовать, а не просто ушёл в фон. Поэтому сигналы доходят до приложения напрямую, ровно как в exec-форме.

Без `exec`, если оставить просто `"$@"` последней строкой, приложение запустится как дочерний процесс всё ещё живого shell — и вернётся та же проблема, что и в shell-форме.

## Многоэтапная сборка

Компиляция часто требует тяжёлого инструментария: gcc, полный JDK с Maven, компилятор Go, npm со всеми devDependencies. Приложению для работы это не нужно вообще. Если оставить это в финальном образе, в продакшен уезжает целый набор инструментов для сборки: лишние гигабайты и лишняя площадь для CVE без единой пользы во время выполнения.

Многоэтапная сборка решает это явным разделением стадий:

```dockerfile
# этап сборки
FROM golang:1.25 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app .

# финальный этап
FROM gcr.io/distroless/static-debian13:nonroot
COPY --from=builder /out/app /app
ENTRYPOINT ["/app"]
```

`COPY --from=builder` забирает из промежуточной стадии только то, что действительно нужно — в данном случае один скомпилированный бинарник. Сама стадия `builder` никуда не пушится и не сохраняется в итоговом образе, хотя и участвует в кэше сборки, так что пересборка при небольших правках кода остаётся быстрой.

Результат — образы с гигабайта до десятков мегабайт, а набор инструментов для сборки, сам по себе частый источник CVE, просто не доезжает до продакшена.

Тег `:nonroot` у distroless-образов уже включает предустановленного пользователя с UID 65532. `USER` можно вообще не писать, если этот тег уже выбран, либо прописать `USER nonroot` явно поверх базового тега без суффикса. Для Alpine или Debian slim готового пользователя нет, придётся создать самому:

```dockerfile
RUN addgroup -S app && adduser -S app -G app
USER app
```

Одна деталь, которая пригодится за пределами интервью: если планируется запуск в Kubernetes, лучше указывать числовой UID, а не имя пользователя. Часть политик безопасности читает UID напрямую из конфига образа и не всегда умеет резолвить имя через `/etc/passwd`. Особенно это важно, если финальный образ — `scratch`, где `/etc/passwd` попросту нет.
