# 2. Термины: как устроен GitLab CI/CD

Набор понятий, без которого читать и обсуждать `.gitlab-ci.yml` не получится — они всплывают в первые же минуты почти любого собеса по GitLab CI/CD. Сначала шпаргалка, потом разбор по каждому термину с деталями, которые реально пригождаются на практике.

## Шпаргалка

| Термин | Что это |
|---|---|
| `.gitlab-ci.yml` | YAML-файл в корне репозитория, описывает pipeline |
| **Pipeline** | Полный запуск конфигурации при push / MR / расписании / вручную |
| **Stage** | Логическая группа джоб (build, test, deploy). По умолчанию стадии идут строго по очереди |
| **Job** | Конкретная задача со своим `script`, принадлежит одной стадии. Джобы одной стадии выполняются параллельно |
| **Runner** | Агент, который реально выполняет джобы. GitLab-сервер — только диспетчер, сам код не исполняет |
| **Executor** | Способ, которым runner готовит окружение под джобу: shell, docker, kubernetes и др. |
| **Artifact** | Файлы — результат job'ы. Гарантированно доступны следующим стадиям этого же pipeline, видны в UI |
| **Cache** | Переиспользуемые между запусками зависимости — для ускорения, не гарантирован |
| **Variable** | Переменная окружения: predefined (от GitLab) или своя, может быть protected/masked |

## Путь от разработки до прода: пошагово

Всё держится на одной идее: **пишешь и пушишь код как обычно — а всё, что происходит дальше, делает GitLab сам** по инструкции из `.gitlab-ci.yml`. По шагам:

1. **Пишешь код локально** — в любом редакторе/IDE, обычным образом. `git clone` (один раз) или `git pull`, чтобы подтянуть свежее.
2. **`git add` → `git commit` → `git push`** — из терминала, как всегда. GitLab работает поверх обычного git, никакой особой "гитлабовской" механики коммитов нет.
3. **GitLab получает push и проверяет `.gitlab-ci.yml`** (подробнее о механике — в разделе `.gitlab-ci.yml` ниже) — если файл есть в репозитории, pipeline стартует автоматически, без каких-либо дополнительных действий с твоей стороны.
4. **GitLab раздаёт джобы Runner-у** (подробнее — в разделе Runner ниже), который прогоняет их через Executor — обычно Docker, свежий контейнер под каждую job.
5. **Стадии идут по порядку**, обычно `build → test → deploy`:
   - **build** — собрать проект: скомпилировать, собрать бинарник или Docker-образ
   - **test** — прогнать тесты, линтеры, статический анализ
   - **deploy** — выкатить результат: `kubectl apply`, `scp` на сервер, `docker-compose up`, вызов API облака
6. **Деплой в прод обычно не полностью автоматический** — стадию deploy чаще всего ограничивают через `rules` (например, только ветка `main`) и ставят `when: manual` (вручную), чтобы кто-то осознанно нажал кнопку, а не чтобы каждый push сам улетал в прод.
7. **Результат виден в UI** — статус каждой job, логи, артефакты — всё в CI/CD → Pipelines. Если что-то упало, сразу видно, на каком именно шаге.

Меняется только то, что происходит **после push**: вместо того, чтобы руками собирать, тестировать и деплоить, весь этот путь один раз прописан в `.gitlab-ci.yml`, и дальше GitLab прогоняет его сам на каждый push.

Как это укладывается в иерархию (сама структура pipeline из шага 5 выше):

```
Pipeline
 ├─ Stage: build
 │   └─ Job: build_job        → выполняет Runner (executor: docker)
 ├─ Stage: test
 │   ├─ Job: unit_tests   ┐
 │   └─ Job: lint         ┘ одна стадия → выполняются параллельно
 └─ Stage: deploy
     └─ Job: deploy_job       → стартует только после зелёного test
```

## `.gitlab-ci.yml`

Лежит в корне репозитория (путь можно сменить в Settings → CI/CD → General pipelines → Custom CI/CD configuration path, но это редкость). Триггером служит именно `push`, а не сам факт коммита: `git add` и `git commit` — чисто локальные операции, GitLab о них ничего не знает, пока изменения не отправлены. Как только push долетает до GitLab и в этой ветке есть `.gitlab-ci.yml` — стартует pipeline по его текущему содержимому. Синтаксис удобно проверять ещё до пуша через вкладку **Build → Pipeline editor**: она валидирует конфиг на лету и рисует граф пайплайна прямо в браузере, до коммита — так находишь опечатки в отступах, не дожидаясь красной джобы.

Важно различать файл и pipeline. `.gitlab-ci.yml` — статичное описание, рецепт: сам по себе он ничего не исполняет, просто лежит в репозитории. Создаётся он один раз и дальше просто **редактируется**, как любой другой файл проекта (`README.md`, `Dockerfile`) — никто не пересоздаёт его под каждый запуск. Pipeline, наоборот, каждый раз новый: это конкретный запуск по текущей версии рецепта. Один файл — сколько угодно пайплайнов по нему, один за другим.

При этом файл описывает не просто линейный список команд, а сразу две вещи: **что делать** (стадии и джобы со своим `script:` — собрать, протестировать, задеплоить) и **при каком условии это делать** (через `rules:` — например, деплой только вручную и только на ветке `main`). GitLab сначала разбирает эту структуру и условия, решает, что и когда запускать, и только потом выполняет команды внутри `script:`.

Редактируешь файл в тех же случаях, что и любой другой конфиг проекта: поменялся сам процесс (новый шаг, другая версия образа, другая команда сборки), поменялись условия запуска (деплой был автоматический, стал `when: manual`), что-то сломалось (неверный путь в `artifacts`, отсутствующая зависимость) или проект вырос и конфиг дорабатывается под это (новое окружение, распараллеливание через `needs`).

Отсюда практическое следствие, которое иногда спрашивают на собесе: что будет, если поменять `.gitlab-ci.yml` уже после того, как pipeline стартовал? Ответ — ничего, текущий запуск доработает по той версии файла, что была на момент его старта. Новая версия применится только к следующему pipeline, который запустится после нового коммита. Каждый pipeline как бы "замораживает" свою версию конфига на момент запуска.

Редактировать файл можно двумя способами: как обычный файл через `git add / commit / push` из терминала, либо прямо в GitLab через **Build → Pipeline editor** — второй вариант обычно удобнее, потому что там сразу видна валидация и граф пайплайна.

## Pipeline

Полный прогон всей конфигурации — от первой до последней стадии. Триггерится по-разному:
- push в ветку — обычный **branch pipeline**;
- открытие или обновление Merge Request — отдельный тип, **merge request pipeline**;
- по расписанию — **Build → Pipeline schedules** в проекте, задаёшь интервал обычным cron-синтаксисом;
- вручную — кнопкой в UI или через API.

Статусы общие для pipeline и job: `pending`, `running`, `success`, `failed`, `canceled`, `skipped`, `manual`. Статус самого pipeline складывается из статусов всех его джоб: упала хоть одна обязательная джоба — весь pipeline `failed`.

Смотреть сами пайплайны — в **Build → Pipelines**: список всех запусков с датой, веткой/коммитом, автором и статусом. Клик по конкретному — открывается граф стадий (`build → test → deploy` слева направо) с джобами внутри каждой; клик по джобе — живой лог, реальный вывод команд из `script:` построчно. Статус виден и рядом с коммитом или Merge Request'ом — просто иконка (зелёная галка / красный крестик / жёлтый кружок), без захода в отдельный раздел.

## Stage

По умолчанию стадии идут строго последовательно: следующая не начнётся, пока все джобы предыдущей не завершатся успешно. Джобы внутри одной стадии — параллельно, насколько хватает свободных runner-ов. Если `stages:` вообще не объявлен, GitLab берёт свой набор по умолчанию: `.pre`, `build`, `test`, `deploy`, `.post`.

## Job

Обязательное поле — `script`. Джоба живёт в одной стадии — задаётся ключом `stage:` (например, `stage: test`). Если этот ключ вообще не указать, GitLab по умолчанию отправит джобу в стадию `test`. Из ключей, которые реально используются в самой джобе каждый день: `image` (образ для docker executor), `tags` (на какой runner отправить джобу), `rules` (условия запуска), `before_script`/`after_script`, `allow_failure`, `when`, `retry`, `timeout`.

## Runner

Агент — VM, контейнер или под в кластере, — который реально забирает джобу из очереди и выполняет её. GitLab-сервер код не исполняет никогда, он только диспетчерит: раздаёт задачи и принимает результат.

По области видимости runner бывает трёх типов — отличаются они тем, скольким проектам доступны:

- **instance** — доступен всем проектам сразу на всём GitLab (на всём развёрнутом сервере целиком). Раньше назывался shared.
- **group** — доступен только проектам внутри одной группы (например, всем репозиториям твоей команды).
- **project** — закреплён за одним конкретным проектом, больше никто им не пользуется. Раньше назывался specific.

Это те самые вкладки Assigned/Other available/Group/Instance, которые ты уже видел в Settings → CI/CD → Runners.

Механика простая: runner не ждёт, пока GitLab ему что-то пришлёт — он сам постоянно опрашивает сервер ("есть для меня работа?"), и как только видит подходящую джобу (по тегам и своему типу), забирает её и выполняет. Поэтому runner может физически находиться где угодно — на твоём ноутбуке, в отдельном облаке, на выделенном сервере — лишь бы у него был доступ в интернет до GitLab. Один и тот же runner может обслуживать сразу несколько проектов, если это group или instance runner.

## Executor

Executor — это способ, которым runner готовит окружение для выполнения джобы: где физически выполняются команды из `script:` и насколько это окружение изолировано.

Три варианта, которые должны отскакивать от зубов:
- **shell** — джоба выполняется прямо на хосте runner-а, без изоляции. Быстро, но окружения разных джоб могут "протекать" друг в друга.
- **docker** — под каждую джобу поднимается свежий контейнер из образа в `image:`. Самый частый вариант в реальных проектах и самый частый вопрос на собесе.
- **kubernetes** — джоба выполняется как под в k8s-кластере, используется, когда сам runner живёт в кластере.

Executor выбирается прямо во время регистрации runner-а — тем самым флагом `--executor "docker"`, который ты указывал при установке раннера в команде `gitlab-runner register`. GitLab-runner сам сохраняет этот выбор в `config.toml` (локальный файл на машине/в контейнере, где живёт runner, обычно `/etc/gitlab-runner/config.toml`) — руками туда лезть не нужно, разве что захочешь поменять executor уже после регистрации. `image:` в job лишь говорит, какой конкретно образ подтянуть — но это работает только если runner уже настроен на docker или kubernetes executor.

## Artifact

Artifact — это файлы-результат работы джобы: собранный билд, скомпилированный бинарник, отчёт тестов, лог, скриншот — что угодно, что джоба произвела и что должно остаться доступным после её завершения. Джоба явно объявляет, что именно сохранить, через `artifacts: paths:` (например, `paths: [dist/]`, если это папка со сборкой). GitLab гарантированно сохраняет эти файлы у себя и автоматически подтягивает их в джобы следующих стадий — пробрасывать руками ничего не нужно. Их же можно скачать через UI: Pipelines → нужная джоба → Browse/Download — удобно, когда хочется глазами посмотреть на билд или отчёт тестов.

## Cache

Cache — это сохранённые файлы, обычно зависимости проекта (библиотеки, пакеты — то, что устанавливается перед сборкой). Их можно переиспользовать между разными запусками pipeline, чтобы не устанавливать одно и то же с нуля каждый раз — это чисто про ускорение сборки.

Как это работает: после выполнения джобы GitLab сохраняет указанную папку с зависимостями на стороне runner-а, а в следующем pipeline (обычно на той же ветке) джоба сначала пытается восстановить её из сохранённого кэша — и только если её там нет, ставит зависимости с нуля.

Хранится cache на диске самого runner-а — и в отличие от артефакта, гарантий тут никаких. GitLab совершенно нормально относится к ситуации "кэша не оказалось", поэтому любой скрипт установки зависимостей обязан спокойно работать и с нуля, а не ломаться без готовой папки.

## Cache vs Artifacts — вопрос, который спросят почти наверняка

Путают их не просто так — оба про "не считать всё заново". Но назначение прямо противоположное: cache — это про ускорение (необязателен, может отсутствовать), artifact — про результат работы (обязателен, гарантированно сохраняется).

Один job часто использует оба сразу — разница нагляднее всего именно в связке:

```yaml
build_job:
  stage: build
  cache:
    key: $CI_COMMIT_REF_SLUG
    paths:
      - deps/
  script:
    - ./install-deps.sh
    - ./build.sh
  artifacts:
    paths:
      - dist/
    expire_in: 1 week
```

`./install-deps.sh` отработает быстрее, если папка `deps/` найдётся в кэше — а если не найдётся, просто установит всё заново, ничего не сломается. А вот `dist/` — результат сборки, который обязан дойти до стадии `deploy`, тут уже без вариантов.

Формулировка для собеса одной фразой: *cache ускоряет, но не обязателен; artifact — результат job'ы, который обязан дойти до следующей стадии.*

## Variable

**Predefined** (заранее определённые) — те, что GitLab прокидывает сам, без объявления: `CI_COMMIT_BRANCH`, `CI_COMMIT_SHORT_SHA`, `CI_PROJECT_NAME`, `CI_PIPELINE_ID`, `CI_JOB_NAME`, тот же `CI_COMMIT_REF_SLUG` из примера с кэшем выше. Полный список — в документации GitLab, но именно эти несколько встречаются в конфигах постоянно.

**Custom** (свои, пользовательские) — задаются либо прямо в `.gitlab-ci.yml` (для несекретных значений), либо в Settings → CI/CD → Variables — туда идёт всё чувствительное: токены, пароли, ключи деплоя. Хардкодить секреты в yml-файл — плохая практика: файл лежит в репозитории и виден всем с доступом к коду.

У переменной, заданной в Settings → CI/CD → Variables, есть два параметра, про которые часто спрашивают на собесе:
- **protected** — переменная доступна только в pipeline на protected-ветках/тегах (обычно `main`); в pipeline обычной рабочей ветки (например, `feature/login-page` — незащищённой, где просто разрабатывается задача) её просто не будет;
- **masked** — значение скрывается в логах job'ы, вместо него показывается `[MASKED]`, чтобы токен случайно не утёк в консольный вывод.
