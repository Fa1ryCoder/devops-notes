Глоссарий:
    Сущности данных от самой маленькой к самой большой:
        1) Sample - точка. Самая маленькая единица данных = (timestamp, value). Это атом данных. Она состоит из timestamp, которое хранится в милисекундах и value - значение. Пример: (1770234926103, 5.1).
        2) Metric — имя измеряемого показателя. Пример: node_cpu_seconds_total
        3) Label — пара ключ=значение для фильтрации и группировки. Пример: cpu="0"
        4) Time series - временной ряд. Это комбинация: метрика + лейблы + последовательность sample'ов. Time series = {metric_name, set of labels} + [sample1, sample2, ...]. Пример:
            node_cpu_seconds_total{cpu="0", mode="idle"}:
            (1770234926103, 5.1)
            (1770234932103, 5.2)
            (1770234938103, 5.2)
        - metric_name это node_cpu_seconds_total
        - set of labels это {cpu="0", mode="idle"}
        - samples это (1770234926103, 5.1), (1770234932103, 5.2), (1770234938103, 5.2)
        То есть time series - это метрика + лейблы + её временные точки
        Важно! Если поменяется лейбл, это уже другая time series:
            node_cpu_seconds_total{cpu="1", mode="idle"}
        На этом моменте приходит ещё одно вытекающее понятие. Кардинальность (Cardinality) — это общее количество уникальных time series в системе. Каждая уникальная комбинация метрики + набора лейблов = одна time series. Высокая кардинальность — главный враг производительности Prometheus. Если у тебя метрика с лейблом user_id, а пользователей миллион — это миллион time series, и HEAD будет занимать огромное количество RAM. На собесе часто спрашивают: «Что будет, если метрика создаёт слишком много time series?» — ответ: рост потребления памяти, замедление запросов, возможный OOM.
        5) Chunk - это группа ~120 sample's одной time series. Дефолтный scrape_interval в Prometheus = 60 секунд. При 60s интервале 120 sample'ов накопятся за 2 часа (120 × 60с = 7200с = 2ч). При 15s — за 30 минут. Число 120 привязано к максимуму sample'ов в чанке, а не к конкретному интервалу. Если значение scrape interval дефолтное(60сек), то ~120 chunk. Одна series со временем состоит из цепочки chunk:
            Series A = [chunk1][chunk2][chunk3]...
        Прометей закрывает чанк по истечению ~2 часов или 120 sample's одной time series что наступит раньше.
        6) Chunk file - это файл контейнер, внутри которого лежит много chunk'ов разных series. Файл chunks не знает, какой chunk какой series принадлежит. Он просто хранит бинарные данные        
        7)Block - это директория с данными за определенный временной диапозон. Про данные имеется ввиду вот эти файлы:
        - index - это файл внутри каждого блока (block) данных Prometheus, который реализует инвертированный индекс (inverted index) для быстрого поиска временных рядов (series) по лейблам.
        - meta.json  - метаданные о блоке: временной диапазон, источник, версия
        - chunks/ - (поддиректория с файлами chunk)
        - tombstones - (удалённые данные, если есть)
        Цепочка:
        Sample (точка) --> Metric name + Labels = Time series --> Chunk --> Chunk file --> Index --> Block


Начнем с определения Prometheus. Что такое Prometheus?
"Prometheus" — это система мониторинга, которая собирает и хранит метрики как временные ряды, используя многомерную модель данных с labels (тегами). Она работает по pull-модели (сама опрашивает targets по http с помощью config где указаны nodes), предоставляет мощный декларативный язык запросов PromQL для агрегации и анализа, имеет встроенный механизм алертинга и активно используется в cloud-native стеках (Kubernetes)
Все равно остаются вопросы по определению. Метрика, временной ряд и т.д. Что же все это такое?

"Метрика (metrics)" - это измерение какого либо параметра системы во времени. Проще: это число которое, Prometheus регулярно записывает. Например:
    Загрузка CPU = 72%
    Свободная память = 1.3 GB
    Количество HTTP-запросов = 152
    температура сервера = 45°C
Важно отметить что Prometheus оперирует сырыми числами(row data) и не хранит информацию о единицах измерения. Чтобы превратить его в осмысленную метрику (например, в процент загрузки или скорость запросов в секунду), данные необходимо обработать с помощью PromQL(Это уже задача специалиста кто создает запросы). Изначально данные будут выглядить вот так: 0.72 (ratio), 1395864371 (bytes), 1003152, 45000.
В Prometheus метрика выглядит примерно так:
    node_cpu_seconds_total{cpu="0",mode="idle"} 12345.6
Здесь:
    - node_cpu_seconds_total = имя метрики
    - {cpu="0",mode="idle"} = теги (labels) - пары ключ="значение"
    - 12345.6 = значение

"Временной ряд (time series)" - это история значения метрики во времени. То есть Prometheus не просто хранит одно число. Он хранит: 
    время --> значение. 
Например:
    12:00 --> CPU = 40%
    12:01 --> CPU = 55%
    12:02 --> CPU = 72%
    12:03 --> CPU = 38%
Это и есть временной ряд. Временный ряды хранятся локально на диске, можно опционально интегрировать с удалёнными системами хранения. Он собирает данные(метрики во времени), примерно, ~2 часа и потом запечатывает в блок. Пример блока:
    /01KGPQB344WPSFXVM8F0A1XJCR/
Имя директории блока — это ULID (Universally Unique Lexicographically Sortable Identifier). В нём закодировано время создания, поэтому блоки при сортировке по имени автоматически выстраиваются хронологически.
Важно: Мы не собираем данные когда пишем, например, запрос: node_cpu_seconds_total{mode="idle"}[5m]. Мы запрашиваем собранные данные с помощью PromQL. PromQL это язык запросов, а не сбора! 

"Теги (labels)" - это пары ключ="значение", которые прикрепляются к метрике для добавления контекста. Метрики нужны для:
    Дифференциация: Позволяют отличить метрику одного сервера от другого (instance="web-01" vs instance="web-02").
    Агрегация: Позволяют посчитать общую сумму запросов по всему региону или конкретному приложению, используя фильтры в PromQL
    Динамичность: Тебе не нужно создавать метрику http_requests_total_server1, ты создаешь одну метрику http_requests_total и разделяешь данные метками.

Возьмем пример:
    http_requests_total{instance="web-01", method="GET"}
        - 1-ый ключ instance = значению "web-01", 
        - 2-ой ключ method = значению "GET". 
При конфигурировании мы можем и будем вынуждены задавать свои собственные теги и значения каждой ноде для гибкостки наших запросов. Задаются они в конфиг файле самого Prometheus в формате .yml(дефолтный путь /etc/prometheus/prometheus.yml).
Лейблы делятся на два вида:

Инструментальные — задаются в коде приложения или экспортёра (например, method="GET", status="200")
Целевые (target labels) — добавляются Prometheus при скрейпе: job, instance, а также кастомные лейблы из конфига (через labels: в scrape_configs или через relabel_configs)

Лейблы, начинающиеся с __ (двойное подчёркивание), являются служебными и удаляются после relabeling. Например, __address__ содержит адрес таргета, но в итоговую time series не попадает.

Этап №1: 
Каждые N секунд (по умолчанию 60, настраивается через scrape_interval в конфиге) Prometheus дергает http://node-exporter:9100/metrics и получает метрики с ноды со служебными лейблами (например job и instance) и кастомные лейблы из /etc/prometheus/prometheus.yml. Затем данные записываются в WAL. 

WAL (Write Ahead Log, prometheus/wal/) - это черновик страховка. Простой бинарный файл на диске куда Prometheus изначально записывает метрики. Цель простая: если сервер умрет, то при включении Prometheus восстановит те частичные данные которые он успел записать в WAL.

HEAD(prometheus/chunks_head/) - это структура данных для самых свежих, ещё не запечатанных в блок данных. Зачем она нужна? Когда мы в Grafana открываем график за последние 5 минут, Prometheus сначала лезет именно в HEAD, а не в архивные блоки.
Важный нюанс: HEAD не полностью живёт в RAM. Начиная с Prometheus 2.19+ используется механизм memory-mapped chunks (m-map):

 - In-memory часть: самые свежие sample'ы (текущий незакрытый чанк каждой series) действительно живут в оперативке. Это то, что пишется прямо сейчас
 - Memory-mapped часть: когда чанк в памяти заполняется (~120 sample'ов), он сбрасывается в файлы chunks_head/ на диск и далее читается через mmap. Операционная система сама решает, какие страницы держать в page cache

Это позволяет не держать все 2 часа данных в RAM. Prometheus потребляет оперативку пропорционально количеству активных time series, а не количеству sample'ов в HEAD.
После того как прошло 2 часа и HEAD заполнился, Prometheus берёт всё, что накопилось, упаковывает, сжимает и превращает в блок (директория вида 01KGPQB344WPSFXVM8F0A1XJCR/). После того как блок сохранён, старые сегменты WAL удаляются.

WAL Checkpoint
Параллельно с обычной работой Prometheus периодически создаёт checkpoint — сжатую версию WAL, содержащую только актуальные данные (те series, которые ещё живут в HEAD). Это ускоряет восстановление при рестарте: вместо перечитывания всех сегментов WAL, Prometheus читает последний checkpoint + сегменты после него. Файлы checkpoint'а лежат в wal/checkpoint.NNNNNN/.

prometheus/lock - этот файл гарантирует что только один экземпляр Prometheus работает с данными в один момент времени, предотвращая конфликты записи другим Prometheus. Когда Prometheus стартует создается файл lock. Если другой экземпляр начнет писать туда же то получится ошибка:
    opening storage failed: lock DB directory: resource temporarily unavailable
Другими словами файл-блокировщик который не дает записывать данные в TSDB

prometheus/queries.active - это список активных запросов которые выполняются прямо сейчас

Небольшое резюме по этому процессу:
1. При старте Prometheus создается lock + восстановление HEAD из WAL (через checkpoint, если есть)
2. Пришла метрика (scrape)
3. Добавили лейблы и записали в WAL (защита от потери данных)
4. Тут же добавили в HEAD (теперь данные доступны для запросов)
5. Прошло 2 часа, HEAD заполнился
6. HEAD сбрасывается в новый блок (упаковка, сжатие, запись index)
7. Удаляются старые сегменты WAL, создаётся новый checkpoint 
Процесс пошел по новой

Про блоки, а точнее из каких частей они состоят. 
Каждый блок состоит из 4-х ключевых частей: chunks, index, meta.json и tombstones. Они работают вместе как единая система.
/chunks/ - директория которая содержит числовые данные метрик в бинарном виде. В этой директории есть файлы вида 000001. Это не текст, а компактно сжатый поток временных рядов. 
Prometheus хранит точки не по одной, а группирует их в chunks — небольшие последовательности значений одной time series. Внутри chunk лежит последовательность пар «timestamp → value», сжатых специализированными алгоритмами:

 - Timestamps: используется double-delta encoding (delta-of-delta). Поскольку scrape происходит с фиксированным интервалом, разницы между соседними timestamp'ами почти одинаковы, и разница разниц часто равна нулю — это сжимается до 1 бита
 - Values: используется XOR-компрессия (алгоритм из Facebook Gorilla paper). Соседние значения временных рядов обычно меняются плавно, и XOR между ними содержит много нулевых бит — хранится только изменившаяся часть

Важно понимать, что файл chunks/000001 — это просто большой контейнер с данными всех time series в этом блоке. В нём нет удобной структуры для поиска по имени метрики или лейблам. Он организован по смещениям (offsets). По смещениям значит что каждый chunk - это кусок байтов:
    chunk A1 = 4096 байт
    chunk B1 = 4096 байт
    chunk C1 = 4096 байт
Тогда файл выглядит вот так:
    байты 0–4095     → chunk A1
    байты 4096–8191  → chunk B1
    байты 8192–12287 → chunk C1
Смещение (offset) = позиция в файле в байтах. То есть:
    chunk A1 → offset 0
    chunk B1 → offset 4096
    chunk C1 → offset 8192

Чтобы найти нужные данные, Prometheus должен знать, в каком месте файла лежит конкретный chunk, и эту информацию он получает из файла index.
Таким образом, chunks — это чистое хранилище значений, оптимизированное для компактности и быстрого последовательного чтения.


/index - слой поиска (Инвертированный индекс). Файл index читается с конца. Prometheus после того как определил нужный блок по временному диапазону (с помощью minTime и maxTime из meta.json), открывает index этого блока.
Подробная структура index описана ниже в этапах 2.1 (запись) и 2.2 (чтение).


/meta.json - Это метаданные блока в читаемом JSON-виде. Содержит: 

 - Он описывает временной диапазон блока (minTime и maxTime)
 - Статистику (количество series, samples и chunks)
 - Информацию о compaction(слияние блоков, если level > 1 то значит этот блок это результат обьединения нескольких мелких блоков)
 - Версию формата данных. 

Prometheus использует этот файл при старте и при выполнении запросов, чтобы быстро понять, нужен ли данный блок для конкретного временного диапазона. Например, если ты запрашиваешь данные за последние 30 минут, а блок покрывает период недельной давности, Prometheus даже не будет открывать его index и chunks.
Также meta.json содержит информацию о происхождении блока: был ли он создан напрямую из HEAD или получен в результате объединения нескольких меньших блоков. Это важно для механизма compaction и отладки. Можно сказать, что meta.json — это оглавление блока, которое позволяет быстро ориентироваться в его содержимом.

Пример meta.json:
{
    "ulid": "01KGPQB344WPSFXVM8F0A1XJCR",
    "minTime": 1770220800000,
    "maxTime": 1770228000000,
    "stats": {
        "numSamples": 5843210,
        "numSeries": 12450,
        "numChunks": 24900
    },
    "compaction": {
        "level": 1,
        "sources": ["01KGPQB344WPSFXVM8F0A1XJCR"]
    },
    "version": 1
}
Если level: 1 — блок создан из HEAD напрямую. level: 2 и выше — результат compaction.


/tombstones - это записи о данных, помеченных на удаление. Когда пользователь вызывает API удаления (POST /api/v1/admin/tsdb/delete_series), Prometheus не удаляет данные из chunks физически — это было бы слишком дорого (пришлось бы перезаписать весь chunk file). Вместо этого он записывает «надгробие» (tombstone) с информацией: какие series и за какой временной диапазон считать удалёнными.
При выполнении запросов Prometheus проверяет tombstones и пропускает помеченные данные — они «невидимы». Физическое удаление происходит позже, во время compaction: при объединении блоков Prometheus просто не переносит данные, помеченные tombstone'ами.
Если файл tombstones пуст или отсутствует — удалений не было.


Этап №2.1 Как записывается(Создается):
2.1.1) Как формируется Symbol Table в процессе работы. Когда Prometheus получает метрики и складывает их в HEAD - оперативную память(RAM), он паралельно ведет учет всех новых строк, которые встречает. Этот процесс называется интернированием строк. 
Допустим пришли первые метрики:
    http_requests_total{method="GET", status="200"} 42
    cpu_usage{core="0"} 0.45
Prometheus смотрит и видит новые строки
    - Имена метрик: http_requests_total, cpu_usage
    - Ключи меток: method, status, core
    - Значения меток: GET, 200, 0
Все эти строки он заносит во временный словарь в памяти и присваивает каждой следующий номер по порядку:

Номер:	Строка:
1	    http_requests_total
2	    cpu_usage
3	    method
4	    GET
5	    status
6	    200
7	    core
8	    0

Приходит следующая метрика:
    http_requests_total{method="POST", status="200"} 13
Prometheus проверяет каждую строку: http_requests_total — уже есть (номер 1), method — уже есть (номер 3), POST — новая строка → добавляем под номером 9, status — уже есть (номер 5), 200 — уже есть (номер 6). Обновляет таблицу дописывая :

Номер:  Строка:
9       POST

Приходит ещё одна метрика:
    go_gc_duration_seconds{quantile="0.5"} 0.00023
Новые строки: go_gc_duration_seconds, quantile, 0.5. Так же добавляются в таблицу:

Номер	Строка
...	...
10	go_gc_duration_seconds
11	quantile
12	0.5

и т.д.

По истечении ~2 часов (или при заполнении HEAD) происходит Compaction — сброс данных на диск. Допустим, набиралось 15 342 уникальных строк. Все они собраны в памяти, у каждой есть свой номер от 1 до 15 342. Когда наступает момент сброса HEAD на диск (создание блока 01KKKPJMX34CY5MDQ4YSTK1GHS), Prometheus формирует файл index. Где Symbol Table записывается в самом начале этого файла (сразу после заголовка). После того как Symbol Table записана, все остальные структуры индекса не хранят строки — они хранят только номера строк.

Пример: запись временного ряда
Ряд http_requests_total{method="GET", status="200"} кодируется не как текст, а как последовательность чисел:

[1] [3,4] [5,6]
Где:

1 — номер строки http_requests_total в Symbol Table

3,4 — номер строки method (3) и номер строки GET (4)

5,6 — номер строки status (5) и номер строки 200 (6)

Важно: при записи на диск Symbol Table сортируется в лексикографическом порядке, а номера переназначаются. Это позволяет использовать бинарный поиск при чтении.


2.1.2) Запись Series-секции в индексный файл. 
Что такое Series-секция? Это раздел файла index, в котором хранятся описания всех временных рядов, попавших в данный блок данных. Каждое описание представляет собой компактную числовую запись, полностью основанную на Symbol Table и содержащую ссылки на чанки с реальными значениями. Что же содержит запись одного временного ряда? 

Запись одного временного ряда содержит:
 1) Имя метрики и набор меток (в виде чисел-ссылок на Symbol Table)
 2) Информацию о том, где в чанках лежат данные этого ряда
Для каждого временного ряда Prometheus берет его метки и превращает их в последовательность чисел. Все строки уже имеют номера в Symbol Table, поэтому описание ряда состоит только из этих номеров.
По пункту №1, пример: Ряд http_requests_total{method="GET", status="200"}

Если в Symbol Table:

http_requests_total = 1

method = 3

GET = 4

status = 5

200 = 6

То в Series-секцию запишется последовательность: [1, 3, 4, 5, 6]

По пункту №2. Информация о чанках. К каждому ряду прикрепляется информация, где лежат его данные:
 - Какой файл в директории chunks/ (например, 000001)
 - С какого смещения в этом файле начинаются данные
 - Временной диапазон этих данных
Благодаря этому, когда Prometheus позже получит Series ID, он сразу будет знать, куда идти в чанках.


2.1.3) Появление Series ID. В момент записи ряды просто идут друг за другом. Series ID — это порядковый номер ряда в этой последовательности:

 - Первый записанный ряд получает ID = 1
 - Второй ряд — ID = 2
 - Последний ряд в блоке — ID = N (где N — общее количество рядов)

ID нигде отдельно не хранится, он определяется позицией записи.Что получается на выходе этих этапов? После завершения записи Series-секции в файле index есть:
 1) Symbol Table (словарь строк)
 2) Series-секция (все ряды, закодированные числами, с привязкой к чанкам)
 3) У каждого ряда есть Series ID (его номер)
Теперь Prometheus знает, какие ряды существуют, из каких меток они состоят и где искать их данные.


2.1.4) Формирование Postings (Инвертированный индекс).
Если на предыдущих этапах мы создали список «паспортов» для каждой метрики (Series), то теперь нам нужно создать «телефонную книгу», чтобы быстро находить эти паспорта по конкретным признакам (меткам). 
Что такое Postings? Это разделы файла index, в которых для каждой уникальной пары Метка="Значение" хранится список всех Series ID, в которых эта пара встречается. Как это записывается:
Для каждой пары (например, status="200") создается блок данных:

 - len: Общая длина этой секции.
 - #entries: Количество рядов, которые содержат эту метку.
 - Список Series ID: Массив номеров рядов.

Пример: у нас в блоке 3 ряда:

 - ID 1: http_requests_total{method="GET", status="200"}
 - ID 2: http_requests_total{method="POST", status="200"}
 - ID 3: cpu_usage{core="0", status="200"}

Prometheus проходит по всем рядам и формирует списки для каждой метки:

 - Метка method="GET" —> Список IDs: [1]
 - Метка method="POST" —> Список IDs: [2]
 - Метка status="200" —> Список IDs: [1, 2, 3] (эта метка есть во всех трех рядах)
 - Метка core="0" —> Список IDs: [3]

Помимо лейблов, Prometheus создаёт posting и для имени метрики (используя специальный лейбл __name__):

 __name__="http_requests_total" → [1, 2]
 __name__="cpu_usage"           → [3]

Это позволяет фильтровать по имени метрики так же быстро, как по любому другому лейблу.

Важное правило: Списки Series ID внутри Postings всегда строго отсортированы по возрастанию. Это критически важно для скорости: когда Prometheus нужно найти пересечение двух меток (например, {method="GET", status="200"}), он берет два отсортированных списка и очень быстро находит общие ID за один проход.

Что получается на выходе этого этапа?
Теперь в файле index помимо словаря строк и описания самих рядов, появилась база для мгновенного поиска. Теперь Prometheus может не перебирать все ряды подряд, а сразу достать список ID тех рядов, которые подходят под фильтры запроса.


2.1.5) Postings Offset Table (Таблица смещений поиска)Что это такое?
Если Postings (2.1.4) — это сами списки ID серий, разбросанные по всему файлу index, то Postings Offset Table — это компактное «оглавление» в конце файла. Она связывает конкретную пару Метка=Значение с конкретным адресом (байтом) в файле, где начинается её список ID.

Зачем она нужна? Без этой таблицы Prometheus при каждом запросе (например, {status="500"}) пришлось бы сканировать весь многогигабайтный файл index с самого начала, чтобы найти нужный posting. С этой таблицей он делает мгновенный «прыжок» (seek) в нужное место.
Для каждой уникальной пары меток в таблицу записывается:

 - n = 2 - Маркер, указывающий, что запись состоит из двух частей (имя и значение)
 - name - Ссылка на имя метки (например, method) в Symbol Table
 - value - Ссылка на значение метки (например, GET) в Symbol Table
 - offset - 64-битное число (uvarint64) — точный адрес в файле, где лежит список Postings для этой пары.

Ключевые особенности:

 - Бинарный поиск: записи отсортированы (по имени метки, потом по значению), что позволяет находить нужный оффсет за O(log n)
 - Кэширование: при открытии блока таблица частично считывается в RAM — одна из причин, почему Prometheus потребляет память
 - CRC32: в конце таблицы записывается контрольная сумма для проверки целостности

Пример работы: пользователь запрашивает {app="frontend"} → Prometheus находит в таблице app="frontend" → видит offset, например 854030 → прыгает на байт 854030 и читает готовый список Series ID.


2.1.6) TOC (Table of Contents — Оглавление файла) Что это такое? 
Это финальная структура в конце файла index. TOC — это фиксированного размера блок данных, содержащий 64-битные указатели (offsets) на начало каждого раздела:

 - Symbol Table Offset — где начинается словарь строк
 - Series Offset — где начинается раздел с описанием рядов
 - Label Indices Offset — где начинаются индексы лейблов
 - Postings Offset — где начинается таблица смещений (Postings Offset Table)
 - Label Offset Table — таблица смещений для label indices
 - CRC32 — контрольная сумма самого TOC

Зачем нужен? Когда Prometheus открывает блок, он не читает файл с начала. Он прыгает в конец файла, считывает TOC и мгновенно узнаёт координаты всех секций.
Почему нельзя просто начинать с Postings Offset Table? Потому что она переменного размера — без TOC Prometheus не знал бы, где она начинается. Пришлось бы сканировать файл, что медленно.

Механика:

1) Прыжок в конец файла (seek)
2) Чтение TOC → получение адресов всех секций
3) Инициализация: зная смещения, Prometheus может мгновенно найти любую метку


Этап №2.2 Как ищется(чтение):
2.2.1) Prometheus читает файл с конца и находит TOC — Table of Contents. 
Это специальная структура, расположенная в конце файла index, которая содержит смещения (offsets) к началу всех остальных основных разделов этого файла. Можно сказать это оглавление в котором лежит маленькая структура фиксированного размера, где уже записано: «postings offset table начинается с байта N», «series — с байта M» и так далее. Тут сразу же возникает вопрос. А зачем нужен TOC если можно предпоследний раздел файла(Postings Offset Table) поместить в конец и начинать с него? Но тогда возникает проблема: он не знает, где postings offset table начинается. Эта таблица переменного размера т.е структура данных, количество записей в которой заранее неизвестно и может меняться. Чтобы её найти без TOC, пришлось бы либо сканировать файл назад, либо хранить какие-то маркеры между секциями. Это медленно и усложняет формат. 


2.2.2) Postings Offset Table (Таблица смещений списков).
Получив координаты из TOC, Prometheus идет сюда.
Это упорядоченный по алфавиту справочник всех пар key="value" (например, method="GET", status="200", job="prometheus"), которые встречаются в данном блоке TSDB. Для каждой такой пары в таблице записано смещение (offset) — точный адрес в байтах, указывающий, где в следующей секции (Postings) начинается список идентификаторов временных рядов для этой конкретной метки.


2.2.3) Postings - списки идентификаторов. 
Найдя смещение, Prometheus прыгает в Postings и читает список Series ID.
Содержимое секции: по найденному адресу лежит упакованный список чисел. Если ты искал status="200", то там будет: [5, 12, 42, 100, 105...] — «Временной ряд №5 имеет тег status="200", ряд №12 тоже, и так далее».

Магия пересечения (Intersection):

Запросы редко состоят из одного тега. Допустим, фильтр: {job="api", status="200"}.

1) Prometheus берёт список для job="api": [12, 42, 50, 100]
2) Берёт список для status="200": [5, 12, 42, 100, 105]
3) Делает пересечение: [12, 42, 100]

Поскольку оба списка отсортированы, пересечение выполняется за один проход (O(n+m)). Для запросов с =~ (regex) или логическим «ИЛИ» используется операция union — объединение списков, тоже за один проход по отсортированным спискам.

2.2.4) Работа с Series-секцией (получение информации о рядах)
После получения списка Series ID (например, [12, 42, 100]) Prometheus обращается к Series-секции. Series ID — это ссылка (offset) на конкретную запись.
Для каждого Series ID он извлекает:

1) Метки ряда (labelset)
Хранятся как числа-ссылки на Symbol Table. Prometheus восстанавливает строки:
[1, 3, 4, 5, 6] → http_requests_total{method="GET", status="200"}

2) Ссылки на чанки (chunk references)
Каждый chunk reference включает:

 - Файл в chunks/ (например, 000001)
 - Смещение внутри файла
 - Временной диапазон (minTime, maxTime)

Фильтрация по времени: Prometheus не читает все чанки подряд. Он использует minTime/maxTime из chunk references и отбирает только те чанки, которые пересекаются с запрошенным интервалом. Фильтрация происходит на уровне чанков, а не целиком series.


2.2.5) Чтение Symbol Table (Резолвинг имен)
Prometheus берёт числа-ссылки (например, 1) и через Symbol Table (которая загружена в память) мгновенно находит текст: 1 = http_requests_total.
После этого у Prometheus полностью восстанавливается текстовый вид метрики и он готов формировать ответ.


2.2.6) Чтение Chunks (получение значений)
Теперь у Prometheus есть chunk references: файл, offset и временной диапазон. Он открывает нужный файл в chunks/, прыгает на указанное смещение и декодирует чанк.
Декодирование — обратный процесс к кодированию:

 - Читает сжатые timestamps (double-delta) и восстанавливает реальные значения
 - Читает сжатые values (XOR) и восстанавливает реальные значения
 - Получает массив пар (timestamp, value) — готовые sample'ы

Если запрос покрывает несколько чанков одного ряда, Prometheus читает все релевантные чанки и склеивает результаты в единый временной ряд.
Полный путь запроса:
PromQL-запрос
  → meta.json: подходит ли блок по времени?
  → TOC: где что лежит в index?
  → Postings Offset Table: где posting для нужного лейбла?
  → Postings: какие Series ID подходят? (+ intersection)
  → Series-секция: какие чанки у этих series? (+ time filtering)
  → Symbol Table: как называются метки текстом?
  → Chunks: достать sample'ы и вернуть данные


Compaction — слияние блоков
Со временем у Prometheus накапливается много мелких двухчасовых блоков. Compaction — это фоновый процесс, который объединяет несколько блоков в один более крупный.
Зачем нужен compaction:

 - Меньше блоков — меньше файлов для открытия и меньше индексов для загрузки в память
 - Дедупликация — если series из разных блоков пересекаются (например, при рестарте HEAD), данные объединяются
 - Удаление tombstones — данные, помеченные на удаление, физически выбрасываются при compaction
 - Оптимизация индекса — один большой индекс эффективнее нескольких мелких

Как работает:

1) Prometheus выбирает несколько смежных блоков (обычно начиная с самых старых мелких)
2) Читает все series и sample'ы из этих блоков
3) Пропускает данные, помеченные tombstones
4) Записывает объединённые данные в новый блок
5) Новый блок получает compaction.level на 1 выше
6) Старые блоки удаляются

Уровни compaction:

level 1 — блок создан напрямую из HEAD (2 часа данных)
level 2 — объединение нескольких level-1 блоков (обычно до 6 часов)
level 3 — объединение level-2 блоков (до ~1.5 суток)

Максимальный размер блока по умолчанию — 10% от retention.time (но не более ~31 часов при дефолтном retention 15 дней). Это гарантирует, что удаление старых данных не потребует перезаписи огромных блоков.


Retention — управление хранением
Prometheus не хранит данные вечно. Retention определяет, когда старые блоки удаляются.
Два параметра (можно использовать оба одновременно):

 - --storage.tsdb.retention.time — хранить данные не старше указанного периода (по умолчанию 15 дней)
 - --storage.tsdb.retention.size — максимальный размер TSDB на диске (по умолчанию не ограничен)

При проверке retention Prometheus смотрит на maxTime блока в meta.json. Если maxTime блока старше retention — весь блок удаляется целиком. Именно поэтому compaction учитывает retention при определении максимального размера блока: блок не должен быть настолько большим, чтобы содержать и актуальные, и просроченные данные.
На собесе часто спрашивают: «Как хранить метрики дольше 15 дней?» — ответ: увеличить retention.time, но для хранения за месяцы/годы лучше использовать remote storage (Thanos, Mimir, VictoriaMetrics). Это уже тема отдельного документа.
