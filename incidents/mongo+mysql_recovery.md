# Восстановление MySQL и MongoDB после аварийного отключения питания

> Подробный разбор инцидента и пошаговое восстановление  
> **Дата инцидента:** 21 апреля 2026

---

## Часть 1. Что случилось и почему

### 1.1 Аварийное отключение питания и его последствия

MySQL — это не просто программа которая читает и пишет файлы. Внутри неё работает сложный механизм под названием **InnoDB** — движок хранения данных. InnoDB использует несколько ключевых структур на диске.

**ibdata** — системное табличное пространство. Содержит undo-логи (журнал откатов транзакций), метаданные таблиц, системные структуры InnoDB.

**Redo log (журнал повторного выполнения)** — файлы `ib_logfile0`, `ib_logfile1`. Каждая транзакция сначала пишется сюда, и только потом попадает в основные файлы данных. Это называется **Write-Ahead Logging (WAL)**.

**Data Dictionary (DD)** — в MySQL 8.0 это системный каталог всех таблиц, баз, индексов. Хранится в специальных системных таблицах внутри самого MySQL.

При **нормальном** завершении MySQL:
- Записывает все буферы из RAM на диск
- Закрывает redo log корректно
- Обновляет Data Dictionary
- Помечает shutdown как чистый

При **аварийном отключении питания** этого не происходит. Данные в RAM теряются, журналы транзакций остаются незакрытыми, файлы метаданных могут быть записаны частично. Именно это и произошло с нашим сервером.

## Часть 2. Восстановление MongoDB

MongoDB падала параллельно с MySQL — оба сервиса вышли из строя одновременно из-за аварийного отключения питания.

### 2.1 Что мы увидели

```
Active: failed (Result: core-dump) since Tue 2026-04-21 14:07:09 MSK; 45min ago
Process: 1242 ExecStart=/usr/bin/mongod (code=dumped, signal=ABRT)
Main PID: 1242 (code=dumped, status=6/ABRT)
CPU: 771ms
```

`core-dump` — процесс упал с созданием дампа памяти ядра. Это не мягкое завершение, а аварийный сбой.

`signal=ABRT` — сигнал 6 (Abort). MongoDB **сама себя убила** через `abort()` когда обнаружила состояние из которого не может восстановиться.

`CPU: 771ms` — процесс прожил меньше секунды. MongoDB падала почти сразу при каждом запуске.

### 2.2 Что показали логи MongoDB

В логах `/var/log/mongodb/mongod.log` была серия ошибок:

```
"msg":"WiredTiger error","attr":{
  "message":"file:WiredTiger.wt, WT_CURSOR.insert: __wt_bm_corrupt_dump,
  {0: 294912, 28672}: (chunk 20 of 28): ..."
}
```

Затем финальные строки:

```
"error":-31802,"message":"WiredTiger.wt: fatal read error: WT_ERROR"
"error":-31804,"message":"WT_PANIC: WiredTiger library panic"
"msg":"Fatal assertion"
"msg":"Got signal: 6 (Aborted)"
```

**Что это означает:**

`WiredTiger.wt` — это внутреннее «оглавление» всей базы MongoDB, в котором хранится информация о том где физически на диске лежат все коллекции и индексы. Без него MongoDB не может найти данные и отказывается запускаться.

В логах видны hex-дампы 28 повреждённых фрагментов — это фрагменты бинарных данных с диска (выглядят как `5f ee 45 48 00 00 01 64...`) с несовпадающими контрольными суммами. Контрольная сумма — это математическая подпись блока данных. Когда WiredTiger пишет блок на диск, он сохраняет эту подпись рядом. При чтении пересчитывает заново. Если суммы не совпадают — данные повреждены. Именно это и произошло при аварийном отключении питания.

`WT_PANIC` → `Fatal assertion` → `SIGABRT` — цепочка: WiredTiger обнаружил повреждение → перешёл в состояние паники → MongoDB вызвала `abort()` → процесс упал.

### 2.3 Первая попытка — mongod --repair

Стандартная команда восстановления MongoDB:

```bash
systemctl stop mongod
mongod --repair --dbpath /var/lib/mongodb
```

`--repair` — MongoDB пытается восстановить повреждённые структуры данных, пересоздать индексы и убрать битые записи.

**Проблема:** repair запускался от пользователя `root`. MongoDB при этом создавала и изменяла файлы с владельцем `root:root`. При следующем обычном запуске через systemd MongoDB работает от пользователя `mongodb` — и не могла читать собственные файлы принадлежащие root.

В логах это выглядело так:

```
"error":13,
"message":"wiredtiger_open: /var/lib/mongodb/WiredTiger.turtle:
handle-open: open: Permission denied"
```

`error:13` — стандартный Linux-код `EACCES` (отказано в доступе). `errno 13` всегда означает проблему с правами файловой системы.

### 2.4 Решение — исправление прав

```bash
chown -R mongodb:mongodb /var/lib/mongodb
```

`chown` — change owner, сменить владельца. `-R` — рекурсивно, то есть для всех файлов и папок внутри. `mongodb:mongodb` — пользователь и группа `mongodb`.

После этой команды все файлы в директории данных MongoDB снова принадлежали нужному пользователю.

```bash
systemctl start mongod
systemctl status mongod
# Active: active (running)
```

MongoDB запустилась. WiredTiger при старте смог прочитать свои файлы и восстановил структуры из уцелевших фрагментов журнала.

### 2.5 Урок — почему repair нужно запускать правильно

Если запускаете `mongod --repair` вручную — всегда делайте это от нужного пользователя:

```bash
# Правильно — от пользователя mongodb
sudo -u mongodb mongod --repair --dbpath /var/lib/mongodb

# Неправильно — от root, сломает права
mongod --repair --dbpath /var/lib/mongodb
```

Если repair уже запустили от root — исправляем права и только потом запускаем сервис:

```bash
chown -R mongodb:mongodb /var/lib/mongodb
systemctl start mongod
```

## Часть 3. Первый запуск — MySQL зависла на старте

### 2.1 Что мы увидели

```
Active: activating (start) since Tue 2026-04-21 14:53:47 MSK; 7s ago
Status: "Server startup in progress"
Memory: 4.0G
CPU: 16.046s
```

**Разбор каждой строки:**

`activating (start)` — процесс mysqld запущен но ещё не готов принимать соединения. Это промежуточное состояние между «запущен» и «работает».

`Memory: 4.0G` — MySQL уже занял 4 гигабайта оперативной памяти. Это нормально — InnoDB при старте загружает в память буферный пул (в нашем случае он был настроен на 50GB через `innodb_buffer_pool_size = 50G`).

`CPU: 16.046s` — за 7 секунд реального времени потрачено 16 секунд CPU. Это признак активной работы — MySQL делает **InnoDB crash recovery**, то есть пытается восстановиться после некорректного завершения, воспроизводя транзакции из redo log.

### 2.2 Почему автовосстановление не помогло

InnoDB умеет восстанавливаться сама после сбоев — это одна из её ключевых возможностей. Но только если повреждения не затронули системные структуры. В нашем случае был повреждён блок страницы в системном табличном пространстве:

```
[FATAL] Unable to read page [page id: space=4294967279, page number=356]
        into the buffer pool after 100 attempts.
```

`space=4294967279` (в hex это `0xFFFFFFEF`) — это зарезервированный номер **системного табличного пространства** InnoDB. Страница №356 внутри него физически повреждена — контрольная сумма не совпадает с данными, то есть на диск записалась частичная или некорректная информация.

MySQL попыталась прочитать эту страницу 100 раз, не смогла, и вызвала `ut_dbg_assertion_failed` — внутренний механизм аварийного завершения. Затем `abort()` → `SIGABRT` → процесс упал.

## Часть 4. innodb_force_recovery — принудительный запуск

### 3.1 Что это такое

`innodb_force_recovery` — параметр конфигурации MySQL который говорит InnoDB: _«игнорируй часть проверок при запуске, поднимись несмотря на ошибки»_. Это аварийный режим, аналог «завести машину с толкача».

Параметр принимает значения от 0 до 6. Каждый следующий уровень игнорирует всё больше проверок:

| Уровень | Что игнорирует |
|---------|----------------|
| 1 | Повреждённые страницы при фоновых операциях |
| 2 | Не запускать фоновые потоки (master thread, purge thread) |
| 3 | Не накатывать redo log при восстановлении |
| 4 | Не откатывать незакоммиченные транзакции |
| 5 | Не смотреть в undo log при старте |
| 6 | Не проверять контрольные суммы страниц |

> ⚠️ **Важное ограничение:** при `innodb_force_recovery > 0` MySQL переходит в режим **только для чтения**. INSERT, UPDATE, DELETE — заблокированы. Только SELECT и, соответственно, mysqldump работают нормально. Уровень 1 — самый щадящий, мы использовали именно его.

### 3.2 Что мы сделали

```bash
echo "innodb_force_recovery = 1" >> /etc/mysql/mysql.conf.d/mysqld.cnf
systemctl restart mysql
```

`echo "..." >> файл` — добавляет строку в конец файла. Двойной `>>` это добавление (append), одинарный `>` это перезапись (overwrite).

MySQL запустилась с этим параметром и стала доступна для чтения.

## Часть 5. Снятие innodb_force_recovery — первая попытка

### 4.1 Что произошло

После того как мы убрали `innodb_force_recovery` из конфига:

```bash
sed -i '/innodb_force_recovery/d' /etc/mysql/mysql.conf.d/mysqld.cnf
```

`sed -i` — редактирование файла «на месте» (in-place). `/innodb_force_recovery/d` — найти строки содержащие этот текст и удалить их (`d` = delete).

MySQL перестала запускаться:

```
mysql.service: Main process exited, code=exited, status=2/INVALIDARGUMENT
```

### 4.2 Настоящая причина

`status=2/INVALIDARGUMENT` — это **не** ошибка конфига (конфиг был валиден, `mysqld --validate-config` подтвердил). Это MySQL сама вернула код 2 при падении. В логе мы увидели:

```
[FATAL] Unable to read page [page id: space=4294967279, page number=356]
        into the buffer pool after 100 attempts.
Assertion failure: buf0buf.cc:4053
```

Та же страница 356 в системном табличном пространстве. Без `force_recovery` MySQL отказывается работать с повреждёнными системными структурами — это правильное поведение, она защищает данные от дальнейшей порчи.

Вернули `force_recovery = 1` обратно и перешли к глубокой диагностике.

## Часть 6. Диагностика — что именно повреждено

> ✅ **Ключевой принцип:** перед любыми радикальными действиями нужно точно понять **что** повреждено. Повреждение служебных файлов журналов лечится за 5 минут. Повреждение самих данных — часы работы.

### 5.1 Определяем компонент повреждения

```bash
# Смотрим какие tablespaces не в нормальном состоянии
mysql -u netroot -pnetroot -e "
SELECT SPACE, NAME, STATE
FROM information_schema.INNODB_TABLESPACES
WHERE STATE != 'normal';"
```

В нашем случае вывод был:

```
+------------+-----------------+--------+
| SPACE      | NAME            | STATE  |
+------------+-----------------+--------+
| 4294967279 | innodb_undo_001 | active |
| 4294967278 | innodb_undo_002 | active |
+------------+-----------------+--------+
```

`space=4294967279` — это тот самый номер который фигурировал в фатальной ошибке при запуске. `STATE=active` вместо `normal` означает что undo tablespaces не закрылись корректно при аварийном отключении питания.

**Undo tablespaces (undo_001, undo_002)** — это журналы откатов транзакций. Они нужны для того чтобы MySQL могла откатить незавершённые транзакции. При аварии они остаются в открытом состоянии.

Ключевое наблюдение: **сами данные в базах не повреждены** — повреждены только служебные файлы журналов. В запросе не оказалось ни одной пользовательской базы или таблицы со статусом отличным от `normal` — это означает что файлы данных (`.ibd`) не затронуты. Это означает что данные можно спасти без дампа и переинициализации.

### 5.2 Полный чеклист диагностики

```bash
# Ошибки в логе — что конкретно не читается
grep -E "\[ERROR\]" /var/log/mysql/error.log | tail -20

# Файлы undo на диске существуют?
ls -lh /var/lib/mysql/undo_*

# Статус undo через FILES
mysql -u netroot -pnetroot -e "
SELECT TABLESPACE_NAME, FILE_NAME, STATUS
FROM information_schema.FILES
WHERE FILE_TYPE = 'UNDO LOG';"

# Целостность таблиц
mysqlcheck -u netroot -pnetroot --all-databases 2>&1 | grep -v "OK" | head -30

# Сломанные view
mysql -u netroot -pnetroot 2>/dev/null << 'EOF'
SELECT COUNT(*) as broken_views
FROM information_schema.VIEWS
WHERE VIEW_DEFINITION LIKE 'select 1 AS%';
EOF
```

| Что проверяем | Хороший результат | Плохой результат |
|---------------|-------------------|------------------|
| INNODB_TABLESPACES | Пусто (все normal) | active у undo файлов |
| Undo файлы на диске | Файлы существуют | Файлы отсутствуют или 0 байт |
| Ошибки в логе | Нет `[ERROR]` | Ошибки чтения `.ibd` файлов |
| Целостность таблиц | Все OK | Corrupt table |
| Сломанные view | 0 | > 0 |

**Правило:** если повреждены только undo/redo файлы — пробуем удалить их и перезапустить (Часть 8). Если повреждены сами файлы данных `.ibd` — смотрим крайние меры (Часть 8).

## Часть 7. Восстановление — пересоздание undo tablespaces

В MySQL 8.0 undo tablespaces можно пересоздать без потери данных. Алгоритм простой — удаляем повреждённые файлы, MySQL создаёт их заново при следующем старте.

### 6.1 Пошаговое восстановление

**Шаг 1 — Останавливаем MySQL:**
```bash
systemctl stop mysql
```

**Шаг 2 — Делаем бэкап повреждённых файлов (на случай если что-то пойдёт не так):**
```bash
mv /var/lib/mysql/undo_001 /var/lib/mysql/undo_001.bak
mv /var/lib/mysql/undo_002 /var/lib/mysql/undo_002.bak
```

**Шаг 3 — Убираем innodb_force_recovery из конфига:**
```bash
sed -i '/innodb_force_recovery/d' /etc/mysql/mysql.conf.d/mysqld.cnf
grep innodb_force_recovery /etc/mysql/mysql.conf.d/mysqld.cnf && echo "ЕЩЁ ЕСТЬ" || echo "УБРАНО"
```

**Шаг 4 — Запускаем и смотрим лог:**
```bash
systemctl start mysql
tail -f /var/log/mysql/error.log
```

MySQL обнаружит отсутствие undo файлов и создаст их заново. Успешный запуск выглядит так:

```
[System] InnoDB initialization has started.
[System] InnoDB initialization has ended.
[System] /usr/sbin/mysqld: ready for connections. Version: '8.0.31'
```

Никаких `[ERROR]` — только `[System]` и `[Warning]` про SSL которые некритичны.

**Если запуск не удался** — возвращаем бэкап и force_recovery:
```bash
mv /var/lib/mysql/undo_001.bak /var/lib/mysql/undo_001
mv /var/lib/mysql/undo_002.bak /var/lib/mysql/undo_002
echo "innodb_force_recovery = 1" >> /etc/mysql/mysql.conf.d/mysqld.cnf
systemctl start mysql
```

### 6.2 Финальная проверка после восстановления

```bash
# force_recovery убран?
grep innodb_force_recovery /etc/mysql/mysql.conf.d/mysqld.cnf && echo "ЕЩЁ ЕСТЬ" || echo "УБРАНО"

# Подключение работает?
mysql -u netroot -pnetroot -e "SELECT 1;" && echo "OK"

# Запись работает? (самый важный тест)
mysql -u netroot -pnetroot -e "
CREATE DATABASE IF NOT EXISTS test_write;
DROP DATABASE test_write;" && echo "ЗАПИСЬ РАБОТАЕТ"

# Сломанных view нет?
mysql -u netroot -pnetroot 2>/dev/null << 'EOF'
SELECT COUNT(*) as broken_views
FROM information_schema.VIEWS
WHERE VIEW_DEFINITION LIKE 'select 1 AS%';
EOF

# Ошибок в логе нет?
grep "\[ERROR\]" /var/log/mysql/error.log | tail -10
```

Результат в нашем случае:
```
УБРАНО
OK
ЗАПИСЬ РАБОТАЕТ
broken_views: 0
(ошибок нет)
```

**MySQL полностью восстановлена без дампа и переинициализации!**

## Итоговая хронология инцидента

| Этап | Действие | Почему |
|------|----------|--------|
| Аварийное отключение | Питание пропало | Данные в RAM потеряны, файлы не закрыты |
| MySQL не стартует | InnoDB не может прочитать страницу 356 | Повреждены undo tablespaces |
| innodb_force_recovery=1 | MySQL запустилась в режиме только для чтения | Игнорируем повреждённые страницы при старте |
| Убрали force_recovery | MySQL снова не стартует | Без костыля повреждения критичны |
| Вернули force_recovery | MySQL снова доступна | Нужна для диагностики |
| Диагностика tablespaces | Обнаружили undo_001/002 в STATE=active | Повреждены только журналы, не данные |
| Удалили undo файлы | Убрали повреждённые журналы | MySQL пересоздаст их при старте |
| Убрали force_recovery | Конфиг чистый | Больше не нужен |
| systemctl start mysql | MySQL запустилась нормально | Новые undo файлы созданы автоматически |
| Проверка записи | CREATE/DROP DATABASE работает | Полный режим чтения/записи восстановлен |

## Рекомендации по предотвращению

### Немедленно
- Убедиться что `innodb_force_recovery` **не** прописан в конфиге после восстановления
- Установить **UPS** (источник бесперебойного питания) — это корень всех проблем
- Проверить работу приложения и веб-сервиса

### Среднесрочно
- Настроить регулярные бэкапы MySQL (`mysqldump` по расписанию через cron)
- Настроить регулярные бэкапы MongoDB (`mongodump`)
- Добавить мониторинг (Zabbix/Prometheus) чтобы знать о проблемах до пользователей
- Настроить алерты на состояние дисков и сервисов

### Долгосрочно
- Разобраться с падениями MongoDB в марте (`status=4/ILL`) — это отдельная проблема несовместимости
- Рассмотреть обновление MongoDB 4.4 до актуальной версии
- Рассмотреть настройку репликации MySQL для отказоустойчивости

## Часть 8. Крайняя мера — переинициализация БД

> ⛔ **Это крайняя и нежелательная мера.** Применяется только если все предыдущие шаги не помогли — то есть повреждены не только undo файлы, но и сами файлы данных `.ibd`, и MySQL не запускается даже с `innodb_force_recovery = 6`.

**Когда переинициализация неизбежна:**
- Повреждены файлы данных (`*.ibd`) а не только undo логи
- MySQL не стартует даже с `force_recovery = 6`
- `mysqlcheck` выдаёт `Corrupt` на системных таблицах
- Все попытки починить undo/redo файлы не дали результата

**Что теряем при переинициализации:**
- Все данные в базах — восстанавливать придётся из дампа или бэкапа
- Все пользователи и права — нужно пересоздавать
- Потеря данных за период с последнего бэкапа

**Общий алгоритм:**
1. Снять дамп через `innodb_force_recovery = 1` пока возможно — `mysqldump --all-databases --single-transaction`
2. Остановить MySQL
3. Очистить `/var/lib/mysql/`
4. Выполнить `mysqld --initialize-insecure --user=mysql`
5. Запустить MySQL и восстановить данные из дампа

> ⚠️ Если дошли до этого пункта — ситуация серьёзная. Наличие свежего бэкапа критично. Именно поэтому настройка регулярных бэкапов из раздела «Рекомендации» так важна.
