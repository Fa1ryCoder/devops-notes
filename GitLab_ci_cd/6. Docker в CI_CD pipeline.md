# 6. Docker в CI

## Docker executor: джоба выполняется внутри контейнера

У GitLab Runner несколько executor'ов (shell, docker, kubernetes и другие) — это то, как именно выполняется job. При **docker executor** раннер на каждую job поднимает отдельный контейнер из образа, указанного в `image:` (глобально в `default:` или в конкретной job), выполняет внутри него `before_script` / `script` / `after_script` и удаляет контейнер после завершения:

```yaml
default:
  image: python:3.10-slim

test-job:
  stage: test
  script:
    - pip install -r requirements.txt
    - pytest
```

Отсюда изоляция между job'ами (никакого мусора от предыдущего запуска), воспроизводимость и возможность у каждой job'ы взять свой образ под конкретную задачу.

## Docker-in-Docker (DinD) и альтернатива — socket binding

Здесь нюанс, который на собеседовании спрашивают едва ли не чаще всего. Job уже выполняется внутри контейнера (docker executor). Если внутри такой job вызвать `docker build`, кто соберёт образ? Команде `docker build` нужен запущенный демон Docker, с которым она говорит через сокет или по сети, — а в job-контейнере (даже если это образ `docker`, где есть только CLI) по умолчанию не запущено никакого демона. Просто поставить и запустить демон внутри обычного контейнера тоже нельзя: для этого нужны расширенные права ядра, которых у обычного контейнера нет.

Отсюда два рабочих варианта.

**Docker-in-Docker (DinD)** — называется так потому, что демон Docker в этом случае сам запускается внутри контейнера, то есть Docker (демон) работает внутри Docker (контейнера, управляемого тем же Docker хоста) — буквально «Docker в Docker'е». Идея подхода — поднять отдельный, полноценный демон Docker как ещё один контейнер рядом с job (через `services: - docker:29-dind`) и обращаться к нему по сети:

```yaml
build-image:
  stage: build
  image: docker:29
  services:
    - docker:29-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  before_script:
    - docker info
  script:
    - docker build -t myapp .
```

Одной `DOCKER_TLS_CERTDIR` достаточно: образ `docker` сам проверяет, лежат ли по этому пути клиентские сертификаты, и если да — сам выставляет `DOCKER_HOST: tcp://docker:2376`, `DOCKER_TLS_VERIFY: "1"` и `DOCKER_CERT_PATH: "/certs/client"` (это видно в его `docker-entrypoint.sh`). Прописать все четыре переменные явно — тоже рабочий вариант, просто более старый стиль, всё ещё встречается в документации GitLab.

Версии образа job и dind-сервиса обычно берут одинаковыми — расхождение версий клиента и демона иногда даёт ошибки совместимости API. Для приватного self-hosted раннера, где полноценный TLS-контур избыточен, можно упростить до `DOCKER_TLS_CERTDIR: ""` — тогда тот же `docker-entrypoint.sh` сам поставит `DOCKER_HOST: tcp://docker:2375` без TLS, но это осознанный отказ от шифрования трафика между job и демоном.

Раннеру для DinD нужен `privileged = true` в `config.toml`: запуск демона внутри контейнера требует прав, которых у обычного контейнера нет (mount cgroups, overlay-файловые системы и т.д.).

`services:` необязательно объявлять в каждом `.gitlab-ci.yml` — то же самое можно один раз настроить глобально в `config.toml` раннера:

```toml
[[runners]]
  executor = "docker"
  [runners.docker]
    image = "docker:latest"
    privileged = true
    services = ["docker:dind"]
```

Тогда DinD-сервис поднимается автоматически для каждой job на этом раннере, и в `.gitlab-ci.yml` `services:` можно вообще не указывать — из-за этого в чужих пайплайнах иногда не видно явного `services: - docker:dind`, хотя DinD там реально используется.

**Docker socket binding (Docker-outside-of-Docker, DooD)** — job-контейнер и так запущен демоном Docker хоста, а при socket binding этому же демону просто прокидывают доступ ещё и внутрь job-контейнера через смонтированный сокет — никакого нового, вложенного демона (как в DinD) не появляется. Отсюда и название — Docker снаружи Docker. Идея — не поднимать отдельный демон, а прокинуть в job-контейнер сокет хостового демона:

```toml
[runners.docker]
  volumes = ["/var/run/docker.sock:/var/run/docker.sock"]
```

Privileged не нужен, зато любая job получает фактический контроль над Docker хоста целиком — с точки зрения безопасности вариант заметно рискованнее, особенно если на раннере крутятся job'ы из чужих репозиториев.

Ещё нюанс: наличие «docker» в имени образа job'ы само по себе ничего не значит. Демон нужен только тогда, когда скрипт реально вызывает `docker build` / `docker run`. Например:

```yaml
unpack-job:
  stage: build
  image: docker:29
  script:
    - tar -xzf release.tar.gz
    - sh run_tests.sh
```

Образ здесь взят просто как готовая Alpine-оболочка с базовыми утилитами (`tar`, `sh` — они есть в `docker:29` из коробки, как в любом Alpine-образе), а сам скрипт распаковывает архив и гоняет тесты через обычный shell — никаких вызовов `docker` внутри него нет. Демон в этой job'е не нужен вообще — ни DinD, ни socket binding, потому что сам Docker (как инструмент) здесь просто не используется, только образ как оболочка.

## `services:` — ещё один контейнер рядом с job

`services:` поднимает дополнительный контейнер, который живёт рядом с основным job-контейнером на время выполнения job, в общей сети. В `services:` мы указываем образ, из которого поднять этот дополнительный контейнер, а обращаться к нему по сети можно по хостнейму, равному имени этого образа без тега. Если такое имя не подходит, можно явно задать своё через `alias:`. На этом же механизме держится и DinD выше — `docker:29-dind` в `services:` это точно такой же сервис, просто в роли демона Docker.

Другой классический сценарий — база данных для интеграционных тестов:

```yaml
integration-test:
  stage: test
  image: python:3.10-slim
  services:
    - postgres:15
  variables:
    POSTGRES_DB: testdb
    POSTGRES_USER: testuser
    POSTGRES_PASSWORD: testpass
    DATABASE_URL: postgresql://testuser:testpass@postgres:5432/testdb
  script:
    - pip install -r requirements.txt
    - pytest tests/integration
```

Момент, который любят проверять на собеседовании: к сервису обращаются по его имени (`postgres`), а не по `localhost` — `localhost` внутри job-контейнера указывает сам на себя, а не на соседний контейнер с базой.

## GitLab Container Registry

GitLab Container Registry — это встроенный в каждый проект GitLab приватный registry для образов (включается в Settings → General → Visibility, project features, permissions, переключателем Container Registry), в отличие от Docker Hub — отдельного, публичного по умолчанию стороннего сервиса. Разница на практике: Docker Hub требует отдельного аккаунта и своих credentials, а образы там публичные, если не платить за приватные репозитории. У каждого проекта в этом registry — свой репозиторий образов, привязанный к пути проекта (`registry.gitlab.com/группа/проект`). Именно этот репозиторий и виден в самом GitLab, в проекте, во вкладке Deploy → Container Registry — там появляются все запушенные образы и их теги (в том числе те самые `$CI_COMMIT_SHORT_SHA`). Сервис один на весь GitLab, но у каждого проекта — своя изолированная часть с отдельным доступом.

Со временем тегов там накапливается много — особенно если тег привязан к коммиту, как в нашем примере: каждый коммит создаёт новый постоянный тег, и место в квоте registry потихоньку заканчивается. Для порядка стоит настроить cleanup policy: Settings → Packages and registries settings → раздел Container registry → Container registry cleanup policies → кнопка «Set cleanup rules». Там задаётся, например, «Keep the most recent: N tags per image name» (хранить последние N тегов на каждый образ) и «Remove tags older than: X days» (удалять теги старше X дней) — и GitLab применяет это правило сам по расписанию.

### Зачем логиниться и какие переменные для этого нужны

Прежде чем пушить образ, `docker push` должен пройти аутентификацию — иначе registry просто откажет в записи, кто угодно образы туда заливать не может. GitLab сам прокидывает в job готовый набор переменных для этого:

- `CI_REGISTRY` — хост registry, например `registry.gitlab.com`;
- `CI_REGISTRY_IMAGE` — путь к репозиторию образов именно этого проекта, например `registry.gitlab.com/pet-python/api-python`;
- `CI_REGISTRY_USER` — служебный пользователь, обычно `gitlab-ci-token`;
- `CI_REGISTRY_PASSWORD` — токен для него, по факту совпадает с `CI_JOB_TOKEN`: короткоживущий, привязан к конкретному job и автоматически истекает;
- `CI_JOB_TOKEN` — тот же токен job, можно использовать вместо `CI_REGISTRY_PASSWORD` напрямую.

Все переменные выше объявлять самому не нужно — GitLab кладёт их в окружение job'ы автоматически, если Container Registry включён у проекта (в том числе `CI_JOB_TOKEN`, у которого и так есть права на push/pull в registry своего проекта); их нужно только использовать по имени. Без валидного логина `docker push` откажет с ошибкой авторизации — это единственный по-настоящему обязательный шаг перед пушем. Современный вариант логина — без пароля в аргументах команды, иначе он оседает в истории шелла и списке процессов:

```bash
echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"
```

`echo` в шелле — встроенная команда (builtin), а не отдельная программа: значение остаётся внутри процесса самого шелла и передаётся в `docker login` напрямую через pipe, не через argv отдельного процесса. Если бы пароль передавался через `-p "$CI_REGISTRY_PASSWORD"`, шелл запустил бы `docker` как отдельный, реальный процесс с паролем прямо в аргументах — и пока этот процесс жив (секунды, пока идёт запрос к registry), любой на этой машине с доступом к `ps aux` увидел бы пароль в списке процессов открытым текстом.

## Собираем pipeline: build → push

```yaml
build-image:
  stage: build
  image: docker:29
  services:
    - docker:29-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  before_script:
    - docker info
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"
  script:
    - docker build --provenance=false --sbom=false -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA" .
    - docker push "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

Тег через `$CI_COMMIT_SHORT_SHA` практичнее вечного `latest`: образ однозначно привязан к коммиту, легко откатиться и понятно, что именно задеплоено. Сам тег обязателен технически (без него `docker push` не поймёт, что и куда пушить), но конкретно `$CI_COMMIT_SHORT_SHA` — это наш собственный выбор ради удобства и трассируемости, а не требование самого registry: с тем же успехом сработал бы `latest` или любая другая строка.

После `docker build` образ появляется в хранилище того самого демона, к которому обращается CLI — в нашем случае это демон внутри контейнера `docker:29-dind`, а не где-то ещё. Снаружи об этом образе никто не знает, пока не выполнится `docker push`.

Флаги `--provenance=false --sbom=false` обязательны при пуше в GitLab Container Registry — без них push упадёт. Почему именно — в следующем разделе.

## Частая проблема: `blob unknown to registry`

Современный `docker build` по умолчанию не просто собирает образ, а ещё прикладывает к нему attestations — служебные метаданные о сборке. Их два вида: provenance (как и из чего собран образ) и SBOM (Software Bill of Materials — список пакетов внутри). GitLab Container Registry эту дополнительную часть принять не умеет, и пуш падает:

```
error from registry: blob unknown to registry - sha256:<digest>
```

При этом слои самого образа к этому моменту уже успешно загружены — падает именно финальный манифест (служебный файл-описание образа: из каких слоёв он состоит, какие у него теги и т.д.).

Фикс — отключить дефолтные attestations, тогда собирается обычный одноархитектурный образ без индекса (те же флаги `--provenance=false --sbom=false`, что и в pipeline-примере выше).

Тот же эффект даёт переменная на уровне job, если не хочется трогать саму команду сборки:

```yaml
variables:
  BUILDX_NO_DEFAULT_ATTESTATIONS: "1"
```
