## 1. Производительность

### Load Average

**Load Average** — это среднее количество процессов которые либо активно выполняются (состояние R), либо ожидают завершения I/O (состояние D) за последние 1, 5 и 15 минут. Это **не процент загрузки CPU** — это длина очереди к ресурсам.

```bash
$ uptime
14:32:01 up 10 days, load average: 2.45, 1.87, 1.20
                                    ▲     ▲     ▲
                                   1мин  5мин  15мин
$ nproc
4   # количество логических ядер CPU
```

Норма: Load Average ≤ количества CPU ядер.

> ⚠️ **Читать тренд справа налево** (15m → 5m → 1m):
> - `4.00, 6.00, 8.00` → нагрузка **снижается**, пик прошёл
> - `8.00, 6.00, 4.00` → нагрузка **растёт**, разбираться прямо сейчас

**Быстрая развилка при высоком LA:**

- LA высокий, `%us` под 100% → процессы реально считают код → **см. Блок 1: CPU Bottleneck**
- LA высокий, `%id` высокий, `%wa` > 20% → процессы ждут диск → **см. Блок 2: I/O Bottleneck**

### vmstat — экспресс-анализ системы

`vmstat` даёт моментальный срез системы: CPU, память, swap, I/O — всё в одной строке. Первую строку игнорируй — она показывает среднее за весь аптайм. Смотри на вторую и дальше.

```bash
vmstat 1 5   # каждую секунду, 5 раз
```

Ключевые колонки:

| Колонка | Полное название | Тревожно если |
|---------|----------------|---------------|
| `r` | Run queue | Стабильно > nproc — CPU bottleneck |
| `b` | Blocked | > 0 долгое время — процессы застряли на I/O |
| `si` / `so` | Swap In / Swap Out | > 0 — RAM кончается, активный своппинг |
| `wa` | I/O Wait | > 20% — диск не справляется |
| `us` | User space | > 80% стабильно — CPU bottleneck в приложении |
| `sy` | System | > 30% — много системных вызовов |
| `cs` | Context Switches | > 100 000 — слишком много переключений |
| `st` | Steal Time | > 0 в облаке — сосед забирает CPU у гипервизора |

**Три аварийных сценария:**

```
r > nproc, us > 80%, wa = 0  →  Блок 1: CPU Bottleneck
b > 0, wa > 20%              →  Блок 2: I/O Bottleneck
si/so > 0                    →  Блок 3: Memory Pressure
```

---

### Блок 1: CPU Bottleneck
*(переходим сюда если в vmstat: `r > nproc` и `us > 80%`)*

Процессор забит работой, дисковая подсистема отдыхает. Ищем топ-5 процессов которые сжигают CPU:

```bash
ps -eo pid,pcpu,cmd --sort=-pcpu | head -5
```

---

### Блок 2: I/O Bottleneck
*(переходим сюда если в vmstat: `b > 0` и `wa > 20%`)*

Самая частая обманка: CPU свободен, но всё тормозит — потоки приложения встали в очередь к диску или сетевому хранилищу (NFS, Ceph). Локализуем проблемный диск и находим виновника:

```bash
iostat -x 1    # детальная утилизация дисков (%util, await)
iotop -o       # только процессы которые прямо сейчас читают/пишут
```

---

### Блок 3: Memory Pressure
*(переходим сюда если в vmstat: `si/so > 0`)*

**Главная ошибка новичков** — смотреть на колонку `free` в `free -h`. Для Linux нормально держать `free` около нуля — ядро намеренно забирает всю свободную память под кэш файлов. Смотри только на `available`:

```bash
$ free -h
#         total    used    free   shared  buff/cache  available
# Mem:    7.8Gi   6.5Gi   200Mi    100Mi       1.1Gi      1.0Gi
#                                                            ▲
#                                              Смотри ТОЛЬКО сюда!
# available — сколько ОС готова мгновенно отдать новому процессу,
#             выкинув ненужный кэш. Если близко к нулю — сервер в опасности.
```

Три уровня деградации памяти:

```
Уровень 1 (Low):      RAM занята, ядро вытесняет page cache. Замедление незаметно.
Уровень 2 (Medium):   Кэш вытеснен, включился swap (si/so > 0 в vmstat).
                      Скорость работы с данными падает в 1000+ раз.
Уровень 3 (Critical): Swap тоже исчерпан → OOM Killer убивает процессы.
```

```bash
# проверить был ли OOM Kill
journalctl -k | grep -i "out of memory\|killed process"
```

**Swappiness** — насколько агрессивно ядро использует swap (0–100, дефолт 60):

```bash
cat /proc/sys/vm/swappiness

# для продакшен БД снижаем до 10
echo "vm.swappiness=10" >> /etc/sysctl.conf && sysctl -p
# При дефолте 60 ядро может выпихнуть в swap рабочие страницы БД.
# Задержки запросов вырастут на порядки — RAM ~100ns vs swap/SSD ~100000ns.
# При swappiness=10 — swap только в экстренной ситуации.
```

**Лимиты памяти в systemd:**

```ini
[Service]
MemoryHigh=400M   # мягкий лимит — throttle при превышении
MemoryMax=512M    # жёсткий лимит — OOM Kill при превышении
MemorySwapMax=0   # запретить swap для этого сервиса
```

```bash
systemd-cgtop                                                   # потребление по сервисам
cat /sys/fs/cgroup/system.slice/nginx.service/memory.current    # байты конкретного сервиса
```

---

### PSI — Pressure Stall Information (Linux 4.20+)

PSI показывает не сколько ресурса занято, а **сколько % времени процессы простаивали из-за его нехватки**. Заменяет эвристики вроде «смотри на free memory».

```bash
cat /proc/pressure/memory
# some avg10=0.00 avg60=2.15 avg300=1.45
# full avg10=0.00 avg60=0.00 avg300=0.10

# some — хотя бы один процесс ждал ресурс
# full — ВСЕ процессы одновременно ждали ресурс (жёсткий ступор)
# avg60 — % времени за последние 60 секунд (основной показатель)
```

Пороги для алертов:

```
memory.some avg60 > 10%  → начинается своппинг, скоро OOM
memory.full avg60 > 1%   → критично, система деградирует
io.some avg60 > 30%      → диск перегружен
cpu.some avg60 > 70%     → CPU не хватает
```

```bash
# какой сервис создаёт давление
cat /sys/fs/cgroup/system.slice/postgresql.service/memory.pressure

# мониторинг в реальном времени
watch -n 1 'cat /proc/pressure/memory /proc/pressure/io /proc/pressure/cpu'
```

> Нулевой `free` при нулевом PSI — идеальная норма. Ненулевой PSI при большом `free` — аномалия.

## 2. strace

### Что такое системный вызов

Любое взаимодействие программы с операционной системой — открытие файла, чтение данных, создание сокета, выделение памяти — это **системный вызов (syscall)**. Программа не может напрямую работать с диском или сетью — только через ядро. Программа «просит» ядро выполнить операцию через специальный механизм.

Пример: когда nginx открывает конфиг, это выглядит так:

```
nginx вызывает:  openat(AT_FDCWD, "/etc/nginx/nginx.conf", O_RDONLY) = 3
ядро отвечает:   3  ← успешно открыл, вот fd
nginx вызывает:  read(3, <данные>, 4096) = 1024  ← прочитал 1024 байта
nginx вызывает:  close(3) = 0  ← закрыл fd
```

**strace** перехватывает и выводит все системные вызовы процесса в реальном времени. Это как «рентген» — видно что процесс реально делает на уровне ОС, даже если логи молчат.

### Основные режимы

```bash
# подключиться к запущенному процессу
strace -p <PID>

# трассировать только определённые вызовы (важно на продакшене!)
strace -p <PID> -e trace=openat,read,write   # файловые операции
strace -p <PID> -e trace=network             # сетевые вызовы
strace -p <PID> -e trace=signal              # сигналы

# статистика: сколько раз вызван, суммарное время
strace -c python3 script.py
# % time   seconds  calls  syscall
#  45.23    0.231   23000  read
#  20.11    0.103   20000  write
#  15.00    0.080    1000  openat

# с временными метками — видно сколько занимает каждый вызов
strace -T -p <PID>   # время каждого вызова справа
strace -t -p <PID>   # абсолютное время

# включая дочерние процессы
strace -f -p <PID>

# записать в файл для анализа
strace -p <PID> -o /tmp/trace.txt
```

### Когда использовать

| Ситуация | Что искать в strace |
|----------|---------------------|
| Процесс завис, логи молчат | `strace -p <PID>` — на каком вызове завис |
| Приложение не находит файл | `strace -e trace=openat` — ENOENT ошибки |
| Права доступа непонятны | `strace -e trace=file` — EACCES ошибки |
| Медленный старт | `strace -c app` — какие вызовы занимают время |
| Утечка fd | `strace -e trace=open,close` — открывает не закрывая |

> ⚠️ strace добавляет overhead (накладные расходы) ~10–30%. На продакшене под нагрузкой — используйте с фильтром `-e trace=` и снимайте как только нашли проблему.

### Практический пример

```bash
# процесс завис, wchan = "pipe_wait"
strace -p 1234
# read(5, <unfinished ...>
# ← завис на чтении из fd=5, данные не приходят

# смотрим что за fd=5
ls -la /proc/1234/fd/5
# l-wx------ -> pipe:[98765]

# кто на другом конце пайпа
lsof | grep 98765
# app  5678  ...  6w  FIFO  pipe:[98765]  ← процесс 5678 держит запись открытой
# но не пишет данные → дедлок
```

## 3. eBPF и bpftrace

### Что такое eBPF

**eBPF (extended Berkeley Packet Filter)** — механизм ядра Linux позволяющий запускать **верифицированный пользовательский код прямо внутри ядра** без модификации ядра и без перекомпиляции. Появился в полноценном виде в Linux 4.4, стал стандартом наблюдаемости к 2021–2022.

В отличие от strace, который перехватывает системные вызовы через ptrace (overhead — накладные расходы — 10–100%), eBPF программы работают внутри ядра с overhead (накладными расходами) < 1%. Можно использовать на продакшене под нагрузкой без страха.

```
  strace:                             eBPF:
  ──────                              ────
  процесс → syscall                   процесс → syscall
       ↓ ptrace (останавливает!)            ↓ eBPF hook (не останавливает)
  strace читает аргументы             eBPF программа выполняется в ядре
       ↓                                    ↓ пишет в ring buffer
  процесс продолжает                  userspace читает события
  
  Overhead: 10–100%                   Overhead: < 1%
  Продакшен: осторожно               Продакшен: ОК
```

### Инструменты: bcc-tools и bpftrace

Два основных набора инструментов поверх eBPF:

**bcc-tools** — готовые скрипты для конкретных задач:
```bash
# установка
apt install bpfcc-tools linux-headers-$(uname -r)
```

**execsnoop** — все новые процессы в реальном времени. Идеально чтобы поймать скрытые скрипты которые кто-то запускает по крону, или понять что именно запускает твой сервис под капотом:
```bash
execsnoop-bpfcc
# TIME     PCOMM  PID    PPID   RET ARGS
# 10:23:01 bash   12345  1234   0   /bin/ls -la /tmp
```

**opensnoop** — какие файлы открывает процесс прямо сейчас. Помогает понять почему сервис игнорирует твой новый конфиг (читает старый путь?) или куда пишет скрытые логи:
```bash
opensnoop-bpfcc -p $(pgrep -o nginx)
# TIME     PID    COMM   FD ERR PATH
# 10:23:05 1234   nginx  10   0 /etc/nginx/conf.d/default.conf
```

**biolatency** — латентность дисковых I/O операций в виде гистограммы. Помогает доказать что тормозит именно диск, а не приложение:
```bash
biolatency-bpfcc
# usecs      : count  distribution
# 0 -> 1     : 1234   |████████
# 2 -> 3     : 5678   |████████████████████████████████
# 4 -> 7     : 234    |██
```

**tcpconnect** — все новые исходящие TCP соединения на уровне ядра. Незаменимо если микросервис куда-то сливает трафик и непонятно куда:
```bash
tcpconnect-bpfcc
# PID  COMM   IP SADDR       DADDR        DPORT
# 1234 nginx  4  10.0.0.1    10.0.0.2     5432
```

**bpftrace** — язык для написания собственных eBPF трейсеров в одну строку:

```bash
# кто и какие файлы открывает (все процессы)
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s → %s\n", comm, str(args->filename)); }'

# латентность read() у конкретного процесса
bpftrace -e 'tracepoint:syscalls:sys_enter_read /pid == 1234/ { @start = nsecs; }
             tracepoint:syscalls:sys_exit_read  /pid == 1234/ { @us = hist((nsecs - @start)/1000); }'

# топ системных вызовов за 5 секунд
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm, probe] = count(); }' --timeout 5

# сколько памяти выделяет процесс (через mmap/brk)
bpftrace -e 'tracepoint:syscalls:sys_enter_mmap /pid == 1234/ { @bytes = sum(args->len); }'

# OOM события в реальном времени
bpftrace -e 'tracepoint:oom:mark_victim { printf("OOM killed: PID=%d %s\n", args->pid, args->comm); }'
```

### strace vs bpftrace — когда что

| Ситуация | Инструмент | Почему |
|----------|-----------|--------|
| Отладка конкретного процесса локально | strace | Проще, не нужна установка bpftrace |
| Мониторинг на продакшене под нагрузкой | bpftrace | Overhead < 1%, strace опасен |
| «Кто открывает этот файл?» для всех процессов | opensnoop / bpftrace | strace одного процесса не покажет |
| Гистограмма латентности I/O | biolatency | strace не умеет агрегировать |
| Отладка зависания (процесс в состоянии D) | bpftrace / strace | strace покажет на каком syscall завис |
| Быстро глянуть что делает процесс | strace -p PID | Проще чем писать bpftrace выражение |

```bash
# проверить что bpftrace доступен
bpftrace --version
uname -r   # нужно >= 4.9, полноценная поддержка >= 5.3
```

> eBPF — это не только трейсинг. На нём построены: Cilium (сетевой слой K8s), Falco (runtime security), Pixie (observability платформа), Cloudflare DDoS protection, Meta's Katran load balancer. Знание базового bpftrace — стандартное ожидание от Senior/Staff SRE в 2026.

## 4. Анти-паттерны

### Читать только одно число load average

```bash
# ❌ — смотрим только первое число и паникуем (или успокаиваемся)

# ✅ — читаем тренд
uptime
# load: 8.00, 4.00, 2.00 → нагрузка РАСТЁТ — нужно разбираться сейчас
# load: 2.00, 4.00, 8.00 → нагрузка СНИЖАЕТСЯ — проблема уходит
```
