# Модель памяти процессов Linux

---

## 1. Виртуальная память и изоляция процессов

Когда ядро запускает процесс, оно выдаёт ему **виртуальное адресное пространство** — диапазон адресов, которые процесс считает «своей» памятью. Аппаратный блок **MMU** преобразует эти виртуальные адреса в реальные адреса физической RAM, разбитой на страницы по 4 КБ.

Это даёт три важных свойства:

- **Изоляция** — процесс A не может прочитать память процесса B. Один упавший контейнер не ломает соседний.
- **Защита** — код программы (text-сегмент) помечается read-only, запись туда вызывает ошибку.
- **Многозадачность** — ядро может заморозить процесс, переключиться на другой, вернуться обратно. Процесс не знает, что его прерывали.

### VSZ vs RSS — что реально занято

При просмотре `ps aux` или `top` видны два числа. Их различие — один из самых частых вопросов на собесах:

```
USER   PID  VSZ    RSS    COMMAND
nginx  123  512Mi  42Mi   nginx: worker
java   456  4Gi    800Mi  java -jar app.jar
```

| Метрика | Что показывает | Когда смотреть |
|---|---|---|
| **VSZ** (Virtual Size) | Сколько виртуальной памяти процесс *зарезервировал* | Почти никогда — может быть огромным и это нормально |
| **RSS** (Resident Set Size) | Сколько физической RAM занято *прямо сейчас* | Всегда — это реальное потребление |

Java-процесс с `VSZ = 4 ГБ` и `RSS = 800 МБ` не съедает 4 ГБ RAM — он зарезервировал это пространство, но физически использует только 800 МБ.

### vm.overcommit — почему VSZ вообще может быть огромным

`vm` — это просто префикс (сокращение от virtual memory), под которым Linux группирует все настройки управления памятью. `vm.overcommit_memory` читается как «настройка памяти, отвечающая за overcommit».

По умолчанию Linux разрешает процессам резервировать **больше памяти, чем есть физически**. Это называется overcommit. Логика простая: ядро выделяет физические страницы лениво — только в момент реальной записи, а не в момент резервирования. Java-сервис при старте резервирует весь heap под флагу `-Xmx`, но физически занимает только то, что реально использует. Поэтому VSZ Java-процесса всегда больше RSS.

```bash
# Посмотреть текущий режим
cat /proc/sys/vm/overcommit_memory
# 0 — эвристика (умный overcommit, дефолт)
# 1 — разрешить всё (aggressively overcommit)
# 2 — запретить (строгий лимит: RAM + swap)
```

**Практика:** Redis в своей документации прямо рекомендует выставить `vm.overcommit_memory = 1`, иначе при `BGSAVE` (бэкап на диск) ядро может отказать в памяти, даже когда её хватает.

Почему так происходит: для бэкапа Redis использует **fork** — создаёт точную копию своего процесса. Копия наследует всю память родителя и в это время сохраняет снимок данных на диск, пока основной процесс продолжает работу.

В режиме `0` (дефолт) ядро перед fork проверяет: «хватит ли памяти под полную копию?». Redis весит 10 ГБ — ядро видит 6 ГБ свободных и отказывает. Хотя физически форк никогда не занял бы все 10 ГБ: он только читает данные и почти ничего не меняет.

При `vm.overcommit_memory = 1` ядро пропускает эту проверку и разрешает fork. Это не страшно — реальной памяти форк берёт немного.

Это не универсальная рекомендация для всех приложений — только для тех, кто использует fork в рантайме. Большинство сервисов (Nginx, Java) этого не делают.

```bash
echo "vm.overcommit_memory = 1" >> /etc/sysctl.conf
sysctl -p
```

## 2. Page Cache — почему «свободной» памяти нет

Linux использует всю незанятую RAM под **Page Cache** — кэш диска. Файлы которые читались недавно хранятся в памяти, чтобы не ходить на диск повторно. Это нормальное и намеренное поведение, не утечка.

### Правильное чтение `free -h`

```
              total    used    free   shared  buff/cache  available
Mem:           31Gi    8Gi    1Gi     200Mi     22Gi        22Gi
Swap:           8Gi    0Gi    8Gi
```

- `free: 1Gi` — оперативной памяти без каких-либо данных осталось всего 1 ГБ. **Не смотрим на это число.**
- `buff/cache: 22Gi` — Page Cache. Linux заполнил этим незанятую RAM.
- **`available: 22Gi` — смотрим на это.** Столько памяти реально доступно для нового процесса: ядро моментально отдаст Page Cache при необходимости.
- `shared: 200Mi` — разделяемая память (Shared Memory / Tmpfs). Например, файлы записанные в `/dev/shm` внутри контейнера. Эта память учитывается в колонке `used`, а не в `buff/cache` — поэтому стандартными утилитами мониторинга процессов её тяжело поймать.

> **Каверзный вопрос на собесе:** «`used` огромный, `buff/cache` маленький, но процессы в `top` ничего не жрут. Куда делась память?». Ответ: ушла в `shared` — кто-то активно пишет в `/dev/shm`.

Видеть `free ≈ 0` на нагруженном сервере — совершенно нормально. Плохо, когда `available` стремится к нулю.

### Page Faults — когда кэш работает против вас

Каждое обращение к странице памяти, которой нет в RAM — это **Page Fault**:

| Тип | Перевод | Что происходит | Стоимость |
|---|---|---|---|
| **Minor Fault** | Мягкая страничная ошибка | Страница есть в RAM, просто не замаплена в таблицу страниц процесса | ~микросекунды, дёшево |
| **Major Fault** | Жёсткая страничная ошибка | Страницы нет в RAM — нужно читать с диска | ~миллисекунды, дорого |

Для баз данных **Major Faults = катастрофа**: каждый промах это дисковый I/O, запросы начинают выполняться секунды вместо миллисекунд (латентность — время ответа).

```bash
# Мониторинг page faults конкретного процесса
ps -o pid,comm,maj_flt,min_flt -p $(pgrep -d, postgres)

# В реальном времени (одинарные кавычки обязательны — иначе pgrep сработает
# один раз при старте и новые PID мониториться не будут)
watch -n1 'ps -o pid,comm,maj_flt,min_flt -p $(pgrep -d, postgres)'
```

**Практика:** Настраивая PostgreSQL или ClickHouse, нельзя отдать всю RAM приложению — нужно оставить место под Page Cache. Если БД работает с большими файлами данных, Page Cache снижает Major Faults. Практическое правило из опыта для PostgreSQL: `shared_buffers = 25% RAM` — это параметр PostgreSQL, который говорит «столько RAM отдай мне под свой внутренний кэш». Остальные 75% остаются операционной системе под Page Cache. Если отдать больше — Page Cache сожмётся и вырастут Major Faults.

### Как снизить количество Major Faults

**1. Оставлять RAM под Page Cache** — главное правило, описано выше.

**2. Снизить `vm.swappiness`** — чем агрессивнее ядро свопирует, тем больше Major Faults при возврате страниц обратно в RAM. Подробно — в разделе 7.

**3. Hugepages** — вместо стандартных страниц по 4 КБ использовать страницы по 2 МБ. Меньше страниц = меньше промахов. Но здесь важно не перепутать два разных механизма:

| Тип | Перевод | Как работает | Для БД |
|---|---|---|---|
| **Explicit (Static) Huge Pages** | Явные (статические) огромные страницы | Резервируются жёстко при старте ОС. Приложение явно запрашивает их. | ✅ Рекомендуется |
| **Transparent Huge Pages (THP)** | Прозрачные огромные страницы | Ядро само на лету объединяет страницы в 2 МБ через процесс `khugepaged`. | ❌ Отключать |

THP звучит удобно, но для баз данных это **скрытый убийца производительности**: ядро тратит ресурсы на динамическое объединение страниц прямо во время работы БД, что вызывает всплески латентности и рост Major Faults.

```bash
# Проверить статус THP
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never  ← always означает включён

# Отключить THP для БД (обязательно для PostgreSQL, Redis, ClickHouse, MongoDB)
echo never > /sys/kernel/mm/transparent_hugepage/enabled

# Сделать постоянным через rc.local или systemd unit,
# так как этот параметр не управляется через sysctl.conf
```

```bash
# Настроить статические Huge Pages
# Посмотреть текущее состояние
cat /proc/meminfo | grep -i huge

# Выделить 512 hugepages (512 × 2МБ = 1ГБ)
echo 512 > /proc/sys/vm/nr_hugepages

# Постоянно
echo "vm.nr_hugepages = 512" >> /etc/sysctl.conf
sysctl -p
```

## 3. Стек (Stack)

Стек — небольшой регион памяти для локального контекста функций: локальных переменных, аргументов, адресов возврата. Управляется процессором автоматически.

**Для DevOps важно одно:** каждый **поток выполнения** (thread) имеет **свой стек**.

```bash
# Лимит размера стека (по умолчанию 8 МБ на поток)
ulimit -s
# 8192

# Изменить для текущей сессии
ulimit -s 16384
```

**Практика:** Java-сервис запустили с 500 потоками — виртуальная память (VSZ) выросла на `500 × 8 МБ = 4 ГБ`, хотя приложение само по себе лёгкое. Это нормально: стек резервируется под каждый поток, но физически (RSS) занимается по мере использования.

Если в логах появился `SIGSEGV` без явной причины — возможен **Stack Overflow**: поток исчерпал свои 8 МБ (например, бесконечная рекурсия).

## 4. Куча (Heap)

Куча — регион памяти для данных, которые должны **жить дольше одной функции**: объекты, буферы, кэши. Управляется аллокатором (`malloc`/`free` в C, GC в Java/Python/Go).

Стек не подходит для таких данных: всё что на стеке — уничтожается при выходе из функции.

### Memory Leak — «куда делась память?»

Утечка памяти — это когда приложение выделяет память в куче и не освобождает её. RSS процесса растёт монотонно и не возвращается.

Типичный сценарий: «У нас в коде всё чисто, это Linux виноват!»

```bash
# Шаг 1: Убедиться, что растёт именно куча
# -d, — если процессов несколько, pgrep вернёт все PID через запятую
pmap -x $(pgrep -d, python3) | sort -k3 -rn | head -20
# Ищем строки с большим Dirty и пометкой [heap] или anon

# Шаг 2: Подробная карта памяти процесса
cat /proc/$(pgrep -d, java)/smaps | grep -A 15 "heap"
# Size       — зарезервировано
# Rss        — реально в RAM
# Dirty      — изменено с момента загрузки (наши данные, не кэш)
```

Если `Dirty` в секции `[heap]` растёт со временем — память занята именно объектами приложения, а не кэшом ОС. Это аргумент для разработчиков.

**Нюанс с аллокатором:** `glibc` (стандартный аллокатор в Linux) ради производительности **не всегда сразу возвращает память ядру** после `free()`. RSS может оставаться высоким, даже когда приложение освободило объекты. Это не утечка — это поведение аллокатора. Отличить можно профайлером (Valgrind, memory_profiler для Python, pprof для Go).

## 5. Ограничения памяти в контейнерах (cgroups)

Docker и Kubernetes ограничивают память контейнеров через **cgroups** — механизм ядра Linux. В современных системах используется **cgroup v2** (дефолт в K8s 1.25+, Ubuntu 22.04+).

### Два типа лимитов (cgroup v2)

```yaml
# Kubernetes: resources секция в манифесте пода
resources:
  requests:
    memory: "256Mi"   # Гарантия: столько ядро резервирует для пода
  limits:
    memory: "512Mi"   # Жёсткий потолок
```

| Параметр cgroup v2 | K8s аналог | Поведение при превышении |
|---|---|---|
| `memory.max` | `limits.memory` | Жёсткий потолок. Процесс получает OOM Kill |
| `memory.high` | *(вычисляется автоматически при включённом Memory QoS)* | Мягкий потолок. Ядро начинает забирать Page Cache и throttle-ить процесс |
| `memory.low` / `memory.min` | `requests.memory` | Защищённый минимум. Ядро старается не трогать эту память даже при нехватке |

**Memory QoS в современном K8s:** если включён Memory QoS, Kubernetes автоматически вычисляет и выставляет `memory.high` чуть ниже `memory.max`. Это позволяет контейнеру при превышении `requests` сначала плавно притормозить (ядро забирает Page Cache), а не сразу получить жёсткий OOM Kill по `memory.max`.

**Практика:** Если выставить `limits.memory` без понимания реального потребления — получите OOM Kill в продакшне. Правило: сначала смотрим на RSS в мониторинге под нагрузкой, потом ставим лимит с запасом ~30%.

```bash
# Посмотреть текущий лимит и потребление контейнера
cat /sys/fs/cgroup/system.slice/docker-<id>.scope/memory.current
cat /sys/fs/cgroup/system.slice/docker-<id>.scope/memory.max
```

## 6. OOM Killer — кого убивает ядро

Когда физическая RAM + swap заканчиваются, ядро включает **OOM Killer**: выбирает процесс и убивает его, чтобы освободить память.

### Диагностика: нашли труп, ищем причину

```bash
# Первое место — лог ядра
dmesg | grep -i "oom\|killed"
# или
journalctl -k | grep -i oom

# Типичный вывод:
# Out of memory: Killed process 12345 (java) total-vm:4096MB, anon-rss:3800MB
# oom_score_adj: 0
```

В строке содержится всё нужное: какой процесс убит, сколько он занимал, в каком контейнере.

### oom_score — по какому принципу выбирается жертва

Ядро считает каждому процессу очки `oom_score` (0–1000). Чем выше — тем вероятнее убьют.

```bash
# Посмотреть score конкретного процесса
cat /proc/$(pgrep java)/oom_score

# Посмотреть все процессы, отсортировать по score
for pid in /proc/[0-9]*; do
  printf "%d\t%s\n" "$(cat $pid/oom_score 2>/dev/null)" "$(cat $pid/comm 2>/dev/null)"
done | sort -rn | head -10
```

### oom_score_adj — как защитить важные процессы

```bash
# Диапазон: от -1000 (никогда не убивать) до +1000 (убить первым)

# Защитить sshd от OOM Kill (иначе потеряешь доступ к серверу)
echo -1000 > /proc/$(pgrep sshd)/oom_score_adj

# Защитить kubelet
echo -1000 > /proc/$(pgrep kubelet)/oom_score_adj

# Сделать процесс первым кандидатом на убийство
echo 1000 > /proc/$(pgrep некритичный-сервис)/oom_score_adj
```

В Kubernetes: `oom_score_adj` для подов выставляется автоматически на основе QoS-класса (Guaranteed → `-997`, BestEffort → `1000`).

## 7. Swap и vm.swappiness

**Swap** — раздел на диске (или файл), который ядро использует как расширение RAM: редко используемые страницы выгружаются на диск, освобождая физическую память.

### Почему Swap — враг баз данных

Дисковый I/O в тысячи раз медленнее RAM. Когда БД уходит в swap:
- латентность запросов улетает с миллисекунд до секунд
- начинаются таймауты и каскадные отказы
- сервер «жив» с точки зрения ОС, но фактически заморожен

```bash
# Посмотреть использование swap
free -h
swapon --show

# Что именно свопируется (топ процессов)
for pid in /proc/[0-9]*; do
  swap=$(awk '/VmSwap/{print $2}' $pid/status 2>/dev/null)
  comm=$(cat $pid/comm 2>/dev/null)
  [ "$swap" -gt 0 ] 2>/dev/null && echo "$swap kB $comm"
done | sort -rn | head -10
```

### vm.swappiness — как агрессивно уходить в swap

**Swappiness** — настройка ядра, которая контролирует насколько агрессивно Linux выгружает страницы памяти в swap. Число от 0 до 100: высокое значение — ядро охотно уходит в swap не дожидаясь нехватки RAM, низкое — держит данные в RAM до последнего.

Живёт в `/proc/sys/vm/swappiness`, настраивается через `sysctl`. Постоянное значение прописывается в `/etc/sysctl.conf`.

```bash
# Посмотреть текущее значение
cat /proc/sys/vm/swappiness
# или
sysctl vm.swappiness

# Применить сразу (до перезагрузки)
sysctl -w vm.swappiness=1

# Сделать постоянным (переживёт перезагрузку)
echo "vm.swappiness = 1" >> /etc/sysctl.conf
sysctl -p
```

> **Ловушка на собесе:** изменения через `sysctl -w` или запись напрямую в `/proc/sys/` действуют только до первой перезагрузки. Классический вопрос: «Вы потюнили ядро, всё стало круто, но ночью сервер перезагрузился и всё упало. Почему?». Ответ: забыли прописать в `/etc/sysctl.conf`.

| Значение | Поведение |
|---|---|
| `60` | Дефолт. Ядро начинает свопировать заблаговременно |
| `10` | Свопирование только при реальной нехватке RAM |
| `1` | Свопирование в крайнем случае (рекомендуется для PostgreSQL, Redis, ClickHouse) |
| `0` | Swap не используется совсем\* |

\* В старых ядрах (до 3.5) `vm.swappiness = 0` означало «никогда не свопируй до абсолютного OOM». В современных ядрах (3.5+, все актуальные дистрибутивы) `0` ведёт себя так же как `1` — агрессивно избегать свопа, но не блокировать его полностью. Поэтому стандартом де-факто сейчас пишут `vm.swappiness = 1`. Чтобы отключить swap физически: `swapoff -a`.

**Рекомендация для Kubernetes-нод:** поддержка swap перешла в статус GA. K8s теперь умеет работать со свопом на нодах: для обычных приложений своп разрешён, для СУБД-нод его по-прежнему полностью отключают через `swapoff -a`.
