# 9. Циклы (`loop`)

## Зачем

Часто одну и ту же задачу нужно выполнить для нескольких элементов: создать несколько пользователей, разложить несколько конфигов, применить несколько sysctl-параметров. Вместо копипаста однотипных задач Ansible даёт циклы: задача описывается один раз, а элементы подставляются по очереди через переменную `item`.

## `loop` — современный способ

`loop` — ключевое слово задачи (как `when` или `register`). Принимает список, задача выполняется по одному разу на каждый элемент, текущий элемент доступен как `{{ item }}`:

```yaml
- name: Создать пользователей
  ansible.builtin.user:
    name: "{{ item }}"      # на каждой итерации item — очередной элемент списка
    state: present
  loop:
    - alice
    - bob
    - carol
```

Внутри Ansible разворачивает это в серию запусков модуля — как если бы руками написать три одинаковые задачи:

```yaml
- ansible.builtin.user:
    name: alice
    state: present

- ansible.builtin.user:
    name: bob
    state: present

- ansible.builtin.user:
    name: carol
    state: present
```

Значение в `item` кладёт сам Ansible: берёт очередной элемент списка из `loop` и подставляет. В задаче ты `item` только читаешь через `{{ item }}` — нигде отдельно создавать его не нужно. Итерация 1: в `item` лежит `alice`, модуль запускается. Итерация 2: `bob`. И так до конца списка. В выводе плейбука это одна задача, но несколько строк результата:

```
TASK [Создать пользователей] ****
changed: [server1] => (item=alice)
changed: [server1] => (item=bob)
changed: [server1] => (item=carol)
```

Список обычно берут из переменной, например:

```yaml
  loop: "{{ admin_users }}"
```

Точек подстановки может быть сколько угодно — `item` рендерится везде, где встречается в задаче. Значение при этом одно на итерацию:

```yaml
- name: Разложить конфиги сервисов
  ansible.builtin.copy:
    src: "configs/{{ item }}.conf"      # item подставляется и здесь...
    dest: "/etc/myapp/{{ item }}.conf"  # ...и здесь — одно и то же значение
    mode: "0644"
  loop:
    - nginx
    - sshd
```

На итерации с `nginx` оба места получат `nginx`: скопируется `configs/nginx.conf` в `/etc/myapp/nginx.conf`.

`loop` принимает только список. Словарь напрямую передать нельзя — его сначала преобразуют фильтром `dict2items` (ниже).

## Список словарей

Когда элементу нужно несколько параметров, элементами списка делают словари, а к полям обращаются через `item.<ключ>`:

```yaml
- name: Создать пользователей с разными шеллами
  ansible.builtin.user:
    name: "{{ item.name }}"      # сюда подставится поле name текущего элемента
    shell: "{{ item.shell }}"    # сюда — поле shell
    state: present
  loop:
    - { name: alice, shell: /bin/bash }          # элемент 1: словарь из двух полей
    - { name: bob, shell: /usr/sbin/nologin }    # элемент 2
```

Механика та же, что с простым списком: на каждой итерации Ansible кладёт в `item` очередной элемент. Только элемент теперь — целый словарь, поэтому `{{ item }}` — это весь словарь сразу, а к отдельным полям доступ через точку. Итерация 1: `item.name` → `alice`, `item.shell` → `/bin/bash`. Итерация 2: `item.name` → `bob`, `item.shell` → `/usr/sbin/nologin`. Разворот «руками»:

```yaml
- ansible.builtin.user:
    name: alice              # из item.name первого элемента
    shell: /bin/bash         # из item.shell первого элемента
    state: present

- ansible.builtin.user:
    name: bob                # из item.name второго элемента
    shell: /usr/sbin/nologin # из item.shell второго элемента
    state: present
```

Зачем это нужно: в простом списке у элемента одно значение, а здесь на одну итерацию нужно два разных — и имя, и шелл. Словарь упаковывает несколько значений в один элемент.

Запись `{ name: alice, shell: /bin/bash }` — просто компактная YAML-форма словаря, то же самое можно написать развёрнуто:

```yaml
  loop:
    - name: alice
      shell: /bin/bash
    - name: bob
      shell: /usr/sbin/nologin
```

## Цикл по словарю: `dict2items`

`dict2items` превращает словарь в список словарей вида `{key: ..., value: ...}` — и по нему уже можно пройтись циклом:

```yaml
vars:
  sysctl_params:
    net.ipv4.ip_forward: 1
    vm.swappiness: 10

tasks:
  - name: Применить sysctl-параметры
    ansible.posix.sysctl:
      name: "{{ item.key }}"
      value: "{{ item.value }}"
    loop: "{{ sysctl_params | dict2items }}"
```

Фильтр применяется прямо в `loop`: взять `sysctl_params`, прогнать через `dict2items`, результат отдать циклу. Было и стало:

```yaml
# было (словарь — loop такое не принимает)
sysctl_params:
  net.ipv4.ip_forward: 1
  vm.swappiness: 10

# стало (список словарей с полями key и value)
- { key: net.ipv4.ip_forward, value: 1 }
- { key: vm.swappiness, value: 10 }
```

Дальше механика ровно та же, что в предыдущем разделе про список словарей — просто поля здесь всегда называются `key` и `value`: итерация 1 — `item.key` → `net.ipv4.ip_forward`, `item.value` → `1`, и так далее.

## `loop_control`

Секция для управления поведением цикла. Основные параметры:

`label` — что печатать в выводе вместо всего элемента. Полезно, когда элементы — большие словари: вывод короче, и в лог не попадает лишнее (в том числе секреты внутри item).

`index_var` — имя переменной с номером итерации (счёт с нуля).

`loop_var` — переименовать `item`. Нужно при вложенных циклах через `include_tasks`: внешний и внутренний циклы иначе будут конфликтовать за одно имя `item`.

`pause` — пауза в секундах между итерациями. Типичный случай — поочерёдный перезапуск сервисов: не ронять всё разом, а давать каждому время подняться.

Всё вместе в одном примере:

```yaml
- name: Разложить конфиги
  ansible.builtin.template:
    src: "{{ item.src }}"
    dest: "{{ item.dest }}"
    mode: "0644"
  loop:
    - { src: nginx.conf.j2, dest: /etc/nginx/nginx.conf }
    - { src: motd.j2, dest: /etc/motd }
  loop_control:
    label: "{{ idx }}: {{ item.dest }}"  # что печатать в выводе вместо всего словаря
    index_var: idx                       # номер итерации, счёт с нуля
    pause: 5                             # секунд между итерациями
```

Без `label` в скобках печатается весь элемент цикла целиком, с `label` — только указанное:

```
# без label — весь элемент целиком
changed: [server1] => (item={'src': 'nginx.conf.j2', 'dest': '/etc/nginx/nginx.conf'})

# с label и index_var
changed: [server1] => (item=0: /etc/nginx/nginx.conf)
changed: [server1] => (item=1: /etc/motd)
```

Пример с `loop_var` — ниже, в разделе про `register` в цикле: там без переименования получается конструкция `item.item`.

## Ловушка: `loop` без `item`

`loop` сам по себе ничего не подставляет — он только запускает задачу N раз. Если в параметрах задачи нигде нет `{{ item }}`, модуль выполнится N раз с одинаковыми параметрами: без ошибки, без предупреждения и без пользы.

```yaml
# каталог создастся один, но модуль отработает четыре раза подряд
- name: Создать каталог
  ansible.builtin.file:
    path: /etc/myapp        # item нигде не используется
    state: directory
  loop:
    - conf.d
    - certs
    - logs
    - cache
```

Автор явно хотел четыре подкаталога, а получил четырёхкратный прогон одного и того же пути. Правильно: `path: "/etc/myapp/{{ item }}"`.

Самопроверка: написал `loop` — найди `item` в задаче. Нет `item` — либо цикл лишний, либо забыта подстановка.

## `register` в цикле

Если на задаче с циклом стоит `register`, переменная получает поле `results` — список результатов по каждой итерации. Логика такая: модуль запускался несколько раз, результатов несколько, а переменная одна — поэтому Ansible складывает их в список. Кроме `results`, у переменной есть верхний `changed` — итог по всей задаче: `true`, если хоть одна итерация что-то изменила, `false`, если не изменила ни одна. Удобно для условий: `when: myvar.changed` — одна проверка вместо разбора `results`. Верхний `failed` устроен так же: `true`, если упала хоть одна итерация, `false`, если все прошли успешно.

```yaml
- name: Проверить наличие конфигов
  ansible.builtin.stat:
    path: "{{ item }}"
  loop:
    - /etc/nginx/nginx.conf
    - /etc/ssh/sshd_config
  register: config_stats

- name: Показать отсутствующие
  ansible.builtin.debug:
    msg: "Нет файла {{ result.item }}"   # result — элемент results, result.item — исходный путь
  loop: "{{ config_stats.results }}"
  loop_control:
    loop_var: result   # переменная второго цикла — result, а не item
  when: not result.stat.exists
```

Вот что реально лежит в `config_stats` после первой задачи (упрощённо):

```yaml
config_stats:
  changed: false          # итог: менялось ли хоть что-то (тут false — stat только читает)
  failed: false           # итог: упала ли хоть одна итерация
  results:                # список, по элементу на итерацию
    - item: /etc/nginx/nginx.conf    # исходный элемент цикла — Ansible сам дописывает это поле
      stat:                          # дальше — обычные поля модуля stat
        exists: true
      changed: false
      failed: false
    - item: /etc/ssh/sshd_config
      stat:
        exists: false
      changed: false
      failed: false
```

То есть каждый элемент `results` — это обычный результат модуля, как при одиночном `register`, плюс поле `item`, куда Ansible записывает элемент цикла этой итерации — иначе было бы не понять, какой результат к какому элементу относится.

Вторая задача крутит цикл уже по `config_stats.results`, поэтому переменная её цикла — целиком один элемент этого списка. Через `loop_var` она названа `result`, и обращения читаются: `result.stat.exists` — поле результата, `result.item` — исходный путь из первого цикла (то самое дописанное поле). На итерации с nginx `result.stat.exists` истинно, `when` отсекает её; на итерации с sshd_config условие срабатывает и печатается путь.

Если `loop_var` не задать, переменная второго цикла тоже будет называться `item` — и обращение к исходному пути превращается в `item.item`: первый `item` — текущий элемент второго цикла, второй `.item` — дописанное поле внутри него. Работает так же, но читается плохо, а в чужом коде встречается постоянно — уметь расшифровать нужно:

```yaml
- name: Показать отсутствующие
  ansible.builtin.debug:
    msg: "Нет файла {{ item.item }}"
  loop: "{{ config_stats.results }}"
  when: not item.stat.exists
```

## Когда цикл не нужен

Многие модули сами принимают список. Классика — установка пакетов: `apt`/`dnf`/`package` принимают список в `name`, и это одна транзакция пакетного менеджера вместо N отдельных запусков модуля — заметно быстрее:

```yaml
# так не надо
- name: Установить пакеты
  ansible.builtin.apt:
    name: "{{ item }}"
    state: present
  loop: [nginx, curl, htop]

# так надо
- name: Установить пакеты
  ansible.builtin.apt:
    name: [nginx, curl, htop]
    state: present
```

## Списки по назначению вместо срезов

Когда цикл должен пройти только по части элементов, соблазн — держать один общий список и резать его индексами: `loop: "{{ packages[0:3] }}"`. Это хрупко: числа `0:3` ничего не говорят читателю, а при первом же добавлении элемента в список срез молча захватит не то. Правильнее разделить список на несколько по смыслу и склеивать оператором `+` там, где нужно:

```yaml
vars:
  base_packages:        # ставятся везде
    - curl
    - htop
  web_packages:         # только на веб-хостах
    - nginx

tasks:
  - name: Установить базовый набор
    ansible.builtin.apt:
      name: "{{ base_packages }}"
      state: present

  - name: Установить полный набор на веб-хостах
    ansible.builtin.apt:
      name: "{{ base_packages + web_packages }}"   # склейка списков
      state: present
    when: "'web' in group_names"
```

Каждый список отвечает на вопрос «зачем эти элементы вместе», склейка читается без комментариев, и добавление пакета в любой из списков ничего не ломает.

## Не путать: `until`

`until` / `retries` / `delay` — это не цикл по списку, а повтор одной и той же задачи, пока не выполнится условие (или не кончатся попытки). Переменной `item` там нет. Типичный случай — дождаться, пока сервис поднимется:

```yaml
- name: Дождаться ответа nginx
  ansible.builtin.uri:
    url: http://localhost/
  register: result
  until: result.status == 200
  retries: 10      # максимум попыток
  delay: 3         # секунд между попытками
```
