## 1. Что такое права доступа

Права доступа — это механизм безопасности Linux, определяющий **кто** и **что** может делать с файлом или директорией.

Каждый файл имеет три атрибута:
- **Владелец (user)** — пользователь которому принадлежит файл
- **Группа (group)** — группа-владелец файла
- **Остальные (others)** — все остальные пользователи системы

Для каждой из трёх категорий задаются три вида прав: **чтение**, **запись**, **выполнение**.

> **Философия Linux:** всё есть файл. Права доступа применяются не только к обычным файлам, но и к директориям, устройствам, сокетам и символическим ссылкам.

## 2. Типы файлов

При выполнении `ls -la` первый символ в строке указывает на тип файла:

| Символ | Тип | Пример |
|--------|-----|--------|
| `-` | Обычный файл | `-rw-r--r-- script.py` |
| `d` | Директория | `drwxr-xr-x /home/user` |
| `l` | Символическая ссылка | `lrwxrwxrwx .face.icon -> .face` |
| `b` | Блочное устройство (диски) | `brw-rw---- /dev/sda` |
| `c` | Символьное устройство (терминалы) | `crw-rw-rw- /dev/tty` |
| `s` | Сокет | `srw-rw-rw- /tmp/mysql.sock` |
| `p` | Именованный канал (pipe) | `prw-r--r-- mypipe` |

> **На собесе могут спросить:** чем отличается блочное устройство от символьного?
> - **Блочное (b)** — работает с блоками данных, поддерживает произвольный доступ (диски, флешки)
> - **Символьное (c)** — передаёт данные побайтово последовательно (терминалы, последовательные порты)

## 3. Структура прав доступа

### 3.1 Три вида прав

| Символ | Название | Цифра | Для файла | Для директории |
|--------|----------|-------|-----------|----------------|
| `r` | read (чтение) | 4 | Просматривать содержимое | Видеть список файлов (`ls`) |
| `w` | write (запись) | 2 | Изменять содержимое | Создавать/удалять файлы внутри |
| `x` | execute (выполнение) | 1 | Запускать как программу | Входить в директорию (`cd`) |
| `-` | нет права | 0 | Право отсутствует | Право отсутствует |

> ⚠️ **Важно:** право на **удаление** файла определяется правом `w` на **директорию**, а не на сам файл. Вы можете удалить файл даже если у вас нет на него прав — если есть `w` на директорию где он лежит.

### 3.2 Три категории пользователей

```
  [тип][u:rwx][g:rwx][o:rwx]
  -    rw-    r--    r--
  ^    ^^^    ^^^    ^^^
  |    |      |      └── others: все остальные пользователи
  |    |      └───────── group:  пользователи группы-владельца
  |    └──────────────── user:   владелец файла
  └───────────────────── тип файла
```

**Реальный пример из системы:**

```bash
fa1ry@fa1ry:~$ ls -lha
drwxr-xr-x   4 fa1ry fa1ry 4,0K .ansible
-rw-------   1 fa1ry fa1ry  40K .bash_history
-rw-r--r--   1 fa1ry fa1ry 3,5K .bashrc
lrwxrwxrwx   1 fa1ry fa1ry    5 .face.icon -> .face
```

> 🚨 **Критическое правило:** проверка идёт **строго по порядку** и останавливается на первом совпадении.
> Если вы **владелец** — применяются только права владельца, права группы и others **не проверяются**.

**Пример парадокса прав:**
```bash
----r----- 1 fa1ry developers secret.txt
# u=---  владелец — нет прав вообще
#    r-- g=r--  группа — может читать
#       --- o=---  остальные — нет прав
```
Владелец `fa1ry` **не может** читать файл — система видит что он владелец, применяет права `u` (`---`) и останавливается. Права группы для него уже не проверяются.

Но `bob` из группы `developers` — **может читать**: он не владелец, система переходит к проверке группы, видит `r--` → доступ разрешён.

```
fa1ry обращается к файлу:
  1. Ты владелец? → Да → применить u=--- → ❌ отказ (проверка остановлена)

bob обращается к файлу:
  1. Ты владелец? → Нет
  2. Ты в группе developers? → Да → применить g=r-- → ✅ чтение разрешено
```

**Парадокс становится глубже:** `fa1ry` тоже состоит в группе `developers` — то есть права `g=r--` формально распространяются и на него. Но система **никогда до них не доберётся**: проверка остановилась ещё на шаге владельца. Членство в группе не спасает если ты владелец файла.

> **Выход из этой ситуации** — **ACL (Access Control Lists, расширенные права доступа)**. ACL позволяют задать права для конкретного пользователя или группы поверх стандартной модели `ugo` — в том числе явно разрешить владельцу доступ через отдельное правило, которое система проверит независимо от его роли владельца. Подробнее это рассматривается ниже в **теме 9**.

## 4. Числовое представление прав

Каждый вид права имеет числовое значение: `r=4`, `w=2`, `x=1`. Права одной группы суммируются:

| Цифра | Права | Символы | Расшифровка |
|-------|-------|---------|-------------|
| `7` | 4+2+1 | `rwx` | Все права |
| `6` | 4+2+0 | `rw-` | Чтение и запись |
| `5` | 4+0+1 | `r-x` | Чтение и выполнение |
| `4` | 4+0+0 | `r--` | Только чтение |
| `3` | 0+2+1 | `-wx` | Запись и выполнение |
| `2` | 0+2+0 | `-w-` | Только запись |
| `1` | 0+0+1 | `--x` | Только выполнение |
| `0` | 0+0+0 | `---` | Нет прав |

### 4.1 Типовые комбинации прав

| chmod | Символы | Применение |
|-------|---------|------------|
| `755` | `rwxr-xr-x` | Исполняемые файлы, директории — стандарт |
| `644` | `rw-r--r--` | Обычные файлы (конфиги, тексты) |
| `600` | `rw-------` | Приватные файлы (SSH ключи, пароли) |
| `700` | `rwx------` | Приватные директории |
| `640` | `rw-r-----` | Файл читает группа, но не все остальные |
| `750` | `rwxr-x---` | Директория: группа может читать, others — нет |
| `400` | `r--------` | Только чтение владельцем (бэкапы) |
| `777` | `rwxrwxrwx` | ❌ Все права всем — **избегать в продакшене** |

> ⚠️ **На собесе часто спрашивают:** какие права у SSH приватного ключа?
> Ответ: `600` (`rw-------`). SSH откажется работать если права менее строгие — выдаст ошибку `Permissions too open`.

## 5. Команда chmod

### 5.1 Символьный синтаксис

```
chmod [кому][действие][права] файл

Кому:     u = владелец, g = группа, o = остальные, a = все
Действие: + = добавить, - = убрать, = = установить точно
Права:    r, w, x
```

```bash
chmod +x script.sh            # добавить execute всем
chmod u+x script.sh           # добавить execute только владельцу
chmod g+w file.txt            # добавить write группе
chmod o-r secret.txt          # убрать read у остальных
chmod go+w file.txt           # добавить write группе и остальным
chmod a=r file.txt            # установить только read для всех
chmod u=rwx,g=rx,o= file.sh   # точная установка для каждой группы
```

### 5.2 Числовой синтаксис

```bash
chmod 755 script.sh           # rwxr-xr-x
chmod 644 config.conf         # rw-r--r--
chmod 600 ~/.ssh/id_rsa       # rw------- (приватный SSH ключ)
chmod 400 backup.tar.gz       # r-------- (только чтение бэкапа)
```

### 5.3 Рекурсивное изменение прав

```bash
chmod -R 755 /var/www/html/   # изменить права рекурсивно
```

> 🚨 **Опасность:** `chmod -R 777 /var/www/` — частая ошибка. Даёт всем права на запись, включая веб-сервер. Если найдут уязвимость в приложении — смогут записать произвольные файлы.

**Правильный подход — разные права для файлов и директорий:**

```bash
# директории должны иметь x чтобы в них можно было войти
find /var/www -type d -exec chmod 755 {} \;

# файлы не должны иметь x без необходимости
find /var/www -type f -exec chmod 644 {} \;
```

## 6. Команда chown

`chown` меняет владельца и/или группу файла.

```bash
chown fa1ry file.txt            # сменить только владельца
chown fa1ry:fa1ry file.txt      # сменить владельца и группу
chown :developers file.txt      # сменить только группу
chown -R fa1ry:fa1ry /project   # рекурсивно для всей директории
```

**Синтаксис:**
- `fa1ry:fa1ry` — меняешь и владельца, и группу
- `fa1ry:` — меняешь только владельца
- `:fa1ry` — меняешь только группу

> ℹ️ `chown` требует прав root (`sudo`). Обычный пользователь не может передать файл другому владельцу — это сделано намеренно, чтобы нельзя было "подсунуть" файл другому пользователю.

**Команда `chgrp` — альтернатива для смены только группы:**

```bash
chgrp developers /var/www/project
chgrp -R www-data /var/www/html
```

## 7. umask — маска создания файлов

`umask` определяет какие права будут у новых файлов и директорий при создании. Работает как инвертированная маска — биты которые установлены в umask будут **убраны** из прав нового файла.

```bash
umask           # посмотреть текущую маску (обычно 022)
umask 027       # установить временно
umask -S        # показать в символьном виде: u=rwx,g=rx,o=
```

**Как вычислить итоговые права:**

```
Максимальные права файла:        666 (rw-rw-rw-)
Максимальные права директории:   777 (rwxrwxrwx)

При umask 022:
  Новый файл:       666 - 022 = 644 (rw-r--r--)
  Новая директория: 777 - 022 = 755 (rwxr-xr-x)

При umask 027:
  Новый файл:       666 - 027 = 640 (rw-r-----)
  Новая директория: 777 - 027 = 750 (rwxr-x---)
```

**Типичные значения umask:**

| umask | Файлы | Директории | Применение |
|-------|-------|------------|------------|
| `022` | `644` | `755` | Дефолт для большинства систем |
| `027` | `640` | `750` | Серверы — группа читает, остальные нет |
| `077` | `600` | `700` | Максимальная приватность |
| `002` | `664` | `775` | Совместная разработка в группе |

> ⚠️ **На собесе:** где устанавливается постоянная umask?
> - `/etc/profile` — глобально для всех пользователей
> - `~/.bashrc` или `~/.profile` — для конкретного пользователя
> - Для systemd сервисов — в unit файле через `UMask=027`

## 8. Специальные биты: SUID, SGID, Sticky bit

Значения 4, 2, 1 совпадают с `rwx` — но это разные октеты в числовой записи прав. Стандартные права пишутся тремя цифрами (`755`), а специальные биты — это четвёртая, ведущая цифра:

```
chmod 4755
      ^───── спецбиты:  SUID=4, SGID=2, Sticky=1
       ^──── owner:     7 = rwx (4+2+1)
        ^─── group:     5 = r-x (4+1)
         ^── others:    5 = r-x (4+1)
```

Когда спецбиты не нужны, первую цифру просто не пишут — `chmod 755` это то же самое что `chmod 0755`. Математика одинаковая (4+2+1 в одном октете), но позиции разные и смысл разный.

### 8.1 SUID (Set User ID) — бит 4

Когда SUID установлен на исполняемый файл — программа запускается с правами **владельца файла**, а не того кто её запустил. Отображается как `s` вместо `x` в правах владельца.

> Речь идёт **не о правах на сам файл**, а о том от чьего имени работает **процесс** после запуска.

Без SUID — обычное поведение:
```
Ты (alice) запускаешь программу → процесс работает от имени alice
```

С SUID:
```
Ты (alice) запускаешь программу → процесс работает от имени ВЛАДЕЛЬЦА ФАЙЛА
```

```bash
ls -la /usr/bin/passwd
-rwsr-xr-x 1 root root ... /usr/bin/passwd
   ^
   s означает SUID
```

**Почему `passwd` имеет SUID root:** обычный пользователь должен менять свой пароль, но пароли хранятся в `/etc/shadow` который принадлежит `root`. SUID позволяет `passwd` временно получить права `root` чтобы изменить этот файл.

```
alice → запускает /usr/bin/passwd (SUID, владелец = root)
           └── процесс временно становится root (UID=0)
                 └── открывает /etc/shadow ✅
                 └── записывает новый хэш пароля ✅
           └── процесс завершился → alice снова alice
```

Без SUID команда `passwd` упала бы с `Permission denied` — потому что `/etc/shadow` обычному пользователю недоступен.

```bash
chmod u+s file              # установить через символы
chmod 4755 file             # установить через цифры (4 = SUID)

# найти все SUID файлы в системе (важно для security audit)
find / -perm -4000 -type f 2>/dev/null
```

> 🚨 **Угроза безопасности:** SUID + уязвимость в программе = потенциальный root доступ для атакующего.
> Регулярно проверяйте список SUID файлов и сверяйте с эталоном.

### 8.2 SGID (Set Group ID) — бит 2

**На файле:** программа запускается с правами группы владельца файла (аналогично SUID но для группы).

Пример — команда `crontab` (управление задачами по расписанию):
```bash
ls -la /usr/bin/crontab
-rwxr-sr-x 1 root crontab /usr/bin/crontab
      ^
      s = SGID, группа владельца = crontab
```
Файлы расписаний хранятся в `/var/spool/cron/crontabs/` — директории доступной только группе `crontab`. Когда `alice` запускает `crontab -e`, процесс временно получает группу `crontab` и может записать её расписание в `/var/spool/cron/crontabs/alice`. Без SGID — `Permission denied`.

**На директории:** все новые файлы внутри наследуют **группу директории**, а не группу создателя. Полезно для общих папок команды.

```bash
chmod g+s /shared           # установить SGID на директорию
chmod 2755 /shared          # через цифры (2 = SGID)

ls -la /shared
drwxrwsr-x 2 root developers /shared
#     ^
#     s в правах группы
```

После установки SGID любой файл созданный в `/shared` будет принадлежать группе `developers` — независимо от того кто его создал.

> ⚠️ **Важно:** SGID на директории влияет **только на группу** нового файла, но не на его права (`rwx`). Права нового файла определяются как обычно — через **umask пользователя** который его создаёт.

```bash
# директория с SGID
drwxrwsr-x  root  developers  /shared

# alice (umask=022) создаёт файл:
-rw-r--r--  alice  developers  /shared/report.txt
#  ^^^^^^^^          ^^^^^^^^^^
#  644 — из umask    группа унаследована от /shared

# bob (umask=002) создаёт файл:
-rw-rw-r--  bob  developers  /shared/notes.txt
#  ^^^^^^^^        ^^^^^^^^^^
#  664 — из umask  группа унаследована от /shared
```

> ✅ **Реальный use case:** папка `/var/www/html` принадлежит группе `www-data` с SGID. Разработчики из группы создают файлы — они автоматически получают группу `www-data`. Веб-сервер может их читать без ручного изменения прав.

### 8.3 Sticky bit — бит 1

**Историческое применение — на файлах (устарело):** sticky bit изначально создавался для исполняемых файлов, а не директорий. Он говорил ядру: после завершения программы не удаляй её образ из свопа, оставь для быстрого повторного запуска.

Когда программа запускается — ядро читает её с диска и загружает в RAM. Без sticky bit при следующем запуске всё повторялось заново: снова читать с диска, снова грузить в RAM. Диски в 70-х были механическими и медленными — головка физически ездила по пластине чтобы найти нужный сектор, и каждый запуск занимал ощутимое время. Sticky bit оставлял образ программы в свопе как промежуточный слой:

```
Без sticky bit:  Диск (медленно) → RAM → выполняется
Со sticky bit:   Своп (быстрее)  → RAM → выполняется
```

Тогдашние компьютеры были многопользовательскими — десятки людей одновременно работали на одной машине. Без sticky bit каждый запуск одной программы читал с диска заново. Со sticky bit — образ лежит в свопе, все пользователи грузят оттуда.

Сейчас RAM стало много, диски стали быстрыми (SSD), и ядро само умно управляет кешированием. **На современных Linux-системах sticky bit на файле игнорируется** — бит установить можно, но ядро на него не смотрит.

**Актуальное применение — на директориях:** удалить файл может только его **владелец**, даже если у других есть право на запись в эту директорию. Отображается как `t` вместо `x` в правах others.

> **Почему нельзя просто убрать `w` у директории?** Это решало бы другую задачу. Если убрать `w` у директории для others — никто вообще не сможет создавать файлы внутри. Sticky bit нужен именно в ситуации когда `w` у всех **есть** (каждый может создавать файлы), но удалять чужие файлы нельзя.
>
> ```
> Без sticky, с w у всех:   каждый может создавать И удалять чужие файлы ❌
> Убрать w у всех:          никто не может ни создавать, ни удалять         ❌
> Sticky + w у всех:        каждый создаёт свои, удаляет только свои        ✅
> ```

```bash
ls -la /tmp
drwxrwxrwt 10 root root ... /tmp
         ^
         t означает sticky bit

chmod +t /shared            # установить sticky bit
chmod 1777 /shared          # через цифры (1 = sticky bit)
```

`/tmp` открыта на запись всем (`rwxrwxrwx`) — но вы не можете удалить файл другого пользователя. Только свои файлы или с правами `root`.

> ℹ️ **Про наследование прав:** файлы **не наследуют** права родительской директории при создании. Права нового файла определяет **umask пользователя** — это описано в разделе 7. Единственное что директория может "передать" новым файлам через специальные биты — это группу (через SGID).

### 8.4 Комбинирование специальных битов

| chmod | Биты | Результат | Применение |
|-------|------|-----------|------------|
| `4755` | SUID | `rwsr-xr-x` | Исполняемый файл с SUID |
| `2755` | SGID | `rwxr-sr-x` | Директория с наследованием группы |
| `1777` | Sticky | `rwxrwxrwt` | Общая директория (/tmp) |
| `6755` | SUID+SGID | `rwsr-sr-x` | Оба бита |
| `3777` | SGID+Sticky | `rwxrwsrwt` | Общая директория с наследованием группы |

> ⚠️ **Важно:** если вместо `s` видите `S` (заглавная) — это означает что SUID/SGID установлен, но бит execute **не установлен**. Обычно это ошибка конфигурации.

## 9. ACL — расширенные права доступа

Стандартные права Linux ограничены тремя категориями. **ACL (Access Control Lists)** позволяет задать права для конкретных пользователей и групп — на файлы и директории.

```bash
apt install acl               # установить если нет
```

---

### 9.1 Синтаксис

```bash
setfacl -m u:username:rwx file.txt
           ^          ^
           |          └── права: те же r, w, x что и обычно
           └── кому: u=user, g=group, o=others
```

Флаги команды `setfacl`:
```
-m   → modify    (добавить/изменить правило)
-x   → remove    (удалить правило)
-b   → remove all (удалить все ACL с файла)
-R   → recursive  (применить ко всем файлам внутри директории)
-d   → default    (новые файлы в директории наследуют правила)
```

---

### 9.2 Пример

Есть файл `report.txt`, владелец `alice`. Нужно дать `bob` право только читать, группе `developers` — читать и писать, остальным — ничего:

```bash
setfacl -m u:bob:r-- report.txt
setfacl -m g:developers:rw- report.txt
setfacl -m o::--- report.txt
```

Проверяем результат:
```bash
getfacl report.txt
# owner: alice
# group: alice
# user::rw-              ← alice (владелец)
# user:bob:r--           ← bob персонально
# group::r--             ← стандартная группа файла
# group:developers:rw-   ← группа developers
# mask::rw-
# other::---             ← все остальные
```

Файл в `ls` показывает `+` в конце прав — сигнал что на файле есть ACL:
```bash
ls -la report.txt
-rw-rw-r--+ 1 alice alice report.txt
#          ^
#          есть ACL
```

---

### 9.3 Mask — потолок прав

Когда на файле есть ACL, появляется запись `mask`. Она работает как **фильтр** — не даёт права, а только срезает лишнее через логическое И (AND):

```
bob записан:  r - -
mask:         r w x
              ─────
реально:      r - -   ← mask rwx не мешает, bob получает свои r--

bob записан:  r w x
mask:         r - -
              ─────
реально:      r - -   ← mask срезала w и x
```

Mask срабатывает только **вниз** — она не может дать прав больше чем записано у пользователя. `mask::rwx` — это по сути отключённая mask, потолок такой высокий что никому не мешает.

**Зачем тогда mask нужна:**

Представь файл с 10 ACL-записями. Пришёл аудит, нужно срочно всем закрыть запись (`w`) на время проверки. Без mask — перебирать все 10 записей по одной. С mask — одна команда:

```bash
setfacl -m mask::r-- file.txt   # всем срезали w одним движением

# после аудита — возвращаем потолок
setfacl -m mask::rwx file.txt   # mask больше не мешает, каждый получает свои права
```

Сами записи не трогались — после возврата mask все права восстановились автоматически.

**На кого влияет mask:**

```
user:: (владелец)          ← mask НЕ влияет
user:bob: (именованный)    ← mask влияет
group:: (группа файла)     ← mask влияет
group:developers:          ← mask влияет
other:: (остальные)        ← mask НЕ влияет
```

Владелец и others — всегда получают именно те права что им выставлены. Mask влияет только на именованных пользователей и группы.

**Effective rights в выводе getfacl:**

Когда mask срезает права — `getfacl` показывает рядом с записью комментарий `#effective:`. Это ключевой маркер при дебаге — сразу видно что реально получает пользователь, а не что написано в записи:

```bash
getfacl report.txt
# user::rw-
# user:bob:rwx            #effective:r--   ← bob записан с rwx, но реально r--
# group:developers:rw-    #effective:r--   ← то же самое
# mask::r--
# other::---
```

---

### 9.4 Нюанс с chmod и mask

Если на файле есть ACL — `chmod g+x` или `chmod g-w` меняет не права группы напрямую, а **mask**. Это неожиданно влияет на всех именованных пользователей и группы сразу:

```bash
# было
# user:bob:rw-
# group:developers:rw-
# mask::rw-

chmod g-w report.txt   # думаешь убираешь w только у группы файла

# стало
# user:bob:rw-          #effective:r--  ← запись не изменилась, но реально r--
# group:developers:rw-  #effective:r--  ← то же самое
# mask::r--             ← mask срезал w у всех
```

`bob` пострадал хотя ты его не трогал — mask срезал права всем именованным записям разом.

> ⚠️ **Вывод:** если на файле есть ACL — управляй правами только через `setfacl`. `chmod` использовать осторожно — он двигает mask и неявно влияет на всех.

---

### 9.5 Порядок проверки прав

Когда пользователь обращается к файлу с ACL — система проверяет записи **сверху вниз** и останавливается на первом совпадении:

```
1. Владелец файла?          → применить user::
2. Есть именованная запись? → применить user:bob:
3. Входит в именованную группу? → применить group:developers:
4. Other                    → применить other::
```

Важный момент: **если пользователь попал под именованную запись `u:bob` — права групп на него уже не смотрятся**, даже если он состоит в группе `developers`. Система останавливается на шаге 2.

```bash
# bob состоит в группе developers
# user:bob:r--            ← система нашла bob здесь и остановилась
# group:developers:rwx    ← это уже не проверяется для bob
```

Это та же логика что и с парадоксом владельца из раздела 3 — система идёт по первому совпадению.

---

### 9.6 Другие команды

```bash
# посмотреть ACL файла
getfacl file.txt

# удалить конкретное ACL правило
setfacl -x u:username file.txt

# удалить все ACL правила
setfacl -b file.txt

# дефолтные ACL — новые файлы в директории наследуют правила
setfacl -d -m g:www-data:rx /var/www/
```

> ✅ **На собесе:** когда использовать ACL вместо стандартных прав?
> Когда нужно дать доступ конкретному пользователю не добавляя его в группу. Например: дать разработчику read доступ к логам nginx не добавляя его в группу `www-data`.
