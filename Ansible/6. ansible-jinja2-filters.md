# Тема 6: Jinja2 — базовые фильтры

## Что такое Jinja2 и зачем он нужен

Jinja2 — это шаблонизатор, который Ansible использует везде, где в тексте встречается конструкция `{{ }}`. Задача Jinja2 простая: взять то, что написано внутри `{{ }}` (переменную, выражение), вычислить его и подставить готовое значение на это место.

Фильтр — это функция, которая обрабатывает значение **перед** тем, как оно будет подставлено. Синтаксис:

```jinja2
{{ переменная | имя_фильтра }}
```

Знак `|` — труба, работает по тому же принципу, что и pipe в Linux: результат слева передаётся на вход фильтру справа. Фильтры можно цеплять цепочкой, выполнение идёт слева направо:

```jinja2
{{ значение | filter_1 | filter_2 }}
```

Как это выглядит на практике — в playbook и в шаблоне — разберём сразу ниже.

---

## Где физически живут `{{ }}` и фильтры

Есть два места, где это пишется:

### 1. Прямо в playbook (YAML-файл с задачами)

Внутри `tasks:` — в любом параметре модуля, где ты подставляешь значение переменной:

```yaml
- hosts: webservers
  vars:
    app_name: MyApp          # переменная, которую мы сами задаём

  tasks:
    - name: Вывести имя хоста в верхнем регистре
      ansible.builtin.debug:
        msg: "Хост: {{ inventory_hostname | upper }}"

    - name: Создать директорию с именем из переменной
      ansible.builtin.file:
        path: "/opt/{{ app_name | lower }}"   # app_name — обычная переменная, не магическая
        state: directory
```

`inventory_hostname` — встроенная **magic-переменная** Ansible. "Magic" — это официальный термин Ansible именно для таких переменных: они нигде не объявляются вручную (не в `vars:`, не в `group_vars`), а появляются автоматически сами по себе в каждом playbook'е, потому что их всегда выставляет сам движок Ansible на основе инвентаря и контекста выполнения. `inventory_hostname` — это как раз имя хоста, для которого сейчас выполняется задача. `app_name` — обычная переменная, которую мы сами объявили в блоке `vars:` (в реальном playbook'е она чаще лежит в `group_vars`/`host_vars`, здесь для наглядности прямо в файле).

Здесь `{{ app_name | lower }}` — это просто текст внутри YAML-строки. Ansible видит `{{ }}`, понимает "тут надо подставить переменную", применяет фильтр `lower` перед подстановкой, и в итоге в модуль `file` уходит уже готовая строка типа `/opt/myapp`.

### 2. Внутри `.j2`-шаблона (файл, который обрабатывает модуль `template`)

Это тот же принцип, что и в модуле `template`, которым ты уже пользовался на практике. У тебя есть файл `something.conf.j2`, и внутри него — обычный текст конфига, но с вкраплениями `{{ }}`:

```jinja2
server_name={{ inventory_hostname }}
log_level={{ log_level | default('info') }}
timeout={{ connection_timeout | int }}
```

Модуль `template` берёт этот `.j2`-файл, прогоняет через Jinja2, все `{{ }}` заменяются на реальные значения с учётом фильтров — и на целевой машине появляется уже готовый конфиг-файл без всяких `{{ }}`, просто с подставленными значениями.

```yaml
- name: Сгенерировать конфиг из шаблона
  ansible.builtin.template:
    src: something.conf.j2
    dest: /etc/myapp/something.conf
```

Про расположение файла: `.j2`-шаблон физически лежит рядом с playbook'ом, в подпапке `templates/` (это стандартное соглашение Ansible). В параметре `src:` указывается только имя файла — Ansible сам ищет его в `templates/` относительно playbook'а. `dest:` — это уже путь на **целевой машине**, куда положить готовый результат.

Наглядно это выглядит так:

```
deploy/
├── site.yml                        ← сам playbook (control node)
└── templates/
    └── something.conf.j2           ← шаблон, лежит здесь по соглашению
```

```yaml
# site.yml
- name: Сгенерировать конфиг из шаблона
  ansible.builtin.template:
    src: something.conf.j2          # ищется в deploy/templates/
    dest: /etc/myapp/something.conf # это уже путь на целевой машине
```

Если `something.conf.j2` не лежит в `templates/`, а, скажем, прямо рядом с playbook'ом — Ansible его не найдёт, и задача упадёт с ошибкой "template file not found".

> **Важно:** отдельной настройки в `ansible.cfg` для пути к шаблонам нет. Ansible всегда сам ищет `.j2`-файл в папке `templates/` рядом с playbook'ом — это встроенное поведение, не настраиваемое через конфиг.

## Зачем тут вообще фильтр, а не просто переменная

Вот реальный сценарий, где фильтр решает конкретную проблему.

Ты делаешь `register` на вывод команды:

```yaml
- name: Получить имя хоста
  ansible.builtin.command: cat /etc/hostname
  register: hostname_output
```

В `hostname_output.stdout` может оказаться `"myhost\n"` — с переносом строки на конце, потому что вывод команды часто "грязный". Если ты просто вставишь `{{ hostname_output.stdout }}` в конфиг — туда улетит и мусорный перенос строки, и это может сломать парсинг конфига на стороне приложения.

Решение:

```yaml
msg: "Хост: {{ hostname_output.stdout | trim }}"
```

`trim` срезает лишние пробелы/переносы — и дальше по коду (условие, сравнение значений, запись в файл) идёт уже чистое значение.

Та же логика работает и для `default` — разберём его подробно ниже, вместе с остальными фильтрами.

---

## default — значение по умолчанию

**Зачем:** переменная может быть не задана для конкретного хоста (нет в `host_vars`/`group_vars`) — без `default` playbook упадёт с ошибкой "variable is undefined". `default` подставляет запасное значение и выполнение продолжается.

**Пример в `.j2`-шаблоне:**

```jinja2
log_level={{ log_level | default('info') }}
```

Если для хоста нигде не задан `log_level`, в конфиг уйдёт `log_level=info` вместо падения playbook'а.

**Пример в playbook:**

```yaml
- name: Установить таймаут соединения
  ansible.builtin.set_fact:
    timeout: "{{ custom_timeout | default(30) }}"
```

**Важный нюанс (частый вопрос на собесе):** у фильтра `default(x)` без второго аргумента есть ровно одно условие срабатывания — переменной вообще нет в плейбуке. Разберём на двух случаях.

**Случай 1 — переменной нет вообще.** Мы ни разу не написали `log_level` ни в `vars`, ни в `host_vars`, ни в `group_vars`:

```jinja2
{{ log_level | default('info') }}
```

Здесь `default` сработает — подставится `info`, потому что Ansible не находит `log_level` нигде.

**Случай 2 — переменная есть, но без значения.** Мы её объявили, просто ничего в неё не положили:

```yaml
vars:
  log_level:        # просто двоеточие и ничего дальше — это None (null)
  # или
  log_level: ""     # явно пустая строка
```
```jinja2
{{ log_level | default('info') }}
```

Здесь `default` **не сработает** — результат будет пустым, а не `info`. Разница со случаем 1: Ansible видит ключ `log_level` в `vars`, значит переменная "определена" — неважно, что внутри неё пусто.

Чтобы фильтр реагировал и на пустые значения, нужен второй аргумент `true`:

```jinja2
{{ log_level | default('info', true) }}
```

Классический вопрос-ловушка: "почему `default` не сработал, если я передал пустую строку?" — потому что переменная была определена, просто пустая.

---

## trim — обрезка пробелов

**Зачем:** значение из `register` часто "грязное" — с переносом строки или пробелами на конце, которые попадают туда из вывода команды в терминале.

**Пример в playbook:**

```yaml
- name: Получить имя хоста
  ansible.builtin.command: cat /etc/hostname
  register: hostname_output

- name: Показать имя хоста без мусора
  ansible.builtin.debug:
    msg: "Хост: {{ hostname_output.stdout | trim }}"
```

Без `trim` в `hostname_output.stdout` может лежать `"myhost\n"` — и этот `\n` улетит дальше в конфиг или в сравнение значений, где может всё сломать.

## upper / lower — регистр строки

**Зачем:** нормализация значений, которые приходят непредсказуемо (от пользователя, из внешнего источника, из вывода другой команды).

**Пример в playbook:**

```yaml
- name: Создать директорию с именем приложения в нижнем регистре
  ansible.builtin.file:
    path: "/opt/{{ app_name | lower }}"
    state: directory
```

Если кто-то в `group_vars` записал `app_name: MyApp`, а на диске нужен путь строго `/opt/myapp` — фильтр приводит к единому виду независимо от того, как ввели переменную.

---

## length — длина строки, списка, словаря

**Зачем:** чаще всего используется в условиях `{% if %}` / `when` — чтобы проверить, есть ли вообще данные, прежде чем с ними что-то делать.

**Пример в playbook (`when`):**

```yaml
- name: Установить пакеты, если список не пустой
  ansible.builtin.apt:
    name: "{{ extra_packages }}"
    state: present
  when: extra_packages | length > 0
```

Без этой проверки задача попыталась бы выполниться даже с пустым списком, что не всегда безопасно в зависимости от модуля.

> **Примечание:** в Jinja2/Python пустой список `[]`, пустой словарь `{}` и пустая строка `""` сами по себе приводятся к `false` (truthiness). Поэтому для списков `when: extra_packages` отработает точно так же, как `when: extra_packages | length > 0` — короче и без явной длины. `| length > N` нужен только тогда, когда важно конкретное количество элементов (например, `| length > 2`), а не просто факт "список не пустой".

---

## join — склейка списка в строку

**Зачем:** списки в Ansible — это Python-списки, а конфигу на целевой машине часто нужна просто строка с разделителем.

**Пример в `.j2`-шаблоне:**

```jinja2
allowed_hosts={{ allowed_hosts_list | join(', ') }}
```

Если `allowed_hosts_list: ['10.0.0.1', '10.0.0.2', '10.0.0.3']`, в конфиг уйдёт строка `allowed_hosts=10.0.0.1, 10.0.0.2, 10.0.0.3`.

---

## replace — замена подстроки

**Зачем:** точечная правка значения на лету, без отдельной задачи `lineinfile` или `replace`-модуля, когда правки нужны именно в момент подстановки.

**Пример в `.j2`-шаблоне:**

```jinja2
config_path={{ base_path | replace('\\', '/') }}
```

Пример: значение пришло с обратными слэшами (например, из Windows-стиля пути в переменной), а конфигу на Linux-машине нужны прямые.

---

## int / float / bool — приведение типа

**Зачем:** значение из `register.stdout` — это всегда **строка**, даже если по смыслу там число или логическое значение. Это создаёт две разные проблемы:
- для арифметики или числового сравнения строки сравниваются неправильно (например, `"9" > "10"` как строки — `true`, что неверно для чисел);
- для логической проверки в Jinja2 **любая непустая строка — это истина**, включая саму строку `"false"`.

Оба случая решаются приведением типа: `int`/`float` — для чисел, `bool` — для логики.

**Пример с числом:**

```yaml
- name: Получить количество свободных мест на диске
  ansible.builtin.shell: df --output=avail /opt | tail -1
  register: free_space

- name: Предупредить, если места мало
  ansible.builtin.debug:
    msg: "Мало места на диске!"
  when: free_space.stdout | trim | int < 1000000
```

Здесь в одной цепочке сразу два фильтра: `trim` убирает пробелы, `int` превращает результат в число для корректного сравнения `<`.

**Пример с логическим значением:**

```yaml
- name: Проверить состояние через самописный скрипт
  ansible.builtin.shell: /opt/scripts/check_maintenance_mode.sh
  register: maintenance_check

- name: Выполнить действие, если режим обслуживания включён
  ansible.builtin.debug:
    msg: "Идёт обслуживание, пропускаем деплой"
  when: maintenance_check.stdout | trim | bool
```

Фильтр `bool` приводит строки `'true'`, `'yes'`, `'1'`, `'y'` к настоящему логическому `true`, а всё остальное — к `false`. И здесь снова цепочка: сначала `trim` (убрать мусор из вывода команды), потом `bool` (превратить строку в логическое значение) — порядок в трубе важен.

Обрати внимание: этот пример специально показывает случай с самописным скриптом, который просто печатает `"true"`/`"false"` в stdout. Если бы речь шла о проверке статуса стандартного systemd-сервиса, правильнее использовать не `shell`, а модуль `ansible.builtin.systemd` — он сразу возвращает структурированный статус (например, `status.ActiveState == 'active'`), и проблема "строка вместо логического значения" там просто не возникает.

## omit — пропустить параметр модуля

**Зачем:** иногда нужно, чтобы параметр модуля **вообще не передавался**, если переменная не задана — а не передавался с пустым значением или заваливал playbook ошибкой. Обычная строка `''` или `None` в качестве значения параметра — это не то же самое, что параметр отсутствует.

**Пример в playbook:**

Задача одна и та же, но переменная `custom_uid` в двух разных playbook'ах (или для двух разных хостов) задана по-разному:

```yaml
# host_vars/host-a.yml
custom_uid: 1500
```

Для **host-b** переменная `custom_uid` вообще не объявлена в `host_vars` — её там просто нет.

```yaml
- name: Настройка системного пользователя
  ansible.builtin.user:
    name: "deploy"
    uid: "{{ custom_uid | default(omit) }}"
```

Для **host-a** Ansible реально выполнит задачу так, будто она написана:

```yaml
- name: Настройка системного пользователя
  ansible.builtin.user:
    name: "deploy"
    uid: 1500
```

На **host-b** `default(omit)` полностью убирает параметр `uid:` из вызова, и задача выполняется так, будто её вообще не было в playbook'е:

```yaml
- name: Настройка системного пользователя
  ansible.builtin.user:
    name: "deploy"
```

В этом случае операционная система сама назначит следующий свободный UID. Если бы вместо `omit` был обычный дефолт вроде `default('')`, в модуль ушла бы пустая строка `uid: ""`, что для этого параметра — ошибка, а не "пропусти меня".

`omit` всегда используется в связке с `default()`, отдельно он не имеет смысла.

**Важное синтаксическое ограничение:** `omit` работает, только когда всё выражение `{{ ... }}` составляет **весь параметр целиком**, а не часть строки:

```yaml
uid: "{{ custom_uid | default(omit) }}"      # работает — omit это весь параметр

uid: "user-{{ custom_uid | default(omit) }}" # не сработает — omit тут часть строки, а не весь параметр
```

Во втором случае Ansible не может "вычеркнуть" только кусок строки — параметр либо передаётся целиком, либо не передаётся вовсе.

## mandatory — обязательная переменная

**Зачем:** есть переменные, для которых **нет разумного значения по умолчанию** — например, пароль от базы данных или адрес продовского сервера. Если такую переменную забыли прописать в `host_vars`, playbook не должен молча продолжать работу с пустым или дефолтным значением — он должен упасть сразу, с понятной ошибкой, а не сломать что-то на целевой машине.

**Пример в `.j2`-шаблоне:**

```jinja2
db_password={{ target_db_password | mandatory }}
```

Если `target_db_password` не определена, Ansible немедленно останавливает выполнение с ошибкой вида `"A mandatory variable was is undefined"`, вместо того чтобы сгенерировать конфиг с пустым паролем.

По сути `mandatory` — это противоположность `default`: `default` говорит "если переменной нет, подставь вот это", `mandatory` говорит "если переменной нет, останови всё немедленно".

---

## Итоговая идея

Фильтр — это не абстрактная теория, а инструмент для конкретной практической проблемы: "значение пришло не в том виде, в каком оно нужно дальше" — грязное после `register`, не того регистра, не того типа, отсутствует вовсе. Фильтр решает эту проблему прямо в месте подстановки, без отдельной задачи в playbook.
