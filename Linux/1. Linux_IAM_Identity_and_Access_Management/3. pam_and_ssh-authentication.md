## 1. Архитектура

### Что происходит когда вы логинитесь по SSH

Ключевой вопрос: кто именно проверяет ваш пароль? Не sshd и не ядро, это делает PAM. sshd только принимает соединение и делегирует проверку.

1. **Запрос.** Пользователь подключается, `sshd` запрашивает логин и пароль.
2. **Проверка.** `sshd` передаёт данные в PAM, и тот по правилам из `/etc/pam.d/sshd` поочерёдно опрашивает модули. Тип `auth` проверяет пароль (`pam_unix.so` сверяет хэш с `/etc/shadow`). Тип `account` проверяет, можно ли этой учётке входить: не заблокирована ли, не истёк ли срок.
3. **Вердикт.** PAM возвращает `sshd` ответ: SUCCESS или код ошибки («пароль неверен», «аккаунт заблокирован»).
4. **Финал.** При ошибке `sshd` обрывает соединение, и пользователь видит `Permission denied`. При успехе `sshd` просит PAM открыть сессию (тип `session`: применить `ulimit`, записать вход в `utmp`/`wtmp`) и после этого запускает командную оболочку.

## 2. PAM — Pluggable Authentication Modules

**Pluggable Authentication Modules** — дословно «подключаемые модули аутентификации». Название отражает главную идею: каждый способ проверки пользователя (пароль, TOTP (одноразовый код из приложения типа Google Authenticator), LDAP, fingerprint) — это отдельный **модуль** (`.so` файл), который можно **подключить или убрать** как плагин, не трогая само приложение.

### Зачем вообще нужен PAM и когда он включается?

**PAM — это вышибала на входе.** Он просыпается только тогда, когда происходит аутентификация (проверка личности) или смена контекста безопасности: попытка войти, повысить права, открыть сессию. На обычные команды вроде `ls` или `mkdir` он не влияет.

**Когда именно срабатывает PAM?** Вы сталкиваетесь с ним каждый раз, когда:
- Подключаетесь к серверу по SSH (`sshd` вызывает PAM, пароль проверяет `pam_unix.so`)
- Хотите выполнить команду от админа через `sudo` (`sudo` вызывает PAM, ваш пароль проверяет `pam_unix.so`)
- Переключаетесь на другого пользователя через `su alice` (`su` вызывает PAM, пароль проверяет `pam_unix.so`, а root проходит без пароля благодаря `pam_rootok.so`)
- Вводите пароль на экране блокировки Linux (`gdm`/`lightdm` вызывают PAM, пароль проверяет `pam_unix.so`)
- Меняете свой пароль через команду `passwd` (`passwd` вызывает PAM, новый пароль записывает `pam_unix.so`)

📌 **Важно:** До PAM каждая программа (`login`, `sudo`, `sshd`) сама реализовывала проверку пароля. Хотите добавить LDAP — патчите все программы, хотите 2FA — снова патчите все.

### Конфигурационные файлы

Каждое приложение, которое использует PAM, имеет **свой конфиг** в `/etc/pam.d/`. Именно там написано: какие модули запускать при входе через это приложение, в каком порядке, и что делать если модуль вернул ошибку.

Но «каждое приложение» — это не любая программа на системе, а только те, которые **сами написаны с поддержкой PAM**. То есть разработчик специально добавил в код вызов `pam_authenticate()`. `ls`, `mkdir`, `touch` — им не нужно проверять личность пользователя, они просто работают с файлами, и конфига в `/etc/pam.d/` у них нет. Личность проверена один раз при входе, дальше доступ к файлам и каталогам решает ядро по UID и правам.

А `sshd`, `sudo`, `su`, `passwd`, `gdm` — это программы, которые по смыслу своей работы должны проверять кто ты. Их разработчики специально интегрировали PAM. Конфиг в `/etc/pam.d/` есть только у тех программ, которые **пускают или не пускают** пользователя куда-либо. Это небольшой список, не тысячи программ на системе.

```bash
ls /etc/pam.d/
# chfn  chsh  common-account  common-auth  common-password  common-session
# cron  gdm-password  login  passwd  su  sshd  sudo  ...
```

Каждая строка в таком файле — одно правило, то есть одна проверка: проверить пароль, проверить не заблокирован ли аккаунт, применить лимиты и т.д. Когда пользователь, например, запускает `sudo`, PAM читает `/etc/pam.d/sudo` и **последовательно сверху вниз** прогоняет все строки. Такая цепочка проверок называется стеком. Итог всего стека — либо SUCCESS, либо FAIL.

Конфиги PAM читаются при каждой новой попытке входа, поэтому правила меняются на лету: изменили файл в `/etc/pam.d/`, и новые правила сразу действуют для всех новых подключений, без пересборки и перезапуска приложений.

### Формат строки

```
<тип>   <управление>   <модуль.so>   [аргументы]
```

Квадратные скобки означают, что часть необязательная: первые три колонки есть в каждой строке, а аргументы указывают только когда нужно.

```
auth    required    pam_unix.so    nullok
│       │           │              │
│       │           │              └── аргументы модуля
│       │           └── какой модуль вызвать (ищется в /lib/x86_64-linux-gnu/security/)
│       └── что делать с результатом
└── какой тип задачи: auth / account / password / session
```

### Четыре типа

Тип в первой колонке показывает, на каком этапе работы программы эта строка должна сработать. Вход состоит из нескольких этапов, и на каждом PAM запускает только строки своего типа. Чтобы выбрать тип, нужно решить, когда модуль должен сработать, и посмотреть в справке модуля (`man`), какие типы он поддерживает: часто он умеет только один или два, и выбирать почти нечего.

**`auth`** — кто ты?

Проверяет личность пользователя — запрашивает пароль, токен, сертификат. Именно этот тип отвечает на вопрос «правда ли ты тот, за кого себя выдаёшь». Также устанавливает group membership.

**`account`** — можешь ли ты войти прямо сейчас?

Личность уже проверена, но этот тип решает — пускать ли вообще. Не истёк ли пароль, не заблокирован ли аккаунт, разрешено ли входить с этого хоста или в это время суток.

**`password`** — смена пароля

Вызывается только командой `passwd`. Проверяет сложность нового пароля, историю — чтобы нельзя было поставить старый пароль обратно.

**`session`** — что происходит после входа

Настраивает окружение уже после того как пользователя пустили: применяет ulimits, монтирует домашнюю директорию, записывает в системные логи (`wtmp`, `lastlog`), устанавливает переменные окружения. И симметрично — убирает всё это при выходе.

### Управляющие флаги

Второй столбец в каждой строке PAM-конфига — это флаг, который говорит что делать с результатом модуля: останавливать стек или продолжать, считать итог успехом или провалом.

**`required`** — должен пройти, но стек не останавливается

Даже если модуль вернул ошибку — PAM продолжает выполнять остальные строки. Итог всё равно будет FAIL, но злоумышленник не поймёт на каком шаге упало — время ответа одинаковое.

**`requisite`** — провал = немедленная остановка

Если модуль вернул ошибку — PAM сразу возвращает FAIL, не выполняя остальное. Используется когда продолжать бессмысленно или опасно: например, пользователь не существует — незачем спрашивать TOTP-код, это утечка информации.

**`sufficient`** — успех = немедленный пропуск

Если модуль успешен — PAM сразу возвращает SUCCESS, не проверяя остальное. Используется для альтернативных способов входа: например, root запускает `su` — незачем просить пароль.

**`optional`** — результат не влияет на итог

Модуль выполняется, но его успех или провал игнорируется. Используется для побочных действий — например показать сообщение дня (`pam_motd.so`, его строки есть в `/etc/pam.d/sshd`, найти можно командой `grep -r pam_motd /etc/pam.d/`). Сообщение дня (MOTD — Message of the Day) — это текст который показывается пользователю сразу после успешного входа:

```
Welcome to Ubuntu 22.04.3 LTS
Last login: Mon Jun 9 12:34:56 2026 from 192.168.1.1
System load: 0.1   Disk usage: 45%
```

Если модуль не смог показать MOTD (например файл не существует) — это не повод отказать во входе. Поэтому `optional`.

**Скобочная нотация `[...]`**

Простые флаги — это сокращения. На самом деле каждый из них означает набор правил «если модуль ответил так — сделай вот так». Например, `required` — это то же самое, что:

```
[success=ok new_authtok_reqd=ok ignore=ignore default=bad]
```

Читается слева направо как список условий. Модуль ответил `success` (всё прошло успешно) — действие `ok`: засчитать результат и идти дальше. Ответил любой другой статус (`default`) — действие `bad`: запомнить провал, итог стека будет FAIL. Скобочная форма позволяет написать такие условия самому, когда четырёх готовых флагов не хватает.

Формат: `[статус_1=действие_1 статус_2=действие_2 ...]`

Вот как выглядит начало `common-auth` в Debian:

```
auth  [success=1 default=ignore]  pam_unix.so nullok
auth  requisite                   pam_deny.so
auth  required                    pam_permit.so
```

Первая строка говорит: если пароль верный (`success`), перепрыгни одну следующую строку, то есть `pam_deny.so`, и попади на `pam_permit.so`, который впускает. Если пароль неверный (любой другой статус, `default`), действие `ignore`: просто иди дальше, а на следующей строке `pam_deny.so` с флагом `requisite` сразу отказывает. Обычными флагами такой «перепрыжок» не выразить. Сверить с вашей системой можно командой `grep -v '^#' /etc/pam.d/common-auth`.

На практике такие строки редко пишут вручную, их создаёт `pam-auth-update`. Умение нужно, чтобы читать готовые конфиги. Ниже полный справочник: какие бывают статусы и действия.

**Что слева (статус)** — код который вернул модуль. У каждого модуля есть около 30 стандартных кодов ответа. Вот самые частые:
- `success` — всё прошло успешно
- `auth_err` — неверный пароль
- `user_unknown` — пользователя не существует
- `maxtries` — превышено число попыток (именно это возвращает `pam_faillock`)
- `authinfo_unavail` — невозможно получить доступ к базе (например, упал LDAP)
- `default` — все остальные статусы не перечисленные явно

**Что справа (действие)** — список строго ограничен: 6 ключевых слов + числа для прыжков.

Числа: `N` — пропустить N следующих строк стека.

Ключевые слова:
- `ignore` — игнорировать, идти на следующую строку как будто ничего не произошло
- `bad` — запомнить ошибку, продолжить стек, но в конце будет FAIL
- `die` — немедленно остановить стек, вернуть FAIL (аналог `requisite`)
- `ok` — засчитать результат модуля и продолжить стек; уже накопленный провал это не отменяет
- `done` — немедленно SUCCESS если до этого не было `bad` (аналог `sufficient`)
- `reset` — сбросить всю память о предыдущих ошибках, начать с чистого листа

### Модуль (`.so` файл) — что именно проверяет

Третий столбец — это и есть сам «подключаемый модуль», файл с расширением `.so` (shared object, динамическая библиотека). Каждый модуль реализует один конкретный способ проверки. PAM ищет их в `/lib/x86_64-linux-gnu/security/`.

```bash
ls /lib/x86_64-linux-gnu/security/
# pam_unix.so  pam_deny.so  pam_permit.so  pam_faillock.so
# pam_google_authenticator.so  pam_limits.so  pam_nologin.so ...
```

Установил пакет `libpam-google-authenticator` — в этой папке появился новый `.so` файл, и теперь его можно использовать в конфиге.

### Аргументы — как настроить поведение модуля

Четвёртый столбец — необязательные параметры, которые передаются конкретному модулю. Каждый модуль поддерживает свои аргументы, общих нет. Посмотреть аргументы конкретного модуля можно через man:

```bash
man pam_unix
man pam_faillock
man pam_limits
```

Например для `pam_unix.so`:
- `nullok` — разрешить пустой пароль (без него пустой пароль = отказ)
- `try_first_pass` — не спрашивать пароль повторно, взять уже введённый из предыдущего модуля
- `remember=5` — запомнить 5 последних паролей, не давать повторять
- `debug` — писать подробные логи в syslog (удобно при отладке)

### Собираем всё вместе

Теперь, когда понятно, из чего состоит строка, можно прочитать настоящий конфиг. Так может выглядеть начало `/etc/pam.d/sshd`:

```
auth     required   pam_unix.so       # проверить пароль
account  required   pam_nologin.so    # не закрыт ли сервер на обслуживание
session  required   pam_limits.so     # применить лимиты к сессии
```

Каждая строка читается слева направо: когда проверять (тип), что делать с результатом (флаг), чем проверять (модуль). Например, первая строка означает: на этапе `auth` вызвать модуль `pam_unix.so`, и если он вернул ошибку, итог всего стека будет FAIL. Аргументов в этих строках нет. Вторая строка использует модуль `pam_nologin.so`: он запрещает вход, если существует файл `/etc/nologin`, так сервер закрывают на обслуживание.

Хотите, чтобы учётка блокировалась после пяти неверных паролей — дописываете строку с модулем `pam_faillock.so`. Код `sshd` при этом не меняется.

### Общие файлы common-*

Среди файлов в `/etc/pam.d/` есть четыре, которые не относятся к конкретной программе: `common-auth`, `common-account`, `common-password` и `common-session`. Проверка пароля, проверка аккаунта и настройка сессии нужны почти каждой программе (`sshd`, `sudo`, `su`, `login`), и переписывать одни и те же строки в каждый файл неудобно: при любом изменении пришлось бы править их все.

Поэтому строки каждого типа вынесены в свой общий файл: все строки типа `auth` лежат в `common-auth`, типа `account` — в `common-account`, и так далее. А в конфиге программы вместо этих строк стоит одна строка `@include common-auth`, которая означает «вставь сюда содержимое файла `common-auth`». Упрощённо конфиг `sshd` выглядит так:

```
account  required  pam_nologin.so
@include common-auth
@include common-account
@include common-session
@include common-password
```

Поэтому, изменив `common-auth`, вы меняете проверку пароля сразу для `sshd`, `sudo`, `login` и всех остальных программ. Файл `common-session-noninteractive` — то же самое, что `common-session`, но для сессий без терминала, например для `cron`.

## 3. SSH и PAM

sshd никогда не отдаёт проверку SSH-ключей в PAM: криптографию `authorized_keys` он всегда выполняет сам. Всё остальное (пароль, второй фактор, допуск аккаунта, настройка сессии) делегируется PAM, и что именно проверяет PAM, зависит от способа входа.

**Вход по ключу.** sshd проверяет ключ сам и обращается к PAM только за двумя вещами: `account` (можно ли этой учётке войти сейчас, например не закрыт ли вход файлом `/etc/nologin`) и `session` (лимиты, окружение, логи). Этап `auth` пропускается, потому что личность уже подтверждена ключом.

**Вход по паролю.** sshd передаёт логин и пароль в PAM, и проходят все этапы: `auth` проверяет пароль по `/etc/shadow` (`pam_unix.so`), `account` смотрит срок действия, `session` готовит окружение.

**Ключ и одноразовый код (2FA).** Сначала sshd проверяет ключ, потом через интерактивный диалог передаёт управление PAM, и `pam_google_authenticator.so` запрашивает TOTP-код. Для этого в `sshd_config` нужны две директивы: `AuthenticationMethods publickey,keyboard-interactive` задаёт порядок (сначала ключ, потом диалог с PAM), а `KbdInteractiveAuthentication yes` включает сам диалог «запрос-ответ». Без неё sshd не покажет строку `Verification code:` и оборвёт соединение. В `/etc/pam.d/sshd` при этом нужно убрать `pam_unix.so`, иначе после ключа система потребует ещё и пароль.

**`UsePAM yes` обязателен.** При `UsePAM no` не применяются лимиты из `limits.conf`, не срабатывает запрет входа через `/etc/nologin` и не пишутся логи сессий. На продакшене так делать нельзя.
