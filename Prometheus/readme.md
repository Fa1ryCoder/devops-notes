            node_cpu_seconds_total{cpu="1", mode="idle"}

            Series A = [chunk1][chunk2][chunk3]...
        Прометей закрывает чанк по истечению ~2 часов или 120 sample's одной time series что наступит раньше.

Начнем с определения Prometheus. Что такое Prometheus?
"Prometheus" — это система мониторинга, которая собирает и хранит метрики как временные ряды, используя уникальную многомерную модель данных с labels (тегами). Она работает по pull-модели (сама опрашивает targets по http с помощью config где указаны nodes), предоставляет мощный декларативный язык запросов PromQL для агрегации и анализа, имеет встроенный механизм алертинга и активно используется в cloud-native стеках (Kubernetes)
Все равно остаются вопросы по определению. Метрика, временной ряд и т.д. Что же все это такое?

"Метрика (metrics)" - это измерение какого либо параметра системы во времени. Проще: это число которое, Prometheus регулярно запысывает. Например:
    Загрузка CPU = 72%
    Свободная память = 1.3 GB
    Количество HTTP-запросов = 152
    температура сервера = 45°C
Важно отметить что Prometheus оперирует сырыми числами(row data) и не хранит информацию о единицах измерения. Чтобы превратить его в осмысленную метрику (например, в процент загрузки или скорость запросов в секунду), данные необходимо обработать с помощью PromQL(Это уже задача специалиста кто создает запросы). Изначально данные будут выглядить вот так: 0.72 (ratio), 1395864371 (bytes), 1003152, 45000.
В Prometheus метрика выглядит примерно так:
    node_cpu_seconds_total{cpu="0",mode="idle"} 12345.6
Здесь:
    - node_cpu_seconds_total = имя метрики
    - {cpu="0",mode="idle"} = теги (labels) - пары ключ="значение"
    - 12345.6 = значение

"Временной ряд (time series)" - это история значения метрики во времени. То есть Prometheus не просто хранит одно число. Он хранит: 
    время --> значение. 
Например:
    12:00 --> CPU = 40%
    12:01 --> CPU = 55%
    12:02 --> CPU = 72%
    12:03 --> CPU = 38%
Это и есть временной ряд. Временный ряды хранятся локально на диске, можно опционально интегрировать с удалёнными системами хранения. Он собирает данные(метрики во времени), примерно, ~2 часа и потом запечатывает в блок. Пример блока:
    /01KGPQB344WPSFXVM8F0A1XJCR/
Важно: Мы не собираем данные когда пишем, например, запрос: node_cpu_seconds_total{mode="idle"}[5m]. Мы запрашиваем собранные данные с помощью PromQL. PromQL это язык запросов, а не сбора!

Каждые 15 секунд (по настройке из конфига) Prometheus дергает http://node-exporter:9100/metrics и получает метрики с ноды со служебными лейблами (например job и instance). Идет добавление лейблов которые мы указываем в /etc/prometheus/prometheus.yml и записывается в WAL. 
WAL (Write Ahead Log, prometheus/wal/) - это черновик страховка. Простой бинарный файл на диске куда Prometheus изначально записывает метрики. Цель простая: если сервер умрет, то при включении Prometheus восстановит те частичные данные которые он успел записать в WAL.
HEAD(prometheus/chunks_head/) - это структура данных которая лежит в оперативке(RAM). Зачем же она нужна? А все очень просто. Когда мы, например, в графане открываем график за последние 5 минут, то Prometheus сначала лезет именно в chunks_head, а не в архивы данных. Т.к. запросы к RAM обрабатываются практически мгновенно. RAM работает в тысячи раз быстрее диска. Но память штука дорогая и не резиновая. Поэтому данные в chunks_head не могут жить вечно. После того как прошло 2 часа, HEAD заполнился. Прометей берет всё, что накопилось в HEAD, упаковывает, сжимает и превращает в блок(та самая директория из примера про блок). После того как блок сохранен, старый WAL уже не нужен и он удаляется.
prometheus/lock - этот файл гарантирует что только один экземпляр Prometheus работает с данными в один момент времени, предотвращая конфликты записи другим Prometheus. Когда Prometheus стартует создается файл lock и если другой экземпляр начнет писать туда же то получится ошибка:
    database is locked
Другими словами файл-блокировщик который не дает записывать данные в TSDB
prometheus/queries.active - это список активных запросов которые выполняются прямо сейчас

Небольшое резюме по этому процессу:
1. При старте Prometheus создается lock + восстановление HEAD из WAL
2. Пришла метрика
3. Добавили лейблы и записали в WAL (защита от потери данных)
4. Тут же добавили в HEAD в оперативку (теперь мы можем отрисовать это на графике)
5. Прошло 2 часа, HEAD заполнился
6. Освобождение HEAD путем упаковывания, сжимания и перемещения в блоки
7. Когда блок сохранен, удаляются старые сегменты WAL

Про блоки, а точнее из каких частей они состоят. 
Каждый блок состоит из 4-х ключевых частей: chunks, index, meta.json и tombstones. Они работают вместе как единая система.
/chunks/ - директория которая содержит числовые данные метрик в бинарном виде. В этой директории есть файлы вида 000001. Это не текст, а компактно сжатый поток временных рядов. 
Prometheus хранит точки не по одной, а группирует их в chunks — небольшие последовательности значений одной time series. Внутри chunk лежит последовательность пар «timestamp → value», но они сжаты алгоритмом XOR-компрессии. Эта компрессия эффективна, потому что соседние значения временных рядов обычно меняются плавно, и можно хранить только разницу между ними.
Важно понимать, что файл chunks/000001 — это просто большой контейнер с данными всех time series в этом блоке. В нём нет удобной структуры для поиска по имени метрики или лейблам. Он организован по смещениям (offsets). По смещениям значит что каждый chunk - это кусок байтов:
    chunk A1 = 4096 байт
    chunk B1 = 4096 байт
    chunk C1 = 4096 байт
Тогда файл выглядит вот так:
    байты 0–4095     → chunk A1
    байты 4096–8191  → chunk B1
    байты 8192–12287 → chunk C1
Смещение (offset) = позиция в файле в байтах. То есть:
    chunk A1 → offset 0
    chunk B1 → offset 4096
    chunk C1 → offset 8192

Чтобы найти нужные данные, Prometheus должен знать, в каком месте файла лежит конкретный chunk, и эту информацию он получает из файла index.
Таким образом, chunks — это чистое хранилище значений, оптимизированное для компактности и быстрого последовательного чтения.

/index - слой поиска (Инвертированный индекс). Если файл по времени подошел мы идем в index. Файл index читается с конца. Prometheus после того как пробежался по всем блокам для того что бы узнать нужный временной интервал(с помощью minTime и maxTime в файле meta.json) залезает в нужный блок и открывает index.

/meta.json - это метаданные блока в читаемом JSON-виде. Он описывает временной диапазон блока (minTime и maxTime), статистику (количество series, samples и chunks) и информацию о compaction(слияние блоков, если level > 1 то значит этот блок это результат обьединения нескольких мелких блоков). Prometheus использует этот файл при старте и при выполнении запросов, чтобы быстро понять, нужен ли данный блок для конкретного временного диапазона. Например, если ты запрашиваешь данные за последние 30 минут, а блок покрывает период недельной давности, Prometheus даже не будет открывать его index и chunks.
Также meta.json содержит информацию о происхождении блока: был ли он создан напрямую из HEAD или получен в результате объединения нескольких меньших блоков. Это важно для механизма compaction и отладки. Можно сказать, что meta.json — это оглавление блока, которое позволяет быстро ориентироваться в его содержимом.

2.1.1) Как формируется Symbol Table в процессе работы. Когда Prometheus получает метрики и складывает их в HEAD - оперативную память(RAM), он паралельно ведет учет всех новых строк, которые встречает. Этот процесс называется интернированием строк. 
Допустим пришли первые метрики:
    http_requests_total{method="GET", status="200"} 42
    cpu_usage{core="0"} 0.45
Prometheus смотрит и видит новые строки
    - Имена метрик: http_requests_total, cpu_usage
    - Ключи меток: method, status, core
    - Значения меток: GET, 200, 0
Все эти строки он заносит во временный словарь в памяти и присваивает каждой следующий номер по порядку:

Номер:	Строка:
1	    http_requests_total
2	    cpu_usage
3	    method
4	    GET
5	    status
6	    200
7	    core
8	    0

Приходит следующая метрика:
    http_requests_total{method="POST", status="200"} 13
Prometheus проверяет каждую строку: http_requests_total — уже есть (номер 1), method — уже есть (номер 3), POST — новая строка → добавляем под номером 9, status — уже есть (номер 5), 200 — уже есть (номер 6). Обновляет таблицу дописывая :

Номер:  Строка:
9       POST

Приходит ещё одна метрика:
    go_gc_duration_seconds{quantile="0.5"} 0.00023
Новые строки: go_gc_duration_seconds, quantile, 0.5. Так же добавляются в таблицу:

...	...

11	quantile
12	0.5

и т.д.

По истечении ~2 часов (или при заполнении HEAD) происходит Compaction — сброс данных на диск. Допустим, набиралось 15 342 уникальных строк. Все они собраны в памяти, у каждой есть свой номер от 1 до 15 342. Когда наступает момент сброса HEAD на диск (создание блока 01KKKPJMX34CY5MDQ4YSTK1GHS), Prometheus формирует файл index. Где Symbol Table записывается в самом начале этого файла (сразу после заголовка). После того как Symbol Table записана, все остальные структуры индекса не хранят строки — они хранят только номера строк.

Пример: запись временного ряда
Ряд http_requests_total{method="GET", status="200"} кодируется не как текст, а как последовательность чисел:

[1] [3,4] [5,6]
Где:

1 — номер строки http_requests_total в Symbol Table

3,4 — номер строки method (3) и номер строки GET (4)

5,6 — номер строки status (5) и номер строки 200 (6)

2.1.2) Запись Series-секции в индексный файл. 
Что такое Series-секция? Это раздел файла index, в котором хранятся описания всех временных рядов, попавших в данный блок данных. Каждое описание представляет собой компактную числовую запись, полностью основанную на Symbol Table и содержащую ссылки на чанки с реальными значениями. Что же содержит запись одного временного ряда? Запись содержит:
 1) Имя метрики и набор меток (в виде чисел-ссылок на Symbol Table)
 2) Информацию о том, где в чанках лежат данные этого ряда
Для каждого временного ряда Prometheus берет его метки и превращает их в последовательность чисел. Все строки уже имеют номера в Symbol Table, поэтому описание ряда состоит только из этих номеров.
По пункту №1, пример: Ряд http_requests_total{method="GET", status="200"}

Если в Symbol Table:

http_requests_total = 1

method = 3

GET = 4

status = 5

200 = 6

То в Series-секцию запишется последовательность: [1, 3, 4, 5, 6]

По пункту №2. Информация о чанках. К каждому ряду прикрепляется информация, где лежат его данные:
 - Какой файл в директории chunks/ (например, 000001)
 - С какого смещения в этом файле начинаются данные
 - Временной диапазон этих данных
Благодаря этому, когда Prometheus позже получит Series ID, он сразу будет знать, куда идти в чанках.


2.1.3) Появление Series ID. В момент записи ряды просто идут друг за другом. Series ID — это порядковый номер ряда в этой последовательности:
 - Первый записанный ряд получает ID = 1
 - Второй ряд — ID = 2
 - Последний ряд в блоке — ID = N (где N — общее количество рядов)
ID нигде отдельно не хранится, он определяется позицией записи.Что получается на выходе этих этапов? После завершения записи Series-секции в файле index есть:
 1) Symbol Table (словарь строк)
 2) Series-секция (все ряды, закодированные числами, с привязкой к чанкам)
 3) У каждого ряда есть Series ID (его номер)
Теперь Prometheus знает, какие ряды существуют, из каких меток они состоят и где искать их данные.

2.1.4) Формирование Postings (Инвертированный индекс).
Если на предыдущих этапах мы создали список «паспортов» для каждой метрики (Series), то теперь нам нужно создать «телефонную книгу», чтобы быстро находить эти паспорта по конкретным признакам (меткам). Что такое Postings? Это разделы файла index, в которых для каждой уникальной пары Метка="Значение" хранится список всех Series ID, в которых эта пара встречается. Как это записывается:
Для каждой пары (например, status="200") создается блок данных:

len: Общая длина этой секции.

#entries: Количество рядов, которые содержат эту метку.

Список Series ID: Массив номеров рядов.

Пример:
Допустим, у нас в блоке 3 ряда:

ID 1: http_requests_total{method="GET", status="200"}

ID 2: http_requests_total{method="POST", status="200"}

ID 3: cpu_usage{core="0", status="200"}

Prometheus проходит по всем рядам и формирует списки для каждой метки:

Метка method="GET" —> Список IDs: [1]

Метка method="POST" —> Список IDs: [2]

Метка status="200" —> Список IDs: [1, 2, 3] (эта метка есть во всех трех рядах)

Метка core="0" —> Список IDs: [3]

Важное правило:
Списки Series ID внутри Postings всегда строго отсортированы по возрастанию. Это критически важно для скорости: когда Prometheus нужно найти пересечение двух меток (например, {method="GET", status="200"}), он берет два отсортированных списка и очень быстро находит общие ID за один проход.

Что получается на выходе этого этапа?
Теперь в файле index помимо словаря строк и описания самих рядов, появилась база для мгновенного поиска. Теперь Prometheus может не перебирать все ряды подряд, а сразу достать список ID тех рядов, которые подходят под фильтры запроса.

2.1.5) Postings Offset Table (Таблица смещений поиска)Что это такое?Если Postings (2.1.4) — это сами списки ID серий, разбросанные по всему файлу index, то Postings Offset Table — это компактное «оглавление» в конце файла. Она связывает конкретную пару Метка=Значение с конкретным адресом (байтом) в файле, где начинается её список ID.Зачем она нужна?Без этой таблицы Prometheus при каждом запросе (например, {status="500"}) пришлось бы сканировать весь многогигабайтный файл index с самого начала, чтобы найти нужную строчку. Это позволяет Prometheus не читать всю таблицу целиком, а находить нужный оффсет методом деления пополам ($O(\log n)$).Кэширование: При открытии блока (Block Load) эта таблица частично считывается в оперативную память. Это одна из причин, почему Prometheus потребляет RAM — он держит в ней «карту» индекса для мгновенного доступа к диску.CRC32: В конце таблицы записывается контрольная сумма. Если файл index повредится (например, из-за сбоя диска), Prometheus узнает об этом при первой же попытке поиска.Пример работы:Пользователь запрашивает {app="frontend"}.Prometheus идет в Postings Offset Table, находит строку app="frontend".Видит оффсет, например: 854030.Система прыгает на байт 854030 и сразу начинает читать готовый список Series ID из секции Postings.

2.1.6) TOC (Table of Contents — Оглавление файла) Что это такое? Это самые последние 32 байта в файле index. Если Postings Offset Table — это карта для поиска меток, то TOC — это карта для самого Prometheus, чтобы он вообще понял, где в этом гигантском файле находятся все разделы (Symbol Table, Series, Postings и т.д.). Зачем она нужна? Когда Prometheus открывает блок данных с диска, он не читает файл с начала. Он сразу прыгает в самый конец файла, считывает последние 32 байта и узнает «координаты» всех ключевых секций. Структура TOC:
В этих 32 байтах лежат 64-битные указатели (offsets) на начало разделов:

 - Symbol Table Offset: Где начинается словарь строк.

 - Series Offset: Где начинается раздел с описанием рядов.

 - Postings Offset: Где начинается таблица смещений (Postings Offset Table).

 - CRC32: Контрольная сумма самого TOC для проверки целостности.

Механика работы (в стиле "Middle DevOps"): Прыжок в конец: Prometheus делает системный вызов seek в конец файла --> Чтение TOC: Узнает адреса всех секций --> Инициализация: Теперь, зная смещение Postings Offset, он может мгновенно найти любую метку, не читая Symbol Table или Series секции целиком.


Этап №2.2 Как ищется(чтение):
2.2.1) Prometheus читает файл с конца и находит TOC — Table of Contents. Это специальная структура, расположенная в конце файла index, которая содержит смещения (offsets) к началу всех остальных основных разделов этого файла. Можно сказать это оглавление в котором лежит маленькая структура фиксированного размера, где уже записано: «postings offset table начинается с байта N», «series — с байта M» и так далее. Тут сразу же возникает вопрос. А зачем нужен TOC если можно предпоследний раздел файла(Postings Offset Table) поместить в конец и начинать с него? Но тогда возникает проблема: он не знает, где postings offset table начинается. Эта таблица переменного размера т.е структура данных, количество записей в которой заранее неизвестно и может меняться. Чтобы её найти без TOC, пришлось бы либо сканировать файл назад, либо хранить какие-то маркеры между секциями. Это медленно и усложняет формат. 

2.2.2) Postings Offset Table (Таблица смещений списков). Получив координаты из TOC, Prometheus идет сюда.
Это упорядоченный по алфавиту справочник всех пар key="value" (например, method="GET", status="200", job="prometheus"), которые встречаются в данном блоке TSDB. Для каждой такой пары в таблице записано смещение (offset) — точный адрес в байтах, указывающий, где в следующей секции (Postings) начинается список идентификаторов временных рядов для этой конкретной метки.

2.2.3) Postings - списки идентификаторов. Когда прометей нашел смещение (offset) он прыгает в Postings. Что такое Series ID? Представь, что в конкретном блоке данных (например, за последние 2 часа) Prometheus сохранил 1 000 000 уникальных временных рядов (комбинаций метрик и тегов). Чтобы не таскать везде длинные строки типа http_requests_total{method="GET", status="200", instance="10.0.0.1"}, он присваивает каждому такому ряду порядковый номер: 1, 2, 3... 1 000 000. Series ID — это просто короткий целочисленный указатель на конкретный временной ряд. 

Содержимое секции Postings: В этой секции по адресу 42047 лежит упакованный список этих самых чисел. Если ты искал status="200", то там будет лежать список: [5, 12, 42, 100, 105...]. Это означает: «Временной ряд №5 имеет тег status="200", ряд №12 тоже его имеет, и так далее». Магия пересечения (Intersection):
Это самый важный момент. Запросы редко состоят из одного тега. Допустим, твой фильтр: {job="api", status="200"}.

Prometheus идет в Postings за списком для job="api". Получает: [12, 42, 50, 100].

Затем берет список для status="200". Получает: [5, 12, 42, 100, 105].

Затем он делает пересечение этих двух списков. На выходе остаются только те ID, которые есть в обоих списках: [12, 42, 100].

После работы с разделом Postings у Prometheus больше нет «текста» (тегов). У него на руках остается только набор чисел (Series ID), которые на 100% соответствуют твоему запросу.

2.2.4) Работа с Series-секцией (получение информации о рядах)
После того как Prometheus получил список Series ID из Postings (например, [12, 42, 100]), у него есть только набор числовых идентификаторов. Чтобы превратить их в осмысленный результат, он обращается к Series-секции. Как происходит получение информации. Series ID логически можно воспринимать как порядковый номер, но на практике это ссылка (offset) на конкретную запись в Series-секции. Используя смещение, полученное через TOC, Prometheus выполняет прямой переход (seek) к нужной записи.

Для каждого Series ID из списка он извлекает две ключевые части информации:

1) Метки ряда (labelset)

Метки хранятся в виде последовательности чисел — ссылок на Symbol Table. Так как Symbol Table уже загружена в память, Prometheus быстро восстанавливает исходные строки.

Пример:
[1, 3, 4, 5, 6]

преобразуется в:
http_requests_total{method="GET", status="200"}

Эти данные используются для формирования результата запроса, а также для операций агрегации и группировки.

2) Ссылки на чанки (chunk references)

Для каждого временного ряда хранится список чанков, содержащих реальные значения метрик.

Каждый chunk reference включает:

файл в директории chunks/ (например, 000001)
смещение внутри файла
временной диапазон (minTime, maxTime)

Пример:

file: 000001, offset: 10240, time: [t1–t2]

Фильтрация по времени

Если в запросе указан временной диапазон, Prometheus не читает все чанки подряд. Вместо этого он использует временные границы (minTime/maxTime) из chunk references и отбирает только те чанки, которые пересекаются с нужным интервалом.

Важно: фильтрация происходит на уровне чанков, а не целиком временного ряда.

Что получается на выходе

После обработки Series-секции для каждого Series ID Prometheus получает:

- полное описание временного ряда (метки)
- список релевантных chunk references


2.1.5) Чтение Series-секции (Извлечение «паспорта» ряда)
После того как на этапе 2.2.3 мы получили список Series ID (например, [12, 42, 100]), нам нужно понять, что это за ряды и где их данные.

Как это работает:
Секция Series — это, по сути, массив записей фиксированной структуры. Series ID — это порядковый номер записи в этом массиве. Prometheus делает «прыжок» по файлу сразу к нужной записи.

Что Prometheus вычитывает из Series-записи:

Набор меток (Labels): Список ID из Symbol Table. Например, [1, 3, 4]. Мы уже знаем, что этот ряд нам подходит, но нам нужны эти ID, чтобы позже вернуть пользователю текстовые имена меток.

Chunk Pointers (Указатели на чанки): Это самое важное для получения графиков. Для каждого ID здесь хранится:

ID файла: В каком файле в chunks/ лежат данные.

Offset: С какого байта начинаются данные.

Maxtime / Mintime: Временной диапазон этого конкретного куска данных.

Заметка для Middle DevOps: На этом этапе Prometheus делает Time-based Filtering. Если ты просишь данные за последний час, а в записи ряда 10 чанков по 2 часа каждый, Prometheus отметит только нужный чанк и не будет трогать остальные 9. Это экономит кучу I/O.

2.1.6) Чтение Symbol Table (Резолвинг имен)
Теперь у Prometheus есть Series ID и наборы чисел, соответствующих меткам (например, [1, 3, 4]). Но пользователю в Grafana нельзя показать «Метрика №1». Нужно вернуть текст.

Как это работает:
Prometheus возвращается в самое начало файла index — к Symbol Table.

Он берет числа-ссылки (например, 1).

Используя таблицу символов как словарь, он мгновенно находит, что 1 = http_requests_total.

Повторяет это для всех меток в ряду.

Итог этапа:
После этого шага у Prometheus полностью восстанавливается текстовый вид метрики: http_requests_total{method="GET", status="200"}. Теперь он готов не просто искать, но и формировать финальный ответ.



"Теги (labels)" - это пары ключ="значение", которые прикрепляются к метрике для добавления контекста. Метрики нужны для:
    Дифференциация: Позволяют отличить метрику одного сервера от другого (instance="web-01" vs instance="web-02").
    Агрегация: Позволяют посчитать общую сумму запросов по всему региону или конкретному приложению, используя фильтры в PromQL
    Динамичность: Тебе не нужно создавать метрику http_requests_total_server1, ты создаешь одну метрику http_requests_total и разделяешь данные метками.

Возьмем пример:
    http_requests_total{instance="web-01", method="GET"}
        - 1-ый ключ instance = значению "web-01", 
        - 2-ой ключ method = значению "GET". 
При конфигурировании мы можем и будем вынуждены задавать свои собственные теги и значения каждой ноде для гибкостки наших запросов. Задаются они в конфиг файле самого Prometheus в формате .yml(дефолтный путь /etc/prometheus/prometheus.yml).
