# Тема 6: Jinja2 — базовые фильтры

## Что такое Jinja2 и зачем он нужен

Jinja2 — это шаблонизатор, который Ansible использует везде, где в тексте встречается конструкция `{{ }}`. Задача Jinja2 простая: взять то, что написано внутри `{{ }}` (переменную, выражение), вычислить его и подставить готовое значение на это место.

Фильтр — это функция, которая обрабатывает значение **перед** тем, как оно будет подставлено. Он нужен, когда значение переменной само по себе не подходит для подстановки: пришло не в том регистре, с лишними пробелами, не того типа, или переменной вовсе нет. Вместо того чтобы городить отдельную задачу на исправление значения, фильтр решает это прямо в момент подстановки, одной припиской через `|`. Синтаксис:

```jinja2
{{ переменная | имя_фильтра }}
```

Знак `|` — труба, работает по тому же принципу, что и pipe в Linux: результат слева передаётся на вход фильтру справа. Фильтры можно цеплять цепочкой, выполнение идёт слева направо:

```jinja2
{{ значение | filter_1 | filter_2 }}
```

Как это выглядит на практике — в playbook и в шаблоне — разберём сразу ниже.

## Где физически живут `{{ }}` и фильтры

Есть два места, где это пишется:

### 1. Прямо в playbook (YAML-файл с задачами)

Внутри `tasks:` — в любом параметре модуля, где ты подставляешь значение переменной:

```yaml
- hosts: webservers
  vars:
    app_name: MyApp          # переменная, которую мы сами задаём

  tasks:
    - name: Вывести имя хоста в верхнем регистре
      ansible.builtin.debug:
        msg: "Хост: {{ inventory_hostname | upper }}"

    - name: Создать директорию с именем из переменной
      ansible.builtin.file:
        path: "/opt/{{ app_name | lower }}"   # app_name — переменная из vars: текущего play
        state: directory
```

`inventory_hostname` — магическая переменная (имя хоста, для которого сейчас выполняется задача), подробно они разобраны в теме 5. `app_name` — обычная переменная из блока `vars:` (в реальном playbook'е она чаще лежит в `group_vars`/`host_vars`, здесь для наглядности прямо в файле).

Здесь `{{ app_name | lower }}` — это просто текст внутри YAML-строки. Ansible видит `{{ }}`, понимает "тут надо подставить переменную", применяет фильтр `lower` перед подстановкой, и в итоге в модуль `file` уходит уже готовая строка типа `/opt/myapp`.

### 2. Внутри `.j2`-шаблона (файл, который обрабатывает модуль `template`)

Это тот же принцип, что и в модуле `template`, которым ты уже пользовался на практике. У тебя есть файл `something.conf.j2`, и внутри него — обычный текст конфига, но с вкраплениями `{{ }}`:

```jinja2
server_name={{ inventory_hostname }}
log_level={{ log_level | default('info') }}
timeout={{ connection_timeout | int }}
```

Модуль `template` берёт этот `.j2`-файл, прогоняет через Jinja2, все `{{ }}` заменяются на реальные значения с учётом фильтров — и на целевой машине появляется уже готовый конфиг-файл без всяких `{{ }}`, просто с подставленными значениями.

Полная цепочка выглядит так. В playbook'е заданы переменные и вызван `template`:

```yaml
- hosts: web-01
  vars:
    log_level: debug
    connection_timeout: "30"    # специально строка — int в шаблоне превратит её в число

  tasks:
    - name: Сгенерировать конфиг из шаблона
      ansible.builtin.template:
        src: something.conf.j2
        dest: /etc/myapp/something.conf
```

После выполнения на хосте `web-01` появится файл `/etc/myapp/something.conf` с содержимым:

```ini
server_name=web-01
log_level=debug
timeout=30
```

Видно, как каждая строка шаблона превратилась в готовое значение: `inventory_hostname` → `web-01`, `log_level` → `debug` (переменная задана, поэтому `default('info')` не понадобился), `connection_timeout` → `30` (фильтр `int` превратил строку `"30"` в число).

Про расположение файла: `.j2`-шаблон физически лежит рядом с playbook'ом, в подпапке `templates/` (это стандартное соглашение Ansible). В параметре `src:` указывается только имя файла — Ansible сам ищет его в `templates/` относительно playbook'а. `dest:` — это уже путь на **целевой машине**, куда положить готовый результат.

Наглядно это выглядит так:

```
deploy/
├── site.yml                        ← сам playbook (control node)
└── templates/
    └── something.conf.j2           ← шаблон, лежит здесь по соглашению
```

Если `something.conf.j2` не лежит в `templates/`, а, скажем, прямо рядом с playbook'ом — Ansible его не найдёт, и задача упадёт с ошибкой "template file not found".

> **Важно:** отдельной настройки в `ansible.cfg`, которая регулирует путь к шаблонам, не существует. Но если шаблон лежит в другой директории — например, в `deploy/configs/` вместо `deploy/templates/` — путь указывается прямо в `src:` относительно playbook'а:
>
> ```yaml
> src: configs/something.conf.j2    # файл физически лежит в deploy/configs/
> ```

## Разбор базовых фильтров

### default — значение по умолчанию

**Зачем:** переменная может быть не задана для конкретного хоста (нет в `host_vars`/`group_vars`) — без `default` playbook упадёт с ошибкой "variable is undefined". `default` подставляет запасное значение и выполнение продолжается.

**Пример в `.j2`-шаблоне:**

```jinja2
log_level={{ log_level | default('info') }}
```

Если для хоста нигде не задан `log_level`, в конфиг уйдёт `log_level=info` вместо падения playbook'а.

**Пример в playbook:**

```yaml
- name: Установить таймаут соединения
  ansible.builtin.set_fact:
    timeout: "{{ custom_timeout | default(30) }}"
```

**Важный нюанс (частый вопрос на собесе):** у фильтра `default(x)` есть ровно одно условие срабатывания — переменной вообще нет в плейбуке. Разберём на двух случаях.

**Случай 1 — переменной нет вообще.** Мы ни разу не написали `log_level` ни в `vars`, ни в `host_vars`, ни в `group_vars`:

```jinja2
{{ log_level | default('info') }}
```

Здесь `default` сработает — подставится `info`, потому что Ansible не находит `log_level` нигде.

**Случай 2 — переменная есть, но без значения.** Мы её объявили, просто ничего в неё не положили:

```yaml
vars:
  log_level:        # просто двоеточие и ничего дальше — это None (null)
  # или
  log_level: ""     # явно пустая строка
```
```jinja2
{{ log_level | default('info') }}
```

Здесь `default` **не сработает** — результат будет пустым, а не `info`. Разница со случаем 1: Ansible видит ключ `log_level` в `vars`, значит переменная "определена" — неважно, что внутри неё пусто.

Чтобы фильтр реагировал и на пустые значения, нужен второй аргумент `true`:

```jinja2
{{ log_level | default('info', true) }}
```

Классический вопрос-ловушка: "почему `default` не сработал, если я передал пустую строку?" — потому что переменная была определена, просто пустая.

### trim — обрезка пробелов

**Зачем:** значение из `register` часто "грязное" — с переносом строки или пробелами на конце, которые попадают туда из вывода команды в терминале.

**Пример в playbook:**

```yaml
- name: Получить имя хоста
  ansible.builtin.command: cat /etc/hostname
  register: hostname_output

- name: Показать имя хоста без мусора
  ansible.builtin.debug:
    msg: "Хост: {{ hostname_output.stdout | trim }}"
```

Без `trim` в `hostname_output.stdout` может лежать `"myhost\n"` — и этот `\n` улетит дальше в конфиг или в сравнение значений, где может всё сломать.

---

### upper / lower — регистр строки

**Зачем:** нормализация значений, которые приходят непредсказуемо (от пользователя, из внешнего источника, из вывода другой команды).

**Пример в playbook:**

```yaml
- name: Создать директорию с именем приложения в нижнем регистре
  ansible.builtin.file:
    path: "/opt/{{ app_name | lower }}"
    state: directory
```

Если кто-то в `group_vars` записал `app_name: MyApp`, а на диске нужен путь строго `/opt/myapp` — фильтр приводит к единому виду независимо от того, как ввели переменную.

---

### length — длина строки, списка, словаря

**Зачем:** чаще всего используется в условиях `{% if %}` / `when` — чтобы проверить, есть ли вообще данные, прежде чем с ними что-то делать.

**Пример в playbook (`when`):**

```yaml
- name: Установить пакеты, если список не пустой
  ansible.builtin.apt:
    name: "{{ extra_packages }}"
    state: present
  when: extra_packages | length > 0
```

Без этой проверки задача попыталась бы выполниться даже с пустым списком, что не всегда безопасно в зависимости от модуля.

> **Примечание:** в Jinja2/Python пустой список `[]`, пустой словарь `{}` и пустая строка `""` сами по себе приводятся к `false` (truthiness). Поэтому для списков `when: extra_packages` отработает точно так же, как `when: extra_packages | length > 0` — короче и без явной длины. `| length > N` нужен только тогда, когда важно конкретное количество элементов (например, `| length > 2`), а не просто факт "список не пустой".

---

### join — склейка списка в строку

**Зачем:** списки в Ansible — это Python-списки, а конфигу на целевой машине часто нужна просто строка с разделителем.

**Пример в `.j2`-шаблоне:**

```jinja2
allowed_hosts={{ allowed_hosts_list | join(', ') }}
```

Если `allowed_hosts_list: ['10.0.0.1', '10.0.0.2', '10.0.0.3']`, в конфиг уйдёт строка `allowed_hosts=10.0.0.1, 10.0.0.2, 10.0.0.3`.

---

### split — разбивка строки на список

**Зачем:** обратная операция к `join`. Иногда команда через `register` возвращает одну строку с разделителем, а дальше по коду нужен именно список — например, для цикла `{% for %}` или для проверки количества элементов через `length`.

**Пример в playbook.** Команда вернула значение, которое изначально хранится одной строкой с разделителем — например, список адресов из конфига:

```yaml
- name: Прочитать список разрешённых хостов из конфига
  ansible.builtin.shell: grep '^allowed_hosts=' /etc/myapp/app.conf | awk -F'=' '{print $2}'
  register: allowed_hosts_raw

- name: Показать как список
  ansible.builtin.debug:
    var: allowed_hosts_raw.stdout | trim | split(',')

- name: Предупредить, если хостов слишком много
  ansible.builtin.debug:
    msg: "В списке больше 10 хостов — возможно, конфиг разросся"
  when: allowed_hosts_raw.stdout | trim | split(',') | length > 10
```

Разбор первой задачи: grep находит в конфиге строку `allowed_hosts=10.0.0.1,10.0.0.2,10.0.0.3`, а `awk` разбивает её по разделителю `=` (`-F'='`) и печатает второе поле (`$2`) — всё, что после знака. `allowed_hosts_raw` — стандартный объект `register` с полями `stdout`, `stderr`, `rc` и т.д.; нас интересует `allowed_hosts_raw.stdout`, где лежит вывод команды — строка `10.0.0.1,10.0.0.2,10.0.0.3`.

Вторая задача превращает эту строку в список: `split(',')` даёт `['10.0.0.1', '10.0.0.2', '10.0.0.3']`.

Третья задача показывает, зачем это нужно: со списком уже работает `length` — посчитать элементы у простой строки так не получилось бы (её `length` вернул бы количество символов, а не хостов).

**Важное уточнение — когда `split` НЕ нужен.** Если команда возвращает многострочный вывод (каждое значение на своей строке), у `register` уже есть готовое поле `stdout_lines` — тот же вывод, но сразу списком по строкам:

```yaml
- name: Получить PID процессов nginx
  ansible.builtin.shell: pgrep -f nginx
  register: nginx_pids

- name: stdout_lines — уже список, split не нужен
  ansible.builtin.debug:
    var: nginx_pids.stdout_lines
```

Если `pgrep` нашёл два процесса, разница между полями выглядит так:

```
nginx_pids.stdout        →  "1234\n5678"
nginx_pids.stdout_lines  →  ['1234', '5678']
```

`stdout` — одна строка с переносами внутри, `stdout_lines` — та же строка уже разбитая построчно на список.

То есть `split` — для строк с разделителем внутри (запятая, двоеточие, точка с запятой), а для построчного вывода — просто `stdout_lines`.

**Пограничный случай — разделитель в конце строки.** `split` режет строку по каждому разделителю и складывает в список всё, что между разрезами. Если строка заканчивается запятой, то после последней запятой тоже "что-то есть" — пустота, и она станет отдельным элементом списка:

```
"10.0.0.1,10.0.0.2"   | split(',')  →  ['10.0.0.1', '10.0.0.2']        # 2 элемента
"10.0.0.1,10.0.0.2,"  | split(',')  →  ['10.0.0.1', '10.0.0.2', '']    # 3 элемента!
```

Хостов по-прежнему два, но `length` вернёт 3, цикл `{% for %}` прокрутится три раза, а сравнение вроде `length > 2` сработает там, где не должно.

**Решение — отфильтровать пустые элементы через `reject`:**

```jinja2
{{ "10.0.0.1,10.0.0.2," | split(',') | reject('equalto', '') | list }}
```

`reject('equalto', '')` проходит по списку и выкидывает все элементы, равные пустой строке (`equalto` — тест на равенство, `reject` — фильтр, отбрасывающий совпадения; обратный ему `select` — наоборот, оставляет только совпадения). `reject` возвращает не готовый список, а ленивый объект, поэтому в конце ставится `| list`, чтобы получить обычный список для дальнейшей работы. Результат: `['10.0.0.1', '10.0.0.2']` — уже без мусора, `length` вернёт корректные 2.

### replace — замена подстроки

**Зачем:** точечная правка значения прямо в момент подстановки — когда значение переменной нужно вставить не как есть, а слегка изменив.

**Пример в `.j2`-шаблоне:**

```jinja2
config_path={{ base_path | replace('\\', '/') }}
```

Пример: значение пришло с обратными слэшами (например, из Windows-стиля пути в переменной), а конфигу на Linux-машине нужны прямые.

### int / float / bool — приведение типа

**Зачем:** значение из `register.stdout` — это всегда **строка**, даже если по смыслу там число или логическое значение. Это создаёт две разные проблемы:
- для арифметики или числового сравнения строки сравниваются неправильно (например, `"9" > "10"` как строки — `true`, что неверно для чисел);
- для логической проверки в Jinja2 **любая непустая строка — это истина**, включая саму строку `"false"`.

Оба случая решаются приведением типа: `int`/`float` — для чисел, `bool` — для логики.

**Пример с числом:**

```yaml
- name: Получить количество свободных мест на диске
  ansible.builtin.shell: df --output=avail /opt | tail -1
  register: free_space

- name: Предупредить, если места мало
  ansible.builtin.debug:
    msg: "Мало места на диске!"
  when: free_space.stdout | trim | int < 1000000
```

Здесь в одной цепочке сразу два фильтра: `trim` убирает пробелы, `int` превращает результат в число для корректного сравнения `<`.

**Пример с логическим значением.** Сам скрипт — обычный bash, логика печати `true`/`false` заложена внутри него:

```bash
#!/bin/bash
# /opt/scripts/check_maintenance_mode.sh
# Проверяем наличие файла-флага режима обслуживания

if [ -f /var/run/maintenance.flag ]; then
    echo "true"
else
    echo "false"
fi
```

Файл-флаг — распространённый паттерн: перед началом работ админ создаёт файл (`touch /var/run/maintenance.flag`), а все автоматизации проверяют его наличие и не трогают хост, пока флаг стоит. Ansible ничего не знает, *как* скрипт принял решение — он видит только то, что прилетело в stdout.

```yaml
- name: Проверить состояние через самописный скрипт
  ansible.builtin.shell: /opt/scripts/check_maintenance_mode.sh
  register: maintenance_check

- name: Выполнить действие, если режим обслуживания включён
  ansible.builtin.debug:
    msg: "Идёт обслуживание, пропускаем деплой"
  when: maintenance_check.stdout | trim | bool
```

Пошагово, что здесь происходит:

1. **Первая задача** запускает скрипт. Тот проверяет наличие файла-флага и печатает в stdout одно слово: `true` или `false`. Результат выполнения сохраняется в `maintenance_check` через `register`.
2. В `maintenance_check.stdout` теперь лежит **строка** — например, `"true\n"` (с переносом строки, потому что `echo` в скрипте его добавляет).
3. **Вторая задача** в `when` обрабатывает эту строку цепочкой: `trim` срезает `\n` → остаётся `"true"`, затем `bool` превращает строку `"true"` в логическое `true`.
4. `when` получает готовое `true` → условие истинно → задача выполняется. Если скрипт напечатал `false`, то `bool` вернёт `false`, и задача будет пропущена.

Без `bool` шаг 4 сломался бы: `when` получил бы строку `"false"`, а любая непустая строка в Jinja2 — истина, и задача выполнилась бы, когда не должна.

Фильтр `bool` приводит строки `'true'`, `'yes'`, `'1'`, `'y'` к настоящему логическому `true`, а всё остальное — к `false`. И здесь снова цепочка: сначала `trim` (убрать мусор из вывода команды), потом `bool` (превратить строку в логическое значение) — порядок в трубе важен.

Обрати внимание: этот пример специально показывает случай с самописным скриптом, который просто печатает `"true"`/`"false"` в stdout. Если бы речь шла о проверке статуса стандартного systemd-сервиса, правильнее использовать не `shell`, а модуль `ansible.builtin.systemd` — он сразу возвращает структурированный статус (например, `status.ActiveState == 'active'`), и проблема "строка вместо логического значения" там просто не возникает.

### omit — пропустить параметр модуля

**Зачем:** сделать параметр модуля необязательным. Если переменная задана — параметр передаётся с её значением. Если не задана — `omit` убирает параметр из задачи целиком, как будто ты его вообще не писал. Без `omit` пришлось бы выбирать из двух плохих вариантов: либо playbook падает на неопределённой переменной, либо `default('')` отправляет в модуль пустую строку, которую тот не поймёт.

**Пример в playbook:**

Задача одна и та же, но переменная `custom_uid` в двух разных playbook'ах (или для двух разных хостов) задана по-разному:

```yaml
# host_vars/host-a.yml
custom_uid: 1500
```

Для **host-b** переменная `custom_uid` вообще не объявлена в `host_vars` — её там просто нет.

```yaml
- name: Настройка системного пользователя
  ansible.builtin.user:
    name: "deploy"
    uid: "{{ custom_uid | default(omit) }}"
```

Для **host-a** Ansible реально выполнит задачу так, будто она написана:

```yaml
- name: Настройка системного пользователя
  ansible.builtin.user:
    name: "deploy"
    uid: 1500
```

На **host-b** `default(omit)` полностью убирает параметр `uid:` из вызова, и задача выполняется так, будто её вообще не было в playbook'е:

```yaml
- name: Настройка системного пользователя
  ansible.builtin.user:
    name: "deploy"
```

В этом случае операционная система сама назначит следующий свободный UID. Если бы вместо `omit` был обычный дефолт вроде `default('')`, в модуль ушла бы пустая строка `uid: ""`, что для этого параметра — ошибка, а не "пропусти меня".

`omit` всегда используется в связке с `default()`, отдельно он не имеет смысла.

**Важное синтаксическое ограничение:** `omit` работает, только когда всё выражение `{{ ... }}` составляет **весь параметр целиком**, а не часть строки:

```yaml
uid: "{{ custom_uid | default(omit) }}"      # работает — omit это весь параметр

uid: "user-{{ custom_uid | default(omit) }}" # не сработает — omit тут часть строки, а не весь параметр
```

Во втором случае Ansible не может "вычеркнуть" только кусок строки — параметр либо передаётся целиком, либо не передаётся вовсе.

### mandatory — обязательная переменная

**Зачем:** есть переменные, для которых **нет разумного значения по умолчанию** — например, пароль от базы данных или адрес продовского сервера. Если такую переменную забыли прописать в `host_vars`, playbook не должен молча продолжать работу с пустым или дефолтным значением — он должен упасть сразу, с понятной ошибкой, а не сломать что-то на целевой машине.

**Пример в `.j2`-шаблоне:**

```jinja2
db_password={{ target_db_password | mandatory }}
```

Если `target_db_password` не определена, Ansible немедленно останавливает выполнение с ошибкой вида `"A mandatory variable was is undefined"`, вместо того чтобы сгенерировать конфиг с пустым паролем.

По сути `mandatory` — это противоположность `default`: `default` говорит "если переменной нет, подставь вот это", `mandatory` говорит "если переменной нет, останови всё немедленно".

### b64decode — чтение файлов через slurp

**Зачем:** модуль `slurp` — стандартный способ прочитать содержимое файла **с целевого хоста** в переменную. Но у него есть особенность: содержимое возвращается не как обычный текст, а в кодировке **base64**. Без декодирования в переменной будет нечитаемая каша вида `bmdpbng...`.

**Пример в playbook:**

```yaml
- name: Прочитать конфиг с целевого хоста
  ansible.builtin.slurp:
    src: /etc/nginx/nginx.conf
  register: nginx_config

- name: Показать содержимое
  ansible.builtin.debug:
    msg: "{{ nginx_config.content | b64decode }}"
```

Содержимое лежит в поле `content` (не `stdout`, как у `command`/`shell`), и читать его можно **только** через `| b64decode`.

**Частая ошибка рядом с этой темой — где выполняется чтение:**
- `slurp` — читает файл **с целевого хоста** (managed node);
- `lookup('file', ...)` — читает файл **с control node** (машины, откуда запущен Ansible).

Это классическая ловушка: `lookup('file', '/etc/nginx/nginx.conf')` прочитает конфиг не с настраиваемого сервера, а с твоей собственной машины, и ошибки не будет — просто не те данные.

### regex_search — поиск по регулярному выражению

**Зачем:** вытащить из строки кусок по шаблону — например, выдернуть номер версии или IP-адрес из длинного вывода команды.

**Пример в playbook:**

```yaml
- name: Получить строку с версией
  ansible.builtin.command: nginx -v
  register: nginx_version_raw

- name: Извлечь номер версии
  ansible.builtin.set_fact:
    nginx_version: "{{ nginx_version_raw.stderr | regex_search('nginx/([0-9.]+)', '\\1') | first }}"
```

Почему `stderr`, а не `stdout`: у `nginx -v` есть известная особенность — версию он печатает в **stderr**, а stdout оставляет пустым. Это не единичный случай: часть утилит пишет служебную информацию (версии, предупреждения, прогресс) именно в stderr, оставляя stdout для основных данных. Если после `register` regex "ничего не находит" в `stdout` — первым делом стоит заглянуть в `stderr`.

**Два важных нюанса:**

1. **Со скобками в шаблоне результат — список, а не строка.** Скобки `()` в регулярном выражении называются **группой захвата**: они выделяют кусок совпадения, который можно вытащить отдельно от остального. В примере выше шаблон `'nginx/([0-9.]+)'` совпадает со всей подстрокой `nginx/1.24.0`, но скобки выделяют из неё только цифры с точками — `1.24.0`. Второй аргумент `'\\1'` говорит фильтру: "верни содержимое первой группы".

   Групп в одном шаблоне может быть несколько — каждая новая пара скобок получает следующий номер, считая слева направо: первая пара — `\1`, вторая — `\2`, и так далее. Например, шаблон `'([a-z]+)/([0-9.]+)'` на строке `nginx/1.24.0` захватит две группы: `\1` = `nginx`, `\2` = `1.24.0`. В нашем примере пара скобок одна, поэтому и группа только `\1`.

   Почему в коде написано `'\\1'`, а не `'\1'`: это экранирование YAML. Внутри строки в кавычках обратный слэш — спецсимвол, поэтому его удваивают: в файле пишется `\\1`, YAML при разборе превращает это в `\1`, и уже эту ссылку на группу получает движок регулярных выражений.

   Нюанс в том, что в этом режиме `regex_search` возвращает **список** групп, даже если группа всего одна — поэтому в конце стоит `| first`, который достаёт первый (единственный) элемент списка.

2. **При отсутствии совпадения `first` падает.** Если шаблон ничего не нашёл, `regex_search` возвращает пустоту — и `first`, которому нечего доставать, роняет задачу с ошибкой. Если совпадение не гарантировано, нужна защита через `default`:

```yaml
- name: Извлечь номер версии (с защитой от отсутствия совпадения)
  ansible.builtin.set_fact:
    nginx_version: "{{ nginx_version_raw.stderr | regex_search('nginx/([0-9.]+)', '\\1') | default(['unknown'], true) | first }}"
```

Это та же задача из примера выше, но с добавленным `default(['unknown'], true)` между `regex_search` и `first`. Если шаблон не совпал (например, nginx не установлен и в выводе нет строки с версией), вместо пустоты `first` получит список `['unknown']` и вернёт строку `unknown` — задача не упадёт. Обрати внимание: значение в `default` — именно **список** `['unknown']`, а не строка, потому что `first` ожидает на входе список (как раз такой, какой вернул бы `regex_search` при успехе).

### regex_replace — замена по регулярному выражению

**Зачем:** как `replace`, но с полноценными регулярными выражениями — когда искомый кусок не фиксированная подстрока, а шаблон.

**Пример в `.j2`-шаблоне:**

```jinja2
{# убрать кавычки вокруг значения #}
server_ip={{ raw_value | regex_replace("^'(.*)'$", '\\1') }}
```

**Главная ловушка: при отсутствии совпадения — не ошибка, а мусор.** Если шаблон не совпал, `regex_replace` **молча возвращает строку нетронутой**. Playbook не упадёт, задача будет зелёной — но дальше по коду поедет исходное значение. Наглядно, на том же примере с кавычками:

```jinja2
{# ожидаем raw_value в одинарных кавычках: '10.0.0.1' #}
server_ip={{ raw_value | regex_replace("^'(.*)'$", '\\1') }}
```

Два сценария:

- `raw_value` = `'10.0.0.1'` (в кавычках) → шаблон совпал → в конфиг уйдёт `server_ip=10.0.0.1` — всё хорошо;
- `raw_value` = `"10.0.0.1"` (в **двойных** кавычках, которых шаблон не ожидает) → шаблон не совпал → `regex_replace` вернёт строку как есть, и в конфиг уйдёт `server_ip="10.0.0.1"` — с кавычками, которые там не нужны.

Во втором сценарии ни одна задача не упала, playbook отработал зелёным. Мусор обнаружится не в момент замены, а позже — когда сервис не сможет распарсить свой конфиг. Поэтому после `regex_replace` с критичными данными имеет смысл проверять результат, а не доверять зелёному статусу задачи.

Отдельная тема, не связанная с примером выше, — многострочный текст и флаг `(?m)`. Это уже не фильтр, а синтаксис самих регулярных выражений, но всплывает именно при работе с regex-фильтрами.

Сначала о том, что такое многострочный текст в этом контексте. Когда команда выводит несколько строк — например, `cat /etc/nginx/nginx.conf` печатает конфиг целиком — в `register.stdout` это попадает как **одна строка** с символами переноса `\n` внутри:

```
"user nginx;\nworker_processes auto;\nlisten 80;\nlisten 443;"
```

Для человека это четыре строки, для регулярного выражения по умолчанию — одна сплошная строка. Поэтому якоря `^` (начало) и `$` (конец) означают начало и конец **всего этого текста целиком**: `^` совпадёт только перед `user nginx;`, и больше нигде. Если ты хочешь, чтобы `^listen` нашёл строки `listen 80;` и `listen 443;` в середине текста — по умолчанию не найдёт, они же не в начале всего текста.

Решение — специальная пометка `(?m)`, которая пишется прямо внутри шаблона, в самом его начале. У регулярных выражений есть переключатели режимов работы — их называют флагами. Обычно флаги передаются отдельно от шаблона (в Python это аргумент `multiline=True`), но их можно записать и внутри самого шаблона в виде `(?буква)` — такая запись называется инлайн-флагом ("inline" — встроенный в строку шаблона). Флаг `(?m)` включает многострочный режим: с ним `^` и `$` начинают означать начало и конец **каждой строки** (по границам `\n`), а не всего текста:

```jinja2
{# закомментировать все строки, начинающиеся с listen #}
{{ config_text | regex_replace('(?m)^listen', '#listen') }}
```

Без `(?m)` шаблон `^listen` совпал бы только если **весь текст** начинается с `listen`. С `(?m)` — совпадает начало **каждой строки**.

## Итоговая идея

Фильтр — инструмент для конкретной практической проблемы: "значение пришло не в том виде, в каком оно нужно дальше" — грязное после `register`, не того регистра, не того типа, отсутствует вовсе. Фильтр решает эту проблему прямо в месте подстановки, без отдельной задачи в playbook.
