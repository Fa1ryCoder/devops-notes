# 7.1. «Истинное» слияние и разрешение конфликтов в git merge

## Fast-forward (перемотка) и «истинное» слияние

Fast-forward возможен, когда текущая ветка — прямой предок сливаемой: в ней нет ни одного коммита, которого нет в другой ветке. В этом случае Git просто передвигает указатель текущей ветки вперёд, к последнему коммиту сливаемой ветки. Новый коммит не создаётся, история остаётся линейной.

«Истинное» слияние нужно, когда ветки разошлись — в каждой есть свои коммиты, которых нет в другой. Просто передвинуть указатель нельзя: это стёрло бы уникальные коммиты текущей ветки. Вместо этого Git создаёт merge-коммит с двумя родителями, который объединяет изменения из обеих веток, а история превращается в граф с точкой слияния.

## Трёхстороннее слияние: base, ours, theirs

Чтобы объединить два разошедшихся состояния, Git сравнивает не два, а три версии:

- **base** — общий предок, коммит, в котором ветки разошлись;
- **ours** — текущая ветка, в которую сливают;
- **theirs** — ветка, которую сливают.

Найти base вручную, не разбирая граф глазами, можно так:

```bash
git merge-base master feature
```

Команда возвращает SHA коммита, от которого разошлись ветки.

Дальше Git сравнивает ours и theirs с base и пытается применить оба набора изменений одновременно. Если изменения не пересекаются — затронуты разные файлы или разные строки одного файла — слияние проходит автоматически, без участия человека.

## Что происходит при конфликте

### Шаг 1. Git пытается слить автоматически

Конфликт возникает, если один и тот же участок файла изменён по-разному в обеих ветках — Git не может решить, чья версия правильная, и останавливается:

```bash
$ git merge feature
Auto-merging file.txt
CONFLICT (content): Merge conflict in file.txt
Automatic merge failed; fix conflicts and then commit the result.
```

### Шаг 2. Слияние приостанавливается

Коммит не создаётся. Git запоминает, что слияние в процессе, через ссылку `MERGE_HEAD` — она создаётся для любого «истинного» слияния, конфликт это или нет, и убирается, когда появляется мердж-коммит, — и помечает конфликтующие файлы в индексе как unmerged.

`git status --short` показывает это кодом `UU` — файл изменён независимо в обеих версиях.

### Шаг 3. Файл на диске переписывается маркерами

Git вставляет в сам файл обе конфликтующие версии, разделённые маркерами, — это реальное содержимое на диске, не абстракция. Если открыть файл в любом редакторе, будет ровно это: маркеры прямо в тексте, вперемешку со строками, которые не конфликтовали.

```
<<<<<<< HEAD
изменение из master
=======
изменение из feature
>>>>>>> feature
```

Всё между `<<<<<<< HEAD` и `=======` — текущая версия (ours), между `=======` и `>>>>>>> feature` — версия сливаемой ветки (theirs). Это обычный текст: редактор подсвечивает маркеры для удобства, но никакой автоматики здесь нет — файл в таком виде не готов к коммиту, его нужно вручную привести к финальному состоянию.

## Как разрешить конфликт

### Шаг 1. Посмотреть подробнее (не обязательно)

Если по маркерам не понятно, что именно изменила каждая сторона, можно заглянуть в base — версию до расхождения.

Без base видны только два готовых текста, и непонятно, конфликтуют ли они по смыслу или это просто две независимые правки:

```
<<<<<<< HEAD
цена: 100 руб
=======
цена: 150
>>>>>>> feature
```

С base сразу видно, что поменяла каждая сторона:

```
<<<<<<< HEAD
цена: 100 руб
||||||| base
цена: 100
=======
цена: 150
>>>>>>> feature
```

master добавил «руб», feature поднял число со 100 до 150 — это две независимые правки одной строки, а не выбор «либо-либо». Правильное разрешение здесь — не взять одну сторону, а объединить: «цена: 150 руб».

Два способа увидеть base показывают одно и то же, но по-разному.

**1. Стиль diff3.** Настраивается заранее и на уже случившийся конфликт задним числом не действует — если конфликт уже есть, нужно `git merge --abort` и повторить merge. Base появляется прямо внутри маркеров:

```bash
git config --global merge.conflictStyle diff3
```

Или разово, не трогая глобальный конфиг:

```bash
git -c merge.conflictStyle=diff3 merge feature
```

```
<<<<<<< HEAD
изменение из master
||||||| e6aee4e
первая строка
=======
изменение из feature
>>>>>>> feature
```

Блок между `|||||||` и `=======` — это base. С Git 2.35 доступен `zdiff3` (то же значение конфига) — он дополнительно схлопывает совпадающие строки на границах блока, разметка компактнее.

**2. Diff между стадиями.** `git status` показывает конфликтующий файл одной строкой (`UU`), но в индексе под этим же путём хранятся сразу три версии, каждая под своим номером стадии (stage): `:1` — base, `:2` — ours, `:3` — theirs. Увидеть их можно только отдельными командами, `status` их не показывает. Сравнить нужные стадии обычным diff'ом — без маркеров и без ограничения на один блок:

```bash
git diff :1:file.txt :2:file.txt   # base → ours: что изменил ours
git diff :1:file.txt :3:file.txt   # base → theirs: что изменил theirs
```

Разница видна на файле с двумя независимыми правками в разных местах. Маркеры разбивают такой конфликт на два отдельных блока:

```
name: service
<<<<<<< ours
port: 443
||||||| base
port: 8080
=======
port: 9090
>>>>>>> theirs
timeout: 30
<<<<<<< ours
workers: 4
log_level: debug
||||||| base
workers: 4
log_level: info
=======
workers: 8
log_level: info
>>>>>>> theirs
```

Чтобы понять, что вообще поменял ours, нужно смотреть в оба блока по очереди и выцеплять из каждого свою часть. `git diff :1:config.yml :2:config.yml` даёт то же самое одним списком:

```diff
 name: service
-port: 8080
+port: 443
 timeout: 30
 workers: 4
-log_level: info
+log_level: debug
```

Всё, что изменил ours по всему файлу, — сразу целиком, а не по кускам из двух разных мест. Командой `:1: :3:` — то же самое для theirs.

### Шаг 2. Разрешить конфликт

Дальше — на выбор.

Отредактировать вручную: открыть файл, привести содержимое между маркерами к финальному виду, сами маркеры удалить.

Либо взять одну сторону целиком, если по файлу должна победить она:

```bash
git restore --ours -- file.txt    # оставить свою версию
git restore --theirs -- file.txt  # взять версию сливаемой ветки
```

Команда меняет только рабочую директорию, в индексе файл остаётся unmerged.

### Шаг 3. Добавить файл(ы) в индекс

```bash
git add file.txt
```

Так для каждого конфликтующего файла — их может быть несколько одновременно.

## Продолжить или отменить

Когда все конфликты разрешены и добавлены в индекс:

```bash
git merge --continue
```

Предпочтительный способ завершить слияние; по сути обёртка над `git commit`, которая подставляет уже подготовленное сообщение вида `Merge branch 'feature'`. Обычный `git commit` без аргументов сработает так же.

У получившегося коммита теперь два родителя вместо одного — это видно прямо в самом объекте коммита:

```bash
git cat-file -p HEAD
```

```
tree d55a004dbf717e695bf9aaf03d5dcacfd8c3af1c
parent f5d01ba41cf1971a7a03b2c3cf148e42bb81c53a
parent dfa237095938ef40fd0c748940e7dcec35765ca9
author Test User <test@example.com> 1786365200 +0000
committer Test User <test@example.com> 1786365200 +0000

Merge branch 'feature'
```

Два хеша в `parents` — это master и feature на момент слияния.

Если решили не продолжать:

```bash
git merge --abort
```

Возвращает к состоянию до начала слияния и старается сохранить незакоммиченные изменения, не связанные со слиянием. Работает только при активном слиянии: без `MERGE_HEAD` команда ответит ошибкой `fatal: There is no merge to abort`. `git reset --merge` — более общая команда: сбрасывает отслеживаемые файлы к указанному коммиту (без аргумента — к HEAD, то есть туда, откуда начали сливать). При активном слиянии (`MERGE_HEAD` есть) ведёт себя так же, как `--abort`.

Жёсткий вариант — `git reset --hard`: тоже прерывает слияние, но откатывает вообще все незакоммиченные изменения в отслеживаемых файлах, даже те, что к слиянию отношения не имеют.

## git rerere: не решать один и тот же конфликт дважды

Полезно при повторяющихся конфликтах — например, один и тот же файл конфликтует при каждом rebase или регулярном слиянии долгоживущей ветки:

```bash
git config --global rerere.enabled true
```

Флаг должен быть включён в момент, когда `git merge` обнаруживает конфликт, — задним числом на уже начавшийся конфликт он не подействует. Начиная с этого момента Git фиксирует решение при разрешении, а при следующем аналогичном конфликте подставляет его вместо маркеров автоматически. Файл всё равно помечается как unmerged — решение стоит проверить и подтвердить через `git add`.
