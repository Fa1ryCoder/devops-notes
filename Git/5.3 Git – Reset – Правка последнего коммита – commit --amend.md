# 5.3 Git – Reset – Правка последнего коммита: `commit --amend`

## Назначение

`git commit --amend` заменяет последний коммит новым — с исправленным содержимым, исправленным описанием или и тем, и другим сразу.

## Алгоритм исправления последнего коммита

1. Исправляются файлы в рабочей директории.
2. Исправленные файлы добавляются в индекс (staging area) через `git add`.
3. Выполняется `git commit --amend`. Открывается редактор с описанием заменяемого коммита — его можно оставить как есть или отредактировать.

```bash
git add file.txt
git commit --amend
```

## Механика работы («под капотом»)

`--amend` выполняет два действия подряд:

1. Переносит текущую ветку на родителя последнего коммита — аналогично `git reset --soft HEAD^`. Индекс и рабочая директория не трогаются — меняется только ссылка в репозитории.
2. Создаёт новый коммит на основе текущего состояния индекса. Author (автор изменений и время их создания) по умолчанию наследуется от заменяемого коммита. Committer (тот, кто выполняет команду, и момент её выполнения) обновляется всегда — как и при любом обычном коммите.

Коммиты в Git неизменяемы, поэтому это не редактирование старого объекта: у нового коммита новый хеш, но тот же родитель, что и у заменяемого:

```bash
$ git log --oneline -1
a1b2c3d Исправить парсер конфига

$ git commit --amend --no-edit
$ git log --oneline -1
e4f5a6b Исправить парсер конфига
```

Прежний коммит физически остаётся в объектной базе Git и виден в `git reflog` — там действие зафиксировано как `commit (amend)`:

```bash
$ git reflog
e4f5a6b HEAD@{0}: commit (amend): Исправить парсер конфига
a1b2c3d HEAD@{1}: commit: Исправить парсер конфига
```

Он становится недостижимым — ни одна ветка на него не указывает. Удалён он будет позже, при сборке мусора (`git gc`).

## Полезные флаги

- `--no-edit` — заменяет коммит новыми изменениями из индекса, но пропускает вызов редактора, оставляя прежнее описание.
- `--reset-author` — обновляет на текущего пользователя ещё и Author, а не только Committer.
- `-m "новое описание"` — задаёт новое описание сразу через консоль, без вызова редактора.

```bash
git commit --amend --no-edit
git commit --amend -m "Исправленное описание"
```

## Правка только описания коммита

Если ошибка только в тексте сообщения, а содержимое коммита корректно, менять файлы и вызывать `git add` не нужно — `git commit --amend` отрабатывает и при полностью чистом индексе, пересоздавая коммит с тем же деревом файлов и новым описанием.

## Сравнение с `git reset --soft`

`--amend` заменяет только последний коммит. `git reset --soft` сдвигает ветку на произвольное количество коммитов назад — например, на два:

```bash
git reset --soft HEAD~2
git commit -m "Объединённый коммит"
```

Изменения из обоих откатанных коммитов остаются в индексе и рабочей директории единым набором, поэтому следующий `git commit` создаёт из них один коммит вместо двух. По сути, `--amend` — частный случай той же механики, ограниченный глубиной в один коммит.

## Ограничения

Ни `--amend`, ни `reset --soft` не работают глубже вершины ветки — поправить коммит в середине истории, не трогая последующие, ими нельзя. Для правки истории на произвольной глубине нужен `git rebase`.

Новый коммит после `--amend` получает того же родителя, что был у старого, — то есть не продолжает его, а встаёт рядом. Если старый коммит уже был у кого-то в локальной ветке, после force-пуша его версия и версия с origin окажутся двумя разными коммитами от одного родителя, а не последовательными — Git не сможет слить их через fast-forward и потребует ручного решения (`push --force`, лучше `--force-with-lease`, плюс согласование с командой).
