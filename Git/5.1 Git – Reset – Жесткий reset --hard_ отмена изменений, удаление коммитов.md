Незакоммиченные ошибочные правки отменяются обычными средствами — `git restore`, повторным `git add`. Но если правки уже закоммичены, откатывать нужно уже сами коммиты — нужен `git reset --hard`, самый жёсткий из трёх режимов reset.

---

## 1. Что происходит при жёстком ресете

`--hard` — самый радикальный из режимов reset: меняются сразу все три уровня репозитория. Команда `git reset --hard <коммит>` одним действием:

* перемещает указатель текущей ветки на `<коммит>`;
* приводит индекс к состоянию, зафиксированному в этом коммите;
* переписывает файлы в рабочей директории, чтобы они совпадали с этим коммитом.

Сразу после этого `git status` не покажет ни staged, ни unstaged изменений (untracked-файлы вне игры, их эта команда не касается).

У `--hard` есть более мягкие режимы — `--soft` и `--mixed`, которые не трогают часть из этих трёх уровней. Но это уже отдельная тема.

---

## 2. Как указать коммит для отката

Целевой коммит можно задать разными способами:

* Полным или сокращённым **SHA-1-хешем** — `git reset --hard a1b2c3d`.
* **Относительной ссылкой**: `HEAD~1` — на один коммит назад от текущего, `HEAD~3` — на три; число можно опустить, `HEAD~` означает то же, что и `HEAD~1`. `@` — короткий синоним `HEAD`, поэтому `@~2` и `HEAD~2` — одна и та же запись.
* **Вообще без коммита** — целью становится сам `HEAD`, и ветка никуда не движется: это тот же сценарий очистки рабочей директории. Новое начинается там, где коммит указан явно.

---

## 3. Судьба коммитов, оставшихся позади

Когда `reset --hard` передвигает ветку назад, коммиты, на которых она раньше стояла, физически никуда не деваются — это по-прежнему полноценные объекты в базе Git, со своим содержимым и хешем. Меняется только одно: ни одна ветка или тег на них больше не указывает. А `git log` показывает только коммиты, у которых есть ветка или тег.

Такое состояние называется недостижимостью (unreachable): объект есть, а пути к нему от текущих веток нет. Отсюда и расхожая формулировка «коммиты удалены» — на самом деле они не стёрты, а просто выпали из истории проекта, до которой обычными командами уже не добраться.

---

## 4. Восстановление после жёсткого ресета

Пока запись о «потерянном» коммите жива, вернуться к нему можно двумя способами.

**Через git reflog.** Он показывает журнал перемещений `HEAD`, включая и сам reset:

```bash
git reflog
```
```
9f8e7d6 HEAD@{0}: reset: moving to 9f8e7d6
a1b2c3d HEAD@{1}: commit: добавил обработку ошибок
```

Нужный хеш — в строке до ресета. Вернуться можно и напрямую по хешу (`git reset --hard a1b2c3d`), и через саму запись reflog (`git reset --hard HEAD@{1}`).

**Через ORIG_HEAD.** Перед тем как сдвинуть ветку, любая команда, переписывающая историю, — reset, слияние и другие — сохраняет её прежнее положение в `.git/ORIG_HEAD`. Это самый короткий путь назад:

```bash
git reset --hard ORIG_HEAD
```

Разница между способами — в глубине памяти: ORIG_HEAD помнит только последнюю позицию и перезаписывается следующей такой командой, а reflog хранит куда более длинную цепочку и остаётся источником истины, если откатов было несколько подряд.

Окно на восстановление не бесконечно: недостижимые записи по умолчанию живут в reflog не меньше 30 дней, после чего попадают под ближайшую сборку мусора.

---

## 5. Что необратимо: незакоммиченные изменения

`git reset --hard` подгоняет индекс и рабочую директорию под целевой коммит без каких-либо оговорок: всё, что не было зафиксировано коммитом, просто перезаписывается. Восстановить это нечем — `git reflog` и `ORIG_HEAD` помнят только коммиты (как показано выше), а правка, которая коммитом не стала, никакого следа в базе Git не оставляет.

Если правки нужно сохранить, а не потерять, `git reset --hard` — не тот инструмент: для этого случая существуют `git reset --soft` (не трогает рабочую директорию) и `git stash` (откладывает изменения на потом).

Есть и второй риск — уже не про содержимое, а про совместную работу. Если «отменённые» коммиты успели попасть в общий remote, после reset --hard локальная ветка и `origin/...` расходятся — указывают на разные коммиты. Чтобы протолкнуть переписанную историю, понадобится `push --force`, а это способно стереть чужую работу, если коллеги уже что-то допушили поверх старой истории.
