# Изолированная установка Ansible на кассовый сервер

## Зачем вообще так делаем

Artix:ControlCenter — программное обеспечение, предназначенное для централизованного управления конфигурацией торговой сети и обмена данными с АСТУ. Кассовый сервер имеет микросервисную архитектуру: на нём параллельно крутится множество отдельных независимых сервисов, а не одно цельное приложение.

Многие из этих сервисов завязаны на системные библиотеки Linux. Если ставить Ansible стандартным способом через `apt`, он жёстко привяжется к системному Python и может принудительно обновить общие библиотеки. Это несёт огромный риск нарушить совместимость и сломать работу самого ControlCenter.

Поэтому мы ставим Ansible изолированно через `pipx`: он получает свой собственный, закрытый интерпретатор Python и свои личные библиотеки, вообще никак не пересекаясь с компонентами Artix.

---

## Шаг 1. Установка утилиты pipx

```bash
sudo apt update
sudo apt install -y pipx
```

**Что это:** `pipx` — обёртка над обычным пакетным менеджером Python (`pip`). Для каждой устанавливаемой программы `pipx` автоматически создаёт отдельное изолированное виртуальное окружение (venv), защищая систему от конфликтов версий библиотек.

---

## Шаг 2. Настройка путей (PATH)

```bash
pipx ensurepath
source ~/.bashrc
```

**Что такое `ensurepath` технически:** это не отдельная программа, а **подкоманда** самой утилиты `pipx` (так же как `git commit` — `commit` это подкоманда `git`, а не своя программа). Других механизмов вызова `ensurepath` в системе нет — это внутренняя логика `pipx`.

**Зачем `pipx ensurepath`:** все бинарники, которые ставит `pipx` (включая будущий `ansible`), кладутся в папку `~/.local/bin`. Эта папка не всегда есть в переменной `$PATH` по умолчанию — без неё шелл не найдёт команду `ansible`, даже если она физически лежит на диске. Подкоманда `ensurepath` открывает файл `~/.bashrc` и дописывает туда строку вида `export PATH="$PATH:$HOME/.local/bin"`.

**Зачем `source ~/.bashrc`:** файл `~/.bashrc` — это конфиг, который шелл (bash) читает только в момент своего запуска (открытие нового терминала, логин). Если файл изменился, пока терминал уже был открыт, шелл сам по себе не перечитает его. Команда `source ~/.bashrc` форсирует (т.е. принудительно запускает прямо сейчас, не дожидаясь, пока это произошло бы само по себе позже) перечитывание файла в уже открытой сессии — так новый `PATH` применяется немедленно, без перезапуска терминала.

Альтернативная запись той же команды: `. ~/.bashrc` (точка вместо слова `source` — то же самое).

**Проверка:**

```bash
echo $PATH | grep -o "$HOME/.local/bin"
```

Если в консоль вывелся путь (`/root/.local/bin` или с именем вашего пользователя) — всё сделано правильно.

**Важный момент — почему путь именно `~/.local/bin`, а не `~/.local/pipx/venvs/ansible/`:**

Это два разных места с разными ролями.

`~/.local/pipx/venvs/ansible/` — это полная изолированная среда (venv). Внутри неё хранится **всё**: и отдельный интерпретатор Python, и все библиотеки (PyYAML, jinja2, jmespath и т.д.), и сами исполняемые скрипты:

```
~/.local/pipx/venvs/ansible/
├── bin/
│   ├── python          ← отдельный интерпретатор Python
│   ├── ansible
│   ├── ansible-playbook
│   └── ...
└── lib/
    └── python3.10/site-packages/   ← все библиотеки
```

`~/.local/bin/` — это общая папка, куда `pipx` кладёт не сами файлы, а **симлинки** на бинарники из venv:

```bash
ls -la ~/.local/bin/ansible
# lrwxrwxrwx ansible -> /root/.local/pipx/venvs/ansible/bin/ansible
```

Зачем так разделено, а не всё в одном месте: если через `pipx` поставить несколько программ (например, ещё `black` и `httpie`), каждая будет жить в своём отдельном venv:

```
~/.local/pipx/venvs/ansible/
~/.local/pipx/venvs/black/
~/.local/pipx/venvs/httpie/
```

Если бы PATH указывал на каждую из этих папок отдельно — пришлось бы дописывать в PATH по одной строке на каждую установленную программу. Вместо этого используется единая точка входа: одна папка `~/.local/bin` в PATH, а в неё накидываются ярлыки на бинарники из всех venv сразу:

```
~/.local/bin/
├── ansible -> ~/.local/pipx/venvs/ansible/bin/ansible
├── black   -> ~/.local/pipx/venvs/black/bin/black
└── http    -> ~/.local/pipx/venvs/httpie/bin/http
```

Итог: `~/.local/pipx/venvs/ansible/` — это **склад**, где хранится сам инструмент со всеми его зависимостями. `~/.local/bin/` — это **витрина с указателями**, куда смотрит терминал при наборе команды. PATH достаточно настроить один раз на "витрину" — и дальше любая новая программа, поставленная через `pipx install`, автоматически появляется там же, без необходимости трогать PATH заново.

## Шаг 3. Установка Ansible

```bash
pipx install --include-deps ansible
```

**Что делает:** создаёт изолированную среду в каталоге `~/.local/pipx/venvs/ansible/` со своим собственным интерпретатором Python — отдельным от системного `/usr/bin/python3`. Туда же ставятся все Python-зависимости Ansible.

**Зачем флаг `--include-deps`:** пакет `ansible` (метапакет, не путать с `ansible-core`) тянет за собой вспомогательные библиотеки: `jmespath` (нужна для фильтра `json_query` в Jinja2-шаблонах), `netaddr` (для работы с IP/подсетями) и другие. Эти зависимости в любом случае физически устанавливаются — `pip` подтянет их при установке самого `ansible`, иначе он не заработает.

Разница в том, **становятся ли исполняемые утилиты этих зависимостей видны снаружи venv, напрямую из терминала**. Без флага `pipx` считает доступным извне только сам `ansible` (и его команды вроде `ansible-playbook`), а вспомогательные тулы остаются "закопаны" внутри venv. С флагом `--include-deps` наружу выставляются все исполняемые файлы — и самого `ansible`, и его зависимостей. Это важно, потому что некоторые модули Ansible в рантайме рассчитывают на прямую доступность этих вспомогательных инструментов.

## Шаг 4. Проверка работы

```bash
ansible --version
which ansible
```

Ожидаемый результат:

```
ansible [core 2.17.x]
  executable location = /root/.local/bin/ansible
  python version = 3.10.x ... (/root/.local/pipx/venvs/ansible/bin/python)
```

**Критически важно:** обратить внимание на строку `python version`. Путь должен вести внутрь `pipx/venvs/ansible/...`, а не на общий `/usr/bin/python3`. Это подтверждение того, что Ansible изолирован и прод-система в безопасности.

---

Если в будущем понадобится полностью удалить Ansible с сервера:

```bash
pipx uninstall ansible
```

Команда удаляет всё бесследно, не оставляя «мусора» в системном Python.

---

## Итоговый чек-лист (копировать и выполнять по порядку)

```bash
# 1. Ставим базу
sudo apt update && sudo apt install -y pipx

# 2. Прописываем пути и обновляем окружение
pipx ensurepath
source ~/.bashrc

# 3. Ставим изолированный Ansible
pipx install --include-deps ansible

# 4. Проверяем корректность путей Python
ansible --version
which ansible
```
