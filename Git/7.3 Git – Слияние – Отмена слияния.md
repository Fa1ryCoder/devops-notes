# 7.3. Отмена слияния

## 1. Отмена завершённого слияния

Отменить уже сделанное слияние — то же самое, что отменить обычный коммит: `git reset --hard <коммит>`. Особенность в другом: у merge-коммита два родителя, но сам он существует только в той ветке, в которую вливали, — скажем, в `master`, если `git merge feature` выполнялся, стоя на `master`. В истории `feature` этого коммита нет вообще.

Например, `master` и `feature` разошлись — обе ветки по-разному меняют одну и ту же строку `line1`. Сливаем `feature`, конфликт разрешаем вручную и коммитим:

```bash
git log --oneline --graph --all --decorate
```
```
*   947cbd0 (HEAD -> master) Merge branch 'feature'
|\  
| * cbeac23 (feature) feature: добавляем feature.txt
| * adf4dc0 feature: меняем line1
* | b4ad255 master: меняем line1
|/  
* 3fbbac9 base: создание файла
```

У коммита два родителя — `b4ad255` (master) и `cbeac23` (feature), это видно в строке `Merge:` из `git show`. Но в истории `feature` самого коммита нет: merge-коммит создаётся на той ветке, на которой стоишь в момент `git merge` (здесь — `master`), и указатель этой ветки двигается на него. Указатель `feature` при этом не трогается вообще:

```bash
git log feature --oneline
```
```
cbeac23 feature: добавляем feature.txt
adf4dc0 feature: меняем line1
3fbbac9 base: создание файла
```

`git branch --contains 947cbd0` — какие ветки содержат этот коммит — подтвердит то же самое: только `master`.

Для отмены `master` сбрасывают на состояние до слияния. Проще всего указать эту точку через `ORIG_HEAD`. Туда Git сохраняет положение `HEAD` перед потенциально опасными операциями — `merge`, `reset` и подобными, и сам `merge` не исключение:

```bash
git log --oneline -1 ORIG_HEAD
```
```
b4ad255 master: меняем line1
```

```bash
git reset --hard ORIG_HEAD
```
```
HEAD is now at b4ad255 master: меняем line1
```

Обычные коммиты `ORIG_HEAD` не трогают — его обновляют только операции вроде `merge` или `reset`. Поэтому даже если между слиянием и отменой было сделано ещё несколько коммитов, `reset --hard ORIG_HEAD` уберёт слияние и всё, что после него, одним шагом, без подсчёта, на сколько коммитов назад откатываться. Если нужна более ранняя точка — `ORIG_HEAD` уже перезаписан чем-то другим — годится обычный `reset --hard` на хеш или `HEAD~N`.

После сброса `master` снова там, где был до слияния:

```bash
git log --oneline --graph --decorate master feature
```
```
* b4ad255 (HEAD -> master) master: меняем line1
| * cbeac23 (feature) feature: добавляем feature.txt
| * adf4dc0 feature: меняем line1
|/  
* 3fbbac9 base: создание файла
```

Коммит `947cbd0` из графа пропал — тот же эффект недостижимости, что и при обычном `reset --hard`: объект физически остался в базе, просто на него больше не ссылается ни одна ветка. `git branch --contains 947cbd0` теперь ничего не выведет.

## 2. Повторное слияние

Слить ветки снова можно в любой момент. Но если конфликтующие строки за это время не поменялись, конфликт возникнет ровно там же:

```bash
git merge --log feature
```
```
Auto-merging file.txt
CONFLICT (content): Merge conflict in file.txt
Automatic merge failed; fix conflicts and then commit the result.
```

```bash
cat file.txt
```
```
<<<<<<< HEAD
master-line1
=======
feature-line1
>>>>>>> feature
line2
line3
```

Тот же файл, та же строка, те же две версии — Git не запоминает, что конфликт здесь уже разрешали.

`git merge --log` добавляет в сообщение коммита shortlog коммитов сливаемой ветки — `feature`, не обеих веток сразу. При конфликте результат попадает не сразу в коммит, а в `.git/MERGE_MSG` — оттуда его подхватит редактор после `git add`:

```bash
cat .git/MERGE_MSG
```
```
Merge branch 'feature'

* feature:
  feature: добавляем feature.txt
  feature: меняем line1

# Conflicts:
#	file.txt
```

Строки под `# Conflicts` — комментарий, в коммит не попадут в любом случае. А из shortlog'а стоит оставлять только то, что реально информативно: `feature: добавляем feature.txt` называет конкретный артефакт, который иначе никак не всплыл бы в истории `master` — это стоит оставить. А `feature: меняем line1` ничего не говорит сверх того, что и так видно по самому конфликту, — эту строку можно убрать:

```bash
git commit -m "Merge branch 'feature'

* feature:
  feature: добавляем feature.txt

Конфликт в line1 разрешён вручную."
```

При самом разрешении конфликта тоже стоит трогать только конфликтующие строки: основная задача слияния — свести две ветки, а не заодно поправить что-то ещё.

## 3. Комбинированный diff

Merge-коммит `10d3f55` тоже можно посмотреть через `git show` — но формат diff'а у него другой: вместо одного символа `+`/`-` перед строкой стоят два, по одному на каждого родителя. Первый символ — про `master`, второй — про `feature` (тот же порядок, что в `Merge:` из раздела 1). Это называется комбинированным diff'ом (`--cc`), Git включает его автоматически для merge-коммитов:

```bash
git show 10d3f55
```
```
...
diff --cc file.txt
--- a/file.txt
+++ b/file.txt
@@@ -1,3 -1,3 +1,3 @@@
- master-line1
 -feature-line1
++combined-line1
  line2
  line3
```

Первая строка помечена только в первой колонке (`-`, `master`) — `master-line1` было в `master`, но пропало из результата. Вторая помечена только во второй (`-`, `feature`) — та же история для `feature-line1`. Это старые версии `line1`, которые в итоге заменила `combined-line1`.

Третья строка, `++combined-line1`, помечена в обеих колонках сразу: этой строки не было ни у `master`, ни у `feature` — она появилась только при разрешении конфликта. Зеркальный случай — `--` в обеих колонках — означает обратное: строка была одинаковой у обоих родителей, но пропала из результата.

## 4. Восстановление отменённого слияния

Пока нужный коммит физически жив в базе (раздел 1), отмену можно откатить.

ORIG_HEAD не хранит историю изменений. Это единственный слот, фиксирующий состояние HEAD строго перед последней операцией, перемещающей указатель (merge, reset, rebase). Каждая следующая подобная операция полностью перезаписывает этот слот.

Как меняется указатель:

1. Слияние: после git merge переменная ORIG_HEAD указывает на коммит, который был до слияния.
2. Отмена: если сделать git reset --hard ORIG_HEAD, переменная ORIG_HEAD перезапишется и будет указывать уже на сам отмененный merge-коммит. На этом этапе слияние можно вернуть командой git reset --hard ORIG_HEAD.
3. Потеря ссылки: если после отмены выполнить любую новую операцию (например, повторный merge), слот ORIG_HEAD снова перезапишется.

После шага 3 восстановить первый отмененный merge-коммит через ORIG_HEAD невозможно — его хеш придется искать в git reflog. Помогает `git reflog` (он же `git log -g`) — там хранятся все перемещения `HEAD`, а не только последнее:

```bash
git reflog
```
```
10d3f55 HEAD@{0}: commit (merge): Merge branch 'feature'
b4ad255 HEAD@{1}: reset: moving to ORIG_HEAD
947cbd0 HEAD@{2}: commit (merge): Merge branch 'feature'
b4ad255 HEAD@{3}: commit: master: меняем line1
...
```

`HEAD@{2}` — тот самый первый merge-коммит. Восстановление — обычный `reset --hard` на найденный хеш:

```bash
git reset --hard 947cbd0
```
```
HEAD is now at 947cbd0 Merge branch 'feature'
```

История и содержимое файлов возвращаются полностью, как будто отмены и не было.

Правило, по которому Git в итоге всё же удаляет такие объекты, — `git gc`. Он трогает объект только тогда, когда тот одновременно недостижим ни из одной ветки и не упомянут ни в одной записи reflog. Пока запись в reflog жива, объект защищён. После её истечения действует ещё один запас — `gc.pruneExpire`, по умолчанию 2 недели: именно столько объект должен «пролежать» недостижимым, прежде чем `git gc` его окончательно удалит.
