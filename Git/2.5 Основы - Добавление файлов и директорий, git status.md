## 1. Особенности работы с директориями

Git по историческим причинам **не умеет работать с пустыми директориями** — он их просто не видит. Причина простая: Git отслеживает не папки, а файлы. Папка сама по себе для Git не существует — это просто путь до файла. Нет внутри ни одного файла — нечего запоминать, поэтому пустая директория для Git невидима. (Внутри это выглядит так: файлы — объекты `blob`, папки — объекты `tree`; пустой `tree` Git просто не создаёт.)

```bash
mkdir empty-dir
git status
# ничего не покажет — Git не видит пустую папку
```

### Как обойти это ограничение

Чтобы Git начал отслеживать папку — она должна быть не пустой. Общепринятое решение — добавить в неё вспомогательный файл нулевого размера `.gitkeep`:

```bash
mkdir configs
touch configs/.gitkeep
git status
# Untracked files: configs/
```

`.gitkeep` — это просто договорённость в индустрии, Git не знает о нём ничего особенного. Файл может называться как угодно, но `.gitkeep` стал стандартом де-факто. Кстати, `git status` здесь показывает только имя директории, не перечисляя файлы внутри — Git предполагает что всё её содержимое так же неизвестно ему.

## 2. Команда git add

Мы уже знаем что `git add` переводит файл в состояние `staged`. Но у команды есть несколько вариантов использования — и важный нюанс при работе с `git add .` о котором нужно знать заранее.

### Добавление файлов

```bash
# Добавить конкретный файл
git add app.py

# Добавить несколько файлов
git add app.py config.py

# Добавить всю директорию
git add src/

# Добавить все изменения в текущем каталоге
git add .
```

### Разница между git add . / git add -A / git add -u

Это частый вопрос на собеседованиях. Разберём на примере: ты сидишь в подпапке `src/`, а не в корне репозитория. Только что поправил `app.py` (файл уже отслеживается Git) — и где-то в корне репозитория лежит `notes.txt`, новый файл, который в Git ещё ни разу не добавлялся.

- **`git add .`** — добавит только `app.py`. `notes.txt` не увидит вообще, потому что он вне текущей директории (`.` — это буквально «здесь и ниже»).
- **`git add -A`** (`--all`) — добавит и `app.py`, и `notes.txt`, независимо от того, что ты сейчас в `src/`. `-A` смотрит на весь репозиторий и хватает вообще всё, что не в индексе: новое, изменённое, удалённое.
- **`git add -u`** (`--update`) — добавит только `app.py`. `notes.txt` пропустит — не потому что вне текущей директории (по области действия `-u` тоже смотрит на весь репозиторий, как `-A`), а потому что `notes.txt` новый, а `-u` трогает только файлы, которые Git уже и так отслеживает (modified/deleted). Новые файлы для него не существуют.

Зона видимости у `.` — только текущая директория и ниже по дереву, у `-A` и `-u` — весь репозиторий, независимо от того, где запущена команда. Но по содержимому `-A` и `-u` — разные команды: `-A` берёт вообще всё, `-u` — только то, что Git уже отслеживает (см. выше).

`git add .` требует осторожности — вместе с нужными файлами в индекс попадут служебные файлы редакторов и IDE. Чтобы исключить лишние файлы заранее — используется `.gitignore` (подробнее в разделе 3):

```bash
git add .
git status
# Changes to be committed:
#   new file: app.py
#   new file: .idea/workspace.xml      ← служебный файл WebStorm
#   new file: .vscode/settings.json    ← служебный файл VS Code
```

## 3. Игнорирование файлов — .gitignore

Чтобы Git не отслеживал лишние файлы — служебные папки IDE, временные файлы, секреты — в корне проекта создаётся файл `.gitignore`. В него записываем всё что Git должен игнорировать:

```gitignore
# Служебные папки IDE
.idea/
.vscode/

# Зависимости
node_modules/
vendor/

# Временные файлы
*.log
*.tmp

# Переменные окружения (секреты!)
.env
.env.local
```

```bash
git add .
git status
# Changes to be committed:
#   new file: app.py        ← добавлен
#   new file: .gitignore    ← добавлен
# .idea/ и .vscode/ — не показываются, Git их игнорирует
```

### Принудительное добавление игнорируемого файла

Даже если файл указан в `.gitignore` — его можно принудительно добавить в индекс через флаг `-f` (`--force`):

```bash
git add -f .env
```

После этого Git будет отслеживать изменения в нём в обычном режиме независимо от правил в `.gitignore`.

### Что делать если файл уже отслеживается

Правила в `.gitignore` работают **только для неотслеживаемых (`untracked`) файлов**. Если файл (например, `.env`) уже был однажды закоммичен в репозиторий — последующее добавление его в `.gitignore` ничего не изменит. Git продолжит отслеживать в нём изменения.

Чтобы перестать отслеживать файл но **сохранить его на локальном диске** — нужно удалить его из индекса:

```bash
# Удалить файл из индекса, оставив его в рабочей директории
git rm --cached .env

# Удалить целую папку из индекса (например, случайно закоммиченную .idea/)
git rm -r --cached .idea/
```

После этого нужно сделать коммит. Файл перейдёт в статус `untracked` и начнёт успешно игнорироваться `.gitignore`.

Это сценарий именно для файла, который уже коммитился раньше. Если файл ещё ни разу не попадал в коммит, а просто застейджен через `git add` — `git rm --cached` не нужен, достаточно `git restore --staged` (раздел 5), коммит вообще не потребуется.

## 4. Как работает индекс

Когда ты выполняешь `git add` — Git сохраняет в индекс не просто имя файла, а **снимок его содержимого на этот момент**.

Это важно понимать: если ты изменил файл после `git add` но до `git commit` — `git status` покажет этот файл в **двух секциях** одновременно:

```bash
echo "line 1" > app.py
git add app.py          # сохранили снимок в индексе

echo "line 2" >> app.py # изменили файл после add

git status
# Changes to be committed:        ← версия на момент git add
#   modified: app.py
#
# Changes not staged for commit:  ← новые изменения после git add
#   modified: app.py
```

В коммит попадёт именно та версия файла которая была в индексе на момент `git add` — строка "line 1". Строка "line 2" в коммит не войдёт.

Чтобы включить новые изменения в коммит — нужно снова выполнить `git add app.py`.

## 5. Отмена индексации — git restore

Команда `git restore` переносит состояние файла из одной зоны Git в другую — какая зона источник, а какая назначение, зависит от флага `--staged`.

Файл в любой момент лежит сразу в трёх местах:

- **HEAD** — что ты последний раз закоммитил через `git commit`.
- **Индекс** — что ты последний раз положил туда через `git add`.
- **Рабочая директория** — что открыто у тебя на диске прямо сейчас.

### Режим 1: `git restore --staged` — убрать из индекса

Отменяет действие `git add`: файл убирается из очереди на коммит, но все изменения на диске сохраняются.

```bash
# Убрать конкретный файл из индекса
git restore --staged <file>

# Убрать все файлы из индекса сразу
git restore --staged .
```

Пример:

```bash
git add .                      # случайно добавили всё включая .idea/
git restore --staged .idea/    # убрали .idea/ из индекса
git status
# Changes to be committed:
#   new file: app.py            ← остался в индексе
# Untracked files:
#   .idea/                      ← вернулся в untracked, файлы на диске не тронуты
```

Не путать с `git rm --cached` (раздел 3): `git restore --staged` просто убирает файл из текущей очереди на коммит, а `git rm --cached` полностью прекращает отслеживание файла Git'ом — он станет `untracked` для всех последующих коммитов.

### Режим 2: `git restore` без флагов — сбросить правки на диске

Перезаписывает файл в рабочей директории содержимым из индекса. Все локальные правки, сделанные после последнего `git add`, удаляются безвозвратно.

```bash
# Сбросить неиндексированные изменения в файле
git restore <file>
```

### Шпаргалка

| Команда | Направление | Влияние на диск | Когда использовать |
|---|---|---|---|
| `git restore --staged <file>` | HEAD → индекс | Не меняет файлы, без риска | Случайно сделал `git add`, нужно убрать файл из коммита |
| `git restore <file>` | Индекс → рабочая директория | Стирает незакоммиченные правки | Написал плохой код и хочешь откатить файл к состоянию последнего `git add` |

## 6. git status — три состояния

`git status` показывает три группы файлов одновременно:

```bash
git status
```

```
Changes to be committed:          ← 1. В индексе (staged)
  new file: app.py
  modified: config.py

Changes not staged for commit:    ← 2. Изменены, но не в индексе (modified)
  modified: main.py

Untracked files:                  ← 3. Не отслеживаются (untracked)
  README.md
```

| Секция | Статус | Что значит |
|--------|--------|------------|
| `Changes to be committed` | `staged` | Войдут в следующий коммит |
| `Changes not staged for commit` | `modified` | Изменены после последнего `git add` |
| `Untracked files` | `untracked` | Git о них не знает — ни разу не добавлялись через `git add` |

Для ежедневной работы есть компактный формат — `git status -s` (`--short`). Вместо многострочного вывода — одна строка на файл с двухбуквенным кодом:

```bash
git status -s
```

```
A  app.py
M  config.py
 M main.py
?? README.md
```

Тот же пример что и выше, просто в компактном виде: `app.py` и `config.py` — staged (A и M в первой позиции), `main.py` — modified, но не в индексе (M во второй позиции), `README.md` — untracked. Первый символ — статус в индексе, второй — в рабочей директории.

### Полный цикл состояний файла

После первого `git add` файл становится отслеживаемым и остаётся в этом состоянии, пока его явно не открепят через `git rm --cached` (раздел 3) — это единственный путь вернуться в `untracked`. `git push` не влияет на состояния файлов — он только синхронизирует историю коммитов с удалённым репозиторием:

```
touch README.md        →  untracked  (новый файл, Git не знает о нём)
git add README.md      →  staged     (добавлен в индекс)
git commit             →  committed  (сохранён в истории)
git push               →  committed  (push не меняет состояние файлов)
vim README.md          →  modified   (изменён после коммита)
git add README.md      →  staged     (снова добавлен в индекс)
git commit             →  committed  (сохранена новая версия)
git push               →  committed
```

Когда все изменения закоммичены и нет новых файлов:

```bash
git status
# On branch main
# nothing to commit, working tree clean
```
