## 1. Три места, где живут ветки

Чтобы понять, что на самом деле происходит при работе с ветками, полезно держать в голове три места, где Git хранит разные части этой картины.

Рабочая папка (working directory) — файлы, которые ты видишь и редактируешь прямо сейчас. В любой момент времени она показывает ровно одну версию проекта — ту, что соответствует текущей ветке.

`.git/refs/heads/` — здесь лежат сами ветки: каждая — это файл, в котором записан только хеш коммита, на который она указывает.

`.git/objects/` — архив всех снимков проекта за всю историю: сжатые объекты (blob, tree, commit), адресуемые своим хешем. Снимки в `objects/` никогда не изменяются и не удаляются: новый коммит всегда добавляет в архив новый снимок, а не переписывает старый.

## 2. От клонирования до новой ветки

Дальше — пример, который показывает, как эти три места меняются на каждом шаге.

`git clone` скачивает содержимое архива целиком и создаёт ветку `main` с хешем последнего коммита — назовём его `C`. `HEAD` сразу указывает на `main`, а рабочая папка заполняется файлами из снимка `C`.

Дальше создаётся вторая ветка: `git switch -c feature/new-fich`. В `refs/heads/` появляется новый файл, но хеш в нём — тот же самый `C`, что и в `main`: скопировался только хеш, больше ничего. Рабочая папка не меняется ни на байт, потому что обе ветки указывают на один и тот же снимок; изменилось только то, куда теперь указывает `HEAD`.

Слэш в имени ветки — это соглашение для группировки: физически `feature/new-fich` лежит по пути `.git/refs/heads/feature/new-fich`, то есть `feature` становится подпапкой, а все ветки вида `feature/...` можно разом отфильтровать через `git branch --list 'feature/*'`. Из-за той же вложенности нельзя завести ветку `feature`, если уже существует `feature/new-fich` (и наоборот): путь `.git/refs/heads/feature` должен был бы быть одновременно и файлом — самой веткой `feature`, — и папкой, потому что внутри должен лежать `new-fich`. В файловой системе так не бывает, поэтому Git на такой попытке просто выдаст ошибку.

## 3. Коммит добавляет снимок, а не переписывает старый

Дальше — правки кода, `git add`, `git commit`. В момент коммита в архив добавляется новый снимок — назовём его `D`. Именно добавляется: снимок `C` остаётся на месте нетронутым, никто его не переписывает. При этом `D` физически содержит новые blob-объекты только для изменённых файлов — всё, что не менялось, `D` переиспользует из `C` по ссылкам, а не хранит повторно.

Каждый такой новый blob — это полный снимок файла целиком, а не дельта поверх старого содержимого. Поменялась хоть одна строка — `D` получит новый blob с полным текстом файла, все строки, не только изменённая: хеш считается от всего содержимого сразу, и любое изменение даёт совершенно другой хеш. Логически Git — снапшотная система, а не система патчей.

Меняется только `feature/new-fich`: файл этой ветки хранил хеш `C`, а теперь в нём записан хеш `D` — новый последний коммит на этой ветке. Файл `main` никто не трогал, в нём всё ещё записан `C` — фича туда не попала. Картина истории на этом шаге выглядит так:

```
A ← B ← C          main
         ↖ D       feature/new-fich
```

## 4. git push: копия уезжает на сервер

`git push -u origin feature/new-fich` отправляет снимок `D` на сервер и создаёт там такую же ветку `feature/new-fich` с тем же хешем. Серверный `main` эта операция не трогает: фича живёт в своей ветке и в общую историю пока не попадает — слияние, если до него дойдёт, произойдёт отдельным шагом.

## 5. Переключение веток: как перерисовывается рабочая папка

Здесь начинается самое интересное. `git switch main` возвращает тебя обратно — а в рабочей папке в этот момент лежит версия `D` (фича), хотя должна появиться `C`. Кажется, что «файлы уже изменены» и переключение должно быть сложным. На деле всё просто:

1. `HEAD` перестаёт указывать на `feature/new-fich` и начинает указывать на `main`.
2. Через `main` Git находит хеш `C` — тот самый снимок, который всё это время нетронутым лежал в архиве.
3. Рабочая папка перерисовывается: всё, что отличается между `D` и `C`, откатывается на версию из `C`.

В результате в папке снова чистая версия `C`, будто фичи никогда не было. Но фича не потеряна: снимок `D` по-прежнему в архиве, ветка `feature/new-fich` на него указывает, а после пуша есть ещё и копия на сервере.

## 6. Ветки расходятся

Работа на `main` может продолжаться параллельно: правишь код, коммитишь — в архив добавляется снимок `E`, ветка `main` переезжает с `C` на `E`. Получается развилка:

```
A ← B ← C ← E      main
         ↖ D       feature/new-fich
```

Обе линии живут независимо: `git switch feature/new-fich` в любой момент снова перерисует рабочую папку — уже под `D`. Свести две линии в одну — это уже слияние, оно разобрано в теме про базовые операции с ветками.
