# 3.4 Git – Ветки – Перенос незакоммиченных изменений

## 1. Проблема: незапланированная сложность задачи

В реальной работе не всегда заранее понятно, что задача потянет за собой отдельную ветку. Часто всё начинается просто: увидел баг, открыл файл прямо в `master` и взялся исправлять, рассчитывая закрыть вопрос за пару минут.

Но по ходу работы может выясниться, что:

- задача на самом деле шире, чем казалось на первый взгляд;
- уже готов законченный, самостоятельный кусок работы, который хочется сохранить как отдельную единицу, а не смешивать с остальным;
- `master` в большинстве принятых на практике моделей ветвления — это «священная корова»: там должен лежать только стабильный, протестированный и готовый к выкладке код.

В этот момент разработчик оказывается в неудобном положении: в рабочей директории лежит реальный, нужный код, но закоммитить его в `master` нельзя — это нарушит правило чистой ветки. Переносить изменения вручную, копируя файлы туда-обратно, — не вариант: долго и легко что-то потерять.

## 2. Решение: создание ветки «на лету»

Ветку не обязательно создавать заранее, до начала работы. Git разрешает сделать это в любой момент — уже после того, как правки внесены:

```bash
git switch -c <название_ветки>
```

Флаг `-c` — сокращение от `--create`: создаёт новую ветку и сразу переключает на неё. Команда при этом заберёт с собой всё, что к этому моменту накопилось в рабочей директории: и то, что уже добавлено в индекс через `git add`, и то, что просто изменено в отслеживаемых файлах, и даже совсем новые, ещё не отслеживаемые Git файлы. Untracked-файлы при переключении не меняют статус — перед коммитом их так же нужно добавить в индекс обычным `git add`.

## 3. Механизм работы Git при переключении

При переключении на уже существующую ветку итог зависит от того, разошлась ли её история с текущей: если разницы нет — незакоммиченные изменения просто остаются в рабочей директории, если есть — Git либо блокирует переключение, либо просит явно разложить изменения через `stash`.

Создание ветки «на лету» убирает саму возможность расхождения. Новая ветка появляется ровно в той точке истории, где вы сейчас находитесь, — указывает на тот же самый коммит, что и `master`:

```
До:
master → C3   ← HEAD

После git switch -c fix:
master → C3
fix    → C3   ← HEAD
```

## 4. Итог операции

Посмотрим, как это выглядит на практике. Допустим, вы правите файл `config.py` прямо в `master`:

```bash
$ git status
On branch master
Changes not staged for commit:
  modified:   config.py

$ git switch -c fix
Switched to a new branch 'fix'

$ git status
On branch fix
Changes not staged for commit:
  modified:   config.py
```

Обратите внимание: сама команда `git switch -c fix` не сказала про `config.py` ни слова — только `Switched to a new branch 'fix'`. Она не печатает `M`, потому что вообще не запускает сверку файлов с новым HEAD: ветка создаётся от текущего коммита, сравнивать физически нечего.

Правка никуда не делась — просто теперь вы находитесь на ветке `fix`, и именно туда уйдёт следующий коммит:

```bash
$ git add config.py
$ git commit -m "fix: исправлена обработка таймаута соединения"
[fix a1b2c3d] fix: исправлена обработка таймаута соединения
 1 file changed, 4 insertions(+), 1 deletion(-)
```

Коммит теперь принадлежит `fix`. Возвращаемся на `master` и убеждаемся, что она осталась в исходном стабильном состоянии:

```bash
$ git switch master
Switched to branch 'master'

$ git status
On branch master
nothing to commit, working tree clean
```

Дальше можно спокойно продолжать работу в `fix` независимо от `master` — коммитить, дорабатывать и в итоге влить готовый результат обратно уже отдельным шагом.

Стоит помнить о границе этого приёма: он работает гладко только пока изменения не закоммичены. Если код уже ушёл коммитом не в ту ветку — это отдельная ситуация: коммит нужно переносить на нужную ветку, а этим приёмом такое не решить, нужны другие инструменты.
