Рабочая директория со временем обрастает лишним: недописанные правки, файлы сборки, эксперименты, которые не пригодились. Чтобы вернуть проект к состоянию последнего коммита, нужно закрыть две разные по природе задачи — отменить изменения в файлах, которые Git уже отслеживает, и отдельно избавиться от файлов, которые Git никогда не видел.

---

## 1. Сброс изменений в отслеживаемых файлах

Для файлов, которые уже находятся под контролем Git, изменения отменяются командой `git restore`.

Для одного файла:

```bash
git restore file.txt
```

Файл в рабочей директории возвращается к тому виду, что записан в индексе. Если нужно откатить и то, что уже застейджено, — чтобы файл целиком вернулся к состоянию последнего коммита, — команда запускается с двумя флагами сразу:

```bash
git restore --staged --worktree file.txt
```

Тот же приём работает и на весь проект: путь `.` означает «все файлы текущей директории и вложенных поддиректорий»:

```bash
git restore --staged --worktree .
```

Все отслеживаемые файлы одновременно возвращаются к состоянию HEAD — и в рабочей директории, и в индексе.

Для этой же задачи на практике чаще используют более короткую команду:

```bash
git reset --hard
```

Без указания коммита результат получается тем же самым. Разница раскрывается, если коммит всё же указать: `git reset --hard <коммит>` переключает на него HEAD и подтягивает под этот коммит и индекс, и рабочую директорию, тогда как `git restore` HEAD не трогает и просто копирует содержимое из указанного источника.

**Важный нюанс.** Обе команды видят только то, что уже попало в индекс. Обычный untracked-файл, который ни разу не побывал под `git add`, они не замечают и не удаляют. Но стоит его застейджить — и он тут же становится уязвим: `git reset --hard` (как и `git restore --staged --worktree`) без колебаний удалит с диска только что добавленный, но ещё не закоммиченный файл, потому что в HEAD такого файла нет, а «жёсткий ресет» приводит и индекс, и рабочую директорию к точному соответствию с HEAD.

## 2. Удаление untracked-файлов

Файлы, которые Git не отслеживает, `git restore` и `git reset --hard` не видят вовсе. Для их удаления есть отдельная команда — `git clean`.

Без дополнительных флагов она отказывается что-либо делать:

```bash
git clean
# fatal: clean.requireForce defaults to true and neither -i, -n, nor -f given; refusing to clean
```

Это не случайность, а защита: `git clean` удаляет файлы физически и безвозвратно — у untracked-файла никогда не было своего объекта в базе Git, и после удаления восстановить его штатными средствами Git нельзя. Поэтому первый флаг обязателен:

* `-f` (force) — подтверждает намерение и разрешает команде выполниться.

Сам по себе `-f` трогает только отдельные файлы, но не удаляет untracked-директории целиком:

* `-d` — добавляет удаление untracked-директорий вместе с их содержимым.

По умолчанию `git clean` также щадит всё, что перечислено в `.gitignore`, — результаты сборки, локальные конфиги и подобное:

* `-x` — снимает это исключение и удаляет в том числе игнорируемые файлы и директории.

Перед реальным удалением полезно посмотреть, что именно под него попадёт. Флаг `-n` (`--dry-run`) показывает список без единого удаления и, в отличие от обычного запуска, не требует `-f`:

```bash
git clean -fdx -n
```

## 3. Формула полной очистки проекта

Чтобы вернуть проект ровно к тому состоянию, что зафиксировано в последнем коммите, последовательно выполняются обе команды:

```bash
git reset --hard
git clean -fdx
```

Первая возвращает к состоянию HEAD всё, что Git уже отслеживает, — и незакоммиченные правки в рабочей директории, и то, что уже застейджено. Вторая убирает всё остальное — то, что Git никогда не отслеживал, включая игнорируемое. После этих двух команд рабочая директория становится точной копией дерева последнего коммита.

## 4. Практикум: закрепляем руками

Понадобится тестовый репозиторий с одним закоммиченным файлом `file.txt` (содержимое — `line1`). Веток и переключений между коммитами в этой теме нет — HEAD ни разу не сдвинется, поэтому вместо графа коммитов ориентир — `git status` и содержимое файлов.

### Шаг 1. `git restore` откатывает unstaged-правку

```bash
echo "line2" > file.txt
git status
cat file.txt
```

Статус покажет `file.txt` как изменённый, содержимое — `line2`.

```bash
git restore file.txt
git status
cat file.txt
```

Статус снова чистый, содержимое вернулось к `line1`. Индекс в этот момент совпадал с HEAD, поэтому откат дошёл до HEAD.

### Шаг 2. Staged-изменение `git restore` не трогает

```bash
echo "line2" > file.txt
git add file.txt
git status
```

Статус покажет изменение как `staged`. Пробуем откатить обычным `restore`:

```bash
git restore file.txt
git status
cat file.txt
```

Ничего не изменилось: статус и содержимое (`line2`) остались теми же. Восстанавливать было нечего — рабочая копия и так совпадает с индексом.

### Шаг 3. Unstaged поверх staged — restore откатывает только до индекса

```bash
echo "line3" >> file.txt
git status
cat file.txt
```

Статус покажет одновременно и staged-, и unstaged-изменение (`MM`), в файле — две строки: `line2` и `line3`.

```bash
git restore file.txt
git status
cat file.txt
```

Unstaged-часть (`line3`) пропала, но `line2` осталась — файл откатился до застейдженной версии, а не до HEAD.

### Шаг 4. Полный откат до HEAD: `--staged --worktree`

После шага 3 файл уже в нужном стартовом состоянии — `line2` застейджено, ничего сверху. Добавляем то же unstaged-изменение и на этот раз убираем staged-часть тоже:

```bash
echo "line3" >> file.txt
git status
git restore --staged --worktree file.txt
git status
cat file.txt
```

Статус чист, содержимое — снова `line1`. Дошли до HEAD.

### Шаг 5. `git reset --hard` даёт тот же результат

```bash
echo "line2" > file.txt
git add file.txt
git status
git reset --hard
git status
cat file.txt
```

Результат тот же, что и на шаге 4 через `git restore --staged --worktree` — файл на HEAD, статус чист.

### Шаг 6. `git clean` и untracked-файлы/директории

```bash
echo "temp" > temp.txt
mkdir build && echo "obj" > build/output.o
git status
git clean
```

Команда откажет и ничего не удалит — сработает защита `clean.requireForce`.

```bash
git clean -f
git status
ls
```

`temp.txt` исчез, а директория `build/` осталась — `-f` не трогает untracked-директории.

```bash
git clean -fd
git status
ls
```

Теперь пропала и директория `build/` целиком.
