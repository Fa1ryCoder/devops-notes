# Модель памяти процессов Linux

> Этот документ — справочный. Понятия отсюда используются в других темах:
> переменные окружения, управление процессами, контейнеры, производительность.

## Виртуальное адресное пространство

Когда ядро запускает процесс, оно выделяет ему **виртуальное адресное пространство** (virtual address space) — диапазон адресов памяти, которые процесс видит как «свою» память. Это не физическая RAM напрямую, а виртуальные адреса — числа-ссылки. Ядро (через аппаратный блок MMU) в нужный момент преобразует эти виртуальные адреса в реальные адреса физической RAM.

**Физические страницы — это и есть RAM**, просто разбитая на одинаковые блоки по 4КБ (страницы).

### Зачем нужна такая прослойка

MMU решает сразу три задачи:

- **Изоляция процессов** — каждый процесс считает, что у него вся память для себя. Процесс A не может напрямую прочитать память процесса B — их виртуальные адреса маппятся на разные физические страницы RAM. Если процесс падает — он портит только свою виртуальную память, а не чужую.
- **Защита памяти** — ядро помечает каждую страницу правами доступа: код программы (text-сегмент) помечается read-only, попытка записи туда вызывает ошибку. Это не даёт программе случайно или намеренно перезаписать собственный код или залезть в память ядра.
- **Многозадачность** — ядро может «заморозить» процесс, сохранить его состояние, переключиться на другой процесс, а потом вернуться обратно. Виртуальные адреса при этом не меняются — процесс не знает что его прерывали. Без MMU такое переключение было бы невозможным: у всех процессов были бы одни и те же физические адреса и они бы конфликтовали.

## Стек

### Стек vs стековый кадр

Здесь важно сразу разграничить два понятия которые часто путают:

**Стек (stack)** — это целый регион оперативной памяти, выделенный процессу. Это контейнер, хранилище. Он один на весь поток выполнения программы.

**Стековый кадр (stack frame)** — это один блок внутри стека, который создаётся для каждого конкретного вызова функции. Каждый раз когда вызывается функция — в стеке появляется новый кадр для неё. Когда функция завершается — её кадр удаляется.

Стек — это полка, стековый кадр — это одна коробка на этой полке.

Каждый стековый кадр хранит три вещи:
- аргументы переданные в функцию
- локальные переменные функции
- **адрес возврата** — указание куда вернуться в коде после того как функция завершится

Стек работает по принципу стопки тарелок: положить можно только сверху, взять — тоже только сверху. Последним пришёл — первым ушёл.

### Как работает стек: пошаговый пример

Программа: `main()` вызывает `sum()`, та складывает два числа и возвращает результат.

**Программа стартует — `main()` начинает работу.** Процессор создаёт в стеке первый стековый кадр для `main()`:

```
┌─────────────────────┐ ← вершина стека
│  стековый кадр      │
│  main()             │
│  x = ???            │  ← ждём результат от sum()
└─────────────────────┘
        ↑
      СТЕК (весь регион памяти)
```

**`main()` вызывает `sum(3, 5)`.** Прежде чем прыгнуть в `sum()`, процессор обязан запомнить куда потом вернуться. В стеке появляется новый стековый кадр для `sum()` поверх кадра `main()`:

```
┌─────────────────────┐ ← вершина стека (SP сдвинулся)
│  стековый кадр      │
│  sum()              │
│  a = 3              │  ← аргументы функции
│  b = 5              │
│  result = ???       │  ← локальная переменная
│  адрес возврата     │  ← «когда закончишь — вернись в main() на строку print(x)»
├─────────────────────┤
│  стековый кадр      │
│  main()             │
│  x = ???            │
└─────────────────────┘
        ↑
      СТЕК (содержит два кадра одновременно)
```

**`sum()` посчитала результат.** `result = 8`. Функция завершается: процессор читает адрес возврата, стековый кадр `sum()` удаляется из стека — эта память мгновенно освобождается — и выполнение прыгает обратно в `main()`:

```
┌─────────────────────┐ ← вершина стека (SP вернулся)
│  стековый кадр      │
│  main()             │
│  x = 8              │  ← результат получен
└─────────────────────┘
```

**`main()` завершилась** — её стековый кадр тоже удаляется. Стек снова пустой.

Именно поэтому нельзя удалить стековый кадр `main()` пока поверх него лежит кадр `sum()` — функции завершаются строго в обратном порядке относительно вызова.

### Адрес возврата

Ключевой элемент каждого стекового кадра. Без него процессор после выполнения `sum()` не знал бы куда идти дальше. Он записывается в кадр автоматически при каждом вызове — программист этим не управляет.

### Механизм управления стеком

Стек **управляется процессором автоматически**: есть специальный регистр `SP` (stack pointer) — указатель на вершину стека. При вызове функции `SP` сдвигается вверх (новый кадр появился), при возврате — вниз (кадр удалён). Программисту не нужно об этом думать.

## Куча

**Куча (heap)** — это регион памяти для данных, которые должны **жить дольше чем одна функция**. Стек для этого не подходит: данные на стеке уничтожаются как только функция возвращается. Куча — это «долгосрочное хранилище» процесса.

Программист явно запрашивает память из кучи (`malloc()` в C, `new` в C++/Java, создание объектов в Python/Go) и явно освобождает (или это делает сборщик мусора). Ядро не знает какие данные там нужны — это зона ответственности программы.

```
Пример: nginx получил HTTP-запрос
  → выделил в куче буфер для тела запроса (может быть 10КБ или 100МБ)
  → обработал запрос
  → освободил буфер
  → куча уменьшилась

На стеке это хранить нельзя: функция-обработчик вернётся и данные пропадут.
```

### Механизм управления кучей

У кучи механизм управления — **аллокатор памяти** (часть стандартной библиотеки). Это код, который решает где именно выделить блок под `malloc()`, как отслеживать свободные участки, как их возвращать при `free()`. Программист говорит «дай мне 100 байт» — аллокатор решает где именно.

## Как стек и куча сосуществуют в адресном пространстве

Стек и куча — это **регионы памяти**, а не механизмы. Механизмы — это то, *как* ими управляют (процессор для стека, аллокатор для кучи).

Они решают разные задачи:

- **Стек** — быстрый, автоматический, конечный по размеру (обычно 8МБ на поток). Для коротко живущих данных внутри функций.
- **Куча** — медленнее (нужно выделять/освобождать), может расти большой. Для данных которые живут дольше функции или размер которых неизвестен заранее.

Они растут навстречу друг другу внутри адресного пространства.

### Высокие и низкие адреса

Адрес — это просто число-номер байта в памяти. «Высокие адреса» — это большие числа (например `0xFFFF...`), «низкие» — маленькие (близкие к `0x0000...`). Это как нумерация этажей в здании: первый этаж = низкий адрес, последний этаж = высокий. Стек размещается в «верхней» части и растёт вниз (к меньшим номерам), куча — в «нижней» и растёт вверх.

```
Адресное пространство процесса:
─────────────────────────────────────────
Высокие адреса (большие числа, 0xFFFF...)
  ┌──────────────┐
  │    стек      │  ← регион памяти, управляется процессором (регистр SP)
  │  (растёт ↓)  │    для вызовов функций и локальных переменных
  ├──────────────┤
  │     ...      │  ← свободное пространство между ними
  ├──────────────┤
  │    куча      │  ← регион памяти, управляется аллокатором (malloc/free)
  │  (растёт ↑)  │    для долгоживущих данных
  ├──────────────┤
  │    данные    │  ← глобальные переменные программы
  ├──────────────┤
  │     код      │  ← машинный код программы (read-only)
  └──────────────┘
Низкие адреса (маленькие числа, 0x0000...)
```

**Итого: стек и куча — регионы памяти; процессор и аллокатор — механизмы управления ими.**
