## Введение — два разных мира переменных

Прежде чем разбирать конкретные механизмы, важно понять одно принципиальное разделение, которое в Ansible легко упустить в начале.

Все переменные в Ansible делятся на две категории по смыслу:

**Переменные инвентаря** отвечают на вопрос «что я знаю об этих хостах». Это данные об инфраструктуре — адреса, учётные данные, тип оборудования, идентификаторы. Они существуют независимо от того, какой плейбук запускается, и описывают саму среду, а не действия над ней.

**Переменные плейбука** отвечают на вопрос «с какими параметрами выполнять эту задачу». Это данные об автоматизации — имена пакетов, пути к файлам, версии, флаги поведения. Они принадлежат конкретному плейбуку и описывают логику работы, а не инфраструктуру.

Это разделение важно по двум причинам.

Первая — **архитектурная**. Инвентарь и плейбуки должны быть независимы друг от друга: один плейбук можно запускать на разных инвентарях, а один инвентарь использовать с разными плейбуками. Если в `host_vars` начинают появляться переменные, которые относятся к логике конкретного плейбука — это признак, что что-то пошло не туда.

Вторая — **техническая**. Ansible сливает все переменные из всех источников в единый контекст для каждого хоста. Одна и та же переменная, определённая одновременно в инвентаре и в плейбуке, не вызовет ошибки — Ansible просто выберет значение по приоритету, молча. Понимать это разделение нужно именно для того, чтобы предвидеть такое поведение и не удивляться неожиданным результатам.

## 1. Переменные инвентаря

Переменные инвентаря были подробно рассмотрены в теме 2. Здесь — краткое напоминание с акцентом на то, как они соотносятся с остальными видами переменных.

**`host_vars/<hostname>.yml`** — переменные конкретного хоста. Используются для данных, специфичных для одной машины: адрес подключения, тип оборудования, идентификатор магазина.

```yaml
# host_vars/kassa-01.yml
ansible_host: 192.168.1.101
register_type: pirit
store_id: 42
```

**`group_vars/<groupname>.yml`** — переменные группы хостов. Используются для данных, общих для всех машин в группе: параметры подключения, версия ПО, адрес сервера.

```yaml
# group_vars/cash_registers.yml
ansible_user: admin
ansible_ssh_pass: secret
app_version: "2.3.1"
```

## 2. Переменные плейбука — `vars` и `vars_files`

### 2.1 `vars` — переменные прямо в play

Объявляются внутри play в секции `vars`. Доступны всем tasks этого play.

```yaml
- name: Установка ТС ПИоТ
  hosts: pirit_registers
  vars:
    package_name: tsipiot
    config_path: /etc/tsipiot/esmmanager.ini
    required_version: "3.1.0"

  tasks:
    - name: Установить пакет
      ansible.builtin.apt:
        name: "{{ package_name }}"
        state: present
```

**Ограничение:** переменные из `vars` видны только внутри своего play. Если в плейбуке несколько play — переменные не передаются между ними.

---

### 2.2 `vars_files` — переменные из отдельного файла

Вместо того чтобы писать все переменные прямо в плейбук, их можно вынести в отдельный YAML-файл и подключить через `vars_files`.

Эта директория — не то же самое, что `group_vars` и `host_vars`, даже если лежит рядом с ними на верхнем уровне проекта. `group_vars` и `host_vars` — это переменные инвентаря, данные о хостах. Отдельная директория с `vars_files` — это переменные плейбука, данные о логике задачи (имена пакетов, пути, версии), которые не зависят от того, какой хост выполняет плейбук. Если переменных плейбука немного — секция `vars:` прямо в нём вполне достаточна, заводить отдельную директорию имеет смысл, когда переменных становится много или их нужно переиспользовать в нескольких плейбуках.

**Структура файла с переменными** — обычный YAML, просто пары ключ-значение без какого-либо заголовка:

Директория `vars/` — общепринятое соглашение, не зарезервированное слово. Ansible читает файл по тому пути, который указан в `vars_files`, и не проверяет название папки. Можно назвать её `config/`, `params/` или как угодно ещё.

```yaml
# vars/tsipiot.yml
package_name: tsipiot
config_path: /etc/tsipiot/esmmanager.ini
required_version: "3.1.0"
cert_dir: /etc/tsipiot/certs
service_name: tsipiot
```

**Подключение в плейбуке:**

```yaml
- name: Установка ТС ПИоТ
  hosts: pirit_registers
  vars_files:
    - vars/tsipiot.yml

  tasks:
    - name: Установить пакет
      ansible.builtin.apt:
        name: "{{ package_name }}"
        state: present
```

Можно подключить несколько файлов сразу — они загружаются по порядку:

```yaml
  vars_files:
    - vars/common.yml
    - vars/tsipiot.yml
```

**Путь к файлу** указывается относительно директории, где лежит плейбук.

**Практическая разница между `vars` и `vars_files`:**

| | `vars` | `vars_files` |
|---|---|---|
| Где хранятся | Прямо в плейбуке | В отдельном файле |
| Читаемость плейбука | Хуже при большом числе переменных | Плейбук остаётся чистым |
| Повторное использование | Только в этом плейбуке | Файл можно подключать к разным плейбукам |
| Приоритет | Одинаковый | Одинаковый |

По приоритету `vars` и `vars_files` равнозначны — оба относятся к уровню «переменные play».

## 3. Факты хоста — `ansible_facts`

### Что такое факты

При запуске плейбука Ansible автоматически выполняет task под названием `Gathering Facts` — если ты видел эту строку в выводе, это оно. В этот момент Ansible подключается к каждому хосту и собирает информацию о нём: операционная система, сетевые интерфейсы, объём памяти, процессор, дисковые разделы и многое другое.

Всё это складывается в словарь `ansible_facts` и становится доступным как переменные в плейбуке. Модуль `setup`, который это делает, встроен в Ansible — на целевом хосте ничего дополнительно устанавливать не нужно.

### Как посмотреть факты хоста

```bash
ansible kassa-01 -m ansible.builtin.setup
```

Вывод будет большим — несколько сотен строк JSON. Чтобы отфильтровать нужное:

```bash
# Только список сетевых интерфейсов
ansible kassa-01 -m ansible.builtin.setup -a "filter=ansible_interfaces"

# Только информация об ОС
ansible kassa-01 -m ansible.builtin.setup -a "filter=ansible_distribution*"

# Факты конкретного интерфейса
ansible kassa-01 -m ansible.builtin.setup -a "filter=ansible_lo"
```

> **Важно:** фильтр работает только по имени верхнего факта — вложенные ключи он не понимает. `filter=ansible_lo.ipv4` ничего не вернёт. Фильтр нужен только чтобы сократить вывод при ручном просмотре — выбирать конкретное поле нужно уже внутри плейбука.

### Обращение к вложенным данным

Факты имеют вложенную структуру — словари внутри словарей, списки внутри словарей. Доступ через точку для словарей, через `[индекс]` для списков:

```yaml
# Верхний уровень — просто имя факта
ansible_distribution          # "Ubuntu"

# Список имён интерфейсов
ansible_interfaces            # ["lo", "eth0"]

# Факт конкретного интерфейса — отдельный факт ansible_<имя>
ansible_lo.ipv4.address       # "127.0.0.1"

# Словарь внутри факта — через точку
ansible_default_ipv4.address  # "192.168.1.101"
```

В плейбуке:

```yaml
- name: Показать IP интерфейса lo
  ansible.builtin.debug:
    msg: "{{ ansible_lo.ipv4.address }}"
```

### Часто используемые факты

```
ansible_hostname               — имя хоста (без домена)
ansible_fqdn                   — полное доменное имя
ansible_distribution           — название ОС: "Ubuntu", "Debian", "CentOS"
ansible_distribution_version   — версия ОС: "22.04"
ansible_os_family              — семейство ОС: "Debian", "RedHat"
ansible_default_ipv4.address   — основной IP-адрес
ansible_memtotal_mb            — объём RAM в мегабайтах
ansible_processor_vcpus        — число процессорных ядер
ansible_architecture           — архитектура: "x86_64", "aarch64"
```

### Использование в плейбуке

К фактам можно обращаться двумя способами. Короткая форма — напрямую по имени:

```yaml
when: ansible_distribution == "Ubuntu"
```

Полная форма — через `ansible_facts['имя']`. Это современный стиль, защищает от конфликта имён с пользовательскими переменными:

```yaml
when: ansible_facts['distribution'] == "Ubuntu"
```

Обе формы работают. В примерах ниже используется полная форма.

Условная установка пакета в зависимости от ОС:

```yaml
- name: Установить пакет только на Ubuntu
  ansible.builtin.apt:
    name: tsipiot
    state: present
  when: ansible_facts['distribution'] == "Ubuntu"
```

Выбор конфигурации в зависимости от архитектуры:

```yaml
- name: Скопировать бинарник под нужную архитектуру
  ansible.builtin.copy:
    src: "files/tsipiot-{{ ansible_facts['architecture'] }}"
    dest: /usr/local/bin/tsipiot
```

### Отключение сбора фактов

Если факты не нужны — сбор можно отключить. Это ускоряет выполнение плейбука, особенно на большом числе хостов:

```yaml
- name: Быстрое обновление конфига
  hosts: all
  gather_facts: false

  tasks:
    - name: Скопировать конфиг
      ansible.builtin.copy:
        src: esmmanager.ini
        dest: /etc/tsipiot/esmmanager.ini
```

## 4. Переменные времени выполнения — `register` и `set_fact`

Переменные инвентаря и плейбука задаются до запуска — они статичны. Но часто нужно принять решение прямо во время выполнения, опираясь на то, что происходит на хосте.

Например: перед установкой пакета нужно проверить, какая версия уже стоит, и установить новую только если текущая устарела. Или: тип кассы заранее неизвестен, и путь к конфигу нужно собрать на лету из того, что вернула команда. Статическими переменными это не решить — нужны механизмы, которые работают в момент выполнения.

`register` и `set_fact` — это именно такие механизмы. Оба создают переменные в процессе прогона плейбука, но делают это по-разному и для разных целей.

### 4.1 `register` — сохранение результата task

Каждая task в Ansible возвращает объект с результатом своей работы: статус выполнения, вывод команды, изменённые данные. По умолчанию этот результат нигде не сохраняется. `register` позволяет поместить его в переменную.

```yaml
- name: Проверить версию установленного пакета
  ansible.builtin.command: dpkg -l tsipiot
  register: dpkg_result

- name: Показать результат
  ansible.builtin.debug:
    var: dpkg_result
```

Переменная `dpkg_result` — это словарь (dict). Его структура зависит от модуля, но общие поля есть у всех:

```
dpkg_result:
  rc: 0                    # код возврата (0 = успех)
  stdout: "..."            # стандартный вывод
  stderr: "..."            # вывод ошибок
  stdout_lines: [...]      # stdout построчно, в виде списка
  changed: true/false      # был ли изменён хост
  failed: true/false       # завершилась ли task с ошибкой
```

**Типичные применения:**

Проверить, что вернула команда, и использовать это в условии:

```yaml
- name: Получить содержимое crpt.ini
  ansible.builtin.command: cat /etc/crpt.ini
  register: crpt_ini_content
  ignore_errors: true

- name: Установить пакет только если crpt.ini содержит нужную строку
  ansible.builtin.apt:
    name: tsipiot-crpt
    state: present
  when: "'mode=prod' in crpt_ini_content.stdout"
```

Проверить статус сервиса и в зависимости от него принять решение:

```yaml
- name: Проверить статус сервиса
  ansible.builtin.systemd:
    name: tsipiot
  register: service_status

- name: Перезапустить только если сервис уже запущен
  ansible.builtin.systemd:
    name: tsipiot
    state: restarted
  when: service_status.status.ActiveState == "active"
```

**Важно:** переменная, созданная через `register`, существует только в рамках текущего play. Между play она не передаётся (в отличие от `set_fact`).

---

### 4.2 `set_fact` — создание переменной во время выполнения

`set_fact` — это отдельный модуль, который создаёт переменную с произвольным значением в момент выполнения. В отличие от `register`, ты сам определяешь, что в ней будет.

```yaml
- name: Вычислить путь к конфигу на основе типа кассы
  ansible.builtin.set_fact:
    config_path: "/etc/tsipiot/{{ register_type }}/esmmanager.ini"
```

После этой task переменная `config_path` доступна во всех последующих tasks.

**Ключевое отличие от `vars` и `vars_files`:** переменные из `vars` задаются до запуска плейбука и не могут зависеть от того, что происходит на хосте. `set_fact` выполняется в момент прогона и может использовать любые данные, которые уже получены — факты хоста, результаты команд через `register`, другие переменные.

**Типичные применения:**

Вычислить значение на основе факта хоста (`ansible_distribution` — это факт, собранный на этапе `Gathering Facts`):

```yaml
- name: Определить директорию для логов
  ansible.builtin.set_fact:
    log_dir: "{{ '/var/log/tsipiot' if ansible_distribution == 'Ubuntu' else '/opt/log/tsipiot' }}"
```

Упростить сложную структуру из `register`:

```yaml
- name: Получить версию пакета
  ansible.builtin.command: dpkg-query -W -f='${Version}' tsipiot
  register: pkg_version_raw

- name: Сохранить только строку с версией
  ansible.builtin.set_fact:
    tsipiot_version: "{{ pkg_version_raw.stdout }}"

# Теперь можно использовать tsipiot_version вместо pkg_version_raw.stdout везде
```

**`set_fact` сохраняется между play** (в отличие от `register`). Это делает его удобным инструментом для передачи данных от одного play к другому в рамках одного плейбука.

---

### 4.3 Сравнение `register` и `set_fact`

| | `register` | `set_fact` |
|---|---|---|
| Что сохраняет | Результат выполнения task (объект со множеством полей) | Произвольное значение, которое ты задаёшь сам |
| Как используется | Суффикс к любой task | Отдельная task с модулем `set_fact` |
| Живёт между play | Нет | Да |
| Когда применять | Нужно что-то сделать с выводом команды или статусом | Нужно вычислить значение или упростить структуру данных |

Практически они часто работают вместе: сначала `register` получает сырой результат, потом `set_fact` вытаскивает из него нужное поле и кладёт в читаемую переменную.

## 5. Магические переменные — `hostvars`, `groups`, `group_names`

Это встроенные переменные, которые Ansible предоставляет автоматически. Они не объявляются в инвентаре или плейбуке — они всегда доступны.

### 5.1 `hostvars` — заглянуть в соседний хост

### Зачем это нужно

По умолчанию, когда Ansible выполняет задачи на хосте `kassa-01`, он видит переменные только этого хоста. Переменные `kassa-02`, его факты и прочие данные — недоступны.

`hostvars` — это встроенный словарь, через который можно получить переменные **любого другого хоста**, который есть в инвентаре (и у которого уже собраны факты).

### Синтаксис

```yaml
hostvars['имя_хоста']['имя_переменной']

# или через точку:
hostvars['kassa-02'].ansible_default_ipv4.address
```

### Пример: получить IP другого хоста

Представь, что ты настраиваешь конфиг на `kassa-01`, и в этот конфиг нужно прописать IP-адрес сервера `ControlCenter`:

```yaml
- name: Сгенерировать конфиг с адресом сервера
  ansible.builtin.template:
    src: client.conf.j2
    dest: /etc/tsipiot/client.conf

# В шаблоне client.conf.j2:
# server_address = {{ hostvars['control-center-01'].ansible_default_ipv4.address }}
```

### Пример: прочитать переменную инвентаря другого хоста

```yaml
- name: Узнать store_id соседней кассы
  ansible.builtin.debug:
    msg: "store_id у kassa-02 = {{ hostvars['kassa-02']['store_id'] }}"
```

### Важный момент

`hostvars` содержит данные только о тех хостах, для которых уже выполнялся сбор фактов в текущем прогоне плейбука. Если хост есть в инвентаре, но в текущем play он не участвует и `gather_facts` для него не выполнялся — его данные в `hostvars` будут неполными (переменные инвентаря будут, факты — нет).

### Отличие от `ansible_facts`

| | `ansible_facts` | `hostvars` |
|---|---|---|
| Что содержит | Технические данные о **текущем** хосте (ОС, IP, память) | Переменные и факты **любого** хоста из инвентаря |
| Откуда берётся | Собирается автоматически при `gather_facts` | Формируется из инвентаря и собранных фактов |
| Типичное применение | Условия по ОС, архитектуре, железу | Передача данных между хостами в конфигах |

---

### 5.2 `groups` — списки хостов по группам

`groups` — это словарь, где ключи — имена групп из инвентаря, значения — списки хостов, входящих в каждую группу.

Типичное применение — динамическая генерация конфига, в который нужно вписать все хосты из группы. Например, на сервере мониторинга нужно перечислить IP-адреса всех касс:

```jinja2
{# Внутри шаблона для сервера мониторинга #}
{% for kassa in groups['cash_registers'] %}
Касса: {{ kassa }} -> IP: {{ hostvars[kassa].ansible_default_ipv4.address }}
{% endfor %}
```

`groups['all']` содержит все хосты инвентаря без исключения.

---

### 5.3 `group_names` — в каких группах находится текущий хост

`group_names` — это список имён групп, в которые входит **текущий** хост, на котором выполняется task. Удобен для разделения логики внутри одного плейбука, когда он запускается на хостах из разных групп.

```yaml
- name: Отправить расширенные тестовые логи
  ansible.builtin.command: /opt/bin/send_debug_report
  when: "'test_cashnodes' in group_names"  # Выполнится только на хостах из тестовой группы
```

## 6. Приоритет переменных

Когда одна и та же переменная определена в нескольких местах, Ansible выбирает значение по приоритету. Технически уровней 22, но на практике достаточно понимать 4 логические группы — от самого слабого к самому сильному.

**Группа 1 — Умолчания** (легко перебить):

- `role defaults` — дефолтные переменные внутри ролей, самый слабый приоритет в Ansible
- `group_vars/all` — глобальные умолчания для всего инвентаря

**Группа 2 — Контекст инфраструктуры** (инвентарь):

- `group_vars/<groupname>` — переменные группы хостов
- `host_vars/<hostname>` — переменные конкретного хоста, всегда перекрывают группу

**Группа 3 — Логика автоматизации** (код):

- `vars` и `vars_files` в play — код плейбука важнее настроек инвентаря
- `role vars` — переменные, жёстко зашитые внутри роли
- `set_fact` / `register` — динамический рантайм, перебивает любую статику

**Группа 4 — Ядерный удар**:

- `-e` при запуске — не может быть перебито ничем в коде плейбука

```bash
# Переопределить любую переменную «на лету»
ansible-playbook tsipiot_pirit.yml -e "required_version=3.2.0"
```

### Практические следствия

**`host_vars` перекрывает `group_vars`.** Если в `group_vars/cash_registers.yml` стоит `app_version: "2.3.1"`, а в `host_vars/kassa-01.yml` стоит `app_version: "2.2.0"` — для `kassa-01` победит `2.2.0`.

**`vars` в play перекрывает инвентарь.** Переменные плейбука важнее, чем данные инвентаря. Это позволяет плейбуку задавать значения, не зависящие от того, что написано в `host_vars`.

**`set_fact` перекрывает `vars`.** Переменная, вычисленная во время выполнения, перекрывает статически заданную в плейбуке. Это мощно, но может приводить к неочевидному поведению — если где-то в плейбуке есть `set_fact` для переменной, ожидай, что её значение может измениться в процессе.

### Типичная ошибка

Переменная задана в `group_vars`, но плейбук использует не то значение. Причина почти всегда в том, что та же переменная определена с другим значением в `host_vars` или прямо в `vars`. Чтобы найти, откуда берётся значение:

```bash
ansible-playbook myplaybook.yml -v
```

Или отдельной task прямо в плейбуке:

```yaml
- name: Откуда взялась переменная?
  ansible.builtin.debug:
    var: app_version
```

## Итоговая карта переменных

```
СТАТИКА (ДО ЗАПУСКА)                      ДИНАМИКА (В ПРОЦЕССЕ ВЫПОЛНЕНИЯ)
──────────────────────────────────        ──────────────────────────────────
role defaults         — супердефолт       ansible_facts  — данные об ОС и железе текущего хоста
group_vars/all        — умолчания         hostvars       — данные любого хоста из инвентаря
group_vars/<group>    — для группы        groups         — списки всех хостов по группам
host_vars/<host>      — для хоста         group_names    — в каких группах находится текущий хост
vars / vars_files     — внутри play       register       — перехваченный результат работы task
role vars             — внутри роли       set_fact       — вычисленная на лету переменная
-e                    — из консоли/CI
```
