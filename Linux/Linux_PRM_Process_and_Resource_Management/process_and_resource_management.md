## 1. Mental model

**Главный принцип Linux:** программа не может напрямую обратиться к железу или любому системному ресурсу — диску, сети, памяти, другим процессам. Единственный способ — попросить ядро через **системный вызов (syscall)**. `open()`, `read()`, `write()`, `socket()`, `fork()` — всё это системные вызовы, то есть обращения программы к ядру. Ядро проверяет права, выполняет операцию и возвращает результат.

Это намеренная изоляция: программа живёт в **user space** и не имеет прямого доступа к железу. Если бы программа могла напрямую писать в диск — один баг в приложении мог бы уронить всю систему или получить доступ к чужим данным. Именно поэтому strace так полезен — он показывает все системные вызовы процесса, то есть буквально всё что процесс просит у ядра.

Всё что происходит на Linux-сервере — это три слоя:

```
┌──────────────────────────────────────────────────────┐
│  ПРИЛОЖЕНИЯ                                          │
│  nginx, postgres, python app, redis, ...             │
│  Каждое — один или несколько процессов               │
├──────────────────────────────────────────────────────┤
│  SYSTEMD (PID 1)                                     │
│  Менеджер жизненного цикла сервисов                  │
│  Запускает, перезапускает, логирует, изолирует       │
├──────────────────────────────────────────────────────┤
│  ЯДРО LINUX                                          │
│  Планировщик CPU · fd и сокеты · cgroups             │
│  Сигналы · Виртуальная память · Сеть                 │
└──────────────────────────────────────────────────────┘
```

Четыре абстракции которые нужно понимать насквозь:

| Абстракция | Одна фраза | Почему важно |
|-----------|-----------|-------------|
| **Процесс** | Контейнер ресурсов с PID, памятью, fd и cgroup | Единица изоляции и управления |
| **fd (файловый дескриптор)** | Число — ссылка на любой открытый ресурс ОС | Файлы, сокеты, пайпы — всё одна абстракция |
| **Сигнал** | Асинхронное уведомление процессу от ядра или другого процесса | Единственный стандартный способ управлять процессом извне |
| **cgroup** | Группа процессов с общими лимитами ресурсов | Основа изоляции Docker, Kubernetes, systemd |

Ключевые связи:

```
Процесс
  ├── открывает fd  →  файлы, TCP-сокеты, unix-сокеты, пайпы (всё одно)
  ├── принадлежит cgroup  →  ядро ограничивает CPU / RAM / I/O
  ├── имеет ulimits  →  ядро ограничивает количество fd, процессов
  ├── живёт в namespaces  →  видит только свою часть: PID, сеть, файловую систему
  └── управляется systemd  →  unit файл, journald, автоперезапуск
```

## 2. Процессы

### Что такое процесс

Процесс — это не просто «запущенная программа». Точнее: это **изолированный контейнер ресурсов** который ядро создаёт когда вы запускаете программу. Ядро выделяет процессу:

- **PID** — уникальный числовой идентификатор (Process ID)
- **Виртуальное адресное пространство памяти** — процесс видит свою память и не может напрямую читать память другого процесса
- **Таблицу файловых дескрипторов** — список всего что процесс открыл
- **Учётные данные** — от имени какого UID/GID он работает
- **cgroup** — к какой группе ограничений принадлежит

Каждый процесс кроме первого имеет **родителя (PPID)**. Это дерево. PID 1 — всегда `systemd`, он запускает всё остальное. Если PID 1 умирает — ядро паникует и система падает.

> **Как процесс получает свой код:** новый процесс не появляется из ничего — он создаётся через `fork()` (ядро клонирует текущий процесс целиком: код, fd, окружение), а затем почти всегда сразу заменяет свой код через `exec()`/`execve()` (ядро загружает в это же PID совсем другую программу). Почему это два разных шага, а не один, и что именно происходит с памятью при `execve()` — подробно разобрано в `env_variable.md` (раздел «Наследование окружения») на примере того, как bash запускает nginx и почему systemd-сервис не видит переменные из `~/.bashrc`.

```bash
# посмотреть дерево процессов с PID
pstree -p

# посмотреть все процессы со статусами
ps -eo pid,ppid,stat,ni,user,cmd --sort=ppid

# посмотреть всё что ядро знает о конкретном процессе
# /proc/<PID>/ — это не папка на диске, это виртуальная ФС
# ядро генерирует её содержимое на лету при каждом чтении
ls /proc/$(pgrep -o nginx)/
```

### Атрибуты процесса и где их смотреть

У процесса есть два источника информации — они показывают разное:

```
ps aux                         /proc/<PID>/
──────────────────             ──────────────────────────────────
USER  PID  %CPU  %MEM          /status   → PID, PPID, UID, состояние
VSZ   RSS  TTY   STAT          /limits   → ulimits (nofile, nproc...)
START TIME  COMMAND            /fd/      → открытые файлы и сокеты
                               /cgroup   → к какому сервису/контейнеру
                               /cmdline  → точная команда запуска
                               /environ  → переменные окружения
                               /wchan    → в каком вызове ядра завис
                               /oom_score → приоритет для OOM Killer
                               /sched    → vruntime, вес CFS

ps aux показывает только часть.
Остальное — только через /proc/<PID>/
```

#### 🟢 Часто — при деплое, первичной диагностике

| Атрибут | Где смотреть | Когда нужно |
|---------|-------------|-------------|
| PID, PPID, UID | `cat /proc/<PID>/status` | Убить процесс, найти родителя, проверить от какого пользователя запущен |
| Состояние | `ps aux` колонка STAT или `cat /proc/<PID>/status \| grep State` | Процесс завис — посмотреть R/S/D/Z |
| Cgroup | `cat /proc/<PID>/cgroup` | Найти какому контейнеру/сервису принадлежит процесс |
| Открытые fd | `ls -la /proc/<PID>/fd/` | Утечка соединений, что держит файл |
| Ulimits | `cat /proc/<PID>/limits` | Сервис сыпет «Too many open files» |
| Команда запуска (cmdline) | `cat /proc/<PID>/cmdline \| tr '\0' ' '` | Проверить с какими флагами запущен процесс |
| Переменные окружения (environ) | `cat /proc/<PID>/environ \| tr '\0' '\n'` | Проверить подтянулись ли нужные env переменные |

#### 🟡 При авариях — процесс завис, память кончается

| Атрибут | Где смотреть | Когда нужно |
|---------|-------------|-------------|
| В каком kernel call завис (wchan) | `cat /proc/<PID>/wchan` | Состояние D уже видно в `ps` — wchan следующий шаг: понять **где именно** застрял (диск, NFS, сеть) чтобы знать что чинить |
| OOM приоритет | `cat /proc/<PID>/oom_score` | Настроить чтобы ядро не убивало БД первой при нехватке памяти |

#### 🔴 Тюнинг производительности — редко, но метко

| Атрибут | Где смотреть | Когда нужно |
|---------|-------------|-------------|
| Приоритет nice | `ps aux` колонка NI или `ps -o ni` | Снизить приоритет фонового процесса при конкуренции за CPU |
| vruntime / вес CFS | `cat /proc/<PID>/sched` | CPU throttling в K8s, тюнинг планировщика на нагруженных хостах |

**Про cmdline и environ подробнее:**

```bash
# cmdline — с какими аргументами запущен процесс
# \0 это разделитель между аргументами в /proc, tr заменяет на пробел
cat /proc/<PID>/cmdline | tr '\0' ' '
# java -Xmx4g -jar /opt/app/app.jar --port 8080
#      ↑ видно реальный размер heap, не тот что в конфиге

# практический кейс: после деплоя приложение падает с OOM
# смотришь cmdline и видишь что запустилось с -Xmx512m вместо -Xmx4g
# значит переменная окружения JAVA_OPTS не прокинулась

# environ — переменные окружения процесса
cat /proc/<PID>/environ | tr '\0' '\n'
# DATABASE_URL=postgresql://prod-db:5432/app
# SECRET_KEY=...
# JAVA_OPTS=-Xmx512m   ← вот виновник

# найти конкретную переменную
cat /proc/<PID>/environ | tr '\0' '\n' | grep DATABASE_URL

# практический кейс: приложение в K8s падает с ошибкой подключения к БД
# смотришь environ и видишь что DATABASE_URL указывает на staging а не prod
# Secret не прокинули или прокинули не тот
```


### Состояния процессов

Ядро в каждый момент знает в каком состоянии находится каждый процесс. Это не абстракция — это реальный флаг в структуре `task_struct` внутри ядра.

| Символ | Название | Что происходит |
|--------|----------|----------------|
| `R` | Running / Runnable | Выполняется прямо сейчас или стоит в очереди планировщика |
| `S` | Sleeping (interruptible) | Ждёт события (таймер, I/O, сигнал). Можно разбудить сигналом |
| `D` | Disk Sleep (uninterruptible) | Ждёт завершения I/O операции. **Нельзя прервать никаким сигналом, включая SIGKILL** |
| `Z` | Zombie | Процесс завершил работу, но запись о нём ещё не убрана из таблицы процессов |
| `T` | Stopped | Заморожен сигналом SIGSTOP |
| `I` | Idle | Бездействующий поток ядра (с версии 4.14+) |

Дополнительные флаги в колонке STAT:

| Флаг | Значение |
|------|---------|
| `s` | Session leader — процесс является лидером сессии (например `bash`) |
| `l` | Многопоточный процесс |
| `+` | Процесс на переднем плане (foreground) |
| `<` | Высокий приоритет (nice < 0) |
| `N` | Низкий приоритет (nice > 0) |

```bash
# найти зомби
ps aux | awk '$8 == "Z"'

# найти процессы в состоянии D — признак I/O проблем
ps aux | awk '$8 ~ /^D/'

# посмотреть состояние конкретного процесса
cat /proc/$(pgrep -o nginx)/status | grep -E "State|Pid|PPid"
```

### Состояние Z — Zombie подробно

Когда процесс завершается (вызывает `exit()`), он не исчезает мгновенно. Ядро переводит его в состояние Zombie и оставляет минимальную запись в таблице процессов — код завершения и статистику. Это сделано намеренно: **родитель должен забрать результат** через системный вызов `wait()`.

Зачем это нужно — контракт Unix: родитель запустил дочерний процесс с задачей и должен узнать **как** тот завершился. Успешно (код 0)? С ошибкой (код 1, 2...)? Убит сигналом? На основе этого родитель решает что делать дальше — повторить задачу, залогировать ошибку, запустить следующий шаг. Ядро не может выбросить запись пока родитель не заберёт — вдруг он ещё спросит. Вот почему зомби и висит.

Механизм такой:
1. Дочерний процесс вызывает `exit(1)` — сигнализирует что завершился с кодом 1
2. Ядро переводит его в Zombie, сохраняет код завершения
3. Ядро отправляет родителю сигнал SIGCHLD — «твой ребёнок умер»
4. Родитель вызывает `wait()` — считывает код завершения (`wait()` — системный вызов который говорит ядру «я готов принять результат дочернего процесса»)
5. Ядро окончательно убирает запись — зомби исчезает

```
  РОДИТЕЛЬ (PID 100)                          ДОЧЕРНИЙ (PID 101)
  ──────────────────                          ──────────────────
  fork() → запустил дочерний                 ... работает ...
  ... делает своё ...                         exit(1)
                                                   │
                              ┌────────────────────┘
                              │  Ядро: сохраняет код завершения
                              │        переводит в состояние Z
                              │        PID 101 остаётся в таблице
                              │
                              │  SIGCHLD ──────────────────────→ родитель получает сигнал
                              │                                   «твой ребёнок завершился»
                              │
  wait() ←────────────────────┘
  считывает код = 1
       │
       └─→ Ядро: убирает запись PID 101 из таблицы
                 PID освобождается
                 зомби исчезает ✓
```

Если родитель **не вызывает `wait()`**:

```
  РОДИТЕЛЬ (PID 100)                          ДОЧЕРНИЙ (PID 101)
  ──────────────────                          ──────────────────
  ... не обрабатывает SIGCHLD ...             exit(1)
                                                   │
                              ┌────────────────────┘
                              │  Ядро: запись в таблице процессов остаётся
                              │        PID 101 занят — его нельзя переиспользовать
                              │        состояние: Z (zombie)
                              │
  ... продолжает работать ...  ←── SIGCHLD проигнорирован или не обработан
  ... порождает ещё дочерних ...
                                   exit() → Z (PID 102)
                                   exit() → Z (PID 103)
                                   exit() → Z (PID 104)
                                   ...
                              таблица процессов заполняется зомби
                              fork() → EAGAIN  ← новые процессы создать нельзя
```

Если родитель **не вызывает `wait()`** — зомби копятся. Каждый зомби не потребляет CPU и память, но занимает PID и строку в таблице процессов. Когда таблица переполняется — создать новые процессы невозможно, система перестаёт работать. Это всегда баг в родительском процессе.

#### Максимальное количество записей в таблице процессов

Ядро ограничивает максимальный PID параметром `pid_max`. Это одновременно и максимальное количество одновременно существующих процессов в системе (включая зомби).

```bash
# посмотреть текущий лимит
cat /proc/sys/kernel/pid_max
# 32768    ← дефолт на 32-битных и старых системах
# 4194304  ← дефолт на 64-битных системах (Linux 3.3+)
```

Как работает:
- PID выдаются циклически от 1 до `pid_max`
- Каждый зомби держит занятым один PID
- При достижении `pid_max` ядро пытается переиспользовать освободившиеся PID
- Если **все** PID до `pid_max` заняты (живые процессы + зомби) — `fork()` возвращает ошибку `EAGAIN`, создать новый процесс невозможно
- Типичный симптом: `bash: fork: retry: Resource temporarily unavailable`

```bash
# посмотреть сколько процессов сейчас в системе
ps aux | wc -l

# сколько зомби
ps aux | awk '$8 == "Z"' | wc -l

# изменить лимит (временно, до перезагрузки)
echo 65536 > /proc/sys/kernel/pid_max

# постоянно — через sysctl
echo "kernel.pid_max = 65536" >> /etc/sysctl.conf
sysctl -p
```

> ⚠️ Увеличение `pid_max` — это **обходной путь**, не решение. Правильный путь — найти и починить родительский процесс который не вызывает `wait()`. Увеличение лимита только отсрочит проблему.

```bash
# убить зомби нельзя — он уже мёртв
# нужно убить родителя — тогда зомби усыновит systemd и вызовет wait()
# почему это помогает: systemd (PID 1) всегда корректно вызывает wait() для
# всех усыновлённых процессов, поэтому зомби немедленно исчезают
kill -9 $(ps -o ppid= -p <zombie_pid>)

# проверить сколько зомби в системе
ps aux | awk '$8 == "Z"' | wc -l
```

### Процесс-сирота (Orphan)

**Процесс-сирота** — это живой процесс у которого умер родитель. В отличие от зомби (мёртвый процесс ждущий `wait()`), сирота — это **полноценно работающий процесс**, просто оставшийся без родителя.

**Что происходит когда родитель умирает:**
Ядро автоматически переназначает всех осиротевших дочерних процессов новому родителю. В современном Linux (с systemd) новым родителем становится **systemd (PID 1)**. Это называется «усыновление» (reparenting).

```
  ДО — родитель жив:

  systemd (PID 1)
  └── bash (PID 100)
      ├── worker-1 (PID 101)   PPID = 100
      ├── worker-2 (PID 102)   PPID = 100
      └── worker-3 (PID 103)   PPID = 100
```

```
  ПОСЛЕ — родитель умер, ядро усыновляет:

  systemd (PID 1)
  ├── bash (PID 100)   → умер
  ├── worker-1 (PID 101)   PPID = 1  ← усыновлён systemd
  ├── worker-2 (PID 102)   PPID = 1  ← усыновлён systemd
  └── worker-3 (PID 103)   PPID = 1  ← усыновлён systemd
```

```bash
# увидеть усыновление в действии
ps -o pid,ppid,stat,cmd

# до смерти родителя:
# PID   PPID  STAT  CMD
# 100   1     S     bash
# 101   100   S     worker

# после смерти родителя (PID 100):
# PID   PPID  STAT  CMD
# 101   1     S     worker   ← PPID стал 1 (systemd)
```

**Чем отличается от зомби — классический вопрос на собесе:**

| | Зомби | Сирота |
|-|-------|--------|
| Живой? | Нет — уже завершился | Да — полноценно работает |
| Проблема | Занимает PID, не убивается | Никакой — ядро усыновляет |
| Родитель | Жив, но игнорирует `wait()` | Умер |
| Решение | Убить родителя | Ядро решает само |
| Опасен? | Да — при тысячах зомби | Нет |

#### 🛑 Исторический контекст: демонизация через Double Fork

До systemd не было удобного способа запустить фоновый сервис. Приложения сами реализовывали демонизацию — намеренно делали себя сиротой чтобы отвязаться от терминала.

**Почему именно двойной fork (Double Fork):**

Одного `fork()` недостаточно. После первого fork дочерний процесс становится сиротой и уходит под PID 1, но он всё ещё принадлежит той же **сессии терминала**. Это значит что при закрытии SSH-сессии ядро отправит SIGHUP всей группе — и сирота тоже умрёт.

Второй fork решает это: между форками вызывается `setsid()` (системный вызов «я больше не принадлежу ни одному терминалу» — создаёт новую сессию без управляющего TTY) — процесс полностью теряет связь с терминалом. После этого SIGHUP его не достанет.

```
fork() #1  →  родитель умирает, дочерний становится сиротой (PPID=1)
setsid()   →  дочерний создаёт новую сессию, отвязывается от TTY
              (системный вызов: «я больше не принадлежу ни одному терминалу»)
fork() #2  →  ещё один форк чтобы процесс не мог случайно стать лидером сессии
              итоговый процесс: PPID=1, нет TTY, нет сессии терминала = настоящий демон
```

**Как это делается сейчас:**

Этот паттерн считается устаревшим. Приложение пишется так чтобы работало в **foreground** — отдаёт логи в stdout/stderr, не уходит в фон самостоятельно. Systemd сам переводит его в фон, изолирует в cgroup и управляет жизненным циклом.

**Type=forking — когда встречается старый софт:**

Если запускаете legacy-приложение которое по старой привычке делает Double Fork, нужно указать `Type=forking` в unit файле — иначе systemd решит что основной процесс завершился (родитель умер после первого fork) и убьёт всю cgroup:

```ini
[Service]
Type=simple    # современный софт — работает в foreground, systemd следит за ним
Type=forking   # старый софт — сам уходит в фон, systemd ждёт пока осядет дочерний
Type=notify    # современный вариант — процесс сам сообщает systemd что готов
```

**Почему в Docker приложения запускаются строго в foreground:**

Если засунуть в контейнер скрипт который делает демонизацию (уходит в фон через Double Fork), контейнер мгновенно завершится с `Exited 0`. Причина: PID 1 внутри контейнера — это сам процесс приложения. Как только он завершается (даже если породил дочерний) — Docker видит что PID 1 умер и останавливает контейнер.

```bash
# поэтому nginx в контейнере запускают так:
CMD ["nginx", "-g", "daemon off;"]
# daemon off — запрещает nginx делать fork и уходить в фон
# nginx работает в foreground → PID 1 жив → контейнер работает
```

### Состояние D — Uninterruptible Sleep

Когда процесс инициирует операцию I/O (например читает с диска), ядро переводит его в состояние D. В этом состоянии процесс держит **блокировку ядра** — специальную структуру которая говорит «я сейчас работаю с этим ресурсом, никто другой не трогай». Именно поэтому SIGKILL не работает: ядро не может убить процесс пока тот держит блокировку — это привело бы к повреждению данных.

Короткое время в D — это нормально. Проблема когда процессов в D много или они зависают надолго. Типичные причины:

- Зависший NFS mount — процесс ждёт ответа от сетевой ФС которая не отвечает
- Умирающий жёсткий диск — I/O запросы уходят в никуда
- Переполненная очередь I/O — диск не успевает обработать запросы

```bash
# в каком kernel call завис процесс
cat /proc/<PID>/wchan
# примеры: nfs4_wait_on_commit, jbd2_log_wait_commit, pipe_wait

# ошибки диска или NFS в системном журнале
dmesg | tail -30
journalctl -k --since "10 min ago"

# здоровье диска
smartctl -a /dev/sda
```


### CPU планировщик — CFS

#### Как на самом деле работает многозадачность

Прежде чем разбирать CFS — важно понять что происходит на уровне железа.

**На одном ядре CPU в каждый момент времени выполняется только один процесс.** Ощущение что всё работает одновременно — иллюзия. CFS быстро переключает процессы, давая каждому квант времени (~1-10 миллисекунд). Это называется **вытесняющая многозадачность**:

```
Одно ядро CPU:
──────────────────────────────────────────→ время
[nginx][postgres][bash][nginx][postgres][bash]...
  1мс     1мс     1мс    1мс     1мс     1мс

Переключения происходят сотни раз в секунду — мы не замечаем.
```

**Настоящий параллелизм** — только на нескольких ядрах. На каждом ядре свой планировщик:

```
Ядро №1: [nginx   ][nginx   ][nginx   ]...
Ядро №2: [postgres][postgres][postgres]...
Ядро №3: [bash    ][python  ][bash    ]...
Ядро №4: [java    ][java    ][java    ]...
```

**Физические ядра vs логические CPU (Hyper-Threading):**

```bash
lscpu | grep -E "CPU\(s\)|Core|Thread"
# CPU(s):            16   ← логических CPU
# Core(s) per socket: 10  ← физических ядер
# Thread(s) per core:  2  ← Hyper-Threading
#
# 10 физических ядер × 2 потока = 16 логических CPU
```

Intel Hyper-Threading — каждое физическое ядро притворяется двумя. Внутри одного ядра два потока делят вычислительные блоки и переключаются когда один ждёт данных из памяти. Прирост ~20-30%, но не полноценные 16 независимых ядер:

```
Физическое ядро №1:
  Логический CPU 0  [процесс A] ←─┐ делят одно
  Логический CPU 1  [процесс B] ←─┘ физическое ядро

Реально параллельно = 10 процессов (по числу физических ядер)
Логических CPU = 16 (помогают когда потоки ждут данных из памяти)
```

#### Что такое CFS и как его «посмотреть»

**CFS (Completely Fair Scheduler)** — это **механизм внутри ядра Linux**, а не отдельный процесс или сервис. Его нельзя найти через `ps`, нет сервиса `cfs.service`, нет бинарника. CFS — это код который выполняется внутри ядра каждый раз когда нужно решить: «какой процесс запустить следующим на этом CPU-ядре?».

Увидеть работу CFS можно косвенно — через метрики которые он ведёт:

```bash
# детальная информация планировщика о конкретном процессе (включая vruntime)
cat /proc/<PID>/sched
# se.vruntime          :   4832167.123456  ← виртуальное время
# se.sum_exec_runtime  :    987654.321000  ← реальное время на CPU
# se.load.weight       :          1024     ← вес (определяется nice)

# краткая статистика: время на CPU / время в ожидании / кол-во запусков
cat /proc/<PID>/schedstat
# 1234567890  987654321  42

# посмотреть приоритеты всех процессов
top   # колонки: NI = nice, PR = реальный приоритет планировщика

# контекстные переключения в vmstat — признак активной работы CFS
vmstat 1 3
# cs (context switches) — сколько раз планировщик переключал процессы
```

#### Как CFS принимает решения — vruntime

CFS отслеживает `vruntime` (virtual runtime — виртуальное время выполнения) для каждого процесса. Это **учётный счётчик**: сколько «нормализованного» времени CPU уже потратил этот процесс.

#### Можно ли посмотреть vruntime?

Да, `vruntime` можно увидеть напрямую — в отличие от самого CFS, это просто число которое ядро хранит для каждого процесса и выдаёт через `/proc`:

```bash
# /proc/<PID>/sched — детальная информация планировщика о процессе
cat /proc/$(pgrep -o nginx)/sched

# пример вывода (выборочно):
# nginx (1234, #threads: 1)
# -------------------------------------------------------------------
# se.vruntime                          :      4832167.123456   ← вот он
# se.sum_exec_runtime                  :       987654.321000   ← реальное время на CPU (мс)
# se.nr_involuntary_switches           :            12345      ← вытеснен планировщиком
# se.nr_voluntary_switches             :            67890      ← сам отдал CPU (ждал I/O)
# se.load.weight                       :             1024      ← вес (nice 0 = 1024)
```

Что означают ключевые поля:

| Поле | Что показывает |
|------|---------------|
| `se.vruntime` | Виртуальное время — чем больше, тем «дальше» процесс от следующего запуска |
| `se.sum_exec_runtime` | Сколько реального времени CPU потратил процесс за всё время жизни (наносекунды) |
| `se.nr_voluntary_switches` | Сколько раз процесс **сам** отдал CPU (уснул в ожидании I/O, сигнала) |
| `se.nr_involuntary_switches` | Сколько раз CFS **принудительно** вытеснил процесс (истёк квант времени) |
| `se.load.weight` | Вес процесса — зависит от nice, влияет на скорость роста vruntime |

```bash
# сравнить vruntime у двух конкурирующих процессов
# тот у кого меньше — получит CPU следующим
cat /proc/$(pgrep -o worker1)/sched | grep "se.vruntime"
cat /proc/$(pgrep -o worker2)/sched | grep "se.vruntime"

# посмотреть у всех процессов сразу
for pid in $(ps -eo pid --no-headers); do
  vrt=$(cat /proc/$pid/sched 2>/dev/null | grep "se.vruntime" | awk '{print $3}')
  cmd=$(cat /proc/$pid/comm 2>/dev/null)
  echo "$vrt $pid $cmd"
done | sort -n | head -10
# процессы с наименьшим vruntime — следующие кандидаты на CPU
```

> **Важно:** абсолютное значение `vruntime` само по себе мало что говорит — оно монотонно растёт с момента запуска процесса. Смысл имеет только **разница** между процессами: кто «отстал» (меньший vruntime) — тот получит CPU следующим. Сравнивать имеет смысл только процессы которые конкурируют за одно CPU-ядро.

Механизм выбора:
1. У каждого процесса есть `vruntime` — монотонно растущее число
2. CFS хранит все «готовые к выполнению» процессы в структуре red-black tree, отсортированной по `vruntime`
3. Всегда запускается процесс с **наименьшим** `vruntime` — тот кто меньше всего работал
4. После кванта времени `vruntime` процесса увеличивается и он уходит обратно в дерево

```
Дерево процессов (сортировка по vruntime):

  vruntime:  100    150    200    250    300
             [A]    [C]    [B]    [D]    [E]
              ↑
         CFS выбирает этот — он работал меньше всех

  → A получает квант CPU, его vruntime становится 160
  → A возвращается в дерево

  vruntime:  150    160    200    250    300
             [C]    [A]    [B]    [D]    [E]
              ↑
         Теперь следующим идёт C
```

`vruntime` нормализуется по весу процесса: у процесса с `nice -20` (высокий вес) `vruntime` растёт медленнее — поэтому он чаще оказывается «наименее запущенным» и получает больше CPU.

#### nice — мягкий приоритет через вес

**nice** влияет на **вес процесса** в CFS, а не на жёсткий лимит. Чем ниже nice — тем больший вес, тем медленнее растёт `vruntime`, тем чаще процесс выбирается планировщиком:

```
nice -20  →  вес ~88761  (≈ в 10 раз больше CPU чем у nice 0)
nice   0  →  вес   1024  (дефолт)
nice +19  →  вес     15  (получает минимум при конкуренции)
```

Важно: при **свободном CPU** процесс с `nice +19` всё равно получит 100% — конкуренции нет, некому отдавать предпочтение. `nice` имеет значение только когда несколько процессов одновременно хотят CPU.

```bash
# запустить с низким приоритетом — не мешать продакшену
nice -n 19 python3 backup.py

# изменить приоритет запущенного процесса
renice -n 10 -p <PID>
renice -n -5 -p <PID>   # отрицательный nice — только root

# посмотреть приоритеты
top   # колонки: NI = nice, PR = реальный приоритет планировщика
ps -eo pid,ni,cmd --sort=ni
```

#### Nice vs CPUQuota — важное различие

Настройка `nice` влияет только на вес процесса в CFS и на то, как распределяются ресурсы при конкуренции. Если CPU свободен — процесс с любым `nice` заберёт все 100%.

Если нужно **жёстко ограничить** процесс («не более 50% CPU в любом случае») — `nice` здесь не поможет. Для этого используются квоты cgroups (`CPUQuota`). Подробно этот механизм, метрики троттлинга и примеры unit файлов разобраны в **Разделе 10 «cgroups vs ulimits»**.

### Потоки (Threads)

Если совсем просто: **процесс** — это программа целиком, **поток** — это одна задача внутри этой программы которая выполняется параллельно с другими задачами.

```
nginx (процесс)
├── поток 1 — обрабатывает запрос от пользователя A
├── поток 2 — обрабатывает запрос от пользователя B
└── поток 3 — обрабатывает запрос от пользователя C
             Все три выполняют один и тот же код (handle_request)
             но с разными данными — каждый для своего пользователя

java-app (процесс)
├── поток main      — основная логика
├── поток db-pool-1 — ждёт ответа от базы данных
├── поток db-pool-2 — ждёт ответа от базы данных
└── поток gc        — сборщик мусора, чистит память
```

Ключевая идея: пока один поток **ждёт** (ответа от БД, диска, сети) — другие потоки **работают**. Без потоков программа бы стояла и ждала каждой операции по очереди.

**Чем поток отличается от процесса:**

| | Процесс | Поток |
|-|---------|-------|
| Память | Своя (изолированная) | Общая с другими потоками |
| fd | Свои | Общие с другими потоками |
| Создание | Дорого — `fork()` копирует адресное пространство | Дёшево — `clone()` без копирования памяти |
| Падение | Не влияет на другие процессы | Может уронить весь процесс |
| Коммуникация | Через сокеты, пайпы, сигналы | Через общую память напрямую |

**Как Linux видит потоки:**

Ядро Linux **не делает жёсткого различия между процессом и потоком**. Для ядра и процесс и поток — это одна и та же внутренняя структура (`task_struct`). Разница только в том что потоки одного процесса делят общую память и fd, а у процессов всё своё.

Из-за этого у каждого потока есть свой ID — ядро называет его PID, но в пользовательском пространстве его называют **TID (Thread ID)** или **LWP (Lightweight Process)**. Разные инструменты используют разные названия для одного и того же:

```
top -H -p <PID>  → колонка PID показывает TID каждого потока
ps -eLf          → колонка LWP показывает TID каждого потока
/proc/<PID>/      → у каждого потока своя директория с его TID
```

Практическое следствие — **потоки расходуют те же системные лимиты что и процессы**. `pid_max`, `ulimit -u`, `TasksMax` в systemd — всё это считает процессы + потоки суммарно. Если приложение наплодит тысячи потоков — сервер перестанет отвечать так же как при fork bomb:

```bash
# посмотреть загрузку CPU конкретными потоками
top -H -p <PID>          # найти какой поток грузит CPU

# посмотреть все потоки процесса
ps -eLf | grep java      # LWP = TID потока

# количество потоков у процесса
cat /proc/<PID>/status | grep Threads
# Threads: 4

# суммарно потоков + процессов в cgroup сервиса
cat /sys/fs/cgroup/system.slice/<svc>.service/pids.current
```

> ⚠️ Если Java/Elasticsearch/ClickHouse грузит CPU — `top` покажет просто «процесс java жрёт 400%». Это ни о чём не говорит. `top -H -p <PID>` покажет какой конкретный поток (TID) виноват. Этот TID можно сопоставить с thread dump приложения (`jstack` для Java) и найти конкретную строку кода.


**Почему одни приложения используют процессы, другие — потоки:**

```
nginx         → процессы (worker per core)
              Причина: изоляция — падение воркера не роняет других

PostgreSQL    → процессы (один на соединение)
              Причина: изоляция памяти между сессиями

Java / Go     → потоки внутри одного процесса
              Причина: дёшево создавать, общая память = быстрая коммуникация

Python (GIL)  → потоки есть, но реально параллельно работает один
              Причина: GIL (Global Interpreter Lock) не даёт потокам
              выполняться одновременно на разных ядрах
              Выход: multiprocessing (процессы) или asyncio (один поток + event loop)
```

### OOM Killer

Когда физическая RAM исчерпана и своп тоже, ядро запускает **OOM Killer (Out of Memory Killer)**. Он анализирует все процессы, вычисляет `oom_score` для каждого (0–1000, выше = хуже) и убивает процесс с наибольшим score. Score учитывает: сколько RAM потребляет, как давно работает, является ли системным.

В `/proc/<PID>/` есть три файла связанных с OOM:

| Файл | Чтение/Запись | Описание |
|------|--------------|----------|
| `oom_score` | только чтение | Итоговый балл вычисленный ядром (0–1000). Смотришь чтобы понять насколько процесс «в зоне риска» |
| `oom_score_adj` | чтение и запись | Твоя поправка к score (-1000 до +1000). Настраивается двумя способами: вручную через `echo -1000 > /proc/<PID>/oom_score_adj` или постоянно через `OOMScoreAdjust=` в systemd unit файле |
| `oom_adj` | чтение и запись | Устаревший предшественник `oom_score_adj` (диапазон -17 до +15). Оставлен для совместимости — **не использовать** |

```bash
# посмотреть итоговый score процесса
cat /proc/$(pgrep -o nginx)/oom_score

# защитить критический процесс
echo -1000 > /proc/$(pgrep -o postgres)/oom_score_adj
# -1000 = никогда не убивать, +1000 = убить первым
# Почему помогает: OOM Killer прибавляет oom_score_adj к вычисленному score.
# При -1000 итоговый score всегда <= 0 — OOM Killer пропустит этот процесс
# и выберет другую жертву. Критичные сервисы (postgres, redis) защищают так.

# определить был ли процесс убит OOM Killer
journalctl -k | grep -i "out of memory\|killed process\|oom_kill"
dmesg | grep -i "oom"
```

## 3. Сигналы

**Сигнал** — это асинхронное уведомление которое ядро или один процесс отправляет другому процессу. Слово «асинхронное» означает: сигнал может прийти в любой момент, прямо посреди выполнения кода.

Получив сигнал, процесс может:
- **Выполнить обработчик** — разработчик заранее написал в коде функцию «что делать при получении этого сигнала». Например nginx при получении SIGHUP не падает, а перечитывает конфиг — потому что у него есть обработчик для SIGHUP. PostgreSQL при SIGTERM аккуратно завершает транзакции — тоже обработчик.
- **Проигнорировать сигнал** — процесс просто не реагирует. Например если послать SIGTERM процессу который его игнорирует — он продолжит работать как ни в чём не бывало. Именно поэтому после SIGTERM иногда нужен SIGKILL — его игнорировать нельзя.
- Выполнить действие по умолчанию (обычно завершение)

Исключение: `SIGKILL` и `SIGSTOP` нельзя перехватить, заблокировать или проигнорировать — они обрабатываются только ядром.

### Основные сигналы

| № | Имя | Действие по умолчанию | Когда использовать |
|---|-----|----------------------|--------------------|
| 1 | `SIGHUP` | Завершение | Reload конфига демона — процесс перечитывает конфиг без остановки |
| 2 | `SIGINT` | Завершение | Ctrl+C — прервать процесс |
| 9 | `SIGKILL` | Завершение | Крайняя мера — **нельзя перехватить**, ядро убивает немедленно |
| 15 | `SIGTERM` | Завершение | Вежливая просьба завершиться — **всегда пробовать первым** |
| 18 | `SIGCONT` | Продолжение | Разморозить процесс после SIGSTOP |
| 19 | `SIGSTOP` | Остановка | Заморозить процесс — **нельзя перехватить** |
| 10 | `SIGUSR1` | Зависит от приложения | nginx: переоткрыть лог-файлы после logrotate |

### SIGTERM vs SIGKILL — разница в последствиях

**SIGTERM (15):** процесс получает сигнал и **сам** решает как завершиться. Хорошо написанное приложение при получении SIGTERM делает graceful shutdown:
1. Перестаёт принимать новые запросы
2. Дожидается завершения текущих запросов
3. Закрывает соединения с базой данных
4. Сохраняет состояние если нужно
5. Удаляет временные файлы
6. Завершается с кодом 0

**SIGKILL (9):** ядро немедленно уничтожает процесс. Никакого обработчика, никакой очистки. Риски:
- Повреждённые файлы (запись не завершена)
- Незакоммиченные транзакции в БД (PostgreSQL после `kill -9` делает recovery при следующем запуске)
- Брошенные соединения с клиентами
- Временные файлы остаются на диске

```bash
# правильная последовательность
kill <PID>        # 1. SIGTERM — даём шанс завершиться gracefully
sleep 10          # 2. ждём
kill -9 <PID>     # 3. SIGKILL — только если не завершился

# по имени процесса
pkill nginx              # SIGTERM всем nginx
kill -HUP $(pgrep nginx) # reload конфига

kill -l   # список всех сигналов с номерами
```

### Job control — fg, bg, nohup, disown

Шелл (bash) не просто выполняет команды одну за другой — он ведёт **таблицу job'ов**: список процессов, которые запустил именно этот шелл, с их состоянием (running/stopped) и номером. Управление этой таблицей и есть job control.

| Действие | Что происходит | Сигнал |
|---|---|---|
| `command &` | Запустить сразу в фоне | — |
| `Ctrl+Z` | Заморозить процесс на переднем плане, вернуть терминал шеллу | `SIGTSTP` |
| `bg %1` | Разморозить задачу №1, оставить в фоне | `SIGCONT` |
| `fg %1` | Вернуть задачу №1 на передний план, отдать ей терминал | `SIGCONT` |
| `jobs` | Показать таблицу задач текущего шелла | — |

```bash
sleep 300            # запустили долгую команду на переднем плане
# Ctrl+Z              ← нажали, процесс заморожен
# [1]+  Stopped       sleep 300

jobs                  # посмотреть таблицу
# [1]+  Stopped       sleep 300

bg %1                 # разморозить, оставить в фоне — терминал свободен для других команд
# [1]+ sleep 300 &

fg %1                 # забрать обратно на передний план
```

> `Ctrl+Z` шлёт `SIGTSTP`, а не `SIGSTOP` — формально его можно перехватить, но на практике почти никто этого не делает: эффект тот же, процесс переходит в состояние `T`.

**Проблема которую решают `nohup` и `disown`:** когда SSH-сессия рвётся или терминал закрывается, ядро шлёт `SIGHUP` всем процессам, привязанным к этому терминалу — фоновые задачи умирают вместе с передним планом, если их не защитить.

| Инструмент | Когда применять | Что делает |
|---|---|---|
| `nohup command &` | **До** запуска — знаешь что отключишься | Команда с самого старта игнорирует `SIGHUP`. Вывод уходит в `nohup.out`, если не указано иное |
| `disown %1` | **После** запуска — забыл `nohup`, процесс уже в фоне | Убирает задачу из таблицы шелла — шелл больше не считает её своей и не убивает при выходе |

```bash
nohup ./long_migration.sh &     # защитили заранее
disown -h %1                    # уже запустили без nohup — защищаем постфактум
                                 # -h оставляет задачу видимой в jobs, просто иммунизирует к SIGHUP
```

**Когда нужно:** разворачиваешь что-то долгое через SSH (миграция БД, бэкап, тяжёлый деплой) и не уверен что сессия доживёт до конца — без защиты обрыв соединения убьёт процесс на середине.

### screen — сессия которая переживает обрыв SSH

`nohup`/`disown` решают узкую задачу: процесс не умрёт. Но если он упадёт с ошибкой посреди работы — узнаешь об этом только из лога, постфактум. `screen` решает задачу шире: создаёт отдельный виртуальный терминал на сервере, который живёт независимо от твоего SSH-соединения. Можно отключиться, заняться другими делами, вернуться — и увидеть экран ровно таким, каким его оставил, с полной интерактивностью.

```bash
screen -S deploy           # создать именованную сессию (без -S — безымянная)

# работаешь внутри как в обычном терминале

# Ctrl+a, затем d          ← detach: выйти, сессия продолжает жить на сервере
screen -ls                 # посмотреть какие сессии сейчас живы
# There is a screen on:
#   12345.deploy (Detached)

screen -r deploy           # вернуться внутрь — экран точно такой, каким оставил
screen -d -r deploy        # форсированно отцепить от другого места и перецепить сюда
                            # (полезно если забыл detach и сессия "висит attached")
```

Внутри одной сессии можно держать несколько окон:

```bash
# Ctrl+a, затем c           ← новое окно внутри той же сессии
# Ctrl+a, затем n / p       ← следующее / предыдущее окно
# Ctrl+a, затем 0..9        ← переключиться на окно по номеру
```

**Почему это работает лучше `nohup` для долгих интерактивных задач:** управляющий терминал процесса — это сам `screen`, а не твоя SSH-сессия. Когда SSH рвётся, гибнет только канал между тобой и сервером; `screen` и всё что внутри него продолжают жить как ни в чём не бывало. Возвращаешься — видишь живой вывод, можешь печатать команды, как будто никуда не уходил.

> На современных серверах чаще ставят `tmux` — активнее разрабатывается, удобнее со сплитами панелей, но `screen` почти везде есть из коробки и для задачи «не дать SSH-обрыву убить процесс» этого достаточно. Знать оба нормально, синтаксис похож.

## 4. cgroups vs ulimits

И `cgroups`, и `ulimits` — это не сторонние утилиты, это **интерфейсы к ядру Linux** — ручки управления которые ядро предоставляет для контроля над процессами. Когда ты пишешь лимиты в unit файле или выполняешь команды — ты просто просишь систему совершить системные вызовы к ядру.

**Как ulimits общаются с ядром:**

Когда ты запускаешь процесс, systemd перед его стартом делает ядру команду: «Поставь этому PID лимит на файлы 1024». Ядро записывает лимит в свою структуру данных этого процесса (`task_struct`) которая хранится в памяти ядра. Дальше всё просто:

1. Приложение стучится в ядро: «Я хочу открыть файл/сокет!» (`open()`)
2. Ядро смотрит в его профиль: «У тебя уже открыто 1024 файла. Больше нельзя»
3. Ядро шлёт приложение лесом, приложение валит в логи ошибку `Too many open files` (`EMFILE`)

**Как cgroups общаются с ядром:**

Здесь общение идёт через папки в `/sys/fs/cgroup/`. Выглядит как обычная файловая система, но на диске ничего нет — ядро генерирует её на лету прямо в памяти. Когда ты пишешь в `memory.max` — данные не сохраняются на диск, ты напрямую меняешь значение в памяти ядра. Перезагрузишь сервер — сбросится.

1. systemd создаёт папку сервиса в `/sys/fs/cgroup/` и закидывает туда PID мастера и воркеров
2. Ты пишешь `512M` в `memory.max` — ядро ставит у себя галочку: «Вот эта пачка PID суммарно может сожрать только 512 МБ»
3. Процесс просит у ядра: «Дай ещё памяти»
4. Ядро складывает память всех процессов в этой cgroup. Если вылезают за 512 МБ — вызывает OOM Killer и гасит процесс наглухо

**Разница для ядра:**
- **ulimits** — поштучная проверка: один процесс → одна запись в его личной карточке
- **cgroups** — коллективная ответственность: ядро вешает на процессы теги и считает ресурсы по этим тегам глобально

### 1. Анатомия cgroups — как устроена ФС

**cgroup (control group)** — механизм ядра для группировки процессов и применения к ним общих ограничений ресурсов. Каждая директория в `/sys/fs/cgroup/` — одна cgroup, каждый файл внутри — один параметр.

```
/sys/fs/cgroup/
├── system.slice/                    ← все системные сервисы
│   ├── nginx.service/
│   │   ├── cgroup.procs            ← PID всех процессов nginx
│   │   ├── memory.max              ← лимит RAM (записать = установить)
│   │   ├── memory.current          ← текущее потребление (читать)
│   │   ├── cpu.max                 ← лимит CPU
│   │   └── cpu.stat                ← статистика CPU
│   └── postgresql.service/
│       ├── cgroup.procs            ← мастер + все воркеры
│       ├── memory.max              ← лимит суммарно на весь сервис
│       └── memory.current          ← суммарное потребление
└── user.slice/                      ← пользовательские сессии
```

**Как перейти от `/proc/PID/cgroup` к реальным лимитам:**

```bash
cat /proc/$(pgrep -o postgres)/cgroup
# 0::/system.slice/postgresql.service

# 0:: — cgroups v2. Путь после :: добавляем к /sys/fs/cgroup/
cat /sys/fs/cgroup/system.slice/postgresql.service/memory.max
# 536870912   ← 512MB в байтах, или "max" если лимит не задан

cat /sys/fs/cgroup/system.slice/postgresql.service/memory.current
# 314572800   ← 300MB суммарно мастер + все воркеры

cat /sys/fs/cgroup/system.slice/postgresql.service/cgroup.procs
# 1234   ← мастер
# 1235   ← worker 1
# 1236   ← worker 2
```

```bash
systemd-cgls    # (cgroup list) дерево cgroups
systemd-cgtop   # (cgroup top) мониторинг потребления в реальном времени
```

### 2. cgroups vs ulimits — в чём разница

**ulimits — каждому своя коробка.** Ядро применяет лимит к каждому процессу индивидуально. При `fork()` дочерний получает копию таблицы лимитов родителя. Лимиты не суммируются.

```
bash (nofile=1024)
  ├── nginx-master (nofile=65536)   ← systemd задал через setrlimit()
  │   ├── nginx-worker-1 (nofile=65536)   ← скопировал при fork
  │   ├── nginx-worker-2 (nofile=65536)   ← скопировал при fork
  │   └── nginx-worker-3 (nofile=65536)   ← скопировал при fork
  └── psql (nofile=1024)   ← скопировал от bash, не от nginx
```

> Каждый воркер может открыть до 65 536 fd независимо. Суммарно nginx может открыть 3 × 65 536 = 196 608 fd — нормально.

**cgroups — одна коробка на всех.** Ядро считает суммарное потребление всех процессов группы.

```
nginx.service cgroup (MemoryMax=512M)
  ├── nginx-master:   50M
  ├── nginx-worker-1: 150M
  └── nginx-worker-2: 150M
                      ────
  Итого:              350M из 512M — ОК
  Если сумма > 512M → OOM ко всей группе
```

| Критерий | cgroups | ulimits |
|----------|---------|---------|
| Единица ограничения | Суммарное потребление группы | Лимит одного процесса |
| Применяется к | Сервис целиком (мастер + все воркеры) | Каждый процесс индивидуально |
| Типы ресурсов | Физические ресурсы машины (CPU, RAM, I/O, сеть) | Поведение самого процесса (сколько файлов открыть, процессов породить, файл какого размера создать) |
| Иерархия | Да — дерево, дочерняя группа ≤ родительской | Нет групп — только копирование через `fork()` |
| Изменение без рестарта | Да | Soft лимит: да. Hard лимит: только root |
| В systemd | `CPUQuota=`, `MemoryMax=`, `TasksMax=` | `LimitNOFILE=`, `LimitNPROC=` |
| Docker / K8s | Основа изоляции контейнеров | Практически не используется |

```bash
ulimit -a               # лимиты текущей сессии
cat /proc/<PID>/limits  # реальные лимиты запущенного процесса
```

Один и тот же лимит ядра можно задать тремя способами — в зависимости от контекста:

**`Limit<ИМЯ>=` в unit файле** — задаёшь лимит один раз в конфиге сервиса, systemd применяет его каждый раз при старте. Это постоянная настройка для сервиса.

**`/etc/security/limits.conf`** — когда пользователь логинится по SSH или через `su`, PAM читает этот файл и устанавливает лимиты для его сессии. То есть у разработчика Васи может быть `nofile=10000`, а у Пети `nofile=1024`. Или например `nproc=500` — не более 500 процессов от этого пользователя.

**`ulimit`** — показывает или меняет лимит в текущей сессии прямо сейчас. Флаг `-n` указывает **какой именно лимит** — `-n` это сокращение от `nofile`, то есть открытые fd:

```bash
ulimit -n        # посмотреть лимит на открытые fd в текущей сессии
# 1024           ← процессы в этой сессии могут открыть не более 1024 fd

ulimit -n 65536  # поднять лимит в текущей сессии
ulimit -n        # проверить
# 65536          ← применилось, но только до закрытия терминала

ulimit -a        # показать все лимиты сразу
```

Закроешь терминал — вернётся обратно. Удобно проверить как поведёт себя приложение с другим лимитом не меняя конфиги.

> Все три способа устанавливают один и тот же лимит ядра — просто через разные интерфейсы.

**🛑 Грабли №1: limits.conf не работает для сервисов**

`/etc/security/limits.conf` читается PAM только при интерактивном входе (SSH, su). systemd запускает сервисы напрямую в обход PAM. Для сервисов — только `Limit*=` в unit файле.

**🛑 Грабли №2: LimitNPROC проверяется по UID (пользователю), а не по cgroup сервиса**

Большинство ulimits (например `LimitNOFILE` — лимит на открытые файлы и сокеты) ядро отслеживает изолированно для каждого PID. Но `LimitNPROC` (лимит на количество процессов и потоков) — глобальное исключение: ядро проверяет его строго по **UID**.

Когда пишешь `LimitNPROC=1024` в unit файле, systemd устанавливает этот лимит для стартового процесса сервиса. Но при каждом следующем `fork()` ядро проверяет суммарное количество процессов от этого UID **во всей системе**.

**В чём засада:** если `nginx` (мастер + 2 воркера = 3 процесса) и `mysql` (мастер + 2 воркера = 3 процесса) запущены от `www-data` — для ядра они находятся в одной общей куче из 6 процессов. Как только суммарное число дойдёт до лимита — ни один из сервисов не сможет создать новый воркер или поток, в логи полетит `Resource temporarily unavailable` (`EAGAIN`).

Директива `LimitNPROC=5` внутри `nginx.service` не означает «у nginx лимит 5 процессов». Она означает «обнови глобальный лимит для UID `www-data` в значение 5». Счётчик у всех сервисов под этим UID — **один на всех**.

**📜 Исторический контекст:** `nproc` создавался в эпоху классического многопользовательского Unix, задолго до cgroups. Это был единственный способ защитить сервер от fork bomb со стороны одного пользователя. Для интерактивных сессий в `limits.conf` он актуален и сейчас.

**Как делать правильно:**

- **Разные сервисы — разные пользователи:** `nginx` от пользователя `nginx`, `mysql` от пользователя `mysql`. Тогда счётчики раздельные.
- **Для изоляции процессов внутри сервиса — только `TasksMax=` (максимум процессов + потоков в cgroup сервиса).** Ему не важен пользователь — он считает процессы строго внутри cgroup конкретного сервиса.

### 3. Настройка ресурсов в systemd

**CPUQuota** — жёсткий лимит CPU через cgroup. Отличие от `nice`:

```
nice +19:       при свободном CPU возьмёт 100% — мягкий приоритет
CPUQuota=50%:   не получит больше 50% ядра никогда — жёсткий лимит
```

```bash
# изменить без рестарта
systemctl set-property nginx.service CPUQuota=50%
systemctl set-property nginx.service MemoryMax=512M

# проверить текущие лимиты сервиса
systemctl show nginx | grep -E "^(CPU|Memory|IO|Tasks)"
```

Все параметры в unit файле:

```ini
[Service]
CPUWeight=100             # вес при конкуренции за CPU (1–10000, дефолт 100)
CPUQuota=50%              # жёсткий лимит CPU (200% = не более 2 ядер)
MemoryMin=128M            # гарантированный минимум — не отберут даже при OOM
MemoryHigh=400M           # мягкий лимит — throttle при превышении
MemoryMax=512M            # жёсткий лимит — OOM kill при превышении
MemorySwapMax=0           # запретить swap для этого сервиса
IOReadBandwidthMax=/dev/sda 100M    # лимит чтения с диска
IOWriteBandwidthMax=/dev/sda 50M    # лимит записи на диск
TasksMax=200              # максимум процессов + потоков в cgroup
                          # защита от fork bomb, лучше чем LimitNPROC
LimitNOFILE=65536         # лимит открытых fd (файлы + сокеты)
LimitNPROC=4096           # лимит процессов (считается по пользователю — см. Грабли №2)
LimitMEMLOCK=infinity     # для Elasticsearch, Redis
LimitCORE=infinity        # разрешить core dump при падении
OOMScoreAdjust=-100       # снизить приоритет для OOM Killer
TimeoutStopSec=30         # сколько секунд ждать после SIGTERM перед SIGKILL (дефолт 90)
```

> **Fork bomb и TasksMax:** при достижении `TasksMax` вызов `fork()` возвращает `EAGAIN`. Бомба останавливается на уровне сервиса не затрагивая систему. Восстановление: `systemctl kill --kill-who=all --signal=SIGKILL <svc>`.

## 5. Namespaces и контейнеры

### Что такое Namespace

Если cgroup отвечает на вопрос «сколько ресурсов процессу можно потребить?», то Namespace отвечает на вопрос «что процесс вообще видит в системе?».

Контейнеров как отдельных сущностей в ядре Linux не существует. Docker, containerd, Podman — это просто обёртки которые берут обычный процесс и вешают на него набор изоляторов (Namespaces).

| Namespace | Что изолирует | Практический эффект |
|-----------|--------------|---------------------|
| `pid` | Таблицу процессов | Внутри контейнера `ps` видит только свои процессы. Главный процесс — PID 1. |
| `net` | Сетевой стек | У контейнера свой виртуальный интерфейс (`eth0`), свой localhost, свои таблицы маршрутов |
| `mnt` | Точки монтирования | Контейнер заперт в своей файловой системе и не видит диски хоста если их явно не пробросить через volumes |
| `uts` | Hostname / Domain | Контейнер может называться `my-nginx-pod` и это никак не влияет на имя самого сервера |
| `ipc` | Межпроцессное взаимодействие | Процессы внутри контейнера не могут читать Shared Memory или семафоры процессов с хоста |
| `user` | UID / GID | Внутри контейнера ты `root` (UID 0), но для хоста этот процесс выполняется от бесправного пользователя. База для Rootless-контейнеров. |
| `cgroup` | Иерархию cgroups | Контейнер видит только свою часть дерева ограничений, скрывая от себя структуру всего сервера |

### Как проверить namespaces процесса

```bash
# дескрипторы namespace лежат в /proc
ls -la /proc/<PID>/ns/
# lrwxrwxrwx pid -> pid:[4026532456]
# lrwxrwxrwx net -> net:[4026532460]  ← число в скобках — уникальный inode namespace
```

> **Кейс на собеседовании:** «Как проверить что два контейнера находятся в одном Kubernetes Поде?»
> Ответ: сравнить inode их сетевых namespaces. Если `ls -la /proc/<PID_1>/ns/net` и `ls -la /proc/<PID_2>/ns/net` выдают одинаковый ID — процессы делят одну сеть (один Net Namespace / один Pod).

### nsenter — войти в namespace процесса

Типичный кошмар в проде: контейнер багует. Делаешь `docker exec -it my_container bash` чтобы запустить `curl` или `tcpdump` — а в ответ `bash: command not found`. Образ собран как `distroless` или урезанный `alpine` ради безопасности, внутри нет никаких утилит.

`nsenter` позволяет находясь на хосте (где есть весь арсенал дебага) просунуть голову внутрь изоляции контейнера. Запускаешь инструмент хоста, но заставляешь его смотреть на мир глазами процесса контейнера.

```bash
# войти в network namespace — выполнить одну команду и выйти
nsenter -t <PID> -n ss -tnlp

# интерактивный вход в сеть контейнера
nsenter -t <PID> -n bash
# теперь хостовые утилиты ip addr, ss, curl, tcpdump видят ТОЛЬКО сеть этого контейнера

# войти в сеть (-n) + файловую систему (-m) одновременно
nsenter -t <PID> -n -m bash
# используешь curl с хоста, но пути /etc, /var ведут внутрь контейнера

# полный аналог docker exec -it (войти во все namespaces)
nsenter -t <PID> -a bash
```

**Боевой пример** — проверить эндпоинт изнутри сети «голого» контейнера:

```bash
PID=$(docker inspect --format '{{.State.Pid}}' my_container)
nsenter -t $PID -n curl http://127.0.0.1:8080/health
```

> Одиночная команда (`nsenter ... <команда>`) выполняет её и возвращает на хост. Запуск с `bash` — даёт интерактивную сессию. Выход — `exit`.

### Почему top показывает память хоста

Если внутри контейнера с лимитом 512MB запустить `top` — он покажет все 64GB RAM сервера. Это архитектурная особенность Linux.

`top` читает `/proc/meminfo`. Docker при старте честно монтирует контейнеру его собственный отдельный экземпляр `procfs`. Но когда `top` запрашивает `/proc/meminfo`, ядро запускает функцию которая **ничего не знает про cgroups** — она просто берёт глобальную переменную всей RAM сервера и выдаёт её.

```
Контейнер читает свой /proc/meminfo
        │
        ▼
Ядро генерирует текст из глобальной переменной: «Всего RAM = 64GB»
        │
        ▼
top внутри контейнера показывает 64GB
```

> ⚠️ Если процесс начнёт потреблять память ориентируясь на `top` — его молча прибьёт OOM Killer при достижении лимита cgroup (512MB). `top` до последней секунды будет показывать что памяти ещё вагон.

**С процессами (`ps`) такой проблемы нет** — PID Namespace на уровне ядра умеет фильтровать дерево процессов. `ps` в контейнере видит только свои процессы, `ps` на хосте видит процессы всех контейнеров с их реальными хостовыми PID.

**Как смотреть ресурсы контейнера правильно:**

```bash
# истинные лимиты и потребление — в cgroup, не в top
cat /sys/fs/cgroup/memory.max          # жёсткий лимит (в байтах)
cat /sys/fs/cgroup/memory.current      # текущее потребление

# OOM kill внутри контейнера не увидеть — процесс просто исчезнет
# следы искать только на хосте:
dmesg | grep -i oom
journalctl -k | grep -i -E "oom|killed process"

# найти все реальные PID процессов контейнера с хоста
CPID=$(docker inspect --format '{{.State.Pid}}' my_container)
cat /proc/$CPID/cgroup                 # путь к cgroup контейнера
cat /sys/fs/cgroup/<path>/cgroup.procs # все PID процессов контейнера
```
