# 8. Security & production-практики

## Protected branches и protected environments

### Protected branches

Protected branch — ветка, для которой ограничены push и merge напрямую. Настраивается в настройках проекта: Settings → Repository → Branch rules (у группы этого раздела нет, только у проекта). Работает и по точному имени ветки, и по wildcard (`release/*`).

Для правила задаются:
- **Allowed to merge** — кто может смёрджить merge request в эту ветку;
- **Allowed to push and merge** — кто может пушить в неё напрямую, без merge request (на практике почти всегда ставят «No one», чтобы исключить прямые пуши в обход review);
- **Allow force push** — разрешить ли force push (`git push --force`), по умолчанию выключено. Force push перезаписывает историю удалённой ветки вместо того, чтобы добавить новые коммиты поверх старых, — если это разрешено на общей ветке, можно случайно затереть чужие коммиты, которые кто-то запушил после тебя;
- **Code owner approval** — требовать ли approval от CODEOWNERS для затронутых файлов. Это Premium/Ultimate: на Free тарифе этого тоггла в Branch rule details просто нет, там доступны только Allowed to merge, Allowed to push and merge и Allow force push.

Default-ветка проекта (`main`) защищена автоматически сразу при создании репозитория. Базовая защита веток есть на Free-тарифе; более гранулярный доступ — конкретные пользователи и группы, а не только роли — это уже Premium/Ultimate.

### Protected environments

Protected environment ограничивает не то, кто может положить код в ветку, а то, кто может **задеплоить** через `environment:` — независимо от прав на merge. Принцип простой: в job указываешь `environment: name: production` (как в примере ниже), а затем в Settings → CI/CD → Protected environments защищаешь окружение с этим же именем `production` — GitLab сопоставляет их по имени. Это фича Premium/Ultimate, на бесплатном gitlab.com этого раздела в настройках просто нет.

```yaml
deploy_prod:
  stage: deploy
  script:
    - ./deploy.sh production
  environment:
    name: production
    url: https://myapp.example.com
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

`name` — имя окружения, именно на него настраивается protection в Settings → CI/CD → Protected environments; `url` — необязательная ссылка, которая появится у окружения в интерфейсе (Operate → Environments), чтобы одним кликом открыть то, что задеплоено.

Для окружения `production` задаются:
- **Allowed to deploy** — роль, конкретные пользователи или группы, которым можно запускать job с этим `environment:`;
- **Approval rules** (deployment approvals) — можно потребовать N подтверждений от заданных пользователей или групп, прежде чем заблокированный job сможет запуститься. Job не обязан быть `when: manual` — он сам уходит в статус «blocked» и ждёт approval, а после подтверждения его всё равно нужно запустить вручную.

Важный момент: доступ проверяется по тому, **с какой ветки или тега запущен pipeline**, а не по роли того, кто нажал «Run». Если job с `environment: production` пытается стартовать из pipeline на незащищённой ветке — он заблокирован, даже если у пользователя роль Maintainer.

**Частый вопрос на собеседовании:** чем protected branch отличается от protected environment. Branch защищает код — контролирует, кто может напрямую пушить и мёрджить в неё; environment защищает деплой — контролирует, кто может выкатить уже смёрдженный код в это окружение.

## Merge request pipelines vs branch pipelines vs merged results pipelines

### Branch pipeline

Обычный pipeline, который запускается на `git push` в ветку (а также по расписанию, через API, вручную и так далее). `CI_PIPELINE_SOURCE` в этом случае — `push`. Работает над состоянием ветки как есть на момент коммита.

### Merge request pipeline

Запускается специально для merge request: при его создании, при пуше нового коммита в source-ветку или вручную через кнопку Run pipeline на вкладке Pipelines внутри merge request. `CI_PIPELINE_SOURCE` — `merge_request_event`. Доступно на всех тарифах, включая Free.

Job или весь pipeline должны сами объявить, что участвуют в merge request pipeline:

```yaml
job:
  script: ./test.sh
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

Практический нюанс, который реально путает: `CI_COMMIT_BRANCH` — переменная с именем ветки, из которой запущен pipeline, — доступна только в branch pipeline, а в merge request pipeline она **пустая**.

Сам по себе merge request pipeline всё ещё гоняет только содержимое source-ветки, полностью игнорируя, что сейчас лежит в target, — по сути та же проверка, что и branch pipeline, просто в контексте конкретного merge request и с доступом к его переменным.

Ещё один нюанс, завязанный на тему protected-переменных из первого раздела: **protected variables и protected runners доступны merge request pipeline, только если и source, и target ветка одновременно защищены**, а у автора pipeline есть доступ на push/merge в target. На практике feature-ветки обычно не защищены — а значит, типичный merge request «feature → main» их не получит, даже если `main` защищён.

### Merged results pipeline (Premium/Ultimate)

Расширенный вариант merge request pipeline (Premium/Ultimate): GitLab создаёт внутренний, нигде реально не существующий commit — результат слияния source в target — и гоняет pipeline именно по нему. Так ловятся конфликты интеграции, не видные при тестировании одной source-ветки: например, две ветки по отдельности проходят CI, но вместе ломают сборку.

Включается в Settings → General → Merge requests → Merge options → **Enable merged results pipelines**. Если между source и target реальный git-конфликт, merged results pipeline создать невозможно, и GitLab автоматически откатывается на обычный merge request pipeline. Раз результат — это commit «на момент запуска», если пока идёт работа над merge request target успел уйти вперёд, pipeline стоит перезапустить, чтобы результат остался актуальным.

Merge trains — следующий уровень поверх merged results: очередь merge request, помеченных «Set to auto-merge» (бывшая кнопка «Start merge train»). Каждый следующий в очереди тестируется не просто против target, а против target плюс все merge request, что стоят перед ним в очереди, — это защищает от ситуации, когда несколько по отдельности рабочих изменений вместе всё-таки конфликтуют. Если pipeline у кого-то из очереди падает, его убирают из очереди, а для всех, кто стоял за ним, pipeline пересоздаётся заново. Тоже Premium/Ultimate.

Практическое следствие всей этой связки: если для одного и того же job одновременно верны правила и на `push`, и на `merge_request_event`, пуш в ветку с уже открытым merge request порождает два параллельных pipeline на один и тот же коммит — обычный branch pipeline и merge request pipeline. Разруливается это на уровне `workflow:rules`.

## По мелочи: retry, timeout, parallel:matrix

### retry

Автоматический перезапуск job при падении:

```yaml
test:
  script: ./run-tests.sh
  retry: 2
```

`retry: 2` — job выполнится максимум 3 раза (1 попытка + 2 retry) при любой причине падения. Чтобы перезапускать только на конкретные причины, а не на реальный фейл теста:

```yaml
test:
  script: ./run-tests.sh
  retry:
    max: 2
    when:
      - runner_system_failure
      - stuck_or_timeout_failure
```

`max` — от 0 до 2. `when` сужает retry до конкретных причин: `runner_system_failure` (упал сам runner или окружение), `stuck_or_timeout_failure` (job завис или упёрся в timeout), `script_failure` (упал сам script — настоящий фейл теста). Смысл сужения: если ретраить всё подряд без разбора, флейковый тест будет молча перезапускаться и создавать иллюзию стабильности вместо того, чтобы такая нестабильность бросалась в глаза.

### timeout

```yaml
long_job:
  script: ./integration-tests.sh
  timeout: 3h 30m
```

Переопределяет для конкретного job дефолтный timeout проекта (Settings → CI/CD → General pipelines, по умолчанию 60 минут). Используется в обе стороны: увеличить — для реально долгих job (полная сборка, интеграционные тесты), уменьшить — чтобы job, который должен отрабатывать быстро, не висел до общего лимита, если где-то завис.

### parallel:matrix

Запускает несколько инстансов одного job параллельно с разными значениями переменных — не разбиение одного прогона на части, а прогон **разных комбинаций** конфигурации:

```yaml
test:
  stage: test
  parallel:
    matrix:
      - PYTHON_VERSION: ["3.10", "3.11", "3.12"]
        DJANGO_VERSION: ["4.2", "5.0"]
  image: python:$PYTHON_VERSION
  script:
    - pip install "django==$DJANGO_VERSION"
    - pytest
```

Это создаёт 3×2 = 6 job (`test: [3.10, 4.2]`, `test: [3.10, 5.0]` и так далее) — типичный сценарий: прогнать тесты сразу на нескольких версиях языка или фреймворка, вместо того чтобы писать шесть одинаковых job руками. Верхний предел — 200 job из одной матрицы.

## SAST / DAST / dependency & container scanning — shift-left security

Shift-left — поймать уязвимость на этапе merge request или коммита, а не после того, как она уже в проде: чинить дешевле, пока разработчик ещё держит контекст в голове.

На каждый вид проверки у GitLab есть готовый CI/CD template — подключается через `include`, поднимает нужные job в стадии `test` (если стадии переопределены вручную, `test` обязателен в списке) и кладёт результат в отчёт, который виден в Security Dashboard проекта и прямо в виджете merge request — «обнаружено N новых уязвимостей».

```yaml
include:
  - template: Jobs/SAST.gitlab-ci.yml
  - template: Jobs/Dependency-Scanning.gitlab-ci.yml
  - template: Jobs/Container-Scanning.gitlab-ci.yml
```

### SAST (Static Application Security Testing)

Анализирует исходный код без его выполнения: ищет SQL-инъекции, небезопасную десериализацию, слабую криптографию и подобные паттерны. Под капотом — набор анализаторов, которые GitLab подбирает по языкам в репозитории (для Python это в первую очередь Semgrep-based job `semgrep-sast`).

```yaml
include:
  - template: Jobs/SAST.gitlab-ci.yml

variables:
  SAST_EXCLUDED_PATHS: "spec, test, tests, tmp"
```

`SAST_EXCLUDED_PATHS` — стандартная настройка, чтобы не гонять анализатор по тестовому коду. Отдельно есть GitLab Advanced SAST — более мощный движок с межфайловым и межфункциональным анализом потоков данных вместо построчных паттернов, но это уже Ultimate.

### DAST (Dynamic Application Security Testing)

В отличие от SAST, DAST атакует уже запущенное приложение снаружи — реальными HTTP-запросами ищет SQL-инъекции, XSS, CSRF. Поэтому DAST не может стартовать раньше, чем приложение куда-то задеплоено и до него можно достучаться — обычно в review environment.

На 2026 год: старый proxy-based анализатор на связке с OWASP ZAP полностью убран (deprecated в 16.9, removed в 17.3), актуальный вариант — только browser-based DAST. И вся фича целиком — Ultimate, на Free и Premium её просто нет.

### Dependency Scanning

Проверяет зависимости проекта (`requirements.txt`, `package-lock.json`, `go.sum`) на известные CVE по базе уязвимостей — ничего не собирает и не запускает, только читает файлы с зафиксированными версиями пакетов.

```yaml
include:
  - template: Jobs/Dependency-Scanning.gitlab-ci.yml
```

Практическая деталь: скан имеет смысл, только если версии пакетов реально зафиксированы (лучше через `pip-compile` или `poetry.lock`, а не голый `requirements.txt` без версий) — без точных версий сопоставлять их с базой CVE не с чем.

### Container Scanning

Сканирует уже собранный Docker-образ на уязвимости в системных пакетах внутри него — то, что попало через `apt`/`apk` в базовый образ, а не через `pip`/`npm` (за это отвечает Dependency Scanning выше). Анализатор — Trivy; старый Grype в статусе deprecated и полностью отключат к GitLab 19.0.

```yaml
include:
  - template: Jobs/Container-Scanning.gitlab-ci.yml

variables:
  CS_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

По умолчанию job пытается собрать имя образа из `$CI_APPLICATION_REPOSITORY`/`$CI_APPLICATION_TAG` — это дефолт под Auto DevOps naming convention, который на обычном pipeline почти никогда не совпадает с тем, как ты сам называешь и тегируешь образ. Поэтому `CS_IMAGE` почти всегда переопределяют явно, указывая тот же тег, что и в `docker push` этого же pipeline. Отсюда и порядок стадий: container scanning идёт после build/push в registry — сканировать нечего, пока образа там ещё нет.

**Частый вопрос на собеседовании:** в чём разница между dependency scanning и container scanning, если оба вроде проверяют «зависимости». Dependency scanning — про пакеты уровня языка (pip/npm/go modules), container scanning — про пакеты уровня операционной системы внутри образа (то, что притащил базовый `FROM python:3.11-slim`). Одно не заменяет другое.

**Итог:** понимаешь, как разграничить доступ к коду и к деплою через protected branches и protected environments, чем pipeline для merge request отличается от обычного branch pipeline и от merged results, как retry/timeout/parallel:matrix закрывают типовые проблемы pipeline без ручной возни, и как встроить SAST/DAST/scanning в pipeline и куда смотреть за результатом.

## Bonus (Middle+): секреты за пределами CI/CD variables — Vault и внешние secret-менеджеры

У CI/CD variables — даже protected и masked — на реальном проде есть слабые места:
- значение не ротируется само (ротация — это когда секрет автоматически меняется на новый через какое-то время или по событию): утёкший секрет остаётся рабочим, пока кто-то не поменяет его вручную;
- один и тот же секрет часто копируют в переменные нескольких проектов, и невозможно централизованно понять, где именно он использован;
- нет аудита реальных обращений к значению — только факт, что pipeline его использовал;
- masked прячет секрет в логах job, но не от людей с доступом к Settings → CI/CD → Variables.

Для боевых секретов вместо статичных переменных используют внешний secret-менеджер — HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault. Секрет запрашивается в момент выполнения job и не живёт дольше, чем сам job.

### HashiCorp Vault через id_tokens

Современная аутентификация pipeline в Vault — не статичный токен, а JWT, который GitLab подписывает на каждый запуск job через ключевое слово `id_tokens`.

```yaml
deploy_production:
  id_tokens:
    VAULT_ID_TOKEN:
      aud: https://vault.example.com
  secrets:
    DATABASE_PASSWORD:
      vault: production/db/password@ops
      token: $VAULT_ID_TOKEN
  script:
    - echo "используем $DATABASE_PASSWORD"
```

`vault: production/db/password@ops` читается как `<путь к секрету>/<поле>@<точка монтирования secrets engine>`.

Как это работает:
1. GitLab генерирует JWT с claims вроде `project_path`, `namespace_path`, `ref`, и кладёт его в `VAULT_ID_TOKEN`.
2. Job предъявляет этот JWT методу аутентификации Vault (Vault заранее настроен доверять OIDC discovery URL вашего GitLab).
3. Vault сверяет claims токена с `bound_claims`, прописанными в конфиге role, — например, что pipeline запущен именно из нужного проекта и именно с `main`.
4. Если совпало — Vault выдаёт короткоживущий токен, привязанный к политике этой role, и уже этим токеном job читает секрет.

Смысл шага 3: доступ привязан не к токену, который можно скопировать и унести, а к тому, откуда именно запущен pipeline. Даже если этот JWT утечёт из логов, он бесполезен вне контекста конкретного проекта и ветки и истекает вместе с job.

Нюанс по тарифам: `secrets:vault` в таком декларативном виде — Premium/Ultimate. На Free тот же результат получают вручную: `id_tokens` доступен на всех тарифах, а обращение к Vault (`vault login -method=jwt`, `vault kv get`) прописывают прямо в `script`.

### Внешние secret-менеджеры (AWS/GCP/Azure)

Та же схема, только вместо Vault — облачный STS. Для AWS: `id_tokens` выпускает JWT, job вызывает `aws sts assume-role-with-web-identity` с этим токеном и получает временные ключи вместо хранения `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` как статичных переменных проекта. AWS IAM настраивается доверять GitLab как OIDC-провайдеру — точно так же, как Vault. GCP Secret Manager и Azure Key Vault работают по тому же принципу.

**Частый вопрос на собеседовании:** зачем вообще нужны id_tokens/OIDC, если можно просто положить ключ в masked-переменную. Разница — во времени жизни и области действия: masked-переменная живёт, пока её не удалят вручную, и доступна любому job проекта; токен через `id_tokens` выпускается на конкретный запуск конкретного job, несёт в себе claims о том, откуда он взят, и истекает вместе с ним.
