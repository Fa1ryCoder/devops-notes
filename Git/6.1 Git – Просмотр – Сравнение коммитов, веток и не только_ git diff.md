# 6.1 Git – Просмотр – Сравнение коммитов, веток и не только: git diff

`git diff` сравнивает два состояния проекта и построчно показывает разницу между ними. Состояниями могут быть коммиты, ветки, индекс или рабочая директория — команда одна и та же, разница только в том, какие две точки ей передать.

## Сравнение коммитов и веток

Базовый синтаксис — `git diff <commit1> <commit2>`: git берёт снапшот каждой точки целиком и построчно сравнивает их между собой. Вместо имён веток можно передавать что угодно, что указывает на коммит — хеш, `HEAD~2`, тег: механика сравнения от этого не меняется.

Запись через две точки, `git diff master..feature`, полностью эквивалентна записи через пробел — это просто альтернативный синтаксис для того же самого сравнения.

Три точки работают иначе. `git diff master...feature` сначала ищет общего предка обеих веток (merge-base — коммит, от которого они разошлись), а затем сравнивает именно его с последним коммитом `feature`. Вопрос, на который отвечает такая запись: «что изменилось в `feature` с момента, когда она отделилась от `master`» — всё, что тем временем случилось в самом `master`, полностью игнорируется.

Разница хорошо видна на примере. Есть общий коммит `B`, после которого ветки разошлись: в `master` появился коммит `D`, в `feature` — коммит `C`.

`git diff master..feature`:

```diff
diff --git a/app.py b/app.py
index 1f4cad6..a5b78a0 100644
--- a/app.py
+++ b/app.py
@@ -5,4 +5,4 @@ def login(user, password):
 def logout(user):
     print("logging out")
 line added by B
-master-only change after split
+feature-only change
```

`git diff master...feature`:

```diff
diff --git a/app.py b/app.py
index 6b6298c..a5b78a0 100644
--- a/app.py
+++ b/app.py
@@ -5,3 +5,4 @@ def login(user, password):
 def logout(user):
     print("logging out")
 line added by B
+feature-only change
```

## Анатомия вывода git diff

Изменения по каждому файлу git выводит отдельным блоком. Разберём один такой блок построчно — тот же файл, `git diff master..feature` из примера выше:

1. **`diff --git a/app.py b/app.py`.** Собственный расширенный заголовок git, не часть стандартного unified diff. `a/` — исходное состояние, `b/` — целевое; сами директории `a` и `b` в проекте не существуют, это условные префиксы. Если файл не переименовывался, пути после них совпадают.

2. **`index 1f4cad6..a5b78a0 100644`.** Хеши blob-объектов файла до и после изменения, а следом — режим файла в Unix-нотации: `100644` — обычный файл без права на исполнение, `100755` — исполняемый. Это не тип git-объекта (blob/tree/commit), а тип и права доступа самого файла.

3. **`--- a/app.py` и `+++ b/app.py`.** Стандартные заголовки unified diff — те же `a/`/`b/`, но уже в формате, понятном любой diff-утилите, не только git.

4. **`@@ -5,4 +5,4 @@ def login(user, password):`.** Заголовок хунка — куска, на которые разбиваются изменения. `-5,4` значит: в исходном файле показанный кусок начинается с 5-й строки и занимает 4 строки; `+5,4` — то же самое для итогового файла. Текст после второй пары `@@` — попытка git определить, к какой функции относится хунк: он берёт ближайшую строку выше начала хунка, похожую на объявление функции. Здесь это `def login`, хотя изменение на самом деле происходит рядом с `def logout` — но `def logout` идёт первой строкой самого хунка, а не строкой перед ним, поэтому в поиск не попадает, и git берёт более раннее совпадение. Это справочная информация, доверять ей как точному источнику не стоит.

5. **Строки с `-` и `+`.** Убрать из исходного файла и добавить в итоговый соответственно. Остальные строки хунка, без пометки, — контекст, они не менялись. То же деление на хунки использует `git add -p` при интерактивном стейджинге.

## Рабочая директория, индекс и HEAD

Самое частое применение `git diff` — не сравнение веток, а проверка собственных изменений перед коммитом. Здесь работают три команды:

| Команда | Что сравнивает |
|---|---|
| `git diff` | рабочая директория ↔ индекс |
| `git diff --cached` (или `--staged`) | индекс ↔ HEAD |
| `git diff HEAD` (или `git diff @`) | рабочая директория ↔ HEAD (staged и unstaged вместе) |

Разница хорошо видна на конкретном случае. У файла есть изменение, уже добавленное в индекс, и поверх него — ещё одно, пока не застейдженное:

```
$ git status --short
MM app.py
```

```
$ git diff              # только незастейдженное
+second unstaged change

$ git diff --cached     # только застейдженное
+unstaged change

$ git diff HEAD         # оба вместе
+unstaged change
+second unstaged change
```

`git diff --cached` показывает ровно то, что попадёт в следующий коммит — это последняя возможность свериться перед `git commit`, что в индекс не утекло лишнее: закомментированный debug-вывод, случайно застейдженный файл с паролем или токеном и так далее. `git status` покажет только список застейдженных файлов, а какие именно строки в них изменились — видно исключительно через diff.

По умолчанию `git diff` игнорирует неотслеживаемые (untracked) файлы — они не участвуют в сравнении, пока не окажутся в индексе. Исключение — `git add -N` (intent-to-add): файл помечается как отслеживаемый, но без реального содержимого в индексе, и после этого `git diff` показывает его целиком как добавленный.

`HEAD` в `git diff HEAD` можно заменить на любой другой коммит или ветку — команда сравнит рабочую директорию не с последним коммитом текущей ветки, а с указанной точкой. `git diff feature`, стоя на `master`, покажет, чем текущая рабочая директория — включая незакоммиченные правки, если они есть, — отличается от `feature`, без переключения веток.

## Дополнительные опции и приёмы

1. **`git commit -v`.** Verbose-режим. В редакторе сообщения коммита ниже строки-«ножниц» `# ------------------------ >8 ------------------------` показан diff — тот же, что даёт `git diff --cached`. Это просто справка: всё ниже этой строки в само сообщение не попадёт. Включить навсегда: `git config commit.verbose true`.

2. **Ограничение по путям.** `git diff master feature -- app.py` покажет разницу только по одному файлу, не трогая остальные изменённые.

3. **`--` перед путём.** Нужен, когда имя файла совпадает с именем ветки или тега — иначе git не может понять, что перед ним, и падает с ошибкой:

```
$ git diff app.py
fatal: ambiguous argument 'app.py': both revision and filename
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'
```

`git diff -- app.py` при этом отрабатывает без ошибок: `--` явно говорит git, что дальше идут пути, а не ссылки на коммиты.

4. **`--name-only` и `--stat`.** `--name-only` выводит только список изменённых файлов, без содержимого правок. `--stat` — компактную сводку с числом добавленных и удалённых строк по каждому файлу:

```
$ git diff master feature --stat
 README.md | 1 +
 app.py    | 2 +-
 2 files changed, 2 insertions(+), 1 deletion(-)
```

5. **Сравнение файла между коммитами.** `git diff master:app.py feature:app.py` — синтаксис `<коммит>:<путь>` указывает на версию файла в конкретном коммите, можно сравнить версии из любых двух коммитов, не обязательно соседних по истории.

6. **`--no-index`.** `git diff --no-index file1.txt file2.txt` сравнит два произвольных файла на диске тем же движком, что и обычный `git diff` — даже если ни один из них не имеет отношения к git-репозиторию.
