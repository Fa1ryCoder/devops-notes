# 7.5 Git – Слияние – Полезный приём: сохранение веток с флагом --no-ff

## 1. Суть и назначение флага --no-ff

Если в целевой ветке с момента ответвления не появилось новых коммитов, `git merge` по умолчанию не создаёт отдельный коммит слияния — указатель целевой ветки просто передвигается на последний коммит вливаемой ветки. Это называется fast-forward слиянием, или «перемоткой». Например, `feature` ушла от `master` на два коммита, а сам `master` с этого момента не менялся:

```bash
git log --oneline --graph --decorate master feature
```
```
* 252f56e (feature) feature: добавляем line3
* 5c801ac feature: добавляем line2
* b4ed470 (HEAD -> master) base: создание файла
```

`master` стоит на общем предке, `feature` ушла на два коммита вперёд, новых коммитов на `master` за это время не появилось — условие для перемотки выполнено:

```bash
git merge feature
```
```
Updating b4ed470..252f56e
Fast-forward
 file.txt | 2 ++
 1 file changed, 2 insertions(+)
```

`master` теперь указывает туда же, куда и `feature`:

```bash
git log --oneline --graph --decorate master feature
```
```
* 252f56e (HEAD -> master, feature) feature: добавляем line3
* 5c801ac feature: добавляем line2
* b4ed470 base: создание файла
```

Флаг `--no-ff` (no fast-forward) отключает это поведение: даже когда перемотка технически возможна, Git создаёт коммит слияния с двумя родителями, а указатель `master` получает новый коммит вместо того, чтобы просто переместиться на коммит `feature`.

## 2. Проблемы слияния «перемоткой»

В примере выше коммиты `feature: добавляем line2` и `feature: добавляем line3` после перемотки ничем не отличаются от обычных коммитов `master` — общая линия, общий указатель. На двух коммитах это ещё можно понять по одним сообщениям, но в проекте, где через `master` прошли десятки веток, определить по структуре истории, где заканчивается работа над одной фичей и начинается другая, уже не получится.

Отсюда вторая проблема. Если после такого слияния в фиче находят критическую ошибку, единой точки, которую можно было бы просто отменить, в истории не появляется — сам факт слияния нигде не зафиксирован. Приходится вручную определять, какие именно коммиты относятся к нужной фиче, и откатывать их по отдельности или подбирать диапазон.

## 3. Преимущества --no-ff

`--no-ff` устраняет обе проблемы: Git создаёт коммит слияния всегда, и коммиты `feature` остаются в истории отдельной линией вместо того, чтобы сливаться в общую с `master`.

После сброса `master` обратно на `b4ed470` и повторного слияния с этим флагом:

```bash
git reset --hard b4ed470
```
```
HEAD is now at b4ed470 base: создание файла
```

```bash
git merge --no-ff feature --no-edit
```
```
Merge made by the 'ort' strategy.
 file.txt | 2 ++
 1 file changed, 2 insertions(+)
```

```bash
git log --oneline --graph --decorate master feature
```
```
*   f154e75 (HEAD -> master) Merge branch 'feature'
|\  
| * 252f56e (feature) feature: добавляем line3
| * 5c801ac feature: добавляем line2
|/  
* b4ed470 base: создание файла
```

Теперь видно то, чего не было при перемотке: два коммита `feature` остаются на отдельной линии графа, слияние зафиксировано коммитом `f154e75`, и метка `feature` всё ещё показывает, где заканчивается история этой ветки.

Из этой же структуры следует и простая отмена. Сразу после слияния `ORIG_HEAD` указывает туда же, куда указывал `master` перед вливанием `feature`, и слияние убирается одним сбросом:

```bash
git reset --hard ORIG_HEAD
```
```
HEAD is now at b4ed470 base: создание файла
```

При перемотке `ORIG_HEAD` тоже сохранился бы сразу после операции, но проблема не в этом моменте, а в том, что происходит позже: если `ORIG_HEAD` к тому времени уже перезаписан чем-то другим, точку отмены найти будет негде — в истории нет коммита слияния, который отмечал бы, где начиналась `feature`.

## 4. Настройка конфигурации

Чтобы не указывать `--no-ff` в каждой команде, поведение можно закрепить в конфигурации.

Глобально для всех слияний отвечает параметр `merge.ff`:

```bash
git config merge.ff false
```

После сброса `master` на `b4ed470` обычный `git merge`, без единого флага в самой команде, теперь ведёт себя как `--no-ff`:

```bash
git merge feature --no-edit
```
```
Merge made by the 'ort' strategy.
 file.txt | 2 ++
 1 file changed, 2 insertions(+)
```

Для конкретной ветки то же самое настраивается через `branch.<имя_ветки>.mergeoptions`:

```bash
git config branch.master.mergeoptions "--no-ff"
```

Опция попадает в `.git/config` отдельной секцией:

```
[branch "master"]
	mergeoptions = --no-ff
```

и так же заставляет `git merge feature` на этой ветке создавать коммит слияния без явного флага в команде.

Оба варианта можно переопределить прямо в вызове команды: флаги, указанные в самой команде, всегда имеют приоритет над настройками из файла конфигурации. Достаточно явно передать `--ff`:

```bash
git merge --ff feature
```
```
Updating b4ed470..252f56e
Fast-forward
 file.txt | 2 ++
 1 file changed, 2 insertions(+)
```

Слияние прошло перемоткой, несмотря на `merge.ff false` в конфигурации — то же самое сработает и для `mergeoptions`.
