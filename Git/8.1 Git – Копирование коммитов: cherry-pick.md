# 8.1. Git — копирование коммитов: cherry-pick

## Часть 1. Что такое cherry-pick и как он работает

`git cherry-pick` берёт изменения одного существующего коммита — диф между этим коммитом и его родителем — и применяет их поверх текущей ветки, создавая новый коммит. Автор, его email и исходная дата автора сохраняются из коммита-источника, а дата коммита и родитель — новые, соответствующие месту и моменту применения. Текст сообщения коммита остаётся тем же, если не указано иное.

В отличие от merge, который сливает ветку целиком, cherry-pick переносит только выбранные изменения — например, исправление бага из ветки, где остальная работа ещё не завершена.

Хеш нужного коммита можно найти, посмотрев историю исходной ветки:

```
(master) $ git log --oneline feature
```
```
8e485da Исправить обработку ошибок в b.txt
83ab28c Добавить вторую строку в a.txt
b20aca6 Добавить a.txt
```

Переключаемся на ветку, куда нужно перенести изменения, и переносим коммит по хешу:

```
(feature) $ git switch master
(master) $ git cherry-pick 8e485da
```
```
[master d6f181a] Исправить обработку ошибок в b.txt
 1 file changed, 1 insertion(+)
 create mode 100644 b.txt
```

```
(master) $ git log --oneline --graph --decorate master feature
```
```
* d6f181a (HEAD -> master) Исправить обработку ошибок в b.txt
| * 8e485da (feature) Исправить обработку ошибок в b.txt
| * 83ab28c Добавить вторую строку в a.txt
|/
* b20aca6 Добавить a.txt
```

### Синтаксис

Базовая форма — коммит указывается, когда вы уже находитесь на той ветке, куда нужно перенести изменения:

```
git cherry-pick <хеш-коммита>
```

Можно передать несколько коммитов подряд — они применяются по одному, в указанном порядке:

```
git cherry-pick <хеш1> <хеш2> <хеш3>
```

### Флаг -x

При переносе изменений между долгоживущими ветками — например, из хотфикса в master и в develop — полезно сохранить в сообщении ссылку на исходный коммит. Флаг `-x` добавляет её автоматически:

```
(hotfix-x) $ git cherry-pick -x feature~1
```
```
Добавить вторую строку в a.txt

(cherry picked from commit 83ab28cf472264741023f1ff8eaefe7cdd1f9905)
```

Это упрощает поиск: увидев коммит в истории одной ветки, легко найти, откуда именно он был перенесён.

### Флаг -n (--no-commit)

Флаг `-n` применяет изменения к индексу и рабочей директории, но не создаёт коммит:

```
(hotfix-n) $ git cherry-pick -n feature~1
(hotfix-n) $ git status
```
```
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   a.txt
```

Это удобно, если нужно объединить несколько переносимых коммитов в один или что-то поправить руками перед фиксацией.

### Копирование merge-коммита

У merge-коммита несколько родителей, поэтому Git не может сам решить, относительно какого из них считать изменения — без уточнения команда завершается ошибкой:

```
(merge-cherry-target) $ git cherry-pick 09796b2
```
```
error: commit 09796b27941c8735073a92e7cab76d4e5814cf34 is a merge but no -m option was given.
fatal: cherry-pick failed
```

Флаг `-m <номер>` (или `--mainline <номер>`) задаёт, какой родитель считать основным: номер — это порядковая позиция родителя в самом merge-коммите, начиная с 1. В новый коммит попадает то, что привнёс родитель с другим номером:

```
(merge-cherry-target) $ git cherry-pick -m 1 09796b2
```
```
[merge-cherry-target 20c2e42] Merge branch 'merge-side' into merge-base
 1 file changed, 1 insertion(+)
 create mode 100644 y.txt
```

```
(merge-cherry-target2) $ git cherry-pick -m 2 09796b2
```
```
[merge-cherry-target2 cd78871] Merge branch 'merge-side' into merge-base
 1 file changed, 1 insertion(+)
 create mode 100644 x.txt
```

Номер легко перепутать, а Git никак на это не укажет — cherry-pick молча перенесёт не те изменения. Перед использованием `-m` стоит явно посмотреть порядок родителей через `git log` или `git show`.

### Особенности истории после cherry-pick

Новый коммит не связан по родителям с оригиналом, поэтому команды, которые ходят по истории через эту связь, не находят между ними ничего общего. `git branch --contains` для исходного коммита не покажет ветку, куда изменение было перенесено, хотя по содержимому оно там уже есть:

```
(master) $ git branch --contains 8e485da
```
```
  feature
```

```
(master) $ git log --oneline --all -- b.txt
```
```
d6f181a Исправить обработку ошибок в b.txt
8e485da Исправить обработку ошибок в b.txt
```

Если попытаться перенести изменение, которое в целевой ветке уже есть, Git сравнивает получившийся диф и обнаруживает, что применять нечего:

```
(master) $ git cherry-pick 8e485da
```
```
The previous cherry-pick is now empty, possibly due to conflict resolution.
If you wish to commit it anyway, use:

    git commit --allow-empty

Otherwise, please use 'git cherry-pick --skip'
```

Проверить заранее, какие коммиты одной ветки ещё не перенесены в другую, можно командой `git cherry` — она сравнивает не хеши, а содержимое изменений (patch-id), и помечает уже перенесённые коммиты знаком `-`, а не перенесённые — знаком `+`:

```
(master) $ git cherry -v master feature
```
```
+ 83ab28cf472264741023f1ff8eaefe7cdd1f9905 Добавить вторую строку в a.txt
- 8e485da3577eab2b89e6e5f1c4f6ad3ae36177c8 Исправить обработку ошибок в b.txt
```

## Часть 2. Разрешение конфликтов

Cherry-pick использует тот же механизм трёхстороннего слияния, что и merge, поэтому конфликты возникают в той же ситуации: переносимый коммит и текущая ветка изменили одни и те же строки по-разному.

```
(conflict-demo-master) $ git cherry-pick bb7d15b
```
```
Auto-merging a.txt
CONFLICT (content): Merge conflict in a.txt
```

`git status` в этот момент показывает, на каком коммите произошла остановка, какие файлы конфликтуют и доступные команды:

```
On branch conflict-demo-master
You are currently cherry-picking commit bb7d15b.
  (fix conflicts and run "git cherry-pick --continue")
  (use "git cherry-pick --skip" to skip this patch)
  (use "git cherry-pick --abort" to cancel the cherry-pick operation)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   a.txt
```

Внутри конфликтующего файла — привычные маркеры: между `<<<<<<< HEAD` и `=======` — версия текущей ветки, между `=======` и `>>>>>>>` — версия из переносимого коммита:

```
<<<<<<< HEAD
правка на мастере
=======
правка из другой ветки
>>>>>>> bb7d15b (Переписать a.txt в отдельной ветке)
```

Файл правится вручную: маркеры удаляются, остаётся нужный код. После этого файл добавляется в индекс, и перенос продолжается:

```
(conflict-demo-master) $ git add a.txt
(conflict-demo-master) $ git cherry-pick --continue
```

При `--continue` Git открывает редактор с сообщением коммита — его можно оставить как есть или изменить; чтобы завершить без редактора, есть `--no-edit`.

В отличие от merge, во время конфликта cherry-pick HEAD не сдвигается — он остаётся на коммите, с которого начали, пока итоговый коммит не будет создан. Поэтому `--abort` отменяет незавершённую операцию и возвращает рабочую директорию в исходное состояние, без необходимости куда-либо возвращать HEAD. Команда `--quit` в этом смысле мягче: она прекращает отслеживание процесса cherry-pick, но оставляет файлы как есть — с маркерами конфликта и незавершённым слиянием в индексе, если конфликт не был разрешён.

Если переносится несколько коммитов и один из них конфликтует, а сам по себе не нужен, его можно пропустить — Git перейдёт к следующему коммиту и применит оставшиеся автоматически:

```
(skip-demo) $ git cherry-pick --skip
```
```
[skip-demo eb7d4b4] Добавить d.txt
[skip-demo 2243a9a] Добавить e.txt
```

### Незакоммиченные изменения

Если в рабочей директории есть незафиксированные изменения в файлах, которые затрагивает переносимый коммит, cherry-pick прерывается сразу, не начиная перенос:

```
(master) $ git cherry-pick 83ab28c
```
```
error: Your local changes to the following files would be overwritten by merge:
	a.txt
Please commit your changes or stash them before you merge.
Aborting
fatal: cherry-pick failed
```

Варианта два: закоммитить эти изменения или временно спрятать их через `git stash`, выполнить cherry-pick и вернуть их обратно командой `git stash pop`. Во втором случае стоит учитывать: если перенесённый коммит и спрятанные правки трогают одни и те же строки, конфликт возникнет уже на этапе `git stash pop` — и разрешать его придётся так же вручную.
