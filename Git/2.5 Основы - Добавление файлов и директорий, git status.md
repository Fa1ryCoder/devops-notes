## 1. Особенности работы с директориями

Git по историческим причинам **не умеет работать с пустыми директориями** — он их просто не видит. Причина в объектной модели Git: файлы хранятся как объекты `blob` (от Binary Large Object — способ Git хранить содержимое файла внутри своей базы данных), а папки — как объекты `tree` (список ссылок на другие `tree` или `blob`). Объект `tree` не может существовать в коммите если он пустой и не ссылается ни на один `blob` — Git просто не создаёт такой объект.

> Подробнее про объектную модель (blob, tree, commit) разберём в отдельной теме.

```bash
mkdir empty-dir
git status
# ничего не покажет — Git не видит пустую папку
```

### Как обойти это ограничение

Чтобы Git начал отслеживать папку — она должна быть не пустой. Общепринятое решение — добавить в неё вспомогательный файл нулевого размера `.gitkeep`:

```bash
mkdir configs
touch configs/.gitkeep
git status
# Untracked files: configs/
```

`.gitkeep` — это просто договорённость в индустрии, Git не знает о нём ничего особенного. Файл может называться как угодно, но `.gitkeep` стал стандартом де-факто.

### Как git status отображает директории

Если в проекте появляется новая директория с файлами — `git status` покажет только саму директорию, не перечисляя каждый файл внутри:

```bash
mkdir src
touch src/main.go src/utils.go src/config.go
git status
# Untracked files:
#   src/
```

Git предполагает что всё содержимое внутри директории также неизвестно ему.

## 2. Команда git add

Мы уже знаем что `git add` переводит файл в состояние `staged`. Но у команды есть несколько вариантов использования — и важный нюанс при работе с `git add .` о котором нужно знать заранее.

### Добавление файлов

```bash
# Добавить конкретный файл
git add app.py

# Добавить несколько файлов
git add app.py config.py

# Добавить всю директорию
git add src/

# Добавить все изменения в текущем каталоге
git add .
```

### Разница между git add . / git add -A / git add -u

Это классический вопрос на собеседованиях Middle+:

**`git add .`** — добавляет всё в текущей директории и вложенных папках. Если запустить не из корня репозитория — файлы выше по дереву не затронет. Требует осторожности — вместе с нужными файлами в индекс попадут служебные файлы редакторов и IDE. Чтобы исключить лишние файлы заранее — используется `.gitignore` (подробнее в разделе 3):

```bash
git add .
git status
# Changes to be committed:
#   new file: app.py
#   new file: .idea/workspace.xml      ← служебный файл WebStorm
#   new file: .vscode/settings.json    ← служебный файл VS Code
```

**`git add -A`** (`--all`) — добавляет абсолютно всё во всём репозитории независимо от того в какой директории запущена команда.

**`git add -u`** (`--update`) — добавляет только изменения в уже отслеживаемых файлах (modified и deleted). Новые `untracked` файлы игнорирует.

## 3. Игнорирование файлов — .gitignore

Чтобы Git не отслеживал лишние файлы — служебные папки IDE, временные файлы, секреты — в корне проекта создаётся файл `.gitignore`. В него записываем всё что Git должен игнорировать:

```gitignore
# Служебные папки IDE
.idea/
.vscode/

# Зависимости
node_modules/
vendor/

# Временные файлы
*.log
*.tmp

# Переменные окружения (секреты!)
.env
.env.local
```

```bash
git add .
git status
# Changes to be committed:
#   new file: app.py        ← добавлен
#   new file: .gitignore    ← добавлен
# .idea/ и .vscode/ — не показываются, Git их игнорирует
```

### Принудительное добавление игнорируемого файла

Даже если файл указан в `.gitignore` — его можно принудительно добавить в индекс через флаг `-f` (`--force`):

```bash
git add -f .env
```

После этого Git будет отслеживать изменения в нём в обычном режиме независимо от правил в `.gitignore`.

### Что делать если файл уже отслеживается

Правила в `.gitignore` работают **только для неотслеживаемых (`untracked`) файлов**. Если файл (например, `.env`) уже был однажды закоммичен в репозиторий — последующее добавление его в `.gitignore` ничего не изменит. Git продолжит отслеживать в нём изменения.

Чтобы перестать отслеживать файл но **сохранить его на локальном диске** — нужно удалить его из индекса:

```bash
# Удалить файл из индекса, оставив его в рабочей директории
git rm --cached .env

# Удалить целую папку из индекса (например, случайно закоммиченную .idea/)
git rm -r --cached .idea/
```

После этого нужно сделать коммит. Файл перейдёт в статус `untracked` и начнёт успешно игнорироваться `.gitignore`.

## 4. Как работает индекс

Когда ты выполняешь `git add` — Git сохраняет в индекс не просто имя файла, а **снимок его содержимого на этот момент**.

Это важно понимать: если ты изменил файл после `git add` но до `git commit` — `git status` покажет этот файл в **двух секциях** одновременно:

```bash
echo "line 1" > app.py
git add app.py          # сохранили снимок в индексе

echo "line 2" >> app.py # изменили файл после add

git status
# Changes to be committed:        ← версия на момент git add
#   modified: app.py
#
# Changes not staged for commit:  ← новые изменения после git add
#   modified: app.py
```

В коммит попадёт именно та версия файла которая была в индексе на момент `git add` — строка "line 1". Строка "line 2" в коммит не войдёт.

Чтобы включить новые изменения в коммит — нужно снова выполнить `git add app.py`.

## 5. Отмена индексации — git reset

Если случайно добавил в индекс лишние файлы — можно убрать их из индекса.

Старый синтаксис (работает во всех версиях Git):
```bash
# Убрать конкретный файл из индекса
git reset HEAD <file>

# Убрать все файлы из индекса сразу
git reset HEAD
```

`HEAD` здесь — указатель на последний коммит. Команда сбрасывает файл в индексе до состояния последнего коммита — то есть убирает его из staged обратно в `modified` или `untracked`.

Современный синтаксис (Git 2.23+, читается понятнее):
```bash
# Убрать конкретный файл из индекса
git restore --staged <file>

# Убрать все файлы из индекса сразу
git restore --staged .
```

`--staged` означает что работаем с файлом именно в индексе, а не в рабочей директории. Файл остаётся в рабочей директории — только из индекса убирается, изменения не теряются.

```bash
git add .                      # случайно добавили всё включая .idea/
git restore --staged .idea/    # убрали .idea/ из индекса
git status
# Changes to be committed:
#   new file: app.py            ← остался в индексе
# Untracked files:
#   .idea/                      ← вернулся в untracked
```

## 6. git status — три состояния

`git status` показывает три группы файлов одновременно:

```bash
git status
```

```
Changes to be committed:          ← 1. В индексе (staged)
  new file: app.py
  modified: config.py

Changes not staged for commit:    ← 2. Изменены, но не в индексе (modified)
  modified: main.py

Untracked files:                  ← 3. Не отслеживаются (untracked)
  README.md
```

| Секция | Статус | Что значит |
|--------|--------|------------|
| `Changes to be committed` | `staged` | Войдут в следующий коммит |
| `Changes not staged for commit` | `modified` | Изменены после последнего `git add` |
| `Untracked files` | `untracked` | Git о них не знает — ни разу не добавлялись через `git add` |

### Полный цикл состояний файла

`untracked` бывает только один раз — при первом появлении файла. После первого `git add` файл навсегда становится отслеживаемым. `git push` не влияет на состояния файлов — он только синхронизирует историю коммитов с удалённым репозиторием:

```
touch README.md        →  untracked  (новый файл, Git не знает о нём)
git add README.md      →  staged     (добавлен в индекс)
git commit             →  committed  (сохранён в истории)
git push               →  committed  (push не меняет состояние файлов)
vim README.md          →  modified   (изменён после коммита)
git add README.md      →  staged     (снова добавлен в индекс)
git commit             →  committed  (сохранена новая версия)
git push               →  committed
```

Когда все изменения закоммичены и нет новых файлов:

```bash
git status
# On branch main
# nothing to commit, working tree clean
```
