# 7. Модульность и связи между проектами

## include: local / project / remote / template

`include` подключает в pipeline конфигурацию из других файлов.

Без него вся конфигурация живёт в одном `.gitlab-ci.yml`, который разрастается с каждой новой job, а одинаковые куски конфигурации приходится копировать в другие проекты вручную. Источник подключаемого файла определяется одним из четырёх ключей.

### local

Файл из того же репозитория:

```yaml
include:
  - local: '/ci/build.yml'
  - local: '/ci/test.yml'
```

### project

Файл из другого проекта на том же GitLab:

```yaml
include:
  - project: 'my-group/ci-templates'
    ref: main
    file: '/templates/deploy.yml'
```

`ref` необязателен — по умолчанию берётся default branch указанного проекта. Чтобы include сработал, у пайплайна должен быть доступ на чтение к этому проекту.

### remote

Файл по произвольному HTTP(S)-адресу, который отдаёт чистый YAML:

```yaml
include:
  - remote: 'https://raw.githubusercontent.com/my-org/ci-configs/main/base.yml'
```

### template

Готовые шаблоны, которые идут в комплекте с самим GitLab:

```yaml
include:
  - template: 'Auto-DevOps.gitlab-ci.yml'
```

Несколько include любых типов можно комбинировать в одном массиве. Если один и тот же job определён в нескольких include, её параметры мёрджатся, как при extends — конфликтующие ключи берёт более поздний include, остальные сохраняются. С `stages:` иначе: это список, а не хэш, поэтому он не мёрджится — если `stages:` объявлен в нескольких файлах, побеждает только один, полностью перезаписывая остальные. Поэтому `stages:` обычно объявляют один раз, в основном `.gitlab-ci.yml`, со всеми stage, которые вообще используются job из всех подключённых файлов. Дальше порядок выполнения работает как в едином файле — по позиции stage в этом списке и по `needs`, если он задан; из какого файла физически приехала job, значения не имеет. `include` также поддерживает `rules:` — файл можно подключать только при выполнении условия, как обычную job. Циклический include (файл A подключает B, а B подключает A) — ошибка, GitLab это отследит и остановит сборку конфигурации.

## extends — DRY (Don't Repeat Yourself)

`extends` переиспользует конфигурацию job, не копируя её вручную.

Без него одинаковые куски конфигурации (image, tags, before_script) приходится дублировать в каждой job, и при изменении легко забыть поправить не во всех местах.

`extends` наследует для job конфигурацию от одной или нескольких «шаблонных» job.

Шаблонные job обычно скрывают — имя начинают с точки, тогда GitLab не запускает их как отдельную job, они существуют только как источник для extends. Наследоваться можно и от обычной, не скрытой job — тогда она выполнится в pipeline сама по себе, плюс отдельно отработает job, которая от неё унаследовалась.

`extends` работает даже если шаблон и job, которая от него наследуется, лежат в разных include-файлах — GitLab сначала объединяет всю конфигурацию через include, и только потом резолвит extends:

```yaml
.test_template:
  image: python:3.11
  stage: test
  before_script:
    - pip install -r requirements.txt

unit_tests:
  extends: .test_template
  script:
    - pytest tests/unit

integration_tests:
  extends: .test_template
  script:
    - pytest tests/integration
```

Можно наследовать сразу от нескольких шаблонов: `extends: [.template_one, .template_two]`. При конфликте ключей побеждает значение, указанное позже: если job наследует от нескольких шаблонов — побеждает более поздний в списке шаблон; если ключ задан и в шаблоне, и в самой job — побеждает job:

```yaml
.test_template:
  image: python:3.11
  before_script:
    - pip install -r requirements.txt

unit_tests:
  extends: .test_template
  image: python:3.12
  before_script:
    - echo "custom setup"
```

`unit_tests` выполнится с `image: python:3.12` — значение перезаписывается. С `before_script` работает то же самое правило: итоговый `before_script` — это только `echo "custom setup"`, шаг `pip install -r requirements.txt` из шаблона пропадает целиком. С массивами это менее очевидно — кажется, что элементы должны сложиться вместе, но правило одно и то же для любых ключей, включая `script` и `tags`: полная замена, а не объединение.

Отдельно стоит знать про `!reference` — способ переиспользовать не всю job целиком, а конкретный ключ из другой job. Синтаксис: `!reference [имя_job, ключ]` — указывается, у какой job и какой именно ключ забрать:

```yaml
.setup:
  before_script:
    - echo "setup"

test:
  before_script:
    - !reference [.setup, before_script]
    - echo "running tests"
```

## needs — вместо жёсткой последовательности стадий

`needs` — директива, которая задаёт жёсткие зависимости между job. Она указывает, что job не должна стартовать, пока не завершатся перечисленные в `needs` job.

Без `needs` GitLab ждёт всю стадию целиком, даже если job на самом деле зависит только от одной job из неё. Например, если в стадии `test` десять job, а конкретной job нужен результат только одной из них, без `needs` она будет ждать все десять — хотя девять из них ей вообще не нужны. С `needs: [нужная-job]` она стартует сразу, как только выполнится именно эта одна, не дожидаясь остальных девяти.

`needs` не меняет сам порядок стадий — он убирает лишнее ожидание внутри них, распараллеливая то, что реально можно выполнять параллельно.

```yaml
stages:
  - build
  - test

build_backend:
  stage: build
  script: echo "build backend"

build_frontend:
  stage: build
  script: echo "build frontend"

test_backend:
  stage: test
  needs: ["build_backend"]
  script: echo "test backend"

lint:
  stage: test
  needs: []
  script: echo "не зависит ни от чего"
```

`test_backend` стартует сразу после `build_backend`, не дожидаясь `build_frontend`. `lint` с `needs: []` вообще ничего не ждёт и стартует параллельно со стадией build.

Важное ограничение: `needs` может ссылаться только на job из той же или более ранней стадии. Сослаться на job из более поздней стадии нельзя — GitLab выдаст ошибку `is not defined in current or prior stages`.

Стадии при этом можно вообще не объявлять — pipeline целиком на `needs` тоже валиден, GitLab сам выстроит порядок выполнения по графу зависимостей.

`needs` заодно автоматически передаёт артефакты: job скачивает артефакты от job, перечисленных в `needs`, без всякой дополнительной настройки — но только от них, а не от всех job предыдущих стадий, как было бы по умолчанию — экономия времени, если артефакты большие. Отключить скачивание артефактов от конкретной зависимости:

```yaml
test_backend:
  needs:
    - job: build_backend
      artifacts: false
```

Частый вопрос на собесе — разница между `needs` и `dependencies`: `dependencies` только ограничивает, какие артефакты скачивать, но не меняет порядок выполнения (job всё равно ждёт всю предыдущую стадию целиком). `needs` меняет и порядок выполнения, и правила скачивания артефактов одновременно. Смешивать `needs` и `dependencies` в одной job не стоит.

Ещё один частый баг: если job, указанная в `needs`, не попадает в pipeline — например, её отсеяло условием в `rules` — сборка pipeline упадёт с ошибкой ещё до старта. Чтобы такая зависимость была необязательной, нужно явно пометить её `optional: true`:

```yaml
test_backend:
  needs:
    - job: build_backend
      optional: true
```

## Multi-project pipelines и trigger

`trigger` — ключевое слово, которое вместо обычного script запускает другой pipeline. Такая job называется bridge job.

Запуск pipeline в другом проекте: `project:` — путь до целевого проекта, `branch:` — ветка, на которой должен собраться запущенный pipeline (необязательна, по умолчанию берётся default branch целевого проекта):

```yaml
deploy:
  stage: deploy
  trigger:
    project: my-group/deployment-project
    branch: main
```

По умолчанию bridge job получает статус `passed`, как только запущенный через `trigger` pipeline стартовал — не дожидаясь его завершения. Чтобы родительский pipeline реально ждал результата и отражал его статус, нужно добавить `strategy: depend`:

```yaml
deploy:
  stage: deploy
  trigger:
    project: my-group/deployment-project
    branch: main
    strategy: depend
```

Аутентификация между проектами при таком trigger идёт через `CI_JOB_TOKEN` — какие проекты можно триггерить и к каким API обращаться, настраивается в Settings → CI/CD → Job token permissions. Важно: allowlist настраивается на стороне того проекта, к которому обращаются, а не на стороне того, кто триггерит. То есть если `api-python` триггерит `deployment-project`, allowlist с `api-python` добавляется в настройках именно `deployment-project`.

Из текущего pipeline можно передать переменные в запущенный через `trigger` — прямо из trigger-job:

```yaml
deploy:
  stage: deploy
  trigger:
    project: my-group/deployment-project
    branch: main
  variables:
    VERSION: $CI_COMMIT_SHORT_SHA
```

## Итог

`include` и `extends` убирают дублирование конфигурации — один и тот же YAML не нужно копировать в десять job или десять проектов. `needs` убирает дублирование по времени — job выполняются параллельно, как только готовы их реальные зависимости, а не по границам стадий. `trigger` позволяет разложить один гигантский pipeline на несколько связанных вместо одного нечитаемого файла.

Конфиг не дублируется, стадии выполняются эффективнее.
