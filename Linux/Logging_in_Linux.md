Логирование — это фундаментальный механизм наблюдаемости (observability) за системой. Когда сервис падает в 3 часа ночи, единственное, что позволяет восстановить картину произошедшего — это логи. Логируются не только прикладные сервисы и приложения, но и:
- ядро системы Linux (загрузка драйверов, обнаружение оборудования, ошибки ядра);
- события аутентификации и авторизации (удачные/неудачные попытки входа, sudo, ssh);
- установка и удаление пакетов (dpkg, apt);
- работа cron-задач, состояние сети, монтирование файловых систем и многое другое.

## Путь сообщения: от ядра до файла

Представим, что вставили флешку в компьютер. Драйвер USB обнаруживает устройство и ядро с помощью функции `printk()` пишет сообщение в **кольцевой буфер ядра** (Kernel Ring Buffer) — область в оперативной памяти фиксированного размера. При переполнении старые сообщения перезаписываются новыми.

Далее демон `systemd-journald` читает этот буфер и записывает данные в бинарные структурированные логи. Параллельно (если установлен и настроен) `rsyslog` или `syslog-ng` могут принимать сообщения и записывать их в привычные текстовые файлы.

```
[ ЖЕЛЕЗО / СОБЫТИЕ ]
          │
          ▼
 [ ЯДРО (Kernel Space) ] ──▶ Функция printk()
          │
          ▼
 [ Kernel Ring Buffer (RAM) ] ◀── Команда dmesg читает отсюда
          │
          ▼
 [ systemd-journald ] ◀────────── Команда journalctl читает отсюда
          │
          ├──────────────────────────────┐
          ▼                              ▼
 [ Бинарные логи ]              [ rsyslog / syslog-ng ]
 /var/log/journal/                       │
                                         ▼
                                [ Текстовые логи ]
                                /var/log/syslog
                                /var/log/auth.log
                                /var/log/kern.log
```

> **Важно:** На современных системах с systemd текстовые логи (`syslog`, `auth.log`, `kern.log`) являются опциональными — они появляются только если установлен и настроен `rsyslog`. Всё то же самое можно просматривать через `journalctl`. Эти файлы сохраняются для совместимости со старыми инструментами и скриптами.

## Уровни серьёзности (Severity Levels)

Прежде чем разбирать конкретные файлы и утилиты, необходимо понять концепцию **уровней серьёзности** (severity levels). Это числовой приоритет сообщения, определённый в стандарте RFC 5424. Без понимания этих уровней невозможно разобраться с правилами rsyslog и фильтрацией в journalctl.

| Код | Название   | Описание                                                              |
|-----|------------|-----------------------------------------------------------------------|
| 0   | `emerg`    | Система нестабильна, требуется немедленное вмешательство              |
| 1   | `alert`    | Необходимо срочное действие                                           |
| 2   | `crit`     | Критическое состояние                                                 |
| 3   | `err`      | Ошибка (нормальная работа нарушена)                                   |
| 4   | `warning`  | Предупреждение (работа продолжается, но требует внимания)             |
| 5   | `notice`   | Нормальное, но значимое событие                                       |
| 6   | `info`     | Информационное сообщение                                              |
| 7   | `debug`    | Отладочная информация                                                 |

Достаточно запомнить крайние точки шкалы: `0 = emerg` (система упала) и `7 = debug` (максимальная детализация).

> **Правило наследования в rsyslog:** Указание уровня в правиле означает "этот уровень **и всё выше**" (то есть более серьёзное). Например, `kern.warning` — это warning, err, crit, alert, emerg. Чтобы указать **строго один** уровень, используется `=`: `kern.=warning`. Чтобы исключить уровень и выше — `!none`.

## Facilities (Источники сообщений в syslog)

Помимо уровня серьёзности, каждое сообщение syslog имеет **facility** — идентификатор источника. Это позволяет rsyslog направлять сообщения от разных подсистем в разные файлы.

| Facility   | Источник                                      |
|------------|-----------------------------------------------|
| `kern`     | Ядро Linux                                    |
| `user`     | Пользовательские процессы                    |
| `mail`     | Почтовая подсистема                           |
| `daemon`   | Системные демоны (без собственного facility)  |
| `auth`     | Аутентификация и безопасность                 |
| `syslog`   | Внутренние сообщения syslogd                  |
| `lpr`      | Подсистема печати                             |
| `cron`     | Планировщик задач (cron, at)                  |
| `authpriv` | Приватные сообщения аутентификации (SSH и др.)|
| `local0`–`local7` | Зарезервированы для пользовательских приложений |

Запись лога состоит из: `<facility>.<severity> сообщение`. Например, запись ядра об ошибке: `kern.err`.

## Форматы логов: JSON vs Plain Text

Прежде чем перейти к конфигурированию, важно понять фундаментальный выбор, с которым сталкивается каждое приложение: в каком формате писать логи.

### Plain Text: проблемы классического подхода

Традиционный формат лога выглядит так:

```
May 20 14:32:11 web-01 nginx: 192.168.1.5 - - [20/May/2024:14:32:11 +0000] "GET /api/users HTTP/1.1" 500 312
May 20 14:32:12 web-01 app: ERROR Failed to connect to database: connection refused (attempt 3/5)
```

Формат у каждого приложения **свой**. Чтобы извлечь из этой строки IP-адрес, статус-код или имя сервиса, нужно писать регулярные выражения. Это означает:
- хрупкие парсеры, которые ломаются при малейшем изменении формата сообщения;
- сложность агрегации логов из разных приложений (у каждого свой формат);
- невозможность автоматически фильтровать по полям без предварительного парсинга;
- разработчик изменил формат строки — парсер на стороне Logstash/Loki сломался, логи перестали индексироваться.

### JSON: структурированное логирование

Современный подход — писать каждое событие как JSON-объект. Одна строка лога = один валидный JSON:

```json
{
  "timestamp": "2024-05-20T14:32:11.453Z",
  "level": "error",
  "service": "user-api",
  "host": "web-01",
  "trace_id": "4bf92f3577b34da6",
  "message": "Failed to connect to database",
  "error": "connection refused",
  "attempt": 3,
  "max_attempts": 5,
  "db_host": "postgres-primary.internal",
  "duration_ms": 5023
}
```

В реальности каждая запись пишется в одну строку (newline-delimited JSON, NDJSON):
```
{"timestamp":"2024-05-20T14:32:11.453Z","level":"error","service":"user-api","trace_id":"4bf92f3577b34da6","message":"Failed to connect to database","attempt":3}
```

**Почему JSON стал стандартом:**

Поля уже структурированы — никаких регулярных выражений. Системы сбора логов (Loki, Elasticsearch, Fluent Bit) читают JSON нативно и сразу индексируют по полям. Фильтрация `level=error AND service=user-api AND attempt>2` работает без парсинга. Добавление нового поля в лог (например, `region`) не ломает существующие запросы — они просто игнорируют незнакомые поля. Поле `trace_id` позволяет сквозным образом связать логи одного запроса через несколько микросервисов (distributed tracing). Поле `duration_ms` превращает лог в метрику — можно строить графики времени ответа прямо из логов.

## Конфигурирование rsyslog

Главный конфигурационный файл: `/etc/rsyslog.conf`. По хорошей практике, в нём указывается директива:

```bash
$IncludeConfig /etc/rsyslog.d/*.conf
```

И уже в директории `/etc/rsyslog.d/` создаются отдельные файлы под каждое приложение или сервис, например `my-cool-app.conf`. Это сохраняет основной конфиг чистым и позволяет легко добавлять/удалять правила.

**Синтаксис правила:**
```
facility.severity    /путь/к/файлу
```

**Примеры правил:**
```bash
# Все сообщения ядра уровня warning и выше → в kern.log
kern.warning         /var/log/kern.log

# Все auth-сообщения → в auth.log
auth,authpriv.*      /var/log/auth.log

# Строго только info сообщения от cron
cron.=info           /var/log/cron.log

# Всё, кроме debug → в syslog
*.info;mail.none;authpriv.none;cron.none  /var/log/syslog
```

**Шаблоны форматирования:** rsyslog позволяет задавать собственный формат записи через директиву `$template`.

## Основные файлы логов в /var/log/

### Debian/Ubuntu vs RHEL/CentOS

Важно знать, что имена файлов различаются в зависимости от дистрибутива:

| Событие                       | Debian/Ubuntu          | RHEL/CentOS/Fedora     |
|-------------------------------|------------------------|------------------------|
| Системный журнал (общий лог)  | `/var/log/syslog`      | `/var/log/messages`    |
| Аутентификация и безопасность | `/var/log/auth.log`    | `/var/log/secure`      |
| Сообщения ядра                | `/var/log/kern.log`    | включено в `messages`  |

---

### 1. /var/log/auth.log (Debian) / /var/log/secure (RHEL)

Содержит все события, связанные с аутентификацией, авторизацией и безопасностью:
- удачные и неудачные попытки входа в систему;
- использование `sudo` и `su` (кто, когда, какую команду);
- SSH-соединения (кто, с какого IP, успешно/нет);
- попытки смены пароля;
- локальный вход через терминал (tty).

Этот файл — первое место, куда смотрят при расследовании инцидентов безопасности (brute-force атаки, несанкционированный доступ).

---

### 2. /var/log/syslog (Debian) / /var/log/messages (RHEL)

Основной системный журнал — агрегирует сообщения из большинства источников: ядра, демонов, сетевых интерфейсов, пользовательских приложений. Именно здесь видна **хронологическая картина событий**: «В 10:00 упала сеть → в 10:01 ядро выдало ошибку драйвера → в 10:02 служба Nginx перестала работать». Специализированные логи (kern.log, auth.log) нужны, когда хочется сосредоточиться на конкретной подсистеме без шума от остальных.

> Обратите внимание: сообщения из auth.log и kern.log **дублируются** в syslog, поскольку rsyslog направляет их в несколько мест одновременно согласно своим правилам.

---

### 3. /var/log/kern.log

Лог-файл, создаваемый rsyslog, в который в режиме **реального времени** записываются сообщения ядра Linux. Ядро никогда не пишет напрямую в файлы — оно пишет в кольцевой буфер (Kernel Ring Buffer в RAM). Чтобы прочитать оттуда сообщения, у ядра есть два интерфейса доступа:

- **`/proc/kmsg`** — псевдофайл в procfs (`-r--------`, только root). Старый интерфейс. Это **destructive read**: прочитанное сообщение «потребляется» и недоступно другим процессам. Одновременно читать может только **один** процесс. Именно его традиционно использует `rsyslog` через модуль `imklog`.

- **`/dev/kmsg`** — символьное устройство (`crw-r--r--`, character device). Современный интерфейс (Linux 3.5+). Поддерживает **несколько читателей** одновременно (non-destructive read), поддерживает `poll()` — подписку на новые сообщения в реальном времени, а также **запись** в буфер ядра. Его используют `systemd-journald` и утилита `dmesg`.

Несмотря на одинаковое название, это **разные интерфейсы** с разной семантикой. Оба обращаются к одному источнику — кольцевому буферу ядра. `/proc/kmsg` — исторический интерфейс, который нельзя убрать ради обратной совместимости. `/dev/kmsg` — его современная замена.

```
Kernel  printk()
   │
   ▼
ring buffer (RAM)
   │          │
   │          └──▶ /dev/kmsg  (character device) ◀── systemd-journald, dmesg
   │
   └──────────────▶ /proc/kmsg (псевдофайл procfs) ◀── rsyslog (imklog)
                         │
                         ▼
                  /var/log/kern.log  ← обновляется в реальном времени
```

Здесь фиксируются: загрузка и выгрузка модулей ядра, ошибки драйверов во время работы, проблемы с оборудованием, сетевые ошибки уровня ядра. В отличие от `/var/log/dmesg`, этот файл обновляется на протяжении **всей работы системы**, а не только при загрузке.

---

### 4. /var/log/dmesg

Это **снимок (snapshot)** кольцевого буфера ядра на момент **загрузки системы**. Он создаётся однократно в процессе инициализации и не обновляется в процессе работы. Полезен для диагностики проблем, возникающих на ранних этапах загрузки: ошибок инициализации оборудования, проблем с драйверами до того, как rsyslog успел запуститься.

```
Kernel
   │
   ▼
ring buffer (RAM)
   │
   ▼  (при старте системы, однократно)
/var/log/dmesg  ← файл-снимок, далее не изменяется
```

**Важно понимать разницу:**
- `dmesg` (команда) — читает **текущее** содержимое кольцевого буфера напрямую из RAM, показывает актуальные сообщения.
- `/var/log/dmesg` (файл) — статичный снимок буфера **на момент загрузки**, не меняется.
- `journalctl -k` или `journalctl --dmesg` — показывает сообщения ядра через journald (предпочтительный способ на systemd-системах).

---

### 5. /var/log/boot.log

Записывает события процесса инициализации **пользовательского пространства (userspace)** — то есть того, что происходит после того, как ядро загрузилось и передало управление systemd. Сюда попадают: запуск и остановка systemd-юнитов, монтирование файловых систем, старт сетевых интерфейсов, запуск демонов.

> На современных systemd-системах этот файл может **отсутствовать**. Вместо него используйте `journalctl -b` (логи текущей загрузки) или `journalctl -b -1` (логи предыдущей загрузки). boot.log появляется только если установлен и настроен соответствующий скрипт или sysvinit-совместимый initscript.

---

### 6. /var/log/dpkg.log

Основной лог **низкоуровневой** работы с пакетами. Записывает каждый конкретный шаг, выполняемый утилитой `dpkg` — фундаментом всей пакетной экосистемы Debian-based систем (Ubuntu, Mint, Kali). Все высокоуровневые менеджеры — `apt`, `apt-get`, `aptitude`, графические центры приложений — являются обёртками над `dpkg`.

Когда вы вводите `sudo apt install nginx`, происходит следующее:
1. `apt` скачивает `.deb` пакет и проверяет зависимости;
2. `apt` вызывает `dpkg` для распаковки и установки;
3. `dpkg` записывает каждое действие в `/var/log/dpkg.log`.

Пример записей в `dpkg.log`:
```
2024-05-20 14:00:02 install libcurl4:amd64 <none> 7.81.0-1
2024-05-20 14:00:02 status half-installed libcurl4:amd64 7.81.0-1
2024-05-20 14:00:02 status unpacked libcurl4:amd64 7.81.0-1
2024-05-20 14:00:03 install curl:amd64 <none> 7.81.0-1
```

---

### 7. /var/log/apt/history.log

Пишет то же самое, что и `dpkg.log`, но в **человекочитаемом** формате. Вместо потока строк — лаконичные блоки операций:

```
Start-Date: 2024-05-20  14:00:01
Commandline: apt install curl
Requested-By: user (1000)
Install: libcurl4:amd64 (7.81.0-1), curl:amd64 (7.81.0-1)
End-Date: 2024-05-20  14:00:05
```

Удобен, когда нужно быстро ответить на вопрос: «Что и когда было установлено/удалено на этом сервере?»

---

### 8. Бинарные логи: wtmp, btmp, lastlog

Это особая категория — файлы, которые **нельзя читать через `cat`**, только через специализированные утилиты.

| Файл                  | Содержимое                                        | Утилита для чтения |
|-----------------------|---------------------------------------------------|--------------------|
| `/var/log/wtmp`       | История всех входов и выходов пользователей       | `last`             |
| `/var/log/btmp`       | Неудачные попытки входа                           | `lastb`            |
| `/var/log/lastlog`    | Время последнего входа для каждого пользователя   | `lastlog`          |
| `/var/log/faillog`    | Счётчики неудачных попыток входа по пользователям | `faillog`          |

Эти файлы критичны для аудита безопасности: `btmp` позволяет обнаружить brute-force атаки даже если злоумышленник зачистил `/var/log/auth.log`. Команды для работы с ними — в шпаргалке в конце документа.

## journald и journalctl

### Преимущества journald над rsyslog

`journalctl` — это CLI-интерфейс для просмотра и фильтрации структурированных логов, собранных демоном `systemd-journald`. Разберём ключевые преимущества:

**1. Единый коллектор из четырёх источников:**
- **Ядро:** journald напрямую читает `/dev/kmsg` (копия кольцевого буфера).
- **stdout/stderr сервисов:** Если запустить скрипт с `print('Error')` как systemd-службу, journald перехватит этот вывод автоматически. Раньше нужно было вручную перенаправлять вывод в файлы.
- **Нативный API (`sd-journal`):** Современные программы (Docker, Nginx) могут слать структурированные логи в формате ключ-значение, передавая не просто текст, а сразу ID пользователя, код ошибки, имя хоста и т.д.
- **Совместимость с syslog:** Демон слушает сокет `/dev/log`, куда по-прежнему отправляют данные старые приложения.

**2. Бинарный формат и метаданные:**
Логи хранятся в `/var/log/journal/` в файлах `.journal` — их нельзя читать через `cat`. Зато journald индексирует каждое сообщение и прикрепляет метаданные:
- `_PID` — номер процесса;
- `_UID` — кто запустил;
- `_SYSTEMD_UNIT` — имя службы;
- `_BOOT_ID` — идентификатор сессии загрузки;
- временна́я метка с точностью до микросекунды.

Именно поэтому `journalctl` умеет мгновенно фильтровать гигабайтные логи — он использует индексы, а не последовательное чтение.

**3. Режимы хранения (параметр `Storage=` в `/etc/systemd/journald.conf`):**

| Режим        | Поведение                                                                 |
|--------------|---------------------------------------------------------------------------|
| `volatile`   | Хранение в RAM (`/run/log/journal/`). Быстро, не нагружает диск, но теряется при перезагрузке. |
| `persistent` | Запись на диск в `/var/log/journal/`. Переживает перезагрузку.           |
| `auto`       | Если папка `/var/log/journal/` существует — пишет на диск. Если нет — в память. Это поведение **по умолчанию**. |
| `none`       | Логи не сохраняются вообще (только пересылка в rsyslog).                 |

**4. Встроенная самоочистка (`/etc/systemd/journald.conf`):**

В отличие от rsyslog, где для ротации нужен внешний инструмент `logrotate`, journald управляет размером журнала самостоятельно:

| Параметр            | Смысл                                                                         |
|---------------------|-------------------------------------------------------------------------------|
| `SystemMaxUse`      | Максимальный суммарный размер логов на диске (например, `2G`).               |
| `SystemKeepFree`    | Минимум свободного места на диске, которое journald всегда оставляет.        |
| `MaxRetentionSec`   | Максимальный срок хранения записей (например, `1month`). Важно для compliance.|
| `MaxFileSec`        | Максимальное время жизни одного файла журнала перед ротацией.                |

Journald разбивает журнал на множество небольших файлов. При превышении лимита он удаляет самый старый файл целиком — мгновенно и без нагрузки на систему.

**5. Rate Limiting — защита от шторма логов (`/etc/systemd/journald.conf`):**

На нагруженных системах отдельный сервис может начать генерировать тысячи сообщений в секунду (баг в коде, бесконечный цикл с логированием, DDoS). Journald умеет это ограничивать, чтобы один процесс не забил весь журнал и не убил диск I/O.

| Параметр                  | Смысл                                                                              | Значение по умолчанию |
|---------------------------|------------------------------------------------------------------------------------|-----------------------|
| `RateLimitIntervalSec`    | Окно времени, в котором считается лимит сообщений                                  | `30s`                 |
| `RateLimitBurst`          | Максимальное число сообщений от одного сервиса за это окно                         | `10000`               |

Если сервис за 30 секунд отправит более 10 000 сообщений, journald начнёт их **молча отбрасывать** и запишет в журнал предупреждение вида:
```
systemd-journald[…]: Suppressed N messages from nginx.service
```

Это критически важно знать: если при дебаге кажется, что логов нет — возможно, они просто отброшены rate limiter'ом. Проверить это можно через:
```bash
journalctl -u systemd-journald | grep Suppressed
```

Чтобы отключить rate limiting для конкретного сервиса (например, во время дебага), в его unit-файле можно указать:
```ini
[Service]
LogRateLimitIntervalSec=0
LogRateLimitBurst=0
```

### Команды journalctl

Это самая практическая часть — именно команды journalctl используются ежедневно.

```bash
# ─── БАЗОВЫЙ ПРОСМОТР ───────────────────────────────────────────────

journalctl                        # Все логи (постраничный вывод)
journalctl -e                     # Перейти сразу в конец журнала
journalctl -f                     # Режим follow (как tail -f)
journalctl -n 50                  # Последние 50 строк
journalctl --no-pager             # Вывод без постраничной навигации (для скриптов)

# ─── ФИЛЬТРАЦИЯ ПО ВРЕМЕНИ ──────────────────────────────────────────

journalctl --since "2024-05-20 10:00:00"
journalctl --until "2024-05-20 11:00:00"
journalctl --since "2024-05-20 10:00:00" --until "2024-05-20 11:00:00"
journalctl --since "1 hour ago"
journalctl --since today
journalctl --since yesterday

# ─── ФИЛЬТРАЦИЯ ПО ЗАГРУЗКЕ ─────────────────────────────────────────

journalctl -b                     # Логи текущей загрузки
journalctl -b -1                  # Логи предыдущей загрузки
journalctl -b -2                  # Два сеанса загрузки назад
journalctl --list-boots           # Список всех сохранённых загрузок

# ─── ФИЛЬТРАЦИЯ ПО СЕРВИСУ ──────────────────────────────────────────

journalctl -u nginx               # Логи конкретного юнита
journalctl -u nginx -u postgresql # Логи нескольких юнитов одновременно
journalctl -u nginx -f            # Follow-режим для конкретного сервиса

# ─── ФИЛЬТРАЦИЯ ПО УРОВНЮ ───────────────────────────────────────────

journalctl -p err                 # Ошибки и выше (err, crit, alert, emerg)
journalctl -p warning             # Предупреждения и выше
journalctl -p "emerg".."err"      # Диапазон уровней (от emerg до err включительно)
journalctl -p 0..3                # То же самое, но числами

# ─── ФИЛЬТРАЦИЯ ПО ЯДРУ ─────────────────────────────────────────────

journalctl -k                     # Только сообщения ядра (аналог dmesg)
journalctl -k -b                  # Сообщения ядра текущей загрузки
journalctl -k --since "10 min ago"

# ─── ФИЛЬТРАЦИЯ ПО ПОЛЯМ МЕТАДАННЫХ ─────────────────────────────────

journalctl _PID=1234              # Логи конкретного процесса
journalctl _UID=1000              # Логи от конкретного пользователя
journalctl _SYSTEMD_UNIT=ssh.service
journalctl /usr/sbin/sshd        # Логи по пути к исполняемому файлу

# ─── ФОРМАТЫ ВЫВОДА ─────────────────────────────────────────────────

journalctl -o short               # Стандартный формат (по умолчанию)
journalctl -o verbose             # Все метаданные каждого сообщения
journalctl -o json                # JSON — удобно для парсинга скриптами
journalctl -o json-pretty         # JSON с форматированием
journalctl -o cat                 # Только текст сообщения, без метаданных

# ─── УПРАВЛЕНИЕ ЖУРНАЛОМ ────────────────────────────────────────────

journalctl --disk-usage           # Сколько места занимают логи на диске
journalctl --vacuum-size=500M     # Удалить старые логи, оставив не более 500 МБ
journalctl --vacuum-time=2weeks   # Удалить логи старше 2 недель
journalctl --verify               # Проверить целостность журнала
```

## logrotate

`logrotate` — утилита для автоматической ротации, сжатия и удаления **текстовых** лог-файлов (rsyslog/syslog-ng). Для журнала journald используется встроенный механизм очистки (см. выше).

Главный конфиг: `/etc/logrotate.conf`. Конфиги для отдельных приложений: `/etc/logrotate.d/`.

### Пример конфигурации

```bash
# /etc/logrotate.d/nginx
/var/log/nginx/*.log {
    daily              # Ротировать ежедневно
    missingok          # Не ругаться, если файл отсутствует
    rotate 14          # Хранить 14 ротированных файлов
    compress           # Сжимать старые файлы (gzip)
    delaycompress      # Не сжимать самый последний ротированный файл
                       # (нужно, чтобы Nginx успел дописать в него)
    notifempty         # Не ротировать пустые файлы
    create 0640 www-data adm  # Создать новый файл с этими правами
    sharedscripts      # Выполнить postrotate один раз для всех файлов
    postrotate
        # Сигнал Nginx перетекать в новый файл
        [ -f /var/run/nginx.pid ] && kill -USR1 $(cat /var/run/nginx.pid)
    endscript
}
```

### Ключевые директивы logrotate

| Директива       | Описание                                                              |
|-----------------|-----------------------------------------------------------------------|
| `daily/weekly/monthly` | Частота ротации                                             |
| `rotate N`      | Сколько ротированных файлов хранить                                   |
| `compress`      | Сжимать старые файлы через gzip                                       |
| `delaycompress` | Отложить сжатие на одну итерацию (для процессов с открытым дескриптором) |
| `missingok`     | Не выводить ошибку, если файл не найден                               |
| `notifempty`    | Пропустить ротацию, если файл пуст                                    |
| `create`        | Создать новый пустой файл после ротации с заданными правами           |
| `copytruncate`  | Скопировать файл, затем обнулить оригинал (альтернатива для процессов, которые не умеют переоткрывать файл) |
| `postrotate`    | Скрипт, выполняемый после ротации (обычно — сигнал сервису)           |
| `size`          | Ротировать при достижении размера (например, `size 100M`)             |

**Проверка конфигурации без реального выполнения:**
```bash
logrotate -d /etc/logrotate.d/nginx   # Dry run — покажет, что будет сделано
logrotate -f /etc/logrotate.d/nginx   # Принудительная ротация прямо сейчас
```

## Stdout-first: логи как потоки событий

### Идея (12-Factor App)

В современной инфраструктуре (Docker, Kubernetes) действует принцип **«Logs as event streams»** — один из постулатов методологии [12-Factor App](https://12factor.net/logs). Суть: приложение не должно знать и не должно заботиться о том, куда и как сохраняются его логи. Его единственная задача — писать события в **stdout** и **stderr** как непрерывный поток строк.

Что происходит с этим потоком дальше — ответственность инфраструктуры, а не приложения:

```
┌─────────────────────────────────────────────────────────────────┐
│ Традиционный подход (антипаттерн)                               │
│                                                                 │
│  Приложение → открывает /var/log/app/app.log → пишет туда      │
│  Приложение знает о файловой системе, ротации, правах доступа  │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ Современный подход (12-Factor)                                  │
│                                                                 │
│  Приложение → stdout/stderr                                     │
│       │                                                         │
│       ▼                                                         │
│  Рантайм (Docker / containerd / systemd)                        │
│       │  перехватывает поток                                     │
│       ▼                                                         │
│  Агент сбора (Fluent Bit / Promtail / journald)                 │
│       │  маршрутизирует и отправляет                             │
│       ▼                                                         │
│  Центральное хранилище (Loki / Elasticsearch / syslog-сервер)  │
└─────────────────────────────────────────────────────────────────┘
```

Это даёт важное преимущество: один и тот же бинарник приложения разворачивается в любой среде (разработка, стейджинг, продакшн) без изменения кода. В разработке логи просто идут в терминал. В продакшне тот же поток перехватывается и отправляется в Loki.

### Коварный вопрос на собеседовании: «Куда пишет лог контейнер?»

**Плохой ответ:** «В папку `/var/log`».

**Хороший ответ:** Приложение внутри контейнера пишет в свои файловые дескрипторы `stdout` и `stderr`. Эти потоки перехватываются **container runtime** (Docker, containerd) и сохраняются на файловой системе хоста — обычно в `/var/lib/docker/containers/<container_id>/` в виде JSON-файлов (каждая строка лога — JSON с полями `log`, `stream`, `time`). В Kubernetes логи пода доступны по пути `/var/log/pods/<namespace>_<pod>_<uid>/<container>/`. Агент сбора логов (Fluent Bit, Promtail, Filebeat) запускается на каждом узле как DaemonSet, читает файлы из этих директорий и отправляет в центральное хранилище.

```bash
# Посмотреть логи контейнера через Docker (читает из /var/lib/docker/containers/...)
docker logs <container_id>
docker logs -f --tail 100 <container_id>

# Посмотреть «сырой» файл логов контейнера на хосте
cat /var/lib/docker/containers/<container_id>/<container_id>-json.log | head -5
# {"log":"Started server on port 8080\n","stream":"stdout","time":"2024-05-20T14:32:11Z"}

# В Kubernetes — логи пода
kubectl logs <pod_name> -n <namespace>
kubectl logs -f --tail=100 <pod_name> -c <container_name>
```

> Тот же принцип работает и для обычных systemd-сервисов: `stdout`/`stderr` процесса автоматически перехватываются `systemd-journald` и попадают в журнал. Поэтому скрипт с `print()`, запущенный как unit, виден через `journalctl -u my-service` без какой-либо настройки логирования внутри скрипта (подробнее — в разделе «journald и journalctl»).

## Логирование и производительность (I/O)

Логи — это постоянная запись на диск. На нагруженном сервере это ощутимая I/O-нагрузка. Middle+ DevOps должен понимать, как логирование влияет на систему и как это контролировать.

### Синхронная vs асинхронная запись в rsyslog

По умолчанию rsyslog после каждой записи вызывает `fsync()` — это гарантирует, что данные физически записаны на диск до продолжения работы. Это безопасно, но медленно.

Если поставить символ `-` перед путём к файлу в правиле rsyslog, запись становится **асинхронной** — данные сначала буферизируются в RAM и сбрасываются на диск периодически, без `fsync()` после каждой строки:

```bash
# /etc/rsyslog.d/50-default.conf

# Синхронная запись (по умолчанию) — надёжно, но медленно
mail.*   /var/log/mail.log

# Асинхронная запись — быстро, но при крахе системы
# последние несколько строк лога могут быть потеряны
mail.*  -/var/log/mail.log
```

Асинхронная запись оправдана для **высокочастотных, некритичных** логов (например, access-логи веб-сервера). Для логов безопасности (`auth.log`) асинхронность недопустима — нельзя потерять запись о входе злоумышленника.

### Как понять, что логи «тормозят» систему: iostat

Если система начала тормозить, а подозрение падает на дисковый I/O от логирования, используется `iostat` из пакета `sysstat`:

```bash
iostat -xz 1
```

Флаги: `-x` — расширенная статистика, `-z` — не показывать устройства с нулевой активностью, `1` — обновление каждую секунду.

На что смотреть в выводе:

```
Device   r/s    w/s   rMB/s  wMB/s  await  %util
sda      0.00  850.00  0.00   42.5   120.5  98.7
```

| Метрика  | Смысл                                                                                   |
|----------|-----------------------------------------------------------------------------------------|
| `w/s`    | Операций записи в секунду. Большое значение при минимальных чтениях — признак логов.    |
| `wMB/s`  | Мегабайт в секунду на запись.                                                           |
| `await`  | Среднее время ожидания I/O операции в миллисекундах. >100ms — диск перегружен.          |
| `%util`  | Утилизация устройства. 100% — диск является узким местом (bottleneck).                  |

Если `%util` близок к 100% и `w/s` велико — нужно либо переходить на асинхронную запись, либо выносить `/var/log` на отдельный диск, либо снижать verbosity логов.

### Log Burning: деградация SSD от логов

Отдельная проблема, характерная именно для SSD — **log burning**. Каждый SSD имеет ограниченный ресурс записи, измеряемый в **DWPD** (Drive Writes Per Day) — сколько раз в сутки можно перезаписать весь объём диска до его износа.

Если на нагруженном сервере включить `debug`-уровень логирования, поток записи может составить десятки гигабайт в час. Для бюджетного SSD ёмкостью 480 ГБ с DWPD=0.3 суточный ресурс записи — всего ~144 ГБ. При активном debug-логировании этот ресурс исчерпывается за несколько часов, а весь заявленный ресурс диска — за несколько месяцев вместо расчётных лет.

**Практические следствия:**
- `debug` в продакшне — это не просто «шум в логах», это физический износ железа;
- `/var/log` на production-серверах с интенсивным логированием стоит выносить на отдельный диск, либо использовать HDD для логов и SSD только под данные;
- мониторинг записи через `iostat` должен быть частью регулярного наблюдения за системой, а не только при инцидентах.

## Траблшутинг: «Куда делось место?»

Это классический вопрос на собеседованиях по DevOps. Ситуация: диск почти полон, ты удалил большой лог-файл через `rm`, но `df -h` показывает, что место **не освободилось**.

### Почему так происходит

В Linux `rm` удаляет не сам файл, а **имя (ссылку)** из директории. Физические данные на диске остаются до тех пор, пока файл открыт хотя бы одним процессом. Если rsyslog, Nginx или любой другой демон держит файловый дескриптор открытым и продолжает писать в удалённый файл — ядро не освобождает блоки на диске, потому что они ещё «используются».

```
┌─────────────────────────────────────────────────────┐
│  Файловая система                                    │
│                                                      │
│  /var/log/nginx/access.log  ──┐                      │
│  (имя удалено через rm)       │  inode (данные)      │
│                               └──▶ [блоки на диске]  │
│                                         ▲            │
│  Процесс nginx (PID 1234)  ─────────────┘            │
│  fd=7 (дескриптор открыт)   держит блоки занятыми   │
└─────────────────────────────────────────────────────┘
```

Блоки будут освобождены только когда процесс закроет дескриптор — то есть при перезапуске сервиса или перезагрузке сервера.

### Как найти процесс, держащий удалённый файл

```bash
# Найти все открытые, но удалённые файлы (deleted)
lsof | grep deleted

# Или более конкретно — только большие удалённые файлы в /var/log
lsof | grep '/var/log' | grep deleted

# Вывод будет примерно такой:
# nginx  1234  www  7u  REG  8,1  2147483648  123456  /var/log/nginx/access.log (deleted)
# ^      ^pid       ^fd       ^размер в байтах
```

### Варианты решения

**Вариант 1 — Перезапустить сервис (правильный способ):**
```bash
systemctl restart nginx
# Nginx закроет старый дескриптор и откроет новый файл.
# Место освободится немедленно.
```

**Вариант 2 — Обнулить файл через дескриптор (если перезапуск невозможен):**

Если сервис нельзя перезапускать (например, он в середине важной операции), можно обнулить файл через procfs, не закрывая дескриптор:

```bash
# Узнать PID и номер дескриптора из вывода lsof (например, PID=1234, fd=7)
> /proc/1234/fd/7
# или
truncate -s 0 /proc/1234/fd/7
```

Это обнулит содержимое файла (место освободится), при этом дескриптор останется открытым и сервис продолжит писать в тот же (теперь пустой) файл без ошибок.

**Вариант 3 — Правильная ротация через logrotate:**

Корень проблемы в том, что файл был удалён вручную, минуя logrotate. Правильный инструмент для удаления логов — это `logrotate` с директивой `postrotate`, которая после ротации отправляет сервису сигнал переоткрыть файл (`kill -USR1`). Это полностью исключает ситуацию с «висящими» дескрипторами.

## Архитектура поставки логов (Log Shipping)

Вопрос на собеседовании: «У нас 100 серверов, на каждом rsyslog/journald. Как увидеть общую картину в одном месте?»

Ответ строится через понимание ролей в цепочке. В любой системе централизованного логирования есть три роли, и важно понимать, что делает каждая:

```
┌──────────────┐     ┌──────────────┐     ┌──────────────────────┐
│   ИСТОЧНИК   │────▶│  АГРЕГАТОР   │────▶│     ХРАНИЛИЩЕ        │
│   (Origin)   │     │  (Shipper /  │     │  (Storage / Backend) │
│              │     │  Forwarder)  │     │                      │
│ rsyslog      │     │ Fluent Bit   │     │ Elasticsearch        │
│ journald     │     │ Promtail     │     │ Loki                 │
│ приложение   │     │ rsyslog fwd  │     │ syslog-сервер        │
│ контейнер    │     │ Logstash     │     │ S3 / object storage  │
└──────────────┘     └──────────────┘     └──────────────────────┘
```

**Источник (Origin)** — любой процесс или система, генерирующая события. Его задача — просто отдать лог: в stdout, в сокет, в файл. Источник не знает, куда логи пойдут дальше.

**Агрегатор/Форвардер (Shipper)** — агент, который забирает логи из источников, при необходимости парсит и обогащает их метаданными (добавляет имя хоста, окружение, namespace), и надёжно доставляет в хранилище. Именно здесь решается, что делать, если хранилище временно недоступно (буферизация на диске). Лёгкий агент, который разворачивается на каждом узле — это Fluent Bit или Promtail. Тяжёлый агент с богатой логикой трансформации — Logstash.

**Хранилище (Backend)** — принимает, индексирует и хранит логи. Предоставляет интерфейс для поиска и визуализации (Kibana над Elasticsearch, Grafana над Loki).

### Почему не rsyslog напрямую в хранилище?

Технически rsyslog умеет пересылать логи напрямую (см. раздел Remote Logging). Это работает для однородной инфраструктуры с простыми требованиями. Специализированные агенты (Fluent Bit, Promtail) появились потому, что они лучше справляются с контейнерной средой, умеют читать из нескольких источников одновременно (файлы, docker API, journald, kubernetes API) и имеют встроенные механизмы back-pressure — замедление сбора при перегрузке хранилища, чтобы не потерять события.

## Remote Logging: централизация на уровне OS

Даже без ELK-стека Middle+ должен уметь настроить пересылку логов с одного Linux-хоста на другой через нативный rsyslog. Это востребовано в корпоративных средах, на изолированных серверах и там, где нет ресурсов на сложные стеки.

### TCP vs UDP

| Критерий            | UDP (`@`)                                    | TCP (`@@`)                                   |
|---------------------|----------------------------------------------|----------------------------------------------|
| Гарантия доставки   | ❌ Нет (fire and forget)                     | ✅ Есть (подтверждение доставки)             |
| Потеря при нагрузке | Возможна (переполнение буфера сети)          | Нет (буферизация на стороне клиента)         |
| Производительность  | Выше (нет overhead на подтверждения)         | Немного ниже                                 |
| Потеря при падении  | Если сервер упал — логи теряются             | rsyslog буферизует и отправит после восстановления |
| Применение          | Некритичные логи в быстрой локальной сети    | Продакшн, аудит, compliance                  |

### Настройка клиента (отправитель)

```bash
# /etc/rsyslog.d/99-remote.conf на клиентском хосте

# Отправить все логи на центральный сервер по TCP
*.* @@logserver.example.com:514

# Или только auth-логи (для security-мониторинга)
auth,authpriv.* @@logserver.example.com:514

# С буферизацией на случай недоступности сервера (очередь на диске)
$ActionQueueFileName fwdRule1        # Имя файла очереди
$ActionQueueMaxDiskSpace 1g          # Максимум 1 ГБ на диске
$ActionQueueSaveOnShutdown on        # Сохранить очередь при остановке rsyslog
$ActionQueueType LinkedList          # Асинхронная очередь
$ActionResumeRetryCount -1           # Бесконечные попытки переподключения
*.* @@logserver.example.com:514
```

### Настройка сервера (получатель)

```bash
# /etc/rsyslog.conf на сервере-получателе

# Включить приём по TCP на порт 514
module(load="imtcp")
input(type="imtcp" port="514")

# Или по UDP
module(load="imudp")
input(type="imudp" port="514")

# Раскладывать логи от разных хостов в отдельные директории
$template RemoteLogs,"/var/log/remote/%HOSTNAME%/%PROGRAMNAME%.log"
*.* ?RemoteLogs
```

### TLS-шифрование для rsyslog

В логах нередко оказывается конфиденциальная информация: имена пользователей, IP-адреса, фрагменты запросов. Пересылать их по сети в открытом виде — нарушение базовой гигиены безопасности. Для шифрования используется модуль `gtls`.

**На сервере и клиенте нужны сертификаты.** Упрощённая схема с самоподписанными сертификатами (в продакшне — CA):

```bash
# Генерация CA и сертификатов (один раз)
certtool --generate-privkey --outfile ca-key.pem
certtool --generate-self-signed --load-privkey ca-key.pem --outfile ca.pem

certtool --generate-privkey --outfile server-key.pem
certtool --generate-certificate --load-privkey server-key.pem \
         --load-ca-certificate ca.pem --load-ca-privkey ca-key.pem \
         --outfile server-cert.pem
```

```bash
# /etc/rsyslog.conf на сервере (получатель с TLS)
module(load="imtcp"
       StreamDriver.Name="gtls"
       StreamDriver.Mode="1"        # 1 = TLS обязателен
       StreamDriver.Authmode="anon" # или x509/name для взаимной аутентификации
)

global(
  DefaultNetstreamDriver="gtls"
  DefaultNetstreamDriverCAFile="/etc/rsyslog.d/tls/ca.pem"
  DefaultNetstreamDriverCertFile="/etc/rsyslog.d/tls/server-cert.pem"
  DefaultNetstreamDriverKeyFile="/etc/rsyslog.d/tls/server-key.pem"
)

input(type="imtcp" port="6514")   # Стандартный порт для syslog over TLS — 6514
```

```bash
# /etc/rsyslog.d/99-remote.conf на клиенте (отправитель с TLS)
global(
  DefaultNetstreamDriver="gtls"
  DefaultNetstreamDriverCAFile="/etc/rsyslog.d/tls/ca.pem"
)

action(
  type="omfwd"
  target="logserver.example.com"
  port="6514"
  protocol="tcp"
  StreamDriver="gtls"
  StreamDriverMode="1"
  StreamDriverAuthMode="anon"
)
```

> **Порты:** стандартный syslog — `514` (TCP/UDP). Syslog over TLS (RFC 5425) — `6514`. Убедитесь, что файрвол пропускает нужный порт.

## Аудит событий: auditd

`auditd` — это «старший брат» обычного логирования. Если syslog записывает то, что **приложение само захотело сообщить**, то `auditd` записывает то, что приложение **фактически сделало** — на уровне системных вызовов ядра. Подделать или обойти auditd из пространства пользователя невозможно: он работает непосредственно в ядре.

Это обязательный инструмент для соответствия стандартам безопасности: PCI DSS, HIPAA, CIS Benchmarks, SOC 2.

### Что auditd умеет отслеживать

- открытие, чтение, запись, удаление конкретных файлов или директорий;
- выполнение определённых исполняемых файлов (бинарников);
- смену прав доступа (`chmod`, `chown`);
- системные вызовы (`open`, `execve`, `connect`, `ptrace` и т.д.);
- изменения в учётных записях и группах;
- использование привилегий (sudo, setuid).

### Архитектура

```
Приложение делает системный вызов (например, open())
          │
          ▼
   [ Ядро Linux — Audit Subsystem ]  ← правила из auditd
          │
          ▼
   [ Audit Netlink Socket ]
          │
          ▼
   [ auditd (демон) ]
          │
          ▼
   /var/log/audit/audit.log
```

### Основные компоненты

| Компонент    | Роль                                                                       |
|--------------|----------------------------------------------------------------------------|
| `auditd`     | Демон, принимает события от ядра и пишет в `/var/log/audit/audit.log`     |
| `auditctl`   | CLI для управления правилами в реальном времени (не персистентно)          |
| `auditd.rules` / `/etc/audit/rules.d/` | Персистентные правила, загружаются при старте |
| `ausearch`   | Поиск по логам auditd с фильтрацией                                        |
| `aureport`   | Генерация отчётов (сводка по входам, командам, файлам и т.д.)              |

### Примеры правил

```bash
# Следить за чтением и записью файла паролей
auditctl -w /etc/passwd -p rwa -k passwd_changes
#           ^путь        ^права (r=read w=write a=attr x=exec)  ^метка для поиска

# Следить за директорией с SSH-ключами
auditctl -w /home/user/.ssh/ -p rwa -k ssh_keys

# Аудит всех выполнений команды sudo (через системный вызов execve)
auditctl -a always,exit -F path=/usr/bin/sudo -F perm=x -k sudo_usage

# Аудит попыток изменить права доступа к файлам
auditctl -a always,exit -S chmod -S fchmod -S chown -k permission_changes

# Посмотреть текущие активные правила
auditctl -l

# Записать правила персистентно
# /etc/audit/rules.d/audit.rules
-w /etc/passwd -p rwa -k passwd_changes
-w /etc/sudoers -p rwa -k sudoers_changes
```

### Чтение логов auditd

Логи auditd нечитаемы напрямую из-за специфичного формата. Используются специальные утилиты:

```bash
# Найти все события по метке
ausearch -k passwd_changes

# Найти события за последний час
ausearch --start recent

# Найти все команды, запущенные конкретным пользователем
ausearch -ua 1000 -i    # -i = переводить UID/GID в имена

# Найти все неудачные попытки доступа к файлам
ausearch --success no -i

# Отчёт по всем входам в систему
aureport --login

# Отчёт по выполненным командам (execve)
aureport --executable

# Полный сводный отчёт
aureport --summary
```

### auditd vs syslog: ключевое отличие

```
syslog/journald:
  Nginx → "Received request from 1.2.3.4" → /var/log/syslog
  (Nginx сам решает, что писать и как)

auditd:
  Nginx открыл /etc/nginx/nginx.conf (syscall: open)
  → ядро зафиксировало факт → /var/log/audit/audit.log
  (Nginx не контролирует эту запись — её делает ядро)
```

Именно поэтому auditd используется там, где важна **неотказуемость** (non-repudiation): нельзя сказать «я этого не делал», если факт системного вызова зафиксирован ядром.

## Trace ID (Correlation ID)

В микросервисной архитектуре один запрос пользователя проходит через цепочку из множества сервисов на разных серверах. Если в середине этой цепочки появилась ошибка — найти её начало по разрозненным логам практически невозможно.

**Проблема без Trace ID:**
```
# Сервис А (auth-service)          Сервис Б (order-service)      Сервис В (payment-service)
[10:00:01] User 42 authenticated   [10:00:01] Creating order...   [10:00:02] ERROR: timeout
[10:00:01] User 17 authenticated   [10:00:01] Creating order...   [10:00:02] Payment OK
[10:00:01] User 99 authenticated   [10:00:02] Order failed        [10:00:02] ERROR: timeout
```
Какой из трёх пользователей столкнулся с ошибкой? Какой запрос привёл к `Order failed`? Без связующего ключа — неизвестно.

**Решение — Trace ID:** При получении первого запроса генерируется уникальный идентификатор (`trace_id`). Он передаётся в каждый последующий сервис через HTTP-заголовок (`X-Trace-ID` или `traceparent` по стандарту W3C) и включается в каждую строку лога на всём пути запроса.

```json
// Сервис А — auth-service
{"timestamp":"2024-05-20T10:00:01Z","trace_id":"abc-123","user_id":42,"event":"authenticated"}

// Сервис Б — order-service (получил trace_id из заголовка запроса)
{"timestamp":"2024-05-20T10:00:01Z","trace_id":"abc-123","event":"creating_order","user_id":42}
{"timestamp":"2024-05-20T10:00:02Z","trace_id":"abc-123","level":"error","event":"order_failed","reason":"payment timeout"}

// Сервис В — payment-service (тот же trace_id)
{"timestamp":"2024-05-20T10:00:02Z","trace_id":"abc-123","level":"error","event":"payment_timeout","duration_ms":5023}
```

Теперь в любой системе поиска по логам (Kibana, Grafana Loki) один запрос `trace_id: "abc-123"` мгновенно выдаёт полную хронологию инцидента по всем сервисам.

### Что важно знать DevOps про Trace ID

**Trace ID генерирует приложение**, а не инфраструктура — это ответственность разработчиков. Задача DevOps — убедиться, что системы сбора и хранения логов не теряют это поле при парсинге и индексируют его. В Loki это означает вынести `trace_id` в label или использовать `detected_fields`. В Elasticsearch — убедиться, что поле не попадает под `dynamic: false` в маппинге.

**Span ID** — дополнение к Trace ID. Если Trace ID идентифицирует весь запрос целиком, то Span ID идентифицирует конкретную операцию внутри него (например, запрос к БД внутри обработки заказа). Вместе они составляют основу **distributed tracing** — полноценной трассировки, реализованной в системах OpenTelemetry, Jaeger, Zipkin.

## Шпаргалка: что смотреть при типичных проблемах

| Проблема                              | Куда смотреть / Команда                                                |
|---------------------------------------|------------------------------------------------------------------------|
| Сервис не стартует                    | `journalctl -u имя_сервиса -n 50` или `journalctl -xe`                |
| Ошибки при загрузке системы           | `journalctl -b`, `/var/log/boot.log`, `/var/log/dmesg`                 |
| Проблемы с оборудованием/драйверами   | `dmesg -T`, `journalctl -k`, `/var/log/kern.log`                       |
| Подозрительная активность / взлом     | `/var/log/auth.log`, `lastb`, `journalctl _SYSTEMD_UNIT=sshd.service` |
| История входов пользователей          | `last`, `last -n 20` (из `/var/log/wtmp`)                              |
| Неудачные попытки входа               | `lastb` (из `/var/log/btmp`, требует root)                             |
| Последний вход конкретного юзера      | `lastlog -u <username>`                                                |
| Что устанавливали/удаляли             | `/var/log/apt/history.log`, `/var/log/dpkg.log`                        |
| Общая хронология событий              | `/var/log/syslog` или `journalctl --since "1 hour ago"`                |
| Сколько места занимают логи           | `journalctl --disk-usage`, `du -sh /var/log/`                          |
| Место не освобождается после `rm`     | `lsof \| grep deleted`, затем `systemctl restart <сервис>`             |
| Диск тормозит из-за логов             | `iostat -xz 1` — смотреть `%util` и `await` по устройству             |
| Логи «пропадают» на нагруженном хосте | `journalctl -u systemd-journald \| grep Suppressed` — rate limiting    |
| Кто открывал защищённый файл          | `ausearch -k <метка> -i`                                               |
| Отчёт по входам в систему             | `aureport --login`                                                     |
| Полный путь запроса по микросервисам  | Поиск по `trace_id` в Kibana / Loki                                    |
