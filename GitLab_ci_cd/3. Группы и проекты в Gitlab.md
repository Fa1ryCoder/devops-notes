# Группы, подгруппы и проекты в GitLab

Иерархия group → subgroup → project — это не только про порядок папок, а про то, где реально настраивать доступ, CI/CD variables и runner-ы, чтобы не повторять одно и то же в каждом проекте отдельно. На собесе это всплывает через вопросы вида «как организовать доступ команды» или «где расшарить переменную на десяток проектов» — и то, и другое как раз про эту тему.

## Шпаргалка

| Термин | Что это |
|---|---|
| **Project** | Репозиторий + issues + CI/CD + wiki + registry — базовая единица работы |
| **Group** | Контейнер для нескольких проектов: общие участники, права, CI/CD-настройки |
| **Subgroup** | Группа внутри группы — та же логика, вложенная под структуру организации |
| **Namespace** | Уникальный «адрес» проекта или группы — личный (твой username) или групповой |

## Иерархия

```
GitLab instance
 └─ Group: company
     ├─ Subgroup: backend
     │   ├─ Project: payment-service
     │   └─ Project: auth-service
     └─ Subgroup: frontend
         └─ Project: web-app
```

Полный путь вроде `gitlab.com/company/backend/payment-service` — это и есть namespace проекта, он же часть git remote URL:

```bash
git clone https://gitlab.com/company/backend/payment-service.git
```

Вкладывать подгруппы друг в друга можно на несколько уровней, но на практике редко уходят дальше 2–3 — глубже уже неудобно ориентироваться.

## Project

Базовая единица: код, issue tracker (трекер задач и багов — как встроенная mini-Jira), wiki, Container/Package Registry (хранилище для собранных Docker-образов и пакетов, типа встроенного Docker Hub для проекта) и CI/CD — всё в одном месте.

Это не что-то внешнее, что нужно отдельно подключать — это встроенные инструменты самого GitLab. Когда создаёшь Project, всё это сразу доступно внутри него, только не плоским списком, а сгруппировано по разделам в сайдбаре слева:

- **Plan** — issues, доски, milestones, **wiki**
- **Code** — repository, merge requests, ветки, коммиты
- **Build** — пайплайны, jobs, раннеры проекта
- **Deploy** — package registry, container registry, releases

Практическая польза от того, что это одна сущность: дал человеку Developer — он разом получил доступ и к коду, и к issues, и к пайплайнам. Смёржил MR (merge request — запрос на слияние веток, аналог pull request) — задача может закрыться сама (`Closes #12` в коммите). Собрал Docker-образ в CI — он тут же лежит в Container Registry этого же проекта.

Может жить сам по себе, в личном namespace (`gitlab.com/artem/pet-project`), вообще без группы — именно так у тебя сейчас и настроено. В личных проектах ты по факту Owner. Группа нужна не для того, чтобы проект заработал, а чтобы масштабировать это на много людей и проектов сразу.

## Group и Subgroup

**Group** объединяет несколько проектов под одним «зонтиком»: общие участники и права, общие CI/CD variables, общие runner-ы — чтобы не настраивать одно и то же в десяти местах. **Subgroup** — та же группа, просто вложенная в другую: нужна, когда структура больше одного уровня, например `company` → `backend` / `frontend` / `infra`, у каждой подгруппы свои проекты и, если нужно, свои права поверх родительских.

### Зачем это вообще нужно

Представь, что ты один — и у тебя один личный pet-проект. Группа тут правда не нужна, весь смысл в ней появляется, когда в дело вступает команда/компания с кучей проектов.

**Проблема без группы:** допустим, в компании 10 проектов (5 бэкенд-сервисов, 3 фронтенда, 2 инфраструктурных). Каждый — отдельный Project. Без группы каждый из них живёт сам по себе, изолированно. И тогда:

- Хочешь дать новому разработчику доступ Developer ко всем 5 бэкенд-сервисам — идёшь в каждый проект отдельно и добавляешь его 5 раз. Уволился — удаляешь 5 раз.
- Нужна одна и та же CI/CD-переменная (например, токен для деплоя) во всех 5 — копируешь её в Settings → CI/CD → Variables каждого проекта отдельно. Токен утёк — идёшь менять в 5 местах.
- Поднял раннер, хочешь, чтобы он обслуживал все 5 сервисов — регистрируешь как project runner в каждом по отдельности, 5 раз.

**Group решает это всё разом:** создаёшь группу `backend`, закидываешь туда все 5 проектов. Теперь:
- Добавил разработчика Developer'ом один раз на группу — он автоматически Developer во всех 5 проектах внутри.
- Задал переменную один раз на группе — она видна во всех 5 проектах, без копирования.
- Поднял group runner один раз — он подхватывает все 5 проектов, и новые тоже, если их добавят в группу позже.

То есть коротко: group/subgroup — это не про хранение файлов, а про то, чтобы права и настройки CI/CD задавать один раз на группу людей/проектов, а не размножать вручную по каждому проекту.

Группу и подгруппу создают через «New group» → «New subgroup» внутри уже существующей.

## Роли и права доступа

Самая частая тема на собесе про группы. Роль назначается либо на группу (действует на все проекты и подгруппы внутри), либо напрямую на проект — если пересекается и там, и там, действует та, что выше.

| Роль | Что может (коротко) | Кто это обычно |
|---|---|---|
| **Guest** | Смотреть issues/MR, комментировать | Внешний стейкхолдер |
| **Planner** | + вести issues, epics, доски — без доступа к коду | PM, аналитик |
| **Reporter** | + читать код и CI/CD-логи, без права пушить | QA, наблюдатель |
| **Developer** | + push в незащищённые ветки, запуск pipeline, MR | Обычный разработчик |
| **Maintainer** | + мердж в защищённые ветки, CI/CD variables и runner-ы **проекта** | DevOps-инженер чаще всего тут |
| **Owner** | + удаление, участники, биллинг, CI/CD variables и runner-ы **группы** | Тимлид/руководитель |

## Важный нюанс для DevOps: группа — это не проект

Тут многие спотыкаются на практике, и это же любят спрашивать: на уровне **проекта** Maintainer-у доступны CI/CD variables и project runner-ы. А вот на уровне **группы** управлять group-level CI/CD variables и group runner-ами может только **Owner** группы — Maintainer-у прав не хватит, даже если он Maintainer в самом проекте. Maintainer с недавних версий GitLab может хотя бы *посмотреть* список group runner-ов, но создать, поставить на паузу или удалить — только Owner.

Отсюда типичная путаница на практике: ты Maintainer в проекте, видишь в Settings → CI/CD → Variables унаследованную от группы переменную, а перейти по ссылке к ней не можешь — не хватает роли уже на уровне группы.

Заодно про терминологию runner-ов — она обновилась по сравнению с тем, что было раньше:

- **Instance runner** (раньше называли shared) — доступен всем проектам инстанса.
- **Group runner** — доступен всем проектам и подгруппам конкретной группы.
- **Project runner** (раньше — specific) — привязан к одному проекту. Именно такой ты регистрировал в теме 1.

Если заведёшь второй pet-проект и захочешь использовать тот же runner на оба — есть смысл поднять его заново как group runner на уровне группы, а не дублировать project runner в каждом проекте.

## Видимость: Private / Internal / Public

Задаётся отдельно и на группу, и на проект:

- **Private** — видят только явно добавленные участники.
- **Internal** — видит любой залогиненный пользователь инстанса. На GitLab.com эта опция отключена для новых групп/проектов ещё с 2019 года: на публичном мультитенантном инстансе «любой залогиненный» практически означает «кто угодно в интернете», толку от такого уровня немного.
- **Public** — видит кто угодно, даже без аккаунта.

Правило наследования простое: дочерний элемент не может быть «более открытым», чем родитель. Приватная группа не может содержать публичный проект или публичную подгруппу — только private внутри private.

## Перенос проекта в другую группу

Реальная практическая ситуация: Settings → General → Advanced → Transfer project. Нужна роль Owner и в исходной, и в целевой группе/namespace. Что стоит держать в голове:

- CI/CD variables, заданные на уровне **старой** группы, теряются вместе с переездом — они принадлежат группе, а не проекту. Переменные, заданные прямо в проекте, переезжают вместе с ним.
- То же с runner-ами: project runner едет вместе с проектом, а доступ к group runner-ам старой группы пропадает — зато появляется доступ к runner-ам новой.
- Старый URL какое-то время редиректит на новый, но лучше поправить `origin` вручную, чтобы не зависеть от редиректа:

```bash
git remote set-url origin https://gitlab.com/new-group/project.git
```

## Коротко для собеса

Group и subgroup существуют, чтобы не настраивать доступ, CI/CD variables и runner-ы в каждом проекте по отдельности, а сделать это один раз выше по иерархии. Настройки наследуются сверху вниз — группа → подгруппа → проект, никогда наоборот, и всегда побеждает самая высокая назначенная роль. Ключевая деталь, которую реально проверяют на собесе: управление на уровне группы (variables, runners) — это зона Owner, а не Maintainer.
