# 3.7 Git – Ветки – Восстановление предыдущих версий файлов

## 1. Назначение git restore для файлов

`git switch` работает с состоянием всего проекта: меняет, на какую ветку смотрит HEAD, и подтягивает файлы под эту ветку целиком. `restore` работает точечно — команда меняет содержимое конкретных файлов или директорий, не переключая ветку и не затрагивая остальной проект. Типичный повод — в одном файле нашлась ошибка, и его нужно вернуть к состоянию из более раннего коммита, оставив всё остальное как есть.

## 2. Отмена незакоммиченных изменений

Простейший сценарий: правки в файле оказались неудачными, ни в индекс, ни в коммит они ещё не попали, и файл нужно вернуть к последнему зафиксированному состоянию. Для этого достаточно передать `restore` путь без каких-либо флагов:

```bash
git restore <путь>
```

`<путь>` — это путь к файлу: просто имя, если файл лежит в текущей директории (`config.py`), или относительный путь, если глубже (`src/config.py`).

Команда копирует содержимое файла из индекса в рабочую директорию. Пока `git add` для файла не выполнялся, индекс совпадает с HEAD — поэтому на практике команда воспринимается как «вернуть файл к последнему коммиту»:

```bash
$ cat config.py
MAX_RETRIES = 50

$ echo 'MAX_RETRIES = 100' > config.py
$ git status --short
 M config.py

$ git restore config.py

$ cat config.py
MAX_RETRIES = 50
$ git status --short
```

Пустой вывод `git status` означает, что рабочая директория снова совпадает с индексом и HEAD.

Если файл перед этим добавляли в индекс, результат будет другим. Сам индекс `restore` без флагов не трогает — добавленная правка так и останется подготовленной к коммиту. Откатятся только изменения, сделанные после `git add`: файл вернётся к добавленной версии, а не к состоянию из HEAD, потому что источник у команды один — индекс.

Стёртые таким образом правки вернуть не получится: они не попадали ни в коммит, ни в stash, поэтому в объектах Git их просто нет. Перед запуском стоит убедиться, что содержимое действительно больше не нужно.

## 3. Отмена добавления в индекс

Обратная ситуация: файл уже добавлен в индекс, но включать его в ближайший коммит передумали. Убрать файл из индекса — операция unstage — выполняется тем же `restore`, но с флагом `--staged`:

```bash
git restore --staged <путь>
```

Флаг меняет и цель, и источник: обновляется индекс, а содержимое берётся из HEAD. Запись о файле в индексе возвращается к состоянию последнего коммита, рабочая директория при этом не затрагивается — правки остаются на диске нетронутыми:

```bash
$ echo 'MAX_RETRIES = 30' > config.py
$ git add config.py
$ git status --short
M  config.py

$ git restore --staged config.py

$ git status --short
 M config.py
$ cat config.py
MAX_RETRIES = 30
```

Позиция буквы `M` в статусе показывает, что произошло: первая колонка — разница между HEAD и индексом, вторая — между индексом и рабочей директорией. До команды файл был изменён в индексе, после — только в рабочей директории. Тот же результат даёт `git reset <путь>`.

## 4. Восстановление файла из старого коммита

Основной сценарий темы: ошибка закралась не в текущие правки, а в один из прошлых коммитов, и файл нужно вернуть к более ранней версии. Сначала — найти коммит, в котором файл ещё был правильным. `git log` с путём покажет только те коммиты, где этот файл менялся:

```bash
$ git log --oneline config.py
4464469 increase retry config
220c979 add retry config
```

Дальше содержимое достаётся флагом `--source` — он принимает хеш коммита или имя ветки:

```bash
git restore --source=<коммит_или_ветка> <путь>
```

По умолчанию результат записывается только в рабочую директорию:

```bash
$ git restore --source=220c979 config.py

$ cat config.py
MAX_RETRIES = 5

$ git status --short
 M config.py

$ git show :config.py
MAX_RETRIES = 50
```

`git show :config.py` выводит содержимое файла в индексе — там по-прежнему текущее значение. С точки зрения Git произошло то же, что при обычном редактировании: в рабочей директории появилась незакоммиченная правка, просто её содержимое взято из старого коммита. В следующий коммит восстановленная версия не попадёт, пока файл не пройдёт через `git add`. Это главное отличие от старого `checkout <коммит> <путь>`, который молча записывал восстановленный файл ещё и в индекс.

Рабочая директория в примере выше обновилась и без флагов — это поведение по умолчанию. То же самое можно прописать явно, добавив `--worktree`:

```bash
$ git restore --source=220c979 --worktree config.py

$ cat config.py
MAX_RETRIES = 5

$ git status --short
 M config.py
```

`--worktree` указывает: результат нужно записать в рабочую директорию.

Если в `--source` указать имя ветки, файл возьмётся из её последнего коммита. Это удобно, когда нужная версия уже лежит в соседней ветке и её проще забрать оттуда, чем искать конкретный хеш. Допустим, на `hotfix` значение уже поправили и закоммитили:

```bash
$ git branch --show-current
master
$ cat config.py
MAX_RETRIES = 50

$ git restore --source=hotfix config.py

$ cat config.py
MAX_RETRIES = 8
$ git branch --show-current
master
```

Переключения не происходит — `restore` читает файл из последнего коммита ветки `hotfix`, а текущей веткой остаётся `master`.

## 5. Восстановление с одновременным обновлением индекса

Если восстановленную версию нужно сразу подготовить к коммиту, к `--source` добавляют флаги цели. `--staged` в этой комбинации обновляет только индекс — рабочая директория остаётся как была:

```bash
$ git restore --source=220c979 --staged config.py

$ cat config.py
MAX_RETRIES = 50

$ git status --short
MM config.py
```

В рабочей директории всё ещё текущее значение, а в индексе уже лежит восстановленное — отсюда сразу две `M` в статусе. Такое промежуточное состояние на практике нужно редко; обычно обновляют обе стороны, указывая оба флага:

```bash
$ git restore --source=220c979 --staged --worktree config.py

$ cat config.py
MAX_RETRIES = 5

$ git status --short
M  config.py
```

Файл обновлён и добавлен в индекс за один шаг — осталось выполнить `git commit`, сама команда его не делает. Ровно так вёл себя старый `checkout <коммит> <путь>`. Тот же результат получится и в два шага: `restore --source=...` из предыдущего раздела, затем `git add`. Комбинация `--staged --worktree` сокращает эти два шага до одного, но `git commit` в любом случае остаётся отдельным действием после.

## 6. Несколько файлов и директории целиком

`restore` принимает не один путь, а сколько угодно, включая директории — тогда откатывается содержимое всех файлов внутри:

```bash
$ git log --oneline settings/
f0b53dc tune settings (bad tuning)
744e357 add settings

$ git restore --source=744e357 --staged --worktree settings/

$ cat settings/db.py settings/cache.py
POOL_SIZE = 10
TTL = 60

$ git status --short
M  settings/cache.py
M  settings/db.py
```

Флаги работают так же, как с одиночным файлом, — они определяют, куда запишется результат, а не сколько путей можно передать.

## 7. Что restore никогда не меняет

Ни один вариант `restore`, включая любые значения `--source`, не сдвигает HEAD и не переключает ветку — в отличие от `git switch --detach <коммит>`, который переводит репозиторий в detached HEAD. `restore` только читает содержимое из коммита-источника; сам этот коммит текущим не становится. В примере с `hotfix` `git branch --show-current` до и после команды выводит одно и то же.

Из этого следует и то, что путь никогда не конфликтует с именем ветки. У `checkout` аргумент был неоднозначным: имя могло оказаться и веткой, и файлом, и при совпадении команда переключала ветку вместо восстановления файла. У `restore` позиционные аргументы — всегда пути: даже если завести ветку с именем `config.py`, команда `git restore config.py` восстановит файл, а ветку не тронет.

Разделитель `--` перед путями при этом остаётся в синтаксисе — он нужен, если имя файла начинается с дефиса и Git иначе примет его за флаг:

```bash
$ git restore -weird.txt
error: unknown switch `w'

$ git restore -- -weird.txt
```

В остальных случаях `--` необязателен.
