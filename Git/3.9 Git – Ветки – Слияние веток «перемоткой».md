# 3.9 Git – Ветки – Слияние веток «перемоткой»

## Слияние веток

Когда работа в отдельной ветке закончена — например, в `fix` исправили баг, — эти изменения нужно добавить в основную ветку, обычно `master`. За это отвечает команда `git merge`.

Направление важно: вы переключаетесь на ветку, которая должна получить изменения (её называют **целевой**), а в самой команде `merge` называете ветку, откуда эти изменения берутся (**ветка-источник**):

```bash
$ git switch master
$ git merge fix
```

После этого все коммиты, которые есть в `fix`, но которых не было в `master`, становятся частью истории `master`.

## Fast-forward: перемотка вместо слияния

Если с момента создания `fix` в `master` не появилось ни одного нового коммита, Git не создаёт коммит слияния и не сравнивает содержимое файлов — он просто передвигает указатель `master` вперёд, на тот же коммит, куда указывает `fix`. Это и называется fast-forward (в русскоязычных источниках — «перемотка»): ветка перематывается вперёд по уже существующей линии истории, никакого нового ответвления в результате не возникает.

Условие жёсткое: коммит, на который указывает `master`, должен быть прямым предком коммита `fix`. Если после создания `fix` в `master` добавился хотя бы один коммит, истории расходятся, и простым перемещением указателя дело не обойдётся — потребуется реально объединять содержимое.

На практике это выглядит так. На `master` один коммит:

```bash
$ git log --oneline --decorate
c45a7c5 (HEAD -> master) Initial commit
```

Создаём `fix` и добавляем исправление:

```bash
$ git switch -c fix
$ git commit -am "Fix: add retries to db connection"
$ git log --oneline --all --graph --decorate
* c6f0ca3 (HEAD -> fix) Fix: add retries to db connection
* c45a7c5 (master) Initial commit
```

Возвращаемся на `master` и сливаем `fix`:

```bash
$ git switch master
$ git merge fix
Updating c45a7c5..c6f0ca3
Fast-forward
 app.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

Первая строка показывает старое и новое положение `master`, вторая прямо называет использованный алгоритм, дальше — обычная сводка изменённых файлов, как при любом коммите.

После слияния обе ветки указывают на один и тот же коммит:

```bash
$ git branch -v
  fix    c6f0ca3 Fix: add retries to db connection
* master c6f0ca3 Fix: add retries to db connection
```

`fix` при этом никуда не делась и не изменилась — как указывала на `c6f0ca3`, так и указывает. Просто `master` её догнал. Новых коммитов слияние не создало: единственные два коммита в репозитории — «Initial commit» и «Fix: add retries to db connection» — существовали ещё до операции, теперь на второй из них указывают уже обе ветки.

## `ORIG_HEAD`: страховка перед потенциально опасной операцией

`merge` двигает указатель ветки, а такие операции Git считает потенциально опасными: сдвинуть указатель легко, а без специальных мер вспомнить, где он был секунду назад, — нет. Поэтому перед подобными операциями Git сохраняет прежнее положение `HEAD` в отдельную ссылку — `ORIG_HEAD`. Технически это обычный файл, такой же, как указатели веток в `refs/heads/`, только лежит он в корне `.git/`:

```bash
$ cat .git/ORIG_HEAD
c45a7c55de335e3d1c808a2620b87efa2679c3b2

$ git log --oneline -1 ORIG_HEAD
c45a7c5 Initial commit
```

Это ровно тот коммит, на котором стоял `master` до слияния. `ORIG_HEAD` ведёт себя как обычная ссылка на коммит: его можно передавать в `log`, `diff`, `branch`, `switch` и любые другие команды точно так же, как имя ветки или хеш. Нюанс один: слот единственный — при следующей потенциально опасной операции `ORIG_HEAD` перезапишется новым значением, так что вернуться с его помощью можно ровно на один шаг назад, а не к произвольной точке истории.

## Откат fast-forward слияния

Раз `ORIG_HEAD` хранит положение `master` до слияния, откат — это перемещение ветки обратно на тот коммит:

```bash
git branch -f master ORIG_HEAD
```

Загвоздка в том, что `git branch -f` не может подвинуть ветку, на которой вы стоите прямо сейчас. А сразу после `git merge` вы стоите именно на `master` — вы переключились на неё ещё до слияния, это был первый шаг алгоритма. Поэтому команда завершится ошибкой:

```bash
$ git branch -f master ORIG_HEAD
fatal: cannot force update the branch 'master' used by worktree at '/home/claude/repo'
```

Git отказывается это делать: если бы команда сработала, указатель `master` ушёл бы на другой коммит, а рабочая директория и индекс остались бы от прежнего — то, что реально лежит на диске, разошлось бы с тем, куда указывает ветка. Для текущей ветки нужна команда, которая двигает указатель и одновременно обновляет рабочую директорию под новое положение, — `git switch -C`:

```bash
$ git switch -C master ORIG_HEAD
Reset branch 'master'

$ git log --oneline --all --graph --decorate
* c6f0ca3 (fix) Fix: add retries to db connection
* c45a7c5 (HEAD -> master) Initial commit
```

`master` вернулся туда, где был до слияния. Ветку `fix` откат вообще не затрагивает — она по-прежнему указывает на свой коммит, так что исправление никуда не делось, просто снова не влито в `master`.

Если до отката вы уже переключились на другую ветку, ограничение не действует — в этом случае `git branch -f master ORIG_HEAD` отработает без ошибок.
