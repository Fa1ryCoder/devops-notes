# 3.10 Git – Ветки – Удаление веток

## Зачем удалять ветки?

Ветка в Git — это именованная ссылка на коммит, а не отдельное хранилище данных. Когда работа над временной веткой (`fix`, `feature/*`, `hotfix/*`) завершена и её изменения слиты в основную линию разработки (`master`), сама ветка как отдельная сущность теряет смысл: всё, что в ней делалось, уже часть истории основной ветки, а вторая ссылка на те же коммиты просто дублирует уже доступную информацию.

Практическая причина удалять такие ветки — список `git branch` со временем захламляется. В репозитории, где над задачами работает несколько человек, за несколько месяцев может накопиться сотня-другая устаревших имён, среди которых сложно найти те, что реально в работе прямо сейчас. Это создаёт путаницу не только у автора ветки, но и у любого, кто заходит в репозиторий и пытается понять, что там происходит.

На GitHub и GitLab это настолько стандартная практика, что после слияния pull/merge request'а хостинг сам предлагает удалить исходную ветку одной кнопкой — по сути автоматизируя ту же операцию, которую можно выполнить локально командой из следующего раздела.

## Команды для удаления веток

### Безопасное удаление: `git branch -d`

```bash
git branch -d <название_ветки>
```

Команда `git branch -d` не удаляет коммиты. Она лишь удаляет файл-указатель в директории `.git/refs/heads/`, который содержит хэш последнего коммита. Сами объекты коммитов остаются в базе данных `.git/objects/`.

С удалением указателя связан риск: если после этого на коммиты ветки больше ничто не указывает, найти их обычными командами становится невозможно. Поэтому перед удалением Git отвечает на один вопрос: сохранятся ли эти коммиты где-то ещё, или потеряются? Для этого он берёт последний коммит удаляемой ветки и смотрит, входит ли тот в историю ветки, на которой ты сейчас стоишь, — то есть является ли предком твоего текущего HEAD.

- Если да — после слияния эти коммиты уже стали частью твоей ветки, удаление указателя ничего не теряет. Git удаляет и печатает хэш последнего коммита:

  ```
  $ git merge fix
  $ git branch -d fix
  Deleted branch fix (was 3a87a68).
  ```

- Если нет — в ветке есть работа, которой нет в твоей истории, и после удаления указателя она потеряется. Git блокирует операцию с ошибкой `not fully merged`:

  ```
  $ git branch -d fix
  error: the branch 'fix' is not fully merged.
  If you are sure you want to delete it, run 'git branch -D fix'
  ```

Проверка идёт только относительно текущей ветки, а не всего репозитория: Git спрашивает не «слита ли `fix` хоть куда-нибудь», а «слита ли `fix` в то, на чём я стою». Если `fix` слита в `dev`, её коммиты есть в истории `dev`, но их нет в истории `master`. Поэтому, стоя на `master`, ты получишь отказ, а стоя на `dev` — удалишь без проблем. Одна и та же команда даёт разный результат в зависимости от того, где находится HEAD в момент выполнения.

**Проблема Squash и Cherry-pick**

Git сравнивает коммиты по хэшу, а не по содержимому файлов. При cherry-pick или squash-merge на ветку, в которую переносишь изменения (ту, на которой стоишь), создаётся новый коммит с новым хэшем — пусть даже с теми же изменениями в файлах. При `git branch -d feature` Git ищет в твоей истории оригинальный хэш из `feature`, но там лежит копия с другим хэшем. Для Git это «не слито», и он откажет — хотя по коду всё перенесено и `git diff` между ветками пустой:

```
$ git diff feature master --stat
$ git branch -d feature
error: the branch 'feature' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature'
```

Это ложная тревога: изменения на месте, без ссылки останется только дубликат. Для таких случаев используется принудительное удаление.

### Принудительное удаление: `git branch -D`

```bash
git branch -D <название_ветки>
```

Заглавная `-D` — сокращение для `--delete --force`. Та же операция удаления файла-указателя, но без проверки: Git удаляет ветку независимо от того, что в ней есть.

Применяется в двух ситуациях:
- ветка оказалась тупиковой — работа в ней осознанно выбрасывается; её коммиты действительно останутся без ссылок;
- ветка на деле уже интегрирована через cherry-pick или squash, но `-d` этого не видит из-за разных хэшей; здесь ничего не теряется — содержимое сохранено в другом коммите.

Ни `-d`, ни `-D` не удалят ветку, на которой ты сейчас стоишь, — сначала нужно переключиться командой `git switch` на любую другую:

```
error: cannot delete branch 'fix' used by worktree at '/path/to/repo'
```

## Недостижимые коммиты (Unreachable Commits)

Коммит считается достижимым, если до него можно дойти по цепочке родителей, начиная от какой-нибудь ссылки — ветки, тега или HEAD. Пока хотя бы одна ссылка ведёт к коммиту, он виден в истории и защищён от удаления.

После `git branch -d` все коммиты удалённой ветки остаются достижимыми — раз команда вообще согласилась выполниться, они уже входят в историю ветки, в которую были слиты. А вот после `git branch -D` на ветке с уникальными коммитами последняя ссылка на них исчезает, и они становятся недостижимыми: не показываются ни в `git log`, ни в `git log --all`. Физически при этом объекты — коммиты и связанные с ними tree и blob — продолжают лежать в `.git/objects/`, просто добраться до них через обычные ссылки больше нельзя.

Окончательно такие объекты исчезают позже, во время сборки мусора: Git запускает её автоматически (`git gc --auto`, когда в базе накапливается достаточно рыхлых объектов) или вручную (`git gc`). По умолчанию недостижимый объект не трогается, пока не пролежит в этом состоянии около двух недель (настройка `gc.pruneExpire`). Этот запас времени и делает возможным восстановление.

## Восстановление удалённой ветки

Пока сборка мусора не удалила коммиты, ветку можно вернуть — достаточно создать ссылку заново.

**Шаг 1 — найти хэш последнего коммита удалённой ветки.**

Проще всего взять его из сообщения, которое Git напечатал при удалении: `Deleted branch feature (was 7c1a371).`

Если вывод уже потерян, хэш ищется через `git reflog` — историю перемещений HEAD: переключения, коммиты, слияния. Коммиты удалённой ветки создавались, когда HEAD был на ней, поэтому записи о них в reflog есть:

```
7c1a371 HEAD@{2}: commit: feature: add line5
```

**Шаг 2 — создать ветку заново, указав найденный хэш.**

```bash
git branch <название_ветки> <идентификатор_коммита>
```

Для примера выше: `git branch feature 7c1a371`. Ветка снова появится в списке `git branch` и будет указывать ровно на тот же коммит — с тем же автором, датой и сообщением, поскольку это тот же объект в базе данных. Не восстанавливается только собственный reflog ветки: у воссозданной ветки он начинается с записи `branch: Created from <хэш>`, прежняя история переключений на этой ветке не возвращается.

Дальше можно переключиться на восстановленную ветку и продолжить работу: `git switch feature`.
