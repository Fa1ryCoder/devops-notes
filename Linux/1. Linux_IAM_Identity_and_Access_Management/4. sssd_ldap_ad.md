## 1. Зачем нужна централизованная аутентификация

> **На пальцах:** LDAP — это база данных сотрудников, Kerberos — это безопасный вход по билетам, а SSSD — это клей, который соединяет их с Linux. Этого понимания часто хватает, чтобы пройти 80% интервью.

### Проблема: 1000 серверов, 200 пользователей

В небольшой компании с 5 серверами можно управлять пользователями вручную через `useradd`. В компании с сотнями серверов это невозможно.

Когда инженер увольняется, его аккаунт нужно удалить вручную на каждом сервере, и легко пропустить один. Новый сотрудник ждёт доступа, пока кто-то не пройдёт по всем машинам и не создаст учётку везде. Смена пароля — та же история. Аудит («кто куда заходил») превращается в поиск по логам сотен серверов. А единую политику паролей при локальных аккаунтах обеспечить невозможно.

### Решение: централизованное хранилище учётных записей

```
Администратор
      │  создаёт пользователя ОДИН РАЗ
      ▼
 Active Directory / LDAP
      │
      ├── server-01  ←── SSSD ──→ AD
      ├── server-02  ←── SSSD ──→ AD
      ├── server-03  ←── SSSD ──→ AD   Все серверы обращаются
      └── server-N   ←── SSSD ──→ AD   к одному источнику

Уволился сотрудник → отключить в AD → мгновенно потерял доступ везде
```

Хранилищем может быть Active Directory (решение Microsoft) или любой LDAP-сервер, например OpenLDAP. Подробнее об этом — в разделах 2–4.

### Что такое SSSD

**SSSD** (System Security Services Daemon) — это служба (демон) на Linux-сервере, которая связывает его с центральным хранилищем пользователей, например AD. Сама Linux про AD ничего не знает: она смотрит только в локальные файлы `/etc/passwd` и `/etc/shadow`. SSSD встаёт между системой и AD и работает как переводчик.

Когда кто-то логинится на сервер, Linux спрашивает SSSD, есть ли такой пользователь и верный ли пароль. SSSD идёт с этим вопросом в AD, получает ответ и передаёт его системе. Ещё он запоминает ответы в локальном кэше, поэтому при недоступном AD уже заходившие пользователи всё равно могут войти.

### Три задачи, которые решает SSSD

**Identity** — кто существует в системе. `getent passwd alice@company.com` — команда, которая спрашивает у системы, есть ли такой пользователь. Благодаря SSSD система находит его в AD и возвращает UID, GID и домашнюю директорию.

**Authentication** — тот ли это человек, за кого он себя выдаёт. SSSD подключается к PAM, и пароль проверяется на контроллере домена AD через Kerberos, а не по `/etc/shadow`.

**Authorization** — что пользователю можно. SSSD отдаёт системе членство в AD-группах, поэтому `/etc/sudoers` работает с группой вроде `linux-admins` как с локальной.

В следующих разделах — по порядку все компоненты: LDAP (где хранятся данные), Kerberos (как проверяется вход), AD (что их объединяет), SSSD (как это подключается к Linux) и практическая настройка на Debian.

## 2. LDAP — каталог пользователей

### Что такое LDAP

**LDAP (Lightweight Directory Access Protocol)** — протокол доступа к иерархическому каталогу объектов. Каталог оптимизирован для чтения: данные меняются редко, читаются очень часто.

Порты: `389` (LDAP), `636` (LDAPS — LDAP поверх TLS), `3268/3269` (Global Catalog в AD).

### Структура каталога (DIT — Directory Information Tree)

```
dc=company,dc=com               ← корень (domain component)
├── ou=users                    ← organizational unit
│   ├── cn=alice                ← объект пользователя
│   ├── cn=bob
│   └── cn=charlie
├── ou=groups
│   ├── cn=developers
│   └── cn=admins
└── ou=serviceaccounts
    ├── cn=jenkins
    └── cn=gitlab-runner
```

### DN — Distinguished Name

Полный путь к объекту в дереве, читается справа налево:

```
cn=alice,ou=users,dc=company,dc=com
   ─────  ────────  ────────────  ──────
    ↑        ↑           ↑           ↑
  имя     отдел     домен company  домен верхнего уровня com
```

### Атрибуты пользователя

Чтобы Linux мог использовать запись из каталога как пользователя, у неё должны быть POSIX-атрибуты: `uid` (логин), `uidNumber` и `gidNumber` (UNIX UID и основная группа), `homeDirectory`, `loginShell`. Также могут быть `shadow`-атрибуты со сроком действия пароля.

Проверить, что записи есть, можно командой `ldapsearch`. Она подключается к каталогу под технической учёткой и ищет объекты по фильтру. Флаги знать не нужно, важно понимать, что она делает.

## 3. Kerberos — вход по билетам

### Зачем нужен Kerberos

Простой LDAP bind передаёт пароль при каждой аутентификации. Kerberos решает эту проблему: **пароль никогда не передаётся по сети**, даже при первом входе. Вместо него используется система криптографических билетов.

Почему не нужен TLS для защиты пароля на первом шаге: клиент не отправляет пароль. Он использует хэш пароля как **ключ шифрования** для подписи запроса. KDC проверяет подпись своим экземпляром того же хэша, и если они совпадают, аутентификация прошла.

### Участники

```
KDC (Key Distribution Center) = AS + TGS — центр доверия, в AD это контроллер домена
  ├── AS (Authentication Service) — выдаёт TGT
  └── TGS (Ticket Granting Service) — выдаёт Service Tickets

Client — пользователь или сервис
Service — ресурс, к которому нужен доступ (файловый сервер, веб-сервис)
```

### Процесс аутентификации (3 шага)

```
── Шаг 1: получить TGT (Ticket Granting Ticket) ──────────────────

Клиент                    AS (часть KDC)
   │── "Я Alice, дайте TGT" ──────────────────────────────→│
   │                                               проверяет хэш пароля
   │                                               (пароль как ключ шифрования)
   │←── TGT (зашифрован ключом KDC) ──────────────────────│
   │    TGT содержит: имя пользователя, срок действия,
   │    session key (для общения с TGS), PAC (группы, см. раздел 4)

── Шаг 2: получить Service Ticket для конкретного сервиса ────────

Клиент                    TGS (часть KDC)
   │── TGT + "хочу доступ к server.company.com" ──────────→│
   │                                               проверяет TGT
   │←── Service Ticket (зашифрован ключом сервиса) ────────│

── Шаг 3: аутентификация у сервиса ──────────────────────────────

Клиент                    Сервис
   │── Service Ticket ────────────────────────────────────→│
   │                                               расшифровывает своим ключом
   │                                               проверяет валидность
   │←── доступ разрешён ─────────────────────────────────│
```

Пароль не передавался ни разу. TGT действует обычно 10 часов, после этого нужно заново получить его через `kinit`.

**Время критично.** В билеты зашита метка времени, поэтому часы клиента и KDC не должны расходиться больше чем на 5 минут, иначе Kerberos откажет. Это самая частая причина «непонятных» отказов аутентификации.

### Принципалы и SPN

Каждый участник Kerberos (пользователь, компьютер, сервис) имеет **принципал** — уникальное имя вида `имя@REALM`. Для сервисов принципал называется **SPN (Service Principal Name)** и имеет формат `сервис/хост@REALM`, например `host/server01.company.com@COMPANY.COM`.

Если два объекта в AD имеют одинаковый SPN, Kerberos-аутентификация к этому сервису ломается.

### Keytab-файлы — вход без пароля

Сервисам нельзя интерактивно вводить пароль через `kinit`. Для этого существуют **keytab-файлы**.

Keytab — бинарный файл с парами «принципал Kerberos + зашифрованный ключ (хэш пароля)». SSSD и другие сервисы используют его, чтобы получить TGT без участия человека (`kinit -k -t /etc/krb5.keytab ...`).

При `realm join` keytab создаётся автоматически: `/etc/krb5.keytab`. SSSD использует его для аутентификации машинного аккаунта в AD.

**Безопасность:** keytab эквивалентен паролю. Права должны быть `600`, владелец — root или сервисный пользователь. Компрометация keytab = компрометация учётки сервиса.

### Где хранятся билеты

По умолчанию Kerberos хранит билеты в `/tmp/krb5cc_<UID>`. Если злоумышленник получает root-доступ, он может украсть этот файл и действовать под чужой учёткой до истечения TGT (до 10 часов). Это называется **Ticket Harvesting**.

Защита: хранить билеты в хранилище ядра (`KEYRING`) или в `sssd-kcm` (`KCM:`) вместо файлов в `/tmp`.

### Повседневные команды

```bash
kinit alice@COMPANY.COM   # получить TGT (пароль вводится один раз)
klist                     # показать текущие билеты и срок их действия
kdestroy                  # уничтожить билеты (аналог logout из домена)
```

### Что в /etc/krb5.conf

Файл создаётся при `realm join`. Из него важно знать три параметра:
- `default_realm` — домен Kerberos по умолчанию, пишется заглавными (`COMPANY.COM`).
- `dns_lookup_kdc = true` — искать контроллер домена через DNS-записи, а не прописывать вручную.
- `default_ccache_name = KEYRING:persistent:%{uid}` — хранить билеты в ядре, а не в `/tmp`. Это единственная строка, которую обычно правят руками.

## 4. Active Directory

### AD = LDAP + Kerberos + DNS + Group Policy

Active Directory — это Microsoft-реализация LDAP с существенными расширениями:

| Компонент | Что даёт |
|-----------|---------|
| LDAP (порт 389/636) | Хранение объектов: пользователи, группы, компьютеры |
| Kerberos (порт 88) | Аутентификация без передачи пароля по сети |
| DNS (порт 53) | Поиск контроллеров домена, SRV-записи |
| Group Policy | Централизованное управление настройками |
| Kerberos PAC | Авторизационные данные в билете (группы, атрибуты) |

### Объекты AD, которые важны для Linux

- **Organizational Unit (OU)** — аналог папки, для структурирования
- **User** — учётная запись пользователя
- **Computer** — учётная запись компьютера, создаётся при join к домену
- **Group** — группа (Security Group — для прав, Distribution — для почты)

### Kerberos PAC (Privilege Attribute Certificate)

PAC — расширение Microsoft, которое зашивается внутрь Kerberos-билета. PAC содержит **все SID групп пользователя**, его привилегии и атрибуты.

**Почему это важно:** в чистом LDAP после проверки пароля сервер делает отдельный запрос в LDAP, чтобы узнать группы пользователя. В AD это не нужно: сервер расшифровывает билет, видит PAC с группами и принимает решение об авторизации без единого обращения в AD.

```
LDAP-аутентификация:
  1. Проверить пароль → LDAP bind
  2. Получить группы  → отдельный LDAP-запрос
  3. Авторизовать

Kerberos + PAC:
  1. Проверить билет (расшифровать локально)
  2. Прочитать PAC (группы уже внутри)
  3. Авторизовать ← никаких сетевых запросов!
```

**Проблема больших PAC:** если пользователь состоит в 500+ группах AD, PAC и Kerberos-билет становятся огромными. SSH начинает отвергать соединение или SSSD падает с ошибкой. Решение: сократить количество групп пользователя или ограничить глубину вложенности групп на уровне SSSD.

## 5. SSSD — связка Linux с каталогом

### Как SSSD встраивается в систему

```
Linux-сервер
├── NSS → sssd → identity-провайдер (AD/LDAP)
│    getent passwd alice@company.com
│
├── PAM → sssd → auth-провайдер (Kerberos/LDAP bind)
│    аутентификация при логине
│
└── /var/lib/sss/db/ → локальный кэш (работает offline)
```

SSSD состоит из нескольких процессов:

```
sssd (главный процесс)
├── sssd_be   — backend, подключается к AD/LDAP
├── sssd_nss  — обрабатывает NSS-запросы (getent, id)
├── sssd_pam  — обрабатывает PAM-запросы (аутентификация)
└── sssd_sudo — обрабатывает sudo-правила из LDAP/AD
```

**NSS** (Name Service Switch) определяет, где система ищет пользователей и группы. Чтобы `getent` и `id` видели пользователей из AD, в `/etc/nsswitch.conf` у `passwd`, `group` и `shadow` должен быть источник `sss` после `files`: сначала проверяется локальный `/etc/passwd`, потом SSSD.

### Ключевые параметры sssd.conf

Файл создаётся при `realm join`. Вот что в нём нужно понимать:

- `id_provider` / `auth_provider` — откуда брать пользователей и как проверять пароль (для AD оба `ad`).
- `use_fully_qualified_names` — как выглядит имя: `alice` или `alice@company.com`. От этого зависят записи в sudoers и скрипты.
- `cache_credentials = true` — при недоступном AD вход работает по кэшу.
- `ldap_id_mapping` — как получать UID (см. ниже).
- `simple_allow_groups` и `ad_gpo_access_control` — кого пускать на эту машину.
- `services` — какие сервисы SSSD предоставляет (`nss`, `pam`, `sudo`, `ssh`).

Права на файл должны быть `600`, владелец root, иначе SSSD откажется стартовать.

> ⚠️ **Если вместо AD используется чистый LDAP** (`id_provider = ldap`), включи шифрование. Для этого есть параметр `ldap_id_use_start_tls = true`; альтернатива — подключаться по LDAPS (порт 636 вместо 389, указывается в `ldap_uri`). Без шифрования данные пользователей, включая хэши паролей при простом bind, идут по сети в открытом виде.

### UID/GID маппинг

В реальных корпоративных AD администраторы Windows **крайне редко** заполняют UNIX-атрибуты (`uidNumber`, `gidNumber`). SSSD умеет работать в двух режимах:

**`ldap_id_mapping = false`** — явные атрибуты
- SSSD ищет `uidNumber` и `gidNumber` в объекте пользователя AD
- Если атрибутов нет, пользователь **не авторизуется**
- Требует расширения схемы RFC 2307 (Unix Attributes) в AD

**`ldap_id_mapping = true`** — алгоритмический маппинг (по умолчанию для `id_provider = ad`)
- SSSD берёт SID пользователя из Windows (например `S-1-5-21-3623811015-3361044348-30300820-1013`)
- Хэш-функцией **генерирует из него стабильный UID/GID**
- Windows-атрибуты не нужны
- UID одинаков на всех серверах, если у них один и тот же домен и конфигурация SSSD

### Что где лежит

| Файл / каталог | За что отвечает |
|----------------|-----------------|
| `/etc/sssd/sssd.conf` | Настройки SSSD, создаётся при `realm join` |
| `/etc/krb5.conf` | Настройки Kerberos, создаётся при `realm join` |
| `/etc/krb5.keytab` | Ключи машины для входа в AD без пароля. Эквивалент пароля, права `600` |
| `/etc/nsswitch.conf` | Где система ищет пользователей и группы (`files sss`) |
| `/var/lib/sss/db/` | Кэш SSSD |
| `/var/log/sssd/` | Логи SSSD |

## 6. Интеграция Debian с Active Directory

### Порядок действий

**1. Подготовка.** Три условия, без которых дальше идти нельзя:
- DNS разрешает AD-домен и находит контроллеры по SRV-записям (`_ldap._tcp.company.com`).
- Время синхронизировано с контроллером домена (расхождение > 5 минут ломает Kerberos). На Debian это настраивается в `chrony`, в `/etc/chrony/chrony.conf` указывается `server dc01.company.com iburst`.
- Hostname — FQDN (`server01.company.com`).

**2. Установка.** Ключевые пакеты: `sssd`, `sssd-ad`, `sssd-tools`, `realmd`, `adcli`, `krb5-user`, `libnss-sss`, `libpam-sss`. Пакеты `oddjob*` из RHEL-инструкций на Debian не нужны.

**3. Присоединение к домену.**

```bash
realm join -U domain-join-account company.com
```

Лучше использовать отдельную учётку с минимальными правами только на присоединение компьютеров, а не Domain Admin. `realmd` — не просто обёртка над `net join`. Он автоматически:
- находит контроллеры домена через DNS SRV-записи
- создаёт computer account в AD
- генерирует keytab (`/etc/krb5.keytab`)
- настраивает `/etc/nsswitch.conf`, `/etc/krb5.conf` и `/etc/sssd/sssd.conf`

**4. Домашние директории.** Чтобы `/home/alice` создавался при первом входе, включается модуль `pam_mkhomedir` командой `pam-auth-update --enable mkhomedir`.

**5. Доступ.** По умолчанию после `realm join` на машину может войти любой пользователь домена. Чтобы ограничить вход группой, сначала запрещают всех (`realm deny --all`), потом разрешают нужную (`realm permit -g linux-admins@company.com`).

**6. sudo для AD-групп.** В `/etc/sudoers.d/` пишется правило с именем группы в формате `%группа@домен`. Если включён `use_fully_qualified_names = False`, пишется просто `%linux-admins`.

**7. Проверка.** Цепочка от простого к сложному:

```bash
sssctl domain-status company.com   # Online или Offline?
id alice@company.com               # SSSD видит пользователя и его группы?
getent passwd alice@company.com    # то же через NSS
su - alice@company.com             # вход работает?
```

Если `Offline` — проблема в связи с AD (DNS, firewall, время). Если `id` не находит пользователя — проблема в SSSD или маппинге. Если `id` работает, а вход нет — проблема в PAM.

### SSH-ключи из AD/LDAP

При 1000 серверов копировать `authorized_keys` — та же проблема, что и с локальными пользователями. SSSD умеет отдавать публичные ключи прямо из атрибута пользователя в LDAP/AD.

Для этого в `sssd.conf` добавляется сервис `ssh`, а в `sshd_config` указывается `AuthorizedKeysCommand /usr/bin/sss_ssh_authorizedkeys`. При подключении sshd спрашивает у SSSD публичные ключи пользователя, а SSSD забирает их из AD/LDAP. Добавил ключ в AD, и он работает сразу на всех серверах.
