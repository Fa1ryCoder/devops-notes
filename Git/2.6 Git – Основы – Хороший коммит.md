---

Коммиты — это кирпичики из которых строится вся история проекта. От того насколько они грамотно составлены зависит насколько легко будет работать с проектом через месяц, через год и всей командой.

---

## 1. Что такое хороший коммит

**Хороший коммит** — это не просто бэкап твоего кода на GitHub, а минимальное, логически завершённое изменение с чётким описанием того что и зачем было сделано. Он пишется не для Git, а для коллег (и для тебя самого через полгода) — чтобы историю можно было легко читать, ревьюить и автоматизировать.

Три главных принципа, написанных кровью разработчиков:
- **Атомарность** — одна задача, один коммит
- **Консистентность** — изменение не ломает проект
- **Частота** — коммитить часто, не копить изменения

---

## 2. Атомарность

Каждый коммит должен выполнять **только одну задачу** — исправление конкретной ошибки или добавление одной функциональности. Атомарные коммиты обычно небольшие и затрагивают один или несколько файлов.

Если ты чинил баг в авторизации, попутно поправил опечатку в конфиге и обновил версию библиотеки — это должно быть три разных коммита:

```bash
# ✅ Хорошо — три атомарных коммита
git commit -m "fix: исправить падение при пустом вводе в форме логина"
git commit -m "fix: исправить опечатку в конфиге"
git commit -m "chore: обновить версию библиотеки до 2.1.0"

# ❌ Плохо — всё в одном коммите
git commit -m "исправил баги и добавил новые фичи и обновил зависимости"
```

**Зачем:** если твоя фича вызовет сбой в продакшене, дежурный инженер должен иметь возможность откатить её одной командой `git revert <hash>` — не вырезая попутно другие полезные правки. С гигантским коммитом это невозможно.

---

## 3. Консистентность

Коммит должен представлять собой **логически законченное изменение которое не ломает проект**. Проект должен успешно собираться, проходить линтеры (инструменты автоматической проверки кода на стиль и типичные ошибки) и тесты на каждом отдельном коммите. Нельзя делать коммит "я просто сохраню это здесь, оно пока не компилируется".

Например если переименовываешь функцию — нужно сделать это одним коммитом во всех местах её использования. Если сделать это в двух коммитах — после первого проект сломается и тесты упадут.

```bash
# ❌ Плохо — после первого коммита проект сломан
git commit -m "переименовать функцию authenticate в auth в auth.go"
git commit -m "обновить вызовы функции auth в остальных файлах"

# ✅ Хорошо — всё переименование в одном коммите
git commit -m "refactor: переименовать authenticate → auth во всём проекте"
```

**Зачем:** если в историю попадёт "битый" коммит — это сломает инструмент `git bisect` (бинарный поиск коммита который сломал код — но чтобы он заработал, сначала нужно вручную указать заведомо хороший и заведомо плохой коммит). Коллега, затыкая дыры в продакшене, запустит bisect и застрянет на твоём промежуточном коммите — потому что там в принципе ничего не работает.

---

## 4. Частота коммитов

**"Commit early, commit often"** — коммить рано и часто. Дроби крупные задачи на мелкие шаги и коммить их по мере готовности, не копи изменения неделями. При этом пушить в общую ветку можно гораздо реже.

**Зачем:** чем дольше держишь код только у себя в рабочей директории, тем выше шанс поймать **Merge Hell** — адские конфликты при слиянии с кодом коллег. Частые локальные коммиты — это страховка от потери работы и гибкость при рефакторинге.

---

## 5. Анатомия хорошего Commit Message

В продакшене (особенно в крупных командах) к описанию коммитов относятся так же строго как и к самому коду. Хорошее сообщение должно отвечать на два вопроса: **Что сделано?** и **Зачем это сделано?**

### Правило 50/72

Классическое правило форматирования — история красиво выглядит и в консольном `git log` и в веб-интерфейсах (GitHub/GitLab):

```
Заголовок до 50 символов без точки в конце
                                            ← пустая строка обязательна
Подробное описание что и зачем изменено.
Ширина строки не более 72 символов —
для удобного чтения в консоли.
```

**Заголовок (до 50 символов):** краткая суть изменений. Начинается с заглавной буквы, точки в конце нет.

**Пустая строка:** обязательна — она отделяет заголовок от тела. Если её не поставить, Git сольёт всё в один нечитаемый абзац.

**Тело коммита (перенос на 72 символах):** объясняется контекст и почему изменения были сделаны именно так. Как сделано — писать не нужно, это и так видно в коде через `git diff`.

### Общепринятые коммиты (Conventional Commits)

Стандарт де-факто в DevOps. Заголовки маркируются префиксами которые определяют тип изменений, а после префикса в скобках можно указать scope — конкретный модуль или часть системы, которую затрагивает изменение (например `fix(auth)` — исправление именно в авторизации). CI/CD пайплайн может просканировать такие коммиты, автоматически сгенерировать `CHANGELOG.md` и определить новую версию релиза (Major, Minor или Patch).

Логика простая: `fix` поднимает PATCH-версию (1.2.3 → 1.2.4), `feat` — MINOR (1.2.3 → 1.3.0), а breaking change — MAJOR (1.2.3 → 2.0.0). Инструмент вроде `semantic-release` сканирует коммиты с последнего релиза, по префиксам группирует их в `CHANGELOG.md` (отдельно Features, отдельно Bug Fixes) и сам решает какую версию присвоить следующему релизу — без участия человека. Подробнее это встретится когда дойдём до GitLab CI/CD — там такие правила прописываются прямо в `.gitlab-ci.yml`.

| Префикс | Когда использовать |
|---------|-------------------|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Изменения только в документации |
| `style` | Форматирование, опечатки, пробелы (не влияющие на логику) |
| `refactor` | Изменение кода без исправления бага и без новой фичи |
| `ci` | Правка конфигурационных файлов CI/CD |
| `chore` | Рутинные задачи, обновление зависимостей |

Пример идеального production-коммита:

```
fix(auth): исправлена валидация срока действия токена

Предыдущая логика валидации пропускала просроченные токены если
системные часы расходились более чем на 5 секунд.

Добавлен допуск в 10 секунд для предотвращения ложных срабатываний
при пиковой нагрузке.

Closes #PROJ-1234
```

`Closes #PROJ-1234` — служебная строка для таск-трекера (Jira, GitHub Issues и т.п.): при мерже такого коммита тикет с этим номером закроется автоматически.

## 6. Почему плохи гигантские коммиты

Начинающие часто совершают ошибку — фиксируют все сделанные за долгое время изменения одним коммитом. Это разом нарушает и атомарность (в одном коммите смешаны разные задачи), и частоту (изменения копились неделями) — а на ревью в таком объёме коллегам сложно быстро понять что изменилось и зачем.

Хороший коммит проверяется просто: если ты можешь забрать его в другую ветку через `git cherry-pick` и он заработает там без подтягивания за собой ещё десятка соседних коммитов — ты всё сделал правильно.
