## 1. Структура директории .git

Если заглянуть внутрь `.git/`, увидим следующую структуру:

```
.git/
├── config
├── HEAD
├── hooks/
├── logs/
├── objects/
└── refs/
```

| Файл / Директория | Что внутри                  | За что отвечает                                                     |
|-------------------|-----------------------------|---------------------------------------------------------------------|
| `config`          | Текстовый файл              | Локальная конфигурация этого репозитория (`--local`)                |
| `HEAD`            | Текстовый файл              | Указатель на ветку в которой ты сейчас находишься                   |
| `hooks/`          | Директория со скриптами     | Автоматизация: локальные Git-хуки (скрипты автоматических проверок) |
| `logs/`           | Директория с логами         | История изменений всех ссылок (база для команды `git reflog`)       |
| `objects/`        | Директория (БД)             | Хранилище всего контента: файлы, коммиты, структура папок           |
| `refs/`           | Директория со ссылками      | Список всех веток (локальных/удалённых) и тегов                     |

## 2. config

Обычный текстовый файл в формате INI. В него записываются настройки которые ты задаёшь через `git config --local`. Локальные настройки репозитория всегда приоритетнее глобальных (`--global`).

```bash
cat .git/config
```

```ini
[core]
    repositoryformatversion = 0
    filemode = true
    bare = false
[user]
    email = ivan@company.com
```

Этот файл можно редактировать вручную — без командной строки. Например быстро поменять рабочий email для этого проекта, и Git сразу подхватит изменения.

## 3. HEAD

Файл-указатель, состоящий всего из одной строки. Говорит Git на какой ветке ты сейчас находишься:

```bash
cat .git/HEAD
# ref: refs/heads/main
```

Когда ты переключаешься на другую ветку, Git не перекачивает проект заново. Он просто перезаписывает одну строку внутри файла `HEAD`:

```bash
# После git checkout develop
cat .git/HEAD
# ref: refs/heads/develop
```

Именно так Git мгновенно понимает где ты находишься.

Важный нюанс: не любая операция с ветками трогает `HEAD`. `git branch <имя>` без переключения только создаёт новый файл в `refs/heads/` — указатель на текущий коммит, — а `HEAD` при этом не меняется, он всё ещё смотрит на прежнюю ветку. Переписывается `HEAD` только в момент реального переключения: либо явного (`git switch <имя>`), либо через комбинированный `git switch -c <имя>`, который под капотом — это создание ветки и переключение на неё одной командой, то есть оба шага сразу: сначала появляется файл в `refs/heads/`, потом переписывается строка в `HEAD`.

## 4. hooks/

Здесь лежат скрипты (на Bash, Python, Perl) которые Git автоматически запускает при наступлении определённых событий. Например перед коммитом (`pre-commit`) или перед отправкой кода на сервер (`pre-push`).

Сюда внедряют автоматические проверки. Например утилита `gitleaks` или локальные линтеры могут проверяться прямо здесь. Если разработчик попытается закоммитить код с забытым AWS-токеном или сломанным синтаксисом — скрипт из `hooks/` вернёт ошибку и Git заблокирует коммит прямо на машине разработчика до того как код попадёт на сервер.

## 5. logs/

Git ведёт здесь учёт истории всех указателей — записывает в какой момент ветка `main` или указатель `HEAD` перепрыгивали с одного хеша на другой.

Это база данных для команды `git reflog`. Если разработчик случайно сделал `git reset --hard` и удалил результаты вчерашней работы, или случайно удалил ветку — файлы не стираются из базы объектов мгновенно. По логам из папки `logs/` через `git reflog` можно найти хеш потерянного коммита и полностью восстановить код.

Например, случайно затёрли вчерашний коммит:

```bash
git reset --hard HEAD~1
```

`git reflog` покажет историю переходов `HEAD`, включая тот, что был до отката:

```bash
git reflog

# a1b2c3d (HEAD -> main) HEAD@{0}: reset: moving to HEAD~1
# d4e5f6a HEAD@{1}: commit: добавил модуль авторизации
```

`d4e5f6a` — это и есть потерянный коммит: он всё ещё лежит в `objects/`, удаляет такие объекты только сборщик мусора, и то не сразу. Вернуть его на текущую ветку можно одной командой:

```bash
git reset --hard d4e5f6a
```

## 6. objects/

Это сердце и база данных Git. Сюда складывается абсолютно всё: содержимое файлов (`blob`), структура папок (`tree`) и метаданные коммитов (`commit`).

Два важных момента:
- Все файлы внутри `objects/` сжаты с помощью `zlib` для экономии места
- Именем каждого файла является уникальный **SHA-1 хеш** от его содержимого — изменился файл, изменился хеш

Из второго пункта следует важное следствие: если файл не изменился, у него не появится новый объект в `objects/` — хеш совпадёт с уже существующим, и Git просто сошлётся на старый объект, ничего не пересоздавая.

Это работает не только для файлов (`blob`), но и для целых неизменённых папок. У каждого коммита есть `tree` — объект-снимок структуры папок, где на каждый файл и вложенную папку есть запись с хешем: `blob` для файла, `tree` для подпапки. Если подпапка не менялась, её `tree`-объект в новом коммите — та же самая запись с тем же хешем, что и в предыдущем, без пересборки. Git не «копирует ссылку» отдельным действием: он видит, что объект с таким хешем уже есть в `objects/`, и новый не создаёт — дальше на него просто ссылается новый `tree`.

Важно не путать это с шардингом по директориям (ниже): та разбивка — просто про то, где физически на диске лежит файл с уже готовым хешем. Само переиспользование происходит не из-за директорий, а из-за того, что одинаковый контент всегда даёт одинаковый хеш.

Сами файлы разложены не по коммитам и не по файлам проекта, а по хешу — это шардинг: первые 2 символа SHA-1 становятся именем директории, оставшиеся 38 — именем файла внутри неё. Хеш `a1b2c3d4...` ляжет в `.git/objects/a1/b2c3d4...`.

Смысл шардинга чисто технический. Без разбивки все объекты лежали бы одним списком в одной папке, и на репозитории с десятками тысяч объектов файловая система начала бы тормозить на операциях с директорией. 256 возможных префиксов (`00`–`ff`) снимают эту проблему.

Группировки по файлам проекта или по коммитам здесь нет: один коммит создаёт сразу несколько объектов — сам `commit`, `tree` на структуру папок, `blob` на каждый изменённый файл, — и они расходятся по совершенно разным директориям в зависимости от того, что выпало по хешу. `blob`, `tree` и `commit` спокойно лежат вперемешку в одной `a1/`, если у них совпало начало хеша.

Новая директория появляется, только если выпал ещё не встречавшийся префикс — а префиксов всего 256, так что почти сразу все они уже существуют, и дальше новые объекты просто добавляются файлами в уже существующие папки.

Как и ветки в `refs/`, россыпь файлов в `objects/` тоже не бесконечна: `git gc` периодически упаковывает их в `.git/objects/pack/` — один компактный packfile вместо множества мелких файлов, — и часть директорий `objects/xx/` после этого пустеет.

## 7. refs/

Refs — это ссылки. Внутри `refs/heads/` лежат файлы имена которых совпадают с твоими локальными ветками. Ветка — это обычный текстовый файл весом 41 байт в котором записан хеш коммита на котором она сейчас стоит:

```bash
cat .git/refs/heads/main
# a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2
```

**⚠️ DevOps-ловушка — packed-refs:**

На свежем репозитории структура `refs/heads/` выглядит именно так. Но в реальном продакшене или на долгоживущих CI/CD раннерах Git периодически запускает внутренний сборщик мусора (`git gc`). В этот момент Git физически удаляет отдельные файлы веток из `.git/refs/heads/` и упаковывает их в один файл `.git/packed-refs` ради ускорения чтения диска.

**Никогда не читай хеш ветки напрямую через `cat`** в Bash-скриптах или CI/CD пайплайнах:

```bash
# ❌ НЕПРАВИЛЬНО — после первой оптимизации репозитория упадёт с ошибкой
cat .git/refs/heads/main

# ✅ ПРАВИЛЬНО — всегда используй эту команду
git rev-parse main
```

`git rev-parse` сам знает где сейчас лежит хеш — в отдельном файле или внутри `packed-refs`.
