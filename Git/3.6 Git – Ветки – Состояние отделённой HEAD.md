# 3.6 Git – Ветки – Состояние отделённой HEAD

## 1. Что такое detached HEAD

В обычном состоянии `HEAD` не содержит хеш коммита напрямую — это символическая ссылка на текущую ветку. Файл `.git/HEAD` хранит строку вида `ref: refs/heads/master`, а уже файл самой ветки в `refs/heads/master` содержит хеш последнего коммита. Вся обычная работа — коммиты, переключение веток — держится на этой цепочке: `HEAD` → ветка → коммит.

Detached HEAD — состояние, в котором звено «ветка» из этой цепочки выпадает. `HEAD` перестаёт ссылаться на имя ветки и начинает хранить хеш коммита напрямую — тот же самый хеш, который в обычном состоянии лежал бы в файле ветки. Отсюда и название: HEAD «отделяется» от ветки и указывает прямо на коммит.

Git переводит репозиторий в это состояние всякий раз, когда вы просите переключиться не на ветку, а на то, что веткой не является: на хеш коммита или на тег.

Смысл в том, чтобы не создавать ветку там, где она не нужна. Например, чтобы посмотреть, как выглядел код на конкретном коммите — проверить, воспроизводится ли баг на прошлой версии, — можно было бы завести отдельную ветку, но после такой проверки её пришлось бы удалять. Detached HEAD даёт ту же рабочую директорию в нужном состоянии без этого побочного эффекта: посмотрели, переключились обратно на `master` — и как будто не было.

## 2. Как войти и выйти из этого состояния

Переход в detached HEAD выполняется командой:

```bash
git switch --detach <хеш-коммита>
```

Флаг `--detach` обязателен. Если передать голый хеш без флага, `switch` откажется переключаться:

```bash
$ git switch 7aaf90f
fatal: a branch is expected, got commit '7aaf90f'
hint: If you want to detach HEAD at the commit, try again with the --detach option.
```

Это осознанное поведение команды: она ожидает имя ветки и не станет молча уводить в отделённое состояние, пока это не запрошено явно. С флагом переключение проходит без проблем:

```bash
$ git switch --detach 7aaf90f
HEAD is now at 7aaf90f add: модуль авторизации
```

`git status` и `git branch` сразу показывают, что вы больше не на ветке:

```bash
$ git status
HEAD detached at 7aaf90f
nothing to commit, working tree clean

$ git branch
* (HEAD detached at 7aaf90f)
  master
```

Файл ветки в `refs/heads/master` при этом вообще не трогается — как хранил хеш `0d8bee1`, так и хранит. Меняется только то, куда указывает `HEAD`.

Тот же флаг нужен и для тега — `git switch --detach v1.0` сработает точно так же, только `git status` покажет `HEAD detached at v1.0`, подставив имя тега вместо хеша для читаемости.

Выйти из отделённого состояния так же просто — переключиться на любую существующую ветку:

```bash
git switch master
```

## 3. Что происходит при коммитах в detached HEAD

Коммиты в отделённом состоянии делаются совершенно обычно, `git add` и `git commit` работают без ограничений. Разница — в том, что происходит с указателями после коммита.

В обычном состоянии новый коммит получает родителя из текущей ветки, после чего файл ветки в `refs/heads/` обновляется на хеш нового коммита, а `HEAD`, оставаясь символической ссылкой, автоматически «видит» этот коммит. В detached HEAD ветки в цепочке нет: родителем нового коммита становится тот хеш, что лежал в `.git/HEAD` до коммита, а после коммита в `.git/HEAD` напрямую записывается хеш уже нового коммита. Ни одна ветка при этом не двигается и не создаётся — коммит просто не принадлежит ничему, кроме самого `HEAD`.

На графе это видно наглядно. Если отделиться на коммите `add: модуль авторизации` и сделать там ещё один коммит:

```bash
$ git log --oneline --graph --decorate --all
* f33daa5 (HEAD) debug: проверка старой версии
| * 0d8bee1 (master) fix: исправление в API
|/
* 7aaf90f add: модуль авторизации
* 5c5758e init: базовая структура
```

Коммит `f33daa5` образует отдельное ответвление без имени — `HEAD` указывает прямо на него, а не через ветку, как это происходит с `master`.

Если теперь переключиться на другую ветку, коммит `f33daa5` останется недостижимым ни от одной ветки — переключение всё равно произойдёт, но Git предупредит об этом явно:

```bash
$ git switch master
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  f33daa5 debug: проверка старой версии

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> f33daa5

Switched to branch 'master'
```

Предупреждение появляется именно из-за этого нового коммита: если бы вы просто постояли на `7aaf90f`, не делая новых коммитов, и переключились обратно, Git ушёл бы молча — оставлять там было бы нечего.

Если проигнорировать предупреждение, коммит не исчезает немедленно, но перестаёт быть виден в обычной работе — `git log --all` проходит только по коммитам, достижимым от какой-нибудь ветки или тега, а этот коммит не достижим ни от одной ссылки:

```bash
$ git log --oneline --all
0d8bee1 fix: исправление в API
7aaf90f add: модуль авторизации
5c5758e init: базовая структура
```

Единственное место, где хеш `f33daa5` всё ещё зафиксирован, — reflog. Он ведёт собственную историю перемещений `HEAD`, не зависящую от веток и тегов:

```bash
$ git reflog
0d8bee1 HEAD@{0}: checkout: moving from f33daa5 to master
f33daa5 HEAD@{1}: commit: debug: проверка старой версии
```

Это подстраховка, а не гарантия навсегда. По умолчанию запись о недостижимом коммите хранится в reflog около 30 дней (`gc.reflogExpireUnreachable`), после чего коммит становится кандидатом на окончательное удаление при следующем запуске `git gc` — вручную или автоматически. Момент этого запуска заранее не известен, так что рассчитывать на то, что коммит провисит в reflog вечно, не стоит — искать его стоит сразу, не откладывая.

## 4. Практическое применение

Detached HEAD — не случайность и не ошибка сама по себе, а рабочий режим для ситуаций, когда нужен временный доступ к конкретному состоянию проекта без намерения оставлять там историю.

**Просмотр состояния проекта в прошлом.** Чтобы посмотреть, как выглядел код на конкретном коммите — открыть файлы, свериться со старой структурой, прогнать сборку, — переключение на хеш даёт рабочую директорию именно в этом состоянии, без создания веток, которые потом пришлось бы удалять.

**Проверка старой версии на баг.** Похожая ситуация — нужно понять, воспроизводится ли баг на более ранней версии кода, или найти коммит, после которого что-то сломалось. Сама временность detached HEAD сигнализирует, что эта работа не предназначена становиться частью истории проекта. Если по ходу всё же понадобится что-то сохранить, оставленные коммиты никуда не денутся из reflog, а Git явно предупредит при попытке уйти, не сохранив их.

**Сборка на конкретном коммите в CI/CD.** Раннеры GitLab CI и подобные системы получают для выполнения задачи не имя ветки, а конкретный хеш коммита и переключаются на него напрямую — сборка выполняется в отделённом состоянии, потому что раннеру нужен не указатель, который может сдвинуться, а ровно то состояние кода, для которого запущен пайплайн.

## 5. Как сохранить сделанную работу

Если коммиты в detached HEAD оказались важны, есть два способа их сохранить — выбор зависит от того, нужна отдельная ветка или изменения должны попасть в уже существующую.

**Создать ветку прямо на месте.** Проще всего создать ветку сразу, пока вы ещё в detached HEAD, не переключаясь предварительно на другую ветку:

```bash
$ git switch -c debug-check
Switched to a new branch 'debug-check'
```

Команда создаёт новую ветку в текущей позиции `HEAD` и сразу переключается на неё — вместо повисшего коммита в истории появляется полноценная ветка, видимая в `git branch` и `git log --all`. Хеш коммита указывать не нужно: раз `HEAD` уже стоит на нужном коммите, команда берёт его оттуда.

Если вы уже успели уйти на другую ветку и получили предупреждение, тот же результат даёт команда, которую предлагает сам Git в тексте предупреждения:

```bash
git branch <новое имя ветки> f33daa5
```

Разница в том, что `git branch` создаёт ветку, но не переключает на неё — вы остаётесь там, где были, а новая ветка просто указывает на сохранённый коммит.

**Перенести коммит на существующую ветку через cherry-pick.** Если отдельная ветка не нужна, а сделанный в detached HEAD коммит нужно добавить к истории уже существующей ветки — например, `master`, — применяется `git cherry-pick`. Команда работает по хешу коммита, поэтому ей неважно, лежит ли этот хеш на какой-то ветке или висит без привязки:

```bash
$ git switch master
$ git cherry-pick f33daa5
[master 1fbbad4] debug: проверка старой версии
 1 file changed, 1 insertion(+)
 create mode 100644 debug_notes.txt
```

Получившийся на `master` коммит новый, со своим хешем `1fbbad4`, хотя изменения в нём идентичны исходному `f33daa5`. Исходный коммит при этом никуда не девается и продолжает существовать как самостоятельный объект, пока не будет вычищен сборщиком мусора.
