# 5.4 Git – Reset – Смешанный reset (без флагов), сравнение видов reset

Три режима reset различаются тем, сколько уровней репозитория они меняют: `--soft` — только ветку, `--hard` — ветку, индекс и рабочую директорию разом. Смешанный режим (`--mixed`) — золотая середина: откатывает ветку и индекс, а рабочую директорию не трогает. Это поведение по умолчанию — если запустить `git reset` вообще без флагов, выполнится именно оно.

## Механика

`git reset <commit>` и `git reset --mixed <commit>` — одна и та же команда. Она переносит ветку на `<commit>` и перезаписывает индекс его состоянием, но не трогает рабочую директорию — файлы остаются такими, какими были.

Из-за этого расхождения между индексом и рабочей директорией git сообщает об изменениях как об unstaged сразу после выполнения:

```bash
$ git reset HEAD~1
Unstaged changes after reset:
M	file1.txt
```

Именно это делает смешанный reset удобным для переделки последних коммитов: содержимое отменённого коммита не исчезает, а превращается в обычные незакоммиченные изменения в рабочей директории. Дальше с ними можно поступить как угодно — доработать, застейджить выборочно через `git add` и разложить по нескольким более аккуратным коммитам.

## Сравнение режимов reset

Все три режима одинаково двигают HEAD — различаются они только тем, что происходит с индексом и рабочей директорией.

| Режим | HEAD | Индекс | Рабочая директория |
|---|---|---|---|
| `--soft` | перемещается | не меняется (изменения staged) | не меняется |
| `--mixed` (по умолчанию) | перемещается | сбрасывается (изменения unstaged) | не меняется |
| `--hard` | перемещается | сбрасывается | сбрасывается (данные удаляются) |

## Очистка индекса (Unstaging)

Если запустить `git reset` без указания коммита, целевым автоматически становится HEAD. Ветка при этом никуда не перемещается — она и так уже там, — а индекс сбрасывается до состояния HEAD. Эффект: всё, что было застейджено через `git add`, снимается с индекса, а сами изменения остаются в файлах — их можно отредактировать и добавить в индекс заново.

```bash
git add .
git status --short
```
```
M  file1.txt
M  file2.txt
```

После `git reset`:

```
 M file1.txt
 M file2.txt
```

По результату `git reset` — операция, обратная `git add`: один переносит изменения в индекс, другой убирает их оттуда.

## Сброс конкретных путей

В отличие от `--soft` и `--hard`, смешанный reset допускает указание конкретных путей: `git reset <path>` снимает с индекса изменения только указанного файла, не трогая остальные застейдженные файлы.

```bash
git reset file1.txt
```

Флаги `--soft` и `--hard` с путями несовместимы и завершаются ошибкой:

```
fatal: Cannot do hard reset with paths.
fatal: Cannot do soft reset with paths.
```

`--soft` вообще не трогает индекс, поэтому указывать путь для него бессмысленно, а `--hard` обязан синхронизировать все три уровня целиком, не выбирая отдельные файлы, — с путями работает только смешанный режим.

## Версия файла из другого коммита

`git reset file1.txt` (без указания коммита) и `git reset <commit> -- file1.txt` — одна и та же возможность работать с конкретным файлом, просто с разным источником версии: без указания коммита по умолчанию берётся HEAD (снятие с индекса из раздела выше), а с явно указанным коммитом в индекс попадает версия файла из этого коммита — любого коммита из истории, не обязательно HEAD.

```bash
git reset <commit> -- file1.txt
```

Ключевой момент: команда меняет только индекс, рабочую директорию не трогает — `cat file1.txt` покажет то же самое, что было до команды, а увидеть изменение можно только в индексе (`git show :file1.txt`, `git diff --staged`). Это создаёт намеренное расхождение между тем, что открыто в редакторе, и тем, что зафиксирует `git commit`: если рабочая директория к этому моменту уже отличалась и от HEAD, и от новой версии в индексе, `git status` покажет `MM` — первая `M` за расхождение индекса с HEAD (застейджено), вторая — за расхождение диска с индексом (не застейджено).

Практической пользы в ручной повседневной работе у этого почти нет. Единственный реальный сценарий — когда индекс осознанно готовится отдельно от диска: рабочая директория уже занята другими незакоммиченными правками, которые нельзя трогать, а в индекс всё равно нужно отдельно положить что-то для следующего коммита. На этом же принципе строятся другие команды — например, `git checkout --ours/--theirs <path>` при разрешении конфликтов мержа под капотом делает ровно то же самое: кладёт нужную версию в индекс, а с рабочей директорией разбираются отдельным шагом.

Если нужно, чтобы файл реально изменился и на диске — раньше для этого использовали `git checkout <commit> <path>`; современная замена — `git restore` с указанием источника и обоих целевых мест:

```bash
git restore --source=<commit> --staged --worktree file1.txt
```

## Практика

Выполни шаги по порядку в тестовом репозитории. После каждого шага сверяй вывод `git log --oneline --graph --decorate` и `git status --short` с тем, что описано — это и есть закрепление темы.

**Шаг 1. Три обычных коммита**

```bash
echo "line1" >> file.txt && git add file.txt && git commit -m "первый коммит"
echo "line2" >> file.txt && git add file.txt && git commit -m "второй коммит"
echo "line3" >> file.txt && git add file.txt && git commit -m "третий коммит"
git log --oneline --graph --decorate
```

**Шаг 2. Bare `git reset` — очистка индекса**

```bash
echo "line4" >> file.txt
git add file.txt
git status --short
git reset
git status --short
git log --oneline --graph --decorate
cat file.txt
```

Ветка в логе не сдвинулась. Файл в индексе (`M  file.txt`) стал unstaged (` M file.txt`), а `line4` осталась в файле — reset её не тронул.

Закоммить, чтобы продолжить:

```bash
git add file.txt
git commit -m "четвёртый коммит"
```

**Шаг 3. `git reset --mixed HEAD~1` — раскоммитить и разобрать по частям**

Типичный случай: в один коммит по ошибке попали две несвязанные вещи — правка существующего файла и новая фича. Смоделируем это:

```bash
echo "line5" >> file.txt
echo "feature code" > feature.txt
git add file.txt feature.txt
git commit -m "пятый коммит (правка + фича одним махом)"
git log --oneline --graph --decorate
```

Раскоммичиваем:

```bash
git reset HEAD~1
git status --short
git log --oneline --graph --decorate
```

Ветка вернулась на четвёртый коммит, а оба изменения — `file.txt` (unstaged) и `feature.txt` (untracked) — остались на диске. Теперь их можно застейджить и закоммитить раздельно:

```bash
git add file.txt
git commit -m "line5 в file.txt"
git add feature.txt
git commit -m "добавлен feature.txt"
git log --oneline --graph --decorate
```

Было два перемешанных изменения в одном коммите — стало два чистых отдельных коммита.

**Шаг 4. `git reset <path>` — сброс конкретного файла**

```bash
echo "line6" >> file.txt
echo "note1" > notes.txt
git add file.txt notes.txt
git status --short
git reset file.txt
git status --short
```

Оба файла были застейджены (`M  file.txt`, `A  notes.txt`), после `git reset file.txt` застейджен остался только `notes.txt`. Закоммить оба, чтобы продолжить:

```bash
git commit -m "шестой коммит: notes.txt"
git add file.txt
git commit -m "седьмой коммит"
git log --oneline --graph --decorate
```

**Шаг 5. `git reset <commit> -- <path>` и `git restore`**

Найди хеш коммита, в котором `file.txt` появился впервые (это первый коммит из шага 1 — если репозиторий уже жил до этого упражнения, самый первый коммит в нём вообще может ещё не содержать `file.txt`, поэтому ищем именно по файлу):

```bash
git log --oneline --follow -- file.txt
```

Нужен хеш из последней строки вывода.

Подставь его вместо `<commit>` дальше.

```bash
git show <commit>:file.txt
cat file.txt
git reset <commit> -- file.txt
git status --short
git show :file.txt
cat file.txt
git log --oneline --graph --decorate
```

`git status` покажет `MM file.txt`: первая `M` — версия в индексе (из найденного коммита) разошлась с HEAD, вторая — рабочая директория разошлась с индексом. Ветка не сдвинулась, файл на диске не изменился.

Теперь подтяни ту же версию и в рабочую директорию:

```bash
git restore --source=<commit> --staged --worktree file.txt
git status --short
cat file.txt
```

Индекс и рабочая директория теперь равны найденной версии, а отличие от HEAD видно как один staged `M`. Чтобы вернуть репозиторий в порядок:

```bash
git restore --source=HEAD --staged --worktree file.txt
git status --short
```
