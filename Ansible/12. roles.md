# 12. Roles — структура каталогов, переиспользование, `ansible-galaxy`

## 1. Зачем нужны роли

Всё, что написано в предыдущих темах, живёт в одном плейбуке: переменные, задачи, хендлеры, а рядом с плейбуком — общие каталоги `templates/` и `files/`. Пока play настраивает одну подсистему, это терпимо. Но в реальном проекте один play часто делает несколько вещей сразу: ставит nginx, настраивает sshd, заводит пользователей. В результате:

- плейбук разрастается до сотен строк, задачи разных подсистем перемешаны;
- шаблоны и файлы всех подсистем свалены в общие каталоги без привязки к задачам;
- переиспользовать код нельзя: понадобился тот же nginx в другом проекте — задачи, шаблоны и переменные копируются руками, и с этого момента существуют две расходящиеся копии.

**Роль (role)** — стандартизированная структура каталогов, которая упаковывает всё, что относится к одной функции хоста («настроенный nginx»), в единый переиспользуемый блок: задачи, хендлеры, шаблоны, файлы и переменные едут вместе.

Ключевое слово — «стандартизированная». Ansible знает эту структуру и подключает её автоматически — ничего не нужно подключать руками (полный разбор по каждому каталогу — таблица в разделе 2). Этот принцип называется *convention over configuration* («соглашение вместо конфигурации»).

Сама по себе роль не запускается — это строительный блок, «библиотека». Запускает её плейбук, который указывает хосты и перечисляет роли:

```yaml
# site.yml — плейбук, отдельный файл вне каталога роли
- name: "Configure web servers"
  hosts: webservers
  become: true
  roles:
    - nginx
    - sshd
```

Play отвечает на вопрос «что представляет собой эта группа хостов» — и это просто список ролей. Роль отвечает «как именно это настраивается». Если совсем коротко: роли для плейбуков — то же, что функции для скрипта.

## 2. Структура каталогов роли

Роли живут в каталоге `roles/` рядом с плейбуком. Полная структура (создаётся командой `ansible-galaxy init <имя>`):

```
roles/
  nginx/
    tasks/          # задачи роли
      main.yml      #   точка входа — единственный обязательный файл
    handlers/       # хендлеры роли
      main.yml
    defaults/       # переменные-параметры роли (самый низкий приоритет)
      main.yml
    vars/           # внутренние переменные роли (высокий приоритет)
      main.yml
    files/          # статические файлы (для ansible.builtin.copy)
    templates/      # шаблоны Jinja2 (для ansible.builtin.template)
    meta/           # метаданные: зависимости, автор, лицензия
      main.yml
    tests/          # заготовка для проверки роли (inventory + test.yml)
```

Все каталоги, кроме `tasks/`, опциональны: если роль не использует хендлеры — каталог `handlers/` можно не создавать (или удалить после `ansible-galaxy init`). Ansible молча пропускает отсутствующие каталоги.

Как Ansible подхватывает каждый каталог при подключении роли:

| Каталог | Что происходит автоматически |
|---|---|
| `tasks/main.yml` | Задачи вставляются в play |
| `handlers/main.yml` | Хендлеры регистрируются и доступны для `notify` |
| `defaults/main.yml` | Переменные загружаются с самым низким приоритетом |
| `vars/main.yml` | Переменные загружаются с высоким приоритетом |
| `files/` | `src` у `ansible.builtin.copy` ищется здесь без указания пути |
| `templates/` | `src` у `ansible.builtin.template` ищется здесь без указания пути |
| `meta/main.yml` | Читаются зависимости — они выполняются **до** задач роли |

### Одинаковый main.yml в разных ролях — не конфликт

Имена `main.yml` не конфликтуют, потому что лежат в разных папках:

```
roles/
  nginx/tasks/main.yml   # main.yml роли nginx
  sshd/tasks/main.yml    # main.yml роли sshd — совсем другой файл
```

Ansible находит нужный файл по имени папки роли, и это касается не только `tasks/`, а любого стандартного файла роли:

```yaml
# site.yml — плейбук, отдельный файл вне каталога роли
- hosts: webservers
  roles:
    - nginx    # → roles/nginx/tasks/main.yml, roles/nginx/defaults/main.yml, ...
    - sshd     # → roles/sshd/tasks/main.yml, roles/sshd/defaults/main.yml, ...
```

Главная суть: имя `main.yml` — это просто соглашение, Ansible всегда ищет точку входа с таким именем. А разница между ролями задаётся именем самой папки (`nginx`, `sshd`), которое должно точно совпадать (посимвольно, с учётом регистра) с тем, что написано в плейбуке. Что будет при несовпадении — раздел 7.

### files vs templates

В `files/` лежат файлы, которые копируются **как есть**, байт в байт. В `templates/` — файлы `*.j2`, которые перед доставкой обрабатываются движком Jinja2: подстановка переменных, условия, циклы (см. тему про шаблоны). Если в файле нет ни одной конструкции Jinja2 — ему место в `files/`.

### Если tasks/main.yml разросся

Пока в роли пара задач, всё нормально помещается в один `tasks/main.yml`. Но в нетривиальной роли задачи быстро накапливаются вперемешку — часть про установку, часть про конфигурацию:

```yaml
# roles/nginx/tasks/main.yml — всё в одном файле, без разделения
- name: "Install nginx package"
  ansible.builtin.apt:
    name: nginx
    state: present

- name: "Enable and start nginx service"
  ansible.builtin.service:
    name: nginx
    enabled: true
    state: started

- name: "Deploy nginx config"
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
  notify: Restart nginx

- name: "Deploy site config"
  ansible.builtin.template:
    src: site.conf.j2
    dest: /etc/nginx/conf.d/site.conf
  notify: Restart nginx
```

Уже на четырёх задачах видно две разные группы: первые две — про установку и запуск сервиса, вторые две — про его конфигурацию. На практике список продолжает расти (SSL-сертификаты, ротация логов, security-заголовки), и через полсотни строк такой мешанины сложно быстро найти нужную задачу.

Решение — разложить задачи по смыслу на несколько файлов внутри `tasks/`, а `main.yml` превратить в список ссылок на них. Разложим ровно эти четыре задачи по двум файлам — установка в один, конфигурация в другой:

```
roles/nginx/tasks/
  main.yml        # только ссылки, ни одной задачи напрямую
  install.yml
  configure.yml
```

```yaml
# roles/nginx/tasks/main.yml
- name: "Install nginx"
  ansible.builtin.import_tasks: install.yml

- name: "Configure nginx"
  ansible.builtin.import_tasks: configure.yml
```

```yaml
# roles/nginx/tasks/install.yml
- name: "Install nginx package"
  ansible.builtin.apt:
    name: nginx
    state: present

- name: "Enable and start nginx service"
  ansible.builtin.service:
    name: nginx
    enabled: true
    state: started
```

```yaml
# roles/nginx/tasks/configure.yml
- name: "Deploy nginx config"
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
  notify: Restart nginx

- name: "Deploy site config"
  ansible.builtin.template:
    src: site.conf.j2
    dest: /etc/nginx/conf.d/site.conf
  notify: Restart nginx
```

Ни одна задача не потерялась и не появилась — те же четыре, просто сгруппированы по файлам вместо одной кучи.

`install.yml` указан без пути (не `tasks/install.yml`) — `import_tasks`, вызванный изнутри `tasks/main.yml`, ищет файл рядом с собой, в том же каталоге.

`main.yml` при этом превращается в оглавление роли, а не в файл с задачами напрямую. Обрабатывается это статически: ещё до начала выполнения строка `import_tasks: install.yml` заменяется содержимым файла `install.yml`, как будто его задачи вписаны в `main.yml` вручную. Если файл нужно подключать динамически — по условию, которое вычисляется во время выполнения, или в цикле — вместо `import_tasks` используют `include_tasks`. Разница между ними подробно разобрана в разделе 5 на примере целых ролей (`import_role`/`include_role` работают по тому же принципу).

### Роль целиком: как всё это работает вместе

До сих пор каждый каталог разбирался отдельно. Соберём ту же nginx-роль полностью — добавим `defaults`, `handlers` и `templates` к уже написанным `tasks` — и пройдём по шагам, что именно делает Ansible при её запуске.

```
roles/nginx/
  defaults/
    main.yml
  handlers/
    main.yml
  tasks/
    main.yml
    install.yml
    configure.yml
  templates/
    nginx.conf.j2
    site.conf.j2
```

```yaml
# roles/nginx/defaults/main.yml
nginx_port: 80
```

```yaml
# roles/nginx/handlers/main.yml
- name: Restart nginx
  ansible.builtin.service:
    name: nginx
    state: restarted
```

```
# roles/nginx/templates/nginx.conf.j2
server {
    listen {{ nginx_port }};
    server_name _;
}
```

По той же схеме — второй шаблон, `site.conf.j2`:

```
# roles/nginx/templates/site.conf.j2
server {
    listen {{ nginx_port }};
    server_name example.com;
}
```

Вызов из плейбука:

```yaml
# site.yml — плейбук, отдельный файл вне каталога роли
- hosts: webservers
  become: true
  roles:
    - nginx
```

Что происходит по шагам:

1. Ansible видит `nginx` в `roles:` → ищет каталог `roles/nginx` (раздел 7).
2. `meta/main.yml` в этой роли нет — зависимостей нет, шаг пропускается (каталог необязателен, см. выше).
3. Загружается `defaults/main.yml`: переменная `nginx_port` со значением `80` становится доступна во всей роли.
4. Регистрируется `handlers/main.yml`: хендлер `Restart nginx` теперь известен Ansible, но ещё не выполняется — «на подхвате».
5. Выполняется `tasks/main.yml`: сначала `install.yml` — `ansible.builtin.apt` ставит пакет, затем `ansible.builtin.service` включает автозапуск и стартует сервис; после этого `configure.yml` — две задачи `ansible.builtin.template` рендерят `nginx.conf.j2` и `site.conf.j2`, подставляя `{{ nginx_port }}` → `80` в каждый, и кладут результат в `/etc/nginx/nginx.conf` и `/etc/nginx/conf.d/site.conf`. Обе задачи меняют файлы на диске и обе notify'ят `Restart nginx`.
6. Задачи роли закончились → хендлеры флашатся (раздел 4) → `Restart nginx` выполняется один раз, хотя notify пришёл от двух задач подряд — повторные notify одного и того же хендлера не запускают его повторно → сервис перезапущен с новым конфигом.

Поменяй `nginx_port` на `8080` в `defaults/` (или передай `vars: nginx_port: 8080` при вызове роли — раздел 4) — изменится только шаг 3, вся остальная цепочка отработает так же.

## 3. defaults vs vars — два вида переменных роли

Оба каталога содержат переменные, но их назначение противоположно.

**`defaults/main.yml` — параметры роли.** Это «настройки по умолчанию», которые вызывающая сторона *должна иметь возможность* переопределить: порт, версия пакета, путь к document root. Приоритет — самый низкий во всём Ansible: их перебивают переменные inventory, переменные play, параметры роли — практически всё.

```yaml
# roles/nginx/defaults/main.yml
nginx_port: 80
nginx_worker_processes: "auto"
```

**`vars/main.yml` — внутренние константы роли.** То, что менять извне не предполагается: внутренние пути, имена служб, служебные списки. Приоритет высокий: эти переменные **не** перебиваются inventory (ни `host_vars`, ни `group_vars`) и переменными play. Перебить их могут только переменные уровня задачи, `ansible.builtin.set_fact`, параметры, переданные при вызове роли, и `--extra-vars`.

Правило выбора:
- то, что пользователь роли может захотеть изменить — в `defaults/`;
- то, что менять нельзя — в `vars/`.

Благодаря `defaults/` роль превращается в подобие функции с аргументами по умолчанию.

## 4. Подключение роли в плейбуке

### Секция roles

```yaml
# site.yml — плейбук, отдельный файл вне каталога роли
- name: "Configure web servers"
  hosts: webservers
  become: true
  roles:
    - sshd                       # короткая форма
    - role: nginx                # полная форма — позволяет передать параметры
      vars:
        nginx_port: 8080         # сработает только для этой роли, не для sshd
```

Переменные, переданные через `vars:` при вызове, называются **параметрами роли** (role params) и действуют только для той роли, при вызове которой указаны. Приоритет очень высокий — они перебивают не только `defaults/`, но и `vars/main.yml` самой роли; перебить их может, по сути, только `--extra-vars`. Это и есть «вызов функции с аргументами».

### pre_tasks, post_tasks и порядок выполнения внутри play

Порядок выполнения секций play всегда фиксирован и не зависит от того, в какой последовательности они записаны в файле:

```
pre_tasks  →  (хендлеры, notify'нутые в pre_tasks)
роли из meta/main.yml (зависимости)
roles      →  задачи ролей в порядке перечисления
tasks      →  (хендлеры, notify'нутые в roles и tasks)
post_tasks →  (хендлеры, notify'нутые в post_tasks)
```

Главная ловушка: даже если записать `tasks:` в файле выше `roles:`, Ansible всё равно выполнит роли первыми — порядок задаётся этой схемой, а не расположением ключей в YAML.

`pre_tasks` и `post_tasks` из этой схемы — не каталоги роли, а такие же ключи плейбука, как `roles:` и `tasks:`. Пишутся в том же файле, на одном уровне с ними:

```yaml
# site.yml — плейбук, отдельный файл вне каталога роли
- name: "Configure web servers"
  hosts: webservers
  become: true
  pre_tasks:
    - name: "Update apt cache"
      ansible.builtin.apt:
        update_cache: true
  roles:
    - nginx
  tasks:
    - name: "Verify nginx responds"
      ansible.builtin.uri:
        url: "http://localhost"
  post_tasks:
    - name: "Notify deployment finished"
      ansible.builtin.debug:
        msg: "Done"
```

Важные следствия:

- Секция `roles:` выполняется **до** секции `tasks:` того же play, независимо от того, в каком порядке они записаны в файле.
- Хендлер срабатывает не в момент notify, а в конце текущего этапа (см. схему выше) — как и обычные хендлеры (см. тему про хендлеры). Например: роль `nginx` notify'ит `Restart nginx`, а следом в `tasks:` идут ещё две задачи, не связанные с nginx. Хендлер не запустится сразу после роли — он ждёт, пока отработают обе задачи `tasks:`, и срабатывает только тогда, одним блоком вместе с их хендлерами. Будь одна из этих задач пятиминутной — nginx перезапустился бы только через пять минут после того, как роль его настроила, а не сразу.

## 5. import_role и include_role — подключение из tasks

Роль можно подключать не только в блоке `roles:`, но и вызывать как обычную задачу через `import_role` или `include_role` (как в самом плейбуке, так и внутри других ролей).

Главное отличие — когда Ansible читает задачи подключаемой роли.

### import_role (статическое подключение)

Работает как Ctrl+C / Ctrl+V до старта плейбука. Ansible на этапе разбора файлов вытаскивает все задачи роли и вклеивает их на место вызова.

- Задачи роли видны в `--list-tasks` и поддерживают `--start-at-task`.
- Если повесить `when:`, он автоматически скопируется на каждую задачу внутри роли.
- Ограничение: ✗ нельзя использовать `loop`. Так как разбор происходит до старта, Ansible ещё не знает динамические элементы цикла.

```yaml
# site.yml — плейбук, отдельный файл вне каталога роли
- hosts: webservers
  tasks:
    - name: "Статическое подключение роли"
      ansible.builtin.import_role:
        name: nginx
      when: env == 'production'   # условие скопируется на все таски nginx
```

### include_role (динамическое подключение)

Работает как вызов функции прямо во время выполнения. Ansible идёт по плейбуку и, только дойдя до `include_role`, начинает читать и выполнять роль.

- Условие `when:` проверяется один раз: если `true` — вся роль выполняется, если `false` — пропускается целиком.
- Задачи роли не видны в `--list-tasks` до момента запуска.
- Главный плюс: ✓ работает в `loop` и позволяет крутить роль с разными параметрами.

```yaml
# site.yml — плейбук, отдельный файл вне каталога роли
- hosts: webservers
  tasks:
    # 1. Запуск роли в цикле
    - name: "Вызов роли для списка приложений"
      ansible.builtin.include_role:
        name: app_installer
      loop:
        - nginx
        - postgresql
      loop_control:
        loop_var: app_name

    # 2. Вызов по динамическому факту, полученному в ходе прогона
    - name: "Настроить Nginx, если он установлен"
      ansible.builtin.include_role:
        name: nginx
      when: "'nginx' in ansible_facts.packages"
```

Шпаргалка — что выбирать:

- По умолчанию — секция `roles:` или `import_role`.
- `include_role` нужен только в двух случаях: вызов роли в цикле (`loop`), или по условию, которое рассчитывается прямо во время выполнения плейбука (на основе фактов или `register`).

## 6. Зависимости ролей — meta/main.yml

В `meta/main.yml` роль может объявить, что для её работы нужна другая роль:

```yaml
# roles/webapp/meta/main.yml
dependencies:
  - role: nginx
    vars:
      nginx_port: 8080
```

Зависимости выполняются **до** задач самой роли. Механизм подходит для жёстких технических зависимостей, но в командах его часто избегают в пользу явного перечисления ролей в плейбуке — так порядок выполнения виден в одном месте, а не размазан по `meta/` разных ролей.

## 7. Где Ansible ищет роли

Как уже отмечалось в разделе 2 — имя роли ищется как обычное имя каталога на диске, посимвольно и с учётом регистра. Порядок поиска, по приоритету:

1. Каталог `roles/` рядом с плейбуком.
2. Каталоги из `roles_path` в `ansible.cfg`. Значение по умолчанию — сразу три пути: `~/.ansible/roles:/usr/share/ansible/roles:/etc/ansible/roles`.
3. Каталог самого плейбука.

Если совпадения нет ни по одному из путей, Ansible останавливается с ошибкой и прямо перечисляет всё, что проверил:

```
ERROR: The role 'nginx' was not found in:
  /project/roles:/root/.ansible/roles:
  /usr/share/ansible/roles:/etc/ansible/roles:/project
```

Список в сообщении об ошибке — это и есть три пункта выше, только второй развёрнут в свои три пути. Типичная причина такой ошибки — опечатка в имени роли или расхождение в регистре между `roles:` в плейбуке и именем каталога.

В проектах путь обычно фиксируют явно:

```ini
# ansible.cfg — в корне проекта, рядом с site.yml
[defaults]
roles_path = ./roles
```

Тогда и свои роли, и установленные через `ansible-galaxy` живут в одном каталоге внутри репозитория проекта.

## 8. ansible-galaxy

Под именем Ansible Galaxy живут два разных понятия:

1. **Сайт-репозиторий** [galaxy.ansible.com](https://galaxy.ansible.com) — публичный хаб, куда сообщество выкладывает готовые роли (и коллекции). Прежде чем писать роль для типовой задачи, имеет смысл поискать готовую.
2. **CLI-утилита `ansible-galaxy`** — инструмент для создания, установки и управления ролями. Работает и без сайта: скаффолдинг и установка из Git к galaxy.ansible.com не привязаны.

### Создание своей роли

Команда запускается по разу на каждую роль — под nginx свой вызов, под sshd свой:

```bash
ansible-galaxy init roles/nginx
ansible-galaxy init roles/sshd
```

Создаёт полный скелет роли: все стандартные каталоги с пустыми `main.yml`. Избавляет от рутины и гарантирует стандартную структуру. Неиспользуемые каталоги после генерации можно удалить.

Каталог `roles/` заранее создавать не нужно: если передать путь (`roles/nginx`), а не голое имя, Ansible сам создаст все промежуточные каталоги, включая сам `roles/`. Команда одинаково работает и из корня проекта с путём, и изнутри `roles/` с коротким именем (`ansible-galaxy init nginx`) — результат идентичен.

Повторный запуск на уже существующую директорию роли завершится ошибкой и потребует флаг `--force`, который сбрасывает содержимое `main.yml`-файлов до пустых заготовок — если роль уже написана, `--force` сотрёт код.

### Установка готовой роли

```bash
ansible-galaxy install geerlingguy.nginx
```

Имя состоит из `<автор>.<роль>`. По умолчанию роль ставится в `~/.ansible/roles/`; с `roles_path = ./roles` в `ansible.cfg` — в каталог проекта. Путь можно указать и разово: `ansible-galaxy install -p ./roles <имя>`.

### requirements.yml — зависимости проекта как код

Вместо установки ролей руками по одной, в проекте заводят файл `requirements.yml` со списком всех внешних ролей — по аналогии с `requirements.txt` в Python:

```yaml
# requirements.yml — в корне проекта, рядом с site.yml
- src: geerlingguy.nginx
  version: "3.1.0"              # фиксация версии — обязательная практика

- src: https://github.com/example/ansible-role-firewall.git
  scm: git                      # установка напрямую из Git-репозитория
  name: firewall                # имя, под которым роль будет доступна
  version: main                 # ветка, тег или commit hash
```

Установка всего списка одной командой:

```bash
ansible-galaxy install -r requirements.yml
```

Так окружение проекта воспроизводимо: новый инженер (или CI) клонирует репозиторий, выполняет одну команду — и получает те же роли тех же версий. Версии фиксируются всегда: `version` с тегом для Galaxy-ролей, тег или commit hash для Git — иначе очередная установка может молча притащить несовместимую версию.

## 💡 Типичные вопросы на собеседовании

**Q: В чём разница между ролью и плейбуком?**
A: Плейбук — сценарий запуска: привязывает задачи к хостам и исполняется командой `ansible-playbook`. Роль — упакованный переиспользуемый блок из задач, переменных, шаблонов и хендлеров; сама по себе не запускается — её подключает плейбук. Плейбук без ролей — скрипт; роль — библиотека.

**Q: Чем defaults/main.yml отличается от vars/main.yml?**
A: Приоритетом и назначением. `defaults` — самый низкий приоритет во всём Ansible: это параметры роли, которые вызывающая сторона переопределяет через inventory, переменные play или параметры роли. `vars` — высокий приоритет: внутренние константы роли, которые **не** перебиваются inventory и переменными play; перебить их могут только переменные задачи, `set_fact`, параметры при вызове роли и `--extra-vars`.

**Q: В чём разница между include_role и import_role?**
A: `import_role` — статика: роль встраивается на этапе разбора плейбука; `loop` невозможен, `when` копируется на каждую задачу роли; задачи видны в `--list-tasks`. `include_role` — динамика: роль подключается в момент выполнения; работает в `loop` и под `when` (условие проверяется один раз); задачи заранее не видны.

**Q: В каком порядке выполняются секции play при использовании ролей?**
A: `pre_tasks` → зависимости из `meta/main.yml` → `roles` → `tasks` → `post_tasks`, с флашем хендлеров после каждой секции. Секция `roles:` всегда выполняется раньше `tasks:`, независимо от порядка записи в файле.

**Q: Что будет, если две роли определяют хендлер с одинаковым именем?**
A: Это источник трудноуловимых ошибок, и поведение при конфликте имён менялось между версиями Ansible — полагаться на него нельзя. Надёжные практики: давать хендлерам уникальные имена с префиксом роли (`nginx : reload service`); Ansible и сам регистрирует хендлеры ролей под квалифицированным именем `<роль> : <имя хендлера>`, по которому их можно notify'ить однозначно. Для развязки имён также существует ключ `listen` — хендлеры подписываются на тему, а `notify` указывает тему, а не имя.

**Q: Что делает ansible-galaxy init?**
A: Создаёт стандартный скелет роли — все каталоги (`tasks`, `handlers`, `defaults`, `vars`, `files`, `templates`, `meta`, `tests`) с заготовками `main.yml`. Путь можно передавать сразу с подкаталогом (`ansible-galaxy init roles/nginx`) — промежуточные каталоги, включая `roles/`, создаются автоматически. Повторный запуск на уже существующую роль требует `--force` и сбрасывает файлы `main.yml`.

**Q: Где Ansible ищет роли?**
A: Сначала в `roles/` рядом с плейбуком, затем по путям из `roles_path` в `ansible.cfg` (по умолчанию — `~/.ansible/roles:/usr/share/ansible/roles:/etc/ansible/roles`), затем в каталоге самого плейбука. Имя роли должно точно совпадать с именем каталога — иначе Ansible завершится ошибкой `the role 'X' was not found`, перечислив все проверенные пути.

**Q: Как зафиксировать внешние роли проекта?**
A: Файлом `requirements.yml` со списком ролей и закреплёнными версиями (тег для Galaxy, тег/commit для Git) + `ansible-galaxy install -r requirements.yml`. Это делает окружение воспроизводимым.
