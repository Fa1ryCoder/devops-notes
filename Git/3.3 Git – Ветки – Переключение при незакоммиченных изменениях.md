# 3.3 Git – Ветки – Переключение при незакоммиченных изменениях

## Проблема

При попытке переключиться на другую ветку, имея в рабочей директории незавершённые изменения, `git switch` может отказать в переключении с ошибкой вида `error: Your local changes to the following files would be overwritten by checkout`. Дело в том, что версия файла в рабочей директории отличается от той, что зафиксирована в целевой ветке. Если бы Git позволил переключиться молча, содержимое файла было бы заменено версией из целевой ветки, а незакоммиченная правка потерялась бы безвозвратно. Поэтому Git останавливает операцию и ждёт от вас решения — что делать с этими изменениями.

Важно, что это не универсальный блок «нельзя переключаться, пока в рабочей директории есть правки». Git проверяет каждый изменённый файл отдельно и сравнивает две вещи: текущую версию файла и версию, которая лежит в целевой ветке. Ошибка возникает только там, где эти версии расходятся. Если файл в обеих ветках идентичен, переключение пройдёт беспрепятственно даже с незакоммиченными правками в этом файле — к этому случаю мы ещё вернёмся.

## Почему не стоит коммитить «на всякий случай»

Первое, что приходит в голову при виде такой ошибки, — сделать быстрый коммит, чтобы Git отстал. Это плохая идея. Коммит — это осмысленный, целостный шаг в истории, а не способ обойти техническое ограничение. «Аварийный» коммит с недописанным кодом или временной заглушкой засоряет историю: через месяц при чтении лога будет непонятно, зачем он там нужен, а при попытке отследить, когда появилась конкретная фича, придётся продираться через такие технические коммиты. Для ситуации «мне нужно временно освободить рабочую директорию, не создавая коммит» в Git есть специальный инструмент — `git stash`, о нём ниже.

## Способ 1: принудительное переключение

Если незакоммиченные изменения на самом деле не нужны и их можно потерять, применяется флаг принудительного переключения.

Современная команда `git switch` использует для этого флаг `-f`:

```bash
git switch -f master
```

Git заменит содержимое конфликтующих файлов версиями из ветки `master`, а все текущие незакоммиченные правки в них будут удалены без возможности восстановления. Это осознанное действие — Git не спрашивает подтверждения второй раз, поэтому применять флаг стоит только тогда, когда вы точно уверены, что изменения не нужны.

Отдельный частый случай — нужно не переключиться на другую ветку, а просто откатить рабочую директорию к последнему коммиту текущей ветки, отбросив все локальные правки. Для этого используется команда `git restore`:

```bash
git restore .
```

Она возвращает все отслеживаемые файлы к состоянию последнего коммита, но не трогает неотслеживаемые файлы (те, что ещё ни разу не попадали в индекс). Если нужно удалить и их, добавляется `git clean -fd`.

## Способ 2: git stash

Когда изменения важны и их нужно сохранить, используется временное хранилище.

```bash
git stash
```

Git собирает все незакоммиченные изменения, убирает их из рабочих файлов и сохраняет отдельно в хранилище, никак не привязывая к текущей ветке. Рабочая директория становится идентична последнему коммиту, и переключение между ветками больше ничем не блокируется.

Чтобы вернуть сохранённые правки обратно:

```bash
git stash pop
```

Здесь есть нюанс, о котором стоит помнить. Git не запоминает, «для какой ветки» были сделаны спрятанные изменения — стек общий для всего репозитория. Это удобно, если вы намеренно хотите перенести правку с одной ветки на другую: сделали `stash` в одной ветке, переключились, применили `stash pop` — и правка оказалась там, где нужно. Но если применить `pop` не в той ветке, в которой изменения задумывались, и файл там успел разойтись сильнее, чем в исходной ветке, Git может выдать конфликт слияния прямо при восстановлении из стека — придётся разрешать его так же, как обычный конфликт при слиянии веток.

## Способ 3: изменения переезжают вместе с вами

Третий случай — не столько способ решения, сколько особенность поведения, которую полезно знать заранее. Ошибка при переключении возникает не из-за самого факта незакоммиченных изменений, а из-за расхождения версии файла между ветками. Если файл, в котором есть незакоммиченные правки, в обеих ветках выглядит одинаково — переключение пройдёт без единой ошибки, и Git ничего не потребует у вас решать.

В этом случае незакоммиченные изменения просто остаются в рабочей директории — вы как будто переносите их с собой в новую ветку. Git сообщает об этом, помечая такие файлы буквой `M` (modified) в выводе после переключения:

```
Switched to branch 'feature-login'
 M src/utils.js
```

## Риски и на что смотреть

Главная опасность автоматического переноса — не техническая, а невнимательность: несложно не заметить пометку `M` в выводе и в итоге закоммитить изменения не в ту ветку. Разберём по шагам, как это происходит.

1. Вы работаете в ветке `feature-login`, правите файл `config.js` — добавляете настройку для новой фичи. Изменения ещё не закоммичены.
2. Коллега просит помочь разобраться с багом в `master`. Переключаетесь: `git switch master`.
3. Последний коммит `config.js` в `master` на данный момент идентичен закоммиченной версии в `feature-login` — ветки по этому файлу ещё не разошлись. Поэтому Git не блокирует переключение, а незакоммиченная правка едет вместе с вами. Важно: одинаковы именно закоммиченные версии файла, а сама правка — это новые строки, которых нет ни в одном коммите ни одной из веток, она просто лежит в рабочей директории поверх файла.
4. В выводе проскакивает строка `M config.js`, но её легко не заметить среди прочего текста в терминале.
5. Вы находите причину бага, правите её прямо в `master` и коммитите фикс — например, командой `git add . && git commit`. Эта команда добавляет в коммит не только сам фикс, но и заодно `config.js`, который так и остался изменённым с прошлого шага.
6. Правка, которая по смыслу принадлежит `feature-login`, попадает в историю `master`: привязывается к его коммитам, будет видна там при `git log`, хотя задумывалась для совсем другой ветки.

Формально Git тут ничего не нарушает: переключение он блокирует, если версии файла в ветках расходятся, а вот сам коммит не в ту ветку — не останавливает ничем.

Поэтому после каждого переключения, если в рабочей директории до этого были правки, стоит на пару секунд задержаться на выводе команды. Если увидели `M` напротив файла и понимаете, что эта правка не должна была попасть в текущую ветку — не коммитьте её, а вернитесь и переложите в `stash`, после чего примените уже в нужном месте.
