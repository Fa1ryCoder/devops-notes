# 3. Ad-hoc команды и модули Ansible

## Что такое ad-hoc команды

Ad-hoc (от латинского "для этого случая") — это запуск одного конкретного действия прямо из командной строки, без написания плейбука. Способ сказать Ansible: "зайди на эти машины и сделай вот это прямо сейчас".

Структура команды всегда одна и та же:

```bash
ansible <группа> -m <модуль> -a "<аргументы>" -i <inventory>
```

- `<группа>` — кто выполняет (группа из inventory или конкретный хост)
- `-m` — какой модуль использовать
- `-a` — аргументы модуля (что именно сделать)
- `-i` — путь к inventory (если не прописан в `ansible.cfg`)

**Про флаг `-a`:** расшифровывается как "module arguments" — сюда передаются данные для модуля, но что именно, зависит от самого модуля. Например, `command` ждёт команду (`"df -h"`, `"uptime"`), `apt` — пары ключ=значение (`"name=nginx state=present"`), `copy` — пути (`"src=/файл dest=/куда"`), а `ping` вообще работает без `-a`.

Без `-a` упадут только те модули, которым параметры обязательны (например, `command` — непонятно что выполнять). Остальные обойдутся и без него.

---

## Зачем это нужно, если есть плейбуки

Ad-hoc удобен для:
- **Быстрой диагностики** — проверить дисковое пространство на всех серверах одной командой.
- **Разовых действий** — перезапустить сервис, не писать ради этого плейбук.
- **Тестирования модулей** — прежде чем писать плейбук, проверить что модуль делает именно то, что нужно.

---

## Основные модули

Модулей в Ansible сотни, но на практике 80% задач закрывают около десятка:

| Модуль | Что делает |
|---|---|
| `ping` | Проверка связи |
| `command` | Выполнить команду на хосте |
| `shell` | Выполнить команду через `/bin/sh` (поддерживает пайпы, переменные окружения) |
| `apt` | Управление пакетами (установка, удаление, обновление) |
| `copy` | Скопировать файл с control node на хост |
| `fetch` | Скопировать файл с хоста на control node |
| `file` | Создать/удалить файл или директорию, поменять права |
| `service` / `systemd` | Запустить/остановить/перезапустить сервис |
| `template` | Скопировать файл с подстановкой переменных (Jinja2) |
| `user` | Создать/удалить пользователя |

## Три способа передать аргументы модулю

Аргументы в `-a` можно оформлять по-разному — конкретный вариант зависит от модуля и от того, что именно нужно передать.

### Классический стиль «ключ=значение»

Самый популярный способ для большинства стандартных модулей (`apt`, `user`, `service`, `copy` и т.д.). Параметры перечисляются через пробел внутри двойных кавычек.

```bash
ansible all -m user -a "name=alex state=present shell=/bin/bash"
```

### Свободный стиль (Free-Form)

Используется только в тех модулях, которые принимают на вход одну текстовую строку (`command`, `shell`, `raw`, `script`). Никаких знаков `=` здесь не нужно.

```bash
ansible webservers -m shell -a "uptime && free -m"
```

### Смешанный стиль (Free-Form + аргументы модуля)

Используется с модулями вроде `command` или `shell`. Сначала пишется сама команда (free-form), а через пробел — служебные параметры модуля (например, `chdir` — в какой папке запустить, или `creates`/`removes` — условие запуска).

```bash
ansible all -m command -a "make install chdir=/usr/src/app creates=/usr/local/bin/myapp"
```

В этом примере `make install` — свободная команда, а `chdir` и `creates` — параметры самого модуля.

## Модуль `command` — выполнить команду на хосте

Самый базовый модуль. Он просто берёт указанную утилиту и запускает её на удалённой машине напрямую, без привлечения командной оболочки (шелла).

```bash
# Проверить свободное место на дисках всех веб-серверов
ansible webservers -m command -a "df -h" -i inventory/hosts.yml

# Посмотреть аптайм веб-серверов
ansible webservers -m command -a "uptime" -i inventory/hosts.yml
```

**📋 Разбор ответа Ansible**

Когда команда выполнится, вы увидите подобный ответ в терминале:

```
web-01 | CHANGED | rc=0 >>
 21:03:38 up 13 days,  4:33,  6 users,  load average: 0.01, 0.10, 0.21
```

Первая строка — это стандартный сервисный заголовок Ansible. Он всегда строится по жёсткой схеме:

```
<имя_хоста> | <статус> | rc=<код> >>
```

- `web-01` — локальное имя-маска (алиас) хоста из файла inventory.
- `CHANGED` — статус (результат) выполнения.
- `rc=0` — Return Code (код возврата). `0` всегда означает, что Linux-команда завершилась успешно. Любое другое число — признак ошибки.
- `>>` — разделитель, указывающий, что ниже идёт чистый текст, который вернула сама команда.

**Важно:** у `command`/`shell` после заголовка идёт то, что напечатала сама команда — обычный текст. А специализированные модули (вроде `apt` или `file`) никакую команду не запускают, им нечего «печатать» — вместо этого они возвращают структурированный отчёт о своей работе в виде JSON-словаря: что изменилось, какие значения выставлены. Сам заголовок при этом остаётся точно таким же:

```
web-01 | CHANGED => {
    "changed": true,
    "cache_updated": false,
    "stdout": "...",
    ...
}
```

**🎨 Четыре глобальных статуса Ansible**

В зависимости от исхода операции, имя хоста и статус подкрашиваются в терминале разными цветами:

- `SUCCESS` (зелёный) — задача выполнилась успешно, но система уже была в нужном состоянии, поэтому никаких изменений не произошло (например: вы запускали старт сервиса, а он и так уже работал).
- `CHANGED` (жёлтый) — сценарий отработал успешно, и состояние системы изменилось.
- `FAILED` (красный) — произошла ошибка внутри самого сервера (например, вы опечатались в команде). Код возврата `rc` при этом будет отличным от нуля.
- `UNREACHABLE` (красный) — Ansible вообще не смог достучаться до хоста (упала сеть, выключено питание или заблокирован SSH).

**🛠️ Подвох статуса `CHANGED` у модулей `command` и `shell`**

Вы заметите, что обычные команды (`df -h`, `uptime`) всегда возвращают жёлтый статус `CHANGED`. Почему так?

**Как ведут себя «умные» модули (`apt`, `file`, `template`):** они написаны на Python. Перед работой они заглядывают в систему, сравнивают её текущее состояние с тем, что вы просите, и если пакет уже стоит или папка создана — спокойно возвращают зелёный `SUCCESS`.

**Как ведут себя `command` и `shell`:** они «слепые». Ansible видит только факт запуска бинарника и код `rc=0`. Он физически не знает, поменяла ли утилита что-то на диске или нет. Поэтому Ansible действует из соображений паранойи: «Я что-то успешно запустил на хосте, а значит состояние системы потенциально изменилось» — и на всякий случай красит ответ в жёлтый `CHANGED`.

**⚠️ Ограничение модуля `command`**

Поскольку модуль запускает утилиты напрямую, минуя командную оболочку (шелл), он категорически не поддерживает:

- Пайпы и конвейеры (символ `|`) — нельзя отфильтровать вывод через `grep`.
- Перенаправления потоков в файлы (символы `>`, `>>`).
- Чтение системных переменных окружения (например, `$PATH` или `$USER`).

Если нужен этот функционал, вместо `command` используется модуль `shell`, который разберём далее.

## Модуль `shell` — команда через `/bin/sh`

Работает так же как `command`, но выполняет команду через полноценный шелл. Поддерживает пайпы, перенаправления, переменные окружения.

```bash
# Пайп — найти все запущенные nginx-процессы на хостах
ansible webservers -m shell -a "ps aux | grep nginx | grep -v grep" -i inventory/hosts.yml

# Проверить последние строки лога
ansible webservers -m shell -a "tail -n 20 /var/log/nginx/error.log" -i inventory/hosts.yml

# Перенаправление > — сохранить список процессов в файл на хосте
ansible webservers -m shell -a "ps aux > /tmp/processes.txt" -i inventory/hosts.yml

# Перенаправление >> — дописать в конец файла (не перезаписывая)
ansible webservers -m shell -a "date >> /tmp/audit.log" -i inventory/hosts.yml

# Переменная окружения — узнать под каким пользователем реально выполняется команда
ansible webservers -m shell -a 'echo $USER' -i inventory/hosts.yml
```

**Про кавычки в `-a`:** если обернуть аргумент в двойные кавычки (`"echo $USER"`), локальный шелл на управляющем сервере подставит значение `$USER` ещё до отправки команды на хосты — на хостах выполнится уже `echo alex` вместо `echo $USER`. Чтобы переменную читал именно шелл внутри удалённого хоста, используются одинарные кавычки (`'echo $USER'`) — они запрещают локальному шеллу раскрывать переменные.

## Модуль `apt` — управление пакетами (для Ubuntu/Debian)

Используется для установки, обновления или удаления программ.

Ключевые параметры:

| Параметр | Что делает |
|---|---|
| `name` | Имя пакета |
| `state` | `present` — установить, `absent` — удалить, `latest` — обновить до последней версии |
| `update_cache` | `yes` — выполнить `apt update` перед установкой |

Полный список параметров — в документации модуля [ansible.builtin.apt](https://docs.ansible.com/ansible/latest/collections/ansible/builtin/apt_module.html).

```bash
# Установить утилиту curl на все веб-серверы
ansible webservers -m apt -a "name=curl state=present" -i inventory/hosts.yml

# Удалить ненужный пакет (например, nmap)
ansible webservers -m apt -a "name=nmap state=absent" -i inventory/hosts.yml

# Обновить кэш репозиториев (аналог команды apt update)
ansible webservers -m apt -a "update_cache=yes" -i inventory/hosts.yml
```

Обрати внимание на параметры `state=present` (установить, если нет) и `state=absent` (удалить, если есть). Это чистый пример декларативного подхода Ansible.

## Модули `copy` и `fetch` — работа с файлами по сети

`copy` — отправляет файл с управляющего сервера на хосты. `fetch` — наоборот, забирает файл с удалённого хоста на управляющий сервер.

```bash
# Залить обновлённый конфиг на все веб-серверы
ansible webservers -m copy -a "src=/tmp/nginx.conf dest=/etc/nginx/nginx.conf" -i inventory/hosts.yml

# Стянуть лог с одного конкретного проблемного хоста для анализа
ansible web-01 -m fetch -a "src=/var/log/nginx/error.log dest=/tmp/logs/" -i inventory/hosts.yml
```

При использовании `fetch` Ansible не просто кладёт файл в `dest` — он воспроизводит внутри неё полную структуру: имя хоста и полный путь к файлу на удалённой машине. То есть файл из примера выше ляжет не в `/tmp/logs/error.log`, а в:

```
/tmp/logs/web-01/var/log/nginx/error.log
```

Это сделано специально — если забирать одноимённые файлы с нескольких хостов сразу, они не перезапишут друг друга, каждый окажется в своей подпапке с именем хоста.

⚠️ **Ограничение `fetch`:** работает только с одиночными файлами, директории не поддерживаются. Для скачивания целой директории есть два способа: универсальный — через `shell` запаковать директорию в архив `tar` на хосте, потом забрать архив через `fetch`; или через модуль `synchronize` (обёртка над `rsync`) — удобнее, но требует наличия `rsync` на обеих машинах.

## Модуль `file` — управление правами, папками и ссылками

Нужен для создания каталогов, удаления старых файлов и выставления прав (`chmod` / `chown`).

```bash
# Создать папку под новые логи и выставить владельца и права
ansible webservers -m file -a "path=/var/log/myapp state=directory owner=www-data group=www-data mode=0755" -i inventory/hosts.yml

# Удалить временный файл с хостов
ansible webservers -m file -a "path=/tmp/old_dump.sql state=absent" -i inventory/hosts.yml
```

## Модуль `systemd` — управление службами

Позволяет запускать, останавливать, перезапускать сервисы на хостах, а также управлять их автозагрузкой.

```bash
# Массово перезапустить веб-сервер
ansible webservers -m systemd -a "name=nginx state=restarted" -i inventory/hosts.yml

# Остановить службу sshd и убрать её из автозагрузки
ansible webservers -m systemd -a "name=sshd state=stopped enabled=no" -i inventory/hosts.yml
```

## Модуль `user` — управление пользователями

Создаёт, изменяет или удаляет системных пользователей на удалённых машинах.

```bash
# Создать пользователя ansible на всех хостах
ansible webservers -m user -a "name=ansible shell=/bin/bash state=present" -i inventory/hosts.yml

# Удалить пользователя с хостов
ansible webservers -m user -a "name=olduser state=absent remove=yes" -i inventory/hosts.yml
```

Параметр `remove=yes` при `state=absent` дополнительно удаляет домашнюю директорию пользователя.

## 🛠️ Полезные фишки ad-hoc команд

**Группа `all`:** если нужно выполнить команду по всем хостам из инвентаря, вместо имени конкретной группы пишется `all`:

```bash
ansible all -m ping -i inventory/hosts.yml
```

**Режим проверки (`--check`):** флаг `-C` заставляет Ansible симулировать выполнение — зайдёт на хосты, покажет что изменилось бы, но физически на диск ничего не запишет. Идеально для безопасного аудита перед реальным запуском:

```bash
ansible webservers -m apt -a "name=curl state=present" -C -i inventory/hosts.yml
```

**Запуск с повышением прав (`-b`):** если модулю нужны root-права (например, для установки пакетов), добавляется флаг `-b` (become):

```bash
ansible webservers -m apt -a "name=htop state=present" -b -i inventory/hosts.yml
```
