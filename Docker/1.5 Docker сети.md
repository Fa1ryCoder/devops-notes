# Сети Docker

## Network namespace: изоляция на уровне ядра

Когда Docker запускает контейнер, он вызывает runc, а тот через системный вызов clone() с флагом CLONE_NEWNET создаёт новый network namespace. Это отдельное пространство сетевых ресурсов внутри ядра: свои интерфейсы, своя таблица маршрутизации, свои iptables/nftables-правила и своё адресное пространство портов. Сразу после создания в этом namespace есть только loopback-интерфейс (lo), никакого eth0 ещё нет.

Чтобы у контейнера появилась связь с внешним миром, Docker создаёт veth-пару — это два конца одного виртуального кабеля. Один конец помещается внутрь нового namespace и переименовывается в eth0, второй остаётся в namespace хоста и подключается к виртуальному мосту (docker0). Именно поэтому у контейнера появляется "свой" eth0 с собственным IP, который никак не связан напрямую с физическим сетевым интерфейсом хоста.

На практике часто нужно узнать, к какой сети подключён контейнер и какой у него IP. Самый простой способ сделать это без входа в сам контейнер — использовать docker inspect:

```bash
docker inspect web | grep -A 15 Networks
```

Практическое следствие: network namespace — это настоящий объект ядра. Поэтому его можно изучать прямо с хоста, даже не делая docker exec.

Работать с namespace контейнера напрямую можно через nsenter — она умеет заходить в namespace процесса прямо по его PID. Получить PID контейнера нам как раз поможет docker inspect:

```bash
# 1. Узнаем PID контейнера в системе:
docker inspect -f '{{.State.Pid}}' web

# 2. Смотрим сетевые интерфейсы контейнера с хоста, используя полученный PID:
sudo nsenter -t <PID> -n ip addr
```

Это незаменимый способ отладки в ситуациях, когда в контейнере нет shell-оболочки (например, при использовании distroless-образов) или когда контейнер падает с ошибкой ещё до полного старта основного процесса.

## Драйверы и режимы сети: bridge, host, none, macvlan/ipvlan

Все сетевые драйверы решают одну и ту же задачу — как обеспечить контейнеру связь с внешним миром и другими контейнерами, но с разными компромиссами между изоляцией, производительностью и интеграцией с физической сетью.

**bridge** используется по умолчанию и годится для обычных веб-сервисов, баз данных и микросервисов на одном сервере, которым нужна изоляция. Контейнер сидит в закрытой подсети со своим приватным IP, который снаружи не виден. Чтобы зайти внутрь, нужен явный проброс портов флагом -p 8080:80, а наружу трафик идёт через NAT хоста — примерно как домашний роутер выпускает телефон в интернет. Это дефолтная сеть — Docker создаёт её автоматически, и DNS-сервера в ней нет: контейнеры внутри видят друг друга только по IP. Чтобы DNS работал, сеть создают вручную командой docker network create — пример ниже, в разделе «Практика: имя вместо IP».

**host** отключает сетевую изоляцию полностью: у контейнера нет собственного network namespace, он использует сетевой стек самого хоста напрямую. Если процесс внутри слушает порт 80, он и на хосте занимает именно порт 80 — без выбора и без возможности его подменить, в отличие от bridge, где выбором порта можно управлять с помощью флага -p. Маппинга портов в host-режиме просто не существует: -p нечего мапить, поэтому флаг игнорируется. Берут этот режим ради скорости: в bridge каждый пакет ещё и проходит через veth, программный свитч docker0, а на выходе ядро подменяет IP контейнера на IP хоста и обратно (NAT), в host-режиме всего этого попросту нет. Либо берут его, когда сервису нужно самому управлять сетью хоста. Плата — никакой изоляции: два контейнера с одним и тем же портом одновременно не запустятся, будет конфликт.

**none** создаёт контейнеру network namespace, но не подключает его ни к чему, кроме loopback: сети нет вообще, никакой. Годится для автономных задач без сети по определению — пакетной обработки, генерации ключей, изолированных вычислений, где утечка в сеть недопустима в принципе.

**macvlan** обходит мост и NAT Docker целиком и подключает контейнер прямо к физической сети хоста: контейнер получает обычный IP из той же подсети, что и сам хост, как если бы в коммутатор воткнули ещё одну машину. Драйвер создаёт для контейнера виртуальный интерфейс с собственным, уникальным MAC-адресом поверх физической карты хоста — для остальной сети это выглядит как ещё одно физическое устройство. Обычная сетевая карта на аппаратном уровне отбрасывает кадры, чей MAC получателя не совпадает с её собственным, а виртуальных MAC у неё нет, поэтому сетевой карте хоста нужен неразборчивый режим (promiscuous mode): она передаёт наверх все кадры подряд, а уже ядро разбирает, какому виртуальному MAC какой кадр предназначен. Без этого режима все кадры для контейнерных MAC карта отбросила бы ещё на аппаратном уровне, до того как их увидел бы Docker. Это требование и ломает macvlan там, где карта или сеть его не допускают: многие облачные провайдеры и управляемые коммутаторы блокируют свой физический порт, как только через него начинает ходить трафик со вторым MAC-адресом, а часть Wi-Fi-адаптеров чужие MAC вообще не пропускает. Годится для legacy-сервисов, которым обязателен прямой L2-доступ и собственный MAC в реальной сети, и для систем мониторинга трафика на физическом сервере.

**ipvlan** решает ту же задачу прямого подключения к физической сети, но лишних MAC не плодит: все контейнеры выходят наружу с одним и тем же MAC-адресом физической карты хоста, а различает их драйвер уже по IP-адресу в заголовке пакета. Поскольку MAC получателя у всех кадров совпадает с MAC самой карты, неразборчивый режим не нужен — карта принимает трафик как обычно, а раскладывает пакеты по контейнерам уже сам драйвер после приёма. Из-за этого ipvlan работает там, где macvlan не запустить: на Wi-Fi-адаптерах, в облачных виртуальных машинах и в сетях со строгим контролем MAC-адресов на порту (Port Security).

### Особенности macvlan и ipvlan по сравнению с bridge и host

Во-первых, в параметрах сети при её создании: раз контейнер получает настоящий IP из физической сети, а не из внутреннего диапазона Docker, --subnet и --gateway при docker network create для macvlan/ipvlan обязательны и должны строго совпадать с параметрами этой сети — той же подсетью и тем же шлюзом, что раздаёт физический роутер.

Во-вторых, проброс портов тут не нужен и даже не поддерживается: Docker сам вернёт ошибку на попытку указать -p для контейнера в macvlan/ipvlan-сети. Раз у контейнера уже есть настоящий IP в реальной сети, к нему стучатся напрямую по этому IP и нужному порту — пробрасывать через хост нечего.

## Проброс портов: -p, EXPOSE

Порт, который слушает процесс внутри контейнера, существует только в его network namespace — снаружи хоста его не видно, и с самого хоста по умолчанию тоже не видно. Флаг -p 8080:80 говорит Docker: принимай снаружи запросы на порт 8080 хоста и перенаправляй их на порт 80 внутри контейнера.

EXPOSE в Dockerfile — это список портов, которые процесс внутри контейнера собирается слушать. Сам по себе он ничего не открывает и не пробрасывает — чтобы порт стал доступен снаружи, -p при docker run всё равно обязателен.

```dockerfile
EXPOSE 80
```

```bash
docker run -p 8080:80 myimage   # -p всё равно обязателен, даже с EXPOSE 80 в Dockerfile
```

## Пользовательские сети: DNS, изоляция, подключение на лету

IP контейнера не постоянен: при каждом пересоздании контейнера он обычно меняется.

В пользовательских сетях (созданных через docker network create, но не в дефолтной bridge-сети) Docker поднимает встроенный DNS-сервер, доступный внутри каждого контейнера по адресу 127.0.0.11. В дефолтной bridge-сети разрешение имён не работает вовсе, и контейнерам приходится обращаться друг к другу по IP напрямую. Именно из-за отсутствия DNS Docker в официальной документации не рекомендует её для контейнеров, которым нужно общаться между собой. Этот адрес автоматически прописывается в /etc/resolv.conf контейнера. Когда контейнер обращается по имени другого контейнера (или его алиасу в сети), запрос на перевод этого имени в IP уходит на 127.0.0.11. Там dockerd перехватывает его и подставляет текущий IP из внутреннего реестра сети — никакой статической зоны, всё генерируется на лету, по мере того как контейнеры подключаются к сети и отключаются от неё. Запросы к внешним именам (например, google.com) этот механизм пересылает на DNS-серверы хоста.

```bash
docker exec web cat /etc/resolv.conf   # nameserver 127.0.0.11
```

Именно поэтому в пользовательской сети контейнеры принято адресовать по имени, а не по IP: при пересоздании контейнера имя в конфигах менять не нужно, а вот новый IP пришлось бы прописывать вручную каждый раз.

Второе важное свойство пользовательских сетей — изоляция между ними. Контейнер в network-a не достучится до контейнера в network-b, пока кто-то из них не подключён сразу к обеим сетям. Добавить уже работающий контейнер в дополнительную сеть, не пересоздавая его, можно через docker network connect, а отключить — через docker network disconnect.

```bash
docker network connect network-b web      # подключить контейнер web ещё и к network-b
docker network disconnect network-a web   # отключить web от network-a
```

## Практика: имя вместо IP

```bash
docker network create mynet
docker run -d --name web --network mynet nginx:alpine
docker run -it --name client --network mynet busybox sh
```

Внутри client:

```bash
ping web
wget -O- http://web
```

Оба контейнера в одной пользовательской сети видят друг друга по имени — конкретный IP каждого контейнера знать не обязательно.

У docker network create есть и флаги --subnet и --gateway, которыми можно задать адресацию сети явно вместо автоматической. Для обычного bridge они не обязательны — без них Docker сам берёт свободный диапазон из своего дефолтного пула адресов.

Если подсеть задана явно, IP контейнеру можно назначить и вручную — флагом --ip при docker run, но это работает только в пользовательских сетях, а не в default bridge. Само значение --subnet обязано быть сетевым адресом в CIDR-нотации (192.168.1.0/24, а не 192.168.1.5/24) — Docker требует нулевые хостовые биты. И подсеть стоит выбирать так, чтобы она не пересекалась с реальной LAN хоста. Если для bridge-сети взять тот же диапазон, что раздаёт домашний роутер, в таблице маршрутизации хоста окажутся два маршрута к одной подсети: через настоящую сетевую карту и через bridge — и ядро будет непредсказуемо путать, куда слать пакет, реальному устройству в LAN или контейнеру.
