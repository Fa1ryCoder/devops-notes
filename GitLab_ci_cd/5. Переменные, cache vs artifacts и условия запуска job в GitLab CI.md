# 5. Переменные, cache vs artifacts и условия запуска job

Переменная в GitLab CI/CD — это именованное значение, которое подставляется в script вместо того, чтобы писать одно и то же вручную в разных местах. Технически любая такая переменная в итоге становится обычной переменной окружения (environment variable) внутри shell, где выполняется job, поэтому обращаются к ней как к обычной переменной окружения: `$VARIABLE_NAME`. Переменные бывают двух видов — predefined (заранее определённые, создаёт сам GitLab) и custom, свои/пользовательские (задаёшь сам).

## 1. Predefined-переменные

Для каждой job GitLab автоматически прокидывает внутрь несколько десятков переменных с информацией о проекте, коммите, ветке, pipeline и самой job. Почти все они начинаются с `CI_` — по этому префиксу их сразу видно среди своих переменных.

Полный список — это больше сотни переменных, зубрить его бессмысленно. Важно понимать сами категории и держать в голове самые ходовые из каждой.

**Проект:**
- `CI_PROJECT_NAME` — имя проекта
- `CI_PROJECT_PATH` — полный путь вида `namespace/project`
- `CI_PROJECT_DIR` — путь, куда склонирован репозиторий внутри job
- `CI_PROJECT_URL` — ссылка на проект в GitLab

**Коммит и ветка:**
- `CI_COMMIT_SHA` / `CI_COMMIT_SHORT_SHA` — полный и короткий хэш коммита
- `CI_COMMIT_BRANCH` — имя ветки (пусто, если pipeline запущен по тегу)
- `CI_COMMIT_TAG` — имя тега (пусто, если pipeline запущен по ветке)
- `CI_COMMIT_REF_SLUG` — имя ветки/тега, приведённое к виду без спецсимволов: нижний регистр, дефисы вместо пробелов и других символов. Именно из-за этого его чаще всего используют там, где имя должно быть частью строки — например, в cache key или в имени environment
- `CI_DEFAULT_BRANCH` — имя дефолтной ветки проекта (обычно `main`)
- `CI_COMMIT_MESSAGE` — текст коммита

**Pipeline и job:**
- `CI_PIPELINE_ID` — уникальный ID pipeline на всём gitlab.com
- `CI_PIPELINE_IID` — номер pipeline внутри конкретного проекта, тот самый, что видно в интерфейсе
- `CI_PIPELINE_SOURCE` — что запустило pipeline: `push`, `merge_request_event`, `schedule`, `web`, `api` и т.д.
- `CI_JOB_ID`, `CI_JOB_NAME`, `CI_JOB_STAGE` — id, имя и стадия текущей job

**Merge request (MR):**
- `CI_MERGE_REQUEST_IID` — номер merge request
- `CI_MERGE_REQUEST_SOURCE_BRANCH_NAME` / `CI_MERGE_REQUEST_TARGET_BRANCH_NAME` — ветка-источник и ветка-цель
- `CI_OPEN_MERGE_REQUESTS` — список открытых merge request для текущей ветки, пусто, если MR не открыт

**Container Registry:**
- `CI_REGISTRY`, `CI_REGISTRY_IMAGE`, `CI_REGISTRY_USER`, `CI_REGISTRY_PASSWORD` — адрес встроенного в GitLab registry и данные для логина в него. Пригодятся, когда дойдёшь до сборки и пуша Docker-образов.

Практическая штука: если непонятно, что вообще доступно внутри конкретной job — добавь в script строчку `- env | sort` (или `printenv`). Она выведет в лог job все переменные окружения, включая predefined. Быстрее, чем лезть в документацию.

```yaml
debug-vars:
  stage: build
  script:
    - env | sort
```

В логе этой job увидишь что-то вроде:

```
CI_COMMIT_BRANCH=feature-x
CI_COMMIT_SHA=8f3e1a2b9c...
CI_JOB_NAME=debug-vars
CI_PIPELINE_SOURCE=push
CI_PROJECT_NAME=cicd-test
...
```

Job чисто диагностическая, в реальном pipeline не нужна — добавляешь на минуту, смотришь лог, потом убираешь.

## 2. Свои (custom) переменные

**Как объявлять.** Переменную можно задать на двух уровнях:

```yaml
variables:
  APP_ENV: "production"   # глобально, видно всем job

deploy-job:
  variables:
    APP_ENV: "staging"    # только для этой job, перекрывает глобальное значение
  script:
    - echo $APP_ENV
```

Если переменная с одним и тем же именем задана и глобально, и внутри job — побеждает та, что внутри job.

**Где хранить.** Есть три места:

1. **Прямо в `.gitlab-ci.yml`**, в блоке `variables:` — подходит для несекретных значений конфигурации: имя окружения, версия инструмента и т.п. Значение видно всем, у кого есть доступ на чтение репозитория, и хранится в истории git.
2. **В интерфейсе GitLab**: Settings → CI/CD → Variables, на уровне проекта или группы. Здесь держат секреты и всё, что не должно попадать в репозиторий: токены, пароли, ключи API. Такие переменные можно сделать protected и/или masked — см. следующий раздел. Если одноимённая переменная задана и в UI, и в yml — побеждает та, что в UI.
3. **В момент запуска pipeline вручную** — на странице запуска pipeline можно добавить переменные для одного конкретного запуска, не трогая ни yml, ни настройки проекта. Такая переменная перекрывает и глобальную, и заданную в UI. Доступность этого способа может быть ограничена ролью — в проекте есть настройка, кому вообще разрешено передавать переменные при запуске pipeline.

Ещё одна деталь: у переменной в UI есть поле Type — `Variable` (обычная переменная окружения, по умолчанию) или `File`. Во втором случае GitLab кладёт значение во временный файл, а сама переменная содержит путь к этому файлу. Это удобно для многострочных секретов — приватных ключей, сертификатов, kubeconfig — того, что неудобно или невозможно засунуть в одну строку обычной переменной.

## 3. Protected и masked переменные

Обе настройки задаются в том же интерфейсе (Settings → CI/CD → Variables) и решают разные задачи.

**Protected (защищённая)** — переменная доступна только в pipeline, которые запускаются на protected-ветках или protected-тегах (защищённая ветка — та, у которой ограничены права на push и merge, обычно `main`; защищённый тег — тот, у которого ограничено право на создание тега с таким именем, обычно теги-релизы вида `v*`). Смысл: не дать секрету от продакшена утечь в pipeline, запущенный с произвольной feature-ветки, куда пушить может кто угодно с доступом на запись в репозиторий.

**Masked (замаскированная)** — значение в логах job заменяется на что-то вроде `[MASKED]` вместо реального текста, чтобы секрет не осел в логах, которые видит вся команда. Чтобы значение вообще можно было замаскировать, GitLab требует: минимум 8 символов, одна строка без переносов и ограниченный набор символов. Многострочные секреты замаскировать нельзя — для них как раз используют File-тип переменной из предыдущего раздела.

Небольшая тонкость: начиная с GitLab 18.3 новая переменная, которую создаёшь через UI, по умолчанию создаётся как masked (раньше по умолчанию было visible). Если увидишь такое поведение на практике — это не баг, а текущий дефолт.

Практика простая: реальные секреты — токены, пароли, API-ключи — обычно делают одновременно и protected, и masked.

## 4. Cache vs artifacts

Job запускается каждый раз с чистого листа: GitLab склонировал репозиторий — и всё, больше в рабочей директории ничего нет. Ни установленных зависимостей, ни того, что собрала предыдущая job. Cache и artifacts — это два разных механизма, которые позволяют сохранить файлы после job и передать их дальше. Cache передаёт файлы той же job, но в следующем запуске pipeline (следующий коммит/пуш). Artifacts передают файлы другой job здесь же, в этом же запуске pipeline.

Зачем это вообще нужно — потому что **каждая job запускается в своём отдельном, изолированном контейнере**. Job из одной стадии физически не имеет доступа к файловой системе job из другой стадии. Допустим, есть job `build`, которая компилирует исходный код в готовый файл (например `dist/app.js`), и job `deploy`, которая должна взять этот файл и положить на сервер. `deploy` стартует в новом, пустом контейнере, который вообще не видел, как работала `build`: там нет `dist/`, есть только заново склонированный репозиторий — то есть исходники, а не результат их сборки. `deploy` физически не может достать файл, который `build` создала у себя — его там просто нет.

Artifacts — это способ сказать GitLab: «вот эти файлы, которые я создала, сохрани их». GitLab забирает указанные файлы у `build` после её завершения, упаковывает и кладёт в отдельное хранилище. Когда стартует `deploy` — GitLab сам, автоматически, до начала её script, распаковывает эти файлы обратно, уже в её собственный контейнер. Только после этого `dist/app.js` вообще появляется на диске у `deploy`, и она может его задеплоить.

Смысловая разница в двух фразах: **cache ускоряет pipeline, но необязателен — pipeline отработает и без него, просто медленнее. Artifact — это результат job, который обязан дойти до следующей стадии (или до человека, который хочет его скачать); если он не сохранится, зависящая от него job попросту не сможет отработать.**

### Cache: синтаксис

`key:` определяет, какой именно кэш искать и куда сохранять, а `paths:` — что именно класть в этот кэш. Они всегда идут в паре, порознь смысла не имеют. Есть несколько вариантов, как задать `key:`.

Важное ограничение: путь в `paths:` должен быть внутри рабочей директории проекта — той самой, что лежит в переменной `CI_PROJECT_DIR` (раздел 1), куда GitLab склонировал репозиторий. Наружу — например, в системные папки вроде `/root/.cache/pip` — `cache:` дотянуться не может, даже если физически файлы туда установились. **Поэтому команды установки часто и запускают с флагом, который явно указывает целевую папку внутри проекта** (как `pip install -t deps/`), а не полагаются на путь по умолчанию где-то в системе.

**Вариант 1: фиксированная строка**

```yaml
test-job:
  stage: test
  script:
    - pip install -r requirements.txt -t deps/
  cache:
    key: my-cache   # имя может быть любое
    paths:
      - deps/
```

`key:` не хранит зависимости — это просто имя, бирка, а не контейнер для данных. Сами данные лежат в `paths:` — это то, что реально сохраняется. `key: my-cache` — просто текст-имя, сам по себе он ничего не содержит. `paths: - deps/` — а вот это уже говорит GitLab, что реально зазипует и сохранит: содержимое папки `deps/`, куда легли зависимости после установки.

По шагам: job отработала, `deps/` заполнена файлами. GitLab зипует содержимое `deps/` и кладёт в хранилище под именем `my-cache` — как коробку с биркой на складе. В следующем pipeline GitLab видит `key: my-cache`, ищет коробку с этой биркой, распаковывает — и `deps/` заполнена без переустановки с нуля.

Раз `my-cache` — фиксированная строка, она одна и та же в любом pipeline, независимо от ветки. Значит, и коробка одна, общая: pipeline из `main` и из `feature-x` ищут (и перезаписывают) одну и ту же коробку под этой биркой.

**Вариант 2: `$CI_COMMIT_REF_SLUG`**

```yaml
test-job:
  stage: test
  script:
    - pip install -r requirements.txt -t deps/
  cache:
    key: $CI_COMMIT_REF_SLUG   # имя текущей ветки
    paths:
      - deps/
```

Переменная `$CI_COMMIT_REF_SLUG` содержит имя текущей ветки, приведённое к виду без спецсимволов — например `main` или `feature-login` (раздел 1). GitLab подставляет это значение в `key:` при подготовке job: для ветки `main` получается ключ `main`, для `feature-login` — ключ `feature-login`.

Плюс: ветки полностью изолированы друг от друга. Кэш перезаписывается в конце каждой job (при `policy: pull-push`, как по умолчанию), так что реального рассинхрона по времени не возникает — свежее содержимое `deps/` каждый раз сохраняется под тем же ключом. Но привязки к содержимому зависимостей тут нет: ключ считается только из имени ветки. Из-за этого две разные ветки с абсолютно одинаковыми зависимостями всё равно получат два разных, никак не связанных кэша — переиспользования между ветками не происходит. Это и решает следующий вариант.

**Вариант 3: `files:`** — хэш содержимого файла с зависимостями, современный и самый удобный вариант: пока файл не поменялся, переиспользуется старый кэш; поменялся — GitLab сам считает это новым ключом, кэш пересобирается автоматически, без ручной инвалидации. В реальном проекте это lock-файл зависимостей, например `package-lock.json`, `requirements.txt`, `Gemfile.lock`, `go.sum` — конкретное имя зависит от экосистемы:

```yaml
test-job:
  stage: test
  script:
    - pip install -r requirements.txt -t deps/
  cache:
    key:
      files:
        - requirements.txt
    paths:
      - deps/
```

Важное условие: файл в `files:` должен уже существовать в репозитории (быть закоммиченным) до старта job. GitLab считает хеш на этапе подготовки, ещё до запуска `script` — а значит, файл, который создаётся самим script во время выполнения, а не лежит в git заранее, для этого не подойдёт: хешировать в момент подготовки ещё нечего. Если указанный файл не найден — GitLab просто подставляет ключ по умолчанию, без ошибки, но и без реальной привязки к зависимостям.

Дальше идут остальные настройки `cache:`:

- `policy:` (политика) — что job может делать с кэшем:
  - `pull-push` (по умолчанию) — и читает, и перезаписывает после выполнения;
  - `pull` — только читает, не тратит время на аплоад: ставят в job, которые просто пользуются зависимостями и не меняют их;
  - `push` — только записывает, без чтения: например, отдельная job, которая по расписанию «прогревает» кэш.

**`fallback_keys:`** — список запасных ключей. Если кэш по основному `key:` не нашёлся, GitLab пробует найти кэш по ключам из этого списка, по очереди, пока не найдёт совпадение (или не переберёт все и не начнёт с пустого места).

Пример: `key: $CI_COMMIT_REF_SLUG` — свой кэш на каждую ветку. Создаёшь новую ветку `feature-payments` от `main` — первый же pipeline на ней ищет кэш `feature-payments`, а такого ещё никогда не было. Без `fallback_keys` — переустановка зависимостей с нуля, хотя ветка только что отпочковалась от `main` и зависимости у неё почти те же.

```yaml
test-job:
  stage: test
  script:
    - pip install -r requirements.txt -t deps/
  cache:
    key: $CI_COMMIT_REF_SLUG
    fallback_keys:
      - $CI_DEFAULT_BRANCH   # main
    paths:
      - deps/
```

GitLab ищет кэш `feature-payments` → не находит → идёт по списку `fallback_keys` по очереди → находит `main` → распаковывает его. Дальше `pip install` останется докачать разве что то, что реально новое, а не всё с нуля. В конце job сохранение всё равно идёт под основным ключом (`feature-payments`) — со второго запуска у ветки уже свой кэш, fallback больше не нужен.

### Artifacts: синтаксис

`artifacts:` устроен проще, чем `cache:` — тут нет ключа для поиска. Файлы жёстко привязаны к конкретной job внутри конкретного запуска pipeline, а не к какому-то имени, по которому их потом ищут.

**То же ограничение, что и у cache: путь в `paths:` должен быть внутри рабочей директории проекта (`CI_PROJECT_DIR` из раздела 1). Наружу, в системные папки, GitLab дотянуться не может, даже если файлы физически там появились.**

```yaml
stages:
  - build
  - deploy

build-app:
  stage: build
  script:
    - python -m build
  artifacts:
    paths:
      - dist/
    expire_in: 1 week

deploy-app:
  stage: deploy
  script:
    - ls -la dist/
    - ./deploy.sh dist/
```

`paths:` отвечает на тот же вопрос, что и в cache — «что именно сохранить». Тут это папка `dist/`, куда `python -m build` кладёт готовый результат сборки (тот путь, который мы разбирали чуть выше). `expire_in:` — через сколько времени GitLab удалит эти файлы из хранилища, например `1 week`, `3 days`, `1 hour`; если не задать — GitLab всё равно когда-нибудь удалит по своим дефолтным настройкам, лучше указывать явно.

По шагам: `build-app` отработала, GitLab забрал `dist/` и сохранил, привязав к этой конкретной job этого конкретного pipeline. `deploy-app` — job следующей стадии — при старте автоматически получает `dist/` от **всех** job предыдущих стадий: ничего искать по имени не нужно, GitLab сам знает, что это тот же pipeline, и просто прикладывает файлы. `ls -la dist/` в script — просто чтобы наглядно показать: файлы из `build-app` реально лежат в этом, уже другом, контейнере, хотя `deploy-app` их сама не создавала. `./deploy.sh dist/` — деплой использует именно эти файлы, передавая папку аргументом.

**`dependencies:`** — ключ на уровне job, который явно указывает, откуда именно брать artifacts из предыдущих стадий, вместо дефолтного "от всех".

Зачем это нужно:
- **Ускорение pipeline.** Если одна job создаёт большой artifact, а следующей он не нужен — скачивание лишних файлов просто тратит время.
- **Изоляция.** Явно видно, какие файлы точно будут в контейнере job, без сюрпризов от чужих artifacts.

Важные правила:
- В `dependencies:` можно указывать только job из предыдущих стадий.
- Если у указанной job нет своего `artifacts:` — указывать её в `dependencies:` бессмысленно, скачивать нечего.
- `dependencies: []` — частый паттерн: не скачивать artifacts вообще, для лёгких job вроде тестов, линтеров, уведомлений.

Отдельно: внутри самого блока `artifacts:` можно указать `when: on_failure` или `when: always` — не путать с `when:` у самой job (раздел 5). Это отдельная настройка, которая решает только одно: сохранять ли файлы, если job упала. Пригодится, например, чтобы забрать логи именно с упавшего теста.

**Главное, что стоит запомнить про оба механизма:** ни cache, ни artifacts ничего не создают и не устанавливают сами. Они только перекладывают то, что уже реально лежит на диске к концу job — а кладёт туда файлы всегда собственный script (install-скрипт, компилятор, `mkdir`/`touch` — что угодно). При этом руками создавать директорию нужно не всегда: если команда сама создаёт целевую папку, если её ещё нет (как `python -m build` создаёт `dist/`, а `pip install -t deps/` — `deps/`), отдельный `mkdir` не нужен, GitLab просто заберёт то, что там окажется к концу job. Разница между cache и artifacts только в том, между чем именно они перекладывают: cache — между разными запусками pipeline, artifacts — между разными job внутри одного и того же запуска.

## 5. when — когда запускать job

`when:` — настройка внутри конкретной job, которая определяет, должна ли именно эта job запуститься, в зависимости от результата предыдущих стадий. Если `when` вообще не указан — используется значение по умолчанию, `on_success`.

| Значение | Срабатывает, когда | Типичный случай |
|---|---|---|
| `on_success` (по умолчанию) | все job предыдущих стадий завершились успешно | обычный шаг pipeline, ничего указывать не нужно |
| `on_failure` | хотя бы одна job предыдущей стадии упала | уведомление об ошибке, откат, сбор диагностики |
| `always` | независимо от результата предыдущих стадий | финальное уведомление; удалить временный контейнер/тестовую БД, поднятые самим script, даже если pipeline упал |
| `manual` (вручную) | job появляется в интерфейсе, но не стартует сама — нужно нажать «Play» | деплой в production, любое потенциально опасное действие |
| `delayed` (с задержкой) | job стартует автоматически, но через заданное время | отложенный шаг, окно на отмену перед действием — используется редко |
| `never` (никогда) | job не запускается вообще | внутри `rules:`, чтобы явно исключить job при конкретном условии |

Пара важных тонкостей:

`allow_failure` — отдельная настройка job, не только для `manual`: решает, блокирует ли упавшая (красная) job весь pipeline целиком или нет. По умолчанию — `false`: если job упала, весь pipeline считается упавшим. Если `allow_failure: true` — job может упасть, а pipeline всё равно продолжится и в итоге покажет "passed"; сама упавшая job при этом отмечается отдельным предупреждающим значком, а не как критическая ошибка.

```yaml
test-job:
  stage: test
  script:
    - pytest
  allow_failure: true
```

Это самостоятельный ключ на уровне job, соседний с `stage:`/`script:`, а не что-то внутри `rules:`.

**`manual` и блокировка pipeline.** От того, где именно стоит `when: manual`, зависит поведение по умолчанию:
- если `when: manual` стоит на верхнем уровне job, не внутри `rules:` — `allow_failure` по умолчанию становится `true`. Job необязательна: pipeline может успешно завершиться, даже если её так никто и не запустил.
- если `when: manual` стоит внутри блока `rules:` — `allow_failure` по умолчанию становится `false`. Такая job блокирующая: pipeline «зависает» в статусе pending на этой стадии, следующие стадии не запустятся, пока кто-то не нажмёт «Play».

Это поведение можно переопределить явно, прописав `allow_failure: true` или `false` рядом с `when: manual`:

```yaml
deploy-prod:
  stage: deploy
  script:
    - ./deploy.sh
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual
      allow_failure: true
    - when: never
```

На дефолтной ветке job появляется вручную, но помечена как необязательная (`allow_failure: true`) — pipeline пройдёт и без её запуска, хотя по умолчанию для `rules:` было бы наоборот, блокирующее поведение. На всех остальных ветках job вообще не появляется (`when: never`).

**`delayed`** используется вместе с `start_in`, который задаёт задержку:

```yaml
rollback-check:
  stage: verify
  script:
    - ./check-health.sh
  when: delayed
  start_in: 5 minutes
```

## 6. Операторы внутри if:

Каждый блок внутри `rules:` у job может состоять из трёх частей: `if:` — само условие, `changes:` — условие по изменённым файлам (следующий раздел), и `when:` — что делать, если условие выполнилось (полный набор значений разобран в разделе 5 выше). Дальше — подробно про операторы, которые используются внутри `if:`.

Условие внутри `if:` — это выражение над переменными, которое GitLab считает истинным или ложным. Доступные операторы:

- `==` — равно. Пример: `$CI_COMMIT_BRANCH == "main"`
- `!=` — не равно. Пример: `$CI_COMMIT_BRANCH != "main"`
- `=~` — совпадает с регулярным выражением. Пример: `$CI_COMMIT_BRANCH =~ /^release-.*/`
- `!~` — не совпадает с регулярным выражением. Пример: `$CI_COMMIT_BRANCH !~ /^release-.*/`
- `&&` — И, оба условия должны быть истинны. Пример: `$A == "x" && $B == "y"`
- `||` — ИЛИ, достаточно, чтобы было истинно хотя бы одно. Пример: `$A == "x" || $B == "y"`
- `!` — НЕ, отрицает условие целиком или часть выражения. Пример: `!($CI_COMMIT_BRANCH == "main")`

Несколько практических моментов:

- Просто `if: $VARIABLE` без оператора проверяет, что переменная существует и не пустая — это самая частая проверка вида «а вообще задана ли переменная».
- Скобки группируют условия и имеют приоритет: то, что в скобках, вычисляется первым. Между `&&` и `||` приоритет тоже разный — `&&` вычисляется раньше `||`, поэтому в сложных условиях лучше расставлять скобки явно, а не полагаться на порядок по умолчанию.

  Например: `$CI_COMMIT_BRANCH == "main" || $CI_COMMIT_BRANCH == "develop" && $CI_PIPELINE_SOURCE == "schedule"` из-за приоритета читается как `$CI_COMMIT_BRANCH == "main" || ($CI_COMMIT_BRANCH == "develop" && $CI_PIPELINE_SOURCE == "schedule")` — то есть "main при любом источнике pipeline ИЛИ develop именно по расписанию". Если нужен другой смысл — скобки ставятся руками.
- Оператор `!` — сравнительно новая штука, появился в GitLab 18.11, и у него есть неочевидный момент: он проверяет именно «пусто/не определено», а не «равно false». То есть `!$VAR` — это true, только если `$VAR` реально пустая или не задана. Если в `$VAR` лежит строка `"false"` или `"0"` — для GitLab это непустая строка, значит `!$VAR` даст `false`. Чтобы проверить конкретное значение, используют сравнение целиком: `!($VAR == "false")`.

## 7. rules:changes — запуск по изменённым файлам

`changes:` — ещё один тип условия внутри блока `rules:`, срабатывает, если в пуше или merge request поменялся хотя бы один файл из указанного списка (поддерживаются glob-паттерны).

```yaml
docker-build:
  stage: build
  script:
    - docker build -t my-app:$CI_COMMIT_REF_SLUG .
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      changes:
        - Dockerfile
        - docker/**/*
```

Здесь job соберёт образ, только если в merge request затронут `Dockerfile` или что-то внутри папки `docker/`.

Важная тонкость: `changes:` сравнивает изменённые файлы с какой-то базой — обычно с предыдущим коммитом на ветке, а в merge request pipeline — с целевой веткой. Но такая база есть не у всех типов pipeline: у запланированных (schedule), запущенных вручную или по тегу pipeline нет «предыдущего коммита» для сравнения — и в этих случаях `changes:` считается истинным всегда, вне зависимости от того, что реально поменялось. Поэтому `changes:` почти всегда используют вместе с `if:`, который ограничивает тип pipeline (как в примере выше — `merge_request_event`), а не сам по себе.

Более предсказуемый и современный способ — явно указать, с чем сравнивать, через `compare_to`:

```yaml
docker-build:
  stage: build
  script:
    - docker build -t my-app:$CI_COMMIT_REF_SLUG .
  rules:
    - if: $CI_COMMIT_BRANCH
      changes:
        paths:
          - Dockerfile
          - docker/**/*
        compare_to: 'refs/heads/main'
```

Так job сравнивает изменения с веткой `main` явно, а не полагается на то, какая база подставится по умолчанию для конкретного типа pipeline.
