## 1. Разбор вывода git commit

После первого коммита Git выдаёт следующее:

```
[main (root-commit) a1b2c3d] Initial commit
 2 files changed, 10 insertions(+)
 create mode 100644 README.md
 create mode 100644 app.py
```

Разберём каждую строку:

| Часть вывода | Что означает |
|---|---|
| `main` | Ветка в которую сделан коммит |
| `root-commit` | Первый коммит в репозитории — у него нет родителя |
| `a1b2c3d` | Сокращённый SHA-1 хеш коммита |
| `Initial commit` | Сообщение коммита |
| `2 files changed` | Количество изменённых файлов |
| `10 insertions(+)` | Количество добавленных строк |
| `create mode 100644` | Файл создан с правами 100644 |

`create mode 100644` — это и есть права на файл в Git. Разберём подробнее в следующем разделе.

## 2. Как Git хранит права на файлы

### Зачем вообще хранить бит исполняемости в Git

Казалось бы — можно скачать файл и сделать `chmod +x` вручную. Но на практике это создаёт проблемы:

**Команда из 10 человек** — каждый клонирует репозиторий и каждому нужно вручную делать `chmod +x deploy.sh`. Кто-то забудет — скрипт не запустится. Если бит исполняемости хранится в Git — при клонировании файл сразу готов к запуску у всех.

**CI/CD пайплайн** — GitLab Runner или GitHub Actions клонирует репозиторий и запускает скрипты автоматически. Там нет человека который сделает `chmod +x`. Если бит не сохранён в Git — пайплайн упадёт с ошибкой `Permission denied`.

**Docker образ** — в `Dockerfile` часто копируют скрипты из репозитория и запускают их. Если бит исполняемости не сохранён — скрипт не запустится внутри контейнера.

В автоматизации нет человека который будет делать `chmod +x` вручную. Git хранит бит исполняемости чтобы скрипты работали везде одинаково без ручных действий.

Число перед именем файла в индексе состоит из двух частей:

```
100644
^^^---  тип объекта (100 = обычный файл)
   ^^^  права доступа (644 = не исполняемый)
```

**Основные типы объектов:**
- `100` — обычный файл
- `120` — символическая ссылка (symlink)

Остальные типы (`040` — директории, `160` — подмодули) существуют, но к правам доступа отношения не имеют.

**Права доступа:**

В отличие от полноценных прав в Unix (чтение, запись, выполнение для владельца, группы и остальных) — Git сохраняет только **один бит — является ли файл исполняемым**.

В репозитории Git существует всего два режима прав:

| Код | Права | Описание |
|-----|-------|----------|
| `644` | `-rw-r--r--` | Файл не является исполняемым |
| `755` | `-rwxr-xr-x` | Файл является исполняемым |

> Владелец файла и расширенные права (чтение/запись для групп) Git не сохраняет — только бит исполняемости.

Посмотреть права файлов в индексе можно командой:

```bash
git ls-files --stage
# 100644 a1b2c3d 0    README.md
# 100644 b2c3d4e 0    app.py
```

## 3. Отслеживание изменений прав

Для Git изменение прав доступа — такое же существенное изменение как и правка содержимого файла. Если в Unix-системе изменить права через `chmod`, `git status` пометит файл как изменённый:

```bash
# Сделали файл исполняемым
chmod +x app.py

# Git видит изменение
git status
# Changes not staged for commit:
#   modified: app.py

# Посмотреть что изменилось
git diff
# old mode 100644
# new mode 100755
```

Такое изменение можно добавить в индекс и зафиксировать в коммите:

```bash
git add app.py
git commit -m "Make app.py executable"
```

## 4. Особенности Windows

В Windows нет понятия "бит исполняемости" как в Unix. Там файл считается исполняемым по расширению — `.exe`, `.bat`, `.cmd` и т.д. Поэтому когда Git работает на Windows и видит файлы — он не может определить исполняемый файл или нет, потому что файловая система это не поддерживает.

**Если `core.filemode = true` на Windows:**
- Git будет пытаться отслеживать изменения прав
- Будет постоянно видеть все файлы как "изменённые" из-за того что Windows не умеет правильно передавать эту информацию
- `git status` будет показывать кучу изменений которых на самом деле нет

**Если `core.filemode = false` на Windows (Git ставит это автоматически):**
- Git игнорирует биты исполняемости
- Все файлы сохраняются как `644`
- `git status` не засоряется ложными изменениями

При создании репозитория Git проверяет возможности файловой системы и автоматически устанавливает `core.filemode = false`. Это происходит в двух случаях:

**Клонируешь чужой репозиторий:**
```bash
git clone <url>   # Git сам создаёт .git/ и сразу проверяет файловую систему
```

**Создаёшь новый репозиторий с нуля:**
```bash
git init          # создаёт пустой .git/ и проверяет файловую систему
```

```bash
cat .git/config
# [core]
#     filemode = false
```

## 5. Установка прав вручную

Если ты ведёшь разработку на Windows, но проект должен работать в Unix-системах где скрипты должны быть исполняемыми — есть два способа установить бит исполняемости в обход ограничений файловой системы Windows:

**Для файлов которые уже находятся в индексе:**

```bash
# Установить бит исполняемости напрямую в индексе Git
git update-index --chmod=+x app.py

# После этого нужно закоммитить изменение
git commit -m "Make app.py executable"
```

**При добавлении нового файла:**

```bash
# Сразу указать флаг исполняемости при добавлении в индекс
git add --chmod=+x app.py
```

После коммита в репозитории файл будет иметь режим `755` независимо от операционной системы.
