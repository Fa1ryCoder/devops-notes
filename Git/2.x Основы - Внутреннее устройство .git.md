## 1. Структура директории .git

Если заглянуть внутрь `.git/`, увидим следующую структуру:

```
.git/
├── config
├── HEAD
├── hooks/
├── index
├── logs/
├── objects/
└── refs/
```

| Файл / Директория | Что внутри                  | За что отвечает                                                     |
|-------------------|-----------------------------|---------------------------------------------------------------------|
| `config`          | Текстовый файл              | Локальная конфигурация этого репозитория (`--local`)                |
| `HEAD`            | Текстовый файл              | Указатель на ветку в которой ты сейчас находишься                   |
| `hooks/`          | Директория со скриптами     | Автоматизация: локальные Git-хуки (скрипты автоматических проверок) |
| `index`           | Бинарный файл               | Снимок staging area — что попадёт в следующий коммит                |
| `logs/`           | Директория с логами         | История изменений всех ссылок (база для команды `git reflog`)       |
| `objects/`        | Директория (БД)             | Хранилище всего контента: файлы, коммиты, структура папок           |
| `refs/`           | Директория со ссылками      | Список всех веток (локальных/удалённых) и тегов                     |

## 2. config

Обычный текстовый файл в формате INI. В него записываются настройки которые ты задаёшь через `git config --local`. Локальные настройки репозитория всегда приоритетнее глобальных (`--global`).

```bash
cat .git/config
```

```ini
[core]
    repositoryformatversion = 0
    filemode = true
    bare = false
[user]
    email = ivan@company.com
```

Этот файл можно редактировать вручную — без командной строки. Например быстро поменять рабочий email для этого проекта, и Git сразу подхватит изменения.

## 3. HEAD

Файл-указатель, состоящий всего из одной строки. Говорит Git на какой ветке ты сейчас находишься:

```bash
cat .git/HEAD
# ref: refs/heads/main
```

Когда ты переключаешься на другую ветку, Git не перекачивает проект заново. Он просто перезаписывает одну строку внутри файла `HEAD`:

```bash
# После git switch develop
cat .git/HEAD
# ref: refs/heads/develop
```

Важный нюанс: не любая операция с ветками трогает `HEAD`. `git branch <имя>` без переключения только создаёт файл в `refs/heads/` — указатель на текущий коммит, — а `HEAD` продолжает смотреть на прежнюю ветку. Переписывается `HEAD` только при реальном переключении: `git switch <имя>` или `git switch -c <имя>` — создание и переключение одной командой: сначала появляется файл в `refs/heads/`, потом переписывается строка в `HEAD`.

## 4. hooks/

Здесь лежат скрипты (на Bash, Python, Perl) которые Git автоматически запускает при наступлении определённых событий. Например перед коммитом (`pre-commit`) или перед отправкой кода на сервер (`pre-push`).

Сюда внедряют автоматические проверки. Например утилита `gitleaks` или локальные линтеры могут проверяться прямо здесь. Если разработчик попытается закоммитить код с забытым AWS-токеном или сломанным синтаксисом — скрипт из `hooks/` вернёт ошибку и Git заблокирует коммит прямо на машине разработчика до того как код попадёт на сервер.

## 5. objects/

База данных Git. Всё содержимое репозитория хранится здесь в виде объектов трёх основных типов:

- `blob` — содержимое одного файла. Только байты: ни имени, ни пути в blob нет
- `tree` — одна директория: список записей «имя → хеш», где хеш ведёт либо на `blob` (файл), либо на другой `tree` (поддиректория)
- `commit` — снимок проекта в конкретный момент: хеш корневого `tree`, хеш предыдущего коммита (`parent`), автор, коммиттер, сообщение

Есть и четвёртый тип, `tag` — аннотированный тег: отдельный объект со своим автором и сообщением, ссылающийся на коммит.

Объекты знают друг о друге только по хешам, и весь репозиторий держится на этих ссылках: файл ветки в `refs/heads/` хранит хеш коммита, коммит — хеш корневого `tree`, `tree` — хеши блобов и вложенных `tree`. Здесь легко запутаться: у каждого объекта — ровно один, свой собственный хеш, и он никогда не меняется. Когда `cat-file -p` показывает хеш внутри другого объекта — это не «у одного объекта появился второй хеш», это ссылка на **другой, отдельный** объект. Сам `cat-file -p` только печатает то, что уже лежит в `objects/` под этим именем.

Проследим за одним файлом от `git add` до истории коммитов — `sub/file.txt`, до этого момента в базе ничего из него нет:

```bash
mkdir sub && echo "содержимое" > sub/file.txt
git add sub/file.txt
```

В `objects/` появляется ровно один объект:

```
b33712fe…  blob
```

Что происходит при `git add sub/file.txt`:

1. Git сохраняет содержимое файла в базу — это и есть тот самый блоб (`b33712fe…`)
2. Git записывает в `index` одну строку: путь → хеш этого блоба

`index` — это просто список, как таблица:

```
sub/file.txt   →  b33712fe…
src/main.c     →  хеш456
README.md      →  хеш789
```

`tree` для `sub/` пока не существует вообще, он появится только на коммите.

```bash
git commit -m "c1"
```

Теперь в `objects/` четыре объекта:

```
b33712fe…  blob     ← тот же самый, не пересоздавался
6b03b930…  tree     ← sub/
33d5339f…  tree     ← корень
7e7b3cbf…  commit
```

Деревья строятся только на коммите, из `index`. Сначала — для самого глубокого уровня: `tree` на `sub/`, со ссылкой на блоб `file.txt`. Потом — для корня: `tree`, со ссылкой уже на этот `tree` для `sub/`. Поэтому их два: по одному на каждый уровень вложенности, начиная с самого глубокого и заканчивая корнем.

Отсюда общее правило: на коммит — не «три объекта», а `commit` (всегда ровно один, всегда новый) + N `tree` (по числу уровней вложенности, которые реально изменились) + M `blob` (по числу изменившихся файлов — и то не всегда: если новое содержимое совпадает с уже существующим объектом, новый `blob` не создаётся, используется старый).

Хеш коммита (`7e7b3cbf…`) — единственное число, которое показывает `git log` или сам `git commit`. Но commit-объект — это всего пара строк текста (дерево, автор, сообщение), а не файл целиком:

```bash
git cat-file -p 7e7b3cbf
# tree 33d5339f…
# author a <a@a.com> ...
#
# c1
```

Внутри написано `tree 33d5339f…` — это не «у 7e7b3cbf есть ещё один хеш», это commit **ссылается** на дерево, а у дерева — свой, отдельный хеш:

```bash
git cat-file -p 33d5339f
# 040000 tree 6b03b930…    sub
```

Корневое дерево ссылается на дерево `sub/`:

```bash
git cat-file -p 6b03b930
# 100644 blob b33712fe…    file.txt
```

А то — на блоб, где ссылок больше нет, только байты:

```bash
git cat-file -p b33712fe
# содержимое
```

После правки того же файла и второго коммита в объекте коммита появляется ещё и `parent`:

```bash
echo "правка" >> sub/file.txt
git commit -am "c2"
# вернул хеш коммита: 7d505e3b…

git cat-file -p 7d505e3b
# tree e872750c…
# parent 7e7b3cbf…
# author a <a@a.com> ...
#
# c2
```

`parent` — это и есть история: каждый коммит хранит хеш предыдущего, и `git log` просто идёт по этим ссылкам назад. Хеш коммита считается по всему его содержимому, включая `tree` и `parent`. Поэтому подменить незаметно нельзя ни один уже сделанный коммит — необязательно самый первый, а любой не последний: у него изменится хеш, а `parent` у следующего коммита всё ещё указывает на старое значение — связь рвётся. Чтобы её восстановить, следующий коммит нужно пересобрать с новым `parent`, из-за чего меняется уже его хеш — и так дальше по цепочке, до самого свежего коммита.

У любого объекта в `objects/` — blob, tree, commit, не важно — именем служит **SHA-1 хеш** его содержимого, а само содержимое объекта сжато `zlib` для экономии места. Поэтому каждый коммит — полный снимок проекта, а не дифф: он ссылается на дерево целиком, но реально в базе прибавляется только то, что изменилось, — остальное переиспользуется, как уже видно на примере выше.

Разложены объекты по хешу: первые 2 символа — имя директории, оставшиеся 38 — имя файла. Хеш `a1b2c3d4...` ляжет в `.git/objects/a1/b2c3d4...`. Смысл разбивки чисто технический: без неё все объекты лежали бы одним списком в одной папке, а операции над директорией с десятками тысяч файлов медленные — 256 префиксов (`00`–`ff`) снимают проблему. Группировки по смыслу нет: `blob`, `tree` и `commit` лежат вперемешку, директорию объекта определяет только начало его хеша. По имени файла тип объекта не узнать — его показывает `git cat-file -t <хеш>`, например `git cat-file -t b33712fe` вернёт `blob`.

Россыпь мелких файлов тоже не бесконечна: `git gc` периодически упаковывает их в `.git/objects/pack/` — один компактный packfile вместо множества мелких файлов, — и часть директорий `objects/xx/` после этого пустеет.

## 6. index

Бинарный файл `.git/index` — снимок staging area: то, что попадёт в следующий коммит.

Сам файл, в отличие от `HEAD`, `config` и файлов веток в `refs/heads/`, — не текст, а бинарный формат:

```bash
file .git/index
# .git/index: Git index, version 2, 2 entries
```

Разница видна и на хеше одного и того же блоба. `git ls-files --stage` показывает его как строку из 40 hex-символов — так же, как в `refs/heads/main` или в выводе `git rev-parse`:

```bash
git ls-files --stage
# 100644 3b18e512dba79e4c8300dd08aeb37f8e728b8dad 0    file1.txt
```

Но внутри самого `index` этот хеш хранится не как 40 байт текста, а как ровно 20 сырых байт — каждая пара hex-символов упакована в один байт. На одном файле разница незаметна, но в индексе с сотней тысяч файлов это уже мегабайты.

На каждый путь в индексе — ровно один блоб-хеш, актуальный на момент последнего `git add`. Сравнение этого хеша с двумя разными вещами и даёт modified/staged в `git status`:

- рабочая директория vs хеш в index — расхождение показывается как «не застейджено» (красным);
- index vs хеш того же пути в дереве коммита, на который смотрит HEAD, — расхождение показывается как «застейджено» (зелёным).

Файл ветки в `refs/heads/` в этом сравнении не участвует напрямую — там лежит хеш **коммита**, объект другого типа:

```bash
cat .git/refs/heads/main
# 1c7728a62067c063fe21891fda9f7d251868140d
```

Git идёт по цепочке: `refs/heads/<ветка>` → коммит → его `tree` → блоб-хеш для конкретного пути внутри дерева, и только этот блоб-хеш сравнивается с index.

Проверка на реальном репозитории — меняем закоммиченный `file1.txt`, не стейджим:

```bash
git hash-object file1.txt          # рабочая директория
# 1178a1e6d258c5b90e861fc119f957fdddefbe47

git ls-files --stage file1.txt     # index
# 100644 3b18e512dba79e4c8300dd08aeb37f8e728b8dad 0    file1.txt

git ls-tree HEAD file1.txt         # дерево коммита HEAD
# 100644 blob 3b18e512dba79e4c8300dd08aeb37f8e728b8dad    file1.txt
```

Index и HEAD-дерево совпадают (`3b18e5...`), рабочая директория — нет. `git status` в этот момент покажет `M file1.txt` красным.

После `git add file1.txt`:

```bash
git ls-files --stage file1.txt
# 100644 1178a1e6d258c5b90e861fc119f957fdddefbe47 0    file1.txt

git ls-tree HEAD file1.txt
# 100644 blob 3b18e512dba79e4c8300dd08aeb37f8e728b8dad    file1.txt
```

Теперь index совпадает с рабочей директорией, а с HEAD-деревом — уже нет. `git status` покажет тот же `M`, но зелёным.

Кроме хеша, на каждый файл в индексе хранятся права доступа, размер и время последнего изменения (mtime). Отсюда и скорость `git status`: прежде чем честно пересчитывать SHA-1 заново, Git сначала сверяет эти дешёвые метаданные с тем, что записано в индексе. Совпало — файл считается неизменённым без чтения содержимого. Разошлось хотя бы одно поле — только тогда содержимое перечитывается и хешируется.

## 7. logs/

Git ведёт здесь учёт истории всех указателей — записывает в какой момент ветка `main` или указатель `HEAD` перепрыгивали с одного хеша на другой.

Это база данных для команды `git reflog`. Если разработчик случайно сделал `git reset --hard` и удалил результаты вчерашней работы, или случайно удалил ветку — по логам из папки `logs/` через `git reflog` можно найти хеш потерянного коммита и полностью восстановить код.

Например, случайно затёрли вчерашний коммит:

```bash
git reset --hard HEAD~1
```

`git reflog` покажет историю переходов `HEAD`, включая тот, что был до отката:

```bash
git reflog

# a1b2c3d (HEAD -> main) HEAD@{0}: reset: moving to HEAD~1
# d4e5f6a HEAD@{1}: commit: добавил модуль авторизации
```

`d4e5f6a` — это и есть потерянный коммит: он всё ещё лежит в `objects/`, удаляет такие объекты только сборщик мусора, и то не сразу. Вернуть его на текущую ветку можно одной командой:

```bash
git reset --hard d4e5f6a
```

## 8. refs/

Refs — это ссылки. Внутри `refs/heads/` лежат файлы имена которых совпадают с твоими локальными ветками. Ветка — это обычный текстовый файл весом 41 байт в котором записан хеш коммита на котором она сейчас стоит:

```bash
cat .git/refs/heads/main
# a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2
```

**⚠️ DevOps-ловушка — packed-refs:**

На свежем репозитории структура `refs/heads/` выглядит именно так. Но в реальном продакшене или на долгоживущих CI/CD раннерах Git периодически запускает внутренний сборщик мусора (`git gc`). В этот момент Git физически удаляет отдельные файлы веток из `.git/refs/heads/` и упаковывает их в один файл `.git/packed-refs` ради ускорения чтения диска.

**Никогда не читай хеш ветки напрямую через `cat`** в Bash-скриптах или CI/CD пайплайнах:

```bash
# ❌ НЕПРАВИЛЬНО — после первой оптимизации репозитория упадёт с ошибкой
cat .git/refs/heads/main

# ✅ ПРАВИЛЬНО — всегда используй эту команду
git rev-parse main
```

`git rev-parse` сам знает где сейчас лежит хеш — в отдельном файле или внутри `packed-refs`.
