# 7. Templates — модуль `ansible.builtin.template`

## Зачем нужен template

Представь типовую задачу: у тебя 20 веб-серверов, и на каждом nginx должен слушать свой IP-адрес, а в конфиге должно стоять своё имя сервера. Конфиг у всех *почти* одинаковый — отличаются буквально две-три строки.

Модуль `copy` здесь не подходит: он переносит файл байт-в-байт, как есть. Пришлось бы держать 20 почти одинаковых копий конфига и вручную следить за каждой.

Модуль `template` решает эту проблему: ты пишешь **один шаблон** с переменными внутри, а Ansible на этапе выполнения подставляет в него значения, актуальные для каждого конкретного хоста. Один шаблон → уникальный конфиг на каждом сервере.

Механика простая: шаблон — это обычный текстовый файл, внутри которого встречаются конструкции Jinja2 (`{{ }}`, фильтры из темы 6, позже — `{% if %}` из темы 8). Перед отправкой на хост Ansible прогоняет файл через движок Jinja2 **на управляющей машине**, и на хост улетает уже готовый, «отрендеренный» текст без всяких скобок.

## Разница между `copy` и `template`

| | `copy` | `template` |
|---|---|---|
| Что делает с файлом | Переносит как есть, байт-в-байт | Сначала прогоняет через Jinja2, потом переносит результат |
| `{{ }}` внутри файла | Останутся в файле буквально, как текст | Будут заменены на значения переменных |
| Где обрабатывается | — | На управляющей ноде, до отправки |

Практическое правило: **есть `{{ }}` внутри файла → `template`, нет → `copy`.**

Это классический вопрос на собеседовании. Ещё один нюанс, который любят спрашивать: что будет, если файл с `{{ }}` внутри отдать модулю `copy`? Ответ — ничего не сломается, но скобки приедут на хост как обычный текст, и сервис, читающий такой конфиг, скорее всего упадёт с ошибкой парсинга.

## Где живут шаблоны

По конвенции шаблоны кладут в каталог `templates/` рядом с плейбуком, а файлам дают расширение `.j2`:

```
project/
├── nginx.yml            # плейбук
├── templates/
│   └── nginx.conf.j2    # шаблон
└── group_vars/
    └── webservers.yml   # переменные
```

Оба правила — соглашение, а не жёсткое требование (как и с каталогом `vars/` из темы 5). Расширение `.j2` нужно людям и редакторам (подсветка синтаксиса), Ansible на него не смотрит.

А вот как Ansible на самом деле ищет файл, стоит понимать точно:

- Если в `src` указан **относительный путь** (`src: nginx.conf.j2`), Ansible включает свой внутренний поисковый движок и ищет файл по цепочке: сначала в каталоге `templates/` рядом с плейбуком, потом в каталоге `templates/` внутри роли (если используются роли).
- Но никто не запрещает написать **абсолютный путь** (`src: /home/artem/my_files/custom.j2`) или свой относительный (`src: files/templates/config.j2`). В этом случае Ansible просто возьмёт файл по указанному пути, игнорируя стандартный каталог `templates/`.

## Параметры модуля

Синтаксис почти полностью повторяет `copy` — и это не случайно, `template` можно воспринимать как «`copy` с обработкой Jinja2»:

```yaml
- name: Развернуть конфиг nginx
  ansible.builtin.template:
    src: nginx.conf.j2          # шаблон на управляющей ноде
    dest: /etc/nginx/nginx.conf # куда положить результат на хосте
    owner: root
    group: root
    mode: '0644'
    backup: yes                 # перед заменой сохранить копию старого файла
    validate: 'nginx -t -c %s'  # проверить результат ДО подмены файла
```

Два параметра заслуживают отдельного внимания.

**`backup: yes`** — перед перезаписью Ansible сохранит рядом копию старого файла с меткой времени в имени (`nginx.conf.2026-07-04@12:30:45~`). Дешёвая страховка: если новый конфиг оказался кривым, есть с чего откатиться.

**`validate`** — команда, которой Ansible проверит **новый** файл до того, как положить его на место. Параметр настолько важный, что разберём его механику по шагам.

### Как работает `validate` под капотом

**Шаг 1.** Ansible рендерит шаблон и кладёт результат во **временный файл** на целевом хосте — куда-нибудь вроде `/root/.ansible/tmp/ansible-tmp-1720087234.12-8842/source`. Это ещё не `dest` — файл лежит в стороне, боевой конфиг пока не тронут.

**Шаг 2.** Берёт команду из `validate` и подставляет путь к этому временному файлу на место `%s`. То есть строка

```yaml
validate: 'nginx -t -c %s'
```

на хосте реально выполнится как:

```bash
nginx -t -c /root/.ansible/tmp/ansible-tmp-1720087234.12-8842/source
```

`%s` — плейсхолдер в стиле `printf`: «сюда подставь строку». Сам путь ты не знаешь и знать не должен — Ansible генерирует его на лету.

**Шаг 3.** Смотрит на код возврата команды:

- `0` (успех) → конфиг валиден, Ansible перемещает временный файл на место `dest`. Только теперь старый конфиг заменён.
- не `0` → таска падает с ошибкой, временный файл удаляется, **боевой конфиг остаётся старым, нетронутым**.

В этом весь смысл: проверка происходит **до** подмены, а не после. Без `validate` о битом конфиге узнаёшь только когда сервис откажется перезапускаться.

Два практических нюанса:

1. `%s` в команде **обязателен** — без него Ansible выдаст ошибку, потому что ему некуда подставить путь к временному файлу.
2. Команда проверки должна уметь валидировать файл по произвольному пути. У `nginx` это флаг `-c`, у `sshd` — `-f`, у `visudo` — `-cf`. Если у сервиса нет способа проверить конфиг «со стороны», `validate` для него не применим.

Канонический пример — конфиг SSH:

```yaml
- name: Развернуть конфиг sshd
  ansible.builtin.template:
    src: sshd_config.j2
    dest: /etc/ssh/sshd_config
    owner: root
    group: root
    mode: '0600'
    validate: 'sshd -t -f %s'   # sshd проверяет синтаксис конфига
```

Почему это важно: если залить битый `sshd_config` и перезапустить сервис — ты **отрежешь себе SSH-доступ к серверу**. С `validate` битый конфиг просто не доедет до места. Это тоже любимая тема интервьюеров: «как безопасно менять конфиг sshd через Ansible?»

## Живой пример: от простого к рабочему

### Минимальный пример — MOTD

MOTD (Message Of The Day, «сообщение дня») — стандартный механизм Linux: содержимое файла `/etc/motd` автоматически показывается каждому пользователю сразу после входа по SSH. То самое приветствие, которое вываливается при подключении к серверу. Для первого примера идеально: обычный текстовый файл, никаких сервисов перезапускать не надо, результат виден при следующем входе.

Самый простой шаблон, чтобы увидеть механику целиком. Файл `templates/motd.j2`:

```
Добро пожаловать на сервер {{ ansible_hostname }}!
ОС: {{ ansible_distribution }} {{ ansible_distribution_version }}
Обслуживается командой {{ team_name | default('DevOps') }}
```

Таска:

```yaml
- name: Развернуть MOTD
  ansible.builtin.template:
    src: motd.j2
    dest: /etc/motd
    owner: root
    group: root
    mode: '0644'
```

Здесь видно всё сразу: факты (`ansible_hostname`, `ansible_distribution`) Ansible собирает сам, переменная `team_name` может прийти из `group_vars`, а фильтр `default` из темы 6 страхует на случай, если её не определили.

### Рабочий пример — nginx

Переменные в `group_vars/webservers.yml`:

```yaml
nginx_port: 8080
nginx_worker_connections: 2048
server_admin_email: admin@example.com
```

Шаблон `templates/nginx.conf.j2`:

```
# {{ ansible_managed }}

user www-data;
worker_processes {{ ansible_processor_vcpus }};   # факт: число vCPU хоста

events {
    worker_connections {{ nginx_worker_connections | default(1024) }};
}

http {
    server {
        listen {{ nginx_port | default(80) }};
        server_name {{ ansible_hostname }};       # имя хоста подставится само

        # Контакт админа — из group_vars
        # {{ server_admin_email | upper }}
    }
}
```

Плейбук:

```yaml
---
- name: Настройка веб-серверов
  hosts: webservers
  become: true

  tasks:
    - name: Развернуть конфиг nginx
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        owner: root
        group: root
        mode: '0644'
        backup: yes
        validate: 'nginx -t -c %s'
```

Что здесь происходит по шагам:

1. Ansible читает `nginx.conf.j2` на управляющей ноде.
2. Прогоняет его через Jinja2: подставляет факты хоста (`ansible_hostname`, `ansible_processor_vcpus`), переменные из `group_vars`, применяет фильтры.
3. Готовый текст проверяет командой из `validate`.
4. Сравнивает результат с тем, что уже лежит на хосте. Если файлы идентичны — статус `ok`, ничего не делает. Если отличаются — сохраняет бэкап и кладёт новый файл, статус `changed`.

Пункт 4 — это идемпотентность в действии, и именно об неё можно споткнуться. Об этом — в разделе про `ansible_managed` в конце конспекта.

## Переменные и фильтры внутри `.j2`

Внутри шаблона работает всё, что мы разобрали в темах 5 и 6, без каких-либо оговорок:

- **переменные** из `group_vars/`, `host_vars/`, `vars:` и `vars_files:` плейбука — любой источник, без разницы;
- **факты**: `ansible_hostname`, `ansible_lo.ipv4.address`, `ansible_processor_vcpus` и т.д.;
- **магические переменные**: `inventory_hostname`, `hostvars`, `groups`;
- **фильтры** из темы 6: `default`, `upper`, `join`, `replace` и остальные.

Сам разбор фильтров здесь не повторяю — он в конспекте темы 6. Ключевая мысль: `.j2`-файл — это второе (и главное на практике) место, где живут фильтры Jinja2, наряду с YAML плейбука.

Конструкции `{% if %}` и `{% for %}` внутри шаблонов сознательно откладываем: условия — тема 8, циклы — тема 9. Там они лягут на уже знакомую почву.

## `ansible_managed` — маркер и его подводный камень

`ansible_managed` — специальная переменная, которую принято выводить комментарием в первой строке шаблона:

```
# {{ ansible_managed }}
```

Смысл: человек, открывший конфиг на сервере, сразу видит — файл сгенерирован Ansible, править руками бесполезно, при следующем запуске плейбука изменения будут перезаписаны.

### Ловушка: связь с идемпотентностью

Значение `ansible_managed` задаётся в `ansible.cfg` и по умолчанию (в зависимости от версии и настроек) может содержать плейсхолдеры даты и времени, например:

```ini
ansible_managed = Ansible managed: modified on %Y-%m-%d %H:%M:%S
```

В чём ловушка: если в шаблоне есть строка `# {{ ansible_managed }}` и в неё подставляется текущее время запуска плейбука, то **каждый запуск Ansible будет переписывать файл, даже если сами настройки не менялись**. Содержимое файла формально меняется — меняется строка с временем.

Последствия:

- таска всегда в статусе `changed` — идемпотентность сломана напрочь;
- хэндлеры, подписанные на эту таску, будут срабатывать при каждом запуске — сервис будет перезапускаться без причины.

### Как правильно

В продакшене строку `ansible_managed` в `ansible.cfg` переопределяют на статичную, без времени:

```ini
[defaults]
ansible_managed = File managed by Ansible, all changes will be overwritten
```

Теперь строка-маркер одинакова от запуска к запуску, содержимое файла стабильно, и `changed` появляется только тогда, когда реально изменились настройки.

Это отличный сюжет для собеседования: вопрос «почему таска с template всегда changed, хотя ничего не менялось?» проверяет, понимает ли кандидат идемпотентность на уровне механики, а не определения.
