## 1. Зачем нужна централизованная аутентификация

> **На пальцах:** LDAP — это база данных сотрудников, Kerberos — это безопасный вход по билетам, а SSSD — это клей, который соединяет их с Linux. Этого понимания часто хватает, чтобы пройти 80% интервью.

### Проблема: 1000 серверов, 200 пользователей

В небольшой компании с 5 серверами можно управлять пользователями вручную через `useradd`. В компании с сотнями серверов это невозможно:

Когда инженер увольняется — его аккаунт нужно удалить вручную на каждом сервере, и легко пропустить один. Новый сотрудник ждёт доступа, пока кто-то не пробежится по всем машинам и не создаст учётку везде. Смена пароля — та же история. Аудит («кто куда заходил») превращается в квест по логам сотен серверов. А единую политику паролей при локальных аккаунтах вообще невозможно обеспечить централизованно.

### Решение: централизованное хранилище учётных записей

```
Администратор
      │  создаёт пользователя ОДИН РАЗ
      ▼
 Active Directory / LDAP / FreeIPA
      │
      ├── server-01  ←── SSSD ──→ AD
      ├── server-02  ←── SSSD ──→ AD
      ├── server-03  ←── SSSD ──→ AD   Все серверы обращаются
      └── server-N   ←── SSSD ──→ AD   к одному источнику

Уволился сотрудник → отключить в AD → мгновенно потерял доступ везде
```

Три варианта централизованного хранилища — выбор зависит от окружения:
- **Active Directory** — решение Microsoft, Windows-native. Стандарт в корпоративных средах где есть Windows-инфраструктура.
- **LDAP** — это не продукт, а протокол. Можно поднять open source LDAP-сервер (например OpenLDAP) в чисто Linux-окружении без Windows вообще.
- **FreeIPA** — Red Hat решение для Linux-окружений, объединяет LDAP + Kerberos + DNS в одном продукте. Альтернатива AD если Windows в компании нет.

### Три задачи которые решает SSSD

**Identity** — кто существует в системе. Когда ты набираешь `getent passwd alice@company.com` (`getent` — утилита которая спрашивает у системы «есть ли такой пользователь?»), Linux должен найти этого пользователя и вернуть его UID, GID, домашнюю директорию. Без SSSD Linux смотрит только в `/etc/passwd` — и не знает ни про какой AD.

**Authentication** — проверка что пользователь тот, за кого себя выдаёт. SSSD подключается к PAM и перехватывает проверку пароля: вместо `/etc/shadow` пароль проверяется через Kerberos — протокол аутентификации, встроенный в Active Directory. Проще говоря: SSSD отправляет запрос на контроллер домена AD, тот проверяет пароль и отвечает «да, это действительно alice» или «нет». Локальный файл `/etc/shadow` при этом вообще не задействован. Пользователь вводит пароль один раз — SSSD разбирается с остальным.

**Authorization** — что пользователю можно делать. Например, состоит ли он в группе `linux-admins` в AD, которой разрешён `sudo`. SSSD подтягивает членство в группах из AD и отдаёт их системе — `/etc/sudoers` работает с AD-группами как с локальными.

## 2. LDAP — протокол и структура каталога

### Что такое LDAP

**LDAP (Lightweight Directory Access Protocol)** — протокол доступа к иерархическому каталогу объектов. Каталог оптимизирован для чтения: данные меняются редко, читаются очень часто.

Порты: `389` (LDAP), `636` (LDAPS — LDAP over TLS), `3268/3269` (Global Catalog в AD).

> ⚠️ **Безопасность**: никогда не используй `id_provider = ldap` без шифрования. `ldap_id_use_start_tls = true` — это параметр в `/etc/sssd/sssd.conf` в секции `[domain/...]`. Альтернатива — подключаться сразу по LDAPS (порт 636 вместо 389, указывается в `ldap_uri`). Без одного из этих двух вариантов данные пользователей, включая хэши паролей при простом bind, передаются по сети в открытом виде.

### Структура каталога (DIT — Directory Information Tree)

```
dc=company,dc=com               ← корень (domain component)
├── ou=users                    ← organizational unit
│   ├── cn=alice                ← объект пользователя
│   ├── cn=bob
│   └── cn=charlie
├── ou=groups
│   ├── cn=developers
│   └── cn=admins
└── ou=serviceaccounts
    ├── cn=jenkins
    └── cn=gitlab-runner
```

### DN — Distinguished Name

Полный путь к объекту в дереве, читается справа налево:

```
cn=alice,ou=users,dc=company,dc=com
   ─────  ────────  ────────  ────
    ↑        ↑         ↑        ↑
  имя    отдел    домен.com   домен
```

### Атрибуты объекта пользователя

```bash
# Посмотреть атрибуты пользователя через ldapsearch
ldapsearch -x -H ldap://dc.company.com \
  -D "cn=admin,dc=company,dc=com" -W \
  -b "ou=users,dc=company,dc=com" \
  "(uid=alice)"
```

Стандартные LDAP-атрибуты для Linux-пользователей (POSIX schema):

```
dn: cn=alice,ou=users,dc=company,dc=com
objectClass: posixAccount
objectClass: shadowAccount
uid: alice                    ← Unix username
cn: Alice Smith               ← Common Name
uidNumber: 10001              ← Unix UID
gidNumber: 10000              ← Primary GID
homeDirectory: /home/alice
loginShell: /bin/bash
userPassword: {SSHA}...       ← хэш пароля
shadowLastChange: 19742
shadowMax: 90                 ← максимальный срок пароля в днях
```

### LDAP операции

На собесе достаточно сказать: «Я проверю доступность и корректность схемы через `ldapsearch` с биндом технической учётки». Флаги наизусть не нужны — важно понимать, что делает каждая команда.

```bash
# Аутентифицированный поиск пользователя
ldapsearch -x -H ldap://ldap.company.com \
  -D "cn=readonly,dc=company,dc=com" -W \
  -b "dc=company,dc=com" "(uid=alice)"

# Проверить подключение и TLS
ldapsearch -x -H ldaps://ldap.company.com \
  -b "" -s base "(objectClass=*)" namingContexts
```

## 3. Active Directory

### AD = LDAP + Kerberos + DNS + Group Policy

Active Directory — это Microsoft-реализация LDAP с существенными расширениями:

| Компонент | Что даёт |
|-----------|---------|
| LDAP (порт 389/636) | Хранение объектов: пользователи, группы, компьютеры |
| Kerberos (порт 88) | Аутентификация без передачи пароля по сети |
| DNS (порт 53) | Поиск контроллеров домена, SRV-записи |
| Group Policy | Централизованное управление настройками |
| Kerberos PAC | Авторизационные данные в билете (группы, атрибуты) |

### Структура AD

```
Лес (Forest): company.com
└── Домен (Domain): company.com
    ├── Домен: eu.company.com
    └── Домен: us.company.com

Доверие (Trust): между доменами одного леса — автоматическое двустороннее
```

### Важные объекты AD для Linux-интеграции

```
Organizational Unit (OU): аналог папки, для структурирования
User: учётная запись пользователя
Computer: учётная запись компьютера (при join к домену)
Group: группа (Security Group — для прав, Distribution — для почты)
Service Principal Name (SPN): идентификатор сервиса для Kerberos
```

### SPN — Service Principal Name

SPN — уникальный идентификатор сервиса в Kerberos. Формат: `сервис/хост@REALM`.
Примеры: `host/server01.company.com@COMPANY.COM`, `HTTP/web.company.com@COMPANY.COM`.

**Важно:** если два объекта в AD имеют одинаковый SPN — Kerberos сломается, и аутентификация к этому сервису будет падать с ошибкой `KDC_ERR_S_PRINCIPAL_UNKNOWN` или неожиданным поведением. Диагностика: `setspn -X` (на Windows) или поиск дублей через ldapsearch.

## 4. Kerberos

### Зачем нужен Kerberos

Основная проблема которую решает Kerberos: **пароль никогда не передаётся по сети** даже при первой аутентификации. Вместо этого используется система криптографических билетов.

Почему не нужен SSL/TLS для защиты пароля при первом шаге: клиент не отправляет пароль. Он использует хэш пароля как **ключ шифрования** для подписи запроса. KDC проверяет подпись своим экземпляром того же хэша — и если они совпадают, аутентификация прошла. Пароль ни в каком виде по сети не ходил.

### Участники

```
KDC (Key Distribution Center) = AS + TGS — центр доверия, обычно контроллер домена AD
  ├── AS (Authentication Service) — выдаёт TGT
  └── TGS (Ticket Granting Service) — выдаёт Service Tickets

Client — пользователь или сервис
Service — ресурс к которому нужен доступ (файловый сервер, веб-сервис)
```

### Процесс аутентификации (3 шага)

```
── Шаг 1: получить TGT (Ticket Granting Ticket) ──────────────────

Клиент                    AS (часть KDC)
   │── "Я Alice, дайте TGT" ──────────────────────────────→│
   │                                               проверяет хэш пароля
   │                                               (пароль как ключ шифрования)
   │←── TGT (зашифрован ключом KDC) ──────────────────────│
   │    TGT содержит: имя пользователя, срок действия,
   │    session key (для общения с TGS), PAC (группы)

── Шаг 2: получить Service Ticket для конкретного сервиса ────────

Клиент                    TGS (часть KDC)
   │── TGT + "хочу доступ к server.company.com" ──────────→│
   │                                               проверяет TGT
   │←── Service Ticket (зашифрован ключом сервиса) ────────│

── Шаг 3: аутентификация у сервиса ──────────────────────────────

Клиент                    Сервис
   │── Service Ticket ────────────────────────────────────→│
   │                                               расшифровывает своим ключом
   │                                               проверяет валидность
   │←── доступ разрешён ─────────────────────────────────│
```

Пароль не передавался ни разу. TGT действует обычно 10 часов — после этого нужно заново `kinit`.

### Kerberos PAC (Privilege Attribute Certificate)

PAC — это расширение Microsoft, которое зашивается внутрь Kerberos-билета. PAC содержит **все SID групп пользователя**, его привилегии и атрибуты.

**Почему это важно:** в чистом LDAP после проверки пароля сервер делает дополнительный запрос в LDAP чтобы узнать, в каких группах состоит пользователь. В AD — не нужно. Сервер расшифровывает билет, видит PAC с группами, принимает решение об авторизации без единого обращения в AD.

```
LDAP-аутентификация:
  1. Проверить пароль → LDAP bind
  2. Получить группы  → отдельный LDAP-запрос
  3. Авторизовать

Kerberos + PAC:
  1. Проверить билет (расшифровать локально)
  2. Прочитать PAC (группы уже внутри)
  3. Авторизовать ← никаких сетевых запросов!
```

**Проблема больших PAC:** если пользователь состоит в 500+ группах AD, PAC и соответственно Kerberos-билет становятся огромными. SSH начинает отвергать соединение или SSSD падает с ошибкой. Решение: ограничить количество групп пользователя или фильтровать их на уровне SSSD.

### Keytab-файлы — автоматизация без паролей

В production сервисам нельзя интерактивно вводить пароль через `kinit`. Для этого существуют **keytab-файлы**.

Keytab — бинарный файл, содержащий пары «принципал Kerberos + зашифрованный ключ (хэш пароля)». SSSD и другие сервисы используют его для получения TGT без участия человека.

```bash
# Получить TGT из keytab (беспарольно)
kinit -k -t /etc/krb5.keytab host/server01.company.com

# Проверить что в keytab
klist -k /etc/krb5.keytab

# Посмотреть принципалы
ktutil
  rkt /etc/krb5.keytab
  list
  quit
```

При `realm join` keytab создаётся автоматически: `/etc/krb5.keytab`. SSSD использует его для аутентификации машинного аккаунта при запросах к AD.

**Безопасность keytab:** файл эквивалентен паролю. Права должны быть `600`, владелец — root или сервисный пользователь. Компрометация keytab = компрометация учётки сервиса.

### Хранение билетов и безопасность

По умолчанию Kerberos хранит билеты в `/tmp/krb5cc_<UID>`. Если злоумышленник получает root-доступ — он может украсть этот файл и ходить под чужой учёткой до истечения TGT (до 10 часов). Это называется **Ticket Harvesting**.

Защита — использовать хранилище ядра вместо файлов:

```ini
# /etc/krb5.conf
[libdefaults]
    default_ccache_name = KEYRING:persistent:%{uid}
    # или KCM (Kerberos Credential Manager, через sssd-kcm)
    # default_ccache_name = KCM:
```

`KEYRING` хранит билеты в защищённом хранилище ядра Linux — украсть их через `/tmp` невозможно.

### Kerberos на практике

```bash
# Получить TGT (требует пароль один раз)
kinit alice@COMPANY.COM

# Получить TGT из keytab (для автоматизации)
kinit -k -t /etc/krb5.keytab host/server01.company.com

# Посмотреть текущие билеты
klist
# Issued            Expires           Principal
# Jan 15 10:00:00   Jan 15 20:00:00   krbtgt/COMPANY.COM@COMPANY.COM

# Обновить TGT (если не истёк)
kinit -R

# Уничтожить все билеты (аналог logout из домена)
kdestroy
```

```ini
# /etc/krb5.conf — минимальный пример
[libdefaults]
    default_realm = COMPANY.COM
    dns_lookup_realm = true    # искать realm через DNS SRV-записи
    dns_lookup_kdc = true      # искать KDC через DNS
    default_ccache_name = KEYRING:persistent:%{uid}  # безопасное хранение

[realms]
    COMPANY.COM = {
        kdc = dc01.company.com
        admin_server = dc01.company.com
    }

[domain_realm]
    .company.com = COMPANY.COM
    company.com = COMPANY.COM
```

## 5. SSSD — архитектура и конфигурация

### Что такое SSSD

**SSSD (System Security Services Daemon)** — демон который:
- подключается к identity-провайдерам (AD, LDAP, FreeIPA, Kerberos)
- кэширует результаты (пользователи могут логиниться даже если AD недоступен)
- предоставляет NSS (Name Service Switch) и PAM интерфейсы для системы

```
Linux-сервер
├── NSS → sssd → identity провайдер (AD/LDAP)
│    getent passwd alice@company.com
│
├── PAM → sssd → auth провайдер (Kerberos/LDAP bind)
│    аутентификация при логине
│
└── /var/lib/sss/db/ → локальный кэш (работает offline)
```

### Архитектура SSSD

```
sssd (главный процесс)
├── sssd_be  — backend, подключается к AD/LDAP
├── sssd_nss — обрабатывает NSS-запросы (getent, id)
├── sssd_pam — обрабатывает PAM-запросы (аутентификация)
└── sssd_sudo — обрабатывает sudo-правила из LDAP/AD
```

### /etc/sssd/sssd.conf — структура

```ini
[sssd]
services = nss, pam, sudo    # какие сервисы предоставлять
domains = company.com        # список доменов

[domain/company.com]
# Тип провайдера
id_provider = ad             # откуда брать пользователей
auth_provider = ad           # как аутентифицировать
sudo_provider = ad           # sudo-правила из AD

# AD-специфичные настройки
ad_domain = company.com
krb5_realm = COMPANY.COM
ad_server = dc01.company.com, dc02.company.com  # список DC

# Формат имени пользователя
use_fully_qualified_names = False  # alice вместо alice@company.com
fallback_homedir = /home/%u        # шаблон домашней директории
default_shell = /bin/bash

# Кэш
cache_credentials = true           # работать offline
krb5_store_password_if_offline = true

# UID/GID маппинг (см. раздел ниже)
ldap_id_mapping = true             # генерировать UID из SID (рекомендуется для AD)

# Ограничить каких пользователей AD видит эта машина
ad_gpo_access_control = enforcing  # применять Group Policy
# simple_allow_groups = linux-admins, linux-users  # белый список групп
```

```bash
# Права на конфиг — обязательно 600!
chmod 600 /etc/sssd/sssd.conf
chown root:root /etc/sssd/sssd.conf
```

### UID/GID маппинг — критичная тема для AD

В реальных корпоративных AD Windows-администраторы **крайне редко** заполняют UNIX-атрибуты (`uidNumber`, `gidNumber`). SSSD решает эту проблему двумя способами:

**Режим 1: `ldap_id_mapping = false`** (явные атрибуты)
- SSSD ищет `uidNumber` и `gidNumber` в объекте пользователя AD
- Если атрибутов нет — пользователь **не авторизуется**
- Требует настройки расширения схемы RFC 2307 (Unix Attributes) в AD

**Режим 2: `ldap_id_mapping = true`** (алгоритмический маппинг, по умолчанию для `id_provider = ad`)
- SSSD берёт SID пользователя из Windows (например `S-1-5-21-3623811015-3361044348-30300820-1013`)
- Применяет хэш-функцию и **алгоритмически генерирует стабильный UID/GID**
- Windows-атрибуты не нужны
- UID будет одинаковым на всех серверах, если они используют один и тот же домен и конфигурацию SSSD

```
Вопрос на собесе: «Что делать если в AD нет uidNumber/gidNumber?»
Ответ: Использовать ldap_id_mapping = true — SSSD сам сгенерирует
       стабильный UID из Windows SID пользователя.
```

### SSH Public Keys через SSSD

В DevOps-окружении SSH-доступ по паролю не используется. Но при 1000 серверах копировать `authorized_keys` — та же проблема что и с пользователями.

**Решение:** SSSD умеет хранить SSH-ключи прямо в LDAP/AD и отдавать их при запросе.

```ini
# /etc/sssd/sssd.conf
[sssd]
services = nss, pam, sudo, ssh   # добавить ssh

[domain/company.com]
ldap_user_ssh_public_key = sshPublicKey  # атрибут в LDAP/AD
```

```bash
# /etc/ssh/sshd_config
AuthorizedKeysCommand /usr/bin/sss_ssh_authorizedkeys
AuthorizedKeysCommandUser root
```

Теперь при SSH-подключении sshd спрашивает у SSSD публичные ключи пользователя — а SSSD забирает их из AD/LDAP. Добавил ключ пользователю в AD → он работает сразу на всех серверах.

### Настройка NSS для использования SSSD

```bash
cat /etc/nsswitch.conf

# sudoers:  files sss     ← sudo-правила из AD
```

### Присоединение к домену через realm

`realmd` — это не просто обёртка над `net join`. Он автоматически:
- обнаруживает контроллеры домена через DNS SRV-записи
- создаёт computer account в AD
- генерирует keytab (`/etc/krb5.keytab`)
- настраивает `/etc/nsswitch.conf`, `/etc/krb5.conf`, `/etc/sssd/sssd.conf`

```bash
# Обнаружить домен

# Присоединиться (лучше создать отдельный аккаунт с минимальными правами join)
realm join -U domain-join-account company.com

# Проверить что join прошёл успешно
realm list
# company.com
#   type: kerberos
#   realm-name: COMPANY.COM
#   configured: kerberos-member
#   server-software: active-directory
#   client-software: sssd
```

## 7. FreeIPA

### Что такое FreeIPA

**FreeIPA** — open source альтернатива Active Directory для Linux-окружений. Объединяет в одном решении:

```
FreeIPA
├── 389 Directory Server (LDAP) — хранение объектов
├── MIT Kerberos                 — аутентификация
├── Dogtag PKI / CA              — выдача сертификатов
├── BIND DNS                     — встроенный DNS сервер
├── NTP (chrony)                 — синхронизация времени
└── Web UI + CLI                 — удобное управление
```

### Cross-Realm Trust: FreeIPA + Active Directory

На собесе важнее знать концепцию Trust, чем команды CLI.

**Kerberos Cross-Realm Trust** позволяет пользователям Windows AD логиниться на Linux-серверы, управляемые FreeIPA, и наоборот — без создания дублирующих учёток.

```
Как это работает:
─────────────────────────────────────────────────────────
AD пользователь alice@COMPANY.COM хочет попасть на Linux-сервер IPA

1. Alice получает TGT в своём AD (COMPANY.COM)
2. Просит билет для сервиса в IPA realm (LINUX.COMPANY.COM)
3. AD обращается к IPA KDC — между ними настроен Trust
4. IPA выдаёт referral-билет
5. Alice получает Service Ticket для IPA-сервера
6. Логин успешен — без создания учётки в IPA
```

Настройка Trust требует настройки доверия на уровне обоих KDC (AD и IPA) и синхронизации DNS между доменами. В production это делают через `ipa trust-add`.

### Концептуальное сравнение (не команды)

| | FreeIPA | Active Directory |
|--|---------|-----------------|
| Платформа | Linux-native | Windows-native |
| Лицензия | Open Source | Коммерческая |
| LDAP | 389 DS (Red Hat) | Microsoft AD LDAP |
| Kerberos | MIT Kerberos | Microsoft Kerberos |
| Интеграция с Linux | Нативная | Через SSSD/realm |
| Group Policy | Нет (HBAC + sudo rules) | Есть |
| Trusts с AD | Возможны (Cross-Realm) | Нативно |
| Web UI | Да | Нет (ADUC — Windows) |

## 9. Анти-паттерны

**Использование Domain Admin для join:**
Создай отдельный аккаунт с минимальными правами только для присоединения компьютеров к домену. Domain Admin в конфиге sssd — огромный риск.

**Отключение кэширования (`cache_credentials = false`):**
При недоступности AD пользователи не смогут войти. В production всегда оставляй кэш включённым.

**`use_fully_qualified_names = True` без обдумывания:**
Если включено — имена везде будут `alice@company.com`. Скрипты, crontab, файлы конфигурации должны это учитывать. Решите сразу и делайте везде консистентно.

**Нет мониторинга статуса SSSD:**
SSSD может уйти в Offline и никто не заметит. Добавь в мониторинг: `sssctl domain-status company.com` должен отвечать "Online".

**Игнорирование синхронизации времени:**
Kerberos требует расхождение не более 5 минут. Расхождение времени — самая частая причина «непонятных» отказов аутентификации. Всегда настраивай NTP с DC как источником.

**`realm permit --all` в production:**
Разрешает вход ЛЮБОМУ пользователю AD. Используй `realm permit -g specific-group`. Принцип минимальных привилегий.

**Keytab с правами 644:**
Keytab — это эквивалент пароля. Права только `600`, владелец — root или сервисный пользователь.

**Билеты Kerberos в `/tmp`:**
Используй `KEYRING` или `KCM` в `/etc/krb5.conf` — защита от Ticket Harvesting.

## 10. Реальные кейсы с дебагом

### Кейс 1: пользователь не может войти, был раньше

```bash
# Симптом: alice могла войти вчера, сегодня — нет

# Шаг 1: проверить статус SSSD
sssctl domain-status company.com
# Online status: Offline  ← вот причина!

# Шаг 2: проверить сетевой доступ к DC
ping dc01.company.com
nc -zv dc01.company.com 389

# Шаг 3: если AD доступен но SSSD не видит его
systemctl restart sssd
# Иногда SSSD "зависает" в Offline и не замечает что AD снова доступен
```

### Кейс 2: id alice работает, sudo не работает

```bash
# Симптом: id alice — OK, но sudo не даёт права хотя группа есть

# Шаг 1: проверить что sudoers видит AD группу
sudo -l -U alice

# Шаг 2: проверить формат имени в /etc/sudoers
# Если use_fully_qualified_names = True:
# %linux-admins@company.com  ALL=(ALL) ALL  ← нужен FQDN
# Если False:
# %linux-admins  ALL=(ALL) ALL

# Шаг 3: проверить членство в группе как видит SSSD
getent group linux-admins
# Если группы нет — очистить кэш
sss_cache -G && getent group linux-admins
```

### Кейс 3: медленный вход (30-60 секунд)

```bash
# Причина 1: SSSD ждёт таймаута попытки второго DC
dig SRV _ldap._tcp.company.com

# Решение: явно указать DC в sssd.conf
[domain/company.com]
ad_server = dc01.company.com
ad_backup_server = dc02.company.com

# Причина 2: reverse DNS lookup зависает
[domain/company.com]
lookup_family_order = ipv4_only
```

### Кейс 4: слишком много групп — PAC size limit

```
Симптом: пользователь состоит в 500+ группах AD.
         SSH-соединение сбрасывается или SSSD падает с ошибкой.

Причина: PAC внутри Kerberos-билета становится огромным.
         SSH и PAM имеют ограничения на размер буфера аутентификации.

Диагностика:
  klist -v  ← смотри размер билета
  /var/log/sssd/sssd_pam.log ← ошибки вида "token size exceeded"

Решение:
  1. Убрать пользователя из лишних групп в AD (правильный путь)
  2. Фильтровать группы на уровне SSSD:
     [domain/company.com]
     ad_maximum_machine_account_password_age = 30
     # или ldap_group_nesting_level = 2  ← ограничить глубину вложенности групп
```

### Кейс 5: сервер восстановлен из бэкапа — SSSD сломан

```
Симптом: после восстановления сервера из бэкапа (которому 2+ месяца)
         SSSD перестал аутентифицировать пользователей.

Причина: при realm join создаётся учётная запись компьютера в AD.
         SSSD автоматически меняет её пароль каждые 30 дней.
         Восстановленный сервер знает старый пароль — AD знает новый.
         Рассинхрон = SSSD не может аутентифицироваться в AD.

Диагностика:
  sssctl domain-status company.com
  # "Kerberos authentication failed" или "Cannot contact KDC"

Решение:
  adcli update-computer --verbose
  # Обновляет пароль машинного аккаунта в AD
  systemctl restart sssd
```

### Кейс 6: «призрачный» пользователь — удалён из AD, но заходит

```
Симптом: пользователя удалили из AD, но он всё ещё может войти на сервер.

Причина: cache_credentials = true, кэш ещё не истёк.
         SSSD работает в Offline-режиме (или считает что работает).
         Это плата за отказоустойчивость.

Решение (немедленная блокировка):
  sss_cache -u username   ← инвалидировать кэш конкретного пользователя
  sssctl cache-remove --override  ← сбросить весь кэш

Профилактика:
  Настроить мониторинг Online-статуса SSSD.
  Уменьшить entry_cache_timeout в sssd.conf (по умолчанию 5400 сек = 90 мин).
```

## 11. Вопросы на собесе

**«Почему нельзя просто добавить пользователей вручную на всех серверах?»**
Управление учётными записями не масштабируется: увольнение сотрудника требует удаления с каждого сервера, единая политика паролей невозможна, нет единого аудита. Централизованное решение (AD/LDAP/FreeIPA) решает всё это в одной точке.

**«В чём разница между LDAP и Active Directory?»**
AD — реализация Microsoft поверх LDAP с добавлением Kerberos (аутентификация без передачи пароля), DNS (SRV-записи для обнаружения DC), Group Policy и расширений схемы включая PAC. Чистый LDAP — только протокол доступа к каталогу.

**«Зачем Kerberos если LDAP уже есть?»**
LDAP с простым bind передаёт пароль при каждой аутентификации. Kerberos не передаёт пароль по сети вообще — хэш используется как ключ шифрования только локально. Плюс PAC в билете избавляет от дополнительных запросов в LDAP за группами при каждой авторизации.

**«Что такое SSSD и что будет если он упадёт?»**
SSSD — демон-посредник между системой и identity-провайдером. При падении: `getent passwd` не вернёт AD-пользователей, аутентификация AD-пользователей провалится. Но если `cache_credentials = true` — пользователи с кэшем войдут. Локальные пользователи из `/etc/passwd` не затронуты.

**«Что делать если в AD нет uidNumber/gidNumber?»**
Использовать `ldap_id_mapping = true` в sssd.conf — SSSD сам сгенерирует стабильный UID из Windows SID пользователя. UID будет одинаковым на всех серверах с одинаковой конфигурацией домена.

**«Как централизовать SSH-ключи при 1000 серверов?»**
SSSD поддерживает хранение SSH-ключей в LDAP/AD (атрибут `sshPublicKey`). В sshd_config прописывается `AuthorizedKeysCommand /usr/bin/sss_ssh_authorizedkeys` — и SSH при подключении спрашивает ключи у SSSD, а не из `~/.ssh/authorized_keys`.

**«Почему пользователь с 500+ группами не может залогиниться?»**
PAC в Kerberos-билете содержит SID всех групп. При очень большом количестве групп размер билета превышает лимиты буферов SSH/PAM. Решение: уменьшить количество групп или ограничить глубину их вложенности в SSSD.

**«Как проверить что Linux-сервер правильно интегрирован с AD?»**
```bash
realm list                               # статус домена
sssctl domain-status company.com         # Online/Offline
id alice@company.com                     # разрешается ли пользователь
kinit alice@COMPANY.COM && klist         # работает ли Kerberos
getent passwd alice@company.com          # NSS видит пользователя
ssh alice@company.com@localhost          # аутентификация работает
```

## 12. Шпаргалка

```bash
# realm — управление доменом
realm discover company.com              # обнаружить домен
realm join -U domain-join-account company.com  # присоединиться (не Domain Admin!)
realm leave company.com                 # покинуть домен
realm list                              # статус
realm permit -g linux-admins            # разрешить группу

# SSSD
systemctl status sssd
sssctl domain-status company.com        # Online/Offline?
sssctl user-checks alice                # диагностика пользователя
sss_cache -G && sss_cache -U            # очистить кэш групп/пользователей
sss_cache -u alice                      # инвалидировать кэш конкретного пользователя
tail -f /var/log/sssd/sssd_*.log        # логи

# Проверка пользователей
id alice@company.com                    # UID, GID, группы
getent passwd alice@company.com         # через NSS
getent group linux-admins               # члены группы

# Kerberos
kinit alice@COMPANY.COM                 # получить TGT интерактивно
kinit -k -t /etc/krb5.keytab host/server01.company.com  # из keytab (автоматизация)
klist                                   # показать билеты
klist -k /etc/krb5.keytab              # показать принципалы в keytab
kdestroy                                # уничтожить билеты
kinit -R                                # обновить TGT

# LDAP диагностика
ldapsearch -x -H ldap://dc.company.com \
  -D "alice@company.com" -W \
  -b "dc=company,dc=com" "(sAMAccountName=alice)"

# Сеть
nslookup -type=SRV _ldap._tcp.company.com
nslookup -type=SRV _kerberos._tcp.company.com
nc -zv dc01.company.com 88 389 636      # проверить порты

# adcli
adcli info company.com                  # инфо о домене
adcli update-computer --verbose         # обновить пароль машинного аккаунта

# SSH ключи через SSSD
# /etc/ssh/sshd_config:
#   AuthorizedKeysCommand /usr/bin/sss_ssh_authorizedkeys
#   AuthorizedKeysCommandUser root
sss_ssh_authorizedkeys alice            # получить ключи пользователя вручную
```
