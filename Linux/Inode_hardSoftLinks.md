## Что такое inode

**inode** (index node) — это структура данных на диске, в которой файловая система (ext4, xfs, btrfs и др.) хранит **все метаданные файла, кроме его имени**. Каждый файл или директория имеют ровно один inode, а у каждого inode есть уникальный номер в пределах файловой системы.

Когда Linux создаёт файл — происходит две отдельные операции:
Операция 1: данные файла записываются в блоки на диске
Операция 2: создаётся inode — структура метаданных, которая описывает этот файл

Ключевая идея разделения:
- **Имя файла** живёт в записи директории
- **Всё остальное** (права, владелец, размер, указатели на данные) — в inode

Именно это разделение делает возможными hardlink'и.

```
Директория             inode #42              Блоки данных
┌──────────────┐       ┌──────────────────┐   ┌──────────┐
│ notes.txt→42 │──────▶│ тип: regular     │──▶│ block 0  │
│ link.txt →42 │──┐    │ права: 0644      │   ├──────────┤
│ photo.jpg→87 │  └───▶│ uid/gid: 1000    │──▶│ block 1  │
└──────────────┘        │ размер: 2048 B   │   └──────────┘
                        │ link count: 2    │
                        │ atime/mtime/ctime│
                        │ указатели блоков │
                        └──────────────────┘
```

Директория в Linux — это просто специальный файл, содержимое которого представляет собой таблицу из двух колонок:

```
имя файла        номер inode
─────────────────────────────
.                42          ← сама эта директория
..               7           ← родительская директория
notes.txt        1138
photo.jpg        2049
script.sh        3821
```

Когда ты делаешь ls /home/fa1ry — ядро открывает файл директории, читает эту таблицу и показывает тебе имена. Когда ты открываешь notes.txt — ядро смотрит в таблицу, находит номер inode 1138, идёт в inode table, берёт метаданные и указатели на блоки данных.

## Что хранит inode

| Поле | Описание |
|------|----------|
| Тип файла | regular, directory, symlink, block device, char device, socket, pipe |
| Права доступа | rwxrwxrwx + sticky/setuid/setgid биты |
| uid / gid | Владелец файла |
| Размер | В байтах |
| `atime` | Время последнего **доступа** (чтения) |
| `mtime` | Время последнего изменения **содержимого** |
| `ctime` | Время последнего изменения **inode** (права, переименование, hardlink) |
| link count | Число имён (hardlink'ов), указывающих на этот inode |
| Указатели блоков | Адреса блоков данных на диске |

> **Чего нет в inode:** имени файла и пути к нему.

## Hardlink vs Symlink

### Hardlink

**Определение:** hardlink — это просто ещё одна запись в таблице директории, которая указывает на **уже существующий inode**. Никакого нового файла не создаётся — создаётся новое *имя* для того же самого inode. Оба имени абсолютно равноправны: у файловой системы нет понятия «оригинал» и «ссылка».

- Новая запись в директории, указывающая на **тот же inode**
- `link count` увеличивается на 1
- Нельзя создать на директорию (во избежание циклов — подробнее ниже)
- Нельзя пересекать границы файловой системы
- После удаления одного имени данные живут, пока `link count > 0`

```
notes.txt ──┐
             ├──▶ inode #42 (link count = 2) ──▶ data blocks
link.txt  ──┘
```

```bash
$ echo "hello" > notes.txt
$ ln notes.txt link.txt          # создаём hardlink

$ ls -i notes.txt link.txt
42 notes.txt
42 link.txt                      # ← один и тот же inode!

$ stat notes.txt | grep Links
Links: 2                         # link count вырос до 2
```

### Symlink

**Определение:** symlink (символическая ссылка) — это **отдельный файл** с собственным inode, в котором в виде обычной строки хранится путь к цели. Когда ядро встречает такой файл при обходе пути, оно читает строку и продолжает навигацию по ней. Это принципиально отличается от hardlink: два разных inode, два разных объекта файловой системы.

- Отдельный файл со **своим inode** (тип: symlink)
- Содержит **путь** к цели в виде строки
- Может пересекать файловые системы
- Работает для директорий
- Если цель удалена — ссылка "протухает" (dangling symlink)

```
symlink.txt ──▶ inode #201 (хранит путь "/home/user/notes.txt") ──▶ inode #42 ──▶ data
```

Здесь важно, что у `symlink.txt` и `notes.txt` **разные** inode. Это хорошо видно в консоли:

```bash
$ echo "hello" > notes.txt
$ ln -s /home/user/notes.txt symlink.txt   # создаём symlink

$ ls -i notes.txt symlink.txt
42  notes.txt
201 symlink.txt    # ← РАЗНЫЕ inode! symlink — отдельный файл

$ stat notes.txt | grep -E "Inode|Links"
Inode: 42        Links: 1        # у оригинала link count НЕ изменился

$ stat symlink.txt | grep -E "Inode|Links|File:"
  File: symlink.txt -> /home/user/notes.txt
Inode: 201       Links: 1

$ readlink symlink.txt
/home/user/notes.txt             # содержимое symlink — просто строка-путь
```

Схема в сравнении:

```
HARDLINK — одно тело, два имени:

notes.txt  ──┐
              ├──▶  inode #42  ──▶  data
link.txt   ──┘
              (оба имени → один inode)


SYMLINK — два отдельных файла, один указывает на другой:

symlink.txt ──▶  inode #201        inode #42  ──▶  data
                 (тип: symlink)         ▲
                 (данные:               │
                  "/home/user/   ───────┘
                   notes.txt")
              (ядро читает путь и идёт к inode #42)
```

### Сравнительная таблица

| Свойство | Hardlink | Symlink |
|----------|----------|---------|
| Свой inode? | Нет, тот же | Да, новый |
| Что хранит | Номер inode | Путь к цели |
| Пересекает ФС? | Нет | Да |
| Для директорий? | Нет (только root) | Да |
| Переживает удаление цели? | Данные живы, пока count > 0 | Ссылка "протухает" |

## Почему hardlink нельзя создать на директорию

Файловая система — это **дерево**: каждый узел имеет ровно одного родителя, обход всегда конечен. Hardlink на директорию превращает дерево в граф с циклом.

Пример: создаём hardlink `docs → /home`. Теперь путь `/home/user/docs/user/docs/user/…` уходит в бесконечность:

```
Нормальное дерево          Hardlink на директорию

/                          /
└── home                   └── home  ◀─────────────┐
    └── user                   └── user             │
        └── docs               └── docs ────────────┘  (цикл!)
```

Любая утилита, которая рекурсивно обходит дерево — `du`, `find`, `cp -r`, `rsync`, `tar` — попадёт в бесконечный цикл и зависнет:

```bash
$ du -sh /home
# уходит считать /home/user/docs/user/docs/user/... → зависание
```

**Дополнительно ломается `fsck`** — и это отдельная важная история.

### Что такое `fsck` и граф inode

`fsck` (filesystem check) — утилита проверки и восстановления файловой системы после сбоев (внезапное отключение питания, паника ядра, повреждение диска). Запускается автоматически при загрузке или вручную:

```bash
$ fsck /dev/sda1
```

Чтобы понять, что она делает, нужно понять, как файловая система устроена с точки зрения графов.

**Граф inode** — это математическая модель файловой системы. Каждый inode — это **узел** графа. Каждый указатель «директория содержит дочерний объект» — это **ребро** (стрелка) между узлами. Нормальная файловая система — это **дерево**: ориентированный граф без циклов, где у каждого узла ровно один родитель.

```
Нормальная ФС — это дерево (каждый узел имеет ровно 1 родителя):

           /  (inode #2)
          / \
    home/    etc/
  (inode #5) (inode #8)
      |
    user/
  (inode #12)
    /   \
file1  file2
(#31)  (#32)

Путь к file1 единственный: / → home → user → file1
```

`fsck` при проверке делает следующее:
1. Берёт корневой inode (`/`)
2. Обходит всё дерево, считая для каждого inode количество ссылок на него
3. Сравнивает подсчитанное с тем, что записано в поле `link count` самого inode
4. Находит «потерянные» inode (никто не ссылается → файл без имени → перекладывает в `lost+found`)
5. Находит double-allocated блоки, некорректные права и т.д.

Весь этот алгоритм **предполагает, что граф является деревом** — без циклов, каждый inode достижим ровно по одному пути.

---

### Что происходит при цикле

Создаём hardlink на директорию: `ln /home/user /home/user/loop`. Граф перестаёт быть деревом:

```
ЦИКЛ в графе inode:

           /  (inode #2)
           |
         home  (inode #5)
           |
         user  (inode #12)  ◀─────────────┐
         /  \                              │
       docs  loop ──────────────────────── ┘
     (#31)  (#12)  ← loop указывает на тот же inode #12!
                     (это и есть hardlink на директорию)
```

Теперь `fsck` запускает обход:

```
Обход fsck:
inode #12 (user/)  → дочерние: docs, loop
inode #12 (user/)  → дочерние: docs, loop   ← уже был здесь!
inode #12 (user/)  → дочерние: docs, loop   ← бесконечно...
```

`fsck` не может завершиться — она никогда не обойдёт «все» узлы, потому что узлов в цикле бесконечно много с её точки зрения. Алгоритм подсчёта `link count` даёт неверный результат — он считает один и тот же inode многократно. Алгоритм поиска «потерянных» файлов тоже ломается.

Именно поэтому ядро запрещает `link()` для директорий **на уровне системного вызова** — не как рекомендация, а как жёсткий запрет.

> **Исключение:** `.` и `..` — это hardlink'и на директории, которые ядро создаёт само при создании каждой директории. Это контролируемые, заранее известные ссылки, о которых `fsck` и все утилиты знают. Именно поэтому `link count` пустой директории равен 2.

## Почему symlink на директорию — можно

Symlink — принципиально другой механизм, и ядро про него *знает*.

**1. Symlink — отдельный файл, не второе имя inode**

Hardlink встраивается в структуру inode: файловая система видит два равноправных имени и не может отличить "оригинал" от "копии". Граф inode становится цикличным незаметно.

Symlink — отдельный файл со своим inode, внутри которого лежит просто строка-путь. Файловая система видит: "вот файл типа symlink, в нём написано `/home/user`". Никакой связи на уровне inode — просто текст.

**2. Ядро считает глубину разыменований**

**Разыменование** (dereference) — это момент, когда ядро встречает symlink при обходе пути и «заменяет» его на путь, который внутри хранится. Каждая такая замена — одно разыменование.

Пример: ты набираешь `cat /a/b/file.txt`. Ядро идёт по пути слева направо и при каждом компоненте проверяет — не symlink ли это?

```
Без symlink — просто обход дерева (0 разыменований):

cat /a/b/file.txt
     │ │ └── обычный файл
     │ └──── обычная директория
     └────── обычная директория
```

```
С одним symlink — 1 разыменование:

cat /a/b/file.txt
         │
         └── symlink! внутри написано "/home/user/data.txt"
             ядро подставляет: /a/b/file.txt → /home/user/data.txt
             и продолжает обход уже по новому пути
```

Всё это выглядит незаметно для пользователя. Но что если symlink указывает на symlink, который указывает на symlink...?

```
Цепочка symlink'ов:

/a  →  /b
/b  →  /c
/c  →  /d
...
```

При этом возможен и **цикл из symlink'ов**:

```
Цикл symlink'ов — классический способ получить ELOOP:

$ ln -s /tmp/link_b /tmp/link_a
$ ln -s /tmp/link_a /tmp/link_b    # link_b → link_a → link_b → ...

Попытка обратиться:
cat /tmp/link_a/file
    │
    └── symlink → /tmp/link_b       (разыменование 1)
                       └── symlink → /tmp/link_a   (разыменование 2)
                                          └── symlink → /tmp/link_b  (3)
                                                             └── ...  (4, 5, 6...)
```

Чтобы не зависнуть навсегда, ядро ведёт **счётчик разыменований** при каждом системном вызове, работающем с путём (`open`, `stat`, `execve` и т.д.). Как только счётчик достигает `MAXSYMLINKS = 40` — ядро немедленно возвращает ошибку `ELOOP`:

```bash
$ ls слишком/глубокий/симлинк
ls: cannot access '...': Too many levels of symbolic links
```

Схема работы счётчика:

```
Системный вызов open("/path/to/file")
        │
        ▼
   счётчик = 0
        │
        ▼
   Обход пути покомпонентно:
        │
        ├── компонент — обычная директория → просто идём дальше
        │
        └── компонент — symlink!
               │
               ├── счётчик += 1
               │
               ├── счётчик < 40? → подставляем путь из symlink, продолжаем
               │
               └── счётчик == 40? → возвращаем ELOOP, стоп!
```

**Почему 40, а не бесконечность?** Потому что 40 — это практический компромисс: достаточно для любой легитимной цепочки symlink'ов в реальных системах, и достаточно мало, чтобы быстро поймать цикл. Ни одна нормальная программа не строит цепочки из 40+ symlink'ов.

С hardlink-циклом ядро **не может сделать то же самое** — оно не знает, что идёт по циклу, потому что с точки зрения inode это просто нормальный обход дерева. Нет никакого «я сейчас разыменовываю» — есть просто переход из директории в директорию, и ядро не ведёт счётчик таких переходов.

**3. Утилиты по умолчанию не следуют за symlink'ами на директории**

`find`, `du`, `rsync` без явных флагов видят symlink как файл типа symlink и останавливаются — никакого бесконечного обхода:

```bash
find . -follow    # явно разрешить следовать за симлинками
du -L /path       # то же
rsync -L          # то же
```

**Итог:** hardlink встраивается в inode и ядро не видит цикл. Symlink — текстовый файл с путём, ядро видит его как отдельную сущность, умеет считать глубину и останавливаться.

## Жизненный цикл файла и link count

Файл реально удаляется с диска только когда **одновременно** выполнены два условия:

1. `link count == 0` — нет ни одного имени в файловой системе
2. Нет открытых файловых дескрипторов

Практическое следствие: можно удалить файл командой `rm` во время того, как процесс держит его открытым — данные сохранятся до закрытия fd.

```bash
# Прочитать "удалённый" файл через /proc
ls -la /proc/<pid>/fd/
cat /proc/<pid>/fd/<номер>
```

## Полезные команды — шпаргалка

```bash
# Посмотреть inode номер файла
ls -i file.txt
stat file.txt          # все метаданные + inode

# Найти файл по inode (полезно если имя содержит непечатные символы)
find / -inum 42

# Сколько inode использовано и свободно
df -i
df -ih                 # human-readable

# Создать hardlink
ln original.txt hardlink.txt

# Создать symlink
ln -s /path/to/original symlink.txt

# Проверить тип ссылки
file symlink.txt       # "symbolic link to ..."
readlink symlink.txt   # покажет путь цели

# Найти все hardlink'и одного файла (по inode)
find . -inum $(stat -c '%i' notes.txt)

# Расширенные атрибуты (append-only, immutable и др.)
lsattr file.txt
chattr +i file.txt     # immutable — даже root не удалит без снятия
```

## Типичные собесные вопросы

### `df` говорит диск полный, а `df -i` — нет?

Закончились **inodes**. Каждый файл/директория/симлинк потребляет один inode. Типичная причина — миллионы мелких временных файлов (кэш пакетного менеджера, спам-логи).

**Лечение:** удалить лишние файлы или переформатировать раздел с бо́льшим числом inodes (`mkfs.ext4 -N <количество>`).

---

### Почему нельзя создать hardlink на директорию?

Создание hardlink на директорию порождает **цикл** в графе файловой системы — `find`, `du`, `fsck` уходят в бесконечный обход. Ядро запрещает это на уровне системного вызова `link()`.

---

### Почему symlink на директорию можно, а hardlink — нет?

Symlink — отдельный файл с путём внутри. Ядро знает про него, считает глубину разыменований (`MAXSYMLINKS = 40`) и возвращает `ELOOP` при превышении. Hardlink встраивается в inode — ядро не видит цикл и не может остановиться.

---

### Чем `ctime` отличается от `mtime`?

- `mtime` — изменение **содержимого** файла
- `ctime` — изменение **inode**: переименование, смена прав, смена владельца, создание/удаление hardlink

`ctime` нельзя установить вручную через `touch`, в отличие от `mtime` и `atime`.

---

### Что происходит при `rename()`?

`rename()` — **атомарная** операция: запись в директории-источнике удаляется, в директории-цели создаётся — в рамках одного системного вызова. Inode и данные не трогаются.

Поэтому **атомарный deploy через `rename`** — стандартная практика: пишешь новый файл, затем атомарно переименовываешь его поверх старого.

---

### Как symlink отличается от bind mount?

- **Symlink** — файловый объект, разрешается ядром при каждом обращении по пути
- **Bind mount** — механизм VFS, монтирует одно дерево поверх другого, прозрачен для приложений, работает без обхода по пути
