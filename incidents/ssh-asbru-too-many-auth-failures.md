# Too many authentication failures в Asbru / FileZilla — разбор причины и решение

## Симптом

При подключении к клиентским серверам через Asbru Connection Manager (цепочка Jump Host → сервер) соединение обрывалось с ошибкой:

```
Received disconnect from 192.169.19.102 port 2202:2: Too many authentication failures
Disconnected from 192.169.19.102 port 2202
kex_exchange_identification: Connection closed by remote host
```

Позже та же ошибка вылезла в FileZilla при подключении через локальный проброс порта (SFTP-туннель, поднятый Asbru):

```
FATAL ERROR: Remote side sent disconnect message
type 2 (protocol error): "Too many authentication failures"
```

## В чём была причина

В системе работал **GNOME Keyring**, компонент которого (`gnome-keyring-ssh`) при каждом входе в систему автоматически сканировал `~/.ssh` и подгружал в SSH-агент **все найденные приватные ключи** разом — в данном случае шесть штук (кассы, серверы, gitlab и т.д.).

Джамп-хосты клиентов настроены на вход **по паролю**, ключи там не зарегистрированы. Но SSH при подключении сначала предлагает серверу все ключи из агента по очереди, и только когда ни один не подошёл — переходит к запросу пароля. На серверах стоял лимит `MaxAuthTries 6` (значение по умолчанию) — ровно столько у пользователя было ключей в агенте. Шесть неудачных попыток аутентификации по ключу съедали весь лимит, сервер обрывал соединение — и до пароля дело просто не доходило.

Проблема проявлялась одинаково в любом клиенте (Asbru, FileZilla, обычный терминал), потому что SSH-агент один на всю систему и все программы берут ключи из него.

## Почему первые попытки починить не сработали

| Что пробовали | Почему не помогло |
|---|---|
| Правка `~/.ssh/config`, добавление `IdentitiesOnly yes` | Asbru использует собственный временный конфиг (`ssh -F /tmp/asbru-cm-.../....conf`) и полностью игнорирует пользовательский `~/.ssh/config` |
| Опции `-o PubkeyAuthentication=no` / `-o PreferredAuthentications=password` в свойствах соединения Asbru | Джамп-хост поднимается отдельным дочерним SSH-процессом через `-J jumpserver`. Опции командной строки применяются только к внешнему соединению (`server`), а не к дочернему (`jumpserver`) |
| `ssh-add -D` (удалить все ключи из агента) | Ключи хранились не в обычном `ssh-agent`, а подгружались GNOME Keyring — он тут же восстанавливал их обратно |

## Диагностика — как убедились, что дело именно в этом

1. Проверка вручную с отключённым агентом на одну команду:
   ```bash
   SSH_AUTH_SOCK= ssh -v -p 2202 jump@192.169.19.102
   ```
   Пароль запросился сразу, без перебора — подтвердило, что проблема в агенте, а не в сети/VPN/сервере.

2. Определили, что за агент отвечает за автоподгрузку:
   ```bash
   echo $SSH_AUTH_SOCK
   # /run/user/1000/keyring/ssh   — это GNOME Keyring, не обычный ssh-agent

   ps -ef | grep -E "keyring|ssh-agent|gcr"
   ```

## Решение

Отключили автозапуск SSH-компонента GNOME Keyring для текущего пользователя (без затрагивания системных файлов):

```bash
mkdir -p ~/.config/autostart
cp /etc/xdg/autostart/gnome-keyring-ssh.desktop ~/.config/autostart/
echo "Hidden=true" >> ~/.config/autostart/gnome-keyring-ssh.desktop
```

После **полного перелогина** система поднимает обычный пустой `ssh-agent` вместо keyring-агента с ключами:

```bash
echo $SSH_AUTH_SOCK
# /tmp/ssh-XXXXXXXXXX/agent.NNNN   — обычный ssh-agent, не keyring

ssh-add -l
# The agent has no identities.
```

Перебирать стало нечего — SSH сразу переходит к запросу пароля на джамп-хосте, лимит `MaxAuthTries` не расходуется.

## Что не пострадало

Ключи никуда не делись — файлы как лежали в `~/.ssh/`, так и лежат. Подключения к кассам, внутренним серверам и GitLab по ключу продолжают работать, потому что в `~/.ssh/config` для каждого хоста явно прописан `IdentityFile`:

```sshconfig
Host rmk_161
    HostName 192.169.19.161
    User root
    Port 22
    IdentityFile /home/fa1ry/.ssh/id_rmk_161
```

SSH берёт ключ напрямую с диска по этому пути — пустой агент этому не мешает.

## Дополнительные рекомендации на будущее

- **Ключи оказались без passphrase** — при копировании файла (бэкап, кража ноутбука) им можно воспользоваться немедленно. Стоит зашифровать:
  ```bash
  ssh-keygen -p -f ~/.ssh/id_rmk_161
  ```
  повторить для каждого приватного ключа.

- Если понадобится временно держать конкретный ключ в агенте (например, для `ForwardAgent` в цепочке прыжков), поднимать сессионный агент вручную:
  ```bash
  eval $(ssh-agent)
  ssh-add ~/.ssh/id_нужный
  ```
  он исчезнет вместе с закрытием терминала.

- Если есть административный доступ к серверам клиентов, альтернативное (но не обязательное теперь) решение — увеличить `MaxAuthTries` в `/etc/ssh/sshd_config`, чтобы лимит попыток не исчерпывался перебором ключей.

- Ярлык запуска Asbru, который был временно правлен на `env -u SSH_AUTH_SOCK asbru-cm` как обходной путь, можно оставить как есть (безвреден) или откатить к исходному — агент теперь и так пуст.
