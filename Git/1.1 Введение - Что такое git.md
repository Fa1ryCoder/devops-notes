## 1. Что такое Git и зачем он нужен

**Git** — это распределённая система контроля версий (Distributed Version Control System, DVCS), которая представляет собой хранилище (базу данных) истории разработки проекта. Она сохраняет все версии файлов — как текущие, так и старые, что позволяет в любой момент просмотреть историю изменений или восстановить предыдущие версии.

---

### Основные преимущества Git

Git стал стандартом индустрии не случайно. Вот 6 ключевых преимуществ которые выделяют его среди других систем контроля версий:

**Распределённость**
У каждого участника на компьютере хранится полная копия всей истории проекта — не только текущие файлы, но и все коммиты, ветки, теги. Это принципиально отличает Git от старых систем вроде SVN и CVS, где история хранилась **только на сервере**.

```
Централизованная VCS (SVN, CVS) — устаревший подход:
  Разработчик A ──┐
  Разработчик B ──┼──► Центральный сервер (ВСЯ история только здесь)
  Разработчик C ──┘

Распределённая VCS (Git) — современный подход:
  Разработчик A (полная история) ──┐
  Разработчик B (полная история) ──┼──► GitHub / GitLab (облако для синхронизации)
  Разработчик C (полная история) ──┘
```

Проблемы централизованного подхода которые Git решает:
- Нет доступа к серверу (упал, нет интернета) → в SVN вся команда стоит, в Git всем пофиг — у каждого полная копия локально
- Сервер сломался без бэкапа → в SVN история потеряна навсегда, в Git у каждого есть полная копия
- Блокировка файлов → в старых системах разработчик "захватывал" файл для редактирования, остальные ждали пока он не закончит. В Git каждый работает в своей ветке независимо — никаких блокировок

> **Ключевая разница одной фразой:** SVN — история живёт только на сервере. Git — история живёт у тебя на компьютере, а GitHub просто синхронизирует её между участниками.

**Командная разработка**
Несколько разработчиков могут работать над одним проектом одновременно, не перезаписывая работу друг друга. Это обеспечивается через ветки и слияние:

- Каждый разработчик работает в своей ветке — изолированно от остальных
- При слиянии Git сравнивает изменения и объединяет их автоматически
- Если два человека изменили **разные строки** одного файла — Git объединит автоматически (Git работает на уровне строк: A изменил строку 2, B изменил строку 5 — зоны не пересекаются, всё ок)
- Если два человека изменили **одну и ту же строку** — Git сообщит о конфликте и попросит разрешить его вручную, так как не знает какую версию оставить

**Ветвление**
Создать ветку в Git — это буквально создать один текстовый файл с хешем внутри. Например, команда `git branch feature` создаёт файл `.git/refs/heads/feature` с одной строкой внутри — это тот же SHA-1 хеш коммита (про который написано в разделе "Надёжность"), на который указывает ветка. Никаких копий файлов проекта, никакого дублирования. Поэтому создание ветки занимает миллисекунды и несколько байт на диске.

В SVN создать ветку = скопировать всю папку проекта на сервере. Проект весит 2GB — копируется 2GB, и это могло занимать минуты.

Поскольку ветки в Git дешёвые, в командной разработке принято создавать ветку под каждую задачу:

```
main          ← стабильный код, всегда рабочий
feature/auth  ← Иван делает авторизацию
feature/logs  ← Пётр делает логирование
fix/login-bug ← Маша чинит баг в логине
```

Каждый работает изолированно. Готово — делаешь Pull Request, коллеги смотрят код, потом сливаешь в `main`. Никакой незаконченный код не попадает в основную ветку. И никто не думает "стоит ли заводить ветку под эту мелкую задачу" — просто всегда заводишь, это ничего не стоит.

**Надёжность и контрольные суммы**
Git вычисляет **SHA-1 хеш** для каждого объекта — файла, директории, коммита. Хеш — это цифровой отпечаток содержимого: если хоть один байт изменится, хеш станет другим. Это даёт две гарантии:
- **Целостность** — любое случайное повреждение файла будет обнаружено автоматически
- **Неизменяемость истории** — незаметно подменить коммит в истории невозможно, хеш выдаст подмену

Плюс сама распределённость работает как глобальный бэкап — полная копия истории есть у каждого участника команды. Даже если GitHub сгорит вместе с серверами, достаточно одной локальной копии чтобы восстановить всё.

**Скорость**
Почти все операции выполняются локально без обращения к сети — `git log`, `git diff`, `git branch`, `git checkout`. Поэтому они работают мгновенно даже на огромных репозиториях. К сети обращаются только `git push`, `git pull`, `git fetch`.

**Open Source и экосистема**
Git создан Линусом Торвальдсом в 2005 году для разработки ядра Linux. Бесплатен, открытый исходный код. Вокруг него выстроена огромная экосистема: GitHub, GitLab, Bitbucket, Gitea — платформы для хранения и совместной работы. Все современные CI/CD системы (Jenkins, GitHub Actions, GitLab CI) работают с Git из коробки.

## 2. Три состояния файла

Каждый файл в Git может находиться в одном из четырёх состояний:

```
Working Directory  ──git add──►  Staging Area  ──git commit──►  Repository (.git/)
  (изменяем файлы)               (что войдёт                     (история коммитов)
                                   в коммит)
        ◄──────────────────── git restore ────────────────────
```

| Состояние   | Где находится     | Описание                                  | Как попасть       |
|-------------|-------------------|-------------------------------------------|-------------------|
| `untracked` | Working Directory | Новый файл, Git не знает о нём            | `touch file.txt`  |
| `modified`  | Working Directory | Файл изменён, но не добавлен в индекс     | `vim file.txt`    |
| `staged`    | Staging Area      | Файл добавлен в индекс, готов к коммиту   | `git add file.txt`|
| `committed` | Repository        | Файл сохранён в базе данных Git           | `git commit`      |

**Важный нюанс:** `modified` появляется только если файл **уже отслеживается Git** — то есть был добавлен через `git add` хотя бы раз. Если файл новый и ты ни разу не делал `git add` — он всегда `untracked`, даже если ты его уже 10 раз отредактировал. Git просто не следит за ним пока не получит `git add`.
