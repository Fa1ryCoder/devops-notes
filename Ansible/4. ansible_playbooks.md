# Тема 4: Ansible Playbooks — Введение


## 4.1 Зачем нужны плейбуки?

Ad-hoc команды отлично подходят для разовых операций: проверить доступность, скопировать файл, перезапустить сервис. Но в реальной жизни задачи связаны между собой:

```
установить пакет → скопировать конфиг → перезапустить сервис → проверить статус
```

Всё это нужно выполнять последовательно, повторяемо и без необходимости каждый раз вспоминать порядок.

**Плейбук** — это YAML-файл, в котором описывается **желаемое состояние** системы, а не последовательность команд. Это ключевое отличие: ты говоришь «nginx должен быть установлен и запущен», а не «выполни apt install, потом systemctl start».

| | Ad-hoc | Playbook |
|---|---|---|
| Количество задач | одна | неограниченно |
| Повторяемость | ручной запуск | запускается как скрипт |
| Хранение | нигде | файл в git |
| Читаемость через месяц | низкая | высокая |

## 4.2 Идемпотентность — главная концепция

Запусти плейбук 10 раз — результат одинаковый.

- Если nginx уже установлен — Ansible не будет устанавливать его снова.
- Если файл уже в нужном состоянии — он не будет перезаписан.
- Если сервис уже запущен — он не будет перезапущен.

Это называется **идемпотентность** — повторный запуск операции не меняет состояние системы: всё, что уже приведено к нужному состоянию, повторно не выполняется. В ad-hoc режиме ты сам должен был думать «а вдруг уже установлено?». В плейбуке модули делают это за тебя и сообщают статус: `ok` (уже было так) или `changed` (изменили).

## 4.3 YAML — язык плейбуков

Плейбуки пишутся на YAML — формате для описания структурированных данных. Учить его целиком не нужно: весь YAML в Ansible состоит из двух сущностей — **списков** и **словарей**.

```yaml
# Словарь — уникальные пары «ключ: значение»
name: nginx
port: 80

# Список — перечисление однотипных элементов, каждый с тире
- web1
- web2
- web3
```

Пять правил ниже покрывают всё, что нужно для написания плейбуков. Начнём с технического правила про отступы, без которого не заработает ничего.

### Правило 1 — Только пробелы, никаких табов

YAML определяет вложенность исключительно пробелами. Один случайный таб сломает плейбук — парсер выдаст ошибку. Используй ровно 2 пробела для каждого нового уровня вложенности. Настрой редактор (VS Code / Vim) так, чтобы клавиша Tab автоматически вставляла пробелы.

```yaml
# ✗ ОШИБКА — табуляция перед дефисом
tasks:
	- name: "Сломается"

# ✓ ВЕРНО — ровно два пробела
tasks:
  - name: "Работает"
```

### Правило 2 — Словарь: ключ и значение

**Словарь** — это пара «ключ: значение», где каждый ключ уникален: двух одинаковых ключей в одном месте быть не может, а порядок ключей не важен. Именно так задаются все настройки Ansible. После двоеточия всегда обязателен пробел. Тире здесь **не нужно**.

```yaml
# ✗ ОШИБКА — нет пробела после двоеточия
hosts:all
port:8080

# ✓ ВЕРНО — настройки (словарь, без тире)
hosts: all
vars:
  http_port: 80
  app_user: www-data
```

### Правило 3 — Список: элементы с дефисом

**Список** — это перечисление однотипных элементов, где порядок имеет значение. Так в Ansible задаются последовательности: задачи, хосты, роли. Каждый элемент начинается с `- ` (дефис + пробел) и все элементы должны находиться на одном вертикальном уровне. Тире ставится один раз в начале каждого нового элемента.

```yaml
# ✓ ВЕРНО — перечисление хостов (список)
hosts:
  - web_server_1
  - web_server_2
  - web_server_3
```

### Правило 4 — tasks: список, где каждый элемент — словарь

В плейбуке есть секция `tasks` — в ней перечисляются задачи, которые Ansible выполнит на серверах по порядку (подробно разберём в разделе 4.4). Здесь правила 2 и 3 работают вместе. `tasks` — это список, поэтому каждая задача начинается с тире. При этом одна задача — это словарь: у неё есть имя (`name`) и модуль (`ansible.builtin.apt`), внутри которого лежат его параметры. Отсюда картина: тире стоит перед первым ключом задачи, а все остальные ключи пишутся под ним с тем же отступом и без тире. Следующее тире появится только там, где начнётся следующая задача.

```yaml
tasks:                              # список задач
  - name: "Установка nginx"         # элемент списка: первая задача (задача = словарь)
    ansible.builtin.apt:            # второй ключ задачи — модуль (без тире)
      name: nginx                   # параметры модуля — вложенный словарь (без тире)
      state: present

  - name: "Запуск сервиса"          # элемент списка: вторая задача
    ansible.builtin.service:        # ключ задачи — модуль (без тире)
      name: nginx
      state: started
```

> 💡 **Как проверить себя:** таких элементов может быть несколько? Значит это список — ставь тире. Это уникальная настройка с именем? Значит словарь — тире не нужно.

### Правило 5 — Ловушка с кавычками и спецсимволами

В YAML можно писать строки без кавычек. Но если в названии задачи или в параметрах встречаются спецсимволы — `:` (двоеточие), `{{ }}` (фигурные скобки переменных), `[ ]`, `*` — парсер решит, что это элементы кода, и плейбук упадёт.

```yaml
# ✗ ОШИБКА — двоеточие внутри строки ломает парсер
- name: Check status: Production

# ✓ ВЕРНО — строка с двоеточием в кавычках
- name: "Check status: Production"

# ✗ ОШИБКА — переменная в начале значения должна быть в кавычках
- name: "Copy template"
  ansible.builtin.template:
    src: {{ source_file }}

# ✓ ВЕРНО — переменная в кавычках
- name: "Copy template"
  ansible.builtin.template:
    src: "{{ source_file }}"
```

## 4.4 Структура плейбука

**Play** — это набор задач, адресованный конкретной группе серверов. Например: «установить nginx, скопировать конфиг и запустить сервис на всех веб-серверах» или «создать пользователей и настроить PostgreSQL на всех БД-серверах» — каждый такой набор и есть один play.

**Плейбук** — это файл, содержащий список таких plays. Один play — минимум, но их может быть сколько угодно: сначала настроить веб-серверы, затем в том же файле — серверы баз данных.

Внутри каждого play обязательно должен быть параметр `hosts`. Также внутри должна быть описана какая-то полезная нагрузка — чаще всего это список задач (`tasks`) или список ролей (`roles`).

```yaml
---
# Плейбук — список plays (тире перед каждым play)
- name: "Настройка веб-серверов"         # первый play — элемент списка
  hosts: webservers                       # параметр play (без тире)
  become: true                            # параметр play (без тире)

  vars:                                   # переменные (без тире)
    http_port: 80
    app_user: www-data

  tasks:                                  # список задач (тире внутри)
    - name: "Установить nginx"
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: "Скопировать конфиг"
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: "Перезапустить nginx"       # вызвать handler если changed

    - name: "Убедиться что nginx запущен"
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:                               # реагируют на notify
    - name: "Перезапустить nginx"
      ansible.builtin.service:
        name: nginx
        state: restarted
```

> **Примечание:** три дефиса `---` в первой строке примера — это официальный маркер начала YAML-документа. В Ansible он необязателен, но в продакшн-среде считается хорошим тоном.

### Описание ключевых блоков

Всё, что пишется на уровне play (`name`, `hosts`, `become`, `vars`, `tasks`, `handlers` и другие) — это параметры самого play, а не модуля.

**`name`** — у play и у каждой task. Технически необязателен, но без него вывод нечитаемый. Пиши всегда.

**`hosts`** — кому адресован play. Варианты:

```yaml
hosts: webservers            # группа из инвентаря
hosts: webservers:dbservers  # несколько групп
hosts: 192.168.1.10          # конкретный хост
hosts: all                   # все хосты из инвентаря
```

**`become: true`** — параметр play (или отдельной task), означает «выполнять задачи от root через sudo». Можно ставить на весь play или на отдельную task:

```yaml
- name: "Только эта задача под sudo"
  ansible.builtin.apt:
    name: nginx
    state: present
  become: true
```

**`vars`** — переменные для этого play. Используются через синтаксис `"{{ имя_переменной }}"` — в кавычках, как учит правило 5.

**`tasks`** — список задач. Каждая задача = `name` + имя модуля + аргументы модуля. Это то, чем ты занимался в ad-hoc, только теперь записано в файл.

В ad-hoc мы писали просто `ping` или `apt`. В плейбуках принято писать полное имя: `ansible.builtin.apt`. `ansible.builtin` — это имя коллекции, в которой живёт модуль. Короткое имя тоже работает — Ansible знает где искать стандартные модули по умолчанию, и `apt` и `ansible.builtin.apt` идентичны. Полное имя пишут в продакшен-плейбуках, чтобы было явно видно откуда модуль и не было конфликтов если установлены сторонние коллекции с похожими именами.

Частая точка путаницы — почему одни параметры пишутся на уровне task, а другие внутри модуля. Правило простое: если параметр управляет поведением самой task (сохранить результат, поставить условие, игнорировать ошибку) — он на уровне task. Если говорит модулю что делать — идёт внутрь модуля.

```yaml
- name: "Проверить пакет"          # параметр task
  ansible.builtin.command:          # модуль
    cmd: dpkg -l nginx              # параметр модуля — внутри
  register: dpkg_result             # параметр task, не модуля — на одном уровне с модулем
  when: some_condition              # параметр task, не модуля — на одном уровне с модулем

- name: "Показать результат"        # параметр task
  ansible.builtin.debug:            # модуль
    var: dpkg_result                # параметр модуля debug — внутри
```

Параметры task, которые всегда пишутся на одном уровне с модулем: `register`, `when`, `ignore_errors`, `loop`, `notify`, `become`, `tags`. Всё остальное — скорее всего параметр модуля и идёт внутрь.

**`handlers`** — особые задачи, которые:
- запускаются **в конце play**, а не сразу
- запускаются **только если** task вызвала `notify` и имела статус `changed`
- запускаются **один раз**, даже если несколько tasks вызвали один и тот же notify

Типичный пример — перезапуск сервиса только при реальном изменении конфига.

## 4.5 Как запустить плейбук

```bash
# Проверка синтаксиса — убедиться что YAML валидный до запуска
ansible-playbook playbook.yml --syntax-check

# Проверка инвентаря
ansible-inventory -i inventory.yml --list

# Базовый запуск
ansible-playbook playbook.yml

# Указать инвентарь явно
ansible-playbook -i inventory/hosts.ini playbook.yml

# Проверка без выполнения (dry run)
ansible-playbook playbook.yml --check

# Проверка + показать diff изменяемых файлов
ansible-playbook playbook.yml --check --diff

# Только определённые хосты
ansible-playbook playbook.yml --limit web1

# Указать пользователя и SSH-ключ
ansible-playbook playbook.yml -u deploy --private-key ~/.ssh/id_rsa

# Запросить sudo-пароль интерактивно
ansible-playbook playbook.yml --ask-become-pass
```

## 4.6 Статусы выполнения задач

При выполнении плейбука каждая задача получает один из статусов:

| Статус | Цвет в терминале | Что означает |
|---|---|---|
| `ok` | зелёный | задача выполнена, изменений нет |
| `changed` | жёлтый | задача выполнена и что-то изменила |
| `skipped` | голубой | задача пропущена (условие `when` не выполнено) |
| `failed` | красный | задача упала, play на этом хосте остановлен |
| `unreachable` | красный | хост недоступен |

В конце Ansible всегда выводит `PLAY RECAP` — итоговую сводку по каждому хосту:

```
PLAY RECAP *****************************************************
web1 : ok=3  changed=1  unreachable=0  failed=0  skipped=0
web2 : ok=3  changed=0  unreachable=0  failed=0  skipped=0
```

Если `failed=0` и `unreachable=0` — всё выполнено успешно.

## 4.7 Первый рабочий плейбук

Минимальный плейбук — аналог `ansible all -m ping` из ad-hoc:

```yaml
---
- name: "Проверка подключения ко всем хостам"
  hosts: all
  gather_facts: false    # не собирать информацию о хостах (быстрее)

  tasks:
    - name: "Ping"
      ansible.builtin.ping:
```

Сохрани как `test.yml` и запусти:

```bash
ansible-playbook -i inventory/hosts.ini test.yml
```
