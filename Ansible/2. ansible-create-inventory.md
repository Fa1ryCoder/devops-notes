# 2. Подключение Ansible к кассам: создание inventory (инвентаря)

Документ 1 описывал установку Ansible на кассовый сервер. Сейчас Ansible установлен, но ему ещё не сказано, **с какими нодами работать и как к ним подключаться**.

За это отвечает файл **inventory** (инвентарь) — это список всех управляемых нод (касс), с которыми может работать Ansible. Без inventory у Ansible физически нет ни одного адреса, на который можно подключиться: команды вида `ansible all -m ping` или запуск playbook просто не будут знать, к кому стучаться.

В inventory прописывается:
- **Какие хосты существуют** (IP-адреса, имена касс или целые диапазоны хостов вида `cash-[001:050]`);
- **Как их группировать** (например, в группу `cashregisters`, по городам, магазинам или ролям);
- **Иерархия групп** (группы могут входить в другие группы, позволяя управлять всей сетью или отдельным регионом одной командой);
- **Параметры подключения и авторизации** — пользователи (`ansible_user`), нестандартные порты SSH (`ansible_port`), пароли или пути к SSH-ключам;
- **Маршрутизация и проксирование** — если кассы скрыты за сервером переходов (jump-server), параметры прокси-потока также можно закрепить за хостами;
- **Переменные окружения** — пути к интерпретатору Python на целевой системе, флаги и любые специфические настройки, отличающиеся от машины к машине.

Это центральная точка правды о вашей инфраструктуре для Ansible: один файл, который описывает, на что распространяется автоматизация.

---

## Шаг 1. Настройка окружения через ansible.cfg

### Что такое ansible.cfg?

Это главный конфигурационный файл Ansible для всего проекта. Без него Ansible использует встроенные значения по умолчанию — они рабочие, но не оптимальные для продакшена. `ansible.cfg` позволяет один раз прописать настройки для всей сети касс и больше не таскать их флагами в каждой консольной команде.

### Почему с ним лучше

Без `ansible.cfg`:
```bash
# Каждый раз нужно указывать -i, иначе Ansible не знает, где инвентарь
ansible cashregisters -m ping -i inventory/hosts.yml

# Каждый раз нужно указывать -b для sudo и пользователя
ansible cashregisters -m apt -a "name=curl state=present" -b -i inventory/hosts.yml
```

С `ansible.cfg`:
```bash
# Ansible сам знает, где инвентарь, под кем идти и что нужен sudo
ansible cashregisters -m ping
ansible cashregisters -m apt -a "name=curl state=present"
```

### Основные параметры конфигурации

| Параметр | Секция | Что делает | Дефолт |
|---|---|---|---|
| `inventory` | `[defaults]` | Путь к файлу хостов по умолчанию. Избавляет от флага `-i`. | нет |
| `remote_user` | `[defaults]` | Под каким пользователем SSH подключаться к кассам. | текущий юзер |
| `host_key_checking` | `[defaults]` | Проверять SSH host key при первом подключении. Выключаем (`False`), чтобы автоматизация не спотыкалась на новых хостах. | `True` |
| `forks` | `[defaults]` | Сколько хостов обрабатывать параллельно. Для большой сети касс стоит выставлять 20 и более. | `5` |
| `retry_files_enabled` | `[defaults]` | Создавать ли `.retry` файлы в корне проекта, если плейбук на кассе упал. Выключаем (`False`), чтобы не плодить мусор. | `True` |
| `stdout_callback` | `[defaults]` | Формат вывода логов в консоль. Значение `yaml` превращает нечитаемую JSON-кашу в аккуратное дерево. | `default` |
| `become` | `[privilege_escalation]` | Автоматически повышать права до root (аналог флага `-b`). | `False` |
| `become_method` | `[privilege_escalation]` | Каким способом повышать права на целевой системе. | `sudo` |
| `pipelining` | `[ssh_connection]` | Ускорение SSH. Гонит несколько тасок через один коннект, минимизируя сетевые задержки. | `False` |

### Готовый шаблон для копирования в проект

Создайте файл `ansible.cfg` в корневой директории проекта (`~/ansible-cashregisters/`) и вставьте в него следующие настройки:

```ini
[defaults]
inventory = ./inventory/hosts.yml
host_key_checking = False
forks = 20
# Наведение порядка в логах и корне проекта
retry_files_enabled = False
stdout_callback = yaml
bin_ansible_callbacks = True

[privilege_escalation]
become = True
become_method = sudo
become_user = root

[ssh_connection]
pipelining = True
```

⚠️ **Важно для Linux:** если директория вашего проекта доступна на запись другим пользователям (например, имеет права `777` или лежит в `/tmp`), Ansible из соображений безопасности проигнорирует локальный `ansible.cfg`. Держите проект в домашней директории с корректными правами.

## Шаг 2. Структура проекта

```bash
mkdir -p ~/ansible-cashregisters/{inventory,group_vars,host_vars}
cd ~/ansible-cashregisters
```

**Имена `inventory`, `group_vars`, `host_vars` — это не произвольный выбор, а зарезервированные имена**, которые Ansible ищет по умолчанию, без дополнительных указаний:
- `inventory/` — список хостов (или один файл `hosts.yml`/`hosts.ini` рядом с `ansible.cfg`);
- `group_vars/<имя_группы>.yml` — переменные, которые применяются ко всем хостам этой группы;
- `host_vars/<имя_хоста>.yml` — переменные для конкретного хоста, перекрывающие групповые.

Если назвать папку иначе (например, `group-variables` вместо `group_vars`), Ansible её не найдёт и не подхватит переменные автоматически — придётся вручную объяснять путь через `ansible.cfg` или флаг `-i`. Раскладывая проект по этим трём папкам сразу с правильными именами, не приходится потом ничего переименовывать — Ansible находит всё автоматически по самой структуре каталогов.

## Шаг 3. Создание Inventory (списка касс)

Inventory — это файл, где мы перечисляем IP-адреса кассовых серверов и объединяем их в группы, чтобы управлять всей сетью одной командой.

Создайте файл `inventory/hosts.yml` и вставьте туда структуру ниже.

```yaml
# inventory/hosts.yml
all:
  children:
    cashregisters:        # Имя группы (кассы)
      hosts:
        cash-001:         # Удобное имя (алиас) кассы
          ansible_host: 10.0.1.11  # Реальный IP-адрес кассы
        cash-002:
          ansible_host: 10.0.1.12
        cash-003:
          ansible_host: 10.0.1.13
      vars:
        ansible_user: root         # Под каким пользователем подключаться
        ansible_connection: ssh    # Протокол подключения
```

⚠️ **Важно:** Файл написан в формате YAML. Здесь критически важны отступы (пробелы). Не используйте клавишу Tab, только пробелы! Замените IP-адреса и имена на реальные данные касс клиента.

**Разбор ключевых параметров:**

- `cashregisters` — имя группы хостов. Группировка позволяет применять настройки или плейбуки сразу к десяткам касс одной командой, а не перечислять их вручную.
- `cash-001` / `cash-002` — это локальные имена-маски в Ansible. В консоли вы будете видеть именно их, а не безликие IP-адреса.
- Блок `vars` — переменные группы. Всё, что написано здесь (например, пользователь `root`), автоматически применится ко всем кассам в этой группе. Это избавляет от дублирования кода.

**Про `all` и `children`:** это не произвольные слова, а обязательный скелет YAML-инвентаря. `all` — встроенная зарезервированная группа Ansible, которая автоматически включает в себя **все** хосты из инвентаря, сколько бы их ни было. Она существует всегда, даже если не прописана явно. `children:` говорит Ansible: «внутри `all` находятся дочерние группы». Без этого ключевого слова Ansible не поймёт, что `cashregisters` — это группа, а не хост с таким именем. Эта "шапка" `all: / children:` — стандартный обязательный скелет для любого YAML-инвентаря с группами, всегда пишется именно так.

Если запустить плейбук на `all` — он обновит вообще всё разом. Но здесь есть важный профессиональный нюанс. Представь, что со временем в инвентарь добавятся хосты, которые кассами не являются — тестовые стенды, jump-серверы или сервер мониторинга. Группа `all` зацепит и их тоже. При попытке обновить «все кассы» через `all` можно случайно затронуть и сервер мониторинга.

Поэтому на практике создают явную (кастомную) родительскую группу внутри `all`:

```yaml
all:
  children:
    # Создаём свою родительскую группу для ВСЕХ касс
    all_cashregisters:
      children:
        msk_stores:
          hosts:
            msk-cash-01:
              ansible_host: 10.0.1.11
        nsk_stores:
          hosts:
            nsk-cash-01:
              ansible_host: 192.168.20.10
```

В чём магия такой структуры:

1. Только Москва: `ansible msk_stores -m ping`
2. Только Новосибирск: `ansible nsk_stores -m ping`
3. Все кассы вместе (но без лишних серверов): `ansible all_cashregisters -m ping`

**Как проверить, что файл составлен без ошибок?**

Выполните команду проверки синтаксиса:

```bash
ansible-inventory -i inventory/hosts.yml --list -y
```

Ожидаемый результат: если Ansible выведет в терминал аккуратное дерево с вашими хостами — файл составлен верно.

На этом этапе пароль root для подключения ещё нигде не указан, поэтому реальный `ping` с ответом `pong` пока не выполнить — это будет следующим шагом.

## Шаг 4. Управление паролями и проверка связи

В Ansible пароли не принято мешать со списком IP-адресов. Для этого используется механизм **Magic Folders** (специальных папок): `group_vars` (для настроек всей группы) и `host_vars` (для точечных исключений).

**3.1. Задаём общий пароль для всех касс**

В `group_vars` можно хранить любые переменные, которые нужны для группы хостов — не только пароль. Например, нестандартный SSH-порт, путь к интерпретатору Python, версия ПО, которую нужно установить, или любые кастомные параметры, которые используются в плейбуках. Всё, что прописано в этом файле, автоматически становится доступным для каждой кассы из группы.

В нашем случае пока кладём туда пароль. Создайте файл конфигурации для группы касс. `Имя файла должно строго совпадать с именем группы из инвентаря:`

```yaml
# group_vars/cashregisters.yml
ansible_password: "общий_пароль_root_от_касс"
```

**Как это работает:** Ansible автоматически заглядывает в папку `group_vars` и подтягивает этот пароль для каждого хоста, который находится внутри группы `cashregisters`.

**3.2. Если у конкретной кассы пароль отличается (исключение)**

Если на какой-то кассе админы сменили пароль, вам не нужно портить общий групповой файл. Создайте файл с именем-маской этой конкретной кассы. Точно так же, как и `group_vars`, файл `host_vars` предназначен не только для пароля — в нём можно переопределить любую переменную из группы или добавить переменные, `уникальные именно для этого хоста`:

```yaml
# host_vars/cash-002.yml
ansible_password: "другой_пароль_именно_для_этой_кассы"
```

**Приоритет в Ansible:** переменные из `host_vars` (конкретный хост) всегда приоритетнее, чем из `group_vars` (группа). Ansible возьмёт для `cash-002` уникальный пароль, а для остальных касс продолжит использовать общий.

## Шаг 5. Первая проверка связи (генеральный тест)

Теперь проверим, как Ansible видит кассы и правильно ли подхватились пароли. Выполняем команду:

```bash
ansible cashregisters -m ping -i inventory/hosts.yml
```

**Что происходит:** Ansible не просто «пингует» сеть. Он реально заходит на каждую кассу по SSH под пользователем `root`, подставляет нужный пароль, закидывает туда микро-скрипт на Python, выполняет его и возвращает отчёт.

Ожидаемый результат (успех):

```
cash-001 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}
```

Если вы увидели `"ping": "pong"` зелёным цветом — ваш управляющий сервер полностью готов к работе, связь с кассами установлена.

**Про `[WARNING]` в выводе:**

Помимо `SUCCESS` вы можете увидеть в терминале жёлтое предупреждение вида:

```
[WARNING]: Platform linux on host cash-001 is using the discovered Python interpreter at /usr/bin/python3.10, but future installation of another Python interpreter could change the meaning of that path.
```

Это **не ошибка**, можно игнорировать. Ansible сообщает, что сам автоматически нашёл интерпретатор Python на кассе (например, `/usr/bin/python3.10`), и предупреждает: если в будущем на кассе появится ещё один Python (например, после обновления системы или установки нового ПО), путь может стать неоднозначным.

Чтобы убрать это предупреждение и не зависеть от автоопределения, можно явно закрепить путь к интерпретатору в `inventory/hosts.yml`, в блоке `vars` для группы:

```yaml
vars:
  ansible_user: root
  ansible_connection: ssh
  ansible_python_interpreter: /usr/bin/python3.10
```

Делать это прямо сейчас не обязательно — Ansible продолжит нормально работать и с автоопределением. Но если warning будет мешать читать логи, достаточно один раз прописать этот путь, и он исчезнет.

**🛠️ Что делать, если что-то пошло не так? (Траблшутинг)**

Если при запуске пинга вы видите красные ошибки, найдите свою строку ниже и выполните решение:

**1. Ошибка: `Permission denied (publickey,password)`**

Симптом: автоматика падает, но если заходить на эту же кассу вручную через обычный `ssh root@IP`, то пароль подходит и пускает без проблем.

- Причина: Ansible вообще «не увидел» ваш пароль. Скорее всего, имя файла в папке `group_vars/` написано с ошибкой или опечаткой, и настройки не привязались к группе касс.
- Как исправить: проверьте имя файла буква в букву. Если в инвентаре группа называется `cashregisters`, то файл обязан называться `group_vars/cashregisters.yml`.
- Как точно проверить за секунду: выполните команду диагностики:

```bash
ansible-inventory -i inventory/hosts.yml --host cash-001
```

(вместо `cash-001` подставьте имя проблемной кассы). Если в выведенном списке нет строки `ansible_password` — значит, файл с паролем не подхватился.

**2. Ошибка: `Permission denied (password)`**

- Причина: пароль подхватился, но он физически не подходит к кассе.
- Как исправить:
  - Если упали все кассы — опечатка в общем файле `group_vars/cashregisters.yml`.
  - Если упала одна конкретная касса — проверьте её личный файл в `host_vars/`.

**3. Ошибка: `UNREACHABLE` / `No route to host` (или `Connection timed out`)**

- Причина: сетевая недоступность.
- Как исправить: проверьте, правильный ли IP-адрес указан в файле `inventory/hosts.yml`. Попробуйте «дотянуться» до кассы обычной командой `ping 10.0.1.x` прямо с сервера.

**4. Ошибка: `Host key verification failed`**

- Причина: защита безопасности SSH. Сервер видит эту кассу впервые в жизни и боится к ней подключаться без вашего личного разрешения.
- Как исправить: чтобы Ansible не спотыкался и не требовал вручную прожимать «Are you sure you want to continue connecting (yes/no)?» для каждой новой кассы, отключите эту проверку.

Создайте файл `~/ansible-cashregisters/ansible.cfg` и вставьте туда:

```ini
# ansible.cfg
[defaults]
host_key_checking = False
```

После создания этого файла Ansible начнёт игнорировать предупреждения о новых ключах и сразу перейдёт к делу.

## 🔐 Сноска «На будущее»: безопасность и шифрование (Ansible Vault)

Сейчас пароли хранятся в файлах открытым текстом. Для изолированного сервера автоматизации внутри закрытого контура компании — это допустимый компромисс ради простоты.

Однако, если этот проект в будущем поедет в Git или к нему получат доступ сторонние люди, пароли необходимо зашифровать утилитой `ansible-vault`:

**Зашифровать файл:**

```bash
ansible-vault encrypt group_vars/cashregisters.yml
```

Утилита попросит придумать секретный мастер-пароль. Файл станет нечитаемым на диске.

**Запуск команд с зашифрованными паролями:** к любой команде запуска нужно будет просто добавлять флаг расшифровки:

```bash
ansible cashregisters -m ping -i inventory/hosts.yml --ask-vault-pass
```

**Редактировать зашифрованный файл:**

```bash
ansible-vault edit group_vars/cashregisters.yml
```

**Посмотреть содержимое без редактирования:**

```bash
ansible-vault view group_vars/cashregisters.yml
```
