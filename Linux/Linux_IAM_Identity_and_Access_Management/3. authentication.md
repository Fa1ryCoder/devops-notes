## 1. Архитектура

### Что происходит когда вы логинитесь по SSH

Ключевой вопрос: кто именно проверяет ваш пароль? Не sshd, не ядро — это делает PAM. sshd только принимает соединение и делегирует проверку.

```
Пользователь вводит пароль по SSH
        │
        ▼
      sshd
        │  вызывает PAM API: pam_authenticate()
        ▼
   PAM-стек (/etc/pam.d/sshd)
        │
        ├── pam_unix.so ──→ /etc/shadow ──→ проверяет хэш пароля
        ├── pam_faillock.so ──→ /var/run/faillock/ ──→ не превышен ли лимит попыток
        ├── pam_google_authenticator.so ──→ ~/.google_authenticator ──→ TOTP
        │
        ▼
   PAM возвращает PAM_SUCCESS или PAM_AUTH_ERR
        │
        ▼
      sshd
        │  если успех — вызывает pam_open_session()
        ▼
   PAM-стек (секция session)
        │
        ├── pam_limits.so ──→ /etc/security/limits.conf ──→ устанавливает ulimits
        ├── pam_unix.so ──→ записывает в /var/log/wtmp, utmp
        │
        ▼
   Shell запускается уже с установленными ограничениями
```

Один и тот же механизм работает для всех сервисов: `login`, `su`, `sudo`, `sshd`, `gdm`, `screensaver`. Каждый вызывает PAM API — PAM сам разбирается как аутентифицировать, используя правила из `/etc/pam.d/`.

### Три задачи аутентификации

PAM разделяет три разных вопроса, которые часто смешивают:

| Вопрос | PAM тип | Пример |
|--------|---------|--------|
| **Кто ты?** — проверка личности | `auth` | пароль, ключ, токен |
| **Можешь ли ты войти?** — состояние аккаунта | `account` | не истёк ли пароль, не заблокирован ли |
| **Что ты можешь делать?** — ресурсы сессии | `session` | ulimits, монтирование home, запись в wtmp |

## 2. PAM — Pluggable Authentication Modules

> **Pluggable Authentication Modules** — дословно «подключаемые модули аутентификации». Название отражает главную идею: каждый способ проверки пользователя (пароль, TOTP (одноразовый код из приложения типа Google Authenticator), LDAP, fingerprint) — это отдельный **модуль** (`.so` файл), который можно **подключить или убрать** как плагин, не трогая само приложение.

### Зачем вообще нужен PAM и когда он включается?

Самое главное заблуждение: **PAM — это не про выполнение команд в терминале.** Когда вы вводите `ls`, `cd` или `mkdir`, PAM спит. Ему плевать.

**PAM — это вышибала на входе.** Он просыпается только тогда, когда происходит аутентификация (проверка личности) или смена контекста безопасности — попытка войти, повысить права, открыть сессию.

**Когда именно срабатывает PAM?** Вы сталкиваетесь с ним каждый раз, когда:
- Подключаетесь к серверу по SSH (`sshd` вызывает PAM)
- Хотите выполнить команду от админа через `sudo` (`sudo` вызывает PAM)
- Переключаетесь на другого пользователя через `su alice` (`su` вызывает PAM)
- Вводите пароль на экране блокировки Linux (`gdm`/`lightdm` вызывают PAM)
- Меняете свой пароль через команду `passwd` (`passwd` вызывает PAM)

> 📌 **Важно:** Вы никогда не вызываете PAM напрямую из консоли. До PAM каждая программа (`login`, `sudo`, `sshd`) сама реализовывала логику проверки пароля — хочешь добавить LDAP, патчишь все программы, хочешь 2FA, снова патчишь все. PAM решил эту проблему: теперь программы просто вызывают `pam_authenticate()`, как бы спрашивая систему: «Тут чувак ломится в SSH, я сам не умею проверять пароли, спроси у PAM — пускать его или нет?» А как именно проверять — решает конфиг, не код приложения.

**Зачем это нужно DevOps-инженеру и сисадмину?**

Вместо того чтобы ковыряться в исходном коде `sshd` или `sudo`, вы просто управляете правилами входа через текстовые конфиги в `/etc/pam.d/`. Вот реальные задачи, которые решаются за 10 секунд:

1. **Безопасность:** заблокировать учётку на 30 минут после 5 неверных паролей → `pam_faillock.so`
2. **Двухфакторка:** настроить 2FA через Google Authenticator для SSH → `pam_google_authenticator.so`
3. **Техобслуживание:** закрыть сервер и запретить вход всем кроме root → `pam_nologin.so`
4. **Ресурсы:** ограничить максимальное количество открытых файлов для пользователя → `pam_limits.so`

Всё это делается на лету, без пересборки и перезапуска приложений. Изменили конфиг — новые правила тут же заработали для всех новых подключений.

### Конфигурационные файлы

Каждое приложение, которое использует PAM, имеет **свой конфиг** в `/etc/pam.d/`. Именно там написано: какие модули запускать при входе через это приложение, в каком порядке, и что делать если модуль вернул ошибку.

Но «каждое приложение» — это не любая программа на системе, а только те, которые **сами написаны с поддержкой PAM**. То есть разработчик специально добавил в код вызов `pam_authenticate()`. `ls`, `mkdir`, `touch` — им не нужно проверять личность пользователя, они просто работают с файлами, PAM им не нужен, конфига в `/etc/pam.d/` у них нет.

А `sshd`, `sudo`, `su`, `passwd`, `gdm` — это программы, которые по смыслу своей работы должны проверять кто ты. Их разработчики специально интегрировали PAM. Конфиг в `/etc/pam.d/` есть только у тех программ, которые **пускают или не пускают** пользователя куда-либо. Это небольшой список, не тысячи программ на системе.

```bash
ls /etc/pam.d/
# common-auth   common-account   common-password   common-session
# sshd          sudo             su                login
# gdm-password  polkit-1         ...

# На Debian/Ubuntu: common-* — базовые стеки, которые включают остальные через @include
# На RHEL/CentOS: system-auth, password-auth — аналогичные базовые стеки
```

Когда пользователь, например, запускает `sudo`, PAM читает `/etc/pam.d/sudo` и **последовательно сверху вниз** прогоняет все строки — это и есть «стек». Каждая строка — один модуль, который выполняет свою проверку (проверить пароль, проверить не заблокирован ли аккаунт, применить лимиты и т.д.). Итог всего стека — либо SUCCESS, либо FAIL.

`common-*` файлы — это общие стеки, которые подключаются через `@include` в конфиги конкретных приложений, чтобы не дублировать одни и те же правила везде.

### Формат строки

```
<тип>   <управление>   <модуль.so>   [аргументы]
```

```
auth    required    pam_unix.so    nullok
│       │           │              │
│       │           │              └── аргументы модуля
│       │           └── какой модуль вызвать (ищется в /lib/security/)
│       └── что делать с результатом
└── какой тип задачи: auth / account / password / session
```

### Четыре типа (management groups)

**`auth`** — кто ты?

Проверяет личность пользователя — запрашивает пароль, токен, сертификат. Именно этот тип отвечает на вопрос «правда ли ты тот, за кого себя выдаёшь». Также устанавливает group membership.

**`account`** — можешь ли ты войти прямо сейчас?

Личность уже проверена, но этот тип решает — пускать ли вообще. Не истёк ли пароль, не заблокирован ли аккаунт, разрешено ли входить с этого хоста или в это время суток.

**`password`** — смена пароля

Вызывается только командой `passwd`. Проверяет сложность нового пароля, историю — чтобы нельзя было поставить старый пароль обратно.

**`session`** — что происходит после входа

Настраивает окружение уже после того как пользователя пустили: применяет ulimits, монтирует домашнюю директорию, записывает в системные логи (`wtmp`, `lastlog`), устанавливает переменные окружения. И симметрично — убирает всё это при выходе.

### Управляющие флаги

Второй столбец в каждой строке PAM-конфига — это флаг, который говорит что делать с результатом модуля: останавливать стек или продолжать, считать итог успехом или провалом.

**`required`** — должен пройти, но стек не останавливается

Даже если модуль вернул ошибку — PAM продолжает выполнять остальные строки. Итог всё равно будет FAIL, но злоумышленник не поймёт на каком шаге упало — время ответа одинаковое.

**`requisite`** — провал = немедленная остановка

Если модуль вернул ошибку — PAM сразу возвращает FAIL, не выполняя остальное. Используется когда продолжать бессмысленно или опасно: например, пользователь не существует — незачем спрашивать TOTP-код, это утечка информации.

**`sufficient`** — успех = немедленный пропуск

Если модуль успешен — PAM сразу возвращает SUCCESS, не проверяя остальное. Используется для альтернативных способов входа: например, root запускает `su` — незачем просить пароль.

**`optional`** — результат не влияет на итог

Модуль выполняется, но его успех или провал игнорируется. Используется для побочных действий — например показать сообщение дня (`pam_motd`). Сообщение дня (MOTD — Message of the Day) — это текст который показывается пользователю сразу после успешного входа:

```
Welcome to Ubuntu 22.04.3 LTS
Last login: Mon Jun 9 12:34:56 2026 from 192.168.1.1
System load: 0.1   Disk usage: 45%
```

Если модуль не смог показать MOTD (например файл не существует) — это не повод отказать во входе. Поэтому `optional`.

**Скобочная нотация `[...]`** — расширенная альтернатива простым флагам. Позволяет указать разное действие для каждого возможного ответа модуля.

Формат: `[статус_1=действие_1 статус_2=действие_2 ...]`

**Что слева (статус)** — код который вернул модуль. У каждого модуля есть около 30 стандартных кодов ответа. Вот самые частые:
- `success` — всё прошло успешно
- `auth_err` — неверный пароль
- `user_unknown` — пользователя не существует
- `maxtries` — превышено число попыток (именно это возвращает `pam_faillock`)
- `authinfo_unavail` — невозможно получить доступ к базе (например, упал LDAP)
- `default` — все остальные статусы не перечисленные явно

**Что справа (действие)** — список строго ограничен: 6 ключевых слов + числа для прыжков.

Числа: `N` — пропустить N следующих строк стека.

Ключевые слова:
- `ignore` — игнорировать, идти на следующую строку как будто ничего не произошло
- `bad` — запомнить ошибку, продолжить стек, но в конце будет FAIL
- `die` — немедленно остановить стек, вернуть FAIL (аналог `requisite`)
- `ok` — перезаписать предыдущие ошибки, продолжить стек
- `done` — немедленно SUCCESS если до этого не было `bad` (аналог `sufficient`)
- `reset` — сбросить всю память о предыдущих ошибках, начать с чистого листа

### Модуль (`.so` файл) — что именно проверяет

Третий столбец — это и есть сам «подключаемый модуль», файл с расширением `.so` (shared object, динамическая библиотека). Каждый модуль реализует один конкретный способ проверки. PAM ищет их в `/lib/security/` или `/lib/x86_64-linux-gnu/security/`.

```bash
ls /lib/x86_64-linux-gnu/security/
# pam_unix.so  pam_deny.so  pam_permit.so  pam_faillock.so
# pam_google_authenticator.so  pam_limits.so  pam_nologin.so ...
```

Установил пакет `libpam-google-authenticator` — в этой папке появился новый `.so` файл, и теперь его можно использовать в конфиге.

### Аргументы — как настроить поведение модуля

Четвёртый столбец — необязательные параметры, которые передаются конкретному модулю. Каждый модуль поддерживает свои аргументы, общих нет. Посмотреть аргументы конкретного модуля можно через man:

```bash
man pam_unix
man pam_faillock
man pam_limits
```

Например для `pam_unix.so`:
- `nullok` — разрешить пустой пароль (без него пустой пароль = отказ)
- `try_first_pass` — не спрашивать пароль повторно, взять уже введённый из предыдущего модуля
- `remember=5` — запомнить 5 последних паролей, не давать повторять
- `debug` — писать подробные логи в syslog (удобно при отладке)

## 3. Важные PAM-модули

**`pam_unix.so`** — классическая аутентификация

Основной модуль, который стоит почти в каждом PAM-стеке. Проверяет пароль пользователя по `/etc/passwd` и `/etc/shadow`. Именно он спрашивает у тебя пароль когда ты делаешь `sudo` или логинишься по SSH.

**`pam_deny.so` и `pam_permit.so`**

Два противоположных модуля без аргументов. `pam_deny` всегда возвращает FAIL — используется как заглушка-запрет в конце стека. `pam_permit` всегда возвращает SUCCESS — используется как финишная черта после успешного прохождения всех проверок.

**`pam_env.so`** — переменные окружения

Устанавливает переменные окружения при логине. Стоит в типе `session` — переменные устанавливаются уже **после** того как пользователя пустили, в момент открытия сессии. Обычно в конфиге стоят две строки с `pam_env` подряд — это не один вызов, а два отдельных вызова одного модуля с разными аргументами. Каждый работает со своим окружением:

Аргумент `readenv` — булевый: `1` означает «включено» (true), `0` — «выключено» (false). Когда пишешь `readenv=1` — явно указываешь модулю читать `/etc/environment`. С `readenv=0` — `/etc/environment` читаться не будет.

```bash
# /etc/pam.d/login
# readenv=1 читает /etc/environment и /etc/security/pam_env.conf
session required pam_env.so readenv=1
# readenv=0 — не читать /etc/environment повторно, только локаль через envfile= (так конфиг чище)
session required pam_env.so readenv=0 envfile=/etc/default/locale
```

**`/etc/environment`** и **`/etc/security/pam_env.conf`** — общие переменные для всех пользователей, оба читаются через `readenv=1`. Сюда пишешь то что нужно всем при любом входе:
```
HTTP_PROXY=http://proxy.company.com:3128
TZ=Europe/Moscow
PATH=/usr/local/bin:/usr/bin:/bin
```

**`/etc/default/locale`** — только переменные локали. Язык интерфейса, формат дат, кодировка:
```
LANG=ru_RU.UTF-8
LC_ALL=ru_RU.UTF-8
LC_TIME=ru_RU.UTF-8
```

После сохранения переменные появятся у всех пользователей при следующем входе. Текущие сессии не затрагиваются.

**`pam_nologin.so`** — отключение логинов

Если существует файл `/etc/nologin` — запрещает вход всем кроме root и выводит содержимое файла как сообщение.

На практике используется когда нужно срочно закрыть сервер — обновление ядра, миграция базы данных, критический инцидент. Создаёшь файл с объяснением, root продолжает работать, все остальные видят сообщение и не могут войти. Удалил файл — сервер снова открыт. Никаких правок конфигов, никакого перезапуска служб.

Стоит в типе `auth` с флагом `requisite` — проверка файла `/etc/nologin` происходит **до** проверки пароля. Если файл существует — пользователя даже не спрашивают пароль, сразу отказ.

```bash
echo "Техническое обслуживание до 03:00" > /etc/nologin  # закрыть
rm /etc/nologin                                           # открыть
```

**`pam_limits.so`** — ограничения ресурсов

Применяет лимиты из `/etc/security/limits.conf` к сессии пользователя — максимальное количество открытых файлов, процессов, размер памяти. `pam_limits` — это модуль который читает `limits.conf` и применяет лимиты к сессии. Без него файл `limits.conf` просто лежит на диске и никак не используется — система его не читает. То есть ты можешь написать в `limits.conf` что угодно, но без `pam_limits` в стеке это никак не повлияет на пользователей.

**`pam_time.so`** — ограничение по времени

Разрешает или запрещает вход в зависимости от времени суток и дня недели. Конфигурируется в `/etc/security/time.conf`. Например можно разрешить обычным пользователям логиниться только в рабочие часы.

## 4. SSH и PAM

Ключевое правило: sshd никогда не отдаёт **криптографическую** проверку SSH-ключей в PAM — валидацию `authorized_keys` демон всегда выполняет сам. Но стек PAM вызывается при любом способе входа, просто на разных этапах и с разными ролями.

**Способ 1: Вход по публичному ключу**

sshd сам проверяет ключ по `~/.ssh/authorized_keys` — PAM в криптографии не участвует. Как только ключ подтверждён, sshd всё равно прогоняет пользователя через стек `auth` в PAM, но в «пассивном» режиме — говорит PAM: «пользователь уже подтверждён, пароль не нужен». Это нужно чтобы выполнились системные проверки — например `pam_nologin` запретит вход если висит файл `/etc/nologin`, а `pam_faillock` проверит не заблокирован ли аккаунт. Затем `account` проверяет можно ли войти прямо сейчас, `session` настраивает окружение, применяет лимиты и пишет логи.

**Способ 2: Вход по паролю**

sshd сам не знает как проверять пароли — он выступает как курьер и передаёт логин и пароль в PAM. Дальше PAM берёт всё на себя: `auth` проверяет пароль по `/etc/shadow`, `account` проверяет срок действия и ограничения, `session` настраивает окружение.

**Способ 3: Двухфакторная аутентификация (ключ + TOTP)**

Самый красивый гибрид — sshd и PAM работают как команда на разных этапах. Сначала sshd сам проверяет ключ. Если ключ верный — передаёт управление PAM, который через `pam_google_authenticator.so` запрашивает TOTP-код. Только после того как оба фактора подтверждены — `account` и `session` завершают вход.

Чтобы эта схема заработала, в `sshd_config` должна быть настроена директива `AuthenticationMethods publickey,keyboard-interactive` — она жёстко задаёт порядок: сначала ключ (проверяет sshd), потом интерактивный диалог (передаётся в PAM). При этом в `/etc/pam.d/sshd` нужно убрать или обойти `pam_unix.so` — иначе после ключа система потребует ещё и пароль, и только потом TOTP.

**Два параметра в `/etc/ssh/sshd_config` которые касаются PAM:**

`UsePAM yes` — глобально разрешает sshd обращаться к PAM. Если поставить `UsePAM no` — при входе по ключу не применятся системные лимиты (`limits.conf`), не сработает запрет на вход во время техобслуживания (`/etc/nologin`), не запишутся логи сессии. Для продакшена `UsePAM no` — табу.

`KbdInteractiveAuthentication yes` (в старых версиях OpenSSH — `ChallengeResponseAuthentication`) — включает интерактивный режим «запрос-ответ». Он позволяет серверу задавать клиенту произвольные текстовые вопросы в терминале. Без этого флага sshd не сможет отобразить в консоли строчку `Verification code:` и передать ответ в `pam_google_authenticator.so` — соединение просто сбросится.

> 📌 Стек PAM вызывается при любом способе входа. При входе по ключу sshd сам валидирует криптографию, а в стек `auth` передаёт статус «успешно идентифицирован» — чтобы выполнились системные проверки. При входе по паролю sshd делегирует проверку в PAM (`pam_unix.so`). При 2FA sshd последовательно требует два метода — ключ проверяет сам, `keyboard-interactive` передаёт в PAM.

## 5. Анатомия PAM: Модули и файлы конфигурации

Сам по себе PAM — это лишь диспетчер. Когда `sshd` или `login` запрашивают проверку, PAM идёт в `/etc/pam.d/` и выполняет правила из стека. Но откуда модули знают как именно проверять? На сколько секунд блокировать пользователя? Какие лимиты выставлять?

Для этого у PAM есть два уровня конфигурации:

- `/etc/pam.d/*` — «дирижёры». Определяют порядок вызова модулей (`required`, `sufficient` и т.д.)
- `/etc/security/*` — «инструкции». Текстовые конфиги самих модулей, управляющие их логикой. Сами бинарные модули (`.so` файлы) лежат в `/usr/lib/x86_64-linux-gnu/security/`, а их настройки вынесены отдельно

Ниже разобраны три критически важных механизма PAM: откуда можно войти (`securetty`), сколько раз можно ошибиться паролем (`faillock`), и какие ресурсы система выделит пользователю (`limits`).

> 📌 **Важно:** все конфигурационные файлы в `/etc/security/` присутствуют в системе по умолчанию — создавать их не нужно. Ты просто наполняешь их своими настройками, а соответствующий PAM-модуль читает файл при каждом входе пользователя и применяет настройки к сессии.

## 5.1. /etc/securetty — Ограничение входа root по типу терминала

**Историческая справка:** до появления современных практик безопасности этот механизм ограничивал физические и виртуальные консоли (TTY) с которых root мог войти в систему. За логику отвечал модуль `pam_securetty.so` — при попытке входа он читал файл `/etc/securetty` и проверял есть ли там имя текущего терминала. Если root заходил через `tty1` (физический монитор) — вход разрешён, если через сетевой псевдотерминал (`pts/0`) — PAM отказывал.

**Современное состояние:** в актуальных дистрибутивах (Ubuntu 22.04+, Debian 12+) файл `/etc/securetty` упразднён, а модуль исключён из стека PAM. Проверить это можно так:

```bash
# Проверяем наличие файла и упоминание модуля в PAM
cat /etc/securetty
grep -r "securetty" /etc/pam.d/

# В современных системах вывод будет пустым (модуль не вызывается),
# либо система сообщит что файл /etc/securetty отсутствует
```

Сегодня контроль root-входа полностью строится на директиве `PermitRootLogin` в `/etc/ssh/sshd_config` — она надёжнее и покрывает все сетевые подключения.

## 5.2. pam_faillock — Защита от брутфорса

Если злоумышленник или автоматический скрипт пытается подобрать пароль к учётной записи по SSH или локально, PAM должен уметь вовремя это остановить. Модуль `pam_faillock` считает неудачные попытки аутентификации и временно блокирует аккаунт. Каждая неудача записывается в виде бинарного файла-счётчика в директорию `/var/run/faillock/<username>`.

Чтобы модуль начал перехватывать запросы, он должен быть включён в стек PAM. В Ubuntu это делается автоматически при установке пакета или через утилиту `pam-auth-update` — она сама прописывает правила `preauth` и `authfail` в главный файл аутентификации `/etc/pam.d/common-auth`.

Поведение модуля настраивается в файле `/etc/security/faillock.conf`:

```
# Блокировать после 5 неудачных попыток
deny = 5

# Время блокировки в секундах (15 минут)
unlock_time = 900

# Окно времени в секундах в котором учитываются попытки
fail_interval = 900

# Логировать ошибки скрытно в syslog (/var/log/auth.log),
# не вылезая с подсказками в терминал к взломщику
silent
```

**Инструменты управления:**

```bash
# Посмотреть статус попыток и блокировки конкретного пользователя
faillock --user alice

# Сбросить счётчик и разблокировать пользователя вручную (если он вспомнил пароль)
faillock --user alice --reset

# Посмотреть список пользователей у которых есть накопленные ошибки ввода
ls /var/run/faillock/
```

> ⚠️ **Важно для DevOps:** папка `/var/run/` монтируется в оперативную память (`tmpfs`). Если сервер экстренно перезагрузить — все накопленные блокировки `faillock` сбросятся и счётчики обнулятся. Если нужно сохранять блокировки между перезагрузками, в конфиг добавляют параметр `dir = /var/lib/faillock`, но для большинства стандартного поведения в RAM более чем достаточно.

## 5.3. /etc/security/limits.conf — Управление ресурсами сессии

Чтобы один кривой скрипт, утечка памяти или fork-бомба не уронили весь сервер, в Linux существуют ограничения ресурсов. За их автоматическое применение при входе пользователя отвечает модуль `pam_limits.so`, который считывает конфигурацию из `/etc/security/limits.conf`.

### Мягкие (Soft) и Жёсткие (Hard) лимиты

При логине модуль выставляет два типа ограничений. **Soft limit** (мягкий) — текущий рабочий лимит. Пользователь может сам увеличить его прямо во время сессии командой `ulimit`, но не выше чем hard limit. **Hard limit** (жёсткий) — потолок безопасности установленный администратором. Поднять его выше обычный пользователь не может — только root.

```bash
ulimit -a    # все текущие лимиты активной сессии
ulimit -Sn   # мягкий лимит на открытые файлы
ulimit -Hn   # жёсткий лимит на открытые файлы
```

### Формат файла

Каждая строка имеет строгую структуру из четырёх колонок:

```
<domain>   <type>   <item>   <value>
```

- **`<domain>`** — к кому применяется: пользователь (`alice`), группа (`@developers`), все (`*`). Важно: символ `*` на root не распространяется — для root нужно задавать явно.
- **`<type>`** — `soft` или `hard`
- **`<item>`** — ограничиваемый параметр
- **`<value>`** — числовое значение или `unlimited`

```bash
# Ограничение на кол-во открытых файлов для конкретного юзера
alice           soft        nofile     65536
alice           hard        nofile     131072

# Ограничение на кол-во процессов для группы (начинается с @)
@developers     soft        nproc      10000
@developers     hard        nproc      20000

# Запрет генерации core dump для всех, кроме root
*               soft        core       0
*               hard        core       0

# Root задаётся явно — * его не покрывает
root            soft        nofile     65536
root            hard        nofile     131072
```

### Топ-4 важных параметров для DevOps

Параметров (`item`) в Linux порядка 20+. Вот самые важные:

**1. nofile** — максимальное количество открытых файлов и сетевых сокетов для процесса.

Под нагрузкой веб-серверы и базы данных открывают тысячи соединений — каждое соединение это файловый дескриптор. Когда лимит исчерпан, новые подключения отклоняются с ошибкой `Too many open files` — пользователи видят ошибку на сайте хотя сервер физически не перегружен. Просто поднять `nofile` — необходимый, но недостаточный шаг. На уровне архитектуры проблему решают внедрением пула соединений (Connection Pooling) через PgBouncer для PostgreSQL или ProxySQL для MySQL.

**2. nproc** — максимальное количество процессов и потоков которые может запустить пользователь.

Прямая защита от fork-бомб и кривых скриптов которые бесконечно плодят дочерние процессы и утилизируют весь CPU, намертво вешая сервер.

**3. memlock** — максимальный объём памяти в RAM который процесс может заблокировать, запретив системе сбрасывать её в swap.

СУБД и поисковые движки (PostgreSQL, Elasticsearch) критичны к скорости доступа к памяти. Если их данные уйдут в swap (на диск), производительность упадёт в десятки раз. Приложения используют системный вызов `mlock()` чтобы закрепить свои буферы в RAM, а ядро сверяет этот запрос с лимитом `memlock`.

```bash
grep VmLck /proc/$(pgrep postgres)/status
# VmLck: 2097152 kB  ← заблокировано 2GB в RAM
# VmLck: 0 kB        ← ничего не заблокировано, данные могут уходить в swap
```

**4. core** — максимальный размер «посмертного слепка» памяти процесса при аварийном завершении.

Когда программа крашится с ошибкой `Segmentation fault (core dumped)` — Linux сохраняет на диск файл со всем содержимым её памяти в момент падения. Разработчики открывают его в отладчике GDB (GNU Debugger) чтобы понять что именно пошло не так — увидеть стек вызовов и состояние переменных в момент краша.

На продакшене это чаще вредит чем помогает: если приложение падает циклично, dump-файлы быстро забивают весь диск. Поэтому на серверах генерацию обычно отключают (`0`), а включают только когда нужно поймать баг (`unlimited`).

```bash
ulimit -c 0         # отключить генерацию core dump
ulimit -c unlimited # включить без ограничений
```

> ⚠️ Core dump копирует всю память процесса — в файл могут попасть пароли, ключи шифрования и другие конфиденциальные данные. Доступ к этим файлам должен быть только у root.

**Разделение конфигурации — `/etc/security/limits.d/`**

Редактировать основной файл `/etc/security/limits.conf` напрямую — плохая практика: он может перезатереться при обновлении системы и сложно понять какие лимиты откуда пришли. Вместо этого принято создавать отдельные файлы в директории `/etc/security/limits.d/` — по одному файлу на сервис или задачу. PAM автоматически читает все файлы из этой директории. Так конфигурация остаётся чистой и каждый файл отвечает за свою зону.

```bash
cat /etc/security/limits.d/99-nginx.conf
# www-data  soft  nofile  65536
# www-data  hard  nofile  65536
```

⚠️ **Новые лимиты требуют перелогина.** Если ты изменил `limits.conf`, у текущих залогиненных пользователей ничего не поменяется. Модуль `pam_limits.so` срабатывает только в момент создания сессии — пользователю нужно переоткрыть SSH-сессию.

⚠️ **PAM не контролирует systemd.** Это самая частая ошибка в проде. Если Nginx, PostgreSQL или любой другой сервис запускается через systemd — он полностью игнорирует `limits.conf`. Лимиты нужно прописывать в юнит-файле:

```
# /etc/systemd/system/nginx.service.d/override.conf
[Service]
LimitNOFILE=65536
LimitMEMLOCK=infinity
```

`infinity` — без ограничений: процессу разрешено заблокировать столько памяти сколько нужно.

⚠️ **Зависимость от PAM-стека.** Лимиты вообще не применятся если в `/etc/pam.d/common-session` закомментирована или отсутствует строка:

```
session required pam_limits.so
```

## 6. Анти-паттерны

**Отключение PAM для sshd:**
```
UsePAM no   # НИКОГДА без весомой причины
```
Отключает pam_limits (ulimits не применяются), pam_faillock, логирование сессий. Ломает весь стек безопасности.

**PasswordAuthentication yes + без fail2ban/pam_faillock:**
Открытый SSH с паролями без защиты от брутфорса — сервер будет сканироваться и атаковаться постоянно. Проверяйте `grep "Failed password" /var/log/auth.log | wc -l`.

**PermitRootLogin yes:**
Прямой вход root по паролю через SSH. Если злоумышленник подберёт пароль — он сразу получает полный контроль над сервером без каких-либо ограничений. Правильная схема: обычный пользователь → `sudo` — тогда даже при компрометации пароля атакующий ещё должен знать пароль от sudo и преодолеть все его ограничения.

**Редактировать /etc/pam.d/common-auth напрямую без бэкапа:**
Синтаксическая ошибка в `common-auth` заблокирует вход через ВСЕ сервисы включая локальную консоль — потому что `common-auth` подключается через `@include` во все конфиги (`sshd`, `sudo`, `login` и т.д.). Одна ошибка ломает всю цепочку сразу. Всегда держите открытой вторую сессию при правке PAM.

**Пренебрегать правами на ~/.ssh:**
```bash
# Если права неправильные — sshd тихо отказывает в ключевой аутентификации
# без понятного сообщения об ошибке
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
chmod 600 ~/.ssh/id_*
```

**Один SSH-ключ на всё:**
Один ключ для GitHub, для серверов, для CI. Компрометация одного — компрометация всего. Используйте разные ключи для разных контекстов.

## 7. Реальные кейсы с дебагом

### Кейс 1: пользователь не может залогиниться, пароль правильный

```bash
# Симптом: "Permission denied" хотя пароль точно верный

# Шаг 1: проверить заблокирован ли аккаунт pam_faillock
faillock --user alice
# Если много записей — разблокировать
faillock --user alice --reset

# Шаг 2: проверить не истёк ли аккаунт / пароль
chage -l alice
# Account expires: Jan 15, 2024  ← аккаунт истёк!

# Продлить аккаунт
sudo chage -E -1 alice  # -1 = никогда не истекает

# Шаг 3: проверить не заблокирован ли аккаунт вручную
passwd -S alice
# alice L 2024-01-10 0 99999 7 -1  ← L = Locked!
passwd -u alice  # разблокировать
```

### Кейс 2: SSH ключ не работает, "Permission denied (publickey)"

```bash
# Шаг 1: на клиенте — подробный вывод
ssh -vv alice@server 2>&1 | grep -E "Trying|Offering|debug"
# Ищем: "Offering public key" → "Server accepts key" или "Server rejects key"

# Шаг 2: на сервере — проверить права
ls -la ~alice/.ssh/
# drwxr-xr-x .ssh/  ← НЕПРАВИЛЬНО! должно быть drwx------
# -rw-r--r-- authorized_keys  ← НЕПРАВИЛЬНО! должно быть -rw-------

# Исправить
chmod 700 ~alice/.ssh
chmod 600 ~alice/.ssh/authorized_keys
chown -R alice:alice ~alice/.ssh

# Шаг 3: проверить что ключ вообще есть
cat ~alice/.ssh/authorized_keys
# Должен совпадать с ~/.ssh/id_ed25519.pub на клиенте

# Шаг 4: проверить SELinux (на RHEL)
ls -laZ ~alice/.ssh/authorized_keys
restorecon -Rv ~alice/.ssh/
```

### Кейс 3: ulimits не применяются для сервиса

```bash
# Симптом: nginx или postgres не открывает много соединений, ошибки "too many open files"

# Проверить текущие лимиты процесса
cat /proc/$(pgrep -o nginx)/limits | grep "Max open files"
# Max open files  1024  4096  files  ← слишком мало!

# Для systemd-сервисов — НЕ редактировать limits.conf!
# Создать override для юнит-файла:
sudo systemctl edit nginx
# Добавить:
# [Service]
# LimitNOFILE=65536

sudo systemctl daemon-reload
sudo systemctl restart nginx

# Проверить
cat /proc/$(pgrep -o nginx)/limits | grep "Max open files"
# Max open files  65536  65536  files  ✓
```

## 8. Вопросы на собесе

**«Что такое PAM и зачем он нужен?»**
PAM — это API-прослойка между приложениями и механизмами аутентификации. Приложение вызывает `pam_authenticate()` не зная как именно происходит проверка. PAM позволяет менять схему аутентификации (добавить LDAP, 2FA, биометрию) изменив конфиг без пересборки приложений. Четыре типа: auth, account, password, session.

**«Почему sudo не проверяет пароль сам, а делегирует PAM?»**
sudo вызывает `pam_authenticate()` — PAM сам решает как проверить: пароль, LDAP, 2FA, fingerprint. Это значит можно изменить метод аутентификации для sudo просто изменив `/etc/pam.d/sudo` — без пересборки sudo. Именно поэтому добавление Google Authenticator к sudo делается одной строкой в PAM-конфиге, а не патчем самого sudo.

**«В чём разница between required, requisite и sufficient?»**
`required` — неудача замечена, но стек продолжается (итог будет FAIL). `requisite` — неудача немедленно прерывает стек, не давая утечь информации через остальные модули. `sufficient` — при успехе немедленно возвращает SUCCESS минуя остальное.

**«Проходит ли SSH ключевая аутентификация через PAM?»**
Нет, проверка ключа делается sshd напрямую сравнивая с authorized_keys. PAM при ключевой аутентификации вызывается только для account и session (если `UsePAM yes`). Именно поэтому для 2FA с ключами нужно отдельно настраивать `AuthenticationMethods publickey,keyboard-interactive`.

**«Как добавить 2FA в SSH не сломав доступ по ключу?»**
`AuthenticationMethods publickey,keyboard-interactive` — требует оба фактора. `pam_google_authenticator.so` с флагом `nullok` — пользователи без 2FA могут войти только ключом (переходный период). Всегда оставлять открытую сессию при тестировании изменений PAM.

**«Почему изменения в limits.conf не применяются к nginx?»**
Потому что systemd-сервисы не проходят через PAM при старте, они не создают "login session". Для systemd нужен `LimitNOFILE` в юнит-файле.
