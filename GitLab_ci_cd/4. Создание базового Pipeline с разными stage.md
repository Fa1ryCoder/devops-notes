# 4. Написание простого pipeline с разными stage

Разбираемся, как pipeline реально пишется в `.gitlab-ci.yml`: что писать, в каком порядке это исполняется и на что обычно обращают внимание на собесе.

## Минимальный рабочий пайплайн

Самый простой валидный `.gitlab-ci.yml` — один job с одним `script`, stage вообще не обязателен:

```yaml
say_hello:
  script:
    - echo "Hello, pipeline!"
```

`say_hello` здесь — это и есть job: любой ключ, написанный без отступа в самом начале строки (то есть не вложенный внутрь другого ключа), у которого есть `script`. Имя придумываешь сам — единственное ограничение: оно не должно совпадать с зарезервированными словами вроде `stages`, `variables`, `workflow`, `default`, `include`, которые настраивают пайплайн целиком, а не одну задачу. Проще всего отличить: есть `script` — значит job, нет `script` — один из настроечных ключей.

Ещё нюанс: если имя job начать с точки — `.build-template` — GitLab не будет считать её реальной job и не включит в pipeline. Такая запись используется как шаблон, на который потом ссылаются через `extends`, чтобы не дублировать одинаковые куски конфига. Полезно знать хотя бы для того, чтобы не удивляться, почему job вдруг пропала из списка в пайплайне.

GitLab такое примет и запустит. Но реальные пайплайны почти всегда делят работу на **stages**.

## `stages` и `stage`: как задать порядок

Без stages все job в пайплайне попытались бы стартовать одновременно — GitLab не умеет сам угадывать, что тесты нужно гонять после сборки, а не параллельно с ней. Stages — это как раз способ сказать: "сначала выполни всё это, и только потом переходи к следующему". Без них риск словить ситуацию, когда деплой стартует раньше, чем закончилась сборка, или тесты гоняются по ещё не собранному коду.

Синтаксически это два разных ключевых слова, которые легко перепутать:

- **`stages`** (множественное число, верхний уровень файла) — список стейджей и порядок их выполнения.
- **`stage`** (единственное число, внутри job) — к какому из объявленных стейджей относится конкретная job.

```yaml
stages:
  - build
  - test
  - deploy

build_job:
  stage: build
  script:
    - echo "Собираем приложение"

test_job:
  stage: test
  script:
    - echo "Гоняем тесты"

deploy_job:
  stage: deploy
  script:
    - echo "Деплоим"
```

Порядок в `stages` и есть порядок выполнения. Если job ссылается на stage, которого нет в этом списке, GitLab отклонит конфиг ещё на этапе валидации — пайплайн даже не запустится, это ошибка линтинга, а не ошибка выполнения.

## Как это выполняется: стейджи последовательно, джобы внутри — параллельно

- Стейджи идут строго друг за другом: следующий стартует, только когда **все** джобы предыдущего завершились успешно.
- Джобы внутри одного стейджа выполняются параллельно (если раннеров достаточно).

```
Порядок: build → test → deploy

  build:              test:                       deploy:
[build_job]   →   [unit_test] [lint_job]   →   [deploy_job]
                   (выполняются параллельно)
```

Пример: в стейдже `test` параллельно идут `lint` и `unit_test`. `lint` падает раньше, чем `unit_test` успевает закончиться. Что происходит: `unit_test` не обрывается на середине, а доделывает свою работу до конца — просто потому что она уже была запущена и никак не связана с `lint` напрямую. А вот стейдж `deploy`, который идёт после `test`, не стартует вообще — GitLab уже знает, что весь `test` в итоге failed, и дальше по цепочке идти нет смысла.

## Что будет, если `stages` не указать вообще

Вот и то самое отличие пайплайна "со stage" и "без stage", про которое ты спрашивал.

На практике pipeline без стейджей в чистом виде не бывает: если ключ `stages` не объявлен, GitLab всё равно подставляет свои дефолтные пять — **`.pre`, `build`, `test`, `deploy`, `.post`**. Важно не путать: `build`, `test` и `deploy` — это не зарезервированные слова, а просто имена по умолчанию, если ты сам ничего не объявил. Если ты пишешь `stages:` сам, называть стейджи можно как угодно — хоть `compile`, `qa`, `release`, никаких ограничений. А вот у job, если у неё вообще нет ключа `stage` — она автоматически уезжает в **`test`**.

```yaml
# stages нигде не объявлены
say_hello:
  script:
    - echo "Всё равно сработает"
```

Такой файл рабочий, ошибки не будет — `say_hello` молча попадёт в дефолтный `test`. На практике это плохая идея: как только джоб становится больше одной-двух, легко забыть проставить `stage:` где-нибудь, и job уедет не туда, где ты её ждёшь. При этом линтер промолчит — конфиг формально валиден, просто выполнится не в том порядке, что у тебя в голове. Поэтому простое практическое правило: **всегда объявляй `stages` явно**, даже если стейджа всего два.

Отдельная деталь — `.pre` и `.post`. Это зарезервированные стейджи, они существуют всегда, даже если ты их нигде не писал:

- **`.pre`** — выполняется первым, на какой бы позиции его ни объявить.
- **`.post`** — выполняется последним, по той же логике.
- Если в пайплайне есть джобы только в `.pre`/`.post` и больше нигде — пайплайн вообще не запустится, GitLab требует хотя бы один job в обычном стейдже.

```yaml
stages:
  - build
  - test

sanity_check:
  stage: .pre
  script:
    - echo "Проверка перед всем остальным"
```

## Из чего состоит job: `image`, `script`, `before_script`, `after_script`

- **`image`** — какой Docker-образ поднять под job. Если executor раннера — docker, именно `image` определяет, в каком контейнере реально выполнится `script`. Не укажешь — используется образ по умолчанию, заданный на уровне раннера.
- **`script`** — обязательный ключ, без него job невалидна.
- **`before_script`** — выполняется перед `script`, обычно подготовка (например, `chmod +x` или установка зависимостей).
- **`after_script`** — выполняется после `script`, **даже если сам script упал**. Удобно для уборки или отправки уведомления о статусе.

```yaml
deploy_job:
  stage: deploy
  image: alpine:latest
  before_script:
    - chmod +x deploy.sh
  script:
    - ./deploy.sh
  after_script:
    - echo "Джоба завершена, неважно с каким результатом"
```

Путь в `script` должен точно совпадать с тем, где `deploy.sh` реально лежит: если он в корне — пишешь `./deploy.sh`, если в папке `scripts/` — обязательно `./scripts/deploy.sh`, а не просто `./deploy.sh`. Раннер сам клонирует репозиторий перед job, поэтому `script` сразу видит файлы проекта. Нет файла по указанному пути — job упадёт с "No such file or directory".

## `default` — значения по умолчанию для всех job

Отдельный top-level ключ `default` задаёт значения по умолчанию сразу для всех job в файле — удобно, когда десятки job используют одно и то же (например, один и тот же `image` или одинаковую подготовку в `before_script`), и не хочется копипастить это в каждую job вручную:

```yaml
default:
  image: node:20
  before_script:
    - echo "Это выполнится перед script в каждой job"
```

Любая job в файле возьмёт эти значения автоматически. Если конкретной job нужно другое поведение — просто пропиши нужный ключ прямо в ней, он полностью перекроет дефолтный (не сложится с ним, а именно заменит).

## `rules` — актуальный способ управлять запуском

Не все job должны запускаться всегда и на каждый коммит. Например, деплой в прод логично пускать только с ветки `main`, а не с любой feature-ветки, а какую-нибудь тяжёлую проверку — только вручную, а не на каждый push. `rules` — это как раз способ задать условие: запускать job или нет, в зависимости от ветки, события, тега и так далее.

Раньше это делали через `only`/`except`. Сейчас в документации GitLab они прямо помечены как **deprecated** (устаревшие, готовятся к удалению) — рабочий вариант, встретишь в старых проектах, но для нового кода используют `rules`.

```yaml
deploy_prod:
  stage: deploy
  script:
    - echo "Деплой в прод"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual
```

`$CI_COMMIT_BRANCH` — предопределённая переменная с именем текущей ветки, таких переменных у GitLab много (полный список — в документации). Правила проверяются сверху вниз, срабатывает первое совпавшее; если не совпало ни одно — job в пайплайн просто не попадает.

Практический смысл: в `main` обычно не пишут напрямую, разработку ведут в отдельных ветках (feature-ветки, багфиксы), а в `main` код попадает через merge request после ревью. В примере ниже (build → test → deploy) `build_job` и `unit_test` не имеют `rules` — значит, они гоняются на любой ветке при каждом push, чтобы сразу проверять код. А вот `deploy_job` с условием `$CI_COMMIT_BRANCH == "main"` сработает только тогда, когда код уже смержен в `main` — то есть деплой физически не может случиться раньше, чем код пройдёт через merge request и попадёт в основную ветку.

**Практическая засада.** У тебя открыт merge request из ветки `feature-x`. Разбираем по шагам, откуда берётся дубль:

1. Создаёшь ветку `feature-x`, коммитишь, делаешь `git push`. Раз в репозитории есть `.gitlab-ci.yml`, GitLab автоматически создаёт pipeline на любой push — это базовое поведение, отдельно включать не нужно. При создании pipeline GitLab сам, автоматически, заполняет предопределённую переменную `$CI_PIPELINE_SOURCE` — она не задаётся тобой нигде, а просто отражает, что именно вызвало запуск. В данном случае это `push`.
2. Открываешь merge request (`feature-x → main`). Казалось бы, код тот же самый, pipeline на него уже прогнался в шаге 1 — зачем ещё один? Но GitLab считает открытие merge request отдельным событием и запускает для него отдельный, новый pipeline — именно он появится во вкладке проверок самого merge request. У него `$CI_PIPELINE_SOURCE == "merge_request_event"`, и это не тот же pipeline, что из шага 1, а второй, независимый запуск на тот же коммит.
3. Дальше, пока идёт ревью, ты обычно ещё не раз пушишь правки по комментариям — снова `git push` в ту же `feature-x`. Для этого нового коммита сразу срабатывают оба триггера: push (как в шаге 1) и обновление уже открытого merge request (как в шаге 2), потому что ветка уже привязана к открытому merge request. GitLab генерирует оба события на этот коммит одновременно — получаются 2 пайплайна, а не 3. Это не накопление (1 → 2 → 3 с каждым шагом), а один и тот же паттерн: любой коммит, запушенный в ветку с уже открытым merge request, всегда даёт ровно 2 пайплайна.

Итог: два одинаковых пайплайна на один коммит — вдвое больше потраченных минут раннера, и в самом merge request в списке проверок задвоенные джобы, что сбивает с толку того, кто ревьюит. Важно: это не зависит от того, одобрил уже ревьюер или нет, — проблема живёт, пока у ветки открыт merge request. Как только merge request смержен или закрыт, событие `merge_request_event` для этой ветки больше не генерируется, и дубль пропадает сам собой.

**Решение практической засады.** `workflow: rules` — это фильтр на уровне всего файла: решает, создавать ли pipeline вообще. Обычные `rules` внутри job — фильтр рангом ниже, он работает только если pipeline уже создан. Поэтому дубль правильно чинить именно через `workflow: rules`: мы просто не даём создаться одному из двух лишних пайплайнов, а не пытаемся отключить джобы внутри него по отдельности. На практике чаще оставляют именно пайплайн для merge request, а дублирующий push-пайплайн блокируют:

```yaml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH
```

Правила проверяются по порядку, побеждает первое совпавшее:
1. Событие merge request (`$CI_PIPELINE_SOURCE == "merge_request_event"`) — пайплайн создаётся, всё честно.
2. Push в ветку, для которой уже открыт merge request (`$CI_OPEN_MERGE_REQUESTS`) — это и есть тот самый дубль, блокируем его.
3. Обычный push в ветку без открытого merge request (в том числе в `main`) — пропускаем как есть.

Почему выбирают именно пайплайн для merge request, а не push: внутри него доступны отдельные переменные, например `$CI_MERGE_REQUEST_TARGET_BRANCH_NAME` (ветка, в которую мержишься) — полезно, чтобы линтер проверял только изменённые файлы, а не весь репозиторий. Более простой вариант — наоборот, отключить пайплайн для merge request и оставить только push (`if: merge_request_event → when: never`) — тоже рабочий и проще для небольшого pet-проекта, но в реальных командах встречается реже.

И ещё нюанс: смешивать `only/except` и `rules` в одном пайплайне не стоит — технически GitLab не запретит, но логика в таком файле быстро становится нечитаемой.

## Полный пример: build → test → deploy

Собранный пример, близкий к тому, что реально могут попросить написать руками на собесе:

```yaml
stages:
  - build
  - test
  - deploy

build_job:
  stage: build
  image: node:20
  script:
    - npm ci
    - npm run build
  artifacts:
    paths:
      - dist/

unit_test:
  stage: test
  image: node:20
  script:
    - npm ci
    - npm test

lint:
  stage: test
  image: node:20
  script:
    - npm run lint

deploy_job:
  stage: deploy
  image: alpine:latest
  script:
    - echo "Деплой на prod"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual
```

Что тут происходит: `build_job` устанавливает зависимости (`npm ci`) и собирает проект (`npm run build`) — результат сборки (скомпилированные файлы, а не сами зависимости) попадает в папку `dist/` и сохраняется как **artifact**; `unit_test` и `lint` гоняются параллельно в стейдже `test`; `deploy_job` доступен только на ветке `main` и требует ручного нажатия кнопки Play — типичная практика для деплоя в прод. Если сможешь объяснить этот пример построчно на собесе — тему можно считать закрытой.
