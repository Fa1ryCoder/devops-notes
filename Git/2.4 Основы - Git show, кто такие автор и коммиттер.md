## 1. Команда git show

В процессе работы часто возникает необходимость посмотреть что именно было изменено в конкретном коммите — какие файлы затронуты, кто автор, когда это было сделано. Например чтобы разобраться в чужом коде, найти когда появилась ошибка или просто проверить свой последний коммит перед пушем. Для этого используется команда `git show`.

### Как узнать хеш коммита

```bash
# Полный хеш последнего коммита
git rev-parse HEAD
# c9a4aa4e75c7d47a555b3d6608f76c1f65e38a24

# Сокращённый хеш последнего коммита
git rev-parse --short HEAD
# c9a4aa4
```

### Как использовать git show

```bash
# Показать последний коммит
git show

# Показать конкретный коммит по хешу
git show c9a4aa4e75c7d47a555b3d6608f76c1f65e38a24

# Можно указывать сокращённый хеш — минимум 4 символа
git show c9a4
```

Полный идентификатор коммита состоит из 40 шестнадцатеричных символов, но Git принимает любое уникальное сокращение начиная с 4 символов.

### Что выводит команда

```bash
git show
```

```
commit c9a4aa4e75c7d47a555b3d6608f76c1f65e38a24 (HEAD -> main, origin/main)
Author: Иван Иванов <ivan@example.com>
Date:   Mon Jun 1 12:00:00 2026 +0300

    Add app.py                        ← сообщение коммита

diff --git a/app.py b/app.py
new file mode 100644
index 0000000..e69de29
--- /dev/null
+++ b/app.py
@@ -0,0 +1 @@
+print("Hello World")
```

| Поле | Описание |
|------|----------|
| `commit` | Полный SHA-1 хеш коммита + ссылки в скобках (ветки, теги) |
| `Author` | Кто написал код (имя + email) |
| `Date` | Когда был написан код |
| Сообщение | Текст который написали при коммите через `-m` |
| `diff` | Построчное сравнение изменений — `+` добавленные строки, `-` удалённые. Разберём подробно в теме `6.1 git diff` |

## 2. Автор vs Коммиттер

**Автор (Author)** — человек который непосредственно написал код и придумал изменения.
**Авторская дата (AuthorDate)** — время когда автор написал этот код.

**Коммиттер (Committer)** — человек который сохранил изменения в репозиторий.
**Дата коммита (CommitDate)** — время создания записи в репозитории.

По умолчанию когда ты один работаешь над проектом — автор и коммиттер это одно и то же лицо, даты совпадают. При обычном `git show` видны только `Author` и `Date`. Чтобы увидеть все поля — используй флаг `--pretty=fuller`:

```bash
git show --pretty=fuller
```

```
commit c9a4aa4e75c7d47a555b3d6608f76c1f65e38a24 (HEAD -> main, origin/main)
Author:     Иван Иванов <ivan@example.com>
AuthorDate: Mon Jun 1 12:00:00 2026 +0300
Commit:     Пётр Петров <petr@example.com>
CommitDate: Mon Jun 1 14:00:00 2026 +0300

    Add app.py

diff --git a/app.py b/app.py
...
```

## 3. Зачем нужно это разделение

Это особенно важно для проектов с открытым исходным кодом (Open Source).

Типичный сценарий: разработчик хочет внести изменения в чужой проект на GitHub, но у него нет прав на запись в репозиторий. Он доставляет свои изменения одним из двух способов:

**Fork + Pull Request** — Иван создаёт форк (свою копию чужого репозитория на GitHub), вносит изменения и отправляет Pull Request — запрос к владельцу принять его изменения. Владелец проверяет код и нажимает "Merge". GitHub автоматически записывает Ивана как автора, а владельца как коммиттера.

**Патч** — Иван создаёт `.patch` файл из своего коммита и отправляет его владельцу (по email, в мессенджере и т.д.). Владелец применяет патч командой `git am` — автор из патча сохраняется автоматически.

> Fork, Pull Request и `git am` разберём подробно в отдельных темах.

**Признание заслуг** — важно сохранять информацию об исходном авторе изменений. Человек написал код, и история должна это отражать.

**Ответственность** — если в коде обнаружится проблема, сразу понятно к кому обратиться за разъяснениями.

## 4. Управление данными автора

Git позволяет вручную указывать автора при коммите:

```bash
# Изменить автора при коммите
git commit --author="Иван Иванов <ivan@example.com>" -m "Add feature"

# Изменить дату автора
git commit --date="2026-01-01T12:00:00" -m "Add feature"
```

При использовании этих флагов меняется только информация об **авторе** — коммиттером останешься ты (текущий пользователь) и дата коммита будет текущей.

С помощью переменных окружения можно переписать вообще все метаданные коммита. Это часто применяется в скриптах автоматизации (CI/CD деплои, зеркалирование репозиториев):

```bash
# Полная подмена автора и коммиттера
GIT_AUTHOR_NAME="Иван Иванов" \
GIT_AUTHOR_EMAIL="ivan@example.com" \
GIT_AUTHOR_DATE="2026-01-01T12:00:00" \
GIT_COMMITTER_NAME="Пётр Петров" \
GIT_COMMITTER_EMAIL="petr@example.com" \
GIT_COMMITTER_DATE="2026-01-01T12:00:00" \
git commit -m "Add feature from automation script"
```

## 5. Поведение при rebase и cherry-pick

> `rebase` и `cherry-pick` — это команды перемещения коммитов, которые будут разобраны в отдельных темах. Пока важно запомнить как они работают с автором и коммиттером.

Когда ты копируешь или перемещаешь чужие коммиты через `rebase` или `cherry-pick`:

- **Автор** — остаётся прежним. Человек написал код — он и остаётся автором.
- **Коммиттер** — меняется на тебя, так как именно ты инициировал операцию записи этих изменений в текущую ветку.

```
Оригинальный коммит:
  Author:    Иван Иванов
  Committer: Иван Иванов

После rebase/cherry-pick тобой:
  Author:    Иван Иванов   ← не изменился
  Committer: Пётр Петров   ← изменился на тебя
```
