## 1. Что такое ветка

Ветка (branch) — это независимая линия разработки внутри одного репозитория: коммиты, сделанные в одной ветке, не появляются автоматически в других. У каждой ветки — своя последовательность изменений, отдельная от остальных.

Технически ветка — не копия файлов и не отдельная папка с проектом, а указатель на конкретный коммит. Когда создаётся новая ветка, Git не копирует историю — он просто запоминает точку, от которой начинается отдельная линия разработки. Каждый новый коммит в этой ветке продолжает цепочку от предыдущего, а указатель ветки сдвигается вперёд вместе с ним.

Смысл в изоляции. Без веток любое изменение сразу попадает в общую историю проекта: экспериментальный код, недоделанная фича или рискованный рефакторинг оказываются рядом со стабильным, рабочим кодом. Ветка решает эту проблему — можно пробовать, ломать, переписывать, и всё это происходит в отдельном потоке, не задевая основной код, пока изменения не будут готовы к слиянию. Это же свойство позволяет нескольким разработчикам работать параллельно: каждый — в своей ветке, без риска затереть чужие правки.

## 2. Ветка master и текущая ветка

При первом коммите в новом репозитории Git автоматически создаёт ветку с именем `master` (в GitHub и многих современных инструментах по умолчанию используется имя `main` — это настраивается и не имеет технического значения, разница только в названии). Отдельной команды для создания этой ветки не требуется: она появляется сама, как только в истории есть хотя бы один коммит. По негласному соглашению именно в этой ветке хранится стабильный, готовый к использованию код проекта, а не черновики и эксперименты.

Текущая ветка — та, на которой ты находишься в конкретный момент. Git отслеживает это через служебный указатель `HEAD`: он указывает на ветку, активную прямо сейчас, а через неё — на последний коммит этой ветки. Переключение между ветками — не просто пометка «теперь я работаю здесь». Вместе с активной веткой меняется и содержимое рабочей директории: файлы приводятся к тому состоянию, которое соответствует последнему коммиту выбранной ветки. Переключился на другую ветку — увидел другой набор файлов, ровно тот, что был закоммичен там.

## 3. Базовые операции с ветками

**Переключение.** Механика уже описана выше — здесь остаётся только команда: `git switch <имя>` (в старых версиях и по привычке часто встречается `git checkout <имя>`).

**Создание ветки.** Новая ветка нужна, когда хочется начать что-то отдельно от текущей работы, не трогая её. Команда `git branch <имя>` создаёт такую ветку, но не переключает на неё — активной остаётся прежняя (`HEAD` по-прежнему указывает на неё же), а новый указатель просто появляется рядом (в `refs/heads/`), на том же коммите, где ты сейчас находишься. Поскольку следом почти всегда переключаются, чаще пользуются объединённым вариантом — `git switch -c <имя>`.

**Слияние.** Когда работа в отдельной ветке закончена и её пора вернуть в общую историю, используется `git merge`. Классический сценарий: фича в ветке `feature` готова и должна попасть в `master` — переключаешься на `master` и выполняешь `git merge feature`. Git добавляет всё, что накопилось в `feature`, поверх истории `master`; если за это время никто не менял те же строки в `master`, слияние проходит автоматически, а если менял — возникает конфликт, и Git ждёт, что ты укажешь правильный вариант вручную.

**Удаление ветки.** Когда ветка сделала своё дело — слита или оказалась неудачной идеей, — держать её дальше смысла нет: старые ветки только захламляют список. Убирается ветка командой `git branch -d <имя>`; Git сначала проверит, что она уже слита, и откажется удалять, если в ней остались незалитые изменения. Обойти эту проверку можно флагом `-D`, но тогда ответственность за то, что изменения точно не нужны, — на тебе.

## 4. Рабочие процессы: тематические и релизные ветки

**Тематические ветки (topic branches).** Для каждой новой задачи или фичи заводится отдельная ветка, например `feature-auth`, а не прямая работа в `master`. Пока фича не готова, `master` о ней не знает. Когда работа закончена и протестирована, ветку сливают в `master` и удаляют — она была временной. Если идея не сработала, удаляют без слияния, на `master` это не влияет. Подход удобен в команде: разработчики ведут параллельные ветки, не мешая друг другу, но могут посмотреть код коллеги.

**Релизные ветки (release branches).** Поддерживают несколько версий одновременно — и здесь `master` уже не прод, а черновик следующей версии. Жизненный цикл обычно выглядит так:

1. Команда разрабатывает в `master`.
2. Версию решают выпустить — от `master` отпочковывают отдельную ветку, например `v1.0`, и именно её отдают клиентам.
3. `master` продолжает жить своей жизнью: туда льётся новый функционал для будущей `v2.0`. `v1.0` в это время просто работает у клиентов, ничего нового не получая.
4. Через какое-то время в `v1.0` находят баг.
5. Баг чинят не в `v1.0`, а в `master` — раз `v1.0` ответвилась от него, баг почти наверняка есть и в текущей разработке тоже, и его всё равно нужно поправить, чтобы он не всплыл в `v2.0`.
6. Тот же коммит с исправлением точечно копируют в `v1.0` через cherry-pick. Саму ветку `master` целиком в `v1.0` не сливают — иначе вместе с фиксом туда утекут и недоделанные фичи.

Отличие между подходами — в направлении и сроке жизни. Тематическая ветка сливается в `master` и исчезает. Релизная ветка, наоборот, ответвляется от `master` и живёт отдельно — иногда месяцами, — никогда не сливаясь обратно.

## 5. Перенос отдельных коммитов: cherry-pick

Одна и та же проблема нередко требует исправления сразу в нескольких ветках. Классический пример связан как раз с релизными ветками: баг нашли и исправили в `master`, но пользователям версии 1.0 тоже нужно это исправление. Слить `master` в `v1.0` целиком не вариант — вместе с багфиксом туда попадёт и весь остальной новый функционал, которого в релизной ветке быть не должно.

Для таких случаев есть cherry-pick — перенос одного конкретного коммита из одной ветки в другую, без остальной истории. Команда применяет коммит на текущую ветку, поэтому сначала переключаются на неё — `git switch v1.0`, — а затем выполняют `git cherry-pick <хеш коммита>`: берёт нужный коммит (например, из `master`, по хешу) и применяет его поверх `v1.0`. Получившийся коммит на `v1.0` — новый, со своим хешем, хотя изменения в нём те же самые.

## 6. Методологии ветвления

Git не навязывает конкретный способ работы с ветками — сам по себе он одинаково поддерживает и тематические, и релизные ветки, а какую стратегию использовать (или использовать ли обе сразу), решает команда или проект.

Есть проекты, где в ходу только тематические ветки — например, небольшие команды без необходимости поддерживать несколько версий одновременно. Есть проекты, где используются только релизные ветки. А есть и комбинация обоих подходов — на этом принципе построена, например, методология Git Flow, одна из самых известных схем ветвления.
