## 1. Mental model

Прежде чем погружаться в команды, нужно держать в голове архитектурную картину. Это то, что отличает Middle от Junior на собесе — не знание флагов, а понимание как всё связано.

Всё что происходит на Linux-сервере — это три слоя:

```
┌──────────────────────────────────────────────────────┐
│  ПРИЛОЖЕНИЯ                                          │
│  nginx, postgres, python app, redis, ...             │
│  Каждое — один или несколько процессов               │
├──────────────────────────────────────────────────────┤
│  SYSTEMD (PID 1)                                     │
│  Менеджер жизненного цикла сервисов                  │
│  Запускает, перезапускает, логирует, изолирует       │
├──────────────────────────────────────────────────────┤
│  ЯДРО LINUX                                          │
│  Планировщик CPU · fd и сокеты · cgroups             │
│  Сигналы · Виртуальная память · Сеть                 │
└──────────────────────────────────────────────────────┘
```

Четыре абстракции которые нужно понимать насквозь:

| Абстракция | Одна фраза | Почему важно |
|-----------|-----------|-------------|
| **Процесс** | Контейнер ресурсов с PID, памятью, fd и cgroup | Единица изоляции и управления |
| **fd (файловый дескриптор)** | Число — ссылка на любой открытый ресурс ОС | Файлы, сокеты, пайпы — всё одна абстракция |
| **Сигнал** | Асинхронное уведомление процессу от ядра или другого процесса | Единственный стандартный способ управлять процессом извне |
| **cgroup** | Группа процессов с общими лимитами ресурсов | Основа изоляции Docker, Kubernetes, systemd |

> **Про RAM:** RAM (Random Access Memory) — это **оперативная память** (ОЗУ). В этом документе термин RAM используется как синоним «оперативки» — быстрая энергозависимая память в которой хранятся запущенные программы и их данные. В отличие от диска (SSD/HDD) — в 1000+ раз быстрее, но теряет содержимое при выключении питания.

Ключевые связи:

```
Процесс
  ├── открывает fd  →  файлы, TCP-сокеты, unix-сокеты, пайпы (всё одно)
  ├── принадлежит cgroup  →  ядро ограничивает CPU / RAM / I/O
  ├── имеет ulimits  →  ядро ограничивает количество fd, процессов
  └── управляется systemd  →  unit файл, journald, автоперезапуск

LimitNOFILE ограничивает суммарно:
  открытые файлы + TCP-соединения + unix-сокеты + пайпы = всё через fd

systemd при остановке сервиса:
  SIGTERM → всем процессам cgroup
  ждёт TimeoutStopSec
  SIGKILL → всем оставшимся
  Ни один дочерний процесс не выживет — это гарантия ядра
```

## 2. Процессы

### Что такое процесс

Процесс — это не просто «запущенная программа». Точнее: это **изолированный контейнер ресурсов** который ядро создаёт когда вы запускаете программу. Ядро выделяет процессу:

- **PID** — уникальный числовой идентификатор (Process ID)
- **Виртуальное адресное пространство памяти** — процесс видит свою память и не может напрямую читать память другого процесса
- **Таблицу файловых дескрипторов** — список всего что процесс открыл
- **Учётные данные** — от имени какого UID/GID он работает
- **cgroup** — к какой группе ограничений принадлежит

Каждый процесс кроме первого имеет **родителя (PPID)**. Это дерево. PID 1 — всегда `systemd`, он запускает всё остальное. Если PID 1 умирает — ядро паникует и система падает.

```bash
# посмотреть дерево процессов с PID
pstree -p

# посмотреть все процессы со статусами
ps -eo pid,ppid,stat,ni,user,cmd --sort=ppid

# посмотреть всё что ядро знает о конкретном процессе
# /proc/<PID>/ — это не папка на диске, это виртуальная ФС
# ядро генерирует её содержимое на лету при каждом чтении
ls /proc/$(pgrep -o nginx)/
```

### Атрибуты процесса и где их смотреть

| Атрибут | Где смотреть | Что показывает |
|---------|-------------|----------------|
| PID, PPID, UID | `cat /proc/<PID>/status` | Идентификаторы |
| Состояние | `ps -o stat` или `cat /proc/<PID>/status \| grep State` | R/S/D/Z/T |
| Приоритет nice | `ps -o ni`, `top` колонка NI | -20 до +19 |
| vruntime / вес CFS | `cat /proc/<PID>/sched` | Виртуальное время выполнения, вес, кол-во переключений |
| Cgroup | `cat /proc/<PID>/cgroup` | К какой cgroup принадлежит |
| Ulimits | `cat /proc/<PID>/limits` | Реальные лимиты процесса |
| Команда запуска | `cat /proc/<PID>/cmdline \| tr '\0' ' '` | Как был запущен |
| Переменные окружения | `cat /proc/<PID>/environ \| tr '\0' '\n'` | Env процесса |
| В каком kernel call завис | `cat /proc/<PID>/wchan` | Актуально для состояния D |
| Открытые fd | `ls -la /proc/<PID>/fd/` | Что открыто |
| OOM приоритет | `cat /proc/<PID>/oom_score` | 0–1000, выше = убьют первым |

### Состояния процессов

Ядро в каждый момент знает в каком состоянии находится каждый процесс. Это не абстракция — это реальный флаг в структуре `task_struct` внутри ядра.

| Символ | Название | Что происходит |
|--------|----------|----------------|
| `R` | Running / Runnable | Выполняется прямо сейчас или стоит в очереди планировщика |
| `S` | Sleeping (interruptible) | Ждёт события (таймер, I/O, сигнал). Можно разбудить сигналом |
| `D` | Disk Sleep (uninterruptible) | Ждёт завершения I/O операции. **Нельзя прервать никаким сигналом, включая SIGKILL** |
| `Z` | Zombie | Процесс завершил работу, но запись о нём ещё не убрана из таблицы процессов |
| `T` | Stopped | Заморожен сигналом SIGSTOP |
| `I` | Idle | Бездействующий поток ядра (с версии 4.14+) |

Дополнительные флаги в колонке STAT:

| Флаг | Значение |
|------|---------|
| `s` | Session leader — процесс является лидером сессии (например `bash`) |
| `l` | Многопоточный процесс |
| `+` | Процесс на переднем плане (foreground) |
| `<` | Высокий приоритет (nice < 0) |
| `N` | Низкий приоритет (nice > 0) |

```bash
# найти зомби
ps aux | awk '$8 == "Z"'

# найти процессы в состоянии D — признак I/O проблем
ps aux | awk '$8 ~ /^D/'

# посмотреть состояние конкретного процесса
cat /proc/$(pgrep -o nginx)/status | grep -E "State|Pid|PPid"
```

### Состояние Z — Zombie подробно

Когда процесс завершается (вызывает `exit()`), он не исчезает мгновенно. Ядро переводит его в состояние Zombie и оставляет минимальную запись в таблице процессов — код завершения и статистику. Это сделано намеренно: **родитель должен забрать результат** через системный вызов `wait()`.

Механизм такой:
1. Дочерний процесс вызывает `exit(1)` — сигнализирует что завершился с кодом 1
2. Ядро переводит его в Zombie, сохраняет код завершения
3. Ядро отправляет родителю сигнал SIGCHLD — «твой ребёнок умер»
4. Родитель вызывает `wait()` — считывает код завершения
5. Ядро окончательно убирает запись — зомби исчезает

Если родитель **не вызывает `wait()`** — зомби копятся. Каждый зомби не потребляет CPU и память, но занимает PID и строку в таблице процессов. Когда таблица переполняется — создать новые процессы невозможно, система перестаёт работать. Это всегда баг в родительском процессе.

#### Максимальное количество записей в таблице процессов

Ядро ограничивает максимальный PID параметром `pid_max`. Это одновременно и максимальное количество одновременно существующих процессов в системе (включая зомби).

```bash
# посмотреть текущий лимит
cat /proc/sys/kernel/pid_max
# 32768    ← дефолт на 32-битных и старых системах
# 4194304  ← дефолт на 64-битных системах (Linux 3.3+)
```

Как работает:
- PID выдаются циклически от 1 до `pid_max`
- Каждый зомби держит занятым один PID
- При достижении `pid_max` ядро пытается переиспользовать освободившиеся PID
- Если **все** PID до `pid_max` заняты (живые процессы + зомби) — `fork()` возвращает ошибку `EAGAIN`, создать новый процесс невозможно
- Типичный симптом: `bash: fork: retry: Resource temporarily unavailable`

```bash
# посмотреть сколько процессов сейчас в системе
ps aux | wc -l

# сколько зомби
ps aux | awk '$8 == "Z"' | wc -l

# изменить лимит (временно, до перезагрузки)
echo 65536 > /proc/sys/kernel/pid_max

# постоянно — через sysctl
echo "kernel.pid_max = 65536" >> /etc/sysctl.conf
sysctl -p
```

> ⚠️ Увеличение `pid_max` — это **обходной путь**, не решение. Правильный путь — найти и починить родительский процесс который не вызывает `wait()`. Увеличение лимита только отсрочит проблему.

```bash
# убить зомби нельзя — он уже мёртв
# нужно убить родителя — тогда зомби усыновит systemd и вызовет wait()
# почему это помогает: systemd (PID 1) всегда корректно вызывает wait() для
# всех усыновлённых процессов, поэтому зомби немедленно исчезают
kill -9 $(ps -o ppid= -p <zombie_pid>)

# проверить сколько зомби в системе
ps aux | awk '$8 == "Z"' | wc -l
```

### Состояние D — Uninterruptible Sleep

Когда процесс инициирует операцию I/O (например читает с диска), ядро переводит его в состояние D. В этом состоянии процесс держит **блокировку ядра** — специальную структуру которая говорит «я сейчас работаю с этим ресурсом, никто другой не трогай». Именно поэтому SIGKILL не работает: ядро не может убить процесс пока тот держит блокировку — это привело бы к повреждению данных.

Короткое время в D — это нормально. Проблема когда процессов в D много или они зависают надолго. Типичные причины:

- Зависший NFS mount — процесс ждёт ответа от сетевой ФС которая не отвечает
- Умирающий жёсткий диск — I/O запросы уходят в никуда
- Переполненная очередь I/O — диск не успевает обработать запросы

```bash
# в каком kernel call завис процесс
cat /proc/<PID>/wchan
# примеры: nfs4_wait_on_commit, jbd2_log_wait_commit, pipe_wait

# ошибки диска или NFS в системном журнале
dmesg | tail -30
journalctl -k --since "10 min ago"

# здоровье диска
smartctl -a /dev/sda
```


### CPU планировщик — CFS

#### Что такое CFS и как его «посмотреть»

**CFS (Completely Fair Scheduler)** — это **механизм внутри ядра Linux**, а не отдельный процесс или сервис. Его нельзя найти через `ps`, нет сервиса `cfs.service`, нет бинарника. CFS — это код который выполняется внутри ядра каждый раз когда нужно решить: «какой процесс запустить следующим на этом CPU-ядре?».

Увидеть работу CFS можно косвенно — через метрики которые он ведёт:

```bash
# детальная информация планировщика о конкретном процессе (включая vruntime)
cat /proc/<PID>/sched
# se.vruntime          :   4832167.123456  ← виртуальное время
# se.sum_exec_runtime  :    987654.321000  ← реальное время на CPU
# se.load.weight       :          1024     ← вес (определяется nice)

# краткая статистика: время на CPU / время в ожидании / кол-во запусков
cat /proc/<PID>/schedstat
# 1234567890  987654321  42

# посмотреть приоритеты всех процессов
top   # колонки: NI = nice, PR = реальный приоритет планировщика

# контекстные переключения в vmstat — признак активной работы CFS
vmstat 1 3
# cs (context switches) — сколько раз планировщик переключал процессы
```

#### Как CFS принимает решения — vruntime

CFS отслеживает `vruntime` (virtual runtime — виртуальное время выполнения) для каждого процесса. Это **учётный счётчик**: сколько «нормализованного» времени CPU уже потратил этот процесс.

#### Можно ли посмотреть vruntime?

Да, `vruntime` можно увидеть напрямую — в отличие от самого CFS, это просто число которое ядро хранит для каждого процесса и выдаёт через `/proc`:

```bash
# /proc/<PID>/sched — детальная информация планировщика о процессе
cat /proc/$(pgrep -o nginx)/sched

# пример вывода (выборочно):
# nginx (1234, #threads: 1)
# -------------------------------------------------------------------
# se.vruntime                          :      4832167.123456   ← вот он
# se.sum_exec_runtime                  :       987654.321000   ← реальное время на CPU (мс)
# se.nr_involuntary_switches           :            12345      ← вытеснен планировщиком
# se.nr_voluntary_switches             :            67890      ← сам отдал CPU (ждал I/O)
# se.load.weight                       :             1024      ← вес (nice 0 = 1024)
```

Что означают ключевые поля:

| Поле | Что показывает |
|------|---------------|
| `se.vruntime` | Виртуальное время — чем больше, тем «дальше» процесс от следующего запуска |
| `se.sum_exec_runtime` | Сколько реального времени CPU потратил процесс за всё время жизни (нс) |
| `se.nr_voluntary_switches` | Сколько раз процесс **сам** отдал CPU (уснул в ожидании I/O, сигнала) |
| `se.nr_involuntary_switches` | Сколько раз CFS **принудительно** вытеснил процесс (истёк квант времени) |
| `se.load.weight` | Вес процесса — зависит от nice, влияет на скорость роста vruntime |

```bash
# сравнить vruntime у двух конкурирующих процессов
# тот у кого меньше — получит CPU следующим
cat /proc/$(pgrep -o worker1)/sched | grep "se.vruntime"
cat /proc/$(pgrep -o worker2)/sched | grep "se.vruntime"

# посмотреть у всех процессов сразу
for pid in $(ps -eo pid --no-headers); do
  vrt=$(cat /proc/$pid/sched 2>/dev/null | grep "se.vruntime" | awk '{print $3}')
  cmd=$(cat /proc/$pid/comm 2>/dev/null)
  echo "$vrt $pid $cmd"
done | sort -n | head -10
# процессы с наименьшим vruntime — следующие кандидаты на CPU
```

> **Важно:** абсолютное значение `vruntime` само по себе мало что говорит — оно монотонно растёт с момента запуска процесса. Смысл имеет только **разница** между процессами: кто «отстал» (меньший vruntime) — тот получит CPU следующим. Сравнивать имеет смысл только процессы которые конкурируют за одно CPU-ядро.

Механизм выбора:
1. У каждого процесса есть `vruntime` — монотонно растущее число
2. CFS хранит все «готовые к выполнению» процессы в структуре red-black tree, отсортированной по `vruntime`
3. Всегда запускается процесс с **наименьшим** `vruntime` — тот кто меньше всего работал
4. После кванта времени `vruntime` процесса увеличивается и он уходит обратно в дерево

```
Дерево процессов (сортировка по vruntime):

  vruntime:  100    150    200    250    300
             [A]    [C]    [B]    [D]    [E]
              ↑
         CFS выбирает этот — он работал меньше всех

  → A получает квант CPU, его vruntime становится 160
  → A возвращается в дерево

  vruntime:  150    160    200    250    300
             [C]    [A]    [B]    [D]    [E]
              ↑
         Теперь следующим идёт C
```

`vruntime` нормализуется по весу процесса: у процесса с `nice -20` (высокий вес) `vruntime` растёт медленнее — поэтому он чаще оказывается «наименее запущенным» и получает больше CPU.

#### nice — мягкий приоритет через вес

**nice** влияет на **вес процесса** в CFS, а не на жёсткий лимит. Чем ниже nice — тем больший вес, тем медленнее растёт `vruntime`, тем чаще процесс выбирается планировщиком:

```
nice -20  →  вес ~88761  (≈ в 10 раз больше CPU чем у nice 0)
nice   0  →  вес   1024  (дефолт)
nice +19  →  вес     15  (получает минимум при конкуренции)
```

Важно: при **свободном CPU** процесс с `nice +19` всё равно получит 100% — конкуренции нет, некому отдавать предпочтение. `nice` имеет значение только когда несколько процессов одновременно хотят CPU.

```bash
# запустить с низким приоритетом — не мешать продакшену
nice -n 19 python3 backup.py

# изменить приоритет запущенного процесса
renice -n 10 -p <PID>
renice -n -5 -p <PID>   # отрицательный nice — только root

# посмотреть приоритеты
top   # колонки: NI = nice, PR = реальный приоритет планировщика
ps -eo pid,ni,cmd --sort=ni
```

#### CPUQuota — жёсткий лимит через cgroup

`CPUQuota` — это совсем другой механизм, никак не связанный с `nice`. Это **жёсткий лимит** ресурсов через cgroup, а не изменение приоритета.

```
nice +19:
┌─────────────────────────────────────────────┐
│  Если CPU свободен → процесс берёт 100%     │
│  Если CPU занят    → процесс получает мало  │
│  Работает через: vruntime и вес             │
└─────────────────────────────────────────────┘

CPUQuota=50%:
┌─────────────────────────────────────────────┐
│  CPU свободен или нет — НЕВАЖНО             │
│  Процесс получит не более 50% одного ядра   │
│  Остальное просто простаивает               │
│  Работает через: cgroup cpu.max             │
└─────────────────────────────────────────────┘
```

```bash
# задать CPUQuota для сервиса
# В unit файле:
# CPUQuota=50%    ← максимум 0.5 ядра
# CPUQuota=200%   ← максимум 2 ядра (на многоядерном)

# применить без рестарта
systemctl set-property myapi.service CPUQuota=50%

# проверить
systemctl show myapi | grep CPUQuota
# CPUQuotaPerSecUSec=500ms  ← 50% одного ядра в секунду
```

`CPUQuota=200%` означает «не более 2 полных ядер» — это нужно когда приложение многопоточное (например gunicorn с 4 воркерами), и вы хотите ограничить суммарное потребление CPU всем сервисом.


### OOM Killer

Когда физическая RAM исчерпана и своп тоже, ядро запускает **OOM Killer (Out of Memory Killer)**. Он анализирует все процессы, вычисляет `oom_score` для каждого (0–1000, выше = хуже) и убивает процесс с наибольшим score. Score учитывает: сколько RAM потребляет, как давно работает, является ли системным.

```bash
# посмотреть score любого процесса
cat /proc/$(pgrep -o nginx)/oom_score

# защитить критический процесс (score_adj от -1000 до +1000)
echo -1000 > /proc/$(pgrep -o postgres)/oom_score_adj
# -1000 = никогда не убивать, +1000 = убить первым
# Почему помогает: OOM Killer прибавляет oom_score_adj к вычисленному score.
# При -1000 итоговый score всегда <= 0 — OOM Killer пропустит этот процесс
# и выберет другую жертву. Критичные сервисы (postgres, redis) защищают так.

# определить был ли процесс убит OOM Killer
journalctl -k | grep -i "out of memory\|killed process\|oom_kill"
dmesg | grep -i "oom"
```

```ini
# в unit файле systemd
OOMScoreAdjust=-500
```

## 3. I/O

### Что такое I/O

**I/O (Input/Output, ввод-вывод)** — это любая операция обмена данными между процессором/памятью и внешним устройством. Когда процессор работает — он оперирует данными в RAM. Но данные нужно откуда-то взять и куда-то записать. Вот это и есть I/O.

Виды I/O с которыми сталкивается DevOps:

| Тип I/O | Что происходит | Примеры |
|---------|---------------|---------|
| **Disk I/O** | Чтение/запись на жёсткий диск или SSD | Nginx читает статику, PostgreSQL пишет WAL, приложение пишет логи |
| **Network I/O** | Отправка/приём пакетов по сети | HTTP запросы, запросы к БД, Redis |
| **Memory-mapped I/O** | Файл отображён в память — операции с памятью = операции с файлом | Базы данных, JVM |
| **Pipe I/O** | Данные передаются между процессами через пайп | `ps aux \| grep nginx` |

### Почему I/O — главный bottleneck

CPU работает в наносекундах. Диск — в миллисекундах. Это разница в **миллион раз**. Даже быстрый NVMe SSD в 1000 раз медленнее RAM.

```
Время доступа:
  Регистры CPU     : 0.3 ns
  L1 кэш CPU       : 1 ns
  RAM              : 100 ns
  SSD (NVMe)       : 100 000 ns = 0.1 ms
  HDD              : 10 000 000 ns = 10 ms
  Сеть (LAN)       : 500 000 ns = 0.5 ms
```

Когда процессу нужны данные с диска — он инициирует I/O запрос и переходит в состояние **D (Disk Sleep)**. CPU в это время свободен, но процесс не может продолжить работу пока данные не придут. Это и объясняет почему **высокий Load Average при низком CPU** = проблема с диском.

### Синхронный vs асинхронный I/O

**Синхронный I/O** (blocking): процесс вызывает `read()`, ядро переводит его в состояние D, данные читаются с диска, процесс возобновляется. Всё время ожидания — простой.

**Асинхронный I/O** (non-blocking): процесс говорит ядру «начни читать, я занимаюсь другим, уведоми когда готово». Пока идёт I/O — процесс делает другую работу. Nginx, Node.js, PostgreSQL используют именно такой подход для высокой производительности.

```bash
# посмотреть статистику I/O операций
iostat -x 1

# вывод:
# Device  r/s   w/s  rkB/s  wkB/s  await  %util
# sda     5.0  50.0   40.0  400.0   2.50   15.0
#
# r/s, w/s    — операций чтения/записи в секунду
# await       — среднее время ожидания I/O операции (мс)
# %util       — % времени диск был занят (100% = диск перегружен)
```

## 4. Файловые дескрипторы (fd)

### Что такое fd и зачем он нужен

**Файловый дескриптор (fd, file descriptor)** — это просто **целое число**, которое ядро выдаёт процессу когда тот открывает какой-либо ресурс.

Зачем это нужно? Представьте: вашему приложению нужно читать файл `/var/log/app.log`. Чтобы читать файл, нужно знать его расположение на диске, права доступа, текущую позицию чтения, режим открытия (только чтение, запись, и т.д.). Хранить всё это в приложении — неудобно и небезопасно. Вместо этого ядро:

1. Открывает файл, проверяет права, создаёт внутренний объект «открытый файл»
2. Добавляет его в таблицу открытых файлов процесса
3. Возвращает приложению просто число — индекс в этой таблице

Теперь чтобы читать файл, приложение просто говорит ядру: «читай из fd номер 5». Ядро само знает что за этим числом.

```
Приложение вызывает:          Ядро возвращает:
─────────────────────────────────────────────────
open("/var/log/app.log")  →   fd = 3
open("/etc/nginx.conf")   →   fd = 4
socket(TCP)               →   fd = 5
socket(Unix)              →   fd = 6
pipe()                    →   fd = 7, 8
```

### Три стандартных fd

Каждый процесс при запуске уже имеет три открытых fd:

| Номер | Имя | Что это | Пример |
|-------|-----|---------|--------|
| `0` | stdin | Стандартный ввод | Ввод с клавиатуры, данные из пайпа |
| `1` | stdout | Стандартный вывод | `echo "hello"` пишет в fd 1 |
| `2` | stderr | Стандартный вывод ошибок | Сообщения об ошибках программы |

Именно поэтому работает `2>/dev/null` — перенаправить fd 2 (stderr) в `/dev/null`.

### Посмотреть fd процесса на практике

```bash
# посмотреть все открытые fd nginx
# /proc/<PID>/fd/ — это директория, каждый файл в ней это символическая ссылка
# имя файла = номер fd, ссылка указывает на то что открыто
ls -la /proc/$(pgrep -o nginx)/fd/

# пример вывода:
# lrwx------ 0 -> /dev/pts/0              ← stdin (терминал)
# lrwx------ 1 -> /dev/pts/0              ← stdout
# lrwx------ 2 -> /dev/pts/0              ← stderr
# lr-x------ 3 -> /etc/nginx/nginx.conf   ← открытый конфиг
# lrwx------ 4 -> socket:[98765]          ← TCP сокет (слушает :80)
# lrwx------ 5 -> socket:[98766]          ← соединение от клиента
# lrwx------ 6 -> socket:[98767]          ← ещё одно соединение
# l-wx------ 7 -> /var/log/nginx/access.log

# сколько fd открыто прямо сейчас
ls /proc/$(pgrep -o nginx)/fd | wc -l

# более удобный способ — lsof (list open files)
lsof -p $(pgrep -o nginx)

# пример вывода lsof:
# COMMAND  PID  USER  FD  TYPE  DEVICE  SIZE  NODE  NAME
# nginx   1234  root  3r  REG   8,1    4096   123  /etc/nginx/nginx.conf
# nginx   1234  root  4u  IPv4  98765        TCP   *:80 (LISTEN)
# nginx   1234  root  5u  IPv4  98766        TCP   1.2.3.4:80->5.6.7.8:54321
```

Колонка `FD` в `lsof`:
- `r` — открыт на чтение
- `w` — открыт на запись
- `u` — открыт на чтение и запись
- `mem` — отображён в память (memory-mapped)

Колонка `TYPE`:
- `REG` — обычный файл
- `DIR` — директория
- `IPv4` / `IPv6` — сетевой сокет
- `unix` — unix-сокет
- `FIFO` — пайп

### Почему fd это центральная абстракция

Весь смысл fd в том что **для ядра нет разницы** что открыто — файл, TCP соединение, unix-сокет или пайп. Одни и те же системные вызовы работают с любым fd:

```
read(fd, buffer, size)   — прочитать данные
write(fd, buffer, size)  — записать данные
close(fd)                — закрыть
```

Именно поэтому `LimitNOFILE` (лимит на количество открытых файлов) одновременно ограничивает и файлы, и сетевые соединения, и сокеты — потому что всё это fd.

```bash
# посмотреть реальный лимит fd запущенного процесса
cat /proc/$(pgrep -o nginx)/limits | grep "open files"
# Max open files  65536  65536  files
# ─────────────── ──────────────
#                 soft   hard

# системная статистика fd по всей системе
cat /proc/sys/fs/file-nr
# 12480  0  2097152
# ─────     ───────
# открыто   системный максимум
```

### Что происходит когда fd исчерпаны

Когда процесс достигает лимита `nofile`, любая попытка открыть новый файл или принять новое соединение возвращает ошибку `EMFILE (Too many open files)`:

```
[error] 1234#1234: accept() failed (24: Too many open files)
```

```bash
# диагностика: лимит vs реальное количество
cat /proc/$(pgrep -o nginx)/limits | grep "open files"
# Max open files  1024  1024
ls /proc/$(pgrep -o nginx)/fd | wc -l
# 1023   ← почти достигли лимита!

# решение через systemd override
systemctl edit nginx
```
```ini
[Service]
LimitNOFILE=65536
```
```bash
systemctl daemon-reload && systemctl restart nginx
# Почему помогает: systemd передаёт новый лимит ядру через setrlimit() перед
# запуском процесса. Ядро теперь разрешает процессу держать открытыми до 65536 fd.
# При принятии нового соединения ядро проверяет: текущий_fd_count < nofile_limit.
# Раньше проверка на 1025-м соединении давала EMFILE, теперь — на 65537-м.

# ОБЯЗАТЕЛЬНО проверить что применилось — не верить на слово
cat /proc/$(pgrep -o nginx)/limits | grep "open files"
# Max open files  65536  65536  ← применилось
```

### Удалённый файл с открытым fd

Важная особенность: когда вы удаляете файл командой `rm`, ядро удаляет только **имя файла** из директории. Сами данные на диске остаются пока хоть один fd на этот файл открыт. Это означает что место **не освобождается** пока процесс не закроет fd.

```bash
# найти удалённые файлы которые ещё держат место
lsof | grep deleted

# пример вывода:
# nginx  1234  root  7w  REG  /var/log/nginx/access.log (deleted)  2.1G
#              ─────                                    ────────    ────
#              PID                                      удалён!     занимает 2GB!

# решение 1: graceful reload — nginx закроет и переоткроет логи
systemctl reload nginx
# Почему помогает: SIGHUP заставляет nginx выполнить reload. При этом nginx
# закрывает старые fd лог-файлов и открывает новые. Старый удалённый fd
# закрывается, ядро видит счётчик ссылок = 0, освобождает место на диске.

# решение 2: очистить файл через fd без перезапуска процесса
# это обнуляет файл прямо через открытый дескриптор
> /proc/1234/fd/7
# Почему помогает: truncate через /proc/PID/fd/N обнуляет файл через открытый
# дескриптор. Процесс продолжает писать в тот же fd, файл снова пустой.
# Место освобождается мгновенно. Только для логов — не для БД!
```

## 5. Сокеты

Сокеты тесно связаны с fd — это одна тема. Сокет — это просто fd на **коммуникационный канал**. Их два вида и они служат разным целям.

### TCP сокеты

**TCP сокет** — это fd на сетевое соединение через стек TCP/IP. Используется когда нужно общаться **между разными машинами** (или между процессами на одной машине через loopback).

Когда nginx принимает HTTP запрос — он вызывает `accept()`, ядро создаёт новый fd для этого соединения, и все данные запроса/ответа идут через этот fd. Когда соединение закрывается — fd закрывается.

```bash
# посмотреть все TCP соединения nginx с процессами
ss -tnp | grep nginx

# пример вывода:
# State   Recv-Q  Send-Q  Local Address:Port    Peer Address:Port  Process
# LISTEN  0       511     0.0.0.0:80             0.0.0.0:*          pid=1234
# ESTAB   0       0       10.0.0.1:80            10.0.0.2:54321     pid=1234
# ESTAB   0       4096    10.0.0.1:80            10.0.0.3:54322     pid=1234
```

Каждая строка ESTAB — это одно TCP соединение и один fd.

### Unix Domain сокеты

**Unix-сокет** — это fd на коммуникационный канал **внутри одной машины**. Выглядит как файл на диске (с типом `s`), но данные не пишутся на диск — они передаются напрямую через память ядра.

Преимущества перед TCP для локального взаимодействия:
- Быстрее (нет TCP overhead, нет сетевого стека)
- Безопаснее (права доступа как у файла, нет сетевого доступа)
- Ядро может передавать fd через unix-сокет между процессами

```bash
# найти unix-сокеты в системе
ls -la /run/
# srw-rw-rw- /run/docker.sock       ← Docker daemon
# srw-rw---- /run/postgresql/.s.PGSQL.5432  ← PostgreSQL
# srwxrwxrwx /run/redis/redis.sock   ← Redis

# посмотреть unix-сокеты через ss
ss -xnp

# пример конфига nginx → php-fpm через unix-сокет
# fastcgi_pass unix:/run/php/php8.1-fpm.sock;
# это быстрее чем fastcgi_pass 127.0.0.1:9000;
```

---

### Как работает TCP соединение между машинами

```
  КЛИЕНТ (10.0.0.2)                       СЕРВЕР (10.0.0.1)
  ────────────────                         ────────────────
  Приложение                               nginx / postgres

  socket() → fd=5                          socket() → fd=3
  connect(10.0.0.1:80)                     bind(:80)
       │                                   listen()
       │   ──── SYN ────────────────────→  │
       │   ←─── SYN-ACK ─────────────────  │  accept() → fd=4  (новый fd
       │   ──── ACK ────────────────────→  │  на это соединение)
       │                                   │
       │   ──── write(fd=5, "GET /") ────→ │  read(fd=4, buf)
       │                ↑                  │  [обработка запроса]
       │    данные через TCP стек          │  write(fd=4, "HTTP/1.1 200")
       │   ←─── read(fd=5, buf) ─────────  │
       │                                   │
       │   ──── close(fd=5) / FIN ───────→ │  close(fd=4)
       ↓                                   ↓

  Ядро: сетевой стек TCP/IP                Ядро: сетевой стек TCP/IP
  (checksums, ACK, retransmit,             (checksums, ACK, retransmit,
   flow control, congestion)               flow control, congestion)
       │                                        │
  NIC (сетевая карта)  ←── физическая сеть ─→  NIC (сетевая карта)
```

Ключевые моменты:
- `accept()` создаёт **новый fd** для каждого входящего соединения. fd на LISTEN сокете остаётся, он не используется для передачи данных
- Каждое ESTABLISHED соединение = один fd = одна строка в `ss -tnp`
- Сетевой стек TCP/IP в ядре незримо обеспечивает надёжность: подтверждения, повтор при потере пакетов, контроль потока

### Как PostgreSQL общается через Unix-сокет

```
  Приложение (Django, psycopg2)           PostgreSQL
  ─────────────────────────────           ──────────
  
  socket(AF_UNIX) → fd=5                  при запуске:
                                          bind("/var/run/postgresql/
  connect(                                     .s.PGSQL.5432")
   "/var/run/postgresql/                   listen()  → fd=3
    .s.PGSQL.5432")                            │
       │                                        │
       │   [данные идут через память ядра]      │  accept() → fd=7
       │   [НЕТ сетевого стека TCP/IP]          │
       │                                        │
       │  write(fd=5, "SELECT * FROM users")──→ │  read(fd=7, query)
       │                                        │  [выполняет SQL]
       │  read(fd=5, rows)  ←────────────────── │  write(fd=7, rows)
       │                                        │
       ↓                                        ↓

  /var/run/postgresql/.s.PGSQL.5432  ← файл на диске типа 's' (socket)
  Данные на диск НЕ ПИШУТСЯ — файл это просто адрес встречи
  Реальная передача: через кольцевой буфер в памяти ядра

  Скорость: в 2-5 раз быстрее чем TCP на localhost
  Причина: нет TCP overhead (заголовки, checksums, ACK, порты)
```

```bash
# убедиться что postgres слушает на unix-сокете
ss -xnp | grep postgres
# u_str LISTEN 0 128 /var/run/postgresql/.s.PGSQL.5432

# подключиться через unix-сокет явно
psql -h /var/run/postgresql -U postgres   # -h указывает путь к сокету

# подключиться через TCP (если postgres слушает на 127.0.0.1)
psql -h 127.0.0.1 -p 5432 -U postgres

# посмотреть все соединения к postgres
ss -xnp | grep postgres    # unix-сокеты
ss -tnp | grep postgres    # tcp соединения
```

### TCP vs Unix socket — когда что использовать

| Критерий | TCP сокет | Unix-сокет |
|----------|-----------|------------|
| Взаимодействие | Между машинами / локально | Только на одной машине |
| Скорость | Медленнее (overhead TCP стека) | Быстрее (прямая передача через память) |
| Безопасность | Доступен по сети | Контролируется правами файла |
| Настройка в nginx | `proxy_pass http://127.0.0.1:8000` | `proxy_pass unix:/run/app.sock` |
| Типичное применение | Микросервисы, внешний доступ | nginx↔php-fpm, nginx↔gunicorn на одном сервере |

```bash
# посмотреть все сокеты процесса (и TCP и Unix)
lsof -p $(pgrep -o nginx) | grep -E "IPv|unix"
```

## 6. TCP состояния

Каждое TCP соединение проходит через ряд состояний. Для DevOps важно уметь читать вывод `ss` и понимать что каждое состояние означает и почему его может быть много.

```bash
# сводка по всем состояниям
ss -s

# все TCP соединения с процессами
ss -tnp

# только listening порты
ss -lntp

# конкретное состояние
ss -tnp state TIME-WAIT
ss -tnp state CLOSE-WAIT
```

### Таблица состояний

| Состояние | Где | Что значит | Много = проблема? |
|-----------|-----|------------|-------------------|
| `LISTEN` | Сервер | Сокет слушает входящие соединения | Нет |
| `ESTABLISHED` | Оба | Активное соединение, данные передаются | Да, если утечка |
| `TIME_WAIT` | Кто закрыл первым | Ждёт 2×MSL (~60 сек) чтобы убедиться что все пакеты дошли | Да, исчерпание портов |
| `CLOSE_WAIT` | Кто закрыл вторым | Удалённая сторона закрыла, наше приложение ещё не вызвало `close()` | **Да, утечка в приложении** |
| `FIN_WAIT_2` | Кто закрыл первым | Отправил FIN, ждёт FIN от другой стороны | Зависшие соединения |
| `SYN_RECV` | Сервер | Получил SYN, отправил SYN-ACK, ждёт ACK | Да, SYN flood атака |

### TIME_WAIT — почему много и как лечить

`TIME_WAIT` возникает у той стороны которая **первой инициировала закрытие** соединения. Это нормальное поведение TCP — соединение висит в этом состоянии ~60 секунд чтобы «поздние» пакеты не перепутались с новыми соединениями.

**Проблема:** если nginx проксирует тысячи запросов в секунду на upstream и каждый раз создаёт новое TCP соединение — порты исчерпываются. Диапазон портов обычно 32768–60999 = ~28000 портов. При 1000 запросов/сек каждый в TIME_WAIT на 60 сек = 60 000 соединений в TIME_WAIT.

```bash
# диагностика
ss -s | grep TIME-WAIT
cat /proc/sys/net/ipv4/ip_local_port_range   # диапазон портов

# решение 1: keepalive соединения к upstream в nginx — главное решение
# upstream {
#     server 127.0.0.1:8000;
#     keepalive 32;    ← держать 32 переиспользуемых соединения
# }
# Почему помогает: nginx перестаёт создавать новое TCP соединение на каждый запрос.
# 32 соединения открываются один раз и переиспользуются тысячи раз.
# TIME_WAIT перестают накапливаться — соединения просто не закрываются.

# решение 2: разрешить повторное использование TIME_WAIT сокетов
sysctl net.ipv4.tcp_tw_reuse=1
# Почему помогает: ядро может переиспользовать TIME_WAIT порт для нового
# исходящего соединения если прошло достаточно времени (по timestamp).
# Расширяет эффективный пул портов без ожидания 60 секунд.
```

### CLOSE_WAIT — утечка соединений

`CLOSE_WAIT` — удалённая сторона закрыла соединение (прислала FIN), ядро уведомило приложение, но приложение **не вызвало `close(fd)`**. Соединение висит открытым со стороны нашего сервера.

Это **баг в приложении** — оно не закрывает соединения. Со временем исчерпает лимит fd и перестанет принимать новые соединения.

```bash
# диагностика
ss -tnp | grep CLOSE_WAIT

# смотрим сколько и от каких процессов
ss -tnp state CLOSE-WAIT | awk '{print $NF}' | sort | uniq -c | sort -rn
```

### Recv-Q у LISTEN сокета

```bash
ss -lntp | grep nginx
# State   Recv-Q  Send-Q  Local:Port
# LISTEN  0       511     0.0.0.0:80
# LISTEN  128     511     0.0.0.0:80  ← Recv-Q > 0 это плохо!
```

Если `Recv-Q > 0` у LISTEN сокета — новые соединения приходят быстрее чем nginx успевает их принять через `accept()`. Это либо перегрузка, либо нехватка worker процессов.

## 7. Производительность

### Load Average

**Load Average** — это среднее количество процессов которые либо активно выполняются (состояние R), либо ожидают завершения I/O (состояние D) за последние 1, 5 и 15 минут. Это **не процент загрузки CPU** — это очередь.

```bash
$ uptime
14:32:01 up 10 days, load average: 2.45, 1.87, 1.20
                                    1m    5m    15m

$ nproc   # количество логических ядер CPU
4
```

Нормально: Load Average ≤ количества CPU ядер.

```
4-ядерный сервер:
load: 2.00, 2.00, 2.00  → норма, 50% загрузка
load: 4.00, 4.00, 4.00  → 100%, всё занято, не перегружено
load: 8.00, 6.00, 4.00  → нагрузка РАСТЁТ — разбираться прямо сейчас
load: 4.00, 6.00, 8.00  → нагрузка СНИЖАЕТСЯ — проблема уходит
```

> ⚠️ Читать тренд справа налево: 15m → 5m → 1m. Если 1m > 15m — проблема нарастает.

**Диагностика: load высокий, CPU свободен** — это I/O:

```bash
top
# %Cpu: 5.0 us, 2.0 sy, 82.0 wa  ← 82% I/O wait!
# wa (iowait) = процент времени когда CPU простаивал ожидая I/O

iostat -x 1   # детальная статистика диска
iotop -b -n 3  # кто именно грузит диск
```

### vmstat — системная сводка за интервал

`vmstat` даёт моментальный срез состояния системы: CPU, память, swap, I/O — всё в одной строке.

```bash
vmstat 1 5   # каждую секунду, 5 раз
```

```
procs ───────── memory ─────────── swap ── io ──── sys ──── cpu ──────────
 r  b   swpd   free   buff  cache   si  so   bi   bo   in   cs  us sy id wa
 2  0      0 512000  48000 1024000   0   0    5   20  400  800  25  5 68  2
 0  8      0 128000  48000 1024000   0  50  800 5000 2000 3000   5  3  8 84
```

Расшифровка колонок:

| Колонка | Описание | Тревожно если |
|---------|----------|---------------|
| `r` | Процессов в очереди на CPU (состояние R) | Стабильно > nproc |
| `b` | Процессов в Uninterruptible Sleep (состояние D) | > 0 долгое время |
| `swpd` | Использовано swap (KB) | Растёт |
| `si` | Swap in — страницы читаются из swap в RAM (KB/s) | > 0 |
| `so` | Swap out — страницы вытесняются из RAM в swap (KB/s) | > 0 |
| `bi` | Блоков прочитано с диска в секунду | Зависит от задачи |
| `bo` | Блоков записано на диск в секунду | Зависит от задачи |
| `in` | Прерываний в секунду | > 50000 стоит изучить |
| `cs` | Context switches в секунду — смен контекста планировщика | > 100 000 — много переключений |
| `us` | % CPU на пользовательские процессы | > 80% стабильно |
| `sy` | % CPU на системные вызовы (ядро) | > 30% — много syscall |
| `id` | % CPU простаивает | Должен быть > 0 |
| `wa` | % CPU ждёт I/O | > 20–30% — проблема с диском |

**Три сценария в vmstat:**

```bash
# Сценарий 1: CPU bottleneck
 r  b  ...  us sy id  wa
 8  0  ...  90  8  2   0
# r=8 процессов ждут CPU, id=2% (почти нет простоя), wa=0 (диск ни при чём)
# → ищем кто грузит CPU: ps -eo pid,pcpu,cmd --sort=-pcpu | head -10

# Сценарий 2: I/O bottleneck
 r  b  ...  us sy id  wa
 1  5  ...   5  3  8  84
# b=5 процессов в состоянии D, wa=84% (CPU ждёт диск)
# → iostat -x 1, iotop

# Сценарий 3: Memory pressure (RAM кончается, используется swap)
 r  b  swpd ...  si  so  ...
 2  0  2048 ...  50  80  ...
# si/so > 0 — активный swap, система замедляется
# → free -h, systemd-cgtop (кто жрёт память)
```

### Memory pressure — давление на память

**Memory pressure** — состояние когда системе не хватает RAM. Три уровня:

**Уровень 1 — Low pressure:** RAM занята, ядро начинает вытеснять **page cache** (кэш файлов) чтобы освободить место для приложений. Производительность немного падает.

```bash
free -h
#               total   used   free   shared  buff/cache  available
# Mem:          7.8Gi  6.5Gi  200Mi    100Mi       1.1Gi      1.0Gi
#
# free   — физически свободная RAM (маленькое значение не страшно само по себе)
# available — сколько реально доступно для новых приложений (важнее чем free)
# buff/cache — page cache и буферы, ядро освободит при необходимости
```

**Уровень 2 — Medium pressure:** page cache вытеснен, ядро начинает использовать **swap**. Swap — это зарезервированное место на диске которое используется как медленное продолжение RAM. Доступ к данным в swap в 1000+ раз медленнее чем к RAM.

```bash
# si/so > 0 в vmstat — активный swap
vmstat 1 3 | awk '{print $7, $8}'   # si, so

# подробная статистика памяти
cat /proc/meminfo | grep -E "MemTotal|MemAvailable|SwapTotal|SwapFree|Cached"
```

**Уровень 3 — Critical (OOM):** swap тоже исчерпан, OOM Killer убивает процессы.

```bash
journalctl -k | grep -i "out of memory\|killed process"
```

**Swappiness** — параметр ядра, определяет насколько агрессивно использовать swap (0–100):

```bash
cat /proc/sys/vm/swappiness    # дефолт 60

# для серверов с БД рекомендуется 1–10
# при значении 1: swap используется только в критической ситуации
echo "vm.swappiness=10" >> /etc/sysctl.conf
sysctl -p
# Почему помогает: ядро становится «ленивее» в вытеснении страниц в swap.
# При swappiness=60 ядро агрессивно сбрасывает в swap даже активные данные.
# При swappiness=1 — только в экстренной ситуации. Для БД это критично:
# если страницы рабочего набора postgres попадают в swap — задержки запросов
# растут на порядки (RAM ~100ns vs swap/SSD ~100000ns).
```

**MemoryHigh vs MemoryMax в systemd:**

```ini
[Service]
MemoryHigh=400M   # мягкий лимит: при превышении ядро throttle процессы
                  # cgroup (замедляет аллокацию памяти) — это предупреждение
MemoryMax=512M    # жёсткий лимит: при превышении OOM Killer убивает процесс
MemorySwapMax=0   # запретить использование swap для этого сервиса
```

```bash
# где смотреть потребление памяти по сервисам
systemd-cgtop    # интерактивный мониторинг

# точное значение для конкретного сервиса
cat /sys/fs/cgroup/system.slice/nginx.service/memory.current
# 52428800  ← байты (= 50MB)
```

## 8. Сигналы

**Сигнал** — это асинхронное уведомление которое ядро или один процесс отправляет другому процессу. Слово «асинхронное» означает: сигнал может прийти в любой момент, прямо посреди выполнения кода.

Получив сигнал, процесс может:
- Выполнить обработчик (свою функцию-обработчик сигнала)
- Проигнорировать сигнал
- Выполнить действие по умолчанию (обычно завершение)

Исключение: `SIGKILL` и `SIGSTOP` нельзя перехватить, заблокировать или проигнорировать — они обрабатываются только ядром.

### Основные сигналы

| № | Имя | Действие по умолчанию | Когда использовать |
|---|-----|----------------------|--------------------|
| 1 | `SIGHUP` | Завершение | Reload конфига демона — процесс перечитывает конфиг без остановки |
| 2 | `SIGINT` | Завершение | Ctrl+C — прервать процесс |
| 9 | `SIGKILL` | Завершение | Крайняя мера — **нельзя перехватить**, ядро убивает немедленно |
| 15 | `SIGTERM` | Завершение | Вежливая просьба завершиться — **всегда пробовать первым** |
| 18 | `SIGCONT` | Продолжение | Разморозить процесс после SIGSTOP |
| 19 | `SIGSTOP` | Остановка | Заморозить процесс — **нельзя перехватить** |
| 10 | `SIGUSR1` | Зависит от приложения | nginx: переоткрыть лог-файлы после logrotate |

### SIGTERM vs SIGKILL — разница в последствиях

**SIGTERM (15):** процесс получает сигнал и **сам** решает как завершиться. Хорошо написанное приложение при получении SIGTERM делает graceful shutdown:
1. Перестаёт принимать новые запросы
2. Дожидается завершения текущих запросов
3. Закрывает соединения с базой данных
4. Сохраняет состояние если нужно
5. Удаляет временные файлы
6. Завершается с кодом 0

**SIGKILL (9):** ядро немедленно уничтожает процесс. Никакого обработчика, никакой очистки. Риски:
- Повреждённые файлы (запись не завершена)
- Незакоммиченные транзакции в БД (PostgreSQL после `kill -9` делает recovery при следующем запуске)
- Брошенные соединения с клиентами
- Временные файлы остаются на диске

```bash
# правильная последовательность
kill <PID>        # 1. SIGTERM — даём шанс завершиться gracefully
sleep 10          # 2. ждём
kill -9 <PID>     # 3. SIGKILL — только если не завершился

# по имени процесса
pkill nginx              # SIGTERM всем nginx
kill -HUP $(pgrep nginx) # reload конфига

kill -l   # список всех сигналов с номерами
```

## 9. systemd

**systemd** — это PID 1, первый процесс который запускает ядро после загрузки. Он управляет **жизненным циклом всех сервисов**: запускает их в правильном порядке, следит за состоянием, перезапускает при падении, собирает логи, изолирует через cgroups.

До systemd (SysV init) каждый сервис был отдельным bash-скриптом в `/etc/init.d/` — громоздко, нет параллельного запуска, нет зависимостей, нет автоперезапуска.

### restart vs reload vs daemon-reload

Три операции с похожими названиями — их путают даже опытные люди:

| Команда | Что происходит | Даунтайм | Когда использовать |
|---------|---------------|----------|--------------------|
| `systemctl restart` | SIGTERM → ждёт `TimeoutStopSec` → SIGKILL → запуск нового процесса | Да | Нужен полный перезапуск процесса |
| `systemctl reload` | Отправляет SIGHUP — процесс сам перечитывает конфиг | Нет | Изменили конфиг приложения (nginx.conf, etc.) |
| `systemctl daemon-reload` | systemd перечитывает unit файлы с диска | Нет | Изменили сам `*.service` файл |

> ⚠️ **Главная ловушка:** изменили unit файл → `systemctl restart` → изменения **не** применились. systemd кэширует unit файлы в памяти и не перечитывает их автоматически. Правильная последовательность: `daemon-reload` → `restart`.

```bash
# проверить поддерживает ли сервис reload
systemctl cat nginx | grep ExecReload
# ExecReload=/bin/kill -HUP $MAINPID  ← поддерживает
# (если строки нет — reload не работает, нужен restart)

# правильная последовательность при изменении unit файла
systemctl edit nginx          # изменяем override.conf
systemctl daemon-reload       # systemd перечитывает файл с диска
systemctl restart nginx       # процесс перезапускается с новыми настройками
```

### exit codes — расшифровка причин падения

Это первое что нужно смотреть после падения сервиса. По коду завершения можно сразу понять куда копать:

```bash
systemctl status myapi.service
# Active: failed (Result: exit-code) since ...
#   Main PID: 1234 (code=exited, status=1/FAILURE)

journalctl -u myapi -b 0 | grep -E "code=|status="
```

| Что видим | Смысл | Куда копать |
|-----------|-------|-------------|
| `code=exited, status=0` | Чистое завершение (процесс вышел сам с кодом 0) | Кто остановил? Скрипт? Logrotate? |
| `code=exited, status=1` | Ненулевой код выхода (ошибка в приложении) | Смотреть stderr: `journalctl -u svc -b 0 -n 50` |
| `code=exited, status=2` | Ошибка конфига / неверные аргументы | Запустить вручную — сразу увидим ошибку |
| `code=killed, status=9/KILL` | Получил SIGKILL | OOM? Истёк `TimeoutStopSec`? |
| `code=killed, status=11/SEGV` | Segmentation fault | Баг в коде или нехватка памяти |
| `code=killed, status=15/TERM` | Получил SIGTERM | Кто отправил? Другой скрипт? Деплой? |

```bash
# status=9/KILL — проверяем OOM в первую очередь
journalctl -k -b 0 | grep -i "out of memory\|killed process"

# status=1 — смотрим что напечатал перед смертью
journalctl -u myapi -b 0 -n 100

# status=0 — ищем кто мог остановить
journalctl --since "02:55" --until "03:05" | grep -i "stop\|myapi"
```

### Минимальный production unit файл

```ini
[Unit]
Description=My Production API
# After = порядок запуска, не жёсткая зависимость
After=network-online.target postgresql.service
# Requires = жёсткая зависимость: не запустимся если postgresql упал
Requires=postgresql.service
# Не более 5 перезапусков за 2 минуты — защита от бесконечного цикла
StartLimitIntervalSec=120
StartLimitBurst=5

[Service]
# Типы:
# simple  — ExecStart это основной процесс, systemd следит за ним напрямую
# forking — процесс делает fork() и родитель завершается (старые демоны)
# notify  — процесс сам уведомляет systemd через sd_notify() когда готов
# oneshot — выполняется и завершается (скрипты, одноразовые задачи)
Type=notify

User=myapi
Group=myapi
WorkingDirectory=/opt/myapi
EnvironmentFile=/etc/myapi/env

ExecStart=/opt/myapi/venv/bin/gunicorn --workers 4 --bind 0.0.0.0:8000 myapi.wsgi
ExecReload=/bin/kill -HUP $MAINPID

# on-failure = перезапускать при ненулевом коде выхода, SIGKILL и timeout
Restart=on-failure
RestartSec=10s
# После TimeoutStopSec секунд ожидания — SIGKILL всем процессам в cgroup
TimeoutStopSec=30

# Ресурсы через cgroups
CPUQuota=200%           # максимум 2 ядра
MemoryHigh=800M         # мягкий лимит — throttle
MemoryMax=1G            # жёсткий лимит — OOM kill
LimitNOFILE=65536       # лимит fd (через ulimit, не cgroup)

# Hardening — изоляция
NoNewPrivileges=yes     # процесс не может получить новые привилегии
PrivateTmp=yes          # изолированный /tmp
ProtectSystem=strict    # /usr, /boot, /etc только для чтения
ReadWritePaths=/var/log/myapi /var/lib/myapi
OOMScoreAdjust=-100     # чуть меньше шансов быть убитым OOM Killer

[Install]
WantedBy=multi-user.target
```

### Основные команды

```bash
systemctl status <svc>               # статус + последние логи + код завершения
systemctl start|stop|restart <svc>
systemctl reload <svc>               # SIGHUP без даунтайма
systemctl enable --now <svc>         # включить автозапуск + запустить сейчас
systemctl disable --now <svc>        # отключить автозапуск + остановить
systemctl edit <svc>                 # создать override.conf (сохранится при обновлении пакета)
systemctl daemon-reload              # ОБЯЗАТЕЛЬНО после изменений unit файла
systemctl list-units --state=failed  # все упавшие сервисы
systemctl show <svc> | grep -E "^(CPU|Memory|Limit|NRestarts|ActiveEnter)"
systemd-analyze blame                # что тормозит загрузку системы
systemd-analyze verify <svc>.service # проверить синтаксис unit файла
```

### Debugging алгоритм

```bash
# Шаг 1: смотрим код завершения
systemctl status myapi
journalctl -u myapi -b 0 | grep -E "code=|status="

# Шаг 2: полные логи текущей загрузки
journalctl -u myapi -b 0 --no-pager

# Шаг 3: если сервис уже перезапустился — логи предыдущего запуска
journalctl -u myapi -b -1

# Шаг 4: OOM?
journalctl -k -b 0 | grep -i "out of memory\|killed process"

# Шаг 5: история перезапусков
systemctl show myapi | grep NRestarts

# Шаг 6: воспроизвести вручную — часто сразу видна ошибка которую systemd скрывает
sudo -u myapi /opt/myapi/venv/bin/gunicorn --workers 4 myapi.wsgi
```

### journalctl

```bash
journalctl -u <svc> -f              # follow (как tail -f)
journalctl -u <svc> -b -1           # логи предыдущей загрузки системы
journalctl -u <svc> -p err          # только ошибки
journalctl -u <svc> -o json-pretty  # JSON формат (удобно для парсинга)
journalctl -k | grep -i oom         # OOM события из ядра

journalctl --vacuum-time=7d         # удалить логи старше 7 дней
```

## 10. cgroups vs ulimits

### Что такое cgroup и как она работает

**cgroup (control group)** — это механизм ядра Linux для **группировки процессов** и применения к ним общих ограничений ресурсов.

#### Принцип работы

Ядро реализует cgroups через специальную виртуальную файловую систему **cgroupfs**, смонтированную в `/sys/fs/cgroup/`. Это не обычные файлы — ядро генерирует их содержимое на лету. Каждая директория в этой ФС — это одна cgroup. Каждый файл внутри — один параметр управления.

```
/sys/fs/cgroup/                         ← корень cgroupfs
├── system.slice/                       ← все системные сервисы
│   ├── nginx.service/                  ← cgroup для nginx
│   │   ├── cgroup.procs               ← PID всех процессов nginx
│   │   ├── memory.max                 ← лимит RAM (записать число = установить лимит)
│   │   ├── memory.current             ← текущее потребление (читать)
│   │   ├── cpu.max                    ← лимит CPU (записать = установить CPUQuota)
│   │   └── cpu.stat                   ← статистика CPU (читать)
│   └── postgresql.service/            ← cgroup для PostgreSQL
│       ├── cgroup.procs               ← PID мастер-процесса + все воркеры
│       ├── memory.max                 ← лимит суммарный для ВСЕГО сервиса
│       └── memory.current             ← суммарное потребление всех процессов
└── user.slice/                        ← пользовательские сессии
    └── user-1000.slice/
        └── user@1000.service/
```

**Как ядро применяет лимиты:** при каждом выделении памяти или использовании CPU, ядро проверяет к какой cgroup принадлежит процесс и суммирует потребление **всех** процессов в группе. Если сумма превышает лимит — применяется ограничение ко всей группе.

#### Навигация от /proc/PID/cgroup до реальных лимитов

Вы нашли строку в `/proc/PID/cgroup`:
```
0::/user.slice/user-1000.slice/user@1000.service/app.slice/app-gnome-google\x2dchrome-6929.scope
```

Разберём что это значит:
- `0::` — это cgroups v2, единственная иерархия (в v1 было несколько)
- `/user.slice/user-1000.slice/...` — путь внутри cgroupfs

Чтобы посмотреть лимиты — добавьте этот путь к `/sys/fs/cgroup/`:

```bash
# путь из /proc/PID/cgroup (после "0::")
CGROUP_PATH="user.slice/user-1000.slice/user@1000.service/app.slice/app-gnome-google\x2dchrome-6929.scope"

# полный путь к файлам cgroup
ls /sys/fs/cgroup/$CGROUP_PATH/
# cgroup.procs    memory.max    memory.current    cpu.max    cpu.stat ...

# лимит памяти для этой cgroup
cat /sys/fs/cgroup/$CGROUP_PATH/memory.max
# max    ← нет лимита
# или
# 536870912   ← 512MB в байтах

# текущее потребление
cat /sys/fs/cgroup/$CGROUP_PATH/memory.current
# 104857600   ← 100MB

# для systemd-сервиса (например PostgreSQL) проще:
cat /sys/fs/cgroup/system.slice/postgresql.service/memory.max
cat /sys/fs/cgroup/system.slice/postgresql.service/cpu.max
```

Для **сервиса с дочерними процессами** (например PostgreSQL с воркерами) — все процессы сервиса находятся в одной cgroup. Лимит общий на всех:

```bash
# посмотреть все PID в cgroup PostgreSQL
cat /sys/fs/cgroup/system.slice/postgresql.service/cgroup.procs
# 1234   ← мастер-процесс
# 1235   ← worker 1
# 1236   ← worker 2
# 1237   ← worker 3

# лимит памяти 512M — это суммарно для всех четырёх процессов вместе
cat /sys/fs/cgroup/system.slice/postgresql.service/memory.max
# 536870912
```

```bash
# посмотреть к какой cgroup принадлежит процесс
cat /proc/$(pgrep -o nginx)/cgroup
# 0::/system.slice/nginx.service

# посмотреть дерево cgroups
systemd-cgls

# мониторинг потребления ресурсов по cgroups в реальном времени
systemd-cgtop

# прямой доступ к cgroup файлам nginx
ls /sys/fs/cgroup/system.slice/nginx.service/
# cgroup.procs      ← PID всех процессов в этой cgroup
# memory.current    ← текущее потребление RAM в байтах
# memory.max        ← лимит RAM
# cpu.stat          ← статистика CPU

cat /sys/fs/cgroup/system.slice/nginx.service/memory.current
# 52428800   ← 50MB
```

### Сравнение cgroups и ulimits

Прежде чем сравнивать — нужно понять фундаментальное различие в том **как** каждый механизм применяет ограничения.

#### Как работают ulimits

**ulimits (user limits)** — это ограничения ресурсов, которые ядро применяет **к одному процессу индивидуально**. Каждый процесс имеет свою собственную таблицу лимитов в структуре ядра `task_struct`. При создании нового процесса через `fork()` дочерний процесс **наследует копию** таблицы лимитов родителя.

```
  Как ulimits распространяются через fork():

  bash (nofile=1024)
  │
  ├── nginx-master (nofile=65536)   ← systemd установил через setrlimit()
  │   ├── nginx-worker-1 (nofile=65536)   ← наследовал от мастера
  │   ├── nginx-worker-2 (nofile=65536)   ← наследовал от мастера
  │   └── nginx-worker-3 (nofile=65536)   ← наследовал от мастера
  │
  └── psql (nofile=1024)   ← наследовал от bash, не от nginx

  ВАЖНО: nofile=65536 у воркеров означает что КАЖДЫЙ воркер
  может открыть до 65536 fd НЕЗАВИСИМО от других.
  nginx-worker-1: 60000 fd открыто — ОК
  nginx-worker-2: 60000 fd открыто — ОК (это не суммируется!)
  Суммарно система видит 120000 fd от nginx — это нормально.
```

Ключевое: `nofile=65536` — это лимит **на один процесс**, не на группу. Если у nginx 4 воркера с nofile=65536, каждый может открыть по 65536 fd. Суммарно nginx может открыть 4 × 65536 = 262144 fd.

```bash
# посмотреть лимиты текущей оболочки
ulimit -a

# посмотреть реальные лимиты запущенного процесса
cat /proc/<PID>/limits

# пример вывода:
# Limit                Soft Limit  Hard Limit  Units
# Max open files       65536       65536       files
# Max processes        4096        4096        processes
# Max stack size       8388608     unlimited   bytes
# Max core file size   0           unlimited   bytes
```

```
  Разница в природе ограничений:

  ┌─────────────────────────────────────────────────────────────────┐
  │  ulimits: каждый процесс — своя «коробка»                       │
  │                                                                 │
  │  [nginx-w1: fd 0..65536] [nginx-w2: fd 0..65536] [nginx-w3: ..]│
  │   индивидуальный лимит    индивидуальный лимит                  │
  │   не суммируются                                                │
  └─────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────┐
  │  cgroups: все процессы сервиса — общая «коробка»                │
  │                                                                 │
  │  ┌── nginx.service cgroup (MemoryMax=512M) ──────────────────┐  │
  │  │  [nginx-master: 50M] + [worker-1: 150M] + [worker-2: 150M]│  │
  │  │  Итого: 350M < 512M — ОК                                  │  │
  │  │  Если сумма > 512M — ядро применяет throttle/OOM ко всей  │  │
  │  │  группе одновременно                                       │  │
  │  └───────────────────────────────────────────────────────────┘  │
  └─────────────────────────────────────────────────────────────────┘
```

#### Про «иерархию» — разъяснение путаницы

В таблице сравнения есть два понятия которые легко спутать:

**«Применяется к»** — что является единицей ограничения:
- cgroups: **суммарное потребление группы**. PostgreSQL master + 10 воркеров суммарно не могут превысить MemoryMax
- ulimits: **один конкретный процесс**. Каждый воркер PostgreSQL имеет свой независимый лимит

**«Иерархия»** — это про структуру самих ограничений, а не про дочерние процессы:
- cgroups: есть дерево (`system.slice` → `postgresql.service`). Дочерняя cgroup не может иметь лимит **выше** родительской. Сервис не может потреблять больше чем выделено его slice
- ulimits: нет дерева групп. Дочерний **процесс** наследует значения от родителя (через fork), но может снизить их. Повысить hard limit может только root. Нет общей группы — нет и иерархии групп

Другими словами: ulimits наследуются через fork (процесс → дочерний процесс), но это не «иерархия групп» — просто копирование значений. cgroups образуют настоящую иерархию директорий с накапливаемыми лимитами.

| Критерий | cgroups | ulimits |
|----------|---------|---------|
| Единица ограничения | Суммарное потребление **всей группы** процессов | Лимит **одного** конкретного процесса |
| Применяется к | Сервис целиком (master + все воркеры вместе) | Каждый процесс индивидуально |
| Гранулярность | CPU, RAM, I/O, устройства, сеть | fd, nproc, размер стека, core dump |
| Иерархия групп | Да — cgroup дерево, дочерние ≤ родительских | Нет групп — только наследование значений через fork |
| Изменение без рестарта | Да | Soft лимит: да. Hard лимит: только root |
| В systemd | `CPUQuota=`, `MemoryMax=`, `TasksMax=` | `LimitNOFILE=`, `LimitNPROC=` |
| Работает для systemd сервисов | ✅ | ⚠️ только через `Limit*=` в unit файле |
| `/etc/security/limits.conf` | Не используется | Только для интерактивных сессий через PAM |
| Используется в Docker/K8s | Основа изоляции контейнеров | Нет |

> ⚠️ **Самая частая ошибка:** настроили `limits.conf` для nginx и ждёте эффекта. Не сработает. systemd запускает сервисы **напрямую, без PAM** — `limits.conf` игнорируется. Для systemd сервисов лимиты задаются только в unit файле через `Limit*=`.

### cgroups — управление ресурсами

```bash
# изменить лимит БЕЗ перезапуска сервиса
systemctl set-property nginx.service MemoryMax=512M
systemctl set-property nginx.service CPUQuota=50%

# проверить текущие лимиты
systemctl show nginx | grep -E "^(CPU|Memory|IO|Tasks)"
```

```ini
[Service]
CPUWeight=100         # вес при конкуренции за CPU (1–10000, дефолт 100)
CPUQuota=50%          # жёсткий лимит — не получит больше 50% ядра никогда
MemoryMin=128M        # гарантированный минимум — не отберут даже при нехватке RAM
MemoryHigh=400M       # мягкий лимит — throttle при превышении
MemoryMax=512M        # жёсткий лимит — OOM kill при превышении
MemorySwapMax=0       # запретить swap для этого сервиса
IOReadBandwidthMax=/dev/sda 100M   # лимит чтения с диска
IOWriteBandwidthMax=/dev/sda 50M   # лимит записи на диск
TasksMax=200          # максимум потоков + процессов в cgroup
```

### ulimits — лимиты для процессов

**ulimits** — это механизм ядра для ограничения ресурсов **одного процесса**. Каждый процесс в Linux имеет встроенную таблицу лимитов (хранится в `task_struct` внутри ядра). При создании нового процесса через `fork()` дочерний процесс получает **копию** таблицы лимитов родителя.

Каждый лимит существует в двух вариантах:
- **soft limit** — текущий рабочий лимит. Процесс может **сам** снизить его (без root)
- **hard limit** — потолок для soft limit. Повысить его может только root

#### Что такое PAM и при чём тут limits.conf

**PAM (Pluggable Authentication Modules)** — это фреймворк аутентификации в Linux. Это **не имеет никакого отношения к RAM (оперативной памяти)**. PAM — это набор библиотек который работает каждый раз когда вы входите в систему: через `ssh`, `sudo`, `su`, `login`. Именно PAM проверяет пароль, устанавливает окружение, и — применяет ulimits из `/etc/security/limits.conf`.

Цепочка при интерактивном логине:

```
Пользователь вводит пароль (ssh / sudo / login)
        │
        ▼
   PAM (libpam)
        │
        ├── pam_unix.so      → проверяет пароль в /etc/shadow
        ├── pam_limits.so    → читает /etc/security/limits.conf
        │                      и устанавливает ulimits для сессии
        └── pam_env.so       → устанавливает переменные окружения
        │
        ▼
   Shell/программа запускается с ulimits из limits.conf
```

Цепочка при запуске systemd сервиса:

```
systemctl start nginx
        │
        ▼
   systemd (PID 1)
        │
        ├── НЕТ PAM — systemd запускает процессы напрямую через fork/exec
        ├── /etc/security/limits.conf НЕ читается
        └── ulimits берутся ТОЛЬКО из unit файла (LimitNOFILE= и т.д.)
        │
        ▼
   nginx запускается с лимитами из unit файла
```

Именно поэтому `limits.conf` **не работает** для systemd-сервисов — PAM в этой цепочке просто нет. Это самая распространённая причина «я же настроил лимиты, почему не применились».

```bash
ulimit -a                         # все лимиты текущей shell сессии
cat /proc/<PID>/limits            # реальные лимиты запущенного процесса
```

| Параметр | Флаг | Дефолт | Для нагруженного сервера |
|----------|------|--------|--------------------------|
| `nofile` | `-n` | 1024 | 65536+ |
| `nproc` | `-u` | 1024–4096 | 65536+ |
| `memlock` | `-l` | 64 KB | `unlimited` для Elasticsearch, Redis |
| `core` | `-c` | 0 | `unlimited` для отладки core dump |

```ini
# В unit файле — единственный правильный способ для systemd
[Service]
LimitNOFILE=65536        # лимит открытых fd (файлы + сокеты)
LimitNPROC=4096          # лимит процессов/потоков
LimitMEMLOCK=infinity    # для Elasticsearch и Redis
LimitCORE=infinity       # разрешить core dump при падении
```

## 11. Fork bomb

**Fork bomb** — атака или баг при котором процесс бесконечно клонирует себя через `fork()`. Количество процессов растёт экспоненциально: 1 → 2 → 4 → 8 → 16 → ... Таблица процессов переполняется за секунды, система перестаёт отвечать.

```bash
# классическая bash fork bomb (НИКОГДА не запускать на продакшене)
:(){ :|:& };:
# расшифровка: функция с именем ":" вызывает себя дважды через пайп в фоне
```

**Защита через TasksMax** (предпочтительно для сервисов):

```ini
[Service]
TasksMax=512    # максимум потоков + процессов в cgroup сервиса
# Почему помогает: ядро отслеживает количество задач (процессов + потоков)
# суммарно в cgroup. При достижении TasksMax вызов fork() в любом процессе
# этой cgroup вернёт EAGAIN. Бомба остановится на 512 процессах, не затронув
# остальную систему. Другие сервисы продолжат работать нормально.
```

**Защита через nproc** (для пользователей):

```bash
# /etc/security/limits.d/nproc.conf
*  soft  nproc  4096
*  hard  nproc  8192
# Почему помогает: ядро считает суммарное количество процессов/потоков
# от данного пользователя (UID). При fork() проверяет не превышен ли лимит.
# Если превышен — fork() возвращает EAGAIN. Бомба не может расплодиться
# за пределы nproc. Минус: лимит общий для всех сервисов этого пользователя.
```

**Почему `TasksMax` лучше `nproc` для сервисов:** `nproc` — лимит на пользователя, все сервисы от `www-data` делят один лимит. `TasksMax` — лимит на cgroup конкретного сервиса, независимо от пользователя и других сервисов.

```bash
# восстановление
systemctl kill --kill-who=all --signal=SIGKILL <svc>  # убить всю cgroup
pkill -9 -u www-data                                   # убить все процессы пользователя
```

## 12. strace

### Что такое системный вызов

Любое взаимодействие программы с операционной системой — открытие файла, чтение данных, создание сокета, выделение памяти — это **системный вызов (syscall)**. Программа не может напрямую работать с диском или сетью — только через ядро. Программа «просит» ядро выполнить операцию через специальный механизм.

Пример: когда nginx открывает конфиг, это выглядит так:

```
nginx вызывает:  openat(AT_FDCWD, "/etc/nginx/nginx.conf", O_RDONLY) = 3
ядро отвечает:   3  ← успешно открыл, вот fd
nginx вызывает:  read(3, <данные>, 4096) = 1024  ← прочитал 1024 байта
nginx вызывает:  close(3) = 0  ← закрыл fd
```

**strace** перехватывает и выводит все системные вызовы процесса в реальном времени. Это как «рентген» — видно что процесс реально делает на уровне ОС, даже если логи молчат.

### Основные режимы

```bash
# подключиться к запущенному процессу
strace -p <PID>

# трассировать только определённые вызовы (важно на продакшене!)
strace -p <PID> -e trace=openat,read,write   # файловые операции
strace -p <PID> -e trace=network             # сетевые вызовы
strace -p <PID> -e trace=signal              # сигналы

# статистика: сколько раз вызван, суммарное время
strace -c python3 script.py
# % time   seconds  calls  syscall
#  45.23    0.231   23000  read
#  20.11    0.103   20000  write
#  15.00    0.080    1000  openat

# с временными метками — видно сколько занимает каждый вызов
strace -T -p <PID>   # время каждого вызова справа
strace -t -p <PID>   # абсолютное время

# включая дочерние процессы
strace -f -p <PID>

# записать в файл для анализа
strace -p <PID> -o /tmp/trace.txt
```

### Когда использовать

| Ситуация | Что искать в strace |
|----------|---------------------|
| Процесс завис, логи молчат | `strace -p <PID>` — на каком вызове завис |
| Приложение не находит файл | `strace -e trace=openat` — ENOENT ошибки |
| Права доступа непонятны | `strace -e trace=file` — EACCES ошибки |
| Медленный старт | `strace -c app` — какие вызовы занимают время |
| Утечка fd | `strace -e trace=open,close` — открывает не закрывая |

> ⚠️ strace добавляет overhead ~10–30%. На продакшене под нагрузкой — используйте с фильтром `-e trace=` и снимайте как только нашли проблему.

### Практический пример

```bash
# процесс завис, wchan = "pipe_wait"
strace -p 1234
# read(5, <unfinished ...>
# ← завис на чтении из fd=5, данные не приходят

# смотрим что за fd=5
ls -la /proc/1234/fd/5
# l-wx------ -> pipe:[98765]

# кто на другом конце пайпа
lsof | grep 98765
# app  5678  ...  6w  FIFO  pipe:[98765]  ← процесс 5678 держит запись открытой
# но не пишет данные → дедлок
```

## 14. Алгоритм дебага

Универсальный подход который работает для любого инцидента:

```
1. СИМПТОМ
   Что именно наблюдаем?
   сервис упал / тормозит / не принимает соединения / диск заполнен / load высокий

2. СЛОЙ
   Где проблема — приложение? systemd? ядро (OOM, I/O)?
   systemctl status → journalctl → dmesg

3. ВРЕМЕННАЯ МЕТКА
   Когда началось? Что изменилось в это время?
   journalctl --since / git log / deployment history

4. КОД ЗАВЕРШЕНИЯ (если сервис упал)
   code=exited status=1  → баг в приложении
   code=killed status=9  → OOM Killer или TimeoutStopSec
   code=killed status=11 → Segfault

5. МЕТРИКА ПОД СИМПТОМ
   Тормозит    → vmstat 1 (wa, b, si/so) → iostat → iotop
   Нет соед.   → ss -s (CLOSE_WAIT?) → fd лимит
   Диск полный → lsof | grep deleted
   Load высокий→ %wa в top → iostat → iotop
   Память      → free -h → systemd-cgtop → journalctl oom

6. ПРИЧИНА → ФИКС → ПРОВЕРКА
   Всегда проверять что фикс применился фактически
   (cat /proc/<PID>/limits, systemctl show, ss -s)
```

### Маршруты по симптому

| Симптом | Первая команда | Следующий шаг |
|---------|---------------|---------------|
| Сервис упал | `systemctl status svc` | `journalctl -u svc -b 0 \| grep code=` |
| Упал ночью | `systemctl show svc \| grep NRestarts` | `journalctl -k \| grep oom` |
| Тормозит всё | `uptime && nproc` | `vmstat 1 5` → `top %wa` |
| Нет места | `df -h` | `lsof \| grep deleted` |
| Нет соединений | `ss -s` | `cat /proc/$(pgrep -o svc)/limits` |
| Процесс завис | `cat /proc/<PID>/wchan` | `strace -p <PID>` |
| Память кончается | `free -h` | `vmstat 1` (si/so) → `journalctl -k \| grep oom` |

### Кейс 2: «Диск заполнен, но `du` и `df` не сходятся»

Команда `du` считает файлы по именам. `df` считает реально занятое место. Разница = удалённые файлы с открытыми fd.

```bash
lsof | grep deleted
# nginx 1234 root 7w REG /var/log/nginx/access.log (deleted) 2.1G

# решение без перезапуска
> /proc/1234/fd/7        # обнуляем файл через fd
# Почему помогает: операция truncate через /proc/PID/fd/N работает с
# файлом по его дескриптору, минуя имя на диске. Файл обнуляется,
# место немедленно освобождается, nginx продолжает писать в тот же fd.
# или
systemctl reload nginx   # nginx переоткрывает логи сам
# Почему помогает: SIGHUP заставляет nginx закрыть старые fd логов и
# открыть новые файлы с теми же именами. Удалённый файл лишается последней
# ссылки (fd закрыт), ядро освобождает место на диске.
```

Корень проблемы: logrotate удаляет файл но не сигналит nginx переоткрыть его:

```bash
# /etc/logrotate.d/nginx — правильно
postrotate
    systemctl reload nginx
endscript
```

### Кейс 4: «Nginx перестал принимать соединения»

```bash
# fd исчерпаны?
cat /proc/$(pgrep -o nginx)/limits | grep "open files"
# Max open files  1024  1024  ← дефолт!
ls /proc/$(pgrep -o nginx)/fd | wc -l
# 1023  ← достигли лимита

# много CLOSE_WAIT — приложение не закрывает соединения?
ss -s

# фикс
systemctl edit nginx
# [Service]
# LimitNOFILE=65536
systemctl daemon-reload && systemctl restart nginx
# Почему помогает: systemd устанавливает новый лимит через setrlimit() до
# запуска nginx. Теперь ядро разрешает nginx держать 65536 fd одновременно.
# Каждое TCP соединение = 1 fd. Дефолтный лимит 1024 подходит для десктопа,
# для нагруженного веб-сервера нужно минимум 10 000–65 536.

# проверяем
cat /proc/$(pgrep -o nginx)/limits | grep "open files"
# Max open files  65536  65536  ← применилось
```

### Кейс 5: «После деплоя старые процессы ещё живут»

```bash
systemctl status myapi   # смотрим секцию CGroup — там должны быть все PID

# принудительно убить всю cgroup
systemctl kill --kill-who=all myapi.service
# Почему помогает: systemd отправляет SIGKILL напрямую каждому PID из
# cgroup.procs этого сервиса. Даже процессы которые сделали setsid() и
# «убежали» от родителя — всё равно остаются в cgroup. Ядро гарантирует
# что из cgroup нельзя «сбежать» без явного переноса.

# частая причина: Type=forking без PIDFile=
# systemd не знает главный PID и не контролирует дочерние процессы
# фикс: перейти на Type=notify или указать PIDFile=
# Почему помогает: с Type=notify процесс сам сообщает systemd свой PID
# через sd_notify(). systemd точно знает кто главный и корректно отслеживает
# всё дерево процессов в cgroup.
```

## 16. Вопросы на собесе

### Базовый уровень

**В: Что такое файловый дескриптор? Зачем он нужен?**
> О: fd — это целое число, которое ядро выдаёт процессу при открытии любого ресурса: файла, сокета, пайпа. Ядро хранит всю информацию об открытом ресурсе у себя, а процессу возвращает просто число-ссылку. Зачем: единый интерфейс для всего — одни и те же вызовы `read/write/close` работают и с файлами и с сетевыми соединениями.

**В: Почему `LimitNOFILE` влияет на количество сетевых соединений?**
> О: Каждое TCP-соединение — это fd. Файлы, TCP-сокеты, unix-сокеты, пайпы — всё одна абстракция, всё занимает место в таблице fd процесса. Лимит `nofile` ограничивает их суммарное количество. При дефолте 1024 nginx упадёт с `Too many open files` при нагрузке.

**В: Что такое Load Average?**
> О: Среднее количество процессов в очереди на выполнение (состояние R) или ожидающих I/O (состояние D) за 1, 5 и 15 минут. Это не загрузка CPU — процессы в состоянии D тоже увеличивают load, хотя CPU при этом может быть свободен. Нормально когда ≤ количества ядер CPU.

**В: Чем `systemctl restart` отличается от `reload` и `daemon-reload`?**
> О: `restart` — полный перезапуск процесса (SIGTERM → SIGKILL → новый запуск), есть даунтайм. `reload` — отправляет SIGHUP, процесс сам перечитывает конфиг без остановки. `daemon-reload` — systemd перечитывает unit файлы с диска, на запущенные процессы не влияет. После изменения unit файла нужно `daemon-reload` а затем `restart`.

**В: Что такое зомби-процесс и почему опасны тысячи зомби?**
> О: Процесс завершился и вызвал `exit()`, но родитель не вызвал `wait()` чтобы считать код завершения. Ядро держит минимальную запись о нём в таблице процессов. Зомби не потребляет CPU/память, но занимает PID. Если зомби тысячи — таблица процессов переполняется и создать новые процессы невозможно.

---

### Middle уровень

**В: Load average 20 на 8-ядерном сервере, CPU usage 15%. Что происходит и что делать?**
> О: Высокий load при низком CPU означает что процессы не ждут CPU — они ждут I/O (состояние D). `vmstat 1` покажет высокий `wa` и ненулевой `b`. Диагностика: `iostat -x 1` (нагрузка на диск), `iotop` (кто грузит), `ps aux | awk '$8~/^D/'` (какие процессы). Причины: перегруженный диск, умирающий HDD, зависший NFS.

**В: Что значит `code=killed, status=9/KILL` в статусе сервиса?**
> О: Процесс получил SIGKILL. Два источника: OOM Killer (ядро убило из-за нехватки памяти) или systemd (истёк `TimeoutStopSec`). Диагностика: `journalctl -k | grep "out of memory"`. Если OOM — поднять `MemoryMax` или добавить `MemoryHigh` для раннего throttle.

**В: Зачем нужны unix-сокеты если есть TCP?**
> О: Unix-сокеты работают только на одной машине, но быстрее TCP — нет сетевого стека, данные идут напрямую через память ядра. Плюс безопаснее: доступ контролируется правами файла. Типичный случай: nginx → php-fpm на одном сервере через unix-сокет вместо `127.0.0.1:9000`.

**В: Много CLOSE_WAIT соединений — что это значит?**
> О: Удалённая сторона закрыла соединение (прислала FIN), но наше приложение не вызвало `close(fd)`. Это утечка соединений — баг в приложении. Со временем исчерпает лимит fd. Диагностировать: `ss -tnp | grep CLOSE_WAIT`.

**В: Чем cgroups отличаются от ulimits и почему `limits.conf` не работает для systemd?**
> О: cgroups — механизм ядра для суммарного ограничения группы процессов (весь сервис целиком), поддерживают CPU/RAM/I/O. ulimits — лимиты ядра на один конкретный процесс: fd, nproc, размер стека. `limits.conf` применяется через PAM (Pluggable Authentication Modules) — фреймворк аутентификации который запускается при ssh/sudo/login и устанавливает ulimits для интерактивной сессии. systemd запускает сервисы **напрямую через fork/exec, без PAM** — поэтому `limits.conf` игнорируется. Для systemd — только `Limit*=` в unit файле.

**В: Как systemd гарантирует что при остановке сервиса умирают все дочерние процессы?**
> О: systemd помещает все процессы сервиса в одну cgroup при запуске. При остановке — отправляет SIGTERM всем процессам в этой cgroup, ждёт `TimeoutStopSec`, затем SIGKILL всем оставшимся. Процесс не может «сбежать» из cgroup — это гарантия ядра.

**В: Когда и зачем использовать strace?**
> О: strace показывает системные вызовы процесса в реальном времени — что он открывает, читает, пишет, какие ошибки получает. Используем когда логи молчат но процесс ведёт себя странно, когда нужно найти какой файл не может открыть, или когда процесс завис и `wchan` непонятен. На продакшене под нагрузкой — с фильтром `-e trace=` и осторожно (overhead 10–30%).

