# 1.2 Что такое Docker-контейнер на самом деле

## Что разберём

1. Контейнер как процесс, а не отдельная система
2. Namespaces — что процесс видит
3. Cgroups — сколько ресурсов может забрать
4. Overlay fs и слои образа

## 1. Контейнер — это процесс на общем ядре хоста

Когда стартует `docker run -d nginx`, на хосте в этот момент появляется самый обычный процесс `nginx`, видимый в `ps aux` точно так же, как любой другой процесс — просто с ограниченным "обзором" системы. Никакого отдельного ядра внутри контейнера нет — процесс использует то же самое ядро хоста, что и все остальные процессы на нём.

Обратиться к контейнеру можно по его ID или имени. Имя можно задать самому через `--name`. Если не задать — Docker сгенерирует случайное, вроде "stupefied_mayer". Дальше ищем PID процесса на хосте по ID/имени контейнера и убеждаемся, что это обычный процесс хоста:

```bash
docker run -d --name demo nginx
docker inspect --format '{{.State.Pid}}' demo
ps aux | grep <PID>
```

Отсюда и вся практическая разница с VM: не нужно грузить ядро, поднимать init-систему — контейнер стартует за миллисекунды, потому что это по сути `clone()` — расширенная версия `fork()` — плюс `exec()`, с несколькими дополнительными флагами для ядра. Каждый флаг привязан к конкретному виду namespace:

- `CLONE_NEWPID` → PID namespace
- `CLONE_NEWNET` → network namespace
- `CLONE_NEWNS` → mount namespace (историческое название: `NS` здесь означает именно mount — это первый добавленный в ядро namespace, отсюда и общее имя)
- `CLONE_NEWUTS` → UTS namespace
- `CLONE_NEWIPC` → IPC namespace

Каждый флаг говорит ядру: создай для этого процесса отдельный namespace именно этого типа, не шарь его с родителем.

Здесь важно зафиксировать одну вещь, к которой будут возвращаться все следующие разделы. На каждый процесс ядро заводит структуру `task_struct` — "досье процесса". В нём лежит всё, что ядро знает о процессе, и в том числе набор **указателей** (ссылок на другие структуры в памяти ядра): на какие namespace'ы этот процесс смотрит, на какой cgroup-счётчик привязан, где у него корень файловой системы. Вся изоляция контейнера — это ровно эти несколько указателей в `task_struct`.

## 2. Namespaces — иллюзия изоляции ("что видно")

Namespace — это фундаментальный механизм ядра Linux, который изолирует системные ресурсы для группы процессов. На каждый вид ресурса существует свой namespace:

**PID** — процесс думает, что он PID 1, и не видит процессы вне своего namespace.

**Network** — свой изолированный сетевой стек: интерфейсы, IP-адреса, таблицы маршрутизации, правила iptables/nftables, порты.

**Mount** — своё дерево точек монтирования и изолированный взгляд на файловую систему.

**UTS** — своё имя хоста и домена (поэтому `hostname` внутри контейнера отличается от hostname хоста).

**IPC** — свои очереди сообщений, семафоры и shared memory (не видит IPC-объекты хоста).

**User** — свой маппинг UID/GID (позволяет быть root внутри namespace, оставаясь непривилегированным пользователем на хосте).

**Как это работает внутри ядра (`nsproxy`)**

У каждого процесса в `task_struct` есть поле-указатель на `nsproxy`. Сам `task_struct` при этом никогда не шарится — это не один `task_struct` на всех, а отдельная карточка на каждый процесс. Но сам объект `nsproxy`, на который указывает это поле, — самостоятельная структура в памяти ядра, существующая отдельно от любого конкретного процесса. В этом объекте лежат ссылки на все namespace'ы разом: на `pid_namespace`, `net_ns`, `mnt_ns`, `uts_ns`, `ipc_ns` и так далее. Вместо семи отдельных полей в `task_struct` ядро хранит одно — указатель на этот отдельный объект, который может быть общим сразу для многих процессов.

Зачем это нужно (математика на пальцах): если бы ядро хранило 7 ссылок на каждый namespace прямо в `task_struct`, то запуск контейнера с 1000 worker-процессов nginx потребовал бы 1000 процессов × 7 ссылок = 7000 полей в памяти. Чтобы не плодить дубликаты, ядро выносит эти 7 указателей в единый объект `nsproxy`. При обычном `fork()` (без флагов изоляции) ребёнок получает ссылку на тот же объект `nsproxy`, что и у родителя, а ядро лишь увеличивает счётчик ссылок. Итого в памяти: 1000 полей в `task_struct` + 7 ссылок в единственном `nsproxy` = 1007 вместо 7000.

Новый, отдельный объект `nsproxy` появляется только тогда, когда процесс создаётся с флагом `CLONE_NEW*` — то есть ровно в момент, когда `runc` создаёт контейнер (за это в коде ядра отвечает функция `copy_namespaces()`, вызываемая на каждый `clone()`). При этом `nsproxy` не принадлежит master-процессу больше, чем worker'ам: когда `runc` создаёт master с этим флагом, ядро создаёт для него новый `nsproxy`, и master получает на него первый указатель. Когда master форкает worker'ов, они получают указатели на тот же объект. Технически это работает через счётчик ссылок (refcount): при создании счётчик равен 1, при каждом новом форке увеличивается на 1. Объект существует в памяти, пока счётчик больше нуля — то есть пока хотя бы один процесс на него ссылается. Если master завершится, а worker'ы останутся работать, `nsproxy` не исчезнет.

Как увидеть этот sharing на практике: сравним master и worker процессы внутри одного контейнера:

```bash
docker exec demo ps aux                          # находим PID master и одного из worker'ов
docker exec demo ls -la /proc/<PID_master>/ns/
docker exec demo ls -la /proc/<PID_worker>/ns/
```

Если у них все номера в квадратных скобках (например, `pid:[4026531836]`) совпадают — это прямое доказательство: они физически указывают на один объект `nsproxy`, а не на отдельные копии.

Тут важно не ошибиться, ГДЕ именно происходит переиспользование. Механизм экономии реальный, просто работает не там, где может показаться по аналогии с `lower` из раздела про overlay: "одинаковый набор" namespace-указателей означает процессы внутри одного и того же контейнера. Даже если два контейнера запущены из одного и того же образа — общим у них остаётся `lowerdir` (те самые слои образа), но не `nsproxy`: у каждого контейнера он свой, отдельный. Если бы два разных контейнера ссылались на один и тот же `nsproxy`, они оказались бы в одном и том же PID/net/mount namespace и перестали бы быть изолированы друг от друга. Экономия работает внутри контейнера, между его собственными процессами; между контейнерами она в принципе невозможна — это сломало бы саму суть изоляции.

**Практическое применение и слом иллюзии**

Утилита `nsenter` вручную присоединяет вашу консоль к namespace'ам существующего процесса. Именно этот syscall (`setns`) используют containerd/runc при `docker exec` (Docker делает системный вызов, а не запускает саму утилиту):

```bash
sudo nsenter --target <PID> --pid --net --mount --uts --ipc sh
```

А вот команда, которая наглядно ломает иллюзию изоляции контейнера:

```bash
docker run --rm -it --pid=host alpine ps aux
```

Передавая флаг `--pid=host`, мы заставляем контейнер использовать PID namespace самого хоста. Процесс внутри контейнера внезапно видит всю систему. Это доказывает: ощущение контейнера "я один в системе" — это лишь результат работы namespaces, а не изолированная виртуальная машина.

## 3. Cgroups — сколько можно взять ("сколько дают")

Cgroups (control groups) отвечают за лимиты потребления ресурсов: CPU, память, диск I/O, число процессов (pids).

Это два независимых механизма: namespace без cgroup — процесс увидит только своё, но сможет забрать всю память хоста; cgroup без namespace — процесс будет ограничен по ресурсам, но при этом увидит все процессы хоста.

**Механика работы в ядре**

Внутри это ещё один указатель из того же `task_struct`. При старте контейнера `runc` создаёт cgroup-директорию (для systemd-драйвера — по пути `/sys/fs/cgroup/system.slice/docker-<id>.scope/`) с файлами-счётчиками (`memory.max`, `cpu.max` и т.д.) и прописывает в досье процесса ссылку на неё. По этому пути лежит только cgroup-интерфейс — ничего от namespaces, overlay или других механизмов там нет.

Когда процесс внутри контейнера решает выделить себе память и делает syscall, ядро идёт по указателю к cgroup-счётчику и сверяет: лимит 256 MB, уже занято 250, запрос на ещё 10 — превышение. Выделение блокируется, вызывается OOM-killer, процесс получает SIGKILL.

**Устройство cgroup v2 и иерархия**

На современных дистрибутивах (Ubuntu 22.04+, Debian 11+) стандартом стал **cgroup v2** (`Cgroup Version: 2` в `docker info`).

В v2 используется единое смонтированное дерево (`/sys/fs/cgroup`), где процессы разложены по slice'ам (`.slice`). Проверить точку монтирования:

```bash
mount | grep cgroup2
```

Основные ветки иерархии:

- **`system.slice`** — systemd-сервисы (`sshd.service` и т.д.), и туда же Docker кладёт свои контейнеры как `docker-<id>.scope`
- **`user.slice`** — пользовательские сессии (в том числе твоя текущая SSH-сессия)
- **`init.scope`** — сам PID 1 (systemd)

Какой cgroup-драйвер использует Docker — `cgroupfs` или `systemd` — видно в выводе `docker info | grep -i cgroup`. На системах с systemd рекомендуется использовать драйвер `systemd`, чтобы избежать конфликта двух независимых менеджеров, управляющих одним деревом.

**Практика: где смотреть реальные лимиты**

Зададим лимиты флагами при запуске:

```bash
docker run -d --name limited --memory=256m --cpus=0.5 nginx
```

Лимиты пробрасываются напрямую в псевдофайловую систему `/sys/fs/cgroup`. Найти значение `memory.max` через ID контейнера:

```bash
CONTAINER_ID=$(docker inspect --format '{{.Id}}' limited)
cat /sys/fs/cgroup/system.slice/docker-${CONTAINER_ID}.scope/memory.max
```

Если в выводе `max` — лимит не задан; если число — это точный объём в байтах (например, `268435456` для 256M).

Более простой способ получить путь — файл `/proc/<PID>/cgroup`:

```bash
cat /proc/$PID/cgroup
```

Вывод вида `0::/system.slice/docker-<id>.scope` указывает прямой путь относительно `/sys/fs/cgroup`. У обычного процесса хоста там будет просто `0::/`.

**Направление связей: лимит на всю группу**

Здесь направление связи обратное тому, что было с `nsproxy` в разделе 2. Там процесс хранит указатель на объект namespace. В cgroups сама директория хранит список PID'ов, которые в неё входят (в файле `cgroup.procs`).

Отсюда важнейшее практическое следствие: `memory.max` — это лимит на всю группу разом. Если у nginx один master и десять worker'ов внутри одного контейнера с `--memory=256m` — это 256 МБ суммарно на все 11 процессов, а не по 256 МБ на каждый.

**Назначение лимитов и OOM-killer**

Cgroup-директория создаётся всегда при старте контейнера, это делает `runc` — она нужна для учёта ресурсов (`docker stats`) и для возможности завершить всю группу процессов разом.

Однако лимиты в ней появляются только при явном указании флагов `--memory` или `--cpus`. Без них файл `memory.max` содержит `max` (безлимит), и контейнер может утилизировать все ресурсы хоста (проблема "noisy neighbor").

Когда процесс внутри контейнера превышает лимит `--memory`, ядерный OOM-killer убивает именно этот процесс внутри cgroup, а не случайный процесс на хосте. В результате `docker inspect limited` показывает `"OOMKilled": true`, а код завершения процесса равен **137** (128 + 9 / SIGKILL).

Проверка на практике:

```bash
# Python пытается выделить 100 MB в контейнере с лимитом 50 MB
docker run --rm --memory=50m python:alpine python -c "a = 'x' * 100 * 1024 * 1024"
echo $?
```

`echo $?` вернёт **137** — прямое подтверждение срабатывания OOM-killer внутри cgroup.

## 4. Overlay filesystem — как склеиваются слои образа

OverlayFS — это встроенный в ядро Linux механизм, который берёт несколько разных директорий на диске, накладывает их друг на друга как прозрачные слои и показывает результат в одной итоговой точке.

Этот механизм решает две главные задачи контейнеризации: изоляцию изменений (контейнер не ломает базовый образ) и экономию ресурсов (один образ переиспользуется сотнями контейнеров без копирования).

Разберём его сначала на чистых папках Linux без Docker, а затем посмотрим, как эту концепцию применяют контейнерные движки.

**Практический эксперимент на уровне ядра (2 минуты, от root)**

Создадим четыре обычные папки и один файл:

```bash
mkdir -p /tmp/test/lower /tmp/test/upper /tmp/test/work /tmp/test/merged
echo "hello from image" > /tmp/test/lower/file.txt
```

Смонтируем OverlayFS одной командой:

```bash
mount -t overlay overlay -o lowerdir=/tmp/test/lower,upperdir=/tmp/test/upper,workdir=/tmp/test/work /tmp/test/merged
```

Сейчас у нас есть четыре директории. Разберём, что хранит каждая из них:

**`lower`** (образ) — read-only слой, общий источник. Ядро в него никогда не пишет. Это гарантия того, что исходные данные остаются нетронутыми. Слоёв `lower` может быть несколько (они перечисляются через двоеточие).

**`upper`** (контейнер) — read-write слой, приватный для каждого процесса/контейнера. Изначально пустая. Всё, что процесс создаёт, меняет или удаляет — оседает здесь как "дельта".

**`work`** (служебная) — директория для внутренних нужд ядра. Нужна для атомарного переноса файлов между слоями, чтобы избежать битых файлов при сбоях (обязана лежать на той же ФС, что и `upper`).

**`merged`** (точка монтирования, mount point) — не хранилище, а вычисляемое на лету представление. Процесс видит её как единую файловую систему: ядро на лету комбинирует данные из `upper` и `lower`.

Отдельное правило — не для содержимого файла, а для листинга самой директории (`ls`). Здесь ядро не выбирает "либо `upper`, либо `lower`" — оно **объединяет**: читает список файлов и из `upper`, и из каждого слоя `lower`, и складывает их в один общий список без дублей (если имя уже встретилось в верхнем слое, из нижнего оно повторно не берётся). Именно это видно при `ls /tmp/test/merged` или `ls` внутри контейнера — состав директории каждый раз пересобирается заново из всех слоёв разом, а не берётся из какого-то одного места.

**Как ядро обрабатывает три базовые операции**

*1. Чтение:* `cat /tmp/test/merged/file.txt`
Ядро ищет файл сначала в `upper`. Там его нет — спускается в `lower`, находит и отдаёт.

*2. Изменение (copy-up):* `echo "modify" > /tmp/test/merged/file.txt`
Файл в `lower` изменять нельзя. Поэтому в момент записи ядро сначала целиком копирует файл из `lower` в `upper` (операция copy-up), а затем применяет изменение к верхней копии. Теперь `merged` перекрывает нижний файл новым.

*3. Удаление (whiteout):* `rm /tmp/test/merged/file.txt`
Удалить файл из `lower` физически нельзя. Ядро создаёт в `upper` специальную заглушку — whiteout (символьный файл с устройствами 0/0). Для `merged` это сигнал: "скрой этот файл, сделай вид, что его нет". В `lower` файл остаётся нетронутым.

(По окончании эксперимента: `umount /tmp/test/merged && rm -rf /tmp/test`)

**Как это применяет Docker: слои и Dockerfile**

В эксперименте `lower` был один. На практике `lowerdir` — это список из множества папок, чтение которых идёт слева направо (сверху вниз): `lowerdir=layer3:layer2:layer1`.

Количество этих папок зависит от Dockerfile. Каждая инструкция, меняющая файловую систему, создаёт новый слой:

- `FROM` — приносит слои базового образа
- `RUN` — всё, что команда записала на диск, становится отдельной папкой
- `COPY` / `ADD` — добавленные файлы формируют ещё одну папку

(Мета-инструкции вроде `ENV`, `EXPOSE`, `CMD` слоёв не создают.)

**Пример: три слоя от начала до конца**

Шаг 1. Dockerfile:

```dockerfile
FROM ubuntu                                    # слой 1: базовая ОС
RUN apt-get update && apt-get install -y curl  # слой 2: добавленный curl
COPY app.py /app/                              # слой 3: скопированный файл
```

Шаг 2. Как это выглядит на диске:
Каждая инструкция — это отдельная папка. Важно: `layer2` не содержит копию всей ОС, там только `usr/bin/curl`. В `layer3` — только `app.py`.

Шаг 3. Запуск контейнера (`docker run`):

- `lowerdir = layer3:layer2:layer1` (общие read-only папки)
- `upperdir` = пусто (свежая, приватная для этого контейнера)
- `merged` = точка монтирования (mount point), где всё собирается вместе

Если процесс внутри контейнера изменит `/app/app.py` или удалит curl, сработают описанные выше механизмы copy-up и whiteout: изменения осядут в `upperdir`, а слои образа (`lowerdir`) останутся неизменными. Второй контейнер из этого же образа получит те же `lowerdir`, но абсолютно чистый, свой собственный `upperdir`.

**Наглядно на реальном контейнере**

```bash
docker run -d --name demo nginx
PID=$(docker inspect --format '{{.State.Pid}}' demo)
UPPER=$(cat /proc/$PID/mounts | grep ' / overlay' | grep -oP 'upperdir=\K[^,]+')

ls $UPPER
# почти пусто — контейнер только что стартовал, ничего толком не поменял

docker exec demo cat /etc/nginx/nginx.conf
# а этот файл прекрасно виден и читается изнутри контейнера
```

Если бы процессу подсунули как корень именно `upper` — он увидел бы почти пустую файловую систему: ни бинарника nginx, ни конфигов, ни библиотек, потому что всего этого физически в `upper` нет — всё в `lower`. Но процесс прекрасно работает, потому что подсовывают ему точку монтирования (`merged`): там видно и тысячи файлов из `lower` (сам nginx, его библиотеки, конфиги), и те немногие изменения, что успели попасть в `upper`.

**Как `merged` становится корнем контейнера (`pivot_root`)**

Собрать `merged` — это ещё не изоляция. Это просто папка на диске хоста. Чтобы запереть в ней процесс, `runc` (рантайм) использует системный вызов `pivot_root()`. Он берёт `merged`-директорию, делает её новым абсолютным корнем (`/`) для процесса контейнера (внутри его mount namespace), а настоящий корень хоста отцепляет. Теперь для процесса контейнера ничего за пределами `merged` физически не существует.

**Эпохи бэкендов: от overlay2 к containerd**

Раньше Docker раскладывал слои в `/var/lib/docker/overlay2/`, и `docker inspect` честно показывал пути в поле `GraphDriver.Data`.

Начиная с Docker Engine 29, по умолчанию включён бэкенд **containerd image store**. Снэпшотами теперь управляет containerd. Поэтому поле `GraphDriver` может быть пустым — это не баг, а следствие смены бэкенда (проверить можно через `docker info | grep driver-type`).

Но независимо от бэкенда, ядру всё равно, кто собрал слои. Увидеть реальные пути для любого запущенного контейнера можно так:

```bash
# Узнаём PID главного процесса контейнера
PID=$(docker inspect --format '{{.State.Pid}}' demo)
# Смотрим таблицу монтирования процесса
cat /proc/$PID/mounts | grep ' / overlay'
```

В выводе будут реальные пути к `lowerdir` и `upperdir` на диске хоста — но `merged` там не будет ни в каком виде, и это не пропуск в выводе, а особенность самого механизма. Причина в том, что `lowerdir`, `upperdir`, `workdir` — это именованные опции команды `mount` (ключ=значение внутри `-o`), а вот то, что мы называем "`merged`", — это вообще не опция, а обычный **target** (место назначения) самой команды `mount`, тот же аргумент, что и в любом `mount /dev/sda1 /mnt/disk`. Параметра `mergedir=` не существует в природе — ни в документации ядра, ни в реальности.

В реальном выводе target — это `/`, потому что `/proc/$PID/mounts` показывает таблицу монтирования изнутри mount namespace самого контейнера, а корень контейнера и есть это самое место назначения. Docker/containerd не монтируют overlay куда-то в сторону, а потом отдельно переключают процесс — они сразу монтируют его туда, что станет `/` (плюс `pivot_root()`, который и довершает дело, — разбирали чуть выше). А то, что в самом первом эксперименте этого раздела мы назвали папку `/tmp/test/merged`, — просто наша договорённость для удобства объяснения; в документации ядра это называется просто "mount point".

**Подводные камни и production-грабли (уровень Middle+)**

На собеседованиях любят спрашивать, почему OverlayFS — не серебряная пуля. Вот главные архитектурные нюансы:

**1. Удаление целых директорий (opaque directories)**

*(Не путать с Opaque Secrets в Kubernetes — термин тот же, но к overlayfs это не имеет никакого отношения, просто совпадение в названии.)*

Если процесс удаляет файл, создаётся whiteout. А если выполнить `rm -rf /var/log/app`, где в `lower` лежат 10 000 файлов?

Ядро не будет создавать 10 000 заглушек. Удаление директории кодируется так же, как удаление файла — **одним** whiteout на саму директорию: `merged` просто перестаёт видеть `/var/log/app` целиком, вместе со всем содержимым, не заглядывая внутрь по одной записи.

Opaque-директория — это отдельный, более узкий случай: когда директорию не просто удаляют, а сразу пересоздают с тем же именем (`rm -rf /etc && mkdir /etc`). Тогда новая директория в `upper` помечается расширенным атрибутом `trusted.overlay.opaque=y` — сигнал ядру "не подмешивай сюда содержимое одноимённой директории из `lower`", иначе в новую, только что созданную папку неожиданно "просочились" бы старые файлы снизу.

**2. Штраф производительности за copy-up (почему БД нужны volumes)**

Если в образе лежит лог-файл или база данных размером 2 ГБ, и процесс пытается дописать в него всего один байт, драйвер сначала скопирует все 2 ГБ из `lower` в `upper`, и только потом разрешит запись.

Важно понимать принцип: копирование происходит один раз на файл, а не на каждую запись (тот же copy-up, что в первом эксперименте раздела — просто здесь речь о файле в 2 ГБ, а не в пару байт). После первого копирования файл уже в `upper`, и все следующие записи идут напрямую, без повторного копирования.

Без volume процесс действительно пишет прямо в `upper` — это и есть "писать в контейнер". Проблема на практике не в разовой паузе при каждом старте: чаще всего файл базы данных создаётся заново пустым при первом запуске (то есть сразу в `upper`, без штрафа). Но если файл БД именно принесён образом — например, кто-то запёк стартовый дамп прямо в Dockerfile — каждый новый контейнер из этого образа будет заново переживать полный copy-up при первом же обращении к этому файлу, потому что у каждого контейнера свой отдельный, пустой `upper`, и предыдущего copy-up там ещё не было.

Вывод: любые I/O-интенсивные данные (СУБД, кэши, частые логи) обязаны выноситься в Docker volumes. Volume монтируется напрямую поверх точки в файловой системе, минуя весь механизм `lower`/`upper`/copy-up целиком — запись сразу идёт на реальный диск, без копирования большого файла при первом обращении.

**3. Экономия оперативной памяти (Page Cache Sharing)**

Экономится не только место на диске, но и RAM. Так как файлы в `lowerdir` неизменяемые (read-only), ядро Linux кэширует их в page cache ровно один раз. Если запустить 50 контейнеров nginx, бинарник `/usr/sbin/nginx` и общие библиотеки будут загружены в оперативную память хоста единожды — все 50 процессов прозрачно читают один и тот же участок RAM.

Экономию места на диске можно увидеть напрямую:

```bash
docker system df -v
```

В колонке `SIZE` для образа — вес слоёв, посчитанный один раз. В колонке `SIZE` для каждого контейнера — вес именно его `upperdir` (writable-слоя), обычно на порядки меньше веса самого образа.

**4. Исчерпание inodes**

`upperdir` живёт на обычной файловой системе хоста (например, ext4). Если приложение в контейнере активно создаёт и удаляет миллионы мелких временных файлов, оно может исчерпать лимит inodes на хосте. В этом случае сервер перестанет работать ("No space left on device"), даже если на диске есть ещё сотни свободных гигабайт.
